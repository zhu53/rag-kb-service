## 参考答案（判档完成前不许展开）

<details>
<summary>第 1 题 · 事务边界（必过）</summary>

**经过谁**：HTTP → TraceMiddleware → 路由 `create_kb` → `get_db`（yield 一个 Session）→
`KBService.create()` → `KBRepository.add()`（只 `session.add`，不碰 commit）→ 回到 service `_commit()` →
`get_db` 的 finally：`session.close()`。

**事务什么时候开始**：autobegin——Session 创建时**没有**事务；第一条 SQL 发出时才隐式开启。
"Session() 到第一条 SQL 之间什么都没发生"（这句是 W4 手画时间轴的原点）。

**flush vs commit**：flush = 把内存里的变更**翻译成 SQL 发给数据库**，但没提交，别人看不见、
回滚就没了；commit = 提交事务，变更对其他连接可见、持久。flush 报成功 ≠ 落库（本周实测）。

**commit 为什么在 service**：事务边界 = 业务原子性的边界。"一次业务操作 = 一个事务"（建库、
或"正文+chunks+doc_count 一起落"），service 才知道一次操作包含几个写点；repo 只认识单表，
把 commit 放 repo，跨两个 repo 的操作就没法在一个事务里（要吗各自 commit 半途失败留半成品，
要吗没人 commit）。**谁拥有"这次操作到哪才算完"的知识，谁握 commit。**

判档要点：只答"分层规范"不到 2 档；答出"跨 repo 原子性"才算真懂。
</details>

<details>
<summary>第 2 题 · 索引（必过）</summary>

**DDL**：

```sql
CREATE INDEX ix_doc_kb_created ON documents (kb_id, created_at);
```

**为什么**：等值列 `kb_id` 放最左（最左前缀），`ORDER BY created_at DESC` 直接沿索引有序读，
免去 filesort；`LIMIT 20` 只需要回表 20 行。不用 `(kb_id, created_at, ...)` 更宽——范围查询
后面的列才失效，这里 kb_id 是等值，created_at 排序能用上。

**EXPLAIN 看什么**：`key` = `ix_doc_kb_created`（真用上了）；`type` ≥ `ref`（不是 ALL）；
`rows` 是预估扫描行数（无索引时=全表，有索引时≈20 上下）；`Extra` 里**不该出现** `Using filesort`
（出现了 = 排序没吃到索引）。

判档要点：说不出"最左前缀"或漏了 filesort 的，索引题不过。
</details>

<details>
<summary>第 3 题 · 并发丢失更新</summary>

**会发生什么**：两个事务都读到 5，各自 +1 写回 6——**丢了 1 次更新**，最终 6 而不是 7
（丢失更新，READ COMMITTED 和 REPEATABLE READ 默认都防不住，因为普通 SELECT 是快照读，不加锁）。

**为什么原子自增能避免**：`UPDATE ... SET doc_count = doc_count + 1` 把"读-算-写"压成
**一条当前读语句**，行锁从事句开始持有到事务结束，第二个事务排队；加法在数据库内部做，
不存在"基于旧快照算出过期值"。

**代价**：写锁持有时间变长（并发写同一行会排队）；以及它只能做"相对量"，要回读新值得再查一次
（或用 `RETURNING`——MySQL 8.4 没有，这是本项目保留"读改写"也要走当前读的原因）。

判档要点：只答"加锁了"不到 2 档；答出"快照读 vs 当前读"才算。
</details>

<details>
<summary>第 4 题 · 迁移</summary>

**为什么不能用 create_all 上线**：`create_all` 只会"从零建出当前结构"，它**不会改已存在的表**——
第二次部署加一列它什么都不做，也没法回滚。上线要的是"从当前版本演进到下一版"，
有历史状态要维护，这才必须 Alembic；测试没历史状态，`create_all` 反而合法（判据：有没有历史状态）。

**1101**：MySQL 不许 TEXT/BLOB 有默认值，`server_default=''` 直接炸；且前面的 DDL 已隐式提交，
库结构和 `alembic_version` 半途脱节。规矩：模型和迁移**两边同步改**，还原靠手工 DROP。

**1553**：先拆单列索引、后建复合索引 → FK 列短暂没有索引覆盖，MySQL 拒绝。
规矩：**先建后拆**，downgrade 同理；autogenerate 生成的 op 顺序不可信，人工重排是必要工序。
</details>

<details>
<summary>第 5 题 · StaticFiles 挂最后</summary>

Starlette 按注册顺序匹配路由。`StaticFiles` 挂在 `"/"` 会**吞掉所有路径**——挂在前面，
`/api/v1/kbs` 这些 API 路由永远轮不到，全部 404（或被当静态文件找）。挂最后 = API 先匹配，
剩下的路径才落到静态文件。**路由顺序就是匹配优先级，这是"隐式契约"里最典型的一条。**
</details>

<details>
<summary>第 6 题 · 门禁判据 / 测试隔离</summary>

**为什么自己算覆盖率**：判据必须来自数据，不能来自工具的口头表态。实测发现两层失效：
`pytest-cov` 的 FAIL 文案只打印、**从不设置退出码**（源码里没有 `exitstatus`）；
`coverage report --fail-under` 按**四舍五入后的整数**比较（94.75 → 95 不触发）。
叠加后果：覆盖率掉到 60% 门禁照样绿。所以 `check.py` 读 `coverage json` 的精确浮点自己比。

**为什么不能自造 app**：`dependency_overrides[get_db]` 是 conftest 的 `db` fixture 打在
**`app` fixture 那个实例**上的；`TestClient(create_app())` new 了新实例，override 不生效 →
走真 `get_db` → 本地有 `.env` 指 MySQL（有表）就绿、CI 没 `.env`（空 sqlite）就
`no such table`。这属于失效三档里的**静默档**（本地全绿、毫无线索）。
修法：用例走 `client` fixture + conftest 把 `DATABASE_URL` 钉成 `sqlite://`（赋值不是 setdefault）。
</details>

## 判卷详单（差距一句 + 追问链 + 重写指引）

### 第 2 题 · 追两个问题，答上来索引题算过

- **追问 2a**：`(kb_id, created_at)` 为什么 kb_id 在前、created_at 在后？把两条列换个位置会怎样？
- **追问 2b**：`EXPLAIN` 的 `Extra` 列出现 `Using filesort` 时，说明什么？这时 `LIMIT 20` 还省事吗？
- **差距一句**：你背下了"看哪三列"，但"索引为什么长这个形状"还没说出来——索引题的验收是**判断**，不是背列名。

### 第 3 题 · 红区，闭卷重写（还债优先）

- **差距一句**："最终 +2"和"select 是当前读"是同一个错误的两面——**你把"并发安全"的功劳记给了自己没验证过的机制**。D4 两天的实验（`see_locks` / `read_deadlock` 探针）就是为了推翻这个直觉的。
- **闭卷重写指引**：纸上重画"两个事务并发改 doc_count"时序图（D4·上 的原图），标出三行：
  ① T1 SELECT 读到 5（快照读，不加锁）② T2 SELECT 也读到 5 ③ T1 写 6 提交、T2 写 6 提交——最终值是多少？
  写完对着 `D4·上-事务边界与丢失更新-教材.md` 的实测记录核对。
- **一句话锚点**（重写时先写这句）：**普通 SELECT 读的是快照；只有 UPDATE/DELETE/`FOR UPDATE` 才是当前读。丢失更新 = 两个事务基于同一条快照各自算出"过期的新值"。**

### 第 4 题 · 1553 纠正（一句话记住）

> 外键列**必须始终有索引覆盖**。错的做法是"先解决外键依赖"（外键不能删）；
> 对的做法是**先建复合索引、再拆单列索引**——先建后拆，downgrade 同理，autogenerate 不排这个序。
