## 1. 交付物 1：没索引 = 锁全表

| 场景 | `documents` 上的锁对象数 | 主要 `LOCK_MODE` |
|---|---|---|
| `WHERE status='ready'`，status **无**索引 | **5040**（5039 RECORD + 1 IX） | `X` 5039 = 5000 个临键锁 + 39 个页尾 supremum，全在 PRIMARY |
| 建索引后普通 UPDATE（**优化器没走它**） | 5040（同上，一模一样） | 同上 —— 全表扫 |
| `FORCE INDEX (ix_documents_status)` | **9014** | 二级索引 `X` 4513（4500 临键 + 13 supremum）+ 聚簇 `X,REC_NOT_GAP` 4500 |

结论（为什么差这么多）：

> ① 锁的是**扫描过的**，不是命中的：命中 4500，无索引时 5000 行全锁（含 500 个 pending/failed 误伤）+ 每页页尾 39 个 supremum。5000 行 ≈ 39 页 ≈ 128 行/页（行约 130B）。
> ② 建了索引 ≠ 走了索引：90% 选择性下优化器**执行时**放弃新索引。铁证 `Handler_read_rnd_next=5001 / Handler_read_next=0`（全表扫）；而 `EXPLAIN UPDATE` 显示 `type=index` —— **EXPLAIN 是意图，Handler 是事实，两者可以不一致**（且该 EXPLAIN 的 `key_len=128` 与 status 单列应得的 82 自相矛盾）。
> ③ 真走索引后锁翻倍，但**形状变好**：聚簇从"带缝临键"变成"纯记录"，防插入交给二级索引的缝；supremum 39→13（二级索引行窄 52B，页更宽）。
> ④ 杀伤半径缩小：无索引时 B 改**任意一行**都被误伤；有索引后改 pending 秒过、改 ready 报 1205。

**副作用记录**：会话 B 的 `UPDATE ... WHERE id=?` 卡了 **28.2s** 后成功返回（1 行受影响）——A `ROLLBACK` 放行，不是 1205。B 的锁请求本身也占一个对象（挂起时总数 5042 = 5039 + 1 挂起 + 2 IX）；B 走主键等值只要 `X,REC_NOT_GAP` 一个锁，对比 A 的 5039。

## 2. 交付物 2：间隙锁挡住 INSERT

| 隔离级别 | `SELECT ... WHERE id > 'ffff…' FOR UPDATE` 的锁 | 会话 B 的 INSERT 表现 |
|---|---|---|
| REPEATABLE-READ | **0 行命中仍有 1 个记录锁**：`PRIMARY / X / supremum pseudo-record`（+1 个表级 IX） | 卡住；A `ROLLBACK` 后放行，B 等 **4.426s** 成功（用户实测）。探针复跑对照：等 **3.024s** 后 `1205 Lock wait timeout` |
| READ COMMITTED | **只剩表级 IX，0 个记录锁** —— RC 不加任何缝锁 | 秒过：用户实测插入成功；探针复跑 **0.399s** 成功 |

抄一条 RR 下的 `supremum` 记录原文（`see_locks.py` 输出）：

```
PRIMARY                   X                       supremum pseudo-record
```

卡住那一刻的等待关系（`data_lock_waits`）：

```
trx 6708  等  trx 6706  要 X,INSERT_INTENTION @ PRIMARY  LOCK_DATA=supremum pseudo-record
```

结论：

> ① **0 行命中 ≠ 没锁**。`id > 'ffff…'` 一行都不返回，但 RR 下 InnoDB 把"最后一条记录之后到 +∞"的缝锁住了（挂 supremum 虚拟记录上），防的就是往表尾插新行的幻读。supremum 是虚拟记录、锁不了它本身，所以 `LOCK_MODE` 是裸 `X`（不带 GAP 标志）——这是昨天"`X,GAP` 锁右端点左边"规则的表尾特例。
> ② INSERT 被挡时请求的锁模式是 **`X,INSERT_INTENTION`（插入意向锁）**——也是缝锁的一种，语义是"我打算往这条缝里塞新值"。它和缝锁冲突（所以被挡），但**多个插入意向锁互不冲突**：缝没被占时大家一起插，冲突交给唯一约束。
> ③ **幻读防线只存在于 RR**。RC 下 A 只拿了一个表级 IX，一条记录锁都没有——同一个 SELECT，换隔离级别连锁的形状都变了。RC 不防幻读不是"检测不到"，是**压根没设岗**。

**遗留小坑（探针）**：`SET SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ` 必须写**空格**，带连字符报 1064；但 `@@transaction_isolation` 的**值**显示为 `REPEATABLE-READ`（连字符）——语句和值两种写法。

## 3. 交付物 3：死锁复现与日志解读

| 项 | 内容 |
|---|---|
| 会话 A 的 SQL 顺序 | `BEGIN` → `UPDATE … WHERE id='aaaa…'`（k1，成功）→ `UPDATE … WHERE id='kb000001…'`（k2，**卡住等 B**）→ 死锁解除后 `ROLLBACK` |
| 会话 B 的 SQL 顺序 | `BEGIN` → `UPDATE … WHERE id='kb000001…'`（k2，成功）→ `UPDATE … WHERE id='aaaa…'`（k1）→ **发出即报 1213** |
| 谁收到 1213 | **B**（日志 `*** (2)`，trx 6729），InnoDB 自动回滚它；A 卡住的语句立刻放行 |
| `(1) HOLDS` 的 asc 值 | `asc aaaa…` = k1 |
| `(1) WAITING FOR` 的 asc 值 | `asc kb000001…` = k2 |
| `(2) HOLDS` 的 asc 值 | `asc kb000001…` = k2 |
| `(2) WAITING FOR` 的 asc 值 | `asc aaaa…` = k1 |
| `WE ROLL BACK TRANSACTION (?)` | **(2)** = B |

死锁时间 `2026-11-17 18:39:07`（上一份 LATEST 是 2026-11-16 16:07 探针自动跑留下的——InnoDB 只保留最近一次，实验前特意先读了旧日志做对照）。日志附 `/* ApplicationName=PyCharm */` 可定位事故 SQL 来源。

**读法**：日志看着吓人，每个事务只看两样——HOLDS（手里攥着哪行，`asc` 列就是主键原值）和 WAITING FOR（在等哪行）。A 攥 k1 等 k2、B 攥 k2 等 k1，两个 `waiting` 一连就是环。

**如果这是线上代码，错在哪、怎么改**：

> 错在**两个事务以相反顺序拿同样的两把锁**。两个修法：① **统一加锁顺序**——应用层先把要改的 id 按值排序，再逐个更新，环就永远凑不成；② **缩短事务**——把"读出来改回去"合成单条原子语句 `SET doc_count = doc_count + 1`，锁拿了立刻随提交释放，不给对方凑环的时间窗。交付物 4 的 `incr_doc_count` 用的是 ②。
>
> 附：为什么回滚 B 不是 A——InnoDB 挑代价最小的受害者（undo log entries 最少的），两个事务各改 1 行权重相同，于是回滚**让环闭合的那个**。若挑了 A，B 的等待会被放行、正常执行成功。1213 是事件驱动的秒级检测，与 `innodb_lock_wait_timeout`（1205 超时）是两套机制：**1213 = 环成立谁也别想动，主动拆局；1205 = 普通排队等到超时**。第一次手工尝试没成环（顺序滑了）只拿到旧日志，恰好事实验证了这点。

## 4. 交付物 4：`incr_doc_count` 原子自增

| 项 | 内容 |
|---|---|
| SQL 条数（测试实测） | 改前 **2 条**（SELECT + UPDATE，读-改-写）→ 改后 **1 条**（`test_incr_issues_single_sql`：`sql_log` 恰好 1 条且以 UPDATE 开头） |
| 20 次自增最终值 | **20**（`test_twenty_sequential_increments_reach_twenty`；真并发验证留 MySQL 集成测试——SQLite 文件库多线程锁库，测不了） |
| kb 不存在时抛的异常 | `NotFoundError`（靠 `rowcount == 0` 判断，不发额外 SELECT） |
| `scripts/check.py` 结果 | passed 78 / 覆盖率 96.82% / mypy 全绿 → **门禁全绿** |

实现（用户手写，`kb_repo.py:82`）：session 分支照 `create()` 的过渡态模式，单条 `update(KnowledgeBase).where(...).values(doc_count=KnowledgeBase.doc_count + delta)`。

**过程中撞出的三个真实知识点**：
1. **mypy `rowcount` 报错**：`session.execute()` 静态类型是 `Result`，`rowcount` 在子类 `CursorResult` 上——运行时对、类型标注保守，用 `cast("CursorResult[Any]", ...)` 解决。
2. **教材 §11.2 的 `-> int` 是坑**：MySQL 8 不支持 `UPDATE ... RETURNING`，要返回自增后的值只能再发一条 SELECT（SQL 变 2 条，违背原子自增省往返的初衷）或用 SQLite 的方言扩展（上生产就炸）。按 protocol 的 `-> None` 写是对的，教材已修。
3. **docstring 位置**：写在 `else:` 块里是孤立字符串表达式，不是 docstring；必须紧跟 `def`。另：execute 后的 `flush()` 是多余的——Core update 语句在 execute 时已发 SQL，flush 管的是 ORM 积攒的变更。
