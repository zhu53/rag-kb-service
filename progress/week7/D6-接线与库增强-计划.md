# D6 计划：接线范围与库增强（2026-11-19，3h）

> 触发：11-18 晚用户问「2h 够吗，我想要这个项目最后能打通展示，而且目前数据库设计也有点简陋，担心功能太简单」。
> 结论：**2h 不够**（接线本身 2.5h 起，还不含集成测试）。目标从「变异体验收」改成「**打通 + 可演示**」，变异体挪 W8 首日。

---

## 一、2h 到底够不够：给个实数

| 步骤 | 内容 | 估时 | 说明 |
|---|---|---|---|
| 1 | 迁移 #3：`documents.content` + 唯一约束 + 2 个复合索引 + `chunks(doc_id, seq)` 唯一 | 30min | 迁移已做过两条，这次是"用起来" |
| 2 | KB 链接线：5 个 repo 方法切 DB + service 持 session + handler `Depends(get_db)` + commit | 50min | 最容易卡在 `select()` 语法和分页 |
| 3 | Doc 链接线：`doc_repo` 切 DB + 正文从 DB 读 + `_parse_sync` 把 chunks 写库 | 50min | 真正让"文档"落地的一步 |
| 4 | 集成测试：独立 `kb_test` 库，断言"另开 session 查得到"（KB 1 例 + doc 1 例） | 30min | 这一步才是能抓「漏 commit」的靶子 |
| 5 | chat 从 `chunks` 检索（替换扫 `documents.content`） | 20min | 可顺延，不影响"数据不丢" |
| | **合计** | **3h** | 不含变异体 |

**所以：**
- **2h** = 只能做 1+2+4（KB 单链），doc 仍走内存 → 演示到"上传文档"就断，重启丢
- **3h** = 1~4 全做，能演示"重启数据还在" → 这就是你要的"打通"
- **4h+** = 再加 5（chunks 检索）+ 变异体闭环

**定案：D6 做 1~4（3h）；第 5 步和变异体挪 W8 首日。**

## 二、数据库"简陋"体检（标准：面试第二层能不能扛）

先说结论：**三张表不是问题**。面试官不会因为表少扣分，会因为"字段/约束/索引为什么这么设"答不上来扣分。但现在有 **4 处是真缺陷**（不是简化），追问一层就露。

| # | 缺口 | 不做会怎样 | 严重度 | 落在哪 |
|---|---|---|---|---|
| 1 | `documents` **没有正文列**，正文只在内存 `DocRow["content"]` | 重启全丢；`to_row()` 里 `content=""` 是硬写死的空串，任何"读正文"的下游都拿不到 | 🔴 致命 | **D6 迁移 #3** |
| 2 | **没有任何唯一约束**，但 API 文档承诺"名称不可重复" | 文档承诺 vs 代码保证裂开；并发下必然出现重名；现在内存实现其实也没校验 | 🔴 致命 | **D6 迁移 #3**：`UNIQUE(owner_id, name)` |
| 3 | **没有 `users` 表**，`owner_id` 是裸 UUID | W8 多租户/鉴权没有落点；`owner_id` 无法做外键，脏数据删不掉 | 🔴 致命（W8 暴露） | W8 第 1 天 |
| 4 | `chunks` 没有 **`(doc_id, seq)` 唯一约束**，`_parse_sync` 也从不写 chunks | 表建了但永远是空的；重复写入无法防；向量检索周要返工 | 🔴 致命（W12 暴露） | **D6 迁移 #3 + 步骤 3** |
| 5 | 列表查询缺复合索引：`(owner_id, created_at)`、`(kb_id, created_at)` | 分页按 `created_at` 排序会 filesort；数据一多 p99 抖——D3 学的"复合索引最左前缀"没有落地实例 | 🟡 可讲但丢分 | **D6 迁移 #3** |
| 6 | `status` 无 CHECK/ENUM，无状态机约束 | `'ready'`/`'pending'`/`'failed'` 靠代码自觉；写错一个字符串无人报警 | 🟡 | W8 或 D7 |
| 7 | 无软删除 `deleted_at` | 物理删除，回收站/审计/误删恢复都做不了 | 🟡 | W8 |
| 8 | 时间默认值在 Python 侧（`datetime.now`） | 多实例时钟漂移，同一秒的数据顺序错乱；DB 侧 `CURRENT_TIMESTAMP` 更稳 | 🟢 | 以后 |
| 9 | 无 `version` 列 | D4 讲的乐观锁没有落点，"你项目里用过乐观锁吗"只能空谈 | 🟡 | W9 |
| 10 | 无 `queries`/`retrieval_logs` 表 | W16 评测 Recall@K / 忠实度 没有数据源；线上"为什么答错"查不了 | 🟡 | W16 |

**D6 只做 1/2/4/5（一次迁移，全是 `op.create_index` / `op.add_column` / `op.create_unique_constraint`），其余按周次落。** 一次迁移只做一件事的原则要让步于"同一批结构变更"——但**每条 op 都要在实测记录里写一句为什么**。

## 三、D6 五个步骤（规格，不给代码）

### 步骤 1：迁移 #3（30min）

`alembic revision --autogenerate -m "doc content, unique kb name, list indexes"`，先改模型再生成，然后**人工读**（今晚刚学的：autogenerate 是草稿）。

要生成的 op：
- `add_column("documents", sa.Column("content", sa.Text(), nullable=False, server_default=""))`
- `create_unique_constraint("uq_kb_owner_name", "knowledge_bases", ["owner_id", "name"])`
- `create_index("ix_kb_owner_created", "knowledge_bases", ["owner_id", "created_at"])`
- `create_index("ix_doc_kb_created", "documents", ["kb_id", "created_at"])`
- `create_unique_constraint("uq_chunk_doc_seq", "chunks", ["doc_id", "seq"])`

验收：`upgrade head` → `alembic check` 无 pending → `downgrade -1` 能退 → 再 `upgrade head`。
注意：`server_default=""` 是给已有行用的，模型里别留 `server_default`（否则新写入也带默认值，`alembic check` 会报 diff）。

### 步骤 2：KB 链接线（50min）

- `KBService.__init__(self, repo: KBRepo)` 必传；**删掉 `session is None` 的内存分支**
- `KBRepository.get/list_by_owner/count_by_owner/update/delete` 用 `select()` / `update()` / `delete()`
- handler：`session: Session = Depends(get_db)` → `KBService(KBRepository(session))`
- 事务边界在 service：`create` 末尾 `session.commit()`；异常交给 `get_db` 的 rollback
- `KBOut.model_validate` 用 `from_attributes`

坑预告：`store.kbs` 删掉后，`tests/conftest.py` 的 `_clear_store` 会 import 失败；API 测试会全部变成"要真库"。**先把集成测试跑起来，再回头改老测试**（老测试可以改成用 fake repo 注入，保持单测不依赖 DB）。

### 步骤 3：Doc 链接线（50min）

- `doc_repo` 五个方法切 DB；`create` 要写 `content`；`to_row` 从 DB 字段读，不再返回 `""`
- `_parse_sync`：`split_text` 之后**批量插入 chunks**（`session.add_all` + 一次 flush），再 `update_status(ready, chunk_count)`
- 注意顺序：`incr_doc_count` 与 chunks 插入在**同一个事务**里，任一步失败要整体回滚——这正是"事务边界在 service"的价值

### 步骤 4：集成测试（30min）

新文件 `tests/test_db_integration.py`，`kb_test` 库（与 `kb_dev` 分开，防止测试清表把实验数据洗掉）：
- fixture：`create_engine(settings.database_url.replace("/kb_dev", "/kb_test"))`，`Base.metadata.create_all` 一次，每例前 `DELETE FROM` 三表
- 例 1：`POST /kbs` → 新 session `SELECT` 到 1 行
- 例 2：`POST /kbs/{id}/documents` → `documents` 1 行且 `content` 非空、`chunks` N 行
- 标记 `@pytest.mark.integration`，在 `check.py` 里**单独一段**跑（不混进快速门禁）

### 步骤 5（顺延）：chat 从 chunks 检索

`RagService._retrieve` 改成按 `kb_id → documents → chunks` 取块，`ChatSource.chunk_index = seq`。这样"检索到的是片段"这件事在数据上成立，W12 换向量检索时只改打分不改结构。

## 四、演示剧本（打通的标准，写进 README 的 Demo 段）

1. `POST /api/v1/kbs` → 201（`SELECT` 有行）
2. `POST /api/v1/kbs/{id}/documents`（传 1200 字文本）→ 201，`status` 从 `pending` 到 `ready`，`chunk_count=3`
3. `GET /api/v1/kbs/{id}/documents?page=1&size=10` → `total=1`（走 `(kb_id, created_at)` 索引，贴 `EXPLAIN` 截图）
4. `POST /api/v1/chat` 提问 → `sources` 带出命中片段（不是整篇）
5. **重启 uvicorn** → 再跑一次第 3 步，数据还在 ← 这条就是"打通"的证明
6. `EXPLAIN` 一条列表查询 → `type=ref`、`key=ix_doc_kb_created`、`Extra` 无 `Using filesort`（D3 的成果变成 demo 的一部分）

**"功能太简单"的真解**不在表数量，在于这条剧本能连着 6 步跑完 + 每一步都能说出一个决策。面试讲 5 分钟的三个点：为什么事务边界在 service（不是 repo、也不是 `get_db`）、为什么单列 `status` 索引是废的而 `(kb_id, created_at)` 才对、为什么迁移要 forward fix 不能改历史。
