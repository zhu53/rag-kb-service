## §零 主线：索引的一生（A）

**一句话分界线：建索引时决定「这棵树长什么样」，查询时优化器决定「走不走这棵树」。**

一整条时间轴，全篇的每一节都钉在其中一个刻度上：

```
【建索引那一刻】
  CREATE INDEX idx ON documents (kb_id, status)
      ↓ 树的结构在这里被定死：先按 kb_id 排，kb_id 相同再按 status 排
      ↓ 这个顺序决定了日后哪些查询能用它、哪些用不上（§六）

【写入那一刻】
  INSERT / UPDATE / DELETE
      ↓ 每改一行，所有相关索引都要跟着改（所以索引不是免费的，§八）

【查询那一刻】
  SELECT ... WHERE kb_id = ? AND status = ?
      ↓ ① 解析 SQL
      ↓ ② 优化器估算：「走索引 + 回表」和「直接全表扫」哪个便宜（§七、§八）
      ↓ ③ 选定访问方式（EXPLAIN 的 type / key 就是这一步的结果，§九）
      ↓ ④ 按索引定位到主键
      ↓ ⑤ 拿主键回聚簇索引取整行 —— 这就是「回表」（§四、§五）
      ↓ ⑥ 返回
```

**今天最容易混的一件事**：EXPLAIN 里看到"没用索引"，有两种完全不同的原因——

| 原因 | 意思 | 怎么办 |
|---|---|---|
| **写法上就用不上** | 索引按 `title` 排好了序，你写 `LEFT(title,3)=?`，排序信息被函数毁掉，无从下手 | 改写法（§七） |
| **能用，但优化器觉得不划算** | 这条件命中 67% 的行，走索引要回表 3 万次，不如直接扫全表 | 认了，或改索引设计（§八） |

本篇会给你两组实测，证明第二种情况真实存在、而且很常见。**很多面经把这两种混成一种，说"`!=` 一定失效""`LIKE '%x'` 一定失效"——那是把结果当原因。**

## §零·二 全篇其实是一条因果链（B，整体看不懂时只看这一节）

上面那条时间轴讲的是"索引的一生"三个时刻，但那是**流程**，不是**因果**。
真正的因果是：**每一节都在回答上一节留下的那个麻烦。**

八连问，按顺序看：

| # | 上一节留下了什么麻烦 | 这一节怎么解决 | 在哪节 |
|---|---|---|---|
| 1 | 我要找一行，数据库只能从头翻到尾 | 给它建一份"排好序的目录" | §一 |
| 2 | 目录也要存磁盘上，它该长什么样？内存里的二叉树搬过来行不行？ | 不行：扇出只有 2，2000 万行要 25 层 = 25 次磁盘 IO。把节点放大到一页，扇出变 1170，3 层就够 | §三 |
| 3 | B+ 树的叶子里到底放什么？ | 主键索引放**整行**（聚簇索引）；其他索引只放**索引列 + 主键**（二级索引，一页能塞更多条目） | §四 |
| 4 | 二级索引只存主键，可我要的是 `title`，它不在里面 | **回表**：拿主键再查一次聚簇索引 | §四、§五 |
| 5 | 每行都回表一次，5000 行就是 5000 次随机 IO，太贵 | **覆盖索引**：把要查的列也放进索引，`Extra` 显示 `Using index`，一次都不用回 | §五 |
| 6 | 两个条件 `kb_id=? AND status=?`，难道建两个索引？ | **联合索引**：一个顶三个，但只能从最左列往右用 | §六 |
| 7 | 那把所有列都建上？为什么 `status` 建了也不用？ | **区分度**：只有 3 个不同值的列，走索引反而更慢 | §八 |
| 8 | 我明明建了索引，`EXPLAIN` 里 `key` 却是 `NULL` | 分清两种：**写法上用不上**（函数包列、前缀通配）vs **优化器觉得不划算**（命中比例太高） | §七、§九 |

**一句话串起来**：

> 为了不逐行翻（1），造一个目录（2）；目录里放整行太占地方，所以二级索引只放主键（3），于是要回表（4）；回表太贵就覆盖（5）；多条件用一个联合索引顶（6）；但不是所有列都值得进目录（7）；最后，索引建了也可能不被选（8）。

## §零·五 词表（A）

| 词 | 一句人话 | 没有它会怎样 |
|---|---|---|
| **索引（index）** | 数据库为某一列（或几列）单独维护的一份**排好序的目录**，目录里记着"这个值在哪一行" | 找一行要翻遍整张表 |
| **B+ 树** | 索引的数据结构：多层"目录的目录"，只有最底层的叶子存实际条目，叶子之间还用链表串起来 | 不理解它，就记不住"为什么是最左前缀""为什么范围查询快" |
| **页（page）** | InnoDB 读写磁盘的最小单位，默认 **16KB**。数据库不是一行一行读，是一页一页读 | 不理解页，就理解不了"树高 3 层能存两千万行"这个反直觉结论 |
| **聚簇索引（clustered index）** | 就是主键索引，它的叶子节点存的是**整行数据**。一张表只有一个 | 会以为"主键只是个 id"，不知道它决定了数据的物理组织 |
| **二级索引（secondary index）** | 除主键外的其他索引，叶子只存**索引列 + 主键值**，不存整行 | 会不理解为什么要"回表" |
| **回表（bookmark lookup）** | 用二级索引查到主键后，再拿主键去聚簇索引取整行。**多一次查找** | 会写出"索引明明建了还是很慢"的代码 |
| **覆盖索引（covering index）** | 查询要的列**全在索引里**，不用回表。EXPLAIN 的 `Extra` 显示 `Using index` | 会错过最容易拿的性能提升 |
| **最左前缀（leftmost prefix）** | 复合索引 `(a,b,c)` 只能从最左边的列开始用，等价于 `(a)`、`(a,b)`、`(a,b,c)` 三个索引 | 会建一堆用不上的索引 |
| **区分度（cardinality / selectivity）** | 这一列有多少个不同的值。`status` 只有 3 个值 → 区分度极低 | 会给 `status`、`is_deleted` 这种列单独建索引，白占空间还拖慢写入 |
| **执行计划（execution plan）** | 优化器决定"怎么查"的结果，用 `EXPLAIN` 看 | 只能靠猜和试 |
| **优化器（optimizer）** | 数据库里负责"选哪条路走"的组件，靠**成本估算**做决定，不是靠规则 | 会以为"我建了索引它就一定用" |

## §一 没有索引时，数据库怎么找一行（A）

### 1.1 最朴素的做法：从头翻到尾

你要执行：

```sql
SELECT * FROM documents WHERE kb_id = 'kb-007';
```

没有索引，InnoDB 只能做一件事：**从表的第一页读到最后一页，逐行判断 `kb_id` 是不是 `'kb-007'`**。这叫**全表扫描**（full table scan）。

实测（`probe_index.sql` 实验 A1，5 万行表）：

```
type=ALL | key=NULL | rows=50000 | Extra=Using where
```

`type=ALL` 就是"全表扫"，`rows=50000` 是优化器估算要读的行数。

### 1.2 为什么这在线上是灾难

三个叠加的代价：

1. **磁盘 IO**：5 万行可能几百个页，每页一次 IO。机械盘一次随机 IO 约 10ms，几百个页就是几秒。
2. **CPU**：每一行都要把 `kb_id` 取出来比较，5 万次字符串比较。
3. **内存**：扫过的页会挤掉缓存里更有用的页（Buffer Pool 有限），**拖慢所有人**，不只是你这条查询。

第 3 条最隐蔽，也是面试能加分的地方：**慢查询的危害不止它自己慢，它还会污染缓存，把别人也拖慢。**

### 1.3 索引要解决的正是这个

给 `kb_id` 建索引：

```sql
CREATE INDEX idx_kb_id ON documents (kb_id);
```

再看看同一句查询（实测 A2）：

```
type=ref | key=idx_kb_id | rows=1000 | Extra=Using index condition
```

`type` 从 `ALL` 变成 `ref`，`rows` 从 50000 变成 1000。**这就是索引的全部意义：把"翻遍全表"变成"按目录直达"。**

> 记住这对数字：**50000 → 1000**。这是本篇第一个"可复现指标"，比任何百分比都可信。

## §三 B+ 树为什么快（A）

### 3.1 先看一个数字，它决定了整个设计

InnoDB 一页 **16KB**。一棵 B+ 树分三层（根 / 中间 / 叶子）：

> **先钉死一个前提：B+ 树的一个节点，正好占一页（16KB）。**
> 这一句不钉死，后面"树高 = IO 次数"就是空话。
> 为什么必须对齐一页？① 页是 InnoDB 读写磁盘的最小单位，读一个节点就是读一页；
> ② 节点做成 2 页 → 读一个节点要 2 次 IO，扇出翻倍、IO 也翻倍，白折腾；
> ③ 节点做成半页 → 扇出白砍一半、树变高。**"一页一个节点"是唯一不浪费的对齐点。**
>
> 但要注意两层不是一回事：**节点数 = 页读取次数 ≥ 磁盘 IO 次数**。
> 页如果在 Buffer Pool 里，页读取照常发生，但一次磁盘都不碰。

- 非叶子节点只存「key + 指向下一页的指针」，一个 bigint 主键 8 字节 + 指针 6 字节 = 14 字节 → **一页能放约 1170 个**
- 叶子节点存实际数据，假设一行 1KB → **一页放 16 行**

那么三层能存多少行？

```
1170 × 1170 × 16 ≈ 2190 万行
```

**两千万行，三次页读取就能定位到。** 根节点和中间层几乎常驻内存（Buffer Pool），所以真实磁盘 IO 通常只有 1 次。

**为什么能常驻？不是因为"它们重要"，是因为它们小到装得下**——这条比"三层"本身更值钱：

```
非叶子页总数 = 1（根） + 1170（中间层） = 1171 页
            = 1171 × 16KB ≈ 18.7 MB
```

MySQL 8 `innodb_buffer_pool_size` 默认 **128MB**。18.7MB 的目录，随便就全塞进去了。
塞进去之后，"三次页读取"里的**前两次根本不碰磁盘**，是内存读。

对照一下其他结构做目录有多大：

| 结构 | 目录需要多少个节点 | 大约占多少内存 | 能不能全进 Buffer Pool |
|---|---|---|---|
| B+ 树（扇出 1170） | 1171 页 | ~19 MB | ✅ 轻松 |
| 红黑树（扇出 2，2000 万行） | 约 2000 万个节点 × 24 字节 | ~480 MB | ❌ 装不下，只能靠 OS 页缓存，命中率不可控 |

所以树高矮的真正收益是**两条**，不是一条：
**① 路径短（要读的页少）；② 目录本身小到能整体缓存在内存里，让"路径短"从"少读几次盘"变成"几乎不读盘"。**

这就是 B+ 树的全部卖点：**用很矮的树，把随机 IO 压到个位数**。

### 3.2 为什么不用别的东西

面试爱问"为什么是 B+ 树不是别的"，标准答案是**三个对比**：

| 结构 | 为什么不行 |
|---|---|
| **二叉搜索树 / 红黑树** | 每个节点只有 2 个孩子，扇出 = 2。2000 万行需要 **25 层**（`2^24 = 1677 万 < 2000 万 < 2^25`）= 最多 25 次磁盘 IO。B+ 树把"一个节点"放大到一页，扇出从 2 变成 1170，树高降到 3 |
| **哈希索引** | `WHERE id = 5` 是 O(1)，但 `WHERE id > 5`、`ORDER BY id`、`WHERE id BETWEEN 1 AND 9` 全部无能为力——**哈希把顺序信息丢了**。而且哈希冲突多了要退化成链表 |
| **跳表（Redis 用的）** | 内存里很好（无磁盘 IO，指针跳转便宜），但磁盘上一次跳转就是一次随机 IO，层数一多就崩 |

一句话总结：**B+ 树的形状是"磁盘 IO 次数"逼出来的，不是"算法优美"选出来的。**

### 3.3 叶子链表：范围查询的底座

B+ 树的叶子节点之间用**双向链表**串起来。所以：

```sql
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
ORDER BY created_at
```

找到起点后，**顺着叶子链表往后走**就行——不需要回到根节点重新找。这就是"范围查询快"和"`ORDER BY` 能免排序"的物理原因（§六会实测 `Backward index scan`）。

### 3.4 一个 L 级知识点：为什么 B+ 树不把数据放非叶子节点

B 树（不是 B+）的非叶子节点也存数据，所以同样一页能放的 key 更少 → 树更高。B+ 树把所有数据赶到叶子，非叶子只当目录，把扇出做到最大。**知道这个差别就行，面试问"B 树和 B+ 树区别"能答这句就够。**

## §四 聚簇索引与二级索引（A）

### 4.1 聚簇索引：主键就是数据的存放顺序

InnoDB 里，**表的数据本身就组织在主键这棵 B+ 树上**——叶子节点存的是整行。

所以：

- 一张表**只有一个**聚簇索引（就是主键）
- 按主键查，找到叶子就拿到整行了，**不需要回表**
- 主键不是自增的（比如 UUID），插入位置随机 → 页分裂 → 性能下降。这是 D1 讲 UUID 主键时的另一半理由

### 4.2 二级索引：叶子只存主键

给 `kb_id` 建的索引是二级索引，它的叶子长这样：

```
(kb-007, 0x0000000000000012)   ← 索引列值 + 主键值
(kb-007, 0x0000000000000035)
(kb-008, 0x0000000000000007)
```

注意：**它不存 `title`、不存 `status`、不存 `created_at`**，只存索引列和主键。

于是查 `SELECT * FROM documents WHERE kb_id = 'kb-007'` 要两步：

1. 在 `idx_kb_id` 里找到所有 `kb-007` 的条目，拿到 1000 个主键
2. 拿这 1000 个主键，**逐个回聚簇索引取整行**

第 2 步就是**回表**。1000 行 = 1000 次额外的树查找（虽然大多命中缓存）。

> **这就是为什么"索引不是越多越好"的第一层原因**：每条二级索引都要在写入时维护，而且查询时可能带来回表。
> 第二层原因在 §八。

## §五 回表与覆盖索引（A，本篇最有说服力的一组数据）

### 5.1 同一句查询，只差一列，快 5 倍

实测（`probe_index3.sql`，5 万行，索引 `(kb_id, status)`）：

| 查询 | 执行计划关键行 | 实际耗时 |
|---|---|---|
| `SELECT kb_id, status ...` | `Covering index lookup ... (actual time=0.0342..0.26 rows=1000)` | **0.347 ms** |
| `SELECT kb_id, status, title ...` | `Index lookup ... with index condition ... (actual time=0.241..1.84 rows=1000)` | **1.84 ms** |

**同样命中 1000 行，差 5.3 倍。** 差别只有一个字：`title` 不在索引里，所以每次都要回表。

### 5.2 怎么一眼看出走没走覆盖索引

看 `EXPLAIN` 的 `Extra` 列：

| Extra 里出现 | 含义 |
|---|---|
| `Using index` | **覆盖索引**，没回表 |
| `Using index condition` | 用了索引下推（ICP），**仍然回表**（只是把部分过滤下推到引擎层） |
| `Using where` | 服务器层在过滤，通常意味着索引没覆盖全部条件 |
| `Using filesort` | 额外排序，索引没帮上 `ORDER BY` 的忙 |
| `Using temporary` | 用了临时表，通常是 `GROUP BY` / `DISTINCT` 没走索引 |

**`Using index` 和 `Using index condition` 只差一个词，含义完全不同**——前者不回表，后者回表。这是本篇最容易看错的地方，面试也会问。

### 5.3 覆盖索引在项目里怎么用

列表页最常见的查询是"分页取某知识库的文档，只要 id 和标题"：

```sql
SELECT id, title FROM documents WHERE kb_id = ? ORDER BY created_at DESC LIMIT 20;
```

如果索引是 `(kb_id, created_at)`，那 `id`（主键，二级索引里自带）和 `created_at` 都在索引里，**只有 `title` 要回表**。所以：

- 想全覆盖 → 索引建成 `(kb_id, created_at, title)`，20 行全部从索引拿
- 不想索引太宽 → 接受 20 次回表（只有 20 行，代价很小）

**判断标准是"回表次数"**：分页 20 行 → 20 次回表，可以接受；导出全表 → 几万次回表，必须覆盖。

## §六 复合索引与最左前缀（A，面试最高频）

### 6.1 复合索引的顺序是有语义的

```sql
CREATE INDEX idx_kb_created ON documents (kb_id, created_at);
```

这棵树的排序规则是：**先按 `kb_id` 排，`kb_id` 相同的再按 `created_at` 排**。

就像电话簿先按姓排、同姓再按名排。所以：

```sql
-- 能用：先定位 kb_id，内部已经按 created_at 排好了
WHERE kb_id = 'kb-007' ORDER BY created_at DESC
```

实测（B1）：

```
type=ref | key=idx_kb_created | rows=1000 | Extra=Using where; Backward index scan
```

**注意 `Backward index scan`，没有 `Using filesort`**——排序被索引免费解决了，而且因为你要 `DESC`，它从叶子链表**倒着走**（MySQL 8.0 才支持的能力）。如果建的是 `(kb_id, created_at DESC)` 的降序索引，就会变成正向扫。

### 6.2 最左前缀：等价于三个索引

`(a, b, c)` 能被这些查询用上：

| WHERE 条件 | 能用吗 | 用到几列 |
|---|---|---|
| `a = ?` | ✅ | 1 列 |
| `a = ? AND b = ?` | ✅ | 2 列 |
| `a = ? AND b = ? AND c = ?` | ✅ | 3 列 |
| `a = ? AND c = ?` | ✅（部分） | 只用 `a`，`c` 用不上索引定位 |
| `b = ?` | ❌ | 0 列——**跳过最左列，整棵树无从下手** |
| `c = ?` | ❌ | 0 列 |

实测对照（B3 vs B4）：

```
B3: WHERE created_at > ?        → type=ALL, rows=49677   ← 跳过 kb_id，索引废了
B4: 给 created_at 单独建索引    → type=range, rows=5360  ← 建了就走了
```

**"索引失效"的本质**：树的排序信息从第一列开始，你不给第一列，就没法定位起点。**不是数据库小气，是物理上做不到。**

### 6.3 顺序怎么定：三条规则

1. **等值条件放前面，范围条件放后面**。因为范围条件一旦用上，它后面的列就没法再用索引定位了。
   - `WHERE kb_id = ? AND created_at > ?` → 建 `(kb_id, created_at)` ✅
   - 反过来建 `(created_at, kb_id)` 就浪费了 `kb_id` 的等值能力
2. **区分度高的列放前面**（§八）。`kb_id` 有 50 个值，`status` 有 3 个值 → `(kb_id, status)` 比 `(status, kb_id)` 好。
3. **要考虑 `ORDER BY` / `GROUP BY`**。索引的顺序如果能直接满足排序，就省掉一次 `filesort`（§6.1 的实测就是这个）。

### 6.4 一个实测细节：优化器可能选"更窄"的索引

B2 那个实验：表上同时有 `idx_kb_id(kb_id)` 和 `idx_kb_created(kb_id, created_at)`，查询只有 `WHERE kb_id = ?`：

```
possible_keys=idx_kb_id,idx_kb_created | key=idx_kb_id | key_len=144
```

**优化器选了单列索引**，因为两个都能完成任务，单列的更窄（`key_len` 144 vs 226）。这不是 bug，是成本估算的结果。

**对你的启示**：建了复合索引 `(kb_id, created_at)` 之后，单独的 `(kb_id)` 索引通常是多余的——复合索引的前缀已经覆盖了它。多一个索引 = 多一份写入成本（§八）。

## §七 索引失效：六种写法（A）——但要分清两种"失效"

这一节最重要的一句话：

> **"EXPLAIN 显示没走索引"有两种原因：写法上物理不可行，和优化器算完觉得不划算。前者改写法，后者改设计或认了。**

### 7.1 第一种：写法上就用不上（真·失效）

| # | 写法 | 为什么用不上 | 改法 |
|---|---|---|---|
| 1 | `WHERE LEFT(title,3) = '文档标'` | 索引按 `title` 原值排序，套了函数后**排序信息作废** | 改成 `WHERE title LIKE '文档标%'`；或建函数索引（8.0.13+） |
| 2 | `WHERE title LIKE '%标题-1%'` | 前置 `%` 意味着"可能以任何字符开头"，**没法在有序结构里定位起点** | 改后缀匹配；或上全文索引 / ES |
| 3 | `WHERE kb_id = 7`（列是 `CHAR(36)`） | **隐式类型转换**：字符串列和数字比较，MySQL 把**列**转成数字再比（等价于 `CAST(kb_id AS SIGNED)=7`），函数一上，索引废 | 传字符串 `'7'`，或统一列类型 |
| 4 | `WHERE kb_id = ? OR status = ?`（两列各有索引） | 两列分属不同索引，只能分别扫再合并（index merge），**优化器常常不做**，直接全表 | 拆成两条 SQL 用 `UNION`；或建覆盖两列的复合索引 |
| 5 | `WHERE b = ?`（复合索引 `(a,b)`） | 最左前缀（§6.2） | 建 `(b)` 或调整索引顺序 |
| 6 | `WHERE created_at > ?`（复合索引 `(kb_id, created_at)`） | 同上，跳过最左列 | 同上 |

实测（`probe_index.sql` 实验 D1/D2/D4/D6）：

```
D1 LEFT(title,3)   → type=ALL, key=NULL
D2 LIKE '%...'     → type=ALL, key=NULL
D4 kb_id = 7       → type=ALL, key=NULL（possible_keys 里明明有 idx_kb_id）
D6 OR 两列         → type=ALL, key=NULL
```

### 7.2 第二种：能用，但优化器放弃了（本篇纠正的第一个流行错误）

面经常见说法：**"`!=` 和 `NOT IN` 会让索引失效"**。实测推翻了它。

数据（`probe_index2.sql`，5 万行，`status` 有索引，三个取值均匀分布）：

| 查询 | type | key | rows | 结论 |
|---|---|---|---|---|
| `WHERE status != 'ready'` | **ALL** | **NULL** | 49822 | `possible_keys=idx2_status`，但**优化器主动放弃** |
| `WHERE status = 'ready'` | ref | idx2_status | 24911 | 等值查询**用了索引**，尽管要取 33% 的行 |

**为什么 `!=` 被放弃？** 因为 `!=` 命中约 67% 的行，走索引要回表 3 万多次——比顺序扫全表还贵。优化器算了一笔账，选了便宜的那条。

**为什么 `=` 33% 反而走了？** 等值是"一段连续区间"，索引定位精确、回表虽多但可预测；`!=` 是"两段区间 + 中间挖空"，扫描模式更差。

**正确结论**（面试就答这个）：

> `!=`、`NOT IN`、`LIKE '%x'` 这类**不一定失效**。索引能不能用，由优化器按**成本**决定：命中比例高、回表次数多，就会被放弃。所以判断依据不是"记哪些运算符不能用"，而是"**这个条件能筛掉多少行**"。

### 7.3 第二种的另一个实测：低选择性前缀 LIKE

同样是 `LIKE '前缀%'`，选择性不同，结果不同（`probe_index2.sql` 实验 1a/1b）：

| 查询 | type | key | rows |
|---|---|---|---|
| `LIKE '文档标题-499%'`（约 11 行） | **range** | idx2_title | 111 |
| `LIKE '文档标题-1%'`（约 2 万行） | **ALL** | **NULL** | 49822 |

**同一个写法，一个走索引一个不走。** 差别只在"能筛掉多少行"。这再一次说明：失效不是写法的属性，是**成本**的属性。

> 这两组实测就是本篇最值得带走的东西。你在面试里说"`!=` 不一定失效，要看命中比例和回表成本"，比背"六种失效写法"高一个档次——因为前者是机制，后者是口诀。

## §八 区分度：哪些列不值得建索引（A）

### 8.1 索引的成本

每个索引都要付出：

1. **空间**：一棵 B+ 树，5 万行的 `CHAR(36)` 索引就占几 MB
2. **写入**：每次 `INSERT` / `UPDATE` / `DELETE` 都要维护**所有**相关索引。索引越多，写入越慢
3. **优化器负担**：索引太多，优化器要评估的路径变多，可能选错

所以"给每个 WHERE 列都建索引"是错的。

### 8.2 判据：区分度

```sql
-- 这个列有多少个不同的值，占总行数的比例
SELECT COUNT(DISTINCT status) / COUNT(*) FROM documents;   -- 3/50000 = 0.006%
```

| 区分度 | 例子 | 建索引有用吗 |
|---|---|---|
| 很高（接近 1） | `id`、`kb_id`、`owner_id`、`email` | ✅ 非常有用 |
| 中等 | `created_at`、`title` | ✅ 有用（还能免排序） |
| 极低 | `status`、`is_deleted`、`gender` | ❌ 单独建基本没用，除非配合其他列做复合索引 |

**为什么极低区分度不适合单独建索引**：命中 33% 的行，回表 1.6 万次 > 顺序扫 5 万行。§7.2 的实测就是这个结论。

> 但要区分：**`status` 单独建索引没用 ≠ `status` 不该出现在索引里。**
> 在 `(kb_id, status)` 里它非常有用——因为 `kb_id` 已经把范围缩到 1000 行，再按 `status` 过滤只剩 334 行（实测 3b：`rows=334` vs 单列索引的 `rows=1000` + `filtered=50%`）。

### 8.2.1 同一个 `status` 索引，三种命运（2026-11-15 补，实测）

上面 §7.2 的结论是"低选择性被优化器放弃"。**今天在真表上它没被放弃**——5000 行的 `documents` 上，`status='ready'`（占 90%）照样走了索引：

```
type: ref   key: ix_documents_status   rows: 2410
```

这不是矛盾，是**表规模在改成本**：

| 环境 | 表规模 | `status='ready'`（90%） | 为什么 |
|---|---|---|---|
| `probe_docs`（§7.2） | 5 万行 | 放弃，`type=ALL` | 顺序扫 5 万行比回表 1.6 万次便宜 |
| `documents`（真表） | 5000 行 | **用索引**，`rows=2410` | 全部页在 Buffer Pool 里，回表就是内存访问，几乎免费 |
| `t_big`（放大 200 倍） | 100 万行 | **用索引，但选错了** | 见下表 |

100 万行的实测（`probe_status_volume.sql`，status 分布 90/8/2，行宽与 `documents` 一致）：

| 走法 | 实际耗时（`EXPLAIN ANALYZE` 的 `actual time`） |
|---|---|
| 走 `ix_status` + 回表 | **21.9 s** |
| `IGNORE INDEX (ix_status)` 强制全表扫 | **4.5 s** |
| 覆盖索引（只查 `id, status`） | 7.5 s |

**优化器选了慢 4.8 倍的那条。** 它给出的成本估计是走索引 `89944`、全表扫 `119823`——它以为走索引更便宜，实际 90 万次随机回表才是大头。

估错的原因：成本模型假设回表大致是有序访问，但 `status='ready'` 这 90 万行的主键散在整棵 B+ 树里，回表就是 90 万次随机 IO。表 150MB > Buffer Pool 128MB，命中率掉下来之后，这个假设就崩了。

**所以"低区分度能不能建索引"没有唯一答案，取决于三件事：**

1. 命中比例（区分度决定）
2. 单次回表的成本（表大小 + Buffer Pool 命中率决定）
3. 优化器估得准不准

工程上的处置：

```sql
-- 确认优化器选错了，就强制它别用
SELECT id, title FROM documents IGNORE INDEX (ix_status) WHERE status = 'ready';
```

或者干脆不建单列的 `(status)`，只让它出现在复合索引里（`(kb_id, status)`）。

> **面试价值**：这是"`EXPLAIN` 说走了索引 ≠ 走对了"的最好例子。看到 `type=ref` 别急着高兴，要接着问两件事：`rows` 占全表多少？这次查询要不要回表？

### 8.3 什么时候该建唯一索引而不是普通索引

如果业务要求"同一用户下知识库不能重名"：

```sql
CREATE UNIQUE INDEX uk_owner_name ON knowledge_bases (owner_id, name);
```

它有两个作用：**查得快**（同普通索引）+ **防重复**（数据库层面兜底，绕过应用层也拦得住）。

这跟 D2 讲的外键是同一个思想：**应用层的检查是为了给出准确错误，数据库的约束才是数据不出错的保证。**

## §九 EXPLAIN 字段怎么读（A）

### 9.1 只要看这四个字段

`EXPLAIN` 输出有十几列，日常只需要四列：

| 字段 | 看什么 | 好坏判断 |
|---|---|---|
| **type** | 访问方式 | `system > const > eq_ref > ref > range > index > ALL`，**出现 `ALL` 或 `index` 就要警惕** |
| **key** | 实际用了哪个索引 | `NULL` = 没用索引；`possible_keys` 有值而 `key` 是 `NULL`，说明**优化器主动放弃**（§7.2） |
| **rows** | 估算要扫多少行 | 越小越好。跟表总行数比较，接近总行数就是全表扫 |
| **Extra** | 补充信息 | `Using index` ✅ 覆盖索引；`Using filesort` ⚠️ 额外排序；`Using temporary` ⚠️ 临时表 |

### 9.2 type 的层级（从好到坏）

| type | 含义 | 出现场景 |
|---|---|---|
| `const` | 按主键/唯一索引查一行，优化阶段就确定了 | `WHERE id = 1` |
| `eq_ref` | 联表时被驱动表按主键查一行 | JOIN 的主键关联 |
| `ref` | 按非唯一索引查，可能多行 | `WHERE kb_id = ?`（实测 A2） |
| `range` | 索引范围扫描 | `WHERE created_at > ?`（实测 B4） |
| `index` | **扫整棵索引树**（比 ALL 好一点，因为索引比表窄） | 覆盖索引但无 WHERE，如 `SELECT COUNT(*)` |
| `ALL` | 全表扫描 | 没索引或优化器放弃 |

### 9.3 `rows` 是估算，`EXPLAIN ANALYZE` 才是真的

实测里有个反直觉的现象（`probe_index3.sql`）：

```
4a 覆盖索引: cost=129  actual time=0.0356..0.347
4b 回表:     cost=101  actual time=0.241..1.84
```

**cost 更低的那个反而更慢。** 因为 `cost` 是优化器基于统计信息的估算，统计信息可能过期（InnoDB 采样估算，不是精确值）。

所以：

- 想知道"优化器打算怎么干" → `EXPLAIN`
- 想知道"实际怎么干、花了多久" → `EXPLAIN ANALYZE`（**会真正执行查询**，别在生产上对慢查询随便跑）

> 这个现象本身就是面试素材：**"EXPLAIN 的 rows 和 cost 都是估算值，统计信息不准时优化器会选错路。"** 这也解释了为什么有时候"明明有索引却走了全表"——可能是统计信息过期，`ANALYZE TABLE` 能刷新。

### 9.3.1 统计信息到底是什么、为什么会不准（B，今天你就要用到）

**痛点**：优化器要替你在"走索引"和"全表扫"之间选一个。选择靠什么？靠"猜每种走法要读多少行"。
可它**不可能为每条查询都真数一遍 5000 行**——那样光估算成本就超过查询本身了。

所以数据库平时维护一份**笔记**，查询时只翻笔记。

| 笔记里记什么 | 你从哪看到 |
|---|---|
| 这一列有多少个**不同的值**（`Cardinality`） | `SHOW INDEX FROM documents` 的 `Cardinality` 列 |
| 索引占多少个数据页 | `SHOW TABLE STATUS` 的 `Data_length` / `Index_length` |
| 平均每行多长 | 同上 |

**谁写这份笔记**：InnoDB 后台自动更新，或者你手动 `ANALYZE TABLE` 触发。

**一个关键事实**：`ANALYZE TABLE` **不是精确统计，是采样**——默认只随机读 20 个索引页
（`innodb_stats_persistent_sample_pages`，默认 20），按这 20 页的比例去推算全表。
所以它**可能不准，也可能这次准下次不准**。这是设计上的取舍，不是 bug。

**今天你刚踩到的活例子**（这是灌完 5000 行、还没 `ANALYZE` 时的真实输出）：

```sql
SHOW INDEX FROM documents;
-- ix_documents_kb_id 的 Cardinality = 1     ← 笔记还是空的
```

```
EXPLAIN SELECT id, title FROM documents WHERE status = 'ready';
-- type=ALL  rows=4980  filtered=10.00  Extra=Using where
```

`filtered=10.00` 的意思是"优化器认为自己筛完只剩 10%"——**实际是 90%**（4500/5000）。
笔记离谱到这个程度，它接下来做的任何成本比较都不可信。

**什么时候必须手动跑**：

| 场景 | 为什么 |
|---|---|
| 大批量 `INSERT` / `LOAD DATA` 之后 | 笔记还是导入前的 |
| 刚 `CREATE INDEX` 之后 | 新索引的笔记是空的 |
| 怀疑"明明有索引却走了全表扫" | 先刷笔记，排除统计过期这一种可能，再谈别的 |

**易错点**：

| 坑 | 说明 |
|---|---|
| 以为 `ANALYZE TABLE` 会改数据 | 不改。它只重写统计笔记，一个字节的业务数据都不动 |
| 以为跑完统计就准了 | 采样，可能还是偏。所以判断"索引有没有用"，最终要看 `EXPLAIN ANALYZE` 的 `actual`，不是 `rows` |
| 把"统计过期"当成"索引失效" | 这是初学最常见的误判。先 `ANALYZE` 再 `EXPLAIN`，两次结果不同就说明是统计问题，不是索引问题 |
| 生产上频繁跑 | 有 IO 开销（要读索引页）。它不是免费的 |

```sql
-- 刷新一张表
ANALYZE TABLE documents;

-- 刷完再看笔记变没变
SHOW INDEX FROM documents;
```

**面试问法**："为什么 `EXPLAIN` 的 `rows` 和实际差很多？"
30 秒版：`rows` 是优化器读统计笔记估出来的，笔记由 InnoDB 采样维护（默认 20 页），
大批量导入后或建索引后没刷新就会严重失真；用 `ANALYZE TABLE` 刷新，要真实数字就用 `EXPLAIN ANALYZE`。

### 9.4 `EXPLAIN ANALYZE` 怎么读

```
-> Index lookup on probe_docs3 using idx3_kb_status (kb_id='kb-007'),
   with index condition: (...)  (cost=101 rows=1000)
   (actual time=0.241..1.84 rows=1000 loops=1)
```

- `cost=101 rows=1000`：**估算**
- `actual time=0.241..1.84`：**实际**。前一个数是"返回第一行耗时"，后一个数是"返回所有行总耗时"
- `rows=1000`（actual 里的）：**实际返回行数**。跟估算差很多，说明统计信息不准
- `loops=1`：这个节点被执行了几次。嵌套循环里 `loops` 会很大，`actual time` 要乘以 `loops` 才是总耗时

## §十 本项目该建哪些索引（A）

现在把上面的原理落到 `kb-service` 的三张表上。先列出真实查询，再定索引。

### 10.1 三张表与已有索引

| 表 | 列 | 已有索引 |
|---|---|---|
| `knowledge_bases` | `id`(PK, UUID) / `owner_id` / `name` / `description` / `doc_count` / `created_at` / `updated_at` | `owner_id`（`index=True`） |
| `documents` | `id`(PK, UUID) / `kb_id`(FK) / `title` / `status` / `chunk_count` / `created_at` / `updated_at` | `kb_id`（`index=True`） |
| `chunks` | `id`(PK, UUID) / `doc_id`(FK) / `content`(Text) / `chunk_index` / `created_at` | `doc_id`（`index=True`） |

> 注意：这些 `index=True` 是 D2 建的，**当时只是"外键列该有索引"的直觉**。今天要用 EXPLAIN 验证它们够不够。

### 10.2 五条真实查询，逐条判断

**查询 1：列表页——我的知识库**

```sql
SELECT * FROM knowledge_bases WHERE owner_id = ? ORDER BY created_at DESC LIMIT 20;
```

- 现在：`owner_id` 单列索引，能用
- 问题：`ORDER BY created_at DESC` 要在索引结果上再排序（`filesort`）
- 建议：`(owner_id, created_at)`——等值 + 排序，排序被索引免费解决（§6.1 实测）

**查询 2：详情页——某知识库下的文档，按时间倒序分页**

```sql
SELECT * FROM documents WHERE kb_id = ? ORDER BY created_at DESC LIMIT 20 OFFSET 0;
```

- 现在：`kb_id` 单列索引，能定位，但要 filesort
- 建议：`(kb_id, created_at)`。如果列表只显示 `id/title/status/created_at`，可以考虑把 `title` 也加进去做覆盖索引，但索引会变宽

**查询 3：按状态过滤——找待处理的文档**

```sql
SELECT * FROM documents WHERE kb_id = ? AND status = 'pending' ORDER BY created_at LIMIT 50;
```

- 现在：`kb_id` 单列索引，`status` 靠过滤（实测 3a：`rows=1000`，`filtered=50%`）
- 建议：`(kb_id, status, created_at)`——等值 + 等值 + 排序，三层全用上
- 注意顺序：**两个等值列之间，区分度高的放前面**（`kb_id` 50 个值 > `status` 3 个值）

**查询 4：检索结果回溯——chunk 属于哪篇文档**

```sql
SELECT c.*, d.title FROM chunks c JOIN documents d ON c.doc_id = d.id WHERE c.doc_id IN (...);
```

- 现在：`chunks.doc_id` 有索引，`documents.id` 是主键
- 这条是 W12 检索链路的雏形，今天只要确认 `doc_id` 索引在，JOIN 走 `ref` 就行

**查询 5：删除知识库（D2 的级联）**

```sql
DELETE FROM documents WHERE kb_id = ?;
```

- `kb_id` 有索引 → 走 `ref`，不会全表扫
- 反例：如果没有 `kb_id` 索引，删一个知识库要扫全表。**这就是 D2 那条 `index=True` 的真实理由**——不只是查询，级联删除也靠它

### 10.3 一个反例：不要给 `status` 单独建索引

`status` 只有 3 个值，区分度 0.006%（§8.2）。单独建索引：命中 33% 的行，回表成本 > 全表扫，优化器会直接放弃（实测 2a）。

**它只在复合索引里作为第二、第三列才有价值。**

## §十一·五 业务链条三问（A）

每个技术都要钉回这三问。**第③问不许编百分比**——个人项目没有真实负载，编了一定被面试追问戳穿。

### 索引（一般）

| 问 | 答 |
|---|---|
| ① 哪个用户可见行为 | 打开"我的知识库"列表页，等多久出内容 |
| ② 不做会怎样 | 库一多就转圈；用户以为卡死，反复刷新，进一步压垮数据库 |
| ③ 可复现指标 | `EXPLAIN` 的 `rows`：50000 → 1000（今天实测）；`type`：`ALL` → `ref` |

### 覆盖索引

| 问 | 答 |
|---|---|
| ① 用户可见行为 | 列表页首屏出现时间 |
| ② 不做会怎样 | 每次都要回表取 `title`，1000 行 = 1000 次额外查找 |
| ③ 可复现指标 | `Extra` 从 `Using index condition` → `Using index`；实测耗时 1.84ms → 0.347ms（约 5.3 倍） |

### 复合索引的顺序

| 问 | 答 |
|---|---|
| ① 用户可见行为 | 按状态筛选文档时的响应速度 |
| ② 不做会怎样 | 单列索引只能筛到 1000 行，剩下一半靠逐行过滤 |
| ③ 可复现指标 | `rows`：1000（+`filtered=50%`）→ 334；`Extra` 里的 `Using where` 消失 |

### 关于"业务收益"的诚实说法

上面三个指标全部是**工程指标**（行数、耗时、Extra 标记），不是业务指标（GMV、留存）。

如果你要答"这个优化值多少钱"，正确回答是：**"个人项目没有真实流量，测不出业务收益；我能给出的是可复现的工程指标，以及在生产环境该用 P99 响应时间来验证。"** 这句话比编一个"提升 30%"可信得多。

## §十二 面试问法（A）

### Q1：索引为什么用 B+ 树，不用二叉树 / 哈希 / 跳表？

**30 秒版**：因为磁盘 IO 是按页算的。B+ 树把节点放大到一页（16KB），扇出能到 1170，三层就能存两千万行，随机 IO 压到个位数；二叉树扇出只有 2，树高 20 多层，每层一次 IO。哈希不支持范围和排序，跳表适合内存不适合磁盘。

**追问一层**：B+ 树和 B 树的区别？——B 树的非叶子节点也存数据，同样一页放的 key 更少、树更高；B+ 树数据全在叶子，非叶子只当目录，扇出最大，而且叶子有链表，范围查询顺链走。

**追问二层**：叶子链表对 `ORDER BY` 有什么用？——索引本身有序，`ORDER BY` 的列如果是索引的后缀，可以直接顺链读（甚至倒着读，实测 `Backward index scan`），省掉 `filesort`。

### Q2：回表是什么？怎么避免？

**30 秒版**：二级索引的叶子只存索引列 + 主键，不存整行。查到主键后要再回聚簇索引取整行，这就是回表。避免办法是覆盖索引——把查询要的列都放进索引，`Extra` 显示 `Using index` 就不回表了。

**追问一层**：为什么覆盖索引能快这么多？——实测 5 万行表、命中 1000 行：覆盖索引 0.347ms，回表 1.84ms，差 5.3 倍。因为省了 1000 次树查找（虽然多数命中 Buffer Pool，但仍是 1000 次遍历和拷贝）。

**追问二层**：覆盖索引有什么代价？——索引变宽，占更多空间，写入维护成本更高。所以只在"查询频率高 + 返回列少"时才做。

**场景落地**：项目里列表页 `SELECT id, title ... LIMIT 20`，我会建 `(kb_id, created_at, title)` 让 20 行全覆盖；但如果是导出全表，宁可分批查也不建超宽索引。

### Q3：最左前缀是什么？为什么 `(a,b,c)` 用不上 `b = ?`

**30 秒版**：复合索引的树是"先按 a 排、a 相同再按 b 排、再按 c 排"。不给 a 就不知道从哪开始找，所以 `b = ?` 用不上，`a = ?` 能用，`a = ? AND b = ?` 能用两列。

**追问一层**：`a = ? AND c = ?` 呢？——只能用 a 定位，c 用不上索引，靠过滤。

**追问二层**：范围条件为什么会让后面的列失效？——范围一旦展开，后面列在范围内不再全局有序（`a > 5 AND b = 3`，每个 a 值下 b 各自有序，但跨 a 不有序），所以只能用到范围那一列。

### Q4：索引失效有哪几种情况？

**30 秒版**（注意这题要分开答）：分两类。**写法上物理不可行**的：列上套函数、隐式类型转换、`LIKE '%x'` 前置通配、`OR` 连接不同列、复合索引跳过最左列。**优化器算完放弃**的：`!=`、命中比例高的条件、低选择性前缀 `LIKE`——这类不是写法错，是成本不划算。

**追问一层**：`!=` 到底失不失效？——不一定。实测同一个 `status` 列：`!= 'ready'`（命中 67%）被放弃走全表，`= 'ready'`（命中 33%）反而走了索引。差别在回表次数和扫描模式。

**追问二层**：那怎么让 `!=` 用上索引？——一般不值得。真需要就改需求（比如只查 `status IN ('pending','failed')`，两段区间比"挖空"好），或者加覆盖索引消除回表。

### Q5：怎么判断该不该建索引？

**30 秒版**：看三件事：查询频率（低频查询不值得）、区分度（`status` 这种 3 个值的列单独建没用）、以及索引的代价（占空间 + 拖慢写入）。判断标准是"这个索引能筛掉多少行"，不是"这个列在不在 WHERE 里"。

**追问一层**：索引多了有什么坏处？——每次写入要维护所有相关索引；优化器要评估更多路径，可能选错；占空间。

**追问二层**：低区分度列真的一点用没有？——单独建没用，但在复合索引里当第二、三列很有用：`kb_id` 先把范围缩到 1000 行，`status` 再筛到 334 行（实测）。

8. `EXPLAIN` 的 `cost` 更低的执行计划，实际一定更快吗？为什么？

<details><summary>答案 1</summary>

无索引：`type=ALL`，`rows=50000`。有索引：`type=ref`，`rows=1000`。

`rows` 是 1000 而不是 1，因为 `kb_id` 不是唯一索引——5 万行 / 50 个不同的 `kb_id` = 每个 `kb_id` 平均 1000 行。`rows` 是**估算要扫描的行数**，不是"预期返回行数"（虽然这里相等）。

</details>

<details><summary>答案 2</summary>

一页 **16KB**。非叶子节点存 key + 指针，bigint 8 字节 + 指针 6 字节 = 14 字节 → 一页约 1170 个；叶子存整行，假设 1KB/行 → 16 行/页。

三层：`1170 × 1170 × 16 ≈ 2190 万`。根和中间层几乎常驻 Buffer Pool，所以真实磁盘 IO 通常 1 次（读叶子页）。

</details>

<details><summary>答案 3</summary>

- **聚簇索引**（主键）：叶子存**整行数据**。一张表只有一个。
- **二级索引**：叶子存**索引列值 + 主键值**，不存整行。

所以要拿整行，必须先查二级索引拿主键，再拿主键查聚簇索引——第二步就是回表。

</details>

<details><summary>答案 4</summary>

- `Using index` = **覆盖索引**，查询要的列全在索引里，**不回表**。
- `Using index condition` = **索引下推（ICP）**，把部分过滤条件下推到存储引擎层执行，减少回表次数，但**仍然要回表**取剩余列。

只差一个 `condition` 词，含义完全不同。本篇实测：覆盖 0.347ms / 回表 1.84ms。

</details>

<details><summary>答案 5</summary>

**不能**。索引按 `(kb_id, created_at)` 排序，不给 `kb_id` 就不知道从哪个 `kb_id` 段开始找，整棵树无从下手。实测 `type=ALL, rows=49677`。

改法：给 `created_at` 单独建索引（实测 `type=range, rows=5360`），或者把索引顺序改成 `(created_at, kb_id)`（但那样 `kb_id` 的等值查询又会受影响，要按真实查询取舍）。

</details>

<details><summary>答案 6</summary>

**隐式类型转换**。`kb_id` 是字符串列，跟数字 `7` 比较时，MySQL 会把**列**转成数字（等价于 `CAST(kb_id AS SIGNED) = 7`），列上套了函数，索引的排序信息作废。

改成 `WHERE kb_id = '7'`（加引号）即可。更根本的做法是保持类型一致——应用层传字符串。

（反过来，如果列是 `INT` 而传 `'7'`，MySQL 会把常量转成数字，**仍然能走索引**。所以危险方向只有一个：**字符串列遇到数字常量**。）

</details>

<details><summary>答案 7</summary>

推翻了"`!=` / `NOT IN` 一定导致索引失效"。

真实原因：`!= 'ready'` 命中约 67% 的行，走索引要回表 3 万多行，成本高于全表顺序扫，**优化器主动放弃**（`possible_keys` 有值但 `key=NULL`）。而 `= 'ready'` 命中 33%，是连续区间，优化器判断仍值得走索引。

结论：**失效不是运算符的属性，是成本的属性。**

</details>

<details><summary>答案 8</summary>

**不一定**。`cost` 是优化器基于**统计信息**的估算，InnoDB 的统计信息是采样的、可能过期或不准。

本篇实测反例：覆盖索引 `cost=129` / 实际 0.347ms，回表 `cost=101` / 实际 1.84ms——**cost 低的反而慢 5 倍**。

要看真实情况用 `EXPLAIN ANALYZE`（会真正执行查询）。统计信息过期时可以 `ANALYZE TABLE` 刷新。

</details>

<details><summary>答案 9</summary>

`status` 只有 3 个取值，区分度 0.006%。单独建索引时，任何等值/不等值查询都要命中 33% 以上的行，回表成本超过全表扫，优化器会放弃（实测 `!=` 和低选择性前缀 `LIKE` 都被放弃）。

但在 `(kb_id, status)` 里：`kb_id` 先把候选缩到 1000 行，`status` 再筛到 334 行——**此时索引的选择性由 `kb_id` 提供，`status` 只是"在已缩小的范围内进一步过滤"**，成本极低。实测 `rows` 从 1000（+`filtered=50%`）降到 334。

</details>

<details><summary>答案 10</summary>

建 `(kb_id, created_at)`（或 `(kb_id, created_at, title)` 做覆盖索引）。

理由三层：
1. `kb_id` 是等值条件 → 放最前
2. `created_at` 是 `ORDER BY` 的列 → 紧接在等值列后面，排序被索引免费解决，省掉 `filesort`（实测 `Backward index scan`）
3. 如果 `title` 也进索引，`SELECT id, title` 全部命中索引，不回表；但索引变宽，要权衡

`LIMIT 20` 让回表代价很小（只有 20 次），所以 `(kb_id, created_at)` 通常就够，不必加 `title`。

</details>
