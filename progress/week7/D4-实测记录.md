## 1. 交付物 1：丢失更新复现

时序记录（按**实际执行顺序**还原；终端历史是按窗口分的，两个窗口的交错靠输出反推）：

| 步 | 会话 | 语句 | 看到了什么 |
|---|---|---|---|
| 1 | B | `BEGIN;` | — |
| 2 | B | `SELECT doc_count ...` | **0**（B 的快照在此刻建立） |
| 3 | A | `BEGIN;` | — |
| 4 | A | `UPDATE ... SET doc_count=1` | Changed: 1（拿到行锁） |
| 5 | A | `COMMIT;` | 已提交值 → 1 |
| 6 | A | `SELECT doc_count ...` | 1（新事务、新快照） |
| 7 | B | `UPDATE ... SET doc_count=1` | **0.01s，没阻塞**（A 已提交，无锁竞争）；**Rows matched: 1, Changed: 0** ← 关键痕迹 |
| 8 | B | `COMMIT;` | — |
| 9 | B | `SELECT doc_count ...` | 最终值 = **1** |

> 时序反推依据：B 步 7 的 `Changed: 0` 说明它执行时库里已是 1（写 1 等于没改），
> 而 B 步 2 读到 0——所以 B 的 SELECT 一定发生在 A 提交之前、B 的 UPDATE 在 A 提交之后。
> 如果 B 的 SELECT 在 A 提交之后才敲，RR 下新事务新快照，读到的应该是 1 不是 0。

**证据 1（覆盖发生）**：业务上两次"上传"各 +1，应为 2，库里是 **1**——A 的更新被 B 的写入抹掉，没报错、没异常。
**证据 2（写回旧值的痕迹）**：B 步 7 `Changed: 0`——B 把它基于旧快照算好的 1 写回去，MySQL 告诉它"这行本来就是 1，什么都没改"。B 写的不是"现在的值"，是"几秒前算好的值"。
**证据 3（串行也丢）**：B 的 UPDATE 在 A 提交**之后**才执行（0.01s，无锁等待），仍然丢——因为 B 的值在步 2 的快照时刻就定死了。**丢不丢不看 UPDATE 何时执行，看写的值何时算出。**

**病根一句话**（交付物 4）：

> 读-改-写三步分离：写在几秒后执行，写的值却在几秒前（快照时刻）就算好了，中间没有任何"重新看一眼最新值"的动作，后到的写覆盖先到的写。

## 2. 交付物 2：修复① 原子自增

| 步 | 会话 | 语句 | 看到了什么 |
|---|---|---|---|
| 1 | A | `UPDATE SET doc_count = doc_count + 1` | 25 → 26（Changed: 1） |
| 2 | B | 同上（有没有锁等待？） | 0.18s 返回（日志看不出是否等锁；两次 +1 都生效） |
| 3 | 任一 | `SELECT doc_count ...` | 最终值 = **27**（25 → 27，零丢失） |

对比 §1：为什么这版不丢？一句话：

> `doc_count + 1` 里的加法在**数据库内部、拿到行锁之后**做：先当前读最新已提交值，再加 1 写回，一条语句没有空隙。B 等到锁后读到的是 A 已提交的 26，不是它自己快照里的 25——"读最新值"这个动作被数据库强制塞进了写之前，应用想跳过都跳不掉。

## 3. 交付物 3：修复② `FOR UPDATE`

| 步 | 会话 | 语句 | 看到了什么 |
|---|---|---|---|
| 1 | 会话1 | `BEGIN; SELECT ... FOR UPDATE` | **卡住 39.87 秒**——等的不是自己，是更早某个窗口留下的未提交事务；对方提交后才返回，读到 **3** |
| 2 | 会话1 | `UPDATE ...`（⚠️ **漏了 `WHERE`**）；再跑带 WHERE 的 `+1`；`COMMIT;` | 无 WHERE 那条 `Rows matched: 201  Changed: 201`；带 WHERE 的 3 → 4 → 5 |
| 3 | 会话2 | `BEGIN; SELECT ... FOR UPDATE`（立刻敲） | **卡住 17.54 秒**，会话1 commit 的瞬间返回 |
| 4 | 会话2 | 返回后读到 | **5**（= 会话1 提交后的最新值，不是快照旧值）；再 `+1` → 6 |

三次等待全部记在 `SELECT ... FOR UPDATE` **这一行**上（`1 row in set (39.87 sec)` / `(17.54 sec)`），没有一条是"SELECT 立即返回、后面才卡"——卡住的就是这句本身。

B 读到的值和 §1 步 2 读到的值**一样吗**？为什么：

> **不一样。** §1 步 2 是普通 `SELECT`（快照读，读到 0 这个旧值）；`FOR UPDATE` 是**当前读**：先抢行锁，拿到锁之后再读**最新已提交版本**（3 / 5）。同一个事务里先普通 SELECT 再 FOR UPDATE，两次结果可以不同——这就是"快照读 vs 当前读"的现场。

**等多久由谁决定**：由**持锁方 commit/rollback 的时刻**决定，等待方自己选不了。39.87s 距 `innodb_lock_wait_timeout` 默认的 50s 只差 10 秒——再晚一点就不是"拿到锁"，而是 `ERROR 1205 Lock wait timeout exceeded`。

**副作用（必须记）**：步 2 那条漏了 `WHERE` 的 UPDATE 把 **201 个 kb 的 `doc_count` 全部 +1**，唯一的警报就是 `Changed: 201`。改动后的分布：199 个 kb = 28（累计三次）、`aaaa…` = 3、目标 kb = 6。这是 D6 那类"删掉 where 条件"变异体的真实预演——线上就是"全站计数器被改"级别的事故，而它**零报错**。

## 4. 今天的三个新发现 / 卡住的地方

1. **`BEGIN` 后单条语句报错，事务并没有回滚**：任务 1 第一轮 `UPDATE doc_count SET ...`（表名写错）报 1146，紧接着的 UPDATE 还在同一个事务里正常执行。语句失败 ≠ 事务结束，处置权（COMMIT/ROLLBACK）在自己手里。
2. **`Changed: 0` 是"写回旧值"的唯一痕迹**：丢更新零报错零异常，唯一线索是 MySQL 这行反馈——"你写的值和库里已有值相同"。数值恰好相同时（都写 1）肉眼完全看不见，这正是它阴险的地方；想看清楚就两边写不同的值（A 写 1、B 写 100 → 最终 100，A 的 1 蒸发）。
3. **串行时序也丢**：B 的 UPDATE 在 A 提交后才执行，没有锁竞争、没有阻塞，照样丢。推翻了"只要别同时执行就没事"的直觉——只要代码是"读出来、算好、写回"，两个 HTTP 请求哪怕时间上完全错开，照样丢。
4. **漏写 `WHERE` 的 UPDATE 零报错，`Changed: 201` 是唯一警报**：一条 `UPDATE knowledge_bases SET doc_count = doc_count + 1;` 改了全表 201 行。MySQL 不会问"你确定吗"，affected rows 就是最后一道防线——**每条写语句敲下去先看这个数**。事务里还来得及 ROLLBACK，我 commit 了就没得救（只能靠归零脚本修）。
5. **长事务会卡住所有人**：39.87s 那次等的不是对面那个窗口，而是更早某个没提交的事务。线上"偶发接口超时"有一类就是这个——某个连接拿了锁迟迟不 commit。
