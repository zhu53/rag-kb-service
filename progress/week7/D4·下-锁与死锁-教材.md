## §零 主线：一条 UPDATE 的一生（A）

```
客户端发出 UPDATE
   ↓
① 找行：按索引定位 → 读最新已提交版本（当前读）
   ↓
② 加锁：在索引记录上加 X 锁 —— 从这一刻起，别人改这行会被挡住
   ↓
③ 写 undo：把旧值存进 undo log（回滚用）
   ↓
④ 改内存页：标脏页，还没落盘
   ↓
⑤ COMMIT：写 redo → 锁**一次性全部释放**
```

**这条时间轴上只有两个时刻值得记**：

- **② 加锁**：锁加在**索引记录**上，不是"行"上。加在哪条索引、加几条，决定了你锁住了多少人（§二）。
- **⑤ 释放**：锁在 **COMMIT/ROLLBACK 时统一释放**，不是语句结束就放。**事务越长，你挡别人越久**（§十）。

一句话分界：

> D4·上 关心"**我读到什么**"，D4·下 关心"**我挡住了谁**"。
> 两者是同一枚硬币：**当前读**= 读最新值 **+** 加锁；**快照读** = 读旧版本，**不加锁**。

| 7 | 两个事务互相等怎么办 | 死锁：检测 → 杀一个 → 1213（§七、§八） |

一句话串完整篇：

> 当前读要加锁 → 锁加在索引记录上 → 所以没索引就是锁全表 → 锁有三种形态（记录/间隙/临键）→ 间隙锁是为了防幻读 → 锁看得见（data_locks）→ 两个事务锁的顺序相反就成环 → InnoDB 检测到环会杀掉一个 → 代码必须能重试。

## §一 痛点：两个人同时改同一行（A）

### 1.1 没有锁会怎样

假设 InnoDB 完全不加锁。两个请求同时：

```
请求 A：读 doc_count = 25 → 算 26 → 写 26
请求 B：读 doc_count = 25 → 算 26 → 写 26
```

结果 26，少算一次。这你已经在上半场复现过了（**丢失更新**）。

但还有更糟的一种，叫**脏写**：A 改到一半（未提交），B 直接覆盖了 A 的修改；A 回滚时，B 的修改也跟着没了。锁首先要防的是这个。

### 1.2 最小可跑示例（5 分钟，两个窗口）

开两个 mysql 客户端（`mysql -h127.0.0.1 -P3307 -uroot kb_dev`），**A 先敲，B 后敲，B 会卡住**：

```sql
-- 窗口 A
BEGIN;
UPDATE knowledge_bases SET doc_count = 100 WHERE id='kb000001000000000000000000000000';
-- 先别 commit

-- 窗口 B（此刻敲，会卡住）
UPDATE knowledge_bases SET doc_count = 200 WHERE id='kb000001000000000000000000000000';
```

B 停在原地等 A 的锁。A 一 `COMMIT`，B 立刻返回，`doc_count` 变成 200——**A 的 100 被覆盖了，但这次是"并发写"的正常结果，不是 lost update**（因为 B 没读过 100，它写的是自己算的 200）。

> 这里有个容易混的点：**锁能防"同时写"，但防不了"读了旧值再写"**。后者要靠原子表达式 `+1` 或 `FOR UPDATE`（§十一）。上半场你已经踩过这个坑。

### 1.3 三个必须亲眼看到的现象

| 现象 | 在哪看 | 含义 |
|---|---|---|
| B 卡住 | B 窗口光标停住 | 行锁在排队，不是程序死掉 |
| 卡多久 | 计时 | 由 A 何时 COMMIT 决定（上半场 39.87s 那次） |
| 卡超过 50s | `ERROR 1205` | `innodb_lock_wait_timeout` 默认 50 秒 |

### 1.4 易错点

| 写法 / 认知 | 错在哪 | 正确 |
|---|---|---|
| "行锁锁的是一行数据" | InnoDB 锁的是**索引记录** | §二 |
| "语句结束锁就放了" | 锁到 COMMIT/ROLLBACK 才放 | §零 时间轴 ⑤ |
| "锁能防丢失更新" | 锁只防同时写，防不了"读旧值写回" | §十一 |

## §二 锁加在哪：索引记录上（A）★本篇地基

### 2.1 InnoDB 没有"行锁"这个对象

表里的行**不是**独立的加锁单位。InnoDB 的锁对象是：

> **索引上的一条记录（index record）**。

主键索引（聚簇索引）的叶子记录就是整行，所以"锁主键记录" ≈ 锁这一行。二级索引的叶子记录是 `(索引列, 主键)`，锁它等于锁"这个索引项"。

**推论**：一张表如果**没有任何索引**，你怎么定位一行？只能全表扫。扫过谁，就锁谁。

### 2.2 实测①：没索引 → 锁了 5039 条

`documents` 表 5000 行，`status` 列**没有索引**（今天为了交付物 4 建过又删了）。执行：

```sql
BEGIN;
UPDATE documents SET title = title WHERE status = 'ready';   -- 命中 4500 行
```

`performance_schema.data_locks` 里这张表有：

```
锁对象总数 = 5040
  RECORD:X                 5039      ← 索引记录上的排他锁，几乎覆盖全表
  TABLE:IX                 1         ← 表级意向锁（§五）
```

**命中 4500 行，却加了 5039 个记录锁。** 因为 `status` 没索引，Server 层只能让 InnoDB 从头扫到尾：**扫过的每一条都加锁**，扫完再到 Server 层用 `status='ready'` 过滤。

这就是"我只改 1 行，结果把别人的写入全挡住了"的真相。

### 2.3 实测②：有索引 → 52 个（但仍是 25 行的 2 倍）

```sql
BEGIN;
UPDATE documents SET title = title WHERE kb_id = 'kb000001000000000000000000000000';  -- 25 行
```

```
锁对象总数 = 52
  RECORD:X                 25      ← 二级索引 ix_documents_kb_created 上的临键锁（含间隙）
  RECORD:X,REC_NOT_GAP     25      ← 回表后，聚簇索引 PRIMARY 上的记录锁
  RECORD:X,GAP             1       ← 最后一条命中记录之后的那个间隙
  TABLE:IX                 1
```

**为什么是 25 + 25**：改一行要动两个地方——二级索引项（`kb_id, created_at, id`）和聚簇索引记录（整行）。InnoDB 两边都要锁。

这解释了一条常被问的现象：

> **走二级索引改数据，锁的数量是命中行数的两倍**（二级索引记录 + 聚簇索引记录）。所以二级索引不是越多越好：每个二级索引都可能让同一行的加锁成本翻倍，还拖慢写入。

### 2.4 推论：三条可以直接用的话

1. `UPDATE`/`DELETE` 的 `WHERE` 列**必须**有索引，否则锁全表 → 所有并发写排成一队。
2. 命中行越少越好：范围太大（比如 `status='ready'` 命中 90%），即使有索引也要锁很多行。
3. 二级索引会让加锁数量翻倍——索引不是白给的。

### 2.5 易错点

| 认知 | 正确 |
|---|---|
| "改了 1 行就锁 1 行" | 锁的是**扫描过的**索引记录，不是命中的行 |
| "没索引只是慢" | 没索引还会**锁全表**，从性能问题升级为并发问题 |
| "锁是锁住整行数据" | 锁在索引记录上；一行在两个索引里有两条记录，可能两个锁 |

### 2.6 追问：锁索引，会把非叶子节点也锁住吗？（B）

不会——**事务锁只落在叶子层的用户记录上**，非叶子节点（存导航用目录项的那层）没有被任何事务锁覆盖。

但要先把两个词分开，因为中文都叫"锁"：

| | **lock（事务锁）** | **latch（闩锁）** |
|---|---|---|
| 保护什么 | 行的逻辑内容（这一行、这条缝） | 数据结构的物理完整（页、链表、树结构） |
| 持续多久 | **到事务 commit/rollback** | 操作完立刻释放，微秒~毫秒级 |
| 谁能看见 | `performance_schema.data_locks` | 看不见，用户无感 |
| 落在哪 | 叶子层的用户记录 + 表级意向锁 | **包括非叶子节点在内的任何页** |

回答分两层：

1. **事务锁为什么不锁非叶子节点**：行锁在 InnoDB 内部是"页内第几条记录"的位图（§3.2.1 的锚点），只有叶子页的用户记录有这个编号。更根本的是语义：如果锁 20 要沿树向上把祖先节点也锁住，那么**树根会被最先到达的任何一个行锁占住，整棵树、整张表立刻串行化**——等于没有并发。所以行锁的覆盖面刻意停在叶子。
2. **非叶子节点不是"没人管"**：插入引发页分裂、删除引发页合并时，InnoDB 会短暂持有相关页的 latch（连着父节点一起，俗称"蟹行"）。这跟事务无关——语句做完就释放，别人的等待是毫秒级内部等待，不计入 `innodb_lock_wait_timeout`，你在 `data_locks` 里也看不到它。

**实测反证**（A 持有 `WHERE id=20 FOR UPDATE` 不提交，B 在同一张表、同一棵主键树上依次执行）：

```
UPDATE id=10   （同页相邻记录）   OK
UPDATE id=30   （另一条记录）     OK
SELECT id=30 FOR UPDATE          OK     ← 走同一棵树，畅通
INSERT 15      （缝里插入）       OK     ← 等值命中无间隙锁（§3.3 场景 A）
UPDATE id=20   （被锁那行）       BLOCKED
```

同一棵树，只有挂了锁的那**一条记录**受阻，其余操作全部秒过。如果非叶子节点也被锁，第一条就该卡住。

> 顺带注意：`SELECT id=30 FOR UPDATE` 能通过，不代表 B 拿到了"树"——它拿到的是 30 的记录锁和自己的表级 IX。**"锁一棵树"从来不是锁整棵树，是锁树上的某些叶子记录 + 表上的意向锁。**

### 2.7 易错点（2.6 补）

| 认知 | 正确 |
|---|---|
| "行锁会锁住索引页/整棵树" | 只锁叶子层的用户记录；非叶子节点只有毫秒级 latch |
| "lock 和 latch 是一回事" | latch 保护物理结构、瞬间释放；lock 保护事务语义、到 commit |
| "latch 等待受 50s 超时管" | 不受；`innodb_lock_wait_timeout` 只管事务锁等待 |

## §三 三种锁形态（A）★看不懂就先看图

### 3.1 先建立图像：索引是"一排点 + 点之间的缝"

前面说过锁加在索引记录上。但"索引记录"不是散落的，它是一条**从左到右排好序的序列**：

```
        g0          g1          g2          g3
   -∞ ─────── 10 ─────── 20 ─────── 30 ─────── +∞
              ●           ●           ●
            记录10      记录20      记录30
```

- **点** = 一条索引记录（`●`）
- **缝** = 两条记录之间的空档（`g0`–`g3`），缝里现在没有数据，但**随时可能被 INSERT 填进来**

于是要防的事只有两件：

1. **有人改/删这个点**（改 20 那一行）
2. **有人往缝里插**（插一条 id=15，它就落在 `g1` 里）

三种锁，就是"管点""管缝""两个都管"的区别。

### 3.2 三种锁，其实就是三种覆盖范围

| 锁 | 覆盖范围 | `LOCK_MODE` | 在 `data_locks` 里怎么认 | 挡住谁 |
|---|---|---|---|---|
| **记录锁** | 只有一个点：`{20}` | `X,REC_NOT_GAP` | `LOCK_DATA=20` | 改/删 20 这一行 |
| **间隙锁** | 一段缝，**不含右端点**：`(20,30)` | `X,GAP` | `LOCK_DATA=30` | 往 20 和 30 中间 INSERT |
| **临键锁** | 一个点 + **它左边**那段缝：`(10,20]` | `X`（无后缀） | `LOCK_DATA=20` | 改 20 + 往 10 和 20 中间 INSERT |

三个名字的读音就是它的范围：

- **Record** Lock（记录锁）→ 一个 record（点）
- **Gap** Lock（间隙锁）→ 一个 gap（缝）
- **Next-Key** Lock（临键锁）→ 从"上一个 key"到"这个 key"：`(上一个, 这个]`

> **最容易错的一点：`LOCK_DATA` 里写的是"右边界"。**
> `X,GAP` + `LOCK_DATA=30` 锁的是 **30 左边那段**，不是 30 本身。
> `X` + `LOCK_DATA=20` 锁的是 **(10,20]**，包含 20。
> 看 `data_locks` 时心里要补一句"这个数指的是哪一段的右头"。

### 3.2.1 `LOCK_DATA` 到底是什么：一条锁的"锚点记录"

上一节说 `LOCK_DATA=30` 是右边界。但还有个更根本的问题：**条件里写的是 25，为什么右边界是 30 而不是 25？**

因为 InnoDB 内部一条行锁长这样（简化）：

```
(页号, 页内第几条记录, 锁模式, 含不含这条记录, 含不含它左边的缝)
        ↑
    这里必须是一个物理下标 —— 只有真实记录才有
```

`WHERE id < 25` 里的 25 只活在 **MySQL server 层的过滤器**里，它到不了 InnoDB 层。InnoDB 手里只有"第 0 页、页内第 3 条记录"这样的坐标。所以**一条缝要被锁住，只能挂在它右边那条真实记录上**，再用标志位说明"我要的是这条记录左边的缝，不要记录本身"——这就是 `X,GAP` 的来历。

四种形态的读法：

| `LOCK_MODE` | `LOCK_DATA` 怎么读 | 覆盖 |
|---|---|---|
| `X,REC_NOT_GAP` | 就是被锁的那一行 | `{20}` |
| `X`（裸） | 右端点记录 | `(10,20]` |
| `X,GAP` | 右端点记录，**记录本身不含** | `(20,30)` |
| `X` + `supremum pseudo-record` | 序列末尾的虚拟记录 | `(30,+∞)` |

**实测①：只改上界数值，锁输出一字不差**

```
WHERE id > 15 AND id < 25  →  X      LOCK_DATA=20
                              X,GAP  LOCK_DATA=30

WHERE id > 15 AND id < 29  →  X      LOCK_DATA=20
                              X,GAP  LOCK_DATA=30
```

25 和 29 落在**同一条缝** `(20,30)` 里，锁的对象完全一样。`LOCK_DATA` 跟条件里的数字无关，只跟它落在哪条缝有关。

**实测②：上界越过记录 30（改成 31），形态立刻变**

```
WHERE id > 15 AND id < 31  →  X      LOCK_DATA=20
                              X      LOCK_DATA=30                      ← 30 变成命中行，改回临键锁
                              X      LOCK_DATA=supremum pseudo-record  ← 31 之后没有真记录
```

第三条是决定性反证：如果 `LOCK_DATA` 表示"边界值"，这里应该写 `31` 或 `+∞`；实际写的是 `supremum pseudo-record`——一个**记录的名字**。因为 31 背后没有真记录可以挂，只能挂到 InnoDB 虚拟的末尾记录上。

三句可以直接用的话：

1. `LOCK_DATA` 回答的是"这把锁挂在哪条记录上"，不是"锁了哪个值"。
2. 缝只能以**右端点**命名（标志位语义是"记录之前的缝"），所以没法锁 `(15,20)` 这种半段缝。
3. 条件从 25 改成 29、从 15 改成 19，只要没跨过一条真记录，锁一模一样。

### 3.3 实测：用 INSERT 去试，看哪段真被锁住

光看 `LOCK_MODE` 字符串还是会绕。换个办法验证：**锁住之后，让另一个会话挨个位置 INSERT，被挡的说明那段真被锁了。**

基线表只有三行 `id = 10, 20, 30`（探针 `probes/probe_gap_visual.py`，跑完自动删库）。

**场景 A：`SELECT * FROM t WHERE id = 20 FOR UPDATE`**（唯一索引，等值，命中）

```
锁：  X,REC_NOT_GAP   LOCK_DATA=20        ← 只有一个点 {20}

INSERT  5  → OK        INSERT 15 → OK
INSERT 25  → OK        INSERT 35 → OK
```

**四个缝全都能插。** 记录锁只锁住了 `20` 这个点，左右两边的缝一点没管。

**场景 B：`SELECT * FROM t WHERE id > 15 AND id < 25 FOR UPDATE`**（范围，命中 20）

```
锁：  X      LOCK_DATA=20     ← 临键锁，覆盖 (10,20]
      X,GAP  LOCK_DATA=30     ← 间隙锁，覆盖 (20,30)

INSERT  5  → OK
INSERT 15  → BLOCKED     ← 落在 (10,20] 里，被临键锁挡住
INSERT 25  → BLOCKED     ← 落在 (20,30) 里，被间隙锁挡住
INSERT 35  → OK
```

**这才是关键对照**：同一条 `20` 的记录，A 场景锁 `{20}`，B 场景锁 `(10,20]`。B 多出来的那一段就是缝，它挡住了 `15`。

**场景 C：`SELECT * FROM t WHERE id > 30 FOR UPDATE`**（范围，一条都没命中）

```
锁：  X      LOCK_DATA=supremum pseudo-record   ← 覆盖 (30, +∞)

INSERT 25 → OK
INSERT 35 → BLOCKED
INSERT 40 → BLOCKED
```

`supremum pseudo-record` 是 InnoDB 虚拟出来的**"序列末尾之后"**那条记录，可以理解成 `+∞`。锁住它 = 锁住最后那段开口的缝。

**场景 D：同 C，但会话改成 RC 隔离级别**

```
锁：  （一个行锁都没有，只剩表级 IX）

INSERT 25 / 35 / 40 → 全部 OK
```

**RC 下没有间隙锁。** 同一句 SQL、同一个数据、只换隔离级别，锁就消失了。

### 3.4 为什么默认给临键锁，而不是只给记录锁

因为**只有记录锁挡不住"插"**——场景 A 已经证明了：锁住 `20`，`15` 和 `25` 照样能插进来。

回到幻读：事务 A `SELECT ... WHERE id > 15 FOR UPDATE` 读到 1 行（只有 20），如果只锁记录 20，事务 B 可以插一条 15，A 再查就变 2 行——同一个事务里两次当前读看到不同结果。

那么反过来，只给间隙锁行不行？也不行：**缝锁住了，`20` 本身还是能被人改。**

所以默认给一个"两样都盖住"的形态：

```
临键锁 (10,20] = 记录锁{20} + 间隙锁(10,20)
```

**它不是"第三种更严格的锁"，是"一次把两种威胁都盖住"。** 一个 UPDATE 语句扫到 20，加的就是这个。

### 3.5 什么时候退化成记录锁

| 条件 | 形态 | 为什么 |
|---|---|---|
| **唯一索引 + 等值 + 命中** | `X,REC_NOT_GAP`（记录锁） | 值唯一，别人想插同值必然主键冲突，缝不用锁 |
| 唯一索引 + 等值 + **未命中** | `X,GAP`（间隙锁） | 没有点可锁，但要防别人插这个值 |
| 非唯一索引 + 等值 | `X`（临键锁） | 可能有多条同值，插同值**会成功**，必须锁缝 |
| 范围条件 | `X`（临键锁） | 范围两端都可能被插入 |
| 无索引 | 全表每条记录都加临键锁 | 扫过的都锁（§二 那 5039 个） |

第 3 行是最容易忽略的：`status='ready'` 这种**非唯一索引等值**，看着是等值，但因为"ready 可以有无数条"，插入一条 ready 是合法的，所以必须锁缝 → **临键锁**，不是记录锁。

### 3.6 间隙锁最反直觉的一点

> **间隙锁之间不互斥。**

两个事务可以**同时**持有同一个缝的间隙锁，互不阻塞。它只和 **INSERT** 冲突（严格说是和 INSERT 要加的"插入意向锁"冲突）。

所以间隙锁的定位是：**它是用来挡插入的，不是用来互斥读写的。** 这也是为什么"两个事务都在同一段范围 `FOR UPDATE`"通常不冲突，但要一起 INSERT 就排队。

### 3.7 易错点

| 认知 | 正确 |
|---|---|
| "改一行就锁一行" | 锁的是**扫过的索引记录**；走二级索引改还会同时锁两棵树（§二 的 25+25） |
| "RR 和 RC 只差在快照" | 还差在**间隙锁**：RR 有，RC 没有（场景 D 实测） |
| "间隙锁会互相阻塞" | 间隙锁之间兼容，只挡 INSERT |
| "主键等值也是临键锁" | 唯一索引等值**命中**才退化成记录锁；未命中仍是间隙锁 |
| "非唯一索引等值 = 记录锁" | 不是，仍是临键锁——插同值会成功，缝必须锁 |
| "`X,GAP` 锁的是 `LOCK_DATA` 那一行" | 它锁的是那一行**左边**的缝，不含这一行 |
| "`LOCK_DATA` 是条件里的边界值" | 它是**锚点记录的 id**；条件值（25）从不进入 InnoDB 层，锁只能挂在真记录上（§3.2.1） |
| "条件改成 29 锁会跟着变" | 25 和 29 在同一条缝里，锁输出一字不差（§3.2.1 实测①） |
| "临键锁是更严格的锁" | 它是"记录锁 + 左侧间隙"的合体，不是升级版 |

### 3.8 面试怎么答（30 秒）

> InnoDB 的锁加在索引记录上，而索引是一条有序序列，所以锁的对象其实是"点和点之间的缝"。记录锁只锁一个点，间隙锁只锁一段缝（不含端点），临键锁是"这个点 + 它左边那段缝"，也就是左开右闭区间，RR 下的默认形态。之所以要临键锁，是因为只有记录锁的话别人可以往旁边插新行造成幻读，只有间隙锁又挡不住改这一行本身。唯一索引等值命中可以退化成记录锁，因为插同值必然冲突；非唯一索引的等值不行，插同值会成功，所以还是临键锁。RC 下不加间隙锁，所以 RC 不防幻读，但锁更少、死锁更少。补一句：`data_locks` 里的 `LOCK_DATA` 是锁挂在哪条索引记录上，不是条件里的边界值，所以 `WHERE id < 25` 在只有 10/20/30 的表上会锁到 `(20,30)` 那段，而不是正好锁到 25。

## §四 间隙锁为什么存在：防幻读（A）

上半场说过：RR 下普通 `SELECT` 是快照读，**不加锁**，读到的是事务开始时的快照。

但**当前读**（`UPDATE` / `FOR UPDATE`）读的是最新值。如果只有记录锁：

```
事务 A：SELECT * FROM documents WHERE kb_id=? FOR UPDATE;   -- 读到 25 行
事务 B：INSERT 一条 kb_id 相同的新行;                        -- 插在空隙里，没人和它抢记录锁
事务 A：再 SELECT ... FOR UPDATE;                            -- 变成 26 行
```

同一个事务里两次**当前读**看到不同的行数——这叫**幻读**。间隙锁就是堵这个：A 把 `kb_id=?` 附近的空隙锁住，B 的 INSERT 只能等。

**所以三条连起来看**：

| 读法 | 加锁 | 靠什么一致 |
|---|---|---|
| 快照读（普通 SELECT） | 不加锁 | MVCC 快照，天然不会幻读 |
| 当前读（`FOR UPDATE`） | 记录锁 + 间隙锁 | 锁住空隙，挡住 INSERT |
| RC 下的当前读 | 只有记录锁 | 不防幻读（RC 允许幻读） |

**面试一句话**：RR 的间隙锁不是"额外的保险"，是"当前读在 RR 下必须防幻读"的直接后果；RC 不做这个保证，所以不加间隙锁——这也是很多互联网公司把隔离级别降到 RC 的原因：**少一类锁，少一类死锁**。

## §五 意向锁（L 了解）

你在 `data_locks` 里总看到一行 `TABLE:IX`。`IX` = **Intention eXclusive**，表级意向排他锁。

**它解决什么问题**：有人要 `LOCK TABLES ... WRITE`（表锁）时，得先知道"表里有没有行被锁着"。总不能扫全部行锁记录——所以每个事务在**加行锁之前**，先在表上挂一个"我要锁某些行"的意向。

| 类型 | 含义 |
|---|---|
| `IS` | 我打算给某些行加 S 锁 |
| `IX` | 我打算给某些行加 X 锁 |
| `S` / `X`（表级） | 我要锁整张表 |

**你要记住的只有一句**：意向锁是 InnoDB 自动加的，**你永远不需要手写、也不会因为它而死锁**（它和行锁的兼容矩阵是设计好的）。看到 `TABLE:IX` 不用管。

## §六 怎么看见锁（A）

### 6.1 三张表

| 表 | 看什么 |
|---|---|
| `performance_schema.data_locks` | 当前**持有**的锁（每一行一个锁对象） |
| `performance_schema.data_lock_waits` | **谁在等谁**（请求方 → 阻塞方） |
| `information_schema.innodb_trx` | 事务列表：开了多久、改了几行、正在跑什么 SQL |

### 6.2 一条能直接用的 SQL

```sql
SELECT
  OBJECT_NAME AS tbl,
  INDEX_NAME  AS idx,
  LOCK_TYPE,
  LOCK_MODE,
  LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = 'kb_dev'
ORDER BY OBJECT_NAME, INDEX_NAME, LOCK_DATA;
```

### 6.3 看"谁在等谁"

```sql
SELECT
  r.OBJECT_NAME            AS tbl,
  r.ENGINE_TRANSACTION_ID  AS waiter,
  b.ENGINE_TRANSACTION_ID  AS blocker,
  r.LOCK_MODE              AS waiting_for,
  b.LOCK_MODE              AS held_by_blocker
FROM performance_schema.data_lock_waits w
JOIN performance_schema.data_locks r ON r.ENGINE_LOCK_ID = w.REQUESTING_ENGINE_LOCK_ID
JOIN performance_schema.data_locks b ON b.ENGINE_LOCK_ID = w.BLOCKING_ENGINE_LOCK_ID;
```

### 6.4 两个坑

1. **普通账号可能看不到别人的锁**（需要 `PROCESS` 权限）。用 `root` 查；`kb` 账号只能看到自己的。
2. `data_locks` 只显示**当前**的锁，事务一提交就消失——排查要趁"卡住的那一刻"查。

## §七 死锁（A）

### 7.1 死锁是什么

```
事务 A：锁住了 k1，想锁 k2
事务 B：锁住了 k2，想锁 k1
```

A 等 B 放 k2，B 等 A 放 k1——**环**。谁都不放，永远等下去。

### 7.2 实测复现（探针里已跑通）

两个连接，**相反顺序**改两行：

```
A: BEGIN; UPDATE ... WHERE id=k1;   -- 拿到 k1
B: BEGIN; UPDATE ... WHERE id=k2;   -- 拿到 k2
A: UPDATE ... WHERE id=k2;          -- 卡住，等 B
B: UPDATE ... WHERE id=k1;          -- 卡住，等 A → 成环
```

实测结果：

```
会话A 结果: ('OK',)
会话B 结果: (1213, 'Deadlock found when trying to get lock; try restarting transaction')
```

**A 成功提交，B 被回滚。** B 收到的不是"等超时"，而是立刻的 `1213`。

### 7.3 InnoDB 怎么处理

1. 每个事务等锁时，记一条"我在等谁" → 构成 **wait-for graph**。
2. 检测到**环** → 说明死锁。
3. 选一个**回滚代价最小**的（一般按 undo log 条目数，即"改得最少"的那个）作为牺牲者，回滚它的整个事务。
4. 牺牲者收到 `ERROR 1213`；其他人继续。

`innodb_deadlock_detect` 默认 `ON`。关掉它死锁就只能靠 `innodb_lock_wait_timeout` 超时（50s）打破——**不要关**。

### 7.4 死锁 vs 锁等待超时

| | 死锁 | 锁等待超时 |
|---|---|---|
| 错误码 | **1213** | **1205** |
| 触发 | 环（互相等） | 等太久（50s） |
| 谁决定 | InnoDB 立刻检测 | 时间到 |
| 事务状态 | **整个事务被回滚** | 只有当前语句失败，事务还在（可继续或回滚） |
| 能否预知 | 不能，随机牺牲一个 | 能（等到 50s 必然发生） |

**这两行区别面试常问**：1213 是"你被选中了"，事务没了，**必须整个重做**；1205 是"你等太久了"，只是这一句失败。

### 7.5 死锁不是 bug

> 死锁是**并发系统的正常现象**，不是代码写错了。
> 你的责任不是"消灭死锁"，而是"**死锁发生时，业务能自动恢复**"（§九）。

### 7.6 易错点

| 认知 | 正确 |
|---|---|
| "死锁说明程序有 bug" | 有环是并发常态，关键是能重试 |
| "死锁会一直等到超时" | 有检测器，立刻杀一个 |
| "被杀的总是后到的" | 按回滚代价选，可能杀先到的 |
| "1213 只回滚那条语句" | **整个事务被回滚**，必须重做全部 |

### 8.1 怎么取

```sql
SHOW ENGINE INNODB STATUS\G
```


### 8.3 怎么读：只看四处

| 看哪里 | 得到什么 |
|---|---|
| `*** (1) TRANSACTION:` 下面那行 SQL | **第 1 个事务最后在跑什么**（这是最关键的线索） |
| `(1) HOLDS` 里的 `asc ...` | 它已经锁住了谁（`6161…` = 一串 a = `aaaa…`） |
| `(1) WAITING FOR` 里的 `asc ...` | 它在等谁 |
| `*** WE ROLL BACK TRANSACTION (2)` | **谁被杀了**（这里是被回滚的第 2 个） |

把两个事务的 HOLDS / WAITING FOR 并排一看，环就出来了：

```
(1) 持 aaaa…  等 kb000001…
(2) 持 kb000001…  等 aaaa…
```

### 8.4 一眼定位代码 bug

这个环的形状说明：**两个事务以相反的顺序改同样的两行**。真实代码里长这样：

```python
# 线程 1                       # 线程 2
update(kb_a)                   update(kb_b)
update(kb_b)                   update(kb_a)
```

或者更隐蔽的版本：**批量更新没有排序**：

```python
for kb_id in kb_ids:           # 两个请求拿到的 kb_ids 顺序不同（集合、dict 遍历、IN 查询返回顺序）
    update(kb_id)
```

修法在 §九·2：**批量更新前按 id 排序**。

### 8.5 一个细节：`locks rec but not gap`

原文里都是 `lock_mode X locks rec but not gap`，而不是临键锁。因为这两条 UPDATE 都是**主键等值**命中——按 §3.2 的规则退化成记录锁。**读死锁日志能反推出用了什么索引**，这是老手才注意的点。

## §九 处理死锁的四种手段（A）

### 9.1 手段一：重试（唯一必须做的）

1213 意味着**整个事务被回滚**，什么都没留下。所以上层必须能"原样再来一次"。

```python
async def with_retry(fn, attempts: int = 3) -> None:
    for i in range(attempts):
        try:
            return await fn()
        except OperationalError as e:
            if e.args[0] != 1213 or i == attempts - 1:
                raise
            await asyncio.sleep(0.05 * (2 ** i))   # 退避：50ms / 100ms / 200ms
```

三个要点：

| 要点 | 为什么 |
|---|---|
| 只重试 1213（和 1205），别重试所有异常 | 别的错重试也不会好 |
| 退避，且**加抖动** | 固定间隔会让多个被杀的请求再次撞车 |
| **业务必须幂等** | 重试意味着"这段逻辑可能执行两次"；有副作用的操作（发邮件、扣款）要能识别重复 |

### 9.2 手段二：统一加锁顺序

死锁的根因是"顺序不一致"。**全局约定一个顺序**（比如按主键升序）就能从源头消除一大类死锁：

```python
for kb_id in sorted(kb_ids):      # ← 这一行能消掉 80% 的批量更新死锁
    update(kb_id)
```

### 9.3 手段三：缩短事务

锁在 COMMIT 才释放。事务里做网络调用、等用户输入、跑大循环——都是"持锁等人"。

```python
# 反例
async with db.begin():
    kb = await repo.get(...)
    embedding = await llm.embed(text)     # ← 网络调用 500ms，锁一直握着
    await repo.update(kb.id, embedding)
```

**规则**：事务里只放 SQL，慢操作放到事务外。

### 9.4 手段四：把"读-改-写"压成一条原子语句

大部分"我要先 SELECT 再 UPDATE"的场景，其实一条语句就能做完，根本不需要显式锁：

```sql
-- 不要这样（两步，中间有空隙，还得加锁）
SELECT doc_count FROM knowledge_bases WHERE id=?;
UPDATE knowledge_bases SET doc_count = ? WHERE id=?;

-- 这样（一条语句，原子，无需 FOR UPDATE）
UPDATE knowledge_bases SET doc_count = doc_count + 1 WHERE id=?;
```

### 9.5 三种错误做法

| 做法 | 为什么错 |
|---|---|
| 调大 `innodb_lock_wait_timeout` | 死锁不是等待问题，调大只会让卡住的请求卡更久 |
| 无上限重试 | 真死锁（逻辑环）会无限重试，把 CPU 打满 |
| 用 `FOR UPDATE` 包住一切 | 每多一个锁就多一份死锁概率 |

## §十 锁等待与长事务（A）

### 10.1 两个参数

| 参数 | 默认 | 作用 |
|---|---|---|
| `innodb_lock_wait_timeout` | **50** 秒 | 等锁超过这个时间 → `ERROR 1205` |
| `innodb_deadlock_detect` | ON | 检测到环立刻杀一个 |

### 10.2 查长事务

```sql
SELECT
  trx_id,
  trx_state,
  TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
  trx_rows_locked,
  trx_query
FROM information_schema.innodb_trx
ORDER BY age_sec DESC;
```

`age_sec` 很大 + `trx_rows_locked` 很多 = 事故进行中。

### 10.3 你昨天亲手遇到过一次

上半场那个 `39.87 秒`：某个窗口开了事务没提交，后面所有 `FOR UPDATE` 全排在它后面。**这就是线上"偶发接口超时"的一大来源**——不是慢查询，是有人握着锁不放。

排查口径：**先看 `innodb_trx` 里有没有长事务，再看慢查询日志。**

### 11.1 四种写法对比

| 写法 | SQL | 会丢吗 | 会死锁吗 | 评价 |
|---|---|---|---|---|
| ① 读-改-写 | `SELECT` + `UPDATE SET x=<算好的>` | **会**（上半场已验证） | 可能 | ❌ 禁止 |
| ② 原子表达式 | `UPDATE ... SET x = x + ?` | **不会** | 不会（单语句） | ✅ **首选** |
| ③ 悲观锁 | `SELECT ... FOR UPDATE` + `UPDATE` | 不会 | 可能 | 只在"算的时候依赖别的行"时才用 |
| ④ 乐观锁 | `UPDATE ... WHERE version = ?` | 不会（靠重试） | 不会 | 冲突少时用，需要重试循环 |

### 11.2 目标形态（2026-11-17 已按实测修订）

```python
def incr_doc_count(self, kb_id: UUID, delta: int) -> None:
    """原子自增；kb 不存在抛 NotFoundError。"""
    stmt = (
        update(KnowledgeBase)
        .where(KnowledgeBase.id == kb_id)
        .values(doc_count=KnowledgeBase.doc_count + delta)
    )
    result = cast("CursorResult[Any]", self.session.execute(stmt))
    if result.rowcount == 0:
        raise NotFoundError(f"kb {kb_id} not found")
```

三个要点：

1. `KnowledgeBase.doc_count + delta` 是**列表达式**，会编译成 `SET doc_count = doc_count + ?`——加法在库里做。
2. `result.rowcount == 0` **顺便完成了"存在性判断"**，不需要先 `SELECT` 一次（省一次往返，也省一个锁窗口）。`cast` 是给 mypy 看的：`session.execute()` 的静态类型是 `Result`，`rowcount` 在子类 `CursorResult` 上。
3. 不需要 `FOR UPDATE`：单条 UPDATE 本身就是原子的。

> **签名为什么是 `-> None` 不是 `-> int`**（2026-11-17 实测定案）：初稿写了"返回变更后的值"，但 MySQL 8 **不支持 `UPDATE ... RETURNING`**——想拿回自增后的值只有两条路：再发一条 SELECT（SQL 变 2 条，违背"省往返"的初衷），或用 SQLite 方言的 RETURNING（测试能过、上生产 MySQL 就炸）。所以按 protocol 的 `-> None` 收口；调用方需要新值时自己再读。
>
> 另：初稿末尾的 `self.session.flush()` 已删——Core 的 update 语句在 `execute()` 时就已发出 SQL，flush 管的是 ORM 积攒的变更，这里没有东西可推。

### 11.3 什么时候才真的需要 `FOR UPDATE`

只有当"**下一步的决策依赖读到的值**"时：

```python
# 场景：库存不足要报错，而不是减成负数
row = session.execute(
    select(Product).where(Product.id == pid).with_for_update()
).scalar_one()
if row.stock < qty:
    raise InsufficientStock
row.stock -= qty
```

这里"判断够不够"和"扣减"必须是同一个锁保护下的连续动作，否则两个请求都判断"够"然后都扣。

**而 `doc_count + 1` 没有"够不够"的判断**，所以不需要锁。

## §十四 面试问法（A）

### 30 秒版

> InnoDB 的锁加在**索引记录**上，不是行上——所以 `UPDATE` 的 `WHERE` 列没索引时会锁住扫过的所有记录，实测 5000 行的表能加到 5039 个记录锁。锁有三种形态：记录锁、间隙锁、临键锁；RR 默认临键锁，用来防幻读，RC 下没有间隙锁。两个事务以相反顺序加锁就会成环，InnoDB 用 wait-for graph 检测到后，选择回滚代价小的那个，被选中的收到 1213，**整个事务被回滚**。所以死锁的应对不是"消灭它"，而是**统一加锁顺序 + 业务可重试 + 事务尽量短**。

### 追问一层（机制边界）

| 追问 | 怎么答 |
|---|---|
| 为什么主键等值不是临键锁？ | 唯一索引等值命中不可能有重复值插入，间隙锁没必要，退化成记录锁（实测 `X,REC_NOT_GAP`） |
| 间隙锁之间会互斥吗？ | 不会。它只和插入意向锁冲突，作用是挡 INSERT |
| 1213 和 1205 有什么区别？ | 1213 是检测到环，整个事务被回滚；1205 是等锁超时（默认 50s），只是当前语句失败 |
| 二级索引加锁会加几次？ | 两次：二级索引记录 + 回表后的聚簇索引记录；实测 25 行 → 25 + 25 个锁 |
| 为什么公司把隔离级别设成 RC？ | RC 没有间隙锁，少一类锁就少一类死锁；代价是允许幻读，靠业务或唯一约束兜底 |

### 追问二层（故障现场）

| 追问 | 怎么答 |
|---|---|
| 线上突然大量 1213，怎么查？ | ① `innodb_trx` 看长事务 ② `SHOW ENGINE INNODB STATUS` 抽死锁段，看两个事务的 HOLDS/WAITING FOR 是不是相反顺序 ③ 对照业务代码找"批量更新未排序"或"事务里做网络调用" |
| 死锁日志里 `asc aaaa…` 是什么？ | 被锁记录的字段值——`data_locks` / 死锁日志把索引记录的字段按顺序打印，字符串字段直接给 ASCII，这里就是一串 a 的 kb_id |
| 加了索引为什么反而更容易死锁？ | 锁的粒度变细、数量变多（一次 UPDATE 可能锁两个索引上的多条记录），并发交叉的机会变多；但锁全表的代价更大，不能因噎废食 |
| 怎么证明你的重试是有效的？ | 造一个稳定复现的死锁（相反顺序），跑 100 次带重试的调用，统计 1213 次数 > 0 且最终成功 == 100 |

### 追问三层（场景落地）

> "你的 RAG 服务里，一个知识库被多人同时上传文档、同时删除文档。上传要 `doc_count+1`，删除要 `doc_count-1`，还要写 `documents` 行。这中间怎么保证不死锁、不丢数？"

答要点：① 计数用原子表达式（单语句、无读改写窗口）② 文档行的插入/删除和计数更新放**同一个事务**，保证"文档数 == 实际行数"③ 事务里不做 embedding 调用（慢操作移出去，或用任务表 + 后台 worker）④ 批量删除按 `id` 排序 ⑤ 外层捕获 1213/1205 重试，业务幂等（用 `document_id` 去重）⑥ 有指标：`doc_count != COUNT(*)` 的漂移检测 SQL 定时跑。

8. 死锁日志里哪四行是必看的？

<details>
<summary>答案（先自己写完再展开）</summary>

1. **索引记录**。没有索引就无法定位，只能全表扫，InnoDB 会给扫过的每条记录加锁（实测 5039 个）。
2. 记录锁挡"改/删这一条"；间隙锁挡"往空隙里 INSERT"；临键锁是两者合体（记录 + 前面的间隙），RR 默认。
3. `X` = 临键锁（记录 + 前置间隙）；`X,REC_NOT_GAP` = 纯记录锁；`X,GAP` = 纯间隙锁。
4. 唯一索引等值命中时，不可能插入重复值，间隙没有保护价值，优化器退化为记录锁。
5. RR 加间隙锁防幻读，RC 不加（允许幻读）。因为 RR 承诺"同一事务两次当前读结果一致"，必须挡住 INSERT。
6. 改一行要同时改二级索引项和聚簇索引记录，两棵树上各加一次锁（实测 25 行 → 25 + 25）。
7. 1213 = 检测到死锁环，**整个事务被回滚**，必须重做；1205 = 锁等待超过 `innodb_lock_wait_timeout`（默认 50s），**只有当前语句失败**，事务还在。
8. ① 每个事务最后执行的 SQL ② 各自 HOLDS 的记录值 ③ 各自 WAITING FOR 的记录值 ④ `WE ROLL BACK TRANSACTION (n)`。
9. `for kb_id in sorted(kb_ids):`（统一加锁顺序）。
10. 单条 UPDATE 本身原子：加法在库内、拿到行锁之后对最新已提交值做，没有"读-算-写"的窗口，也不需要额外的锁来保护判断（因为它不做判断）。

</details>
