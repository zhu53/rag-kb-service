## 四、贯穿全周的五个模式（比单个知识点值钱）

### 模式 1：**报告成功 ≠ 实际成功**（本周出现 4 次）
`flush` 报成功 ≠ 落库；pytest-cov 打印 FAIL ≠ 拦住；`[PASS]` 行 ≠ 该段真过；测试 200 绿 ≠ 没打真库。
**统一对策：判据来自数据（SQL 条数 / `coverage json` 浮点 / 另一个连接的 SELECT），不来自工具的口头表态。**

### 模式 2：**顺序即契约，工具不替你排**
Starlette 路由按注册顺序匹配（StaticFiles 必须最后）；迁移 op 必须先建后拆（1553）；
DDL 隐式提交会让"库结构 ≠ alembic_version"半途脱节。autogenerate 生成顺序**不可信，人工重排是工序**。

### 模式 3：**归因要落在保证人头上**
D6 review 三题同一教训：不变式归给"数据库/框架/工具"，但真正的保证人在自家代码
（`doc_count` 靠 create/delete 两个写点；`_commit` 靠 handler 传 `session=session`；override 打在 fixture 实例上）。
**收口三问：这段代码假设了什么？谁在保证它？它失效时我会不会知道？**

### 模式 4：**快照读 vs 当前读是并发问题的总开关**
普通 SELECT 走 MVCC 快照、不加锁；UPDATE/DELETE/`FOR UPDATE` 才是当前读。
丢失更新 = 两个事务基于同一条快照算出"过期的新值"——错在读之前的"算"，不在读本身。
D7 第 3 题就是在这里错的（"最终 +2" / "select 是当前读"），当堂重写还债成功。

### 模式 5：**测试介质分工 + 本地绿要先问来源**
sqlite 内存库管业务逻辑（快、隔离），真 MySQL 管事务真伪与方言（1101/1553 sqlite 根本测不出）。
**本地绿 ≠ 对**：D7 CI 红的测试本地一直是绿的，绿来自"恰好有 .env 指向有表的 MySQL"。
判定句：这条绿来自哪个依赖？它该被替换吗？替换发生在哪个对象上？

## 五、30 秒答案集（面试速答）

1. **flush 和 commit 的区别？** flush 把内存变更翻译成 SQL 发给库但未提交，本会话可见、回滚即没；commit = 自动 flush + 提交事务，跨连接可见、持久。
2. **commit 为什么放 service？** 谁拥有"这次操作到哪才算完"的知识谁握 commit。repo 只认识单表，跨 repo 的原子性只有 service 看得见；commit 放 repo，多写点操作要么半成品要么没人提交。
3. **两个事务并发改同一行会怎样？** 普通 SELECT 是快照读不加锁，读-改-写会丢更新（最终只 +1）；`UPDATE SET x = x + 1` 是一条当前读语句 + 行锁持到事务结束，代价是并发写排队。
4. **RR 和 RC 的本质差别？** 快照建立时机：RC 每条语句一个快照，RR 事务内第一次读建快照并沿用——所以 RR 下可重复读，但也更容易基于过期快照算错。
5. **怎么判断一条 SQL 慢在哪？** `EXPLAIN`：`type`（ALL 全表 / index 全索引扫 / ref / range）、`key` 真用上的索引、`rows` 预估扫描行数、`Extra` 有没有 `Using filesort`。加索引前后各跑一遍对比。
6. **复合索引列顺序怎么定？** 查询形状优先：等值条件列最左（否则定位不了），排序列跟后（沿索引序免 filesort）；多个等值列才轮到区分度排序。
7. **为什么上线不能用 create_all？** 它只会从零建表，不会改已存在的表、不能回滚；上线是"从当前版本演进到下一版"，有历史状态要维护。测试没历史状态，create_all 反而合法。
8. **1101 是什么坑？** MySQL 不许 TEXT/BLOB 有默认值，`server_default=''` 直接炸；且 DDL 隐式提交，库结构和 alembic_version 脱节。修法：模型与迁移两边同步删。
9. **1553 是什么坑？** FK 列必须始终有索引覆盖。先拆单列索引再建复合索引会撞 1553。规矩：先建后拆，downgrade 同理。
10. **N+1 怎么发现怎么解？** SQL 计数探针（查 1 次列表 + N 次详情）；解法 `selectinload`（两条 SQL）或一次 JOIN，取舍在"列表大小 × 行宽"。
