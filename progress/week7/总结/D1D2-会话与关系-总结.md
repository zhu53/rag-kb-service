## 二、逐个知识点讲透

### 1. flush vs commit：事务边界归属

- **一句话定义**：flush 把 ORM 积攒的变更翻译成 SQL 发给数据库；commit 结束事务使变更对其他会话可见。
- **为什么存在**：没有 flush，`session.add(obj)` 后拿不到自增主键、关联对象无法引用；没有 commit/rollback 的显式边界，"多个操作要么全成要么全不算"就无从谈起——这是事务存在的根本理由。
- **怎么用**（本项目真实片段）：`kb_repo.create()` 只 `flush()`，注释明说"commit 是 service 层的事"——repo 层发 SQL，service 层决定边界：

```python
self.session.add(obj)
self.session.flush()   # INSERT 发出去拿到主键；不 commit
return obj.to_row()
```

- **底层机制**：Session 内部 autobegin——第一个操作自动 `BEGIN`；flush 走 unit of work 按依赖排序生成 SQL；commit = flush + COMMIT + 按 `expire_on_commit` 策略过期对象；rollback = COMMIT 的否定，未提交的全部丢弃。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | repo 里随手 commit | 一次 service 调用多个 repo 操作被切成多个事务，半途失败回不去 | repo 只 flush，commit 收在 service |
| 2 | 以为 add 即入库 | 另一会话查不到该行 | flush 才发 SQL，commit 才可见 |
| 3 | flush 后以为回滚能撤 INSERT | close 后行还在（如果已 commit） | 只有未 commit 的才会被回滚掉 |

- **面试问法**："SQLAlchemy 里 flush 和 commit 的区别？" —— 30 秒版：**flush 是把 ORM 攒的变更翻译成 SQL 发出去，事务还开着；commit 是先 flush 再 COMMIT，变更才对别人可见。我们项目里 repo 只 flush，事务边界收在 service 层，这样一次业务操作里多个 repo 动作天然在同一事务里。**
- **追问链**：
  - → *"那 autobegin 是什么？"* 第一个操作前 Session 自动 BEGIN，不需要显式 begin；显式 `with session.begin()` 是把提交也托管给上下文。
  - → *"flush 发出去的 SQL 失败了会怎样？"* 异常抛出、事务标记为需回滚；必须 rollback 才能继续用这个 session，否则后续操作报 PendingRollbackError。
  - → *"你们项目里一次上传文档要动几张表，怎么保证一起成功？"* documents 插入 + kb 的 doc_count 自增在同一个 service 方法、同一 session、同一次 commit；并发计数我们用单条原子 UPDATE（见 D3-D4 总结）。

### 2. get_db 依赖的两个隐藏出口

- **一句话定义**：FastAPI 的 yield 依赖，请求开始给 handler 一个 Session，请求结束按成败走 close 或 rollback+close。
- **为什么存在**：Session 必须请求级——没有它，要么全局单例串请求（事务互相污染），要么每个 handler 手写 try/finally（漏写 = 连接泄漏）。
- **怎么用**（`core/db.py`）：

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    except Exception:
        db.rollback()
        raise          # 原样抛出，不能吞
    finally:
        db.close()
```

- **底层机制**：FastAPI 对 yield 依赖的处理分两步——先取 yield 值喂给 handler 生成响应；响应发完**回到生成器执行收尾段**。实测（`test_get_db_closes_session_on_normal_exit`）：正常路径只 close，**不自动 commit**——commit 责任在 service 层；异常路径先 rollback 再 close 且异常原样抛（`test_get_db_rolls_back_then_closes_on_error`）。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 在 except 里吞掉异常不 raise | handler 报错返回 200 空响应 | `raise` 原样抛 |
| 2 | 以为 get_db 会帮 commit | 数据静默丢失 | commit 写在 service 层 |
| 3 | 在依赖外长期持有 session | 后台任务里用请求的 session → 已关闭 | 后台任务自建 session |

- **面试问法**："FastAPI 里数据库依赖怎么写，请求结束时发生什么？" —— 30 秒版：**yield 依赖，try 里 yield session，except 里 rollback 再 raise，finally 里 close。FastAPI 在响应发完后回来执行收尾段，正常只 close，异常先 rollback。我们实测过两条路径，commit 不在这里做。**
- **追问链**：
  - → *"为什么 close 对未提交事务等价于回滚？"* 连接归还池时驱动回滚未提交事务——提交过的才落库（`test_close_without_commit_rolls_back` 实证）。
  - → *"依赖收尾发生在哪一步，响应之后还是之前？"* 之后——响应生成并发出后才执行收尾段，所以收尾里改不了响应。
  - → *"并发 1000 请求，SessionLocal 怎么撑？"* 进程级单例的 sessionmaker + 连接池复用连接，session 每请求新建很轻；池满会排队或报超时，池大小要配。

### 3. N+1：懒加载的 SQL 账单

- **一句话定义**：查 1 次父表后逐个访问子集合，每次触发 1 条 SQL，一共 1+N 条。
- **为什么存在**：relationship 默认懒加载——"用到才查"对单对象合理，对列表页是灾难；不知道 N+1 的后端会在列表接口里埋下随数据量线性恶化的性能债。
- **怎么用**：

```python
# 病灶：for kb in kbs: kb.documents  ← 每次循环一条 SQL
stmt = select(KnowledgeBase).options(
    selectinload(KnowledgeBase.documents)   # 解法一：两条 SQL，第二条 WHERE kb_id IN (...)
)
# 或 joinedload：一条 SQL，JOIN 拼宽表
```

- **底层机制**：懒加载在**属性首次访问**时才发 SQL（不是查询时）；selectinload 用 IN 把 N 个父的主键打包成第二条批量 SQL；joinedload 用 LEFT OUTER JOIN 一次取回（一对多会把子行重复摊开，分页时行数失真——所以一对多列表选 selectinload）。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 列表页循环访问 relationship | SQL 日志 1+N 条、接口变慢 | 列表查询加 selectinload |
| 2 | 一对多用 joinedload 还带 limit | 分页总数对不上（JOIN 摊开） | 一对多选 selectinload，多对一才 joinedload |
| 3 | 只看功能不看 SQL 条数 | N+1 上线才被发现 | 探针/日志里数 SQL 条数（业务链条三问的可复现指标） |

- **面试问法**："什么是 N+1，怎么解决？" —— 30 秒版：**查列表后循环访问关联属性，懒加载让每行都发一条 SQL，1+N 条。解法是预加载：selectinload 两条 SQL 走 IN，适合一对多；joinedload 一条 SQL 走 JOIN，适合多对一。我们项目用探针实测过 1+N 条改两条的账单。**
- **追问链**：
  - → *"懒加载机制是什么？"* relationship 属性首次访问时向 session 要 SQL；identity map 只缓存对象，不预取集合。
  - → *"怎么在自己代码里发现 N+1？"* 开 SQL echo 或计数探针对账单；特征是同一条 SQL 模板重复 N 次只有参数不同。
  - → *"流量涨十倍这个接口先死在哪？"* 死在 N+1 的往返次数（网络 RTT × N）；先修预加载，再谈缓存与分页。

### 4. Engine 进程级单例 / Session 请求级

- **一句话定义**：Engine（连接池）全局建一次；Session 是一次事务对话的单位，每个请求新建。
- **为什么存在**：建连接昂贵，必须池化复用；而事务和 identity map 必须按请求隔离，否则互相看到半提交数据。
- **怎么用**：`SessionLocal = sessionmaker(bind=engine)` 进程级建一次；`get_db` 里每请求 `SessionLocal()`。
- **底层机制**：Engine 持有连接池（QueuePool），close 的 session 把连接还池而不是关连接；Session 的 identity map 与事务状态都是实例级的。
- **易错点**：每请求建 Engine（池反复重建、连接暴涨）；全局共用一个 Session（并发请求串事务）；以为 `sessionmaker()` 返回的是 session（它是工厂）。
- **面试问法**：30 秒版——**Engine 是连接池，进程级单例；Session 是事务加身份映射的对话，请求级新建。close 的 session 只是把连接还池。**
- **追问链**：→ *"池满了怎样？"* 默认排队等/超时报错，pool_size 和 max_overflow 可调。→ *"Session 线程安全吗？"* 不是，一请求一个正是为了绕开它。→ *"你们怎么保证单例？"* 模块级创建 + import 复用（`db.py`）。

### 5. expire_on_commit 与 detached

- **一句话定义**：commit 后对象属性被标记过期，下次访问重新 SELECT；session 关闭后对象变 detached，再访问属性直接抛错。
- **为什么存在**：保证 commit 后读到的状态与数据库一致（别人可能改了）；detached 防止"session 死了还在拿它当活马使"。
- **怎么用**：项目实测过两种取舍，最终用默认（commit 后过期）；需要跨 session 传递数据时先 `to_row()` 转纯 dict。
- **底层机制**：commit 时对 identity map 里所有对象打 expired 标记；属性访问触发 refresh（发 SELECT）；session.close() 后对象脱离 session，无刷新通道 → DetachedInstanceError。
- **易错点**：commit 后在响应序列化阶段访问 ORM 属性 → 隐形 SELECT 风暴；API 层直接返回 ORM 对象 → detached 炸；正解是**在 session 活着的时候转 DTO**。
- **面试问法**：30 秒版——**commit 后属性过期，访问才重查；session 关了对象就 detached，再摸属性抛 DetachedInstanceError。所以序列化要在 session 内完成，或提前转 dict。**
- **追问链**：→ *"为什么默认要过期？"* 换取读到的数据与库一致；关掉换来性能但可能读到陈旧值。→ *"我们项目怎么选？"* 默认 + session 内转 DTO。→ *"接口突然变慢查哪？"* 先看是不是响应阶段触发了隐性懒加载/刷新（和 N+1 同源）。

### 6. ForeignKey / relationship / back_populates 三分

- **一句话定义**：ForeignKey 是数据库层的外键法律；relationship 是 Python 层的对象导航；back_populates 是两端的反向登记。
- **为什么存在**：外键保证数据一致但导航不便；relationship 让 `kb.documents` 可用；双向关系两端都要登记才不打架。
- **怎么用**（项目三张表）：documents 表 `kb_id = mapped_column(ForeignKey("knowledge_bases.id", ondelete="CASCADE"))`，KnowledgeBase 侧 `documents: relationship(back_populates="kb")`。
- **底层机制**：ForeignKey 生成 DDL 约束；relationship 靠外键推断 JOIN 条件，访问时懒加载/预加载；back_populates 让双向赋值自动同步两端。
- **易错点**：只建 relationship 不建 ForeignKey（推断失败报错）；双向只写单边（赋值不同步）；以为 relationship 删父行会删子行（那是 cascade 的事）。
- **面试问法**：30 秒版——**ForeignKey 管 DDL 一致性，relationship 管 Python 导航，back_populates 管双向同步。一个是法律、一个是便利、一个是登记簿。**
- **追问链**：→ *"外键删父行会怎样？"* 看约束：CASCADE 删子、RESTRICT 拒绝；我们 documents 对 kbs 用 CASCADE。→ *"ORM cascade 和它什么关系？"* ORM cascade 只管 session 内对象级联（如 delete-orphan），骗不过数据库。→ *"上线了还能加外键吗？"* 能但要锁表风险，大表用 pt-osc 之类在线变更。

### 7. 级联的两种：数据库 ON DELETE vs ORM cascade

- **一句话定义**：数据库级联由外键 DDL 定义，SQL 层生效；ORM 级联由 relationship 参数定义，只对 session 管辖的对象生效。
- **为什么存在**：SQL 删除要有兜底规则；ORM 删除（session.delete）需要把对象图里相关对象一起处理——两者管的是不同层。
- **怎么用**：数据删除靠 `ondelete="CASCADE"`；ORM 的 `cascade="all, delete-orphan"` 只在需要"删父连带删 session 里的子"时才开。
- **底层机制**：ON DELETE 写进建表语句，绕过 ORM 直接在库生效；ORM cascade 在 flush 时翻译成额外的 DELETE 语句。
- **易错点**：以为配了 ORM cascade 数据库就不需要外键规则；SQLite 默认不开外键强制（`PRAGMA foreign_keys=ON` 才生效）导致测试里 CASCADE 静默失效。
- **面试问法**：30 秒版——**数据库级联写在外键上、SQL 层生效；ORM cascade 只管 session 里的对象图。别混，混了就会出现"测试里能删、生产里被外键拒绝"这类分层错位。**
- **追问链**：→ *"SQLite 测试和 MySQL 生产行为会不一致吗？"* 会——外键开关默认值不同，所以 conftest 里显式开 PRAGMA。→ *"删除大父节点的子行很慢怎么办？"* 分批删或软删标记。→ *"我们项目删 kb 会怎样？"* MySQL 外键 CASCADE 连带删 documents/chunks，doc_count 不用手工清。

### 8. identity map

- **一句话定义**：session 内按主键缓存对象，同一行在同 session 里只可能有一个对象实例。
- **为什么存在**：避免同一行两个对象导致脏写；重复查询免发 SQL。
- **怎么用**：需要"确定拿到同一个对象"时用 `session.get(KnowledgeBase, id)`——先查 map 命中即返回；普通查询走 SQL 后按主键合并进 map。**注意：identity map 只缓存整行对象，不缓存集合、不缓存任意查询结果**——AI 初版把它的结构写错（当成全量查询缓存），实测修正。
- **底层机制**：Session 内维护"主键 → 对象实例"的字典；flush 时按 unit of work 把新对象登记进去；select 走完 SQL 后按主键合并——同主键只保留一个实例，重复查询靠它免发 SQL。它不失效但对象会过期：commit 后对象留在 map 里、属性访问触发刷新。
- **易错点**：以为第二次 select 同条件不发 SQL（普通 select 仍发，只做合并）；以为 map 永不失效（commit 后对象过期但仍在 map，属性访问触发刷新）。
- **面试问法**：30 秒版——**session 里按主键存一份对象，get 命中直接返回不发 SQL；它保证同一行一个实例，但普通 select 照样发 SQL。**
- **追问链**：→ *"两级缓存（MyBatis）跟它像吗？"* 思路同源，但 SQLAlchemy 只有 session 级，没有跨 session 的二级缓存。→ *"长会话里 map 会膨胀吗？"* 会，长生命周期 session 应避免（也是"Session 请求级"的理由之一）。

### 9. Session 泄漏：`database is locked`

- **一句话定义**：session 不 close → 事务挂着 → 连接和锁不释放 → 别的写操作等锁超时。
- **为什么存在**：演示"泄漏不是不关文件那种显性错误，而是安静地把锁攥在手里"。
- **怎么用**：防线就是 get_db 的 finally close；线上抓长事务用 `information_schema.innodb_trx` 按 `trx_started` 排序（我们的 `see_locks.py` 就这么干）；SQLite 复现最容易——一个未关闭的写事务让整个库锁死。
- **底层机制**：session 不 close → 连接不还池、事务不收尾；SQLite 文件锁下别的写操作直接报 `database is locked`；MySQL 下症状是长事务持有行锁、后面全部排队（D4 交付物 1 的 5039 锁事故就是它的放大版）。
- **易错点**：只在 happy path close（异常路径漏掉）→ 用 yield 依赖的 finally 兜住；后台任务复用请求 session → 泄漏到请求外。
- **面试问法**：30 秒版——**Session 泄漏 = 事务不收尾 = 锁不释放，SQLite 报 database is locked，MySQL 表现为长事务堵人。防线是 get_db 的 finally close。**
- **追问链**：→ *"线上怎么抓长事务？"* `information_schema.innodb_trx` 按 trx_started 排序（我们 `see_locks.py` 就这么干）。→ *"泄漏的根因常是什么？*" 依赖没走 finally、或 service 里自建 session 忘收尾。

## 三、30 秒答案集

1. **flush vs commit**：flush 发 SQL 不结束事务；commit = flush + COMMIT，结束事务才可见。
2. **事务边界在哪层**：repo 只 flush，service 决定 commit/rollback——一次业务多个 repo 动作同事务。
3. **autobegin**：Session 第一个操作自动 BEGIN，不用手写 begin。
4. **get_db 出口**：正常只 close；异常 rollback 后 raise 再 close；都不自动 commit。
5. **Session 请求级、Engine 进程级**：事务和身份映射按请求隔离；连接靠池复用。
6. **expire_on_commit**：commit 后属性过期，访问才重查；关掉省查询但可能读旧值。
7. **detached**：session 关闭后对象摸属性抛 DetachedInstanceError；session 内转 DTO。
8. **N+1**：列表页循环访问 relationship，1+N 条 SQL；selectinload 两条 IN、joinedload 一条 JOIN。
9. **selectinload vs joinedload**：一对多选 selectinload（JOIN 会摊开行数）；多对一选 joinedload。
10. **三个词三分**：ForeignKey 数据库法律、relationship Python 导航、back_populates 双向登记。
11. **级联两层**：ON DELETE CASCADE 在 SQL 层永远生效；ORM cascade 只管 session 对象图。
12. **identity map**：session 内按主键一份实例；get 命中免 SQL；普通 select 照发。
13. **Session 泄漏**：不 close = 事务挂 = 锁不放；SQLite 报 locked，MySQL 堵人。
14. **为什么懂 SQL 还要 ORM**：ORM 管工程效率（边界/复用/防注入），SQL 能力决定你能不能诊断它生成的 SQL。

## 四、白板手写靶

```python
# 靶 1：get_db（默写，含两个出口）
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    except Exception:
        db.rollback()
        raise
    finally:
        db.close()
# 要点：except 里必须 raise；正常路径不 commit
```

# 靶 2：一对多两表模型（ForeignKey + relationship + back_populates）
class KnowledgeBase(Base):
    __tablename__ = "knowledge_bases"
    id: Mapped[Uuid] = mapped_column(primary_key=True)
    documents: Mapped[list["Document"]] = relationship(back_populates="kb")

class Document(Base):

## 五、踩坑实录

| 坑 | 现象 | 教训 |
|---|---|---|
| AI 把 identity map 讲成"全量查询缓存" | 我按它理解后自测对不上 | 结构性断言必须实测；identity map 只按主键存对象 |

| "这东西不存在"该谁判断 | 404 语义在 repo/service 间漂 | D2 §5.6 定案：存在性判断在 repo（查得到查不到），业务错误翻译在 service |

## 六、可以讲成故事的三段

1. **flush 不是 commit**。背景：我写 repo 的 create 时顺手 commit 了。我以为是"写完就保存，没问题"。实际是把 service 一次业务里的三个 repo 操作切成了三个独立事务，中途失败前面的已经落库——"要么全成要么全不算"被我亲手拆了。教训：**repo 发 SQL，service 定边界**。
2. **N+1 是用出来的，不是看出来的**。背景：D2 探针跑列表接口。我以为"加了 relationship 就是优化过了"。实际 SQL 日志里 1 条后面整整齐齐排着 N 条同模板查询，行数翻倍账单翻倍。教训：**relationship 的默认懒加载是给单对象设计的，列表页不预加载就是负债**。
3. **测试绿 ≠ 生产行为一致**。背景：级联删除在 SQLite 测试里一切正常。我以为是同一段代码到哪都一样。实际 SQLite 默认不强制外键，CASCADE 根本没执行，换 MySQL 才暴露。教训：**测试库和真实库的默认行为差异，要在 conftest 里显式抹平**。
