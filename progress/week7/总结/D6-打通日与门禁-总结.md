## 二、逐个知识点讲透

### 1. 事务边界落地：commit 在 service + session 注入

- **一句话定义**：事务边界写在 service 层（每次业务操作末尾 `_commit()`），session 由 FastAPI 依赖注入一路传进来——两层各管一段，谁也不越界。
- **为什么存在**：repo 只认识单表，"这次操作到哪才算完"只有 service 知道；session 从哪来（请求作用域）只有框架知道。两层分工错了就是 D5 探针 A 段的断链。
- **怎么用**（本项目真实落点）：

```python
# api/v1/knowledge_bases.py —— handler 只负责取依赖、组 service
def create_kb(..., session: Session = Depends(get_db)):
    service = KBService(KBRepository(session))
    ...
# kb_service.py —— 事务边界收在这
def _commit(self) -> None:
    if self._session is not None:
        self._session.commit()
# 异常兜底：get_db 的 finally 里 rollback + close（D1 结论）
```

- **底层机制**：`Depends(get_db)` 每请求 yield 一个 Session，请求结束 `finally` 关闭；service 拿到的 repo 持有同一 session，所有写点天然在一个事务里。commit 之后的异常（如 response 序列化失败）回滚不了——这是已知代价，写进注释而不是当它不存在。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | handler 写 `KBService(KBRepository(session))` 漏传 `session=session` | 201 但库 0 行，三层无报错 | 构造时校验，缺了当场 `ValueError` |
| 2 | commit 放 repo | 跨两个 repo 的操作没法一个事务 | 谁拥有"操作到哪算完"的知识谁握 commit |
| 3 | 后台任务复用请求 session | 请求结束 session 关了，后台任务炸 | `run_index` 自己开 session 自己 commit |

- **面试问法**："你的事务边界放在哪，为什么？" —— 30 秒版：**放 service。repo 只认识单表，跨写点的原子性只有 service 看得见；session 用 Depends(get_db) 按请求注入，请求结束统一 rollback/close。我们真实踩过漏传 session 的坑：接口 201、本会话查得到、MySQL 一行没有，三层都静默——所以后来构造函数里缺 session 直接抛 ValueError。**
- **追问链**：
  - → *"为什么不用中间件统一 commit？"* 一个请求可能多次业务操作各有边界；统一 commit 会把读请求也进事务，边界知识还是在 service 手里最准。
  - → *"commit 后还能回滚吗？"* 不能。已知代价：序列化失败等 commit 后异常回滚不了——边界画在哪，责任就画在哪。
  - → *"后台任务怎么办？"* 不复用请求 session——请求生命周期和任务生命周期不同，任务自己开 session 自己 commit。

### 2. DDL 半途状态：1101 活体标本

- **一句话定义**：迁移里第 1 条 op 成功即隐式提交；第 2 条炸时，库的真实结构已经领先于 `alembic_version` 记录——两者脱节。
- **为什么存在**：MySQL 的 DDL 不进事务（数据字典变更），alembic_version 更新在整个迁移成功之后——中间任何失败都制造脱节。
- **怎么用**（本次事故还原）：`server_default=""` 渲染成 `ADD COLUMN content TEXT NOT NULL DEFAULT ''` → `1101 BLOB, TEXT ... can't have a default value`。此时 `uq_chunk_doc_seq`（排在 add_column **之前**）已建成功并提交，版本号还停在 `b0846e5e87de`。
- **底层机制**：修复 = 手工 `DROP INDEX uq_chunk_doc_seq` 还原已生效 op → 模型和迁移**两边同时**删 `server_default`（只改一边，`alembic check` 立刻报 diff）。改历史迁移这次合法，因为：没 commit、没 push、没在第二个库跑过——**还是草稿**。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为加 `server_default` 更安全 | TEXT 列直接 1101 | MySQL TEXT/BLOB 不许默认值；模型用 `default=""`（Python 侧），别用 `server_default` |
| 2 | 报错后只盯着报错那条 op | 忽略前面的 op 已提交 | 先还原半途状态，再看根因 |
| 3 | 只改模型或只改迁移一边 | `alembic check` 报 pending | 两边同步；check 比"模型 vs 库" |

- **面试问法**："迁移跑一半失败，库里是什么状态？" —— 30 秒版：**部分 DDL 已隐式提交，版本号没更新，库结构和 alembic_version 脱节。我们撞过：TEXT 列默认值炸 1101，而排在它前面的唯一约束已经建成提交了。动作是先手工还原已生效的 op，再修根因，两边同步。**
- **追问链**：
  - → *"为什么 TEXT 不能有默认值？"* MySQL 实现限制：TEXT/BLOB 是指针型存储，默认值语义在数据字典里放不下——这是方言细节，sqlite 测不出，所以集成测试必须真库。
  - → *"怎么提前发现？"* 方言差异靠真库集成测试；`default`（Python 侧插值）和 `server_default`（进 DDL）的分界要在模型评审时看。
  - → *"这个半途状态和 create_all 的半途状态像吗？"* 像——都是 DDL 隐式提交的产物；区别是迁移有版本号，脱节可检测。

### 3. 先建后拆：1553

- **一句话定义**：MySQL 要求 FK 列必须始终有索引覆盖；upgrade 顺序"先 drop 单列索引再建复合索引"会在 drop 那一刻让 FK 列裸奔，直接拒绝。
- **为什么存在**：MySQL 外键的级联检查靠索引加速，没有索引它拒绝建立/维持这种约束——这是保护，不是刁难。
- **怎么用**：迁移改索引，**先建后拆——新桥先通车，再拆旧桥**。downgrade 是镜像问题（先 drop 复合再建单列犯同一个错），也要调序。读一遍确认：任何时刻 `kb_id` 上至少有一个索引在。
- **底层机制**：autogenerate 按内部顺序输出 op，**不会**替你排这个序——D5 的"草稿论"在此兑现：生成顺序不可信，人工重排是必要工序。修复后 `upgrade head → check → downgrade -1 → upgrade head` 全通，`SHOW INDEX` 确认 `ix_doc_kb_created` 在、`ix_documents_kb_id` 不在。
- **易错点**：以为 autogenerate 的顺序就是对的（它不知道 FK 依赖）；以为"先解决外键依赖再删索引"（外键不能动，动的是顺序）；downgrade 忘了镜像调序。
- **面试问法**："删一个被外键依赖的索引会怎样？" —— 30 秒版：**MySQL 报 1553 拒绝——外键列必须始终有索引覆盖。所以迁移改索引的规矩是先建后拆：先建复合索引，再拆单列，downgrade 镜像同理。autogenerate 不排这个序，人工重排是工序。**
- **追问链**：
  - → *"为什么 FK 列必须有索引？"* 级联删除/更新要快速定位子表行，没索引就是全表扫。
  - → *"单列索引被复合索引覆盖后留着行吗？"* 行但浪费——写放大；本次迁移顺带删掉了被最左前缀覆盖的两个 `index=True`。
  - → *"怎么验证迁移对了？"* upgrade→check→downgrade→upgrade 全走一遍 + SHOW INDEX 逐项核对，不只看"没报错"。

### 4. 零症状静默失败：默认参数藏 bug

- **一句话定义**：`session: Session | None = None` 这个默认值把"生产路径忘传"和"测试路径故意不传"在类型上变成同一个样子——bug 被藏进静默通道。
- **为什么存在**：当初加默认值是为了单元测试方便（fake repo 没有真 session）——**方便性和正确性冲突时，选正确性**。
- **怎么用**（三层静默表，背下来）：

| 环节 | 结果 | 有没有报错 |
|---|---|---|
| `repo.flush()` | INSERT 已发出，主键到手 | 没有 |
| `service._commit()` | `_session is None` → 直接 return | 没有 |
| 请求结束 `get_db` finally | `close()` → 未提交事务回滚 | 没有 |

- **底层机制**：mypy 只查类型不查调用意图——`None` 是合法类型，漏传不报错。更硬的写法（已落到 DocService/RagService）：构造时检查"repo 或 session 至少给一个"，缺了当场 `ValueError`，**堆栈第一行就是病因**。
- **易错点**：给可选参数默认 None 换测试方便（生产路径同一通道静默）；以为 mypy 会拦（类型合法不拦）；以为"接口 200/201 = 对"（静默档失败没有任何信号）。
- **面试问法**："说说你遇到过的最难查的 bug。" —— 30 秒版：**一个零症状 bug：handler 漏传 session，commit 被默认值静默跳过——flush 报成功、commit 跳过、close 回滚，三层都以为自己成功了，接口照样 201。最后靠"另一个连接查行数"的探针定位。修法不只是补参数：构造时缺依赖当场抛 ValueError，把静默档变成硬失败。**
- **追问链**：
  - → *"失效模式三档里这算哪档？"* 静默档（审查顺序：静默 > 延迟 > 硬失败）——最难发现，最值得优先消灭。
  - → *"怎么系统性防？"* 可选依赖收紧为必传 + 构造校验；测试断言"另一个会话能看到"而不是只断言返回值。
  - → *"fake repo 测试怎么写？"* 测试传 fake 没问题——但要用显式参数而不是靠 None 默认值，意图和代码一致。

### 5. 测试隔离三件套

- **一句话定义**：API 测试打真库的三重防线——sqlite 内存库 + StaticPool、`dependency_overrides[get_db]`（必须生成器函数）、真 MySQL 时按 owner 隔离。
- **为什么存在**：`get_db` 默认连真库；不替换它，测试就会串数据、撞唯一约束、写脏开发库。
- **怎么用**：

```python
# conftest.py（骨架）
engine = create_engine("sqlite://", poolclass=StaticPool)  # :memory: 下每个连接独立库，StaticPool 让它们共享
app.dependency_overrides[get_db] = _get_db                  # _get_db 必须是生成器函数（yield）
# 真 MySQL 通道：KB_TEST_MYSQL=1 才跑，断言只查专属 owner UUID，结束按 owner 清理
```

- **底层机制**：sqlite `:memory:` 默认每连接一个独立库——表建在 A 连接，B 连接看不见，StaticPool 强制共享同一连接；`dependency_overrides` 的值如果用 `lambda: iter([...])` 会被当成普通依赖，**注入进去的是迭代器不是 session**，所以必须是生成器函数。没有 DBA 授权建测试库时（实测 `kb` 账号 `1044 Access denied`），**测试隔离靠数据归属而不是库归属**——专属 owner UUID，断言只查自己。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | sqlite 内存库不加 StaticPool | 表"建了却找不到" | StaticPool 共享连接 |
| 2 | override 用 lambda 迭代器 | 注入迭代器，运行时才炸 | 生成器函数（带 yield） |
| 3 | 测试隔离靠"记得换装饰器" | CI 红才暴露（D7 CI #43） | conftest 钉死 `DATABASE_URL="sqlite://"`，赋值不是 setdefault |

- **面试问法**："你的集成测试怎么隔离数据库？" —— 30 秒版：**两层。逻辑测试走 sqlite 内存库 + StaticPool 共享连接，get_db 用 dependency_overrides 替换成测试 session（生成器函数）；需要真事务语义时显式开 KB_TEST_MYSQL=1 走真 MySQL，按专属 owner 隔离数据——没建测试库权限时，隔离靠数据归属。而且 conftest 把 DATABASE_URL 赋值钉死，不让本地 .env 的真库漏进来。**
- **追问链**：
  - → *"为什么 sqlite 和 MySQL 都要？"* sqlite 管逻辑快、隔离好；方言差异（1101）和事务真伪只有真库测得出——介质分工。
  - → *"测试里 create_all 合法吗？"* 合法——测试没有历史状态要维护；生产要演进才必须 Alembic。判据一句话。
  - → *"override 打在哪？"* 打在 app fixture 那个**实例**上——`TestClient(create_app())` 自造新实例就绕过了（CI #43 详案，见踩坑表）。

### 6. 门禁假绿两连：判据来自数据

- **一句话定义**：`pytest-cov` 的 FAIL 文案只打印、从不设置退出码；`--fail-under` 按四舍五入整数比较——两层叠加，覆盖率掉到 60% 门禁照样全绿。
- **为什么存在**：两个工具各自只完成"报告"职责，没人承诺"拦截"职责——**拦截是调用方的事**，我们一直误以为工具会做。
- **怎么用**（`scripts/check.py` 修法）：绕开两者口头表态，`coverage json` 读精确浮点自己比（94.75 < 95.0 → 真红）。门禁改完必须**故意破坏**验证它会响——把覆盖率踩下去跑一遍，确认退出码非 0。
- **底层机制**：pytest-cov 源码里搜不到 `exitstatus`——FAIL 只进 terminal summary；`coverage report --fail-under` 的比较发生在 round 之后。事故现场（修前）：`FAIL Required test coverage of 95% not reached. Total coverage: 94.75%` 下一行就是 `[PASS]`——**同一屏自相矛盾，看了几周才看见**。
- **易错点**：以为打印 FAIL = 会拦（它只说不做）；以为 95% 档位很稳（96→60% 之间全是假绿盲区）；门禁改完只跑绿不跑红（拦网会不会响没验证过）。
- **面试问法**："你的 CI 值得信吗？" —— 30 秒版：**修过一次才敢说信。pytest-cov 打印 FAIL 但从不设退出码，--fail-under 还四舍五入，94.75 会被当 95 放过——覆盖率掉到 60% 门禁照样绿。现在 check.py 读 coverage json 的精确浮点自己比，而且改完门禁做了故意破坏验证：踩低覆盖率，确认它真的红。判据来自数据，不来自工具的口头表态。**
- **追问链**：
  - → *"怎么想到去查的？"* 门禁输出自相矛盾：FAIL 和 PASS 同屏——**响应文案对不上实现 = 别人在说话**。
  - → *"故意破坏具体怎么做？"* 临时踩低覆盖率跑全量，确认退出码非 0；变异验证同理——删 commit 必须红，红才算闭环。
  - → *"这和 flush 事故的关系？"* 同一个模式：flush 报成功 ≠ 落库，[PASS] 打印 ≠ 达标——报告和事实分离。

### 7. 相对量下推 SQL、绝对量内存改

- **一句话定义**：`doc_count + delta` 是相对量，必须单条 `UPDATE SET x = x + delta`（读改写会丢更新）；`status = "ready"` 是绝对量，读出来改属性、commit 时 ORM 生成 UPDATE 也安全。
- **为什么存在**：相对量的"新值"依赖当前库值，Python 侧算就是基于旧快照算过期值（D4 丢失更新）；绝对量不依赖当前值，没有这个问题。
- **怎么用**（对照表）：

| | `incr_doc_count` | `update_status` |
|---|---|---|
| 语义 | 相对量（`doc_count + delta`） | 绝对值（`status = "ready"`） |
| 写法 | 单条 `update()` 语句 + rowcount 判存在 | `session.get()` 改属性，commit 时生成 UPDATE |

- **底层机制**：单条 UPDATE 是当前读，加法在库里锁保护下做；读改写的"算"发生在 Python、基于快照。另一个判断：`session.get(Document, doc_id)` 在 `create` 刚 `add` 过后**不发 SELECT**——对象在 identity map 里（W7-D2 机制兑现）。
- **易错点**：把两种写法当风格问题随便选；对相对量用读改写还以为有锁保护（普通 SELECT 是快照读）；响应体用 `repo.create` 的返回快照导致 `chunk_count: 0 / status: pending`（库里已是 4/ready）——**快照过时了，要补一次组装**。
- **面试问法**："ORM 里改字段，什么时候必须写 UPDATE 语句？" —— 30 秒版：**增量改（count±1、积分扣减）必须单条 UPDATE 下推，读改写基于旧快照会丢更新；赋值改（状态置为固定值）用 ORM 改属性没问题，因为新值不依赖当前库值。我们项目 doc_count 用原子语句，update_status 用属性赋值，判据就这一句。**
- **追问链**：
  - → *"绝对量在并发下真的安全吗？*" 语义上安全；但要防"读到后被人改走"（ABA）就得 `FOR UPDATE` 或乐观锁——按业务判断。
  - → *"response 怎么拿到最新值？*" 要么 DB 取回（MySQL 8 无 UPDATE RETURNING），要么如本项目由 service 组装返回体。

---

## 三、30 秒答案集

1. **事务边界**：service 握 commit（跨写点原子性），session 由 `Depends(get_db)` 按请求注入，finally 统一 rollback/close。
2. **漏传 session 的三层静默**：flush 成功、commit 跳过、close 回滚——全无报错，接口照样 201。
3. **防静默**：构造时缺依赖当场 `ValueError`；静默档失败优先消灭（静默 > 延迟 > 硬失败）。
4. **1101**：MySQL TEXT/BLOB 不许默认值；模型 `default=""`（Python 侧）不是 `server_default`（进 DDL）。
5. **半途状态**：部分 DDL 已提交、版本号未动；还原已生效 op → 两边同步改 → check 必绿。
6. **1553**：FK 列必须始终有索引覆盖；迁移改索引先建后拆，downgrade 镜像；autogenerate 不排这个序。
7. **StaticPool**：sqlite `:memory:` 默认每连接独立库，StaticPool 共享连接让表互相可见。
8. **override 两要点**：打在 app fixture 实例上；必须是生成器函数（lambda 迭代器会被当普通依赖）。
9. **owner 隔离**：没建测试库权限时，隔离靠数据归属——专属 owner UUID，断言只查自己。
10. **门禁假绿**：pytest-cov FAIL 不设退出码 + fail-under 四舍五入 → 读 coverage json 精确浮点自己比 + 故意破坏验证。
11. **相对量 vs 绝对量**：增量必须下推单条 UPDATE；赋值可以 ORM 内存改。判据一句话。
12. **测试里的 create_all 合法**：没有历史状态要维护——和"生产必须 Alembic"不矛盾。

## 六、可以讲成故事的三段

1. **一天撞出两个"报告成功 ≠ 实际成功"**。背景：上午接线，下午补门禁。我以为上午的 bug 是孤例。实际下午 pytest-cov 给了完全同构的第二例——flush 报成功不等于落库，FAIL 打印不等于拦截。教训：**这不是两个 bug，是同一个模式；模式识别一次，以后见着"报告"先找"事实"**。
2. **预测 7 条 op，实测 7 条，还是炸了**。背景：迁移 #3 生成前逐条预测。我以为预测全中就稳了。实际 1101 和 1553 全在"预测对了内容、没预测顺序和方言"的盲区里。教训：**diff 内容可以预测，op 顺序和方言行为必须实测——autogenerate 给草稿，真库给真相**。
3. **CI 红反而是 CI 第一次干正事**。背景：收工后推代码，CI 红了。我以为又是环境问题。实际揪出 `TestClient(create_app())` 绕过 override 打真库——本地绿是因为恰好有 .env。教训：**本地绿要先问"这条绿来自哪个依赖"；CI 的价值就在它没有你的本地巧合**。
