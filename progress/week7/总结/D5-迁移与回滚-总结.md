## 二、逐个知识点讲透

### 1. flush ≠ commit：三段探针实证

- **一句话定义**：flush 把内存变更翻译成 SQL 发给数据库但不提交；commit 才提交事务——flush 报成功 ≠ 落库。
- **为什么存在**：ORM 默认把"发给库"和"对别人可见"分成两步，换取中途反悔的机会；代价是两步都可能被误当成"完成"。
- **怎么用**（三段探针，可复跑：`progress/week7/probes/check_db_wiring.py`）：

```
A 段  TestClient 打真 app，POST /api/v1/kbs → 201，GET 列表 total=1
      MySQL 0 -> 0 行        ← 接口根本没走库，get_db 定义了没人用，写的是内存 store
B 段  KBRepository(SessionLocal()).create(...) 只 flush 不 commit
      主键到手、本会话查得到；另一个连接 0 行；close() 后仍 0 行  ← close 即回滚
C 段  同一路径补一次 commit()
      MySQL 0 -> 1 行        ← 缺的就是这一道门
```

- **底层机制**：flush 走的是当前连接的事务缓冲，其他连接按隔离级别看不到未提交数据；`session.close()` 时未提交事务隐式回滚。B 段"close 后仍 0 行"就是这条规则的实证。A 段最刺眼：**接口 201、列表里查得到自己刚建的库、MySQL 一行没有——三层都不报错**（D6 定位出根因：`_commit()` 里 `session is None` 静默 return）。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把"本会话查得到"当"落库了" | B 段自欺 | 判据 = **另一个连接**的 SELECT 行数 |
| 2 | 把 flush 当 commit 用（省一次调用） | close 即回滚，白写 | 事务边界收在 service 的 `_commit()` |
| 3 | 以为接口返回 201 = 数据持久了 | A 段 201 但 0 行 | 接口返回只证明 handler 没抛异常，不证明落库 |

- **面试问法**："你怎么证明数据真的落库了？" —— 30 秒版：**我不信接口返回码也不信本会话查询，用另一个连接 SELECT 数行数。我们项目踩过这个坑：接口 201、本会话查得到，MySQL 里 0 行——根因是 commit 被静默跳过。所以集成测试专门断言"另一个 session 能看到"。**
- **追问链**：
  - → *"为什么会静默？"* `_commit()` 里 `if self._session is None: return`——默认参数把"忘传"变成"成功"，三层（flush 成功、commit 跳过、close 回滚）都无报错（D6 事故 3 详案）。
  - → *"怎么防？"* 构造时检查"repo 或 session 至少给一个"，缺了当场 `ValueError`（已落到 DocService/RagService）。
  - → *"测试为什么不抓？"* 当时 78 个测试全跑内存 store + sqlite，MySQL 路径零覆盖——覆盖率 96.82% 是"代码行被跑过"的比例，不是"链路通"的证据。

### 2. create_all 为什么不能上线

- **一句话定义**：`create_all` 是"从零建表脚本"——只 `CREATE TABLE IF NOT EXISTS`，不 diff、不记版本、不能回退、不管并发。
- **为什么存在（它存在的场景）**：测试环境"从零直接到最新"，没有存量数据、不需要演进——这时 create_all **合法**；生产要"从当前版本演进到下一版"，有历史状态要维护。判据一句话：**有没有历史状态要维护**。
- **怎么用**：开发脚手架空库图快可以用；只要有第二个环境（队友/测试服/生产）就必须换 Alembic。
- **底层机制**（七条，按面试出场率排，**每条必须带"不做会怎样"**）：

| # | 理由 | 不做会怎样 |
|---|---|---|
| 1 | 只建不改：模型加一列它什么都不做 | 程序按新模型 INSERT → `1054 Unknown column` → 接口 500，重启不自愈 |
| 2 | **没有版本记录**（最关键） | 你的库、队友的库、测试环境各自漂移，回滚不知道退到哪，无法审计 |
| 3 | 不能回退 | 加错列只能逐环境手写 ALTER，漏一个就是事故 |
| 4 | 并发竞态：checkfirst 先查再建 | 两个实例同时启动同抢 DDL 锁，`1050 Table already exists` |
| 5 | 进程不该有 DDL 权限 | 要么给应用账号开 CREATE/ALTER，要么部署直接权限报错 |
| 6 | 部分失败状态未知：DDL 隐式提交 | 建到第二张挂了前两张已生效，重跑 checkfirst 跳过 → 半成品假象常驻 |
| 7 | 不可评审 | 结构变更不进 Git diff / Review / CI，谁改的线上表说不清 |

- **易错点**：只背"不能改、不能退"名词清单（我判档 2 档的教训）——**面试官考的不是名词，是你知不知道不做会炸在哪**。
- **面试问法**："为什么生产不用 create_all？" —— 30 秒版：**它是建表脚本不是迁移系统：不 diff、不记版本、不能退、不管并发，还要求进程有 DDL 权限。迁移系统缺的每一样都是一次线上事故——比如它不会改已存在的表，模型加了列库没有，接口直接 500 且永不自愈。**
- **追问链**：
  - → *"测试里为什么反而用 create_all？"* 没有历史状态要维护，"从零到最新"正是它擅长的。
  - → *"第二个环境出现前要紧吗？"* 不要紧——判据是历史状态，不是教条。

### 3. autogenerate 生成的是草稿

- **一句话定义**：autogenerate 输出"模型 vs 库的结构差异草稿"，不是变更方案——它看不见意图和数据的命运。
- **为什么存在**：diff 结构是机械活，可以自动化；判断变更是否安全是人的判断，没法自动化。
- **怎么用**：生成后**人工读是必要工序**，重点盯 `drop_*` 和 `alter_column` 两类 op；生产前影子库跑一遍 + 对比行数。
- **底层机制**（它看不见什么，每条一个危险）：

| # | 看不见什么 | 危险 |
|---|---|---|
| 1 | 意图 | 重命名 = drop_column + add_column → 5000 行标题变 NULL，一跑就没 |
| 2 | 数据的命运 | 那条的 downgrade 只是把空列加回来——**结构回得去、数据回不去** |
| 3 | 类型收窄 | varchar(200)→varchar(50) 照写，非严格模式静默截断，数据悄悄残废 |
| 4 | 未注册的模型 | 历史表不在 models 里 → 生成 drop_table，**一条命令删掉线上表** |
| 5 | 数据迁移 | 回填/拆分/编码转换不生成；有数据的表加 NOT NULL 列直接失败 |

- **易错点**：以为"结构层面没问题就能跑"；以为 downgrade 是安全网（它是机械反操作，救不了数据）。
- **面试问法**："autogenerate 生成的迁移为什么要人工检查？" —— 30 秒版：**它只比结构差异，不认识意图。字段重命名会被写成删一列建一列，五千行数据直接没了，downgrade 也只是把空列加回来。所以 drop 和 alter 类 op 必须人审，重命名要手改成 alter_column。**
- **追问链**：
  - → *"重命名正确写法？"* `op.alter_column(..., new_column_name=...)`——Alembic 支持，但 autogenerate 不会自己选。
  - → *"项目里它排错过什么？"* 迁移 #3 的索引换装，drop 排在 create 前撞 1553（D6 详案）——顺序也不替你排。

### 4. DDL 隐式提交 → 失败只能 forward fix

- **一句话定义**：MySQL 每条 DDL 隐式提交，迁移跑一半失败时前半已生效且版本号没更新——没有"撤销"只有"前进"。
- **为什么存在**：DDL 操作的是数据字典（物理结构），不是行数据，MySQL 选择不让它进事务——代价就是迁移不原子。
- **怎么用**（四步标准动作）：① 迁移前备份（唯一真救数据的）② 一个迁移只做一件事（压小爆炸半径）③ 失败先核实真实状态：`alembic current` 说版本、`SHOW CREATE TABLE` 说结构，**不一致时以结构为准**，必要时手工对齐 `alembic_version` ④ forward fix：新写迁移推到目标态，历史一个字不改。
- **底层机制**：`upgrade` 日志那句 `Will assume non-transactional DDL` 就是在声明这件事；`downgrade` 本身也是一串 DDL，同样可能中途失败——所以它不是回滚安全网。
- **易错点**：出错就 downgrade（MySQL 上不成立）；只看 `alembic current` 判断库状态（版本号 ≠ 结构）；重跑迁移以为幂等（半成品会常驻）。
- **面试问法**："线上迁移失败了怎么办？" —— 30 秒版：**先说前提：MySQL 的 DDL 隐式提交，跑到第 3 条失败时前 2 条已经提交、版本号还没动，库结构和版本号脱节了——所以不能指望回滚。动作是：有备份看备份；然后 SHOW CREATE TABLE 核实真实结构、对齐版本号；最后 forward fix 写新迁移。历史迁移一个字不改。**
- **追问链**：
  - → *"版本表手工改错了会怎样？"* 后续 upgrade 跳过该跑的或重跑跑过的，报 `Can't locate revision`，只能人工对齐。
  - → *"大表加索引怎么不停服？"* gh-ost / pt-osc，或 MySQL 8 `ALGORITHM=INPLACE, LOCK=NONE`（看操作类型支持）。
  - → *"项目里见过半途状态吗？"* D6 事故 1：`uq_chunk_doc_seq` 已建成功并隐式提交、版本号停在上一版——活体标本。

### 5. 历史不改写，只往后加

- **一句话定义**：被别的环境执行过的迁移文件是不可变历史；要修正就新写一条迁移，绝不回头改。
- **为什么存在**：改历史会让"同一版本号"在两个环境含义不同——版本系统的根基是编号与内容的绑定。
- **怎么用**：删 `status` 单列索引（D3 实物对照）的正确姿势 = 新写一条 `drop_index` 迁移 + **同步**去掉模型里的 `index=True`——只改一边 `alembic check` 立刻红。
- **底层机制**：`down_revision` 链条把迁移串成单向链表；改已执行节点的效果 = 从链条中间抽走一个 commit。唯一例外：**没 commit、没 push、没在第二个库跑过的草稿**可以改（D6 事故 1 改历史迁移合法的依据）。
- **易错点**：downgrade -1 当"删除工具"用（模型还写着 index=True，check 立刻红）；草稿和历史的界限模糊（判据：有没有在第二个环境执行过）。
- **面试问法**："发现历史迁移写错了怎么办？" —— 30 秒版：**看它有没有被第二个环境执行过。没有 = 还是草稿，直接改；有 = 不可变历史，新写一条 forward fix 迁移。改历史的代价是同一版本号在两个库含义不同，这比错误本身危险。**
- **追问链**：→ *"downgrade 和 forward fix 怎么选？"* downgrade 只用于"有意退版本"，不用于"修错误"；修错误永远 forward。→ *"模型和迁移两边不同步会怎样？"* `alembic check` 报 pending——这就是它该进 CI 的原因。

### 6. 类型落地与方言差异

- **一句话定义**：模型里的抽象类型落到具体库会有方言转化——`sa.Uuid()` 落 MySQL 成 CHAR(32)，`DateTime(timezone=True)` 不存时区。
- **为什么存在**：SQLAlchemy 是跨方言抽象，方言它替你翻译，但翻译结果要自己验证——预测错一条就少一次理解。
- **怎么用**：迁移后 `SHOW CREATE TABLE` / information_schema 逐列核对（本日预测 char(32)/datetime 两个全中）；建库时定 `utf8mb4_0900_ai_ci`，表继承。
- **底层机制**：UUID 在 MySQL 没有原生类型 → CHAR(32) 存储（比自增宽，W7-D3 实测 4 万行多 22% 页数）；MySQL 的 DATETIME 本身不存时区，timezone=True 只对支持时区的方言（如 PostgreSQL timestamptz）生效。`alembic_version` 不在你的迁移里——它由 Alembic 在 upgrade 时自建自维护，因为迁移必须先读版本表才知道该跑哪几条。
- **易错点**：以为 timezone=True 在 MySQL 存时区；以为 alembic_version 要自己写迁移建；以为 ini 里的 sqlalchemy.url 是真连接串（本项目运行时被 env.py 用 settings 覆盖，ini 保留占位符避免密码入库）。
- **面试问法**："你的 UUID 主键在库里长什么样？有什么代价？" —— 30 秒版：**MySQL 落成 CHAR(32)，比 BIGINT 宽得多，而二级索引叶子都存主键——所有索引跟着变肥，我们实测 4 万行页数多 22%，且随机写导致页分裂。自增主键就是为顺序写页尾设计的。**
- **追问链**：→ *"那为什么还用 UUID？"* 分布式下不依赖中心发号器；代价已知、数据量小可承受。→ *"密码放 ini 里行不行？"* 不行——ini 会进 Git；本项目 URL 从 settings（.env）注入。

## 三、30 秒答案集

1. **flush vs commit**：flush = 翻译成 SQL 发给库、未提交、本会话可见；commit = 提交事务、跨连接可见。flush 成功 ≠ 落库。
2. **怎么证明落库**：不信返回码不信本会话，另一个连接 SELECT 数行数。
3. **create_all 为什么不能上线**：不 diff、不记版本（最关键）、不能退、不管并发、要 DDL 权限；判据 = 有没有历史状态。
4. **autogenerate 是草稿**：只比结构差异，不认识重命名——drop+add 一跑五千行数据就没了；人审是工序。
5. **迁移失败怎么办**：MySQL DDL 隐式提交，没有撤销只有前进——备份、小步走、SHOW CREATE TABLE 核实、forward fix。
6. **半途状态**：部分 DDL 已生效但版本号没更新；`alembic current` 说版本、结构以 SHOW CREATE TABLE 为准。
7. **历史迁移能改吗**：在第二个环境执行过就不能；还是草稿就能。判据一句话。
8. **alembic check**：把"模型和库是否一致"变成一条命令，改完模型必跑，该进 CI。
9. **UUID 主键代价**：CHAR(32) 让所有二级索引变宽 + 随机写页分裂；自增主键顺序写页尾。
10. **timezone=True 陷阱**：MySQL DATETIME 不存时区，这个参数只对支持的方言生效。

## 六、可以讲成故事的三段

1. **接口返回 201，数据库一行没有**。背景：写链路探针验证"数据库功能完成度"。我以为 78 个测试全绿就是"能跑"。实际 A 段 201、列表还查得到、MySQL 0→0——接口写的是内存 store，`get_db` 从来没人用。教训：**报告成功 ≠ 实际成功；覆盖率的分母里没有 MySQL，96.82% 不证明链路通**。
2. **删一个没用的索引，规矩比动作重要**。背景：grep 全项目发现没有任何查询用 status 单列索引，想删。我以为 downgrade -1 就行。实际模型还写着 `index=True`，check 立刻红；正确动作是**新写一条 drop_index 迁移 + 两边同步**。教训：**历史不改写只往后加——版本系统的根基是编号与内容绑定**。
3. **预测列类型两个全中**。背景：首条迁移前预测 `sa.Uuid()` 落库形态。我以为会很复杂。实际 char(32)/datetime 与预测全中，还顺带发现 timezone=True 在 MySQL 是空话。教训：**方言差异不是背出来的，是"预测 → 核对 → 对上/打脸"循环出来的**。
