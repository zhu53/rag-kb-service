## 二、逐个知识点讲透

### 1. 丢失更新：病根与原子自增

- **一句话定义**：两个事务都基于读到的旧值计算再写回，后写覆盖先写，"算好的值"被丢掉。
- **为什么存在**：读-改-写三步不在一个原子操作里，两步之间的空隙就是别人的写入窗口；**串行执行也照样丢**——丢的不是锁竞争，是"写回旧值"这个动作本身。
- **怎么用**（本项目已落地）：

```python
# 禁止：读-改-写（改前 2 条 SQL）
row = session.get(KnowledgeBase, kb_id); row.doc_count += 1  # 算好的旧值写回
# 正解：原子自增（1 条 SQL，加法在库里做）
stmt = (update(KnowledgeBase).where(KnowledgeBase.id == kb_id)
        .values(doc_count=KnowledgeBase.doc_count + delta))
result = cast("CursorResult[Any]", session.execute(stmt))
if result.rowcount == 0:
    raise NotFoundError(...)
```

- **底层机制**：`SET x = x + 1` 的加法在**库内、拿到行锁之后**计算——两个并发 UPDATE 各自在锁保护下读加写，天然串行不丢；读-改-写则是"Python 算好 → SET 成常量"，锁只保护写入那一瞬，保护不了几分钟前那次读。`rowcount==0` 顺带完成存在性判断，省一次 SELECT 往返和锁窗口。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把丢失更新理解为"锁竞争" | 以为串行就不丢 | 复现实验证明：B commit 后写 1，A 的 +1 被覆盖，无人违反任何锁规则 |
| 2 | 以为 `SET x=1` 和 `SET x=x+1` 只差写法 | 前者丢后者不丢 | 差在"谁算的"：Python 算 vs 库内算 |
| 3 | 想返回自增后的值 | 加 SELECT → SQL 变 2 条 | MySQL 8 无 UPDATE RETURNING，返回值只能放弃或事后读 |
| 4 | 对 rowcount 直接取属性 | mypy 报 `Result` 无 rowcount | cast 成 `CursorResult`（rowcount 长在游标结果上） |

- **面试问法**："并发计数为什么会少算，怎么修？" —— 30 秒版：**读-改-写把算术放在 Python，写回的是几秒前的旧值，后写覆盖先写。修法是把算术下放到库里：`SET x = x + 1` 一条原子语句，加法在拿锁之后做，天然串行。我们项目 doc_count 就是这么改的，还用 rowcount 顺带做了存在性判断。**
- **追问链**：
  - → *"FOR UPDATE 也能修吗？"* 能（悲观锁），但单语句原子自增更短、无死锁面；只有"下一步决策依赖读到的值"（如库存够不够）才值得 FOR UPDATE。
  - → *"什么情况下原子自增也不够？"* 要先判断再改（库存扣减）→ 悲观锁或乐观锁（version 字段 + 重试）。
  - → *"你们项目哪里真用了？"* 上传/删除文档时 doc_count ±1，测试用 before_cursor_execute 计数证明 1 条 SQL；真并发验证留 MySQL 集成测试。

### 2. 三种锁形态：点/缝图像

- **一句话定义**：InnoDB 行锁三种形态——记录锁锁一个点、间隙锁锁一条缝、临键锁 = 点 + 左缝。
- **为什么存在**：RR 要防幻读（两次读结果集不一致），光锁住已有行不够，还必须锁住"可能长出新行的位置"——缝。
- **怎么用**（先记住图像再记名字）：

```
数轴：……10   20   30……
记录锁  {20}            ← 唯一索引+等值+命中，退化成 X,REC_NOT_GAP
间隙锁  (20,30)         ← 只锁缝，不含两端；挂右端点命名，LOCK_MODE=X,GAP
临键锁  (10,20]         ← RR 默认形态；裸 X
```

- **底层机制**：锁挂在**叶子层索引记录**上（非叶子节点归 latch 管，事务锁不上溯，否则树根被第一个行锁占住=全表串行化）。范围扫描会**向外对齐到记录边界**：`WHERE id>15 AND id<25` 实锁 `(10,30)`——15/25 落在缝里，缝的端点必须是真实记录，无法向内切。**LOCK_DATA 是锚点记录不是条件值**：条件值只活在 server 层，`X,GAP LOCK_DATA=30` 读作"挂在 30 上、只要它左边的缝"；`supremum pseudo-record` 是页尾虚拟记录，代表"最后一行之后到 +∞"。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 LOCK_DATA 读成"锁了这行" | 以为 X,GAP 30 锁住行 30 | 它是锚点；只锁 30 左边的缝 |
| 2 | 认为锁区间 = WHERE 区间 | 不理解 INSERT 11 也被挡 | 锁向外对齐到记录边界，不向内收缩 |
| 3 | 以为等值命中总是临键锁 | 场景判断全错 | 唯一索引+等值+命中 → 退化纯记录锁；范围/非唯一 → 临键 |
| 4 | 认为 RR 下 INSERT 全靠唯一约束挡 | 等不出间隙锁的作用 | 防插入的是二级索引/主键上的缝 |
| 5 | 不知道 INSERT 拿什么锁 | 读不懂 data_lock_waits | `X,INSERT_INTENTION`，插入意向锁；彼此不冲突，撞缝锁才等 |

- **面试问法**："RR 下 SELECT ... FOR UPDATE 到底锁了什么？" —— 30 秒版：**锁扫过的索引区间：命中行临键锁（点+左缝），扫到第一条不满足的为止，它前面的缝用间隙锁封住。所以实际锁区间比 WHERE 宽，两端向外扩到真实记录。唯一索引等值命中退化成纯记录锁。**
- **追问链**：
  - → *"间隙锁只在 RR 有吗？"* 是，RC 不加缝锁——实测同一查询 RC 下 0 个记录锁，RC 不防幻读是"没设岗"不是"检测不到"。
  - → *"INSERT 在等待时显示什么？"* 挂起的 `INSERT_INTENTION` 请求本身也是一条锁记录——等待 ≠ 没锁（总账 5042 = 5039+1+2 的实测）。
  - → *"项目里哪里吃到了这个？*" 无索引 `UPDATE WHERE status='ready'` 锁 5039 个对象误伤全表——所以按状态过滤的列必须有索引（D3 定案的三个索引之一）。

### 3. 隔离级别与 MVCC

- **一句话定义**：MVCC 让读不阻塞写——快照读按 ReadView 看历史版本；当前读跳过版本链读最新已提交并加锁。
- **为什么存在**：不加 MVCC，"报表读"会挡住"业务写"；不加隔离级别，并发读写会出现脏读/不可重复读/幻读。
- **怎么用**：RR（默认）下普通 SELECT 是快照读（首次 SELECT 定快照）；`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 是当前读；要改隔离级别 `SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED`（注意 REPEATABLE READ 带空格，值显示才带连字符）。
- **底层机制**：每行有 undo 版本链；ReadView 记录"开始时活跃的事务集合"，快照读沿版本链找对自己可见的版本；**当前读不走 ReadView**——直接读最新已提交版本并加锁，这就是"我 BEGIN 后别人 commit 了，我的 FOR UPDATE 也能看到"的原因（实测：卡 39.87s 后读到 3 和 5）。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 RR 下读不到别人已提交的新数据 | 不理解 FOR UPDATE 读到新值 | 快照读看 ReadView，当前读看最新 |
| 2 | 以为快照在 BEGIN 时定 | 前后两次 SELECT 结果对不上 | RR 快照在**首次 SELECT** 时定 |
| 3 | 把"RC 不防幻读"归因于检测 | 以为引擎看不见 | RC 根本不加间隙锁，防线没设 |
| 4 | SET 语句里写 REPEATABLE-READ | 1064 语法错 | 语句用空格，变量值才用连字符 |

- **面试问法**："RR 和 RC 的区别，MVCC 怎么实现的？" —— 30 秒版：**MVCC 靠 undo 版本链加 ReadView：快照读按"事务开始时谁还活跃"判断可见版本。RR 首次 SELECT 定快照、全程复用，所以可重复读；RC 每次 SELECT 新建 ReadView，所以读得见别人新提交的。当前读不走这套，直接读最新加锁。**
- **追问链**：
  - → *"为什么当前读不迷路？"* 它要改数据，必须基于最新事实，历史版本没有加锁意义。
  - → *"RR 下幻读彻底防住了吗？"* 快照读+当前读混用时可能出现"先快照后当前读"的错乱——经典追问，答"分别都防，混用有特例"。
  - → *"项目里踩过吗？"* 交付物 2：同一 SELECT 在 RR 锁 supremum、RC 零记录锁——隔离级别决定锁形状。

### 4. 事务边界与 autocommit

- **一句话定义**：autocommit=1 下每条语句是独立事务；要"多条一起成败"必须显式 BEGIN…COMMIT/ROLLBACK。
- **为什么存在**：不明确边界，"两条 UPDATE 要么全成要么全不算"根本无从谈起——复现丢失更新的前提就是先把边界摆出来。
- **怎么用**：MySQL 控制台 `BEGIN; … COMMIT;`；SQLAlchemy 里 autobegin（首操作自动 BEGIN），commit/rollback 收在 service 层（衔接 D1D2 总结知识点 1）。
- **底层机制**：autocommit 时每条语句包一个隐式事务即时提交；显式 BEGIN 后语句共享一个事务，直到 COMMIT/ROLLBACK。**连接断开 = 未提交事务隐式回滚**——PyCharm 改数据源属性导致 5039 个锁瞬间消失的亲历。
- **易错点**：以为 console 里两条 UPDATE 天然一个事务；A commit 后 B 才 SET 常量不叫覆盖——**丢的是算好的旧值，时序无关串行与否**；ROLLBACK 不敲不生效（连接断开才算）。
- **面试问法**：30 秒版——**autocommit 下每条语句独立提交；显式事务靠 BEGIN…COMMIT；连接断开未提交即回滚。事务边界在 Python 侧由 service 层掌管。**
- **追问链**：→ *"autocommit 要不要关？"* 连接级可关，但 SQLAlchemy 已用 autobegin 管理，别在两层各管一遍。→ *"长事务的害处？"* 锁不释放 + undo 膨胀 + MVCC 旧版本堆积；线上按 trx_started 抓长事务。

### 5. 锁跟执行计划走，不跟索引走

- **一句话定义**：行锁的形状由**实际执行的扫描路径**决定——建了索引但优化器没走它，锁形与没建时一模一样。
- **为什么存在**：这解释了"建索引没少锁"的反直觉现象；也是"EXPLAIN 会说谎"的根源。
- **怎么用**：判断真假用 Handler 计数器三步：`FLUSH STATUS;` → 执行语句 → `SHOW SESSION STATUS LIKE 'Handler_read%'`。`Handler_read_rnd_next` 大 = 全表扫，`Handler_read_next` 大 = 走索引。
- **底层机制**：90% 命中率下走二级索引 = 4500 次回表随机 IO，全表顺序扫更便宜 → 优化器**执行时**放弃索引；但 `EXPLAIN UPDATE` 报 `type=index`——**EXPLAIN 是优化器的意图，Handler 和 data_locks 是引擎的事实**，两者可以不一致（该 EXPLAIN 的 key_len=128 与单列应得 82 自相矛盾，是它露的马脚）。
- **易错点**：以为建了索引锁就变少（实测 5039 → 5039）；以为 EXPLAIN 永远如实（它报的是计划不是执行）；FORCE INDEX 后锁 **9014 翻倍**但形状变好——聚簇变纯记录锁、防插入交给二级索引的缝，误伤半径反而缩小（改 pending 秒过、改 ready 才 1205）。
- **面试问法**：30 秒版——**锁跟实际执行计划走。高重复度列的索引优化器可能放弃，锁形和没索引一样；验真假用 Handler 计数器而不是 EXPLAIN。真走索引后锁数量可能翻倍，但误伤半径缩小——防插入交给二级索引的缝。**
- **追问链**：
  - → *"怎么强制走？"* FORCE INDEX（对照实验用），生产上该修的是索引设计不是 hint。
  - → *"多少选择性才值得走索引？"* 无死数字：成本 = 回表随机 IO vs 顺序扫，看行宽和缓冲池，用 Handler/真实负载验证，不背百分比。
  - → *"项目落点？"* status 单列索引 + 联合索引 (kb_id,status,created_at)，`ANALYZE TABLE` 后统计信息才准。

### 6. B+ 树、页与 IO 单位

- **一句话定义**：索引是 B+ 树，节点 = 16KB 页；磁盘 IO 以页为单位，树高决定点查 IO 次数。
- **为什么存在**：不用树结构，找一行只能顺序扫；页是 InnoDB 一切 IO 和缓冲的最小单位。
- **怎么用**：估树高先估每页行数——聚簇行约 130B → 128 行/页；5000 行 ≈ 39 页（实测 supremum 恰 39 个，页尾虚拟记录每页一个，数字自洽）。
- **底层机制**：非叶子层只存键+指针（可常驻 Buffer Pool），叶子层存数据；主键即聚簇索引本身，二级索引叶子存"索引列 + 主键"——这就是回表的来源；UUID 主键比自增宽（CHAR(32)），4 万行实测多 22% 页数（353 vs 289）。
- **易错点**：把"行数"当成本；把"一次 IO"当"读一行"；以为 UUID 只是占空间大——它让**所有二级索引**跟着变宽（每条都存主键）。
- **面试问法**：30 秒版——**B+ 树矮胖，一次点查 = 树高次页 IO；叶子存数据（聚簇）或主键（二级），非叶子层常驻内存。所以成本按页算不按行算，主键越宽所有索引越肥。**
- **追问链**：→ *"为什么用 B+ 树不用 B 树/跳表？"* 叶子链表利于范围扫、非叶子不存数据故更矮。→ *"Buffer Pool 干嘛的？"* 页缓存，命中则免磁盘 IO——所以热数据小表全表扫也不慢。→ *"自增主键的好处？"* 顺序写页尾免页分裂；UUID 随机写分裂+索引变宽。

### 7. 聚簇/二级索引、回表与覆盖索引

- **一句话定义**：聚簇索引叶子存整行；二级索引叶子存"索引列+主键"，拿不到的列要回聚簇再查一次。
- **为什么存在**：一份行数据只能按一棵树物理组织；其余索引靠"存主键指针"复用。
- **怎么用**：`EXPLAIN` 的 `Using index` 是**免回表的唯一标志**（覆盖索引）；`Backward index scan` = 索引有序免 filesort，**免排序 ≠ 免回表**（两组概念独立）。
- **底层机制**：二级索引命中后拿主键回聚簇逐行查（随机 IO）；覆盖索引把查询列全装进索引里，扫一棵树完事——`key_len` 只统计用于 seek 的列，ORDER BY 列不计入（预测 133 实得 128 的教训）。
- **易错点**：以为索引含排序列就覆盖了（ORDER BY 列不进 key_len）；以为免 filesort 就免回表；给 `SELECT *` 建覆盖索引（装不下）。
- **面试问法**：30 秒版——**回表 = 二级索引拿到主键后回聚簇取整行，随机 IO 是大头。查询列全部在索引里 = 覆盖索引，EXPLAIN 显示 Using index，免回表。免 filesort 和免回表是两件独立的事。**
- **追问链**：→ *"key_len 怎么读？"* 实际用于定位的字节宽度（utf8mb4 每字符 4B），据此判断联合索引用到了第几列。→ *"项目里怎么定索引？"* 三业务查询各配一条，D3 §十有定案；不是越多越好，写路径变贵。

### 8. 最左前缀

- **一句话定义**：联合索引 (a,b,c) 按 a 排序、a 内按 b 排序……查询从最左列开始连续命中才能用上。
- **为什么存在**：联合索引只有一棵树，列顺序就是排序字典序；断了就找不到"有序"的性质。
- **怎么用**：等值条件连续命中可继续；**一旦有列没用上，其后所有列既不能定位也不能排序**——(kb_id,status,created_at) 替代不了 (kb_id,created_at)（实测 ORDER BY created_at 时 key_len 停在 status 前）。
- **底层机制**：B+ 树按 (a,b,c) 字典序物理排列；跳过 b 后 c 在树里是"乱序"的——不是不存在，是无序。
- **易错点**：以为命中 a 就能用 c 排序；把索引列顺序当 WHERE 里的书写顺序（后者无关）；区分度低的列放最左（浪费）。
- **面试问法**：30 秒版——**联合索引按最左连续前缀工作：断了一列，后面的列定位和排序都失效。所以列顺序按"等值在前、范围/排序在后、区分度高的在前"设计。**
- **追问链**：→ *"IN 和范围条件算断吗？"* 范围列能用但之后的列断；IN 的多值在 5.x/8.x 表现不同，实测说话。→ *"两条查询该建几条索引？"* 各建或折中，看查询频率——写路径是税。

### 9. 死锁：1213 vs 1205

- **一句话定义**：死锁 = 两事务互相持有对方要的锁形成环，InnoDB 秒级检测并回滚受害者（1213）；锁等待超时是普通排队等到期限（1205）。
- **为什么存在**：两种失败要分开诊断——1213 是结构性问题（加锁顺序），1205 是容量/长事务问题（等太久）。
- **怎么用**（手工复现四步）：A 锁 k1 → B 锁 k2 → A 要 k2（卡住）→ B 要 k1（环闭合，B 立即 1213）。读日志只看四样：各自 UPDATE、各自 HOLDS 的 `asc` 主键值、各自 WAITING FOR、`WE ROLL BACK TRANSACTION (?)`。
- **底层机制**：victim 选择按代价（undo log entries 最少），权重相同时回滚**让环闭合的那个**；`asc` 列直接打印行内容，日志里 `ApplicationName` 能定位来源；InnoDB 只保留最近一次死锁日志（实验前读旧日志做了对照）。
- **易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 1213 要等超时 | 排障方向错 | 死锁事件驱动秒级，1205 才受 50s 超时管 |
| 2 | 第一次复现没成环 | 只读到旧日志 | 顺序必须 A1→B1→A2(卡)→B2；A 没卡住就发 B2 不成环 |
| 3 | 只会修"加锁顺序" | 漏了第二修法 | 统一按 id 排序拿锁（治环）或原子语句+短事务（不给凑环窗口） |

- **面试问法**："线上死锁怎么排查？" —— 30 秒版：**SHOW ENGINE INNODB STATUS 的 LATEST DETECTED DEADLOCK 段：两个事务各看 HOLDS 和 WAITING FOR 的主键，环一目了然，WE ROLL BACK 告诉你受害者。修法要么统一加锁顺序，要么把读-改-写压成原子语句缩短事务。**
- **追问链**：→ *"为什么回滚那个不是另一个？"* 代价最小者；权重相同回滚环的闭合者。→ *"应用层怎么配合？"* 捕获 1213 重试是标准动作（幂等前提下）。→ *"你们项目死锁风险在哪？*" 读-改-写版 doc_count 是潜在环，已用原子自增消除。

### 10. lock vs latch

- **一句话定义**：lock 保护事务语义（行、缝，持续到 commit，可查可见）；latch 保护物理结构（页、树，操作完即放，毫秒级，用户无感）。
- **为什么存在**：中文都叫"锁"，混谈会把"latch 等待"误诊成"行锁等待"。
- **怎么用**：排障时先分世界——50s 超时、`data_locks`、死锁日志都是 lock 世界的词；latch 等待是毫秒级内部现象，监控里看不到也不用管。
- **底层机制/证据**：行锁按页内记录编址只落叶子用户记录——实测 A 持 id=20 锁时，同一棵树上 UPDATE 10/30、SELECT 30 FOR UPDATE 全部秒过；页分裂"蟹行"用 latch，不计入 `innodb_lock_wait_timeout`，`data_locks` 里看不见。
- **易错点**：以为锁住行连页/树都锁了；以为 latch 等待走 50s 超时。
- **面试问法**：30 秒版——**lock 是事务级的行与缝，rollback/commit 释放；latch 是线程级的页与结构，语句做完就放。排障时 50s 超时、data_locks 都是 lock 世界的词。**
- **追问链**：→ *"非叶子节点被谁保护？"* latch（页分裂蟹行）。→ *"行锁为什么不上溯？*" 树根会被第一个行锁占住 = 串行化，所以刻意停在叶子。

## 三、30 秒答案集

1. **丢失更新病根**：读-改-写写回的是算好的旧值；串行也丢。修法 = 算术下放到库：`SET x = x + 1`。
2. **原子自增三要点**：列表达式一条 SQL；rowcount==0 兼做存在性判断；不需要 FOR UPDATE。
3. **三种锁**：记录锁点、间隙锁缝（不含端点）、临键锁点+左缝；唯一索引等值命中退化纯记录锁。
4. **LOCK_DATA**：锁的锚点记录，不是边界值；条件值只活在 server 层；supremum 代表表尾之后。
5. **锁比 WHERE 宽**：向两端对齐到真实记录，缝不能从中间切；INSERT 意向锁撞缝才等。
6. **RR vs RC**：RR 有间隙锁防幻读；RC 无缝锁——不防幻读是没设岗。
7. **快照读 vs 当前读**：快照走 ReadView（RR 首次 SELECT 定），当前读读最新已提交+加锁。
8. **autocommit**：每条语句独立事务；显式 BEGIN 才成组；连接断开 = 未提交即回滚。
9. **锁跟计划走**：建索引 ≠ 用索引；90% 命中优化器弃索引，锁形不变；Handler 计数器验真，EXPLAIN 只是意图。
10. **走索引后锁翻倍但变好**：聚簇变纯记录锁，防插入归二级索引的缝，误伤半径缩小。
11. **回表**：二级索引叶子存主键，取整行要回聚簇随机 IO；Using index = 覆盖免回表。
12. **免 filesort ≠ 免回表**：Backward index scan 管排序，Using index 管覆盖，两个独立标志。
13. **key_len**：只算用于 seek 的列，ORDER BY 列不算；utf8mb4 每字符 4 字节。
14. **最左前缀**：断一列后全断——定位与排序双失效。
15. **1213 vs 1205**：死锁秒级事件驱动主动拆局；锁等待超时是排队到期限；修法统一顺序或原子语句。

# 靶 1：incr_doc_count 原子自增（默写 SQLAlchemy 分支）
def incr_doc_count(self, kb_id: UUID, delta: int) -> None:
    stmt = (update(KnowledgeBase)
            .where(KnowledgeBase.id == kb_id)
            .values(doc_count=KnowledgeBase.doc_count + delta))
    result = cast("CursorResult[Any]", self.session.execute(stmt))
    if result.rowcount == 0:
        raise NotFoundError(f"kb {kb_id} not found")
# 要点：列表达式（加法在库）；rowcount 判存在；无 SELECT 无 FOR UPDATE

## 六、可以讲成故事的三段

1. **建了索引，锁一个没少**。背景：给 status 建索引后重跑锁实验。我以为"索引会让锁变少"。实际 5039 → 5039 一模一样——90% 命中下优化器执行时放弃了索引，EXPLAIN 还报 type=index 骗我。教训：**锁跟执行计划走，EXPLAIN 是意图、Handler 是事实**。
2. **FORCE 之后锁翻倍我反而高兴**。背景：FORCE INDEX 对照实验。我以为锁多了是坏事。实际 9014 个锁里聚簇全是纯记录锁（不带缝），防插入交给二级索引——误伤半径从全表缩到"只挡 ready"。教训：**评价锁不只数数量，看形状：谁被误伤、防的什么**。
3. **死锁日志比想象中友好**。背景：第一次手工复现死锁，顺序滑了只读到旧日志。我以为读日志要啃十六进制。实际每段只看两行——HOLDS 和 WAITING FOR 的 `asc` 值就是主键明文，环一眼可见。教训：**怕日志是因为没分类；先知道"该看哪四样"，日志就从天书变成对账单**。
