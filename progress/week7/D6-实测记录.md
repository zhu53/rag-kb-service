### 事故 1：`1101 BLOB, TEXT ... can't have a default value`

```
ALTER TABLE documents ADD COLUMN content TEXT NOT NULL DEFAULT ''
```

**根因**：`server_default=''` 会渲染成 DDL 的 `DEFAULT ''`，而 MySQL 的 TEXT/BLOB 列**不许有默认值**。
SQLite 没这条限制——典型的"单测发现不了、只有真库才炸"。

**半途状态**（比报错本身更值得记）：`uq_chunk_doc_seq` 排在 `add_column` **之前**，它已经建成功并**隐式提交**；
`alembic_version` 还停在 `b0846e5e87de`。这就是 D5 ③ 讲的"库的真实结构 ≠ 版本号记录"的活体标本。

**修复**：手工 `DROP INDEX uq_chunk_doc_seq` 还原已生效的那条 op，然后 **模型和迁移两边同时**删掉 `server_default`。
只改一边 → `alembic check` 立刻报 diff（它比的是"模型 vs 库"）。

为什么这次改历史迁移文件是合法的：这条迁移没 commit、没 push、没在第二个库跑过——**它还是草稿**。

### 事故 2：`1553 Cannot drop index 'ix_documents_kb_id': needed in a foreign key constraint`

**根因**：upgrade 的顺序是"先 drop 单列索引，再建复合索引"。执行到 drop 那一刻，`documents.kb_id` 这个 FK 列
**没有任何索引覆盖**，MySQL 直接拒绝。

规则一句话：**迁移改索引，先建后拆——新桥先通车，再拆旧桥。**

`downgrade` 犯的是同一个错（先 drop 复合、再建单列），所以两个函数都要调顺序。
autogenerate **不会**替你排这个序，它按内部顺序输出——这正是 D5 说的"生成的是草稿，人工读是必要工序"。

修复后的顺序：upgrade 里 `create_index → drop_index`，downgrade 里 `create_index → drop_index`（镜像）。
读一遍确认：任何时刻 `kb_id` 上至少有一个索引在。

### 收尾验证

```
upgrade head  → Running upgrade b0846e5e87de -> 9540b9312d99
check         → No new upgrade operations detected.
downgrade -1  → Running downgrade 9540b9312d99 -> b0846e5e87de
upgrade head  → Running upgrade b0846e5e87de -> 9540b9312d99
SHOW INDEX    → ix_doc_kb_created 在，ix_documents_kb_id 不在
```

### 事故 3：探针 A 段 `0 -> 0`，201 却一行没落

第一版改完，探针输出：`POST 201`、`GET total = 0`、`MySQL 0 -> 0`。

**根因**：6 个 handler 都写成 `KBService(KBRepository(session))` —— **第二个参数 `session=session` 漏了**。
`_commit()` 里 `if self._session is None: return` 把"忘传"变成了"静默成功"：

| 环节 | 结果 | 有没有报错 |
|---|---|---|
| `repo.flush()` | INSERT 已发出，主键到手 | 没有 |
| `service._commit()` | `_session is None` → 直接 return | 没有 |
| 请求结束 `get_db` | `finally: close()` → 未提交事务回滚 | 没有 |

**三层都以为自己成功了。** 这是"零症状"的教科书案例。

**修复**：6 处补 `session=session`。

**教训**：`session: Session | None = None` 这个默认值，买到了单元测试的方便（fake repo 没有真 session），
付出了这次的零症状 bug——**"生产路径忘传"和"测试路径故意不传"在类型上长得一模一样，mypy 抓不到**。

更硬的写法（今天已落到 `DocService` / `RagService`）：构造时检查"repo 或 session 至少给一个"，
缺了当场 `ValueError`，堆栈第一行就是病因。

### 两个技术判断

**`update_status` 为什么用"读改写"而不是 `update()` 语句**：

| | `incr_doc_count` | `update_status` |
|---|---|---|
| 语义 | **相对量**（`doc_count + delta`） | **绝对值**（`status = "ready"`） |
| 写法 | 必须单条 SQL（读改写会丢更新，D4 实测） | 读出来改属性，commit 时 ORM 生成 UPDATE |

判据：**相对量必须下推到 SQL，绝对值可以在内存改。**

另外 `session.get(Document, doc_id)` 在这里**不发 SELECT** —— `create` 刚 `add` 过，对象在 identity map 里。

**响应体里的 `chunk_count` 陷阱**：`repo.create` 返回的 `row` 是那一刻的快照，
`_parse_sync` 改的是库和 ORM 对象。不补这一步，接口会返回 `chunk_count: 0 / status: pending`，
而库里是 `4 / ready`——用户看到"处理中"，刷新变"就绪"。

## 4. 集成测试（30min）

### 事故 4：门禁的覆盖率判定**从来没生效过**

补完测试后门禁输出自相矛盾：

```
FAIL Required test coverage of 95% not reached. Total coverage: 94.75%
[PASS] pytest + 覆盖率门禁 (95%)
门禁全绿，可以提交
```

查下来两道坑叠加：

1. **本项目装的 `pytest-cov` 在 `pytest_terminal_summary` 里只打印 FAIL 文案，从不设置 `session.exitstatus`**
   （源码里搜不到 exitstatus）→ `--cov-fail-under` 达标与否 pytest 都退 0
2. **`coverage report --fail-under` 用四舍五入后的整数比较** → 94.75 round 成 95 → 不触发

后果：**覆盖率从 96% 掉到 60%，门禁照样全绿。** 之前几周没暴露，只是因为它恰好一直在 95 以上。

**修复**（`scripts/check.py`）：绕开两者的口头表态，`coverage json` 读精确浮点数自己比。

> 判据必须来自数据，不能来自工具的口头表态。

一句话总结：这和上午那个 bug 是同一类——**"报告成功"和"实际成功"是两件事**，
`flush` 报成功不等于落库，`[PASS]` 报成功不等于达标。

### 测试隔离

`get_db` 在测试里必须被换掉，否则 API 测试直接打 `kb_dev`：用例间串数据（`assert 2 == 1`）、
撞唯一约束（`IntegrityError`）。`conftest.py` 里加了 autouse 的 `db` fixture：

- sqlite 内存库 + **`StaticPool`**（默认连接池下每个连接是独立的 `:memory:` 库，看不见彼此）
- 每例清表
- `app.dependency_overrides[get_db] = _get_db`（**必须是生成器函数**，`lambda: iter([...])` 会被当成普通依赖，注入进去的是迭代器）

这里用 `create_all` 是**合法**的，和被否决的生产用法不同：
测试要"从零直接到最新"，没有存量数据、不需要演进；生产要"从当前版本走到下一版"。
判据：**有没有历史状态要维护**。

### 真 MySQL 集成测试

原计划建独立 `kb_test` 库，实测 `kb` 账号没有 CREATE 权限（`1044 Access denied`）。

**折中**：用 `kb_dev` + **专属 owner UUID**（`7777…`）隔离——断言只查自己这个 owner，
结束按 owner 删干净，不清表、不碰别人的行。

> 没有 DBA 授权时，测试隔离靠"数据归属"而不是"库归属"。

`tests/test_db_integration.py`，默认 skip（`KB_TEST_MYSQL=1` 才跑），门禁不受影响。

## 5. 演示剧本（6 步，`probes/demo_playbook.py`）

```
1) 建库        201  kb_id=ec257955-…
2) 传文档      201  status=ready  chunk_count=4  正文=1200 字
3) 列文档      200  total=1
4) 提问        200  sources=1 条   片段长度=200 字（不是整篇 1200 字）
5) 新连接查    正文=1200 字  status=ready  chunk_count=4  chunks 行=4
6) EXPLAIN    key=ix_doc_kb_created  rows=1  Extra='Using where; Backward index scan'
            —— 无 filesort
```

第 5 步的做法：不真重启 uvicorn，而是让**另一个进程**去查——`get_db` 的会话早在请求结束时关了，
还能读到，说明数据不在任何进程的内存里。**"重启还在"的本质是"不依赖进程内状态"。**

第 4 步的插曲值得记：最初用"测试文档内容是什么？"提问，`sources = 0`。
原因是 `_retrieve` 用 `question.split()` 按**空格**分词，中文整句被当成一个词，一次都命中不了。
**这是 W12 换向量检索的动因之一**，不是接线问题。

## 6. 遗留债（写进 W8 首日）

1. **`IntegrityError` 没有翻译成 409**：`uq_kb_owner_name` 现在由 DB 保证，但重名建库会抛
   `IntegrityError` → 500，API 文档承诺的"名称不可重复"应该是 409。
2. **`KBUpdate` 传 `{"name": null}` 会撞 NOT NULL**：`setattr(obj, "name", None)` 需要挡掉。
3. **`update` 的 `updated_at` 返回旧值**：`repo.update` 在 commit 之前就 `to_row()`，`onupdate` 还没发生。
4. **另 2 类变异体**（删 `where` 条件 / 删索引）挪到 W8 首日。
5. **`status` 单列索引**仍在（D3 实物对照），删它要**新写一条 drop_index 迁移**，不能改历史。
6. **【功能需求，非 bug】批量上传文件**（用户 11-19 提出）：当前"上传"是假的（页面内置文本，
   `POST /documents` 收 JSON）。真·文件上传按路线图分期落：W8 单文件 `UploadFile`（含上传安全）→
