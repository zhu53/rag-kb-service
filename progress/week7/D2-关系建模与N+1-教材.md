## §零 主线：两条线，一条分界线

本篇所有知识点钉在两个时刻上：

```
【建表时】                          【查询时】
ForeignKey 声明谁挂谁              relationship 让你写 kb.docs
  ↓                                  ↓
数据库记住这条法律                  Python 假装两个表是一个对象图
  ↓                                  ↓
插孤儿行 → ERROR 1452（实测）        访问 .docs 的那一刻 → 可能又是一条 SQL
  ↓                                  ↓
删父行 → ON DELETE CASCADE 带走子行  列表页循环访问 → N+1（1 条变 N+1 条）
```

**贯穿全篇的分界线只有一句：**

> **外键是数据库的法律**（数据对不对，它管）；**relationship 是 Python 的便利**（写起来顺不顺，它管）；**N+1 是便利的账单**（每一点便利背后可能是一条 SQL，它管）。

三者经常被混成一团。混了的人会说"我加了 relationship 所以有外键约束了"——错，**relationship 不产生任何数据库约束**；也会有人说"我建了外键所以 `kb.docs` 能用"——也错，**外键不产生任何 Python 属性**。今天读完，你要能一句话拆开这三个东西。

## 术语表（每个词一句人话 + "没有它会怎样"，正文首次出现还会再解释）

| 词 | 一句人话 | 没有它会怎样 |
|---|---|---|
| 外键（FK） | 子表里一列，声明"我的值必须是父表某行的主键" | 谁都能塞一个不存在的 kb_id，垃圾数据没人拦 |
| 父表 / 子表 | 1:N 里"1"的那边是父，"N"的那边是子；**外键存在子表** | 方向搞反，约束建不出来 |
| JOIN | 把两张表按条件拼成一张宽表的 SQL 操作 | 想要"知识库名 + 文档标题"就得查两次再手动拼 |
| 笛卡尔积 | 两表行数的乘积；JOIN 不加 ON 条件时的产物 | 3 个知识库 × 6 篇文档 = 18 行垃圾 |
| 级联（CASCADE） | 删父行时数据库自动带走子行 | 父删了子变孤儿，或者反过来删不掉 |
| 懒加载 | 访问关系属性的那一刻才发 SQL 去查 | ——（它本身没问题，是 N+1 的机制） |
| 预加载 | 查询时声明"把关系也一起查了"（`selectinload`/`joinedload`） | 列表页每行都偷偷补一条 SQL，人还不知道 |
| N+1 | 1 条主查询 + 每行补 1 条 = N+1 条 SQL | 页面慢 10 倍，本地没感觉、上线就炸 |

## §一 SQL→关系翻译课：外键与 JOIN（A）

你没系统写过 SQL，这节补最小必要集。**全部在真 MySQL 上验证过**（探针 `probe_fk.sql`，3307 的 `kb_dev` 库，跑完已清理）。

### 1.1 外键：数据库替你把关的那道门

**痛点先来。** 两张表，知识库和文档：

```
knowledge_bases            documents
+----+--------+            +----+---------+-------+
| id | name   |            | id | title   | kb_id |
+----+--------+            +----+---------+-------+
| 1  | kb-AI  |            | 2  | doc-a   | 1     |
+----+--------+            | 3  | doc-b   | 1     |
                           +----+---------+-------+
```

`documents.kb_id` 这列是**你自己写的约定**：它说"这行文档属于哪个知识库"。没有外键约束时，这个约定只活在你的代码里——下面的 SQL 数据库**照单全收**：

```sql
INSERT INTO documents (id, title, kb_id) VALUES (1, 'ghost-doc', 999);  -- 999 不存在！
```

谁都没拦。这行文档从此是孤儿：列表页查不出来（JOIN 时匹配不到父行），删除统计时数不上，永远躺在表里。**数据库不认识你的业务约定，除非你用外键把它变成法律**：

```sql
CREATE TABLE documents (
  id    INT PRIMARY KEY,
  title VARCHAR(60) NOT NULL,
  kb_id INT NOT NULL,
  CONSTRAINT fk_doc_kb FOREIGN KEY (kb_id)
    REFERENCES knowledge_bases (id)   -- "kb_id 必须是 knowledge_bases.id 里的一个真值"
    ON DELETE CASCADE
) ENGINE=InnoDB;
```

**实测（MySQL 3307，探针原文输出）**——建好外键后插孤儿：

```sql
INSERT INTO probe_doc_fk (id, title, kb_id) VALUES (1, 'ghost-doc', 999);
```

```
ERROR 1452 (23000): Cannot add or update a child row: a foreign key
constraint fails (`kb_dev`.`probe_doc_fk`, CONSTRAINT `fk_doc_kb`
FOREIGN KEY (`kb_id`) REFERENCES `probe_kb_fk` (`id`) ON DELETE CASCADE)
```

`1452` 就是"子行挂到了不存在的父行上"。**记这个错误码**——以后你写代码时碰到它，一眼就知道是"外键方向搞反了"或"父行还没插入就插了子行"（比如忘了 `flush()`，D1 说过：flush 才拿到主键）。

### 1.2 JOIN：把两张表拼成一张宽表

先建立直觉：JOIN 的底层动作是**笛卡尔积**——左表每一行 × 右表每一行，全部配一遍对。

```
左表 2 行 × 右表 3 行 = 6 行（全配对）
```

6 行里绝大多数是垃圾配对，所以 JOIN 永远跟着一个 **ON 条件**："只留下 kb_id == 父表 id 的那些对"。

完整 SQL（这是你本篇第一次正经写 JOIN，跟着抄一遍）：

```sql
SELECT kb.name, doc.title
FROM knowledge_bases kb
JOIN documents doc ON doc.kb_id = kb.id;
```

三个新记号，5 秒钟解释完：
- `knowledge_bases kb`：给表起短别名，后面写 `kb.name` 不用写全名；
- `JOIN ... ON ...`：拼表 + 过滤条件；
- `doc.kb_id = kb.id`：**这就是外键关系在 SQL 里的长相**——你建外键时声明的那对列，JOIN 时就是拿它们做匹配。

**手算一遍（别跳，30 秒）**：父表 1 行 `kb-AI`，子表 2 行都挂 kb_id=1。笛卡尔积 1×2=2 行，ON 过滤后 2 行都留下：

```
+--------+---------+
| name   | title   |
+--------+---------+
| kb-AI  | doc-a   |
| kb-AI  | doc-b   |
+--------+---------+
```

### 1.3 INNER 与 LEFT：差在"父行没有子行时，父行还出现吗"

上面那个 `JOIN`（全名 `INNER JOIN`）有个性质：**没有文档的知识库根本不出现**。它没有可匹配的子行，ON 过滤时被扔掉了。

列表页通常不想这样——"kb-legal"下面一篇文档都没有，你也想让它出现在列表里（文档数显示 0）。这时用 **LEFT JOIN**："左表全保留，右表匹配不上就填 NULL"：

```sql
SELECT kb.name, COUNT(doc.id) AS doc_count
FROM knowledge_bases kb
LEFT JOIN documents doc ON doc.kb_id = kb.id
GROUP BY kb.id;
```

```
+----------+-----------+
| name     | doc_count |
+----------+-----------+
| kb-AI    |         2 |
| kb-legal |         0 |   ← INNER JOIN 下这行会消失
+----------+-----------+
```

一句话记死：**INNER = 两边都要有；LEFT = 左边全保留**。面试问"什么时候用 LEFT JOIN"，答案不是背口诀，是这个业务判断：*孤儿的一方可不可以丢*。

### 1.4 把 SQL 翻译回业务

本篇之后，你看到"关系"两个字，脑子里要有这张对照表：

| 业务说法 | 数据库里的东西 | Python 里的东西 |
|---|---|---|
| "文档属于知识库" | `documents.kb_id` 外键列 | `Doc.kb` 属性 |
| "知识库有若干文档" | （没有额外的东西，就是上面那条外键从反面看） | `KB.docs` 属性 |
| "查知识库和它的文档" | 一条 JOIN（或两条 SQL） | `kb.docs`（可能触发额外 SQL，§六） |

**注意第二行**："知识库有若干文档"在数据库层**没有任何新东西**——不需要在建表时"声明一对多"，一个方向的外键就同时表达了两个方向的关系。`KB.docs` 这个属性**只存在于 Python 层**，这就是下一节 relationship 的事。

## §二 痛点：没有 relationship 的时候，人这么干活（A）

D1 你已经会手写 `Session` 存一张表了。现在把需求加一档：**创建一个知识库，带 2 篇文档**。没有关系辅助时，代码长这样：

```python
with Session(engine) as s:
    kb = KB(name="kb-AI")
    s.add(kb)
    s.flush()                    # 不 flush，kb.id 是 None，下面没法填！
    for t in ("doc-a", "doc-b"):
        s.add(Doc(title=t, kb_id=kb.id))   # 手动把父表主键抄给子表
    s.commit()
```

三个别扭，每个都是后面一节的引子：

1. **`flush()` 是自己记着的**——不 flush 就没有 `kb.id`，`kb_id=None` 插进去直接 1452（或 NOT NULL 报错）。顺序错了数据库才告诉你。
2. **查询时手动 JOIN**——想要"知识库 + 文档"，得自己写 §一 那条 JOIN 的 ORM 版本，或者查两次再拼。
3. **列表页的查询会退化成循环查询**——"列出 3 个知识库，每个显示文档数"，没有关系时你的第一反应是：

```python
kbs = s.scalars(select(KB)).all()
for kb in kbs:
    n = s.scalar(select(func.count()).where(Doc.kb_id == kb.id))  # 每循环一次发一条 SQL！
```

3 个知识库 = 1 + 3 = **4 条 SQL**。这段代码没坏、能跑、结果全对——只是慢。它就是 N+1 的**手写版**。下一节你会看到 ORM 的 relationship 在"帮你省掉这段手写"的同时，**用更隐蔽的方式把同一个坑还给你**。

## §三 最小可跑示例（A）—— 5 分钟，亲手跑

把下面文件存成 `scratch/d2_min.py`（`scratch/` 已在 `.gitignore` 里）：

```python
"""D2 最小示例：两张表 + relationship + 穿表访问。"""
from sqlalchemy import ForeignKey, String, create_engine, select
from sqlalchemy.orm import (
    DeclarativeBase, Mapped, Session, mapped_column, relationship,
)


class Base(DeclarativeBase):
    pass


class KB(Base):
    __tablename__ = "min_kbs"
    id: Mapped[int] = mapped_column(primary_key=True)
    name: Mapped[str] = mapped_column(String(50))
    # Python 层的"一对多"：一个 KB 有多个 Doc
    docs: Mapped[list["Doc"]] = relationship(back_populates="kb")


class Doc(Base):
    __tablename__ = "min_docs"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(60))
    # 数据库层的"谁挂谁"：外键列，存在"多"的这一边
    kb_id: Mapped[int] = mapped_column(ForeignKey("min_kbs.id"))
    kb: Mapped["KB"] = relationship(back_populates="docs")


engine = create_engine("sqlite:///./scratch/d2_min.db", echo=True)  # echo=True：每条 SQL 打印出来

Base.metadata.drop_all(engine)
Base.metadata.create_all(engine)

with Session(engine) as s:
    kb = KB(name="kb-AI", docs=[Doc(title="doc-a"), Doc(title="doc-b")])
    s.add(kb)          # 只 add 父对象——子对象跟着一起进来了
    s.commit()         # 不用手动 flush 抄 kb_id：ORM 替你排好了顺序

with Session(engine) as s:
    kb = s.scalars(select(KB)).first()
    print(kb.name, [d.title for d in kb.docs])   # kb.docs：像访问 Python 列表一样穿表
```

跑法（仓库根）：

```powershell
# Windows PowerShell
& .\kb-service\.venv\Scripts\python.exe .\scratch\d2_min.py

# Git Bash / Linux
./kb-service/.venv/Scripts/python.exe ./scratch/d2_min.py
```

**读输出时盯住三件事**（对照 D1 的 autobegin 知识）：

1. `INSERT INTO min_kbs ...` 和两条 `INSERT INTO min_docs ...`——**你只 add 了一个对象，发出了三条 INSERT**，而且子表的 `kb_id=?` 参数里是 1（ORM 替你抄好了主键）。这就是 relationship 的第一个便利：**插不用你抄 id**。
2. INSERT 顺序是**父先子后**——ORM 按"父行先有主键"的依赖自动排序，不用你操心 §二 痛点 1。
3. 最后 `kb.docs` 那一行的前面，会有一条 `SELECT ... FROM min_docs WHERE min_docs.kb_id = ?`——**穿表访问触发了一条新 SQL**。这就是懒加载，§六 的主角。

**判据**：这段跑不出来（或跑出来但看不懂这三件事），§四 别往下读，先回头。

## §四 三个真相：ForeignKey、relationship、back_populates 各管什么（A）

最小示例里有三行"关系代码"，初学者最容易混成一锅。逐个拆：

### 4.1 `ForeignKey("min_kbs.id")` —— 数据库层的法律

`kb_id: Mapped[int] = mapped_column(ForeignKey("min_kbs.id"))` 翻译成 SQL 是：

```sql
kb_id INT NOT NULL, FOREIGN KEY(kb_id) REFERENCES min_kbs(id)
```

它**只做两件事**：让数据库拒绝孤儿行（1452）、让级联删除有依据。**它不会给你任何 Python 属性**——没有它，`kb.docs` 照样可以定义（只是没有数据库兜底）；有了它，你手动写 `Doc(kb_id=999)` 在 commit/flush 时照样炸。D1b 学过的"约束在数据库"在这里兑现。

**方向口诀：外键永远在"多"的那边。** 一个知识库对多篇文档——"多"的是文档，所以 `kb_id` 在 `documents` 表。反过来想：如果外键放知识库表（`kbs.doc_id`），一个知识库只有一列，只能挂**一篇**文档——1:N 直接被表结构锁死成 1:1。这不是风格问题，是数学问题。

### 4.2 `relationship()` —— Python 层的便利

`docs: Mapped[list["Doc"]] = relationship(back_populates="kb")` **不产生任何 SQL 结构**。建表时它贡献的 SQL 是**零**。它做的是告诉 ORM：

- "我要在 KB 对象上有一个叫 `docs` 的属性，类型是 Doc 对象列表"；
- "这个列表的每个元素，是那些 `kb_id` 等于我主键的 Doc"（ORM 自己读 ForeignKey 推出关联列，你不用写）。

于是 `kb.docs` 看起来像普通 Python 列表：append、遍历、len 都行。但记住 §零 那句话——**每次真的去拿这个列表，都可能是一条 SQL**。便利和成本是两个账本。

### 4.3 `back_populates="kb"` —— 双向登记簿

为什么两边都要写 `back_populates`？因为关系是**双向**的：`kb.docs`（父看子）和 `doc.kb`（子看父）是同一对关系的两个面。`back_populates` 就是把两个面**互相登记**：

```python
kb.docs.append(doc)   # 顺手一看：doc.kb 也自动指回 kb 了——这就是 back_populates 在干活
```

不写它会怎样？两个属性各管各的，你 `kb.docs.append(doc)` 之后 `doc.kb` 是 `None`——数据没坏（flush 时外键照样填），但 Python 层的两个视图不同步，早晚写出依赖"另一边自动更新"的代码然后翻车。一句话：**back_populates 管的是内存里两个属性的一致性，不管数据库**。

### 4.4 一张表收尾（面试也能这么答）

| 东西 | 在哪一层 | 产生 SQL 结构？ | 产生 Python 属性？ | 缺了会怎样 |
|---|---|---|---|---|
| `ForeignKey` | 数据库 | **是**（外键约束） | 否 | 孤儿行没人拦（1452 拦不住） |
| `relationship` | Python | 否 | **是** | 没有穿表属性，退回 §二 手写时代 |
| `back_populates` | Python | 否 | 是（双向一致性） | 两个方向的属性各自为政 |

## §五 三张表设计：documents 与 chunks（A；向量表小节 L）

今天的动手任务把项目从一张表扩到三张。设计依据就是 §一 + §四：

```
knowledge_bases (已有)
      ↑ kb_id (FK, ON DELETE CASCADE)
  documents（新）
      ↑ doc_id (FK, ON DELETE CASCADE)
  chunks（新）
```

**为什么是两层而不是一层**：RAG 的检索单位是"分块"（chunk），分块永远属于某篇文档（文档删了它的分块就是垃圾），文档属于某个知识库。挂靠链=检索链，所以表结构跟着挂靠链走。

### 5.1 documents 表（A）

```python
class Document(Base):
    __tablename__ = "documents"

    id: Mapped[UUID] = mapped_column(Uuid, primary_key=True, default=uuid4)
    kb_id: Mapped[UUID] = mapped_column(
        Uuid, ForeignKey("knowledge_bases.id", ondelete="CASCADE"), index=True
    )
    title: Mapped[str] = mapped_column(String(200))
    status: Mapped[str] = mapped_column(String(20), default="pending")
    chunk_count: Mapped[int] = mapped_column(default=0)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), default=lambda: datetime.now(UTC)
    )
    updated_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(UTC),
        onupdate=lambda: datetime.now(UTC),
    )

    def to_row(self) -> DocRow:
        return DocRow(
            id=self.id,
            kb_id=self.kb_id,
            title=self.title,
            content="",  # 正文不在 documents 表，在 chunks（见下）
            status=self.status,
            chunk_count=self.chunk_count,
            created_at=self.created_at,
            updated_at=self.updated_at,
        )
```

四个设计决定，每个都要能说出"为什么"（D1b 的训练在这里接着用）：

1. **`kb_id` 加 `index=True`**——"列出某知识库的全部文档"是最高频查询，WHERE 条件就是 `kb_id`。不加索引，这条查询在 MySQL 里就是全表扫（D3 会用 EXPLAIN 实证这句话，今天先记住决定）。
2. **`ondelete="CASCADE"` 写在 ForeignKey 里**——翻译成 DDL 就是 §一 实测的 `ON DELETE CASCADE`。
3. **主键仍用 UUID**——和 `knowledge_bases` 一致；文档 id 会出现在 API 路径里（`/docs/{id}`），不暴露行数。
4. **`status` 先放字符串**——处理中/就绪/失败是文档的常态（解析可能失败），W12 做向量化流水线时要靠它恢复。
5. **`chunk_count` 是冗余计数**——它能由 `COUNT(*) FROM chunks WHERE doc_id=?` 算出来，但我们仍然存一列：列表页要显示"12 个分块"，每个文档算一次 COUNT 就是 N+1（§六 会实测这个模式）。代价是切块时要同步更新它，属于"用写换读"的典型取舍。
6. **`updated_at` 用 `onupdate=` 而不是 `default=`**——`default` 只管 INSERT，`onupdate` 管 UPDATE：只要这行有字段被改，SQLAlchemy 自动把 `updated_at` 刷成当前时间，你一行代码都不用写。（`default` 和 `onupdate` 可以同时给，所以 INSERT 和 UPDATE 都覆盖到了。）

**为什么正文不放在 `documents` 表里？** 一篇 5 万字的 PDF，正文要是塞进 `documents.content`，每次 `SELECT * FROM documents` 都会把几十 MB 文本拖回内存——列表页根本不需要正文。正文只在检索时按需取，所以它落在 `chunks` 表，按块存、按块取。这也是 `to_row()` 里 `content=""` 的原因：**DTO 的字段由"上层需要的数据形状"决定，不是由表结构决定**；上层还没切块时，正文就是空。

### 5.2 级联的两种，别混（A）

**实测（MySQL 3307）**：`probe_doc_fk` 里插 2 篇文档挂 kb-AI，然后 `DELETE FROM probe_kb_fk WHERE id=1`：

```
docs_before_delete = 2
docs_after_delete  = 0      ← 父行一删，子行被数据库自动带走
```

这是**数据库级联**。但 ORM 还有第二种：Python 层 `relationship(cascade="all, delete-orphan")`。两者的差别是面试题，也是真坑：

| | 数据库级联（`ON DELETE CASCADE`） | ORM 级联（`cascade="all, delete-orphan"`） |
|---|---|---|
| 谁执行 | **数据库**（DELETE 语句一到就带子行） | **SQLAlchemy**（在 session 里逐个发 DELETE） |
| 生效条件 | 无条件生效 | **子对象必须在 session 里**；绕过 session 直接 `engine.execute("DELETE ...")` 它管不着 |
| 附带行为 | 只管删 | 还管"孤儿"：把 doc 从 `kb.docs` 里 remove，session flush 时自动 DELETE 它 |
| 本项目怎么选 | **两个都写** | —— |

**⚠️ 2026-11-14 实测补正**（探针 `probes/probe_cascade_order.py`，6 组对照，SQLite 开 `PRAGMA foreign_keys=ON`）

| 配置 | 子对象**没访问过** | 子对象**访问过** |
|---|---|---|
| 无 cascade、无 ondelete、`kb_id NOT NULL` | `UPDATE doc SET kb_id=NULL` → **IntegrityError**，父行没删掉 | 同上 |
| 无 cascade、无 ondelete、`kb_id` 可空 | UPDATE 置 NULL + DELETE 父 → **子行变孤儿，不报错** | 同上 |
| `cascade="all, delete-orphan"` | `DELETE FROM doc WHERE id=?`（逐行）+ DELETE 父 ✅ | 同上 |
| 只有 `ondelete="CASCADE"`（ORM 默认） | 仍走 UPDATE 置 NULL → **报错**，库级联没机会执行 | 同上 |
| `ondelete="CASCADE"` + `passive_deletes=True` | 只发 `DELETE FROM kb`，**库级联一条搞定** ✅ | 仍报错（已加载的还得处理） |

由此纠正三处常见误解：

1. **ORM 级联不需要你事先访问关系属性**——flush 时它自己会去加载子对象（除非 `passive_deletes=True`）。所以"子对象必须在 session 里"这个说法不准确。
2. **"数据库级联无条件生效"不成立**：ORM 默认会先把子对象外键置 NULL（nullify），把库级联挡在门外。实测只有 `ondelete`、没有 `cascade` 时，`s.delete(kb)` 直接报错。
3. **`cascade` 是必需的，不是可选项**：NOT NULL 外键上没有它，删父对象就报错；`ondelete` 保护的是"绕过 ORM 的路径"（裸 SQL、运维、别的服务）。

性能补充：`cascade="all, delete-orphan", passive_deletes=True` 配合 DB 级联，子对象未加载时可一条 SQL 删完（省掉 N 条逐行 DELETE）。本项目 D2 先按教材写 `cascade`，不加 `passive_deletes`；D4 讲锁和批量删除时再展开。

**为什么两个都写**：`cascade` 保证 ORM 路径（`s.delete(kb)`）能走通并正确删子；`ondelete` 保证任何绕过 ORM 的删除都不留孤儿行。

#### 5.2.1 两层都写时，库级联还执行吗？（A，2026-11-14 实测）

这是最容易被问倒的一句追问，答案反直觉：**执行，但没东西可删。**

先拆一个误解：`ON DELETE CASCADE` **不是触发器**。它没有"删父 → 触发一条 DELETE 子"这种独立动作。真实机制是——

> InnoDB 每删一行父行，**必须**去子表的外键索引上查一次"还有谁引用我"。这是外键约束的强制检查，删几行父行就查几次。查到引用行，才按规则处理（`CASCADE` 删掉 / `SET NULL` 置空 / `RESTRICT` 报 1451）。查不到，就什么也不做。

所以它不存在"被跳过"这回事，它是**幂等**的：删 0 行和删 1 行，结果一样。

**实测（`probes/probe_both_cascade.py`，MySQL 3307，度量 `Innodb_rows_deleted` 前后差值）**

每组都是 1 个知识库挂 2 篇文档，然后 `s.delete(kb)` + `commit()`：

| 场景 | 外键 `ondelete` | 并发插入第 3 篇 | 计数差值 | 删完后子行 | 说明 |
|---|---|---|---|---|---|
| A | 无 | 无 | **3** | 0 | ORM 删 2 子 + 1 父，父行删除时检查外键，无引用 → 什么都不做 |
| B | `CASCADE` | 无 | **3** | 0 | 同上。**库级联没有"再删一遍"**，它查了一圈，0 行 |
| C | `CASCADE` | 有 | **4** | 0 | 2 子 + 1 父 + **库级联补删了那第 3 篇** |
| D | 无 | 有 | **2** | 3（全回滚） | ORM 删了 2 子，删父行撞上第 3 篇 → `1451`，整个事务回滚 |

**B 和 C 的差值是这节的全部价值所在。**

- B 证明：**库级联在 ORM 干完活之后不会重复删**（差值仍是 3，不是 5）。多写的那层不是"再来一次"，是"查一次，没活就走"。
- C 证明：**它不是冗余的**。那第 3 篇是另一条连接、另一个事务插进去的，Session 的可重复读快照里根本没有它——ORM 只知道 2 篇，删了 2 篇；剩下 1 篇只有数据库看得见、也只有数据库能删。差值 4 就是它干的。
- D 反证：同样的并发场景，去掉 `ondelete` → `(1451, 'Cannot delete or update a parent row: a foreign key constraint fails')`，**删库操作整个失败**。这就是 C 里那层 `ondelete` 的实战价值。

一个读表时的坑：D 场景差值 **2** 但最终子行还是 **3 行**——因为 `Innodb_rows_deleted` 统计的是"删过多少行"，**回滚不会让它回退**。它是个操作计数器，不是净变化量。用计数器做实验时要记得这一层，否则会得出"删了 2 行却还有 3 行"的错觉。

**一句话记**

> ORM 级联管"我**看得见**的子对象"，库级联管"**我看不见**的"（并发插入、别的服务写入、运维裸 SQL、批量清理）。前者保证删除走得通，后者保证走得干净。

**代价**：库级联的检查不是免费的——每次删父行都要探一次子表外键索引。这是 `passive_deletes=True` 存在的理由（告诉 ORM"别自己加载了，直接删父行交给库"），也是 D3 讲索引时"外键列为什么必须建索引"的另一半答案：**不建索引，这个检查就是全表扫**。

### 5.5 建表日志里的 `PRAGMA main.` / `PRAGMA temp.` 是什么 —— B（知道即可；末尾有个真陷阱）

跑 §三 的最小示例，`create_all` 那一段会多出两组你没写过的语句，每张表各一对：

```sql
PRAGMA main.table_info("min_kbs")
PRAGMA temp.table_info("min_kbs")
PRAGMA main.table_info("min_docs")
PRAGMA temp.table_info("min_docs")
```

**一句话**：这不是建表语句，是 SQLAlchemy 在问"这张表**已经存在**吗"。`create_all()` 默认 `checkfirst=True`，建之前先查一遍，免得重复建表报错。`main` 和 `temp` 是 SQLite 的**两个命名空间**（不是两个数据库文件）：

- `main`：你的文件库或内存库，正常表都在这。
- `temp`：临时库，`CREATE TEMP TABLE` 建的表在这，连接一断就消失。

**为什么要问两遍**：SQLite 查询不带命名空间时，**先找 temp，找不到才找 main**——temp 里的同名表会**遮蔽** main 的表。既然存在性检查的目的是"等会儿查的时候会不会命中一张表"，那两边都得查。这条逻辑在 SQLAlchemy 源码里写死了（`sqlalchemy/dialects/sqlite/base.py` 的 `_get_table_pragma`）：

```python
# because PRAGMA looks in all attached databases if no schema
# given, need to specify "main" schema, however since we want
# 'temp' tables in the same namespace as 'main', need to run
# the PRAGMA twice
statements = ["PRAGMA main.", "PRAGMA temp."]
```

还有两个细节值得知道：

1. `PRAGMA database_list` 里**看不到 temp**（实测只返回 `main`）——temp 库是惰性出现的，所以不能靠遍历库列表发现它，只能硬编码再查一次。
2. 这两条 PRAGMA 是**短路**的：main 查到就立即 return，不再查 temp。所以"两张表各两条"说明当时**两张表都还不存在**；表建好之后再跑一次 `create_all`，每张表只会看到一条 `PRAGMA main.table_info`，然后跳过建表。

**三库对照（今天真跑的数据）**

| 场景 | 发出的 SQL |
|---|---|
| SQLite，`create_all()` 默认 | 每张表 `PRAGMA main.` + `PRAGMA temp.` 两条 |
| SQLite，`create_all(checkfirst=False)` | **一条 PRAGMA 都没有**，直接两条 `CREATE TABLE` |
| MySQL 8.4，同一套模型 | 只有 `DESCRIBE \`kb_dev\`.\`probe_tmp_kbs\`` 一条 |

结论：**看到 PRAGMA 就说明你在走 create_all 的存在性检查**；MySQL 上对应的是 `DESCRIBE`，目的相同、写法不同。这也顺带解释了两件事：测试里反复 `create_all` 会有额外往返（所以夹具用一次就够）；生产环境不该在启动时 `create_all`（用 Alembic 迁移），自然不会有这些查询。

**⚠️ 真陷阱：temp 里的同名表能让 `create_all` 静默跳过建表**

实测（`progress/week7/probes/probe_checkfirst.py` 实验 4）：先在同一连接上 `CREATE TEMP TABLE min_kbs (...)`，再 `create_all()`：

```
PRAGMA main.table_info("min_kbs")
PRAGMA temp.table_info("min_kbs")      ← main 空，转到 temp，查到了
...
CREATE TABLE min_docs (...)            ← 只建了 min_docs，min_kbs 被跳过
```

结果 `main` 里根本没有 `min_kbs`，但 `SELECT COUNT(*) FROM min_kbs` **不报错**（命中的是 temp 那张），只有显式写 `SELECT ... FROM main.min_kbs` 才暴露 `no such table: main.min_kbs`。另外实测 `drop_all()` 发的是 `DROP TABLE min_kbs`（不带命名空间），所以它删掉的也是 temp 那张表——检查、查询、删除三处都遵循"temp 优先"。

**你要记住的**：一个连接上建过同名 TEMP 表，它就会遮蔽真表，还能骗过 `create_all`。遇到"表明明建了却查不到"或"查到的数据莫名其妙"，先怀疑 temp 遮蔽。日常写业务代码基本碰不到，但被问"SQLite 有什么坑"时，这是个能讲出机制的答案（比背"SQLite 不支持并发"值钱）。

### 5.6 "这东西不存在"该由谁判断？——repo 还是 service（A，2026-11-14 用户质疑后补）

动手任务里会出现两个高度相似的问题，很多人在这一步把分层搞乱：

- **"kb 不存在 → 404"** 该由谁判断？
- **"doc 的 kb_id 指向一个不存在的 kb"** 该由谁拦住？

答案不同，因为**它们根本不是同一类判断**。

#### 判断一：业务意义上的"不存在" —— 在 service

看项目里现成的写法（`services/doc_service.py`）：

```python
def create(self, kb_id: UUID, user_id: UUID, data: DocCreate) -> DocOut:
    self.kb_service.get_or_403(kb_id, user_id)   # ← 第一行就检查了
    row = self.repo.create(kb_id, data)
```

注意这个方法名：**`get_or_403`**，不是 `get_or_404`。因为"kb 不存在"和"kb 是别人的"在 API 上要给不同响应（404 / 403），而这个判断需要 `user_id`——**repo 手里根本没有这个信息**。

这就是分层的真正判据，比"业务逻辑放 service"这种口号好用：

> **谁拥有做这个判断所需的全部信息，判断就归谁。**
>
> 存在性 + 归属权 → 需要 `user_id`、需要领域规则 → service
> 外键是否指向真实行 → 只需要存储事实 → 数据库约束

而 `NotFoundError("知识库不存在")` 这类异常，本质是**应用语义**（要翻译成 HTTP 404 的）。repo 的职责是"把数据存取做对"，它一旦开始抛 404 语义，就等于把 Web 层的东西提前拉进了存储层——W3 讲依赖方向时那条"内层不许知道外层的形状"，说的就是这件事。

#### 判断二：存储完整性 —— 在数据库，不在任何一层代码

那 repo 不该判断，是不是就没人管"孤儿 doc"了？不是。**外键约束管，而且它才是唯一可靠的保证。**

对比一下两条路：

| 做法 | 靠什么 | 可靠性 |
|---|---|---|
| service 先 `get_or_403` 再插入 | 一次 SELECT | **有洞**：查完到插入之间，另一个请求把 kb 删了（TOCTOU） |
| 数据库外键约束 | `FOREIGN KEY` | **无洞**：写在存储引擎里，任何路径都拦 |

所以正确的分工是**两层，职责不同**：

- service 的检查是**为了给出准确的错误响应**（404 说人话），顺带省掉一次必然失败的插入
- 数据库的约束是**为了保证数据不出错**，它不知道 HTTP 状态码，也不需要知道

**"判断是优化，约束才是保证"** —— 这句话面试能直接说，而且比背"分层要清晰"有用得多。

#### 为什么不用 `IntegrityError` 反推"kb 不存在"

有人会想：那让 repo 直接插入，撞了外键就抛 `IntegrityError`，service 捕获翻译成 404，不就行了？两个硬伤：

1. **文案是方言相关的**。同样是外键失败，SQLite 给 `FOREIGN KEY constraint failed`，MySQL 给 `(1452, 'Cannot add or update a child row: a foreign key constraint fails ...')`（`probe_fk.sql` 里实测过）。要判断原因就只能解析字符串，换库就崩。
2. **分不清是哪个约束**。`IntegrityError` 可能是外键、可能是唯一键、可能是 NOT NULL。同一篇文档插两个同名 `title`（如果加了唯一索引），拿到的也是 `IntegrityError`，你没法靠异常类型区分"kb 不存在"和"标题重复"。

所以 `IntegrityError` 只适合做**最后一道兜底翻译**（service 里 `except IntegrityError` → 409 Conflict / 404），不适合做**主判断路径**。

#### 落到代码上

| 位置 | 做什么 | 不做什么 |
|---|---|---|
| `doc_repo.create` | 构造对象、`add`、`flush`、`to_row()` | ❌ 不查 kb 存在、❌ 不抛 `NotFoundError` |
| `DocService.create` | `get_or_403` 判存在与权限 | ❌ 不管外键 |
| `documents.kb_id` 外键 | 兜住任何绕过 service 的写入 | —— |

这也解释了动手任务里那个测试为什么值得写：**测试 ③"插入 kb_id 不存在的 doc → `IntegrityError`"验证的不是 service，是约束层**。它证明"就算有人绕过 service 直接写库，数据也不会脏"。这和 service 的 404 检查是两回事，两个都要有。

## §六 N+1：一行代码的 SQL 账单（A，本篇核心）

### 6.1 现场还原（探针实测，逐行解读）

探针：3 个知识库，分别挂 2/1/3 篇文档。业务操作：「列出全部知识库 → 逐个读它的文档列表」。

**实验 A：什么都不加**

```
SELECT 条数: 4
  · SELECT probe_kbs.id, probe_kbs.name            ← 1 条主查询
  · SELECT probe_docs.id, probe_docs.title, probe_docs.kb_id   ← 读 kb1.docs 时补的
  · SELECT probe_docs.id, probe_docs.title, probe_docs.kb_id   ← 读 kb2.docs 时补的
  · SELECT probe_docs.id, probe_docs.title, probe_docs.kb_id   ← 读 kb3.docs 时补的
```

1 条主查询 + **每行 1 条**补查 = N+1。N 是行数。3 行时是 4 条，看起来无害——**这是它最阴险的地方**：本地 3 行没感觉，上线 500 个知识库就是 501 条 SQL，每条 2ms 也是 1 秒，列表页直接超时。

### 6.2 机制：为什么会这样（懒加载）

D1 学过 Session 是惰性的（第一条 SQL 才借连接）。懒加载是同一个设计哲学落到关系上：

> **查询 KB 时，ORM 只查 KB 的列**。`kb.docs` 这个列表此刻是"还没填的占位"；你**第一次访问它**的那一刻，ORM 才发 `SELECT ... WHERE kb_id = ?`。

为什么这么设计？**默认不浪费**——查 KB 列表的人不一定看文档，预先把 500 个库的文档全查一遍可能全白查。为什么变成灾难？**循环访问时，"按需"退化成"每行一次"**——因为每条补查都只带一个 `kb_id` 条件，ORM 不会自动把 N 个条件合并成一条 IN。

所以 N+1 的准确描述不是"ORM 有 bug"，而是：**懒加载的单次视角，叠加循环的整体视角，账单就爆了**。这是面试标准答案的第一句。

### 6.3 解法一：`selectinload` —— 两条 SQL，IN 打包

```
=== 实验 B：selectinload(ProbeKB.docs) ===
SELECT 条数: 2
  · SELECT probe_kbs.id, probe_kbs.name
  · SELECT probe_docs.kb_id, probe_docs.id, probe_docs.title   ← 第二条带了 WHERE kb_id IN (1, 2, 3)
```

声明方式（查询时加 option）：

```python
kbs = session.scalars(
    select(KB).options(selectinload(KB.docs))
).all()
```

机制一句话：主查询跑完拿到 N 个主键 → **第二条 SQL 用 `WHERE kb_id IN (主键列表)` 一次把所有子行捞回** → ORM 在内存里按 kb_id 分好组塞进各自的 `.docs`。之后你访问 `kb.docs` **不再发 SQL**（东西已经在内存里）。

### 6.4 解法二：`joinedload` —— 一条 SQL，JOIN 拼宽

```
=== 实验 C：joinedload(ProbeKB.docs) ===
SELECT 条数: 1
  · SELECT probe_kbs.id, probe_kbs.name, probe_docs_1.id AS id_1, probe_docs_1.title, probe_docs_1.kb_id
```

声明方式：

```python
kbs = session.scalars(
    select(KB).options(joinedload(KB.docs))
).unique().all()          # ← unique() 忘不得，见下面的实测
```

机制一句话：直接把 §一 的 LEFT JOIN 拼进主查询——一条 SQL 返回**宽行**（3 个知识库 × 6 篇文档 = 6 行），ORM 在内存里把 6 行"折叠"回 3 个 KB 对象。

**实测陷阱①：忘了 `.unique()` 直接报错**（探针原文）：

```
sqlalchemy.exc.InvalidRequestError: The unique() method must be invoked on
this Result, as it contains results that include joined eager loads against collections
```

原因：JOIN 宽行里同一个 KB 出现多次，ORM 要求你显式声明"我知道有重复行，请按主键去重"。**这是运行时报错，门禁抓不住**——因为它不是类型错，是数据形态错。

**陷阱②（B 级，讲原理不要求记）：joinedload + LIMIT 是错的**。SQL 层面 `LIMIT 3` 限制的是**宽行**数：3 个知识库各挂 2 篇文档，`LIMIT 3` 拿到的是"kb1 的前 3 篇文档"拼出来的 3 行——**第 2、3 个知识库直接消失**。SQLAlchemy 的对策是把主查询包成子查询再 LIMIT，但既然这么绕，规矩就一条：**分页 + 集合关系，用 selectinload，不用 joinedload**。

### 6.5 怎么选（背这张表）

| 场景 | 用哪个 | 为什么 |
|---|---|---|
| 列表页 + 每行带集合（知识库列表带 docs） | **`selectinload`** | LIMIT 安全、两条 SQL 的成本可接受、N 行不重复 |
| 单个对象 + 大量子对象（详情页） | **`selectinload`** 或单独查 | 同上 |
| 多对一 / 一对一（文档带它的 kb） | **`joinedload`** | 每行只有一个"父"，无重复行问题，一条 SQL 最省 |
| 就是想省往返、行数少 | `joinedload` | 一条 SQL |

一句话总纲：**集合用 selectinload（IN 两条），标量用 joinedload（JOIN 一条）**。

### 6.6 怎么发现自己代码里有 N+1

N+1 不会报错、测试全绿、功能全对——**只能靠看 SQL**。三个手段，按成本排：

1. 开发期：`create_engine(..., echo=True)`，肉眼数 SELECT 条数（今天探针干的事）。
2. 测试期：挂 `event.listen(engine, "before_cursor_execute", ...)` 数 SQL，断言"这个接口 ≤ 3 条"（今天探针的裁判就是这么写的）。
3. 上线期：慢查询日志 / APM。**但那时已经是事故了**——前两个手段才是工程师的活。

**面试落点**：被问"你怎么发现 N+1 的"，答"开发期开 echo 数 SQL，测试期用 before_cursor_execute 事件做断言"，比答"看日志"高一个档。

## §七 select() 2.0 风格与一个今天实测踩到的坑（B）

**会用即可，讲清"什么时候用"就够了。** 2.0 风格统一成一个入口：

```python
stmt = select(KB).where(KB.owner_id == uid).options(selectinload(KB.docs))
kbs  = session.scalars(stmt).all()        # Session 上的 scalars：直接拿 ORM 对象
```

`session.scalars(stmt)` = `session.execute(stmt).scalars()` 的快捷方式；`.unique()` 在有 joinedload 集合时必须加在 scalars **前面**。

**今天实测踩到的坑（B）**：探针第一版用 `engine.connect().execute(select(KB))`，结果 `.scalars()` 拿出来的是 **int**（主键值），不是 KB 对象——`kb.docs` 直接 `AttributeError: 'int' object has no attribute 'docs'`。

原因一句话：**`Connection.execute` 是 Core 上下文**，它把 `select(KB)` 当普通列查询编译，返回列值行；**ORM 对象、关系加载、身份映射，全是 Session 的产物**。规矩：**查实体永远走 Session**（`session.scalars(...)` / `session.execute(...)`），Connection 只留给不经过 ORM 的裸 SQL。

## §八 易错点表（A）

| 坑 | 症状 | 正解 |
|---|---|---|
| 外键放"1"的那边 | 建表能成，但 1:N 被锁成 1:1；或 `ForeignKey` 指错表 1452 | 外键永远在"多"的一边（`documents.kb_id`、`chunks.doc_id`） |
| 插子行报 1452 | `Cannot add or update a child row` | 父行还没落库——先 `flush()` 拿主键（D1），或检查外键方向 |
| 以为 relationship 会建约束 | 塞孤儿行没报错（SQLite） | relationship 管便利不管约束；SQLite 外键默认关（§十五），MySQL 才强制 |
| 忘 `back_populates` | `kb.docs.append(doc)` 后 `doc.kb` 还是 None | 两边都写 `back_populates`，内存双向同步 |
| 列表页循环读 `.docs` | 3 个库 4 条 SQL，500 个库 501 条 | `selectinload(KB.docs)`，两条封顶 |
| joinedload 忘 `.unique()` | `InvalidRequestError`（运行时，测试可能测不到这分支） | 集合 joinedload 必须链上 `.unique()` |
| joinedload + LIMIT/OFFSET | 第 2、3 个知识库消失，返回"kb1 的前 3 篇文档" | 分页 + 集合 → 换 selectinload |
| `Connection.execute` 查实体 | 拿到 int，`.docs` 炸 AttributeError | 查实体走 Session；Connection 只跑裸 SQL |
| `ondelete="CASCADE"` 拼成 `cascade=` | DDL 里没有 ON DELETE，删父行报 1452 拦截 | SQLAlchemy 参数名是 `ForeignKey(..., ondelete="CASCADE")`，ORM 内存级联才是 `cascade="all, delete-orphan"` |
| 只写 ORM 级联不写数据库级联 | 有人绕过 ORM 裸 SQL 清库 → 孤儿行 | 两个都写（§5.2） |

## §十二 面试问法（A）

### 12.1 三十秒版（背到能一口气说完）

> "N+1 是懒加载叠加循环查询造成的：ORM 查列表只发一条 SQL，但每行第一次访问它的关系属性时都会补一条 SQL，N 行就是 N+1 条。本地几行数据没感觉，上线列表页就慢数倍。解法是预加载——集合关系用 `selectinload`，两条 SQL 打包 IN；标量或多对一用 `joinedload`，一条 JOIN。我是开发期开 echo 数 SQL 发现的，不会等上线。"

（≤3 句的口径：第一句机制、第二句代价、第三句解法+发现手段。上面是展开版，练的时候先收成三句。）

### 12.2 追问链（三层递进）

**追一层（机制）**——"为什么 ORM 默认要懒加载，不是直接一次全查？"
→ 默认不浪费：多数查询不需要关系数据，预载是白查。懒加载把"查不查子表"的决定推迟到第一次访问那一刻。**但**这个决定是"每行独立"做的，循环场景下 N 个独立的小决定拼成一条大账单——单次视角对、整体视角错，这就是 N+1 的准确病根。

**追二层（边界/故障）**——"两种预加载各自什么情况下会坏？"
→ 沿"数据形态"轴：`joinedload` 的 JOIN 会产生重复宽行——集合关系必须 `.unique()`（忘了运行时 `InvalidRequestError`，实测）；再叠加 `LIMIT/OFFSET` 会**分页错行**（限制的是宽行数，后面的知识库消失）。`selectinload` 的 IN 列表有长度上限意识——N 特别大时一条 IN 几千个值也是负担，极端场景要分批。另外 SQLite 与 MySQL 的差别：行为一致（这是 ORM 层），但**约束层不一致**——SQLite 外键默认关，MySQL 强制。

**追三层（场景落地）**——"你项目里哪里有 N+1 风险？"
→ "列出知识库列表页"接口：每个库要显示文档数和文档标题，`kb.docs` 循环访问就是教科书 N+1。我的对策已经写进代码：repo 层 `list` 一律 `selectinload`，并有一个测试用 `before_cursor_execute` 事件断言 SQL 条数 ≤2——**把"N+1 不许回来"写成了回归测试**，不是靠 code review 的眼睛。向量库那层（W12，pgvector）同样要防：检索出的 chunk 再回查 doc 标题，如果不预载又是一个 N+1。

> **用法**：10 题先**闭卷口答**，再点开核对。答不出 ≤2 题算读懂；≥4 题答不出回 §零–§六 重走主线。

**题目清单**：

1. `ForeignKey` 和 `relationship` 各在哪一层？缺了各会怎样？
2. 外键应该建在哪张表上？为什么反过来不行？
3. `kb.docs.append(doc)` 之后 `doc.kb` 是 None，哪个参数没写？
4. 插文档报 `1452`，说出两个最可能的原因。
5. N+1 的"1"和"+N"分别是什么？病根一句话怎么说？
6. `selectinload` 发几条 SQL？第二条长什么样？
7. `joinedload` 忘了 `.unique()` 会发生什么？为什么 ruff/pytest/门禁抓不住它？
8. 为什么"分页 + joinedload"是错的？症状是什么？
9. 数据库级联和 ORM 级联（`cascade="all, delete-orphan"`）差在哪？为什么项目里两个都写？
10. 列表页接口你怎么保证上线后不出现 N+1？（说出具体手段，不是"注意一下"）

---

**答案**：

<details><summary>答案 1</summary>

`ForeignKey` 在数据库层：产生外键约束，缺了→孤儿行没人拦（1452 拦不住）。
`relationship` 在 Python 层：产生穿表属性，缺了→退回手写 JOIN/手动抄 id 的时代。
两者互不产生对方的东西。
</details>

<details><summary>答案 2</summary>

"多"的一边（documents.kb_id、chunks.doc_id）。反过来外键放"1"的一边，父表只有一列，1:N 被表结构锁死成 1:1——数学上不成立，不是风格问题。
</details>

<details><summary>答案 3</summary>

`back_populates`。它管的是**内存里两个方向属性的一致性**，不管数据库——flush 时外键照样填，数据没坏，但 Python 层两个视图不同步。
</details>

<details><summary>答案 4</summary>

① 父行还没插入就插了子行——忘了 `flush()`，主键还是 None/旧值；② 外键方向或目标列写错（kb_id 塞了不存在的值、或 FK 指错了表）。
</details>

<details><summary>答案 5</summary>

"1"=主查询 1 条；"+N"=每行第一次访问关系属性时补 1 条，共 N 条。病根一句话：**懒加载的"每行独立决定"叠加循环访问，单次视角对、整体账单爆**。
</details>

<details><summary>答案 6</summary>

2 条。第二条是 `SELECT ... FROM documents WHERE kb_id IN (主键列表)`——一次把所有子行捞回，内存里按 kb_id 分组。
</details>

<details><summary>答案 7</summary>

运行时 `InvalidRequestError: The unique() method must be invoked...`（实测）。抓不住的原因：它不是类型错（mypy 管不着）、不是 lint 违规（ruff 管不着），只有"真的用集合 joinedload 查询"这个分支跑到才炸——门禁的测试没覆盖到就漏。
</details>

<details><summary>答案 8</summary>

LIMIT 限制的是 JOIN 宽行的行数，不是知识库个数。症状：`LIMIT 3` 拿到的是"第一个知识库的 3 篇文档"，第 2、3 个知识库直接消失。规矩：分页 + 集合关系用 selectinload。
</details>

<details><summary>答案 9</summary>

数据库级联由数据库执行、无条件生效、只管删；ORM 级联由 SQLAlchemy 执行、**要求子对象在 session 里**、还管孤儿自动 DELETE。两个都写的原因：数据库级联是保底（防有人绕过 ORM 用裸 SQL 清库产生孤儿），ORM 级联是便利（`s.delete(kb)` 一行）。实测：MySQL 删父行后 docs 2→0。
</details>

<details><summary>答案 10</summary>

三道防线，按阶段：开发期 `echo=True` 肉眼数 SQL；测试期挂 `before_cursor_execute` 事件**断言 SQL 条数 ≤2**（把"N+1 不许回来"写成回归测试）；repo 层 `list` 一律默认 `selectinload`，不靠 reviewer 的眼睛。上线才看慢查询日志，那时已经是事故。
</details>

## §十五 附录（L：知道有这回事就行）

- **SQLite 外键默认关闭**：SQLite 除非显式 `PRAGMA foreign_keys=ON`（**按连接生效**），否则不强制外键——塞孤儿行不报错。所以"relationship 写得对不对、约束真不真"这类验证要在 MySQL 上做（今天的 `probe_fk.sql` 就是干这个的）。这也解释了"单测 SQLite + 真库 MySQL"的方言风险清单里为什么有这一条。
- **MySQL 8.4 无 VECTOR**：`CREATE TABLE t (emb VECTOR(3))` → `ERROR 1064`（D1b 实测）。向量 W12 走 Postgres + pgvector，今天 `chunks` 不建 embedding 列。
- **`--force` 的真实行为**：mysql 客户端默认**遇错即停**（今天探针实验 1 后的语句没执行）；`--force` 文档上说是"继续"，实测在 `-e "source ..."` 模式下后续语句的输出和执行都不完整——**跑有错误预期的 SQL 脚本，拆成多次跑最稳**。
