## §零·二 因果链（A）

七连问，每一问是上一问留下的麻烦：

| # | 上一问留下的麻烦 | 谁来解决 |
|---|---|---|
| 1 | service 里两句写，第二句失败时第一句已经写进去了 | 事务：一组语句要么全做要么全不做（§二） |

## §一 痛点：没有事务的世界（A）

假设你要实现"上传文档后，知识库的文档计数 +1"。两句 SQL：

```sql
INSERT INTO documents (id, kb_id, title, ...) VALUES (...);      -- 第 1 句
UPDATE knowledge_bases SET doc_count = doc_count + 1 WHERE id = ...;  -- 第 2 句
```

第 1 句成功、第 2 句还没执行时，进程崩了（断电、异常、OOM）。结果：

- `documents` 里多了一行；
- `knowledge_bases.doc_count` 停留在旧值。

**永远**对不上了——因为没有"撤销第 1 句"的机会。这不是概率问题：只要服务跑得够久，一定发生。反过来更糟的场景是扣款：

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 'a';  -- 我的钱扣了
UPDATE accounts SET balance = balance + 100 WHERE id = 'b';  -- 你还没收到
```

两句之间崩了，100 块凭空消失。

**事务就是解决这个的：把多条语句绑成一个整体，要么全做完，要么像没发生过一样。**

> 术语：**事务（transaction）**= 数据库执行的最小逻辑单元，内部所有语句要么全部生效（提交 commit），要么全部撤销（回滚 rollback）。


依次执行（逐句敲，观察每步输出）：

```sql
-- 看初始值
SELECT doc_count FROM knowledge_bases WHERE id='kb000001000000000000000000000000';
-- (当前应为 0)

BEGIN;                                        -- ① 开事务

UPDATE knowledge_bases SET doc_count = 99
 WHERE id='kb000001000000000000000000000000'; -- ② 改

SELECT doc_count FROM knowledge_bases
 WHERE id='kb000001000000000000000000000000'; -- ③ 本会话看：99（自己看得见自己的改）

ROLLBACK;                                     -- ④ 撤销

SELECT doc_count FROM knowledge_bases
 WHERE id='kb000001000000000000000000000000'; -- ⑤ 回到 0，像没发生过
```

**三个必须观察到的现象：**

1. **③ 能看到 99**：事务内的修改对**自己**可见（不然没法继续算）。
2. **④ 之后再查是 0**：undo log 把旧值放回来了。
3. **这一整段没有锁残留、没有报错**：回滚是干净的，不是"报错后才干净"。

然后把 ④ 换成 `COMMIT;` 再跑一遍：提交后 `ROLLBACK` 也救不回来（没有可回滚的东西了）。**BEGIN 到 COMMIT/ROLLBACK 之间就是事务边界。**

## §三 ACID 与 undo / redo（L）—— 一句话版本

这节标 **L**：面试会问"ACID 靠什么实现"，但追问一般不会深挖到源码级。**每条记一句话就够，不展开。**

| 性质 | 一句话 | InnoDB 里靠什么 |
|---|---|---|
| **A**tomicity 原子性 | 全做或全不做 | **undo log**：改之前先存旧值，回滚时反向套用 |
| **C**onsistency 一致性 | 数据从一个合法状态到另一个合法状态 | 是前三条的结果，不是独立机制 |
| **I**solation 隔离性 | 并发事务互不干扰 | **锁 + MVCC**（§五） |
| **D**urability 持久性 | 提交了就不丢 | **redo log**：先写日志再改数据页，掉电后靠日志重做 |

> 记法：**undo 管"后悔"，redo 管"掉电"，锁+MVCC 管"插队"**。

## §四 autocommit 与 Python 侧事务边界（A）

### 4.1 服务器侧：autocommit 默认开着

```sql
SELECT @@autocommit;   -- 1，即默认开
```

含义：**你没写 BEGIN 时，每一条语句都是一个独立事务**——执行完立即提交。所以：

- 单条 `UPDATE ...` 天然是原子的（一句就是一事务，要么成功要么失败）；
- 但**多条语句没有保护**，各提交各的——§一 的痛点就是它造成的。

**只有显式 `BEGIN`（或 Python 里的事务开启）之后，多条语句才被绑成一个事务。**

### 4.2 Python 侧：边界在哪

D1 教材讲过 `get_db`，现在把"事务边界"标上去：

```python
# api/deps.py（示意）
def get_db():
    db = SessionLocal()          # ← 连接从池里取出
    try:
        yield db                 # ← 请求处理期间：db 处于一个事务里
        db.commit()              # ← 边界终点：请求成功 → 提交
    except Exception:
        db.rollback()            # ← 请求失败 → 整体回滚
        raise
    finally:
        db.close()               # ← 连接还池
```

**事务边界 = 一个 HTTP 请求。** 请求里 service 做的所有写（insert 文档 + incr 计数），要么一起提交，要么一起回滚。这就是 §一 痛点在项目里的答案：`DocService.create` 里那句 `incr_doc_count` 和 insert 在同一个请求事务里，不会出现"文档插了、计数没更"。

### 4.3 一个容易搞反的点

**repo 层不 commit**（D2 定过：repo 只 `flush()`）。为什么？

- `flush()` = 把内存改动翻译成 SQL 发给数据库，**但不提交**——同一事务还能继续；
- `commit()` = 结束事务。谁该负责结束？**拥有完整信息的人**——service 知道"这一轮业务做完了没有"，repo 不知道。所以边界划在 service/请求层，repo 里 commit 就等于把边界切碎了，事务保护失效。

## §五 隔离级别与 MVCC（A）

### 5.1 先解决"写写冲突"：锁（一句话版，D4·下 展开）

两个连接同时 `UPDATE` 同一行：第二个会**阻塞等待**第一个提交（或回滚），拿到锁才继续。**写的排队是 InnoDB 自动做的，不用你写任何代码。**

### 5.2 读呢：隔离级别（A）

"读"比"写"复杂：A 事务改到一半还没提交时，B 事务该看到什么？四种答案 = 四种隔离级别：

| 级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
|---|---|---|---|---|
| READ UNCOMMITTED | 会 | 会 | 会 | 能看到别人没提交的改动。没人用 |
| READ COMMITTED (RC) | 不会 | **会** | 会 | 每次读都看"最新已提交"。Oracle/PG 默认 |
| **REPEATABLE READ (RR)** | 不会 | 不会 | 快照读不会* | **MySQL InnoDB 默认**。事务内多次读结果一致 |
| SERIALIZABLE | 不会 | 不会 | 不会 | 读也加锁，并发最差 |

> 术语：
> - **脏读**：读到别人**还没提交**的数（他可能回滚，你读了个假值）。
> - **不可重复读**：同一事务内两次读同一行，值变了（因为别人提交了修改）。
> - **幻读**：同一事务内两次**范围查询**（`WHERE status='ready'`），行数变了。
> - \* RR 下普通 SELECT 靠 MVCC 消灭幻读；但**当前读**仍会看到新行，靠间隙锁挡（D4·下 讲）。

确认你库的级别：

```sql
SELECT @@transaction_isolation;   -- MySQL 8 的变量名（5.7 叫 tx_isolation）
```

### 5.3 MVCC：快照读 vs 当前读（A）—— 本节最重要的二分

InnoDB 不靠"读的时候加锁"来实现隔离（那样并发太差），靠的是 **MVCC（多版本并发控制）**：每行数据带版本链（undo log 里存着旧版本），不同事务按自己的"快照"决定能看到哪个版本。

由此产生一个**必须分清**的二分：

| | 快照读 | 当前读 |
|---|---|---|
| 谁 | 普通 `SELECT` | `UPDATE` / `DELETE` / `INSERT` / `SELECT ... FOR UPDATE` |
| 读什么 | **自己快照里的版本**（可能是旧值） | **最新已提交的版本**（别人刚 commit 的也看得见） |
| 加锁吗 | 不加 | 加行锁 |
| 为什么 | 读不改数据，没必要排队 | 改数据必须基于最新值，不然会覆盖别人 |

**快照建立时机**（面试高频）：

- **RR**：事务内**第一次 SELECT** 时拍快照，此后整个事务都用它 → "可重复读"名字的由来；
- **RC**：**每条语句**都拍新快照 → 所以同事务内两次读可能不同。

时间轴（RR）：

```
时间 →
A: BEGIN ──── SELECT(拍快照,看到v1) ──── SELECT(仍看v1！) ──── COMMIT
B:              └─ UPDATE 那行 → COMMIT
                   (A 的第二次 SELECT 看不到 B 的修改，因为快照停在 v1)
```

**这个二分在 §六 会变成武器：丢失更新恰恰发生在"快照读拿旧值 + 当前读写回"的组合里。**

## §六 丢失更新：病根（A）—— 本篇核心

### 6.1 病灶长什么样

应用代码里最常见的计数写法：

```python
count = repo.get_doc_count(kb_id)        # 第 1 步：读（快照读，可能是旧值）
count += 1                                # 第 2 步：在 Python 里算（内存里）
repo.set_doc_count(kb_id, count)          # 第 3 步：写回（UPDATE，当前读）
```

三步之间有**空隙**。两个请求并发时：

```
时间 →
请求A: 读 doc_count=5 ──────────────── UPDATE SET doc_count=6 ── COMMIT
请求B:            读 doc_count=5 ── UPDATE SET doc_count=6 ────── COMMIT
                      ↑ 两边都读到 5，都写回 6
结果：上传了两份文档，doc_count = 6（应为 7）——丢了一次更新
```

B 的 UPDATE 确实会**等** A 提交（写写锁），但等完之后 B 写回的是它**早就算好的** 6——锁只保证"写不撞车"，保不了"算的时候用的是新值"。

### 6.2 为什么 RR / RC 都防不住

丢失更新**不是隔离级别问题**。RR/RC 解决的是"你读的时候看不看得见别人"，而丢失更新是**应用把读和写拆成了两步**——两步之间数据库管不着。**任何隔离级别下，读-改-写分离都会丢。** 这就是为什么不能说"我们用了 MySQL 默认的 RR 所以没问题"。

### 6.3 项目里的落点

`kb_repo.py:80`：

```python
def incr_doc_count(self, kb_id: UUID, delta: int) -> None:
    if row := store.kbs.get(kb_id):        # 内存版：读
        row["doc_count"] = max(0, row["doc_count"] + delta)   # 算
        row["updated_at"] = store.now()
```

`store.kbs` 是进程内存 dict——单进程内"读-改-写"至少没有数据库层面的并发问题，但**换到 SQLAlchemy 版（D4·下 动手）如果写成"SELECT 读出值 → UPDATE 写回"，§6.1 的丢失更新就原样搬进数据库**。

## §七 三种修复（A）

### 修复 ①：原子自增 —— 首选（A）

把三步压成**一条 SQL**，让"读最新值 + 加 1 + 写回"在数据库内部一口气完成：

```sql
UPDATE knowledge_bases
   SET doc_count = doc_count + 1, updated_at = NOW()
 WHERE id = 'kb000001000000000000000000000000';
```

为什么它不丢：

- `doc_count + 1` 里的 `doc_count` 是**当前读**（最新已提交值），不是快照；
- UPDATE 自带行锁，两个请求天然排队，排队时**重新读最新值**再算；
- 一条语句 = 一个原子操作，没有空隙。

Python 侧（SQLAlchemy）：

```python
def incr_doc_count(self, kb_id: UUID, delta: int) -> None:
    self.session.execute(
        update(KnowledgeBase)
        .where(KnowledgeBase.id == kb_id)
        .values(doc_count = KnowledgeBase.doc_count + delta,
                updated_at = func.now())
    )
```

**关键在 `KnowledgeBase.doc_count + delta` 这个表达式**——它生成 `doc_count = doc_count + :delta`，加法在数据库里做。如果你写成先 `session.get()` 读出来、`.doc_count + 1` 再赋值，就退回病根版。

代价：几乎没有。**90% 的计数场景用这一个方案就够。**

### 修复 ②：`SELECT ... FOR UPDATE` —— 需要"读出值做复杂逻辑"时（A）

```sql
BEGIN;
SELECT doc_count FROM knowledge_bases WHERE id='...' FOR UPDATE;  -- 当前读 + 行锁
-- ... 应用里基于这个值做复杂计算 ...
UPDATE knowledge_bases SET doc_count = ? WHERE id='...';
COMMIT;
```

FOR UPDATE 让这个行**从读到提交一直被你锁住**，别人进不来，自然不会丢。代价：**锁持有时间 = 你的事务长度**，逻辑越重排队越久。适合"读出来要做无法用 SQL 表达的复杂决策"的场景。

### 修复 ③：乐观锁版本号 —— 冲突很少、又不想长持锁时（B）

```sql
-- 表加一列 version INT NOT NULL DEFAULT 0
SELECT doc_count, version FROM knowledge_bases WHERE id='...';   -- 记下 version=7
-- 基于读到的值做计算，写回时带上"版本没变过"的条件：
UPDATE knowledge_bases
   SET doc_count = ?, version = version + 1
 WHERE id = '...' AND version = 7;      -- 影响行数 = 0 说明有人抢先改了 → 重试整个流程
```

不加锁、靠"提交时校验"发现问题。代价：**失败要重试**（重试逻辑自己写）。适合读多写少、真冲突少的场景（比如编辑保存）。个人项目里知道有这条路、能说清权衡即可，不必实做。

### 三者怎么选（一句话）

**能用一条原子 SQL 表达 → 修复 ①；逻辑复杂必须先读 → 修复 ②；读多写少怕锁 → 修复 ③。你的 `incr_doc_count` 属于第一种。**

## §八 易错点表（A）

| # | 错误认知 | 实际 | 证据/后果 |
|---|---|---|---|
| 1 | "RR 隔离级别下不会丢更新" | 丢失更新与隔离级别无关，病根是读-改-写分离 | §6.2；两个会话在 RR 下照样复现 |
| 2 | "UPDATE 等了锁，所以值是对的" | 等锁只保证不撞车；写回的值可能是**锁前就算好的旧值** | §6.1 时间轴：B 算的 6 是锁前读的 |
| 3 | "我把读出来的对象 `.doc_count + 1` 再赋值，很自然" | 这就是 Python 版读-改-写，等于病根 | §7 修复①：要用 `doc_count = doc_count + :delta` 表达式 |
| 4 | "事务里 SELECT 看到的就是最新值" | 普通 SELECT 是快照读，RR 下可能是很旧的值 | §5.3；想读最新用 `FOR UPDATE` |
| 5 | "repo 里 commit 一下没什么" | 把事务边界切碎，前面所有语句失去整体保护 | §4.3：边界归请求层 |
| 6 | "autocommit 开着，多句代码自然是一个事务" | autocommit 每句一提交；多句保护必须显式边界 | §4.1 |
| 7 | "ROLLBACK 能撤销任何事" | COMMIT 之后就撤不了；DDL（如 `TRUNCATE`）多数也隐式提交 | §二 第 3 步观察 |
| 8 | "FOR UPDATE 加了就万事大吉" | 锁持有时间=事务长度；锁太重反而拖垮并发 | §7 修复② 的代价 |

```sql
SET SESSION transaction_isolation = 'READ-COMMITTED';

-- 当前读的两个入口
SELECT ... FOR UPDATE;                -- 读最新 + 行锁
UPDATE ... SET doc_count = doc_count + 1;   -- 表达式自增 = 原子

-- 看锁等待（谁卡谁）
SELECT * FROM performance_schema.data_lock_waits;   -- MySQL 8
```

## §十 面试问法（A）

**30 秒版**（背熟）：

> 事务保证一组 SQL 要么全提交要么全回滚，InnoDB 靠 undo log 回滚、redo log 保证持久。隔离性由锁和 MVCC 共同实现：普通 SELECT 是快照读，走 MVCC 不加锁；UPDATE 这类当前读写最新已提交值并加行锁。MySQL 默认 RR，靠"第一次 SELECT 拍快照"实现可重复读。另外我知道隔离级别防不了丢失更新——读-改-写分离在应用层，得用原子 UPDATE、FOR UPDATE 或乐观锁修。

**追问链**（面试官往下挖的顺序）：

1. **RR 和 RC 的区别？** → 快照建立时机：RR 第一次 SELECT 拍一次用到底，RC 每条语句新拍。
2. **MVCC 怎么实现的？** → 版本链 + ReadView（哪行该看见哪个版本由 ReadView 判断），undo log 存旧版本。答到这层够了。
3. **RR 下还有幻读吗？** → 快照读没有（快照冻结）；当前读有新行会出现，靠 next-key lock（间隙锁+行锁）挡 → 引到 D4·下。
4. **项目里哪里用到这些？** → `incr_doc_count`：内存版读-改-写，切到 DB 版必须写成 `doc_count = doc_count + :delta` 原子自增，否则并发丢计数。
5. **为什么不用 SELECT FOR UPDATE？** → 计数自增能一条 SQL 表达，没必要锁整段事务；FOR UPDATE 留给"必须先读再做复杂决策"的场景。

## §十一 动手任务（A）—— 两个终端，复现 + 修复

**交付物清单**（做完填 `D4-实测记录.md`，模板 §十一 给了骨架）：

| # | 交付物 | 验收标准 |
|---|---|---|
| 1 | 丢失更新复现：两个会话各自"读 5 → 写回 6"，最终值 | 最终 doc_count = **6**（应为 7），两边都没报错 |
| 2 | 修复①原子自增：同样两个会话，各跑一条 `doc_count = doc_count + 1` | 最终 = **2**（从 0 起）或 +2 |
| 3 | 修复②FOR UPDATE：会话 B 的 SELECT 阻塞，A commit 后 B 才返回 | 能贴出 B 卡住→A 提交→B 立即返回的时序 |
| 4 | 一句话病根 | 写进记录："丢的是**算好的旧值**，不是锁没生效" |

**准备**：开**两个** PyCharm 终端，各起一个 mysql 客户端（§九 的命令各跑一次），标 A / B。确认初始值：

```sql
SELECT id, doc_count FROM knowledge_bases WHERE id='kb000001000000000000000000000000';
```

### 任务 1：复现（先做，10 分钟）

按此顺序，**严格交替**（这就是"并发"的手工模拟）：

```sql
-- 会话A                          -- 会话B
BEGIN;
SELECT doc_count ...;             BEGIN;
                                  SELECT doc_count ...;
UPDATE ... SET doc_count=1 ...;
COMMIT;
                                  UPDATE ... SET doc_count=1 ...;
                                  COMMIT;
```

最后任一会话查 `doc_count`。**两份文档、结果是 1**——修复前后差的那一次，就是丢失更新。

> **容易绕进去的两个疑问**（实测有人在这打转 20 分钟）：
>
> ① "A 都 COMMIT 了，B 才 UPDATE，这算哪门子并发？"——丢不丢**不看 UPDATE 何时执行，看写的值是何时算出来的**。B 的 1 在它快照读（读到 0）那一刻就定死了，`SET doc_count = 1` 只是搬运这个算好的旧值，搬运得再晚运的也是旧账。真实系统里两个 HTTP 请求哪怕完全错开，只要代码是"读出来算好再写回"，照样丢——串行时序反而是更真实的演示。
>
> ② "A 写 1、B 写 1，最终 1，不挺正常的吗？"——业务语义是**两次上传**，计数该是 2。丢的是 A 那次 +1：数值上 1 覆盖 1 看不出痕迹，这就是丢失更新没报错的原因。想肉眼看到覆盖：把 B 那句改成写 `100`，最终 100，A 的 1 无影无踪。

> 提示阶梯（卡 10 分钟再看）：
> ① 如果 B 的 UPDATE 报锁等待超时：A 没 COMMIT。UPDATE 是当前读+行锁，B 在等 A。等到了再继续，现象不变。
> ② 如果两边查出来都是 2：你把第二句写成 `doc_count = doc_count + 1` 了——那是修复版，回去用 `SET doc_count=1` 写死值。

### 任务 2：修复①（10 分钟）

先 `UPDATE ... SET doc_count=0` 归零，然后两会话**各执行一次**：

```sql
UPDATE knowledge_bases SET doc_count = doc_count + 1, updated_at = NOW()
 WHERE id='kb000001000000000000000000000000';
```

不需要 BEGIN/COMMIT 包裹（单语句自动就是一个事务）。最终查 → **2**。两条并发 SQL，零丢失。

### 任务 3：修复②（10 分钟）

```sql
-- 会话A                                    -- 会话B
BEGIN;
SELECT doc_count FROM knowledge_bases
 WHERE id='kb0000...' FOR UPDATE;           -- B: 同一句，立刻敲 → 卡住
UPDATE ... SET doc_count = doc_count + 1;
COMMIT;                                     -- A 提交瞬间，B 的 SELECT 返回
                                            UPDATE ... SET doc_count = doc_count + 1;
                                            COMMIT;
```

观察 B 的 SELECT **卡住**（MySQL 默认 50 秒超时，别拖过 50s）以及 A 提交后它立即返回。**B 读到的是 A 提交后的新值**——FOR UPDATE 是当前读。

### 任务 4：写病根一句话

填进记录：**"B 的 UPDATE 确实排队等了锁，但它写回的 1 是排队之前就算好的。锁管写不撞车，不管你算得对不对。"**

## §十二 闭卷自测（A）—— 先看题目，答案折叠

**题目清单**（合卷口述或写下来，再展开对答案）：

1. BEGIN 后执行了 3 句 SQL，第 3 句报错。前 2 句的结果现在处于什么状态？怎么处置？
2. `@@autocommit = 1` 时，一条单独的 UPDATE 有原子性吗？两句 UPDATE 呢？
3. RR 和 RC 的核心区别用"快照建立时机"一句话说清。
4. 普通 SELECT 和 `UPDATE` 各是什么读？分别读哪个版本的值？
5. 丢失更新的病根是哪三个字到五个字？它和隔离级别有关系吗？
6. `SET doc_count = doc_count + 1` 为什么不丢？它读的是什么版本的值？
7. `SELECT ... FOR UPDATE` 卡住的是哪个会话的哪条语句？卡多久由什么决定？

<details>
<summary>答案（先自己答完再展开）</summary>

1. 前 2 句的修改**仍在未提交事务里**（没生效也没丢），处置 = ROLLBACK 整体撤销（或修好第 3 句后 COMMIT）。
2. 一条 UPDATE 有（单语句即一个事务）；两句没有（autocommit 各自提交，中间可插入失败），必须 BEGIN 包裹。
3. RR 第一次 SELECT 拍快照、整个事务用它；RC 每条语句重新拍。
4. 普通 SELECT 是**快照读**（读自己快照里的版本，可能是旧值）；UPDATE 是**当前读**（读最新已提交值并加行锁）。
5. 病根：**读-改-写分离**。与隔离级别无关——RR/RC 都防不住。
6. 因为 `doc_count + 1` 的 `doc_count` 是**当前读**（最新已提交值），且 UPDATE 自带行锁使并发排队，一条语句无空隙。
7. 卡住的是**后到**的那个会话的 `FOR UPDATE` 那条 SELECT；等到先到的会话 COMMIT/ROLLBACK 为止，超过 `innodb_lock_wait_timeout`（默认 50s）报错。

</details>
