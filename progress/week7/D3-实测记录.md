## 1. 五组 EXPLAIN 实验（探针表，5 万行）

**跑法**：`probe_index.sql` / `probe_index2.sql` / `probe_index3.sql` 各建一张 5 万行探针表、跑完自删。原始输出存在 `probes/out_index1.txt` ~ `out_index3.txt`（表一删，EXPLAIN 还在文件里）。

探针表和真表不一样，先记住这张对照，否则数字对不上会以为是错的：

| | `probe_docs`（探针表） | `documents`（真表） |
|---|---|---|
| 行数 | 50000 | 5000 |
| `kb_id` | `CHAR(36)`，50 个值，每值 **1000 行** | `CHAR(32)`，200 个值，每值 25 行 |
| 主键 | `BIGINT AUTO_INCREMENT` | `CHAR(32)` UUID |
| 数据页约 | 300 页 | 45 页 |

### 组 A：无索引 vs 单列索引

`SELECT * FROM probe_docs WHERE kb_id = 'kb-007'`

| | type | key | key_len | rows | filtered | Extra |
|---|---|---|---|---|---|---|
| A1 无索引 | `ALL` | `NULL` | NULL | **49698** | 10.00 | `Using where` |
| A2 有 `idx_kb_id` | `ref` | `idx_kb_id` | **144** | **1000** | 100.00 | `Using index condition` |

**结论**：`rows` 从 49698 降到 1000，降 **49.7 倍**。降得动，是因为 `kb_id` 有 50 个值、每个值只占 2%——**这是有区分度的列**，和后面 `status` 只有 3 个值形成对照。

> 我原来把 A1 的 rows 记成 50000，实际是 **49698**。差的那 302 行不是笔误：`rows` 是**估算值**，统计信息按页采样推算，不会刚好等于 `COUNT(*)`。**记 `rows` 时永远不要当它是精确行数。**

两个数字要会算：

- **`key_len=144`** = `CHAR(36)` × 4 字节/字符（utf8mb4 = 144）。定长字符不加长度前缀；列是 `NOT NULL`，也不加空标志位 1 字节。
- **`filtered=10.00`（A1）是默认值，不是统计结果。** 没索引的列优化器统一按 10% 猜。A2 变成 100.00，是等值条件在索引上能精确落到行。

你那句"索引没有全覆盖，还是需要 1000 次回表"判断是对的——`SELECT *` 要 `owner_id/title/status/created_at`，而这些都在聚簇索引里，`idx_kb_id` 只有 `kb_id + id`，所以 1000 行全要回表。**这正是组 C 要量化的东西。**

### 组 B：复合索引与最左前缀

索引：`idx_kb_id(kb_id)` 和 `idx_kb_created(kb_id, created_at)` 并存。

| | 查询 | type | key | key_len | rows | Extra |
|---|---|---|---|---|---|---|
| B1 | `WHERE kb_id=? ORDER BY created_at DESC` | `ref` | **`idx_kb_created`** | 144 | 1000 | `Using where; Backward index scan` |
| B2 | `WHERE kb_id=?`（无 ORDER BY） | `ref` | **`idx_kb_id`** | 144 | 1000 | `Using index condition` |
| B3 | `WHERE created_at > ?`（跳首列） | `ALL` | `NULL` | NULL | 49698 | `Using where`（filtered 33.33） |
| B4 | 同上，另建 `idx_created(created_at)` | `range` | `idx_created` | **5** | **5360** | `Using index condition` |

**结论：这四行讲的是三件事，恰好是面试追问的三层。**

1. **B1 选了复合索引，没选更窄的单列索引**——因为 `ORDER BY created_at DESC` 能靠复合索引免费满足，`filesort` 直接消失。**索引的收益不只是"少扫行"，还包括"直接给出顺序"。**
2. **B2 又退回单列索引**——两个索引都能定位 1000 行、都不需要排序时，选更窄的（144 字节 vs 两列）。**收益相同时选成本低的，优化器不认"复合索引更高级"。**
3. **B3 → B4**：跳掉最左列 `kb_id`，复合索引彻底用不上（`possible_keys` 是 `NULL`，连候选都不算）；补一个 `created_at` 单列索引，立刻 `range`、扫 5360 行。**最左前缀的机制：索引按 `(kb_id, created_at)` 排序，`kb_id` 不同的行混排在一起，`created_at` 全局无序，找不出起点。**

`key_len=5` 是 B4 的：`DATETIME` 在 MySQL 8 占 5 字节（`NOT NULL` 不加空标志位）。和真表上 `(kb_id, created_at)` 做范围查询时的 `key_len=133 = 128 + 5` 是同一个算法。

#### B5：把列顺序反过来会怎样（真表对照，补昨天欠的那条）

昨天记录里挂着一条"`(created_at, kb_id)` 没真的建出来对比"。今天补上了：在 `documents` 建 `ix_tmp_rev (created_at, kb_id)`，`IGNORE` 掉两个正向复合索引，跑同一条查询：

```sql
SELECT ... FROM documents IGNORE INDEX (ix_documents_kb_created, ix_documents_kb_status_created)
WHERE kb_id = ? ORDER BY created_at DESC LIMIT 20;
```

| 场景 | type | possible_keys | **实际扫描行数** | 实际耗时 |
|---|---|---|---|---|
| 反向索引 + 最新创建的 kb（`kb000001`） | `index` | **`NULL`** | **20** | 0.09 ms |
| 反向索引 + 最旧创建的 kb（`kb000200`） | `index` | **`NULL`** | **4995** | **11.4 ms** |
| 正向索引 `(kb_id, created_at)` + 同一个旧 kb | `ref` | `ix_documents_kb_created` | 20 | 0.11 ms |

三个发现，一个比一个重要：

1. **`possible_keys=NULL` 说明它没被用来"定位"，但 `type=index` 说明它仍在被使用**——顺着索引倒着扫，边扫边过滤 `kb_id`。**"用不上索引定位"和"用索引提供顺序"是两件事**；最左前缀阻止的是前者，不是后者。所以"跳首列索引就完全没用"这句话也不严谨：它还能当排序通道，只是可能很贵。
2. **同索引、同 SQL，只换一个 `kb_id` 取值，慢了 126 倍**（11.4 ms vs 0.09 ms）。因为倒序扫到"凑够 20 行"为止，命中密度决定要扫多远：`created_at` 均匀递增，最新那个 kb 的 25 行就在索引尾部，最旧的在头部，要扫完 4995 行。**这就是 `(created_at, kb_id)` 替代不了 `(kb_id, created_at)` 的量化证据——不建反向索引不是"讲究"，是 126 倍。**
3. **三行的 `EXPLAIN.rows` 全是 20，实际扫描行数是 20 / 4995 / 20。** `rows` 是"估算**返回**多少行"，不是"要**扫**多少行"。**要看见真实扫描量只能上 `EXPLAIN ANALYZE`**。这条比"`rows` 不反映排序代价"更隐蔽，因为这里 SQL 形态完全一样、只有参数不同，计划看起来也一模一样。

### 组 C：覆盖索引 vs 回表

同一张表、同一个 `WHERE kb_id='kb-007'`（1000 行），只改 SELECT 哪些列：

| | 查询 | key | Extra | 含义 |
|---|---|---|---|---|
| C1 | `SELECT kb_id, created_at` | `idx_kb_created` | **`Using where; Using index`** | 覆盖：要的列全在索引里，**不碰聚簇索引** |
| C2 | `SELECT kb_id, created_at, title` | **`idx_kb_id`** | `Using index condition` | 回表：`title` 不在索引里，按主键回聚簇索引取 |

**结论：省掉的是「回表」——那 1000 次对聚簇索引的随机查找。**

C2 有个容易被忽略的细节：它**没有选复合索引**，退回单列 `idx_kb_id`。理由和 B2 一样——既然一定要回表（两个索引都不含 `title`），排序优势也用不上，就选窄的。**"选哪个索引"是每条查询单独算成本，不是看索引名。**

`Using index` 和 `Using index condition` 只差两个词，含义完全不同：前者是**根本不用回表**，后者是**在索引上先过滤、该回表还得回**。

### 组 D：六种"失效"写法

> **判据两条，缺一不可：**
> ① `possible_keys` 有值但 `key=NULL` → **优化器放弃**（能走但觉得不划算）；`possible_keys` 是 `NULL` → **写法本身用不上**（真失效）。
> ② 交叉验证：**把条件收紧到只命中几行，走了索引 → 是放弃；还不走 → 是真失效。**

| 写法 | type | key | possible_keys | 判定 | 依据 |
|---|---|---|---|---|---|
| `LEFT(title,3) = '文档标'` | `ALL` | `NULL` | **`NULL`** | **真失效** | 对列做运算，索引里存的是原值，定位不了 |
| `LIKE '%标题-1%'`（前置通配符） | `ALL` | `NULL` | **`NULL`** | **真失效** | 前缀未知 = 起点未知 |
| `LIKE '文档标题-1%'`（后缀通配符） | `ALL` | `NULL` | **`idx_title`** | **优化器放弃** | 命中 42.95%；同写法收紧成 `'文档标题-499%'` → `range`/111 行 |
| `kb_id = 7`（`CHAR` 列给数字） | `ALL` | `NULL` | `idx_kb_id`, `idx_kb_created` | **真失效** | 字符列与数字比较会隐式转换，等于给列套了函数 |
| `status != 'ready'` | `ALL` | `NULL` | `NULL` | **本组无法判定** | 第一组表上 `status` 根本没索引，不能用它证明 `!=` 失效 |
| `kb_id='kb-007' OR status='ready'` | `ALL` | `NULL` | `idx_kb_id`, `idx_kb_created` | **真失效（本场景）** | `status` 无索引，OR 的一半走不了 → 整体退化 |

**第二组补的对照（`probe_index2.sql`，同样 5 万行）**：

| | 写法 | type | key | key_len | rows | 判定 |
|---|---|---|---|---|---|---|
| 1a | `title LIKE '文档标题-499%'`（约 111 行） | `range` | `idx2_title` | 802 | **111** | 走了 |
| 1b | `title LIKE '文档标题-1%'`（约 2 万行） | `ALL` | `NULL` | — | 49853 | 放弃（filtered 42.95） |
| 2a | `status != 'ready'`（status **有**索引，命中 50%） | `ALL` | `NULL` | — | 49853 | 放弃 |
| 2b | `status = 'ready'`（等值，但命中 33%） | `ref` | `idx2_status` | 82 | **24926** | **走了** |

**这四行合起来推翻了两句流行话**：「`!=` 一定不走索引」「`LIKE '%x'` 一定不走索引」，都不对。

同样的 `!=`，换成 `status = 'failed'`（2% 命中）就会走；同样是 `LIKE` 前缀，选择性从 43% 降到 0.2%，结果从"放弃"变成"`range`"。**失效是成本的属性，不是运算符的属性**——教材 §七 说的就是这句话。

`2b` 还藏一个反直觉的点：**33% 命中（24926 行）照样走了索引**。5 万行的表约 300 页，全在 Buffer Pool 里，回表 2.5 万次等于内存访问。**"命中比例高就走全表"这条经验没有绝对值**，它取决于回表一次有多贵——这就是 §4 那个 100 万行反转实验的另一端。

### 组 E：`EXPLAIN ANALYZE` 的真实耗时

`probe_index3.sql`，`idx3_kb_status(kb_id, status)`，`WHERE kb_id='kb-007'`（1000 行）：

| 场景 | 估算 rows | 实际 rows | 实际耗时 | cost | 相对覆盖索引 |
|---|---|---|---|---|---|
| 4a 覆盖（只取 `kb_id, status`） | 1000 | 1000 | **0.42 ms** | 129 | 1× |
| 4b 回表（多取 `title`） | 1000 | 1000 | **1.86 ms** | 350 | **4.4×** |
| 4c 全表扫（`LIKE '%标题-499%'`） | 5535 | **111** | **17.6 ms** | 5070 | **42×** |

**三条结论：**

1. **回表贵 4.4 倍，省下它的就是覆盖索引。** 4a 和 4b 返回的行数完全一样（1000 行），差别只在"要不要再去聚簇索引把这 1000 行的 `title` 捞出来"。**耗时不取决于扫了多少行，取决于碰了多少个不同的页。**
2. **4c 的估算错得最狠：估 5535 行，实际只返回 111 行**（内层扫了全部 50000 行）。前置通配符让优化器没有依据估命中率，只能拍一个数。**这就是"`rows` 不可信"的极端案例——差 50 倍，方向还是"以为会命中很多"。**
3. **这一组的 `cost` 排序是对的**（129 < 350 < 5070 vs 0.42 < 1.86 < 17.6）。所以不能说"`cost` 一律不准"——它不准的场景是**回表代价被低估**（§3 那个 100 万行慢 4.8 倍的例子）。判断标准是"这个成本模型有没有把主要成本算进去"。

## 2. 本项目三个索引的 DDL

从教材 §10.2 的五条真实查询里选三条最重要的。每条都要写：**列顺序 + 每列放这个位置的理由**。

```sql
-- 索引 1：知识库列表页「我的知识库，按创建时间倒序」
-- 查询：SELECT * FROM knowledge_bases WHERE owner_id = ? ORDER BY created_at DESC LIMIT 20;
-- 列顺序理由：
--   owner_id 是等值条件，放第 1 位负责定位（区分度接近 1，一个用户一个值）
--   created_at 放第 2 位：给定 owner_id 后，组内已按 created_at 有序，
--   倒序读前 20 行就停，filesort 被索引免费消掉
--   写反成 (created_at, owner_id) 会退化：owner_id 成为跳列，等值定位用不上
CREATE INDEX ix_kb_owner_created ON knowledge_bases (owner_id, created_at);

-- 索引 2：文档列表页「某知识库下的文档，按时间倒序分页」
-- 查询：SELECT * FROM documents WHERE kb_id = ? ORDER BY created_at DESC LIMIT 20 OFFSET 0;
-- 列顺序理由：同索引 1——等值在前、排序列在后
-- 实测（§3 组 1）：加索引后 Extra 从「Using index condition; Using filesort」
--   变成「Using where; Backward index scan」，filesort 消失
CREATE INDEX ix_documents_kb_created ON documents (kb_id, created_at);

-- 索引 3：按状态过滤「某知识库里待处理的文档」
-- 查询：SELECT * FROM documents WHERE kb_id = ? AND status = 'pending' ORDER BY created_at LIMIT 50;
-- 列顺序理由：两个等值 + 一个排序。status 必须紧邻 kb_id，不能挪到 created_at 后面
--   正面实测：key_len=210 = 128(kb_id) + 82(status)，ref=const,const（两列都参与定位），无 filesort
--   反面实测：只给 kb_id 时，优化器绕开这个索引、回去用单列 ix_documents_kb_id，
--   filesort 重新出现——因为 status 是未知中间列，created_at 在组内并不有序
CREATE INDEX ix_documents_kb_status_created ON documents (kb_id, status, created_at);
```

**列顺序的三条硬规则**（从上面三条反推出来的）：

1. **等值条件在前，范围/排序列在后**——一旦某列是范围或用于排序，它后面的列就不能再用于定位
2. **等值列之间，区分度高的在前**——不是硬约束，但能更早缩小候选范围
3. **中间不能夹未知列**——`(kb_id, status, created_at)` 服务不了 `WHERE kb_id=? ORDER BY created_at`，因为跳到 `created_at` 时 `status` 未知，顺序就断了

**最终索引清单，以及为什么删掉一个：**

```
PRIMARY                        (id)                        聚簇索引
ix_kb_owner_created            (owner_id, created_at)      索引 1
ix_documents_kb_created        (kb_id, created_at)         索引 2
ix_documents_kb_status_created (kb_id, status, created_at)  索引 3
```

`ix_documents_kb_id (kb_id)` 删掉：任何 `WHERE kb_id=?` 都能被 `(kb_id, created_at)` 的最左前缀服务，留着只占空间、拖慢写入。但 `(kb_id, status, created_at)` **不能删**——它服务查询 3，两列索引替代不了它。**索引不是越多越好，能覆盖就别重复建。**

## 3. 真表加索引前后的 EXPLAIN 对比（3 组）

**在 `documents` 真表上做，不是探针表。** 三组的"加索引前"用 `IGNORE INDEX (新索引名)` 还原（索引已建，只能屏蔽，效果等价）。

| 组 | 查询                                                                              | 加索引前（type / rows / Extra）                                                              | 加索引后（type / rows / Extra）                                                              | 变化                                            |
| - | ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1 | `WHERE kb_id=? ORDER BY created_at DESC LIMIT 20`<br />索引：`(kb_id, created_at)` | `ref` / 25 / **`Using index condition; Using filesort`**<br />key=`ix_documents_kb_id` | `ref` / 25 / **`Using where; Backward index scan`**<br />key=`ix_documents_kb_created` | **rows 没变，`filesort` 消失**。索引本身有序，反向扫到第 20 行就停 |
| 2 | `WHERE status='ready'`（90%）<br />索引：`(status)`                                  | `ALL` / 4820 / `Using where`                                                           | `ref` / **2410** / `NULL`<br />key=`ix_documents_status`, key_len=82                   | rows 降 **2 倍**。降得少，因为命中的是 90% 的行              |
| 3 | `WHERE status='failed'`（2%）<br />索引：`(status)`                                  | `ALL` / 4820 / `Using where`                                                           | `ref` / **100** / `NULL`<br />key=`ix_documents_status`, key_len=82                    | rows 降 **48 倍** ✅ 满足"至少一组降 10 倍以上"            |

**第 1 组为什么 `rows` 不变**：`rows=25` 指的是"这个 kb 下有 25 行"，加索引不会让行数变少。变的是**取这 25 行的方式**——原来要全取出来再排（`filesort`），现在顺着索引直接倒序读 20 行。**`rows` 这一列不反映排序代价**，这是 EXPLAIN 最容易误读的地方。

**第 2、3 组的关键对照**：同一个索引、同一条 SQL 形状，只差一个取值，`rows` 从 2410 变成 100。**"低区分度"说的是索引整体只有 3 个值，但"这次查询的选择性"取决于你查哪个值。**

**第 2 组还有个坑要记**：在 5000 行的表上，`status='ready'` 走索引其实是**划算的**（45 个数据页全在 Buffer Pool，回表等于内存访问）。同样的走法放大到 100 万行就变成灾难——`probe_status_volume.sql` 实测：走索引 21.9s，强制全表扫 4.5s，**优化器选的那条慢 4.8 倍**。详见教材 §8.2.1。

## 4. 为什么 `status` 不单独建索引，但在 `(kb_id, status)` 里有用

一句话说清（不要背"低区分度不能建索引"，要说清机制）：

> 索引里只存了 `status + id`，不存 `title`。所以定位到 2410 行之后，还得**按主键回表把这 2410 行整行取出来**，而它们的主键散在整棵 B+ 树里，等于 2410 次随机访问。全表扫则是 45 个页顺序读完。
>
> 于是走索引省下的是"少读 33 个页"，付出的是"多 2410 次随机回表"。谁赢取决于**表能不能全部装进 Buffer Pool**：
>
> - 5000 行 → 45 页全在内存，回表等于内存访问 → 索引赢
> - 100 万行 → 超出 Buffer Pool，回表变真磁盘 IO → 索引输（21.9s vs 4.5s，实测见 §3）

**验证**：在 `documents` 上单独建一个 `(status)` 索引，`EXPLAIN` 看到什么？（索引已建，`ix_documents_status`，实测结果如下）

| 加 `(status)` 单列索引后的 EXPLAIN             | type  | key                   | key_len | rows     | Extra  |
| --------------------------------------- | ----- | --------------------- | ------- | -------- | ------ |
| `WHERE status='ready'`（4500/5000 = 90%） | `ref` | `ix_documents_status` | 82      | **2410** | `NULL` |
| `WHERE status='failed'`（100/5000 = 2%）  | `ref` | `ix_documents_status` | 82      | **100**  | `NULL` |

> ⚠️ **这里和教材写了不一样的地方**：教材 §8.2 说"低区分度会被优化器放弃"，但 5000 行时 `ready` **没有放弃**，照样走了索引。原因和 100 万行的反转实测都补进教材 §8.2.1 了。**记录里要写"在这个表规模下它没放弃"，不要写"它放弃了"。**

`key_len=82` 的算法：`status` 是 `VARCHAR(20)`，utf8mb4 每字符 4 字节 → `20 × 4 = 80`，再加 2 字节长度前缀 = **82**。（对比 `kb_id` 的 `CHAR(32)`：`32 × 4 = 128`，`CHAR` 是定长，不加长度前缀。）

## 5. 今天的三个新发现 / 卡住的地方

**① `key_len` 只统计"用于定位的列"，不统计"用于排序的列"。**

我原本预测 `(kb_id, created_at)` 的 `key_len` 是 133（128 + 5），实际是 **128**。因为 `created_at` 在这条查询里只参与 `ORDER BY`，不参与 `WHERE`。补测验证：一旦让它进 `WHERE`（`AND created_at >= '2026-01-01'`），`key_len` 立刻变成 **133**。

→ 反过来，`key_len` 可以当尺子用：**`key_len` 告诉你这条 SQL 实际用到了索引的前几列**。`ref=const,const` + `key_len=210` 就说明前两列都用上了。

**② 优化器会选错路，而且错得很贵。**

100 万行的 `t_big` 表上，`status='ready'`（90%）优化器选了走索引：它估算 `cost=89944`，全表扫 `cost=119823`，以为索引便宜。实际走索引 **21.9s**，强制全表扫 **4.5s**，**慢了 4.8 倍**。

→ 原因是成本模型低估了 90 万次随机回表。这正是"`EXPLAIN` 说走了索引 ≠ 走对了"的实例：看到 `type=ref` 还要接着问 `rows` 占全表多少、要不要回表。工程处置是 `IGNORE INDEX (...)` 强制它别用。

**③ `rows` 完全不反映排序代价。**

`WHERE kb_id=? ORDER BY created_at DESC LIMIT 20`：加索引前后 `rows` 都是 25，但 `Extra` 从 `Using filesort` 变成 `Backward index scan`。**如果只看 `rows`，会误判"索引没用"**。

→ 判据要三样一起看：`type`（怎么访问）、`rows`（访问多少）、`Extra`（有没有排序/回表/覆盖）。单看任何一个都会误判。

**④ `rows` 是"估算返回多少行"，不是"要扫多少行"。**

反向索引 + `LIMIT 20` 的两条查询（§1·B5），`EXPLAIN` 的 `rows` **都是 20**，但 `EXPLAIN ANALYZE` 显示实际扫了 **20 行 vs 4995 行**，耗时 0.09 ms vs **11.4 ms**，差 126 倍。同样的 SQL、同样的 `type=key=rows`，只有参数不同。

→ 判据补一条：**带 `LIMIT` 或带过滤条件的查询，`rows` 最不可信**，要看 `EXPLAIN ANALYZE` 里扫描节点的 `rows`（那才是真实扫描量）。

**收尾**：昨天欠的 `(created_at, kb_id)` 反向索引对照已在 §1·B5 补完，不再挂着。今天剩下的欠账只有一项——`(kb_id, status, created_at)` 这个三列索引还没在**探针表**上复现（真表上验过），但机制已由 B1–B5 覆盖，算低优先。
