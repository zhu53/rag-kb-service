## 2. 交付物 2：首条迁移（建三张表）

`alembic revision --autogenerate -m "create base tables"` → `7433ed806f3a`，`down_revision = None`。

生成内容（与模型逐项核对）：

| 对象 | 内容 |
|---|---|
| `op.create_table` | `knowledge_bases`、`documents`、`chunks`（3 个，顺序按 FK 依赖排） |
| `op.create_index` | `ix_knowledge_bases_owner_id`、`ix_documents_kb_id`、`ix_chunks_doc_id`（3 个，来自模型里的 `index=True`） |
| FK | `documents.kb_id → knowledge_bases.id`、`chunks.doc_id → documents.id`，均 `ondelete='CASCADE'` |
| `downgrade()` | 成对且顺序相反：先 `drop_index` 再 `drop_table`，表按 `chunks → documents → knowledge_bases` 倒序 |

`upgrade head` 后实测：

```
表: ['alembic_version', 'chunks', 'documents', 'knowledge_bases']
版本: (('7433ed806f3a',),)
```

列类型落地（预测「char(32) / datetime」两个全中）：

```
id         -> char(32)      ← 模型写的是 sa.Uuid()，MySQL 落成 CHAR(32)
kb_id      -> char(32)
title      -> varchar(200)
status     -> varchar(20)
chunk_count-> int
created_at -> datetime      ← DateTime(timezone=True) 在 MySQL 上不存时区
updated_at -> datetime
```

引擎/排序：`InnoDB` + `utf8mb4_0900_ai_ci`（继承建库设置）。外键 `DELETE_RULE = CASCADE` 两个都在。

**`alembic_version` 不在这条迁移里**——它由 Alembic 自己在 `upgrade` 时创建和维护。原因：迁移必须先读版本表才知道该跑哪几条，让迁移建它就是鸡生蛋。

## 3. 交付物 3：加索引迁移 + 回滚

模型改动：`Document.status` 加 `index=True`。

`revision --autogenerate` → `b0846e5e87de`，`down_revision = '7433ed806f3a'`。全文只有两行有效操作：

```python
def upgrade() -> None:
    op.create_index(op.f('ix_documents_status'), 'documents', ['status'], unique=False)

def downgrade() -> None:
    op.drop_index(op.f('ix_documents_status'), table_name='documents')
```

**没有重新 `create_table`**——autogenerate 只 diff 差异，已存在的对象不会重复生成。

| 步骤 | 实测 |
|---|---|
| `upgrade head` | `Running upgrade 7433ed806f3a -> b0846e5e87de` |
| `SHOW INDEX FROM documents` | `PRIMARY -> id`、`ix_documents_kb_id -> kb_id`、`ix_documents_status -> status` |
| `alembic check` | `No new upgrade operations detected.`（模型与库一致） |
| `downgrade -1` 后 `current` | `7433ed806f3a`（退回上一版） |
| `downgrade -1` 后 `SHOW INDEX` | `ix_documents_status` 消失 |
| `upgrade head`（升回） | `Running upgrade 7433ed806f3a -> b0846e5e87de` |

**`alembic check` 是这次学到的最实用一条**：把「模型和库是否一致」变成一条命令。以后改完模型忘了生成迁移、或者迁移写错，它都会报 pending 操作。

**关于这个单列 `status` 索引的定案（2026-11-18 用户判断）**：

- 全项目 grep 后确认：**没有任何 `WHERE status = ?` 查询**——status 只在 `doc_repo.create()` 写入、在 `update_status()` 里按 `doc_id` 定位修改。所以这个索引当前**没有任何查询会用到**，成本只是写放大。
- D3 实测也支持这一点：3 个值、90% 命中率，优化器不选它；当时提的 `(kb_id, status, created_at)` 复合形态才是对的。
- 结论：**保留，作为 D3 结论的实物对照**；等有真实负载再按实测删除。删除时不能 `downgrade -1`（模型里还写着 `index=True`，check 会红），必须新写一条 `drop_index` 迁移 + 同步去掉模型里的 `index=True`——**历史不改写，只往后加**。

### ① `create_all` 为什么不能上线（三条及格，五条 3 档）

> **你的答案**：只建不存在的表 → 不能更改、不能回退；并发下有资源竞争。

**标准答案（七条，按面试出场率排）**

| # | 理由 | 不做会怎样（必须带这句） |
|---|---|---|
| 1 | **只建不改**：它只 `CREATE TABLE IF NOT EXISTS`，模型加了一列它什么也不做 | 程序按新模型发 `INSERT (…, title, …)`，库里没这列 → `1054 Unknown column`，接口直接 500，且重启多少次都不会自愈 |
| 2 | **没有版本记录**：库里没有 `alembic_version` 这种锚点，说不出"现在是第几版" | 你的库、队友的库、测试环境的库各自漂移，谁也判断不了差异；回滚时不知道该退到哪；出问题无法审计"哪次变更引进来的" |
| 3 | **不能回退**：没有 `downgrade`，只能人肉对着旧结构改 | 上线后发现列加错，只能手写 `ALTER`，多环境逐个改，漏一个就是一个事故 |
| 4 | **并发竞态**：`checkfirst=True` 是"先查再建"，两个实例同时启动会同时查到"不存在" | 两个进程同抢一把 DDL 锁，一个报 `1050 Table already exists`，启动失败或半死 |
| 5 | **进程不该有 DDL 权限**：生产应用账号通常只有 DML | 要么给应用账号开 `CREATE/ALTER`（等于把改结构的权力交给任意一次误启动），要么部署时直接权限报错 |
| 6 | **部分失败状态未知**：MySQL 每条 DDL 隐式提交，三张表建到第二张挂了，前两张已经生效 | 重跑时 `checkfirst` 会跳过前两张，看起来"幂等成功"，实际库里是半成品；它永远不补列/索引，假象会一直留着 |
| 7 | **不可评审**：结构变更不进 Git diff、不进 Code Review、不进 CI | 谁在什么时候改了线上表结构，没人说得出来；也没法在合并前卡住"这条会锁表 10 分钟"的变更 |

**你的差距只有一处，但是最关键那处**：第 2 条（版本记录）。第 3、4 条你已经说到了，第 1 条说成"不能更改"方向对。

**一句背下来的版本**：*create_all 是"建表脚本"，不是"迁移系统"——它不 diff、不记版本、不能退、不管并发，还要求进程有 DDL 权限。迁移系统缺的每一样，都是一次线上事故。*

### ③ 迁移失败了怎么办

> **你的答案**：forward fix。（结论对，但只有结论）

**先答"为什么不能指望回滚"**——这是这题真正的考点：

MySQL 的 DDL **隐式提交**（`alembic upgrade` 日志里那句 `Will assume non-transactional DDL` 就是在说这件事）。一条迁移里有 5 条 DDL，跑到第 3 条失败时，前 2 条**已经提交、退不回来**，而且 `alembic_version` 还没更新——库的真实结构和版本号**已经不一致**了。所以"出错了就 downgrade"在 MySQL 上不成立；`downgrade` 本身也只是另一串 DDL，同样可能中途失败。

**标准答案：四步**

1. **迁移前备份**（逻辑备份或快照）。这是唯一能真正救数据的手段，其余都是止损。
2. **一个迁移只做一件事**，小步走。目的不是好看，是把"半途状态"的爆炸半径压到最小——一条迁移里 1 条 DDL，失败就没有半成品。
3. **失败后先核实真实状态**，别急着重跑：`alembic current` 说跑到哪一版，但 DDL 可能已经执行了一半，**两者不一致时以 `SHOW CREATE TABLE` 的结构为准**；必要时手工修正 `alembic_version` 让它跟真实结构对齐。
4. **forward fix**：新写一条迁移把结构推到目标态，**绝不回头改历史迁移**——历史一旦被别的环境执行过，改它就是让两个环境的"同一版本号"含义不同。大表加索引用 `pt-online-schema-change` / `gh-ost`，避免长时间锁表。

**一句背下来的版本**：*MySQL 的 DDL 没有事务，所以迁移失败没有"撤销"只有"前进"——先备份、小步走、核实真实结构、写新迁移修，历史迁移一个字都不改。*

**追问链**：那 `alembic_version` 被手工改错了会怎样？（后续 upgrade 会跳过该跑的或重跑跑过的，Alembic 报 `Can't locate revision`，只能人工对齐）→ 生产上大表加索引怎么不停服？（gh-ost/pt-osc，或者 MySQL 8 的 `ALGORITHM=INPLACE, LOCK=NONE`，前提是操作类型支持）

### 7.4 明天 D6 计划里的内在矛盾

周计划 D6 要求：`mutation_check.py` 扩 3 类 DB 变异体，**漏 `commit` 必须有测试抓住**。

但目前没有任何测试走「handler → service → repo → session → DB」这条路，所以「把 `commit` 删掉」这个变异体**必然抓不住**——D6 会退化成"确认抓不住 + 写明原因"，验收结果是零收获。这不是变异体设计的问题，是链路没通导致的空转。

### 7.5 建议：D6 拆成「接线 1.5h + 变异体 1.5h」

接线是规格，不是重构（代码自己写，五步）：

1. **服务层持有 session**：`KBService(repo)` 改成必须传入；删掉 `session is None` 的内存分支。**半切换比不切换更危险**——写进 DB、读从内存，刚建完就查不到，跨进程必现。
2. **仓储层五个方法全切 DB**：`get` / `list_by_owner` / `count_by_owner` / `update` / `delete` 用 `select()` / `update()` / `delete()`；`create` / `incr_doc_count` 已就绪。
3. **handler 注入**：`session: Session = Depends(get_db)` → `KBService(KBRepository(session))`；`documents.py` 的 `DocService(kb_repo or KBRepository())` 一并改。
4. **事务边界落在 service**：写完最后一次 repo 调用后 `session.commit()`；异常由 `get_db` 的 `rollback` 兜底。代价要知道：commit 之后的异常（如 response 序列化失败）回滚不了——这是 D1 的结论，写进注释而不是当它不存在。
5. **补集成测试**（这一步才是 D6 变异体的靶子）：新文件跑真 MySQL（单独 `kb_test` 库，每例前后清表），断言**另开一个 session 能查到**。`_count(engine)` 那种"用新会话数行数"的写法就是能抓住「漏 commit」的测试。

时间紧的优先级：`KBService.create` + `list` + `get` 先通（能验证"写进去、读得出来"），`update` / `delete` / 文档链路顺延；后台任务 `run_index` 不复用请求 session（D1 结论），它得自己开 session + 自己 commit，单独一轮处理。

**一句话回答"这个项目最后能跑通吗"**：能，而且差得不远——C 段证明了补一次 commit 就落库。但现在这一版的状态是「数据库功能做完了 60%，其中"接进业务"的 40% 还没开工，而测试和门禁都发现不了这件事」。

| `Path(...).parent.parent[1]` | `TypeError: 'WindowsPath' object is not subscriptable` | Python 3.10 起 Path 不可下标；要么 `parents[1]`，要么整段删（包已装，不需要改 sys.path） |
| 教材给的 `python -c "..."` 嵌套双引号 | `SyntaxError: unterminated string literal` | PowerShell 5.1 的转义规则与 bash 不同；**嵌套引号的命令一律写成脚本文件** |
| 教材说"迁移文件也在 lint 范围" | 实际 `check.py` 的 TARGETS 不含 `alembic/` | 已修正教材；但 import 仍建议放顶部便于阅读 |
