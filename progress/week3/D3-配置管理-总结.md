# W3-D3 · 配置管理 总结（2026-10-24）

> 教材：kb-service `core/config.py` + `.env` / `.env.example` 双文件机制。

## 一、配置三级优先链（核心）

```
环境变量  >  .env 文件  >  代码默认值
```
每个字段按序查找，找到即用。字段名 `secret_key` ↔ 环境变量 `SECRET_KEY`（大小写不敏感）。
**意义**：同一份代码，换一套环境变量就是另一套部署——dev 改 `.env`，生产注入容器变量，代码零改动。

## 二、`@lru_cache` 的真实身份：单例保证

```python
@lru_cache
def get_settings() -> Settings: ...
```
- **为什么要有**：`Settings()` 要读文件+全量校验，不能每个 Depends 重来；缓存 = 全进程只有一个配置实例
- **去掉的风险不是"污染"而是"分裂"**：每次调用新实例 → 测试 monkeypatch 后，进程里同时存在不同步的多个配置副本 → "改了不生效"型 bug
- **测试换配置的正确姿势**：`get_settings.cache_clear()` → 改环境变量 → 再调用（先清血，再换血）

## 三、secrets 管理：结构进 Git，秘密不进

| 文件 | 内容 | 进 Git |
|---|---|---|
| `.env` | 真值（真密钥/真密码） | ❌ `.gitignore` 拦截（`git check-ignore` 可验证） |
| `.env.example` | 模板：字段名+假值+注释 | ✅ 新同事的说明书 |

真实密钥进 Git 历史就**永远删不干净**（每条历史 commit 都有），只能作废重发。

**哪些字段绝不能写死**：`SECRET_KEY`、`LLM_API_KEY`、带真密码的 `DATABASE_URL`——一切"环境专属 + 泄露有后果"的值。

## 四、启动即校验（fail-fast）

- `Field(min_length=16)`：Day2 亲手测过——删短密钥，进程当场起不来
- `Literal["dev","test","prod"]`：非法值（`env=hacker`）**启动即炸**；对比 `str` 会静默存活到某个 if 分支才出鬼

## 五、环境变量注入 vs 挂 .env（生产做法）

容器生产环境**注入环境变量**优于挂 `.env` 文件：
1. **镜像复用**：同一个镜像配不同 env 就是不同环境（12-factor 原则），不用每个环境打一个镜像
2. **秘密不落盘**：`.env` 是明文文件，会随镜像层/卷泄漏；环境变量由编排系统（K8s Secret）管理
