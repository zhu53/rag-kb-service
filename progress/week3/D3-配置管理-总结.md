## 1. 配置三级优先链（核心机制）

```
环境变量  >  .env 文件  >  代码默认值
```

逐字段按序查找，找到即用。字段名 `secret_key` ↔ 环境变量 `SECRET_KEY`（**大小写不敏感**，pydantic-settings 负责映射，配 `env_prefix="KBCLI_"` 后是 `KBCLI_SECRET_KEY`）。

**意义**：同一份代码，换一套环境变量就是另一套部署——dev 改 `.env`，生产注入容器变量，**代码零改动**。

### 面试问法："同一份代码怎么跑在不同环境？"

**30 秒答案**："配置从环境里读，不写死在代码里——这是 12-Factor 的第三条。我用 pydantic-settings，优先级是环境变量 > `.env` 文件 > 代码默认值：本地开发放 `.env` 方便，生产由容器/K8s 注入环境变量，镜像完全复用。所有配置在启动时经由 Pydantic 校验，类型不对或必填缺失就直接起不来，属于 fail-fast。"

## 2. `@lru_cache` 的真实身份：单例保证

```python
@lru_cache
def get_settings() -> Settings:
    return Settings()
```

- **为什么要有**：`Settings()` 要读环境 + 读文件 + 全量校验，不能每个 `Depends(get_settings)` 都重来一遍；缓存 = 全进程只有一个配置实例。
- **去掉的风险不是"缓存污染"，是"多副本分裂"**（我第一次答反了，重点记）：

```
每次调用新实例
  → 模块 A 启动时读了配置（副本 1）
  → 测试 monkeypatch 环境变量，模块 B 读配置（副本 2）
  → 进程里同时存在两份不同步的配置 → "改了不生效"型 bug
```

- **测试换配置的正确姿势**：`get_settings.cache_clear()` → 改环境变量 → 再调用（**先清血，再换血**）。

### 面试问法："为什么 get_settings 要加 lru_cache？"

**30 秒答案**："保证进程级单例。配置对象读环境、读文件、跑校验，成本不低；更重要的是语义上整个进程应该只有一份配置——如果不缓存，每次依赖注入都造一个新实例，测试里 monkeypatch 之后就会出现有的模块拿到新配置、有的拿到旧配置，行为不可预测。测试需要换配置时先 `cache_clear()` 再改环境变量。这也是一种进程内缓存的典型用法：换的是'唯一性'而不是'速度'。"

**追问链**：
- 追问①："配置能热更新吗？" → 默认不能，因为被缓存住了。要热更新得做事件驱动：配置中心（Nacos/Apollo/etcd）推送 → 回调里 `cache_clear()` 或替换单例引用；但要注意已经持有旧配置对象的模块不会自动更新，所以热更新是有成本的设计。
- 追问②："为什么不用全局变量？" → 全局变量没有校验、没有类型、import 顺序敏感、测试难替换；Pydantic 提供类型与校验，函数式单例提供可控生命周期。
- 追问③（深）："配置对象应该传参还是全局获取？" → 库代码传参（不依赖全局状态，好测）；应用层入口可以全局获取，但要在边界处显式注入给 service。

## 3. secrets 管理：结构进 Git，秘密不进

| 文件 | 内容 | 进 Git |
|---|---|---|
| `.env` | 真值（真密钥/真密码） | ❌ `.gitignore` 拦截（`git check-ignore -v .env` 可验证） |
| `.env.example` | 模板：字段名 + 假值 + 注释 | ✅ 新同事的说明书 |

**为什么秘密进 Git 就完了**：每条历史 commit 都留副本，删文件不等于删历史；`git filter-repo` 改写历史很痛，且可能已被 clone/fork。**唯一正确处置：当作已泄露，立刻轮换密钥**。

**绝不能写死的字段**：`SECRET_KEY`（签发 JWT 的根，泄露 = 任意伪造 token）、`LLM_API_KEY`、带真密码的 `DATABASE_URL`——一切"环境专属 + 泄露有后果"的值。

### 面试问法："密钥怎么管理？"

**30 秒答案**："分三层。本地开发用 `.env`，进 `.gitignore`，同时提交一份 `.env.example` 当模板说明有哪些字段。CI 和测试用平台的 secret 机制注入环境变量。生产用 K8s Secret 或专门的密钥管理服务（Vault/KMS），由编排层注入环境变量或挂载文件，镜像里不含任何秘密。原则是秘密只存在于运行时的环境中，不进代码、不进镜像层、不进 Git 历史。如果已经提交过，当作泄露处理——轮换密钥，而不是只删文件。"

**追问链**：
- 追问①："为什么环境变量优于 `.env` 文件进生产？" → ①镜像复用：同镜像不同 env 就是不同环境；②不落盘：`.env` 是明文文件，会随镜像层/日志/卷泄漏。
- 追问②："K8s Secret 就安全吗？" → 默认只是 base64，不是加密；要开 etcd 加密、RBAC 限制、慎用 `envFrom`（环境变量会出现在进程环境、崩溃转储、子进程里），更严的场景用挂载文件或外部密钥服务。
- 追问③："密钥轮换怎么做？" → 双密钥并存期（新旧都能验签，新签发用新密钥）→ 观察旧密钥使用量归零 → 下线旧密钥；数据库密码轮换需要连接池重建配合。

## 4. 启动即校验（fail-fast）

- `Field(min_length=16)`：Day2 亲手测过——把密钥改短，进程**当场起不来**。
- `Literal["dev","test","prod"]`：非法值（`env=hacker`）启动即炸；对比 `str` 会静默存活到某个 `if` 分支才出鬼。

**fail-fast 的价值**：配置错误在启动期暴露 = 一次部署失败；在运行期暴露 = 线上某个请求 500，可能过了几个小时才被发现。

### 面试问法："配置写错了会怎样？"

**30 秒答案**："我希望它在启动时就炸。配置模型用 Pydantic 声明类型和约束——密钥长度、枚举取值、必填字段，启动时一次性校验全部配置，任何一条不合法进程直接退出，K8s 会看到 crashloop 而不是把坏配置带上线。这比运行期才在某个分支里发现'env 是个没见过的值'要好得多，因为启动期失败是可见、可回滚的，运行期失败是沉默的。"

## 5. 生产：注入环境变量 vs 挂 `.env`

1. **镜像复用**：同一个镜像配不同 env 就是不同环境（12-factor），不用每个环境打一个镜像。
2. **秘密不落盘**：`.env` 是明文文件，会随镜像层/卷泄漏；环境变量由编排系统（K8s Secret）管理。

代价也要知道：环境变量对子进程可见、可能进入崩溃转储、修改需要重启容器（不像文件挂载可以热读）——所以敏感度极高的场景更倾向挂载文件 + 应用支持 reload。

## 7. 易错点速查

| 坑 | 教训 |
|---|---|
| 以为去掉 `lru_cache` 是"缓存污染" | 真风险是**多副本分裂**、改了不生效 |
| 测试改环境变量后不 `cache_clear()` | 单例已缓存，改了白改 |
| `.env` 提交进 Git | 历史删不干净 → 只能轮换密钥 |
| 用 `str` 接 `env` 字段 | 非法值静默存活；用 `Literal` 启动即炸 |
| 生产挂 `.env` 文件 | 秘密落盘 + 镜像不可复用 |

## 8. 30 秒答案集（考前速背）

1. **配置优先级** → 环境变量 > `.env` > 代码默认值。
2. **单例的意义** → 全进程一份配置，避免多副本不同步；测试用 `cache_clear()` 换血。
3. **`.env` vs `.env.example`** → 真值不进 Git / 模板进 Git。
4. **秘密泄露处置** → 当作已泄露，立即轮换；别指望删文件。
5. **fail-fast** → 启动期校验（类型/长度/枚举），错了直接起不来。
6. **生产为什么注入 env** → 镜像复用 + 不落盘（K8s Secret）。
7. **12-factor 第三条** → 配置存环境，代码与配置严格分离。
