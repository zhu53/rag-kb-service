## 1. import 的三条底层事实

### 1.1 一句话定义

`import` 是一次**按路径查找 + 执行一次 + 缓存**的操作：找到模块文件 → 在独立命名空间里执行它的顶层代码 → 结果存进 `sys.modules` → 之后所有 import 都复用这份缓存。

### 1.2 查找顺序（`sys.path`，从上到下，先命中先赢）

```
[0] 脚本所在目录（或 -c 时的当前目录 / -m 时的 cwd）
[1] PYTHONPATH
[2] 标准库
[3] site-packages（含 editable 安装的重定向）
```

W1 那次 `Could not import module 'mini_api'` 就是脚本目录里没有它——**"找不到模块"99% 是 sys.path 问题，不是文件不存在**。

### 1.3 模块缓存与"顶层代码=副作用"

每个模块**只在第一次 import 时执行一遍**，之后从 `sys.modules` 直接取。

推论（极重要）：**模块顶层写什么，就等于"import 这个模块的人替你执行了什么"**。顶层调用函数、读文件、连数据库都是 import 的副作用——所以引擎/连接池要延迟创建（lazy init），配置对象要单例（D3 的 `@lru_cache` 正是这个家族）。

### 1.4 `import x` vs `from x import y`

两者拿到的是**同一个模块对象**（`sys.modules` 里同一份），区别只在当前命名空间绑定了什么名字。这一点是理解循环导入的前提。

## 2. 包、`__init__.py`、命名空间包

| | 常规包（有 `__init__.py`） | 命名空间包（无 `__init__.py`，3.3+） |
|---|---|---|
| import | ✅ | ✅ 也能跑 |
| pytest / mypy / 打包工具 | ✅ 全认 | 行为微妙，常出幺蛾子 |
| 可放初始化代码、导出 API | ✅ | ❌ 没有执行入口 |

**结论**：没 `__init__.py` 也能 import（PEP 420 命名空间包），但工程代码一律补上——**工具链的兼容性比"能不能跑"重要**。

`__init__.py` 的三个正经用途：①标记常规包；②定义 `__version__`（包的身份证，kbcli 就靠它）；③限定导出面（`__all__` + re-export），把内部结构藏起来。

### 面试问法："`__init__.py` 是干什么的？没有它为什么也能 import？"

**30 秒答案**："`__init__.py` 是常规包的标记文件，import 包时它会先被执行，可以在里面做初始化、定义 `__version__`、re-export 公共 API。Python 3.3 之后 PEP 420 引入了命名空间包，没有 `__init__.py` 的目录也能被当成包，多个目录还能合并成一个逻辑包。但工程上仍然要写——pytest 收集、mypy 分析、打包工具对常规包的支持最稳，命名空间包容易踩工具链的坑。"

## 3. 绝对导入 vs 相对导入

```python
from kb_service.core.config import settings   # 绝对：从项目根算起
from .config import settings                  # 相对：. 当前包，.. 上级
```

| | 绝对导入 | 相对导入 |
|---|---|---|
| 可读性 | 一眼看到完整路径 | 短，但要知道自己在哪个包 |
| 重构友好 | 改包名要全局替换（IDE 能干） | 包里挪文件不用改 |
| 能否直接 `python xxx.py` 跑 | 能 | **不能**（`__main__` 没有包上下文 → `attempted relative import with no known parent package`） |

**约定**：包内兄弟模块用相对导入（`from .errors import AppError`），跨包用绝对导入；相对层级不超过一层。

**为什么直接运行会炸**（面试常追问）：`python cart.py` 时该文件的 `__name__` 是 `"__main__"`，`__package__` 是 `None`——解释器根本不知道它在哪个包里，`.` 无解。

## 4. 循环导入（重头戏，亲手炸过）

### 4.1 炸的机制

```
from shop.cart import Cart        # ① 开始加载 cart，cart 进 sys.modules（半成品）
  → from shop.pricing import ...  # ② cart 执行到一半，转去加载 pricing
    → from shop.cart import Cart  # ③ cart 已在 sys.modules 但是半成品，
                                   #    class Cart 还没执行到 → ImportError:
                                   #    partially initialized module
```

### 4.2 精确结论（务必背原句）

> **循环本身不炸；"循环 + `from` 导入对方尚未定义的名字"才炸。**
> `import shop.cart`（只要模块对象本身）反而能跑——因为模块对象已经放进 `sys.modules` 了，只是里面的属性还没长全。

这就是为什么"同样的循环依赖，在你这里炸、在别人代码里能跑"——写法不同。

### 4.3 修法：结构修，不是打补丁

依赖必须**单向**。今天是 `empty_cart`（Cart 的工厂函数）放错了文件——它在 `pricing.py` 里却要 `from cart import Cart`，而 `cart.py` 又要用 `pricing` 的折扣函数，双向死锁。把工厂挪回 `cart.py`，依赖变成单向 `cart → pricing`。

**这就是 W1 分层思想的延续：循环依赖往往是"某个东西放错了层"。**

逃生舱（不推荐当修法）：函数内 `import`——延迟到调用时才解析，循环被打破，但**结构问题被掩盖**，且每次调用有查找开销、IDE 跳转失效。真实项目里只在"确实无法调整结构"时用（如插件注册、类型检查专用 import 放 `if TYPE_CHECKING:`）。

### 面试问法："遇到过循环导入吗？怎么解决的？"

**30 秒答案**："遇到过。循环导入本身不一定报错，报错的是循环里用 `from X import 某个名字`，而此时 X 还在半初始化状态，那个名字还没定义。我的处理顺序是：先看依赖方向，通常是有个函数或类放错了模块，把它挪到正确的一层，让依赖单向化；实在不能调整结构时，才用函数内延迟导入或者 `TYPE_CHECKING` 块做逃生。我不用延迟导入当首选，因为它会掩盖分层问题。"

**追问链**：
- 追问①："为什么 `import x` 不炸？" → 只取模块对象，模块对象在 sys.modules 里已存在（半成品也算存在），属性访问推迟到运行时。
- 追问②："延迟导入有什么代价？" → 每次调用都走一遍 sys.path 查找（有缓存但仍有开销）、静态分析看不见依赖、掩盖架构问题。
- 追问③："`if TYPE_CHECKING:` 那个块是干什么的？" → 只在类型检查器眼里为真，运行时为假——用来导入"仅用于注解"的类型，既不产生运行期循环，又保留类型信息。
- 追问④（深）："微服务里怎么避免这种耦合？" → 依赖方向原则（依赖抽象不依赖实现）、分层架构、模块边界用接口（D4 的 Protocol）。

## 5. 文件开头的位置身份

| 位置 | 谁 |
|---|---|
| 第一条语句（前面只许注释） | 模块 docstring |
| 第一条**可执行**语句 | `from __future__ import ...` |

- `from __future__ import annotations` 排在别的 import 后面 → `SyntaxError`：**它是编译器开关，改变整个文件注解的解析方式，必须先于一切代码被读取**。
- docstring 被 import 挤到后面 → **不再是 docstring**，退化成一条没人理的字符串表达式（`__doc__` 变 None，help() 失效）。

今天两个坑都亲手踩过：docstring 位置、`__future__` 位置。

## 6. 注解的求值时机（第二颗炸弹）

```python
class Cart:
    def empty_cart() -> Cart:   # 💥 NameError: name 'Cart' is not defined
```

**`def` 的注解在 def 语句执行那一刻就求值**，而 `Cart` 这个名字要等整个 `class` 语句执行完才绑定——类体内部引用自己必然炸。

三种修法：

| 修法 | 写法 | 适用 |
|---|---|---|
| 不写注解 | `def empty_cart():` | 类型显而易见 |
| 前向引用（字符串） | `-> "Cart"` | 单点解决 |
| 全文件延迟求值 | 顶部 `from __future__ import annotations` | 项目级统一做法（PEP 563） |

**同时记住**：`self.x: 注解` **会求值**，局部变量 `x: 注解` **不求值**。所以属性注解写成 `[str, dict]` 这种 list 字面量时运行期不报错（造个 list 扔掉），只有 mypy 抓——这是第四档 #04/#05/#06 反复出现的静默坑。

## 7. 字符串注解与 FastAPI（亲手纠正过的误解）

**字符串化 ≠ 依赖注入失效。** FastAPI 启动扫描路由时调用 `get_type_hints()` 把字符串注解求值回真实类型：

- `-> "Cart"`，启动时 Cart 已定义 → ✅ 照常工作
- 字符串里名字拼错 → 💥 **启动瞬间 NameError** —— fail-fast，是保护不是坏事

这也是为什么"用 `from __future__ import annotations` 会不会搞坏 FastAPI"的答案是**不会**。

### 面试问法："Pydantic/FastAPI 的类型校验是怎么拿到类型的？"

**30 秒答案**："靠 `typing.get_type_hints()` 在运行时求值注解。所以注解必须是**可在运行期解析的表达式**——字符串前向引用也可以，`get_type_hints` 会去模块命名空间里查名字；但如果名字拼错或只在 `TYPE_CHECKING` 块里导入，就会在启动或首次调用时报 NameError。这也是 FastAPI 的一个好处：注解错误在启动期就暴露，而不是等到线上某个请求。"

## 9. 30 秒答案集（考前速背）

1. **import 干了什么** → 按 sys.path 找文件 → 执行顶层代码一次 → 存 sys.modules → 后续复用。
2. **找不到模块先查什么** → sys.path 和 sys.modules；脚本目录/工作目录在不在里面。
3. **`__init__.py` 干什么** → 常规包标记 + 初始化 + `__version__` + re-export；命名空间包不需要但工具链偏爱它。
4. **绝对 vs 相对** → 包内兄弟用相对（重构友好），跨包用绝对（可读）；相对导入不能直接运行脚本。
5. **循环导入炸的条件** → 循环 + `from` 取半成品模块里还不存在的名字。
6. **修循环导入的态度** → 先修结构（依赖单向），延迟导入只是逃生舱。
7. **`__future__` 为什么第一行** → 编译器开关，影响全文件解析。
8. **注解什么时候求值** → def 执行时立即求值；`__future__ annotations` 或字符串可延迟；`get_type_hints` 负责运行期求回。
