# W3-D1 · Python 包与导入机制 总结（2026-10-24）

> 全部概念都由"亲手炸出来再亲手修好"获得，不是背的。

## 一、import 的机制（三个事实）

**① 查找顺序**（`sys.path` 从上到下）：

```
[0] 脚本所在目录 → 标准库 → .venv/Lib/site-packages → 项目 src（可编辑安装）
```
W1 那次 `Could not import module 'mini_api'` 就是因为脚本目录里没有它。

**② 模块缓存**：每个模块只在第一次 import 时执行一遍，之后从 `sys.modules` 拿。
推论：**模块顶层代码 = import 时刻的全局副作用**（Day5 `@lru_cache` 忘导包直接 NameError 的家族原理）。

**③ `import x` 和 `from x import y`** 拿到同一个模块对象，区别只是命名空间里放什么。

## 二、包：`__init__.py` 的真实身份（3.3 后修正版）

| | 有 `__init__.py`（常规包） | 没有（命名空间包） |
|---|---|---|
| import | ✅ | ✅（3.3+ 也能跑！） |
| pytest/mypy/打包工具 | ✅ 全认 | 行为微妙，常出幺蛾子 |
| `__init__.py` 内容 | 可写导出、初始化 | — |

**结论**：没 `__init__.py` 也能跑（命名空间包），但**项目代码一律补上**——工具链全认。

## 三、绝对 vs 相对导入

```python
from kb_service.core.config import settings   # 绝对：项目代码首选（重构可全局搜）
from .config import settings                  # 相对：. 当前包，.. 上级（只推荐一层）
```
相对导入的文件**不能直接 `python xxx.py` 跑**（没有包上下文）。

## 四、循环导入（今天的重头戏）

**炸的机制**（时间线，背这个流程）：

```
from shop.cart import Cart        # 开始加载 cart
  → from shop.pricing import ...  # cart 暂停，转去加载 pricing
    → from shop.cart import Cart  # 💥 cart 在 sys.modules 里是半成品，
                                   #    class Cart 还没定义 → ImportError
```

**精确表述**：循环本身不炸，**"循环 + from-import 要对方还没定义的名字"才炸**。
`import shop.cart`（拿整个半成品模块）反而能跑——这就是有些循环"在别人代码里能跑"的原因。

**修法（结构修，不是打补丁）**：依赖只能单向。`empty_cart` 是 Cart 的工厂 → 挪进
`cart.py`，依赖方向变成单向 cart → pricing。**"谁放错了层"是 W1 分层思想的延续。**
（函数内懒 import 是逃生舱不是修法——它掩盖结构问题。）

## 五、文件开头位置的身份规则

| 位置 | 谁 |
|---|---|
| 第一条语句（前面只许 docstring/注释） | 模块 docstring |
| 第一条可执行语句 | `from __future__ import ...` |

`from __future__ import annotations` 排在别的 import 后面 → `SyntaxError`：
**它改变编译器解析全文件的方式，必须先于一切代码**。
同理，docstring 被 import 挤到后面就**不再是 docstring**，只是一条没人理的字符串。

## 六、类体内注解的求值时机（今天第二个炸弹）

```python
class Cart:
    def empty_cart() -> Cart:   # 💥 NameError: name 'Cart' is not defined
```
**`def` 的注解在 def 执行那一刻求值**，而 `Cart` 这个名字要等 `class` 语句整体结束
才绑定——类体内部引用自己必然炸。三修法：
1. 不写注解（类型显而易见时可接受）
2. 前向引用 `-> "Cart"`（注解变字符串）
3. 顶部 `from __future__ import annotations`（全文件注解变字符串）

## 七、字符串注解与 FastAPI（bonus 题的纠正）

**字符串化 ≠ 依赖注入失效**。FastAPI 启动扫描路由时调 `get_type_hints()` 把字符串
求值回真实类型（W1 验收器第 9 项抓拼写错用的同一招）：

- `-> "Cart"` + 启动时 Cart 已定义 → ✅ 照常注入
- 字符串里名字拼错 → 💥 **启动瞬间 NameError = fail-fast，是保护不是坏事**

## 八、今天的坑清单

| # | 坑 | 一句话教训 |
|---|---|---|
| 1 | 文件夹名拼错 `import_practicce` | 目录名也会被 import 路径用到，别手拼 |
| 2 | 循环导入 | 依赖必须单向；"谁放错了层" |
| 3 | 类体内 `-> Cart` | 类体执行时类名还不存在 |
| 4 | `__future__` 不在第一行 | 它是编译开关，必须先于一切代码 |
| 5 | docstring 被 import 挤掉 | 文件开头位置有身份 |
| 6 | 以为字符串注解废掉 FastAPI DI | get_type_hints 启动时求值回来 |

## 九、闭卷快问（答案折叠）

<details><summary>1. 循环导入炸的精确条件？</summary>循环 + from-import 要对方"半初始化模块"里还不存在的名字。import 整模块不炸。</details>
<details><summary>2. 没写 __init__.py 为什么也能 import？</summary>Python 3.3+ 命名空间包机制；但工具链不保证，项目代码仍要写（常规包）。</details>
<details><summary>3. 类体内部 def 的返回注解写自己的类名为什么炸？</summary>注解在 def 执行时求值，而类名等 class 语句结束才绑定；修法：前向引用 "Cart" 或 __future__ annotations。</details>
<details><summary>4. __future__ import 为什么必须第一行？</summary>它改变编译器解析整个文件的方式，必须先于一切代码被读取。</details>
<details><summary>5. from __future__ import annotations 后 FastAPI 会坏吗？</summary>不会：启动时 get_type_hints 把字符串求值回真实类型；名字拼错才炸，且是启动期 fail-fast。</details>
