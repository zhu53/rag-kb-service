## 一、逐题判定与标准答案

### Q1 循环导入（1/2）
**标准答案（30 秒版）**：
循环本身不炸——`sys.modules` 里会留下**半成品模块**。炸的是"循环 + `from 半成品模块 import 还不存在的名字`"，报错关键词是 **`ImportError: cannot import name 'Cart' from partially initialized module`**。`import shop.cart` 不炸，因为它只从 `sys.modules` 拿半成品模块对象，不需要任何名字已绑定；`from ... import Cart` 要求名字**此刻已存在**。

- 丢分：关键词没说出；"为什么 import 模块不炸"没答。
- **锚点**：半成品模块（partially initialized module）躺在 sys.modules 里——拿模块安全，取名字危险。

### Q2 类体内注解求值（2/2 满分）
类体执行时 `-> Cart` 立即求值，Cart 尚未绑定 → NameError。修法：字符串注解 / `from __future__ import annotations`（**必须文件第一条语句**）/ 不写注解。FastAPI 不失效：启动扫描用 `get_type_hints()` 把字符串求值回来，typo 会在启动瞬间 NameError（fail-fast）。

### Q3 extras vs groups vs dependencies（1.5/2）
三分法：`[project] dependencies` 运行必须（给用户装）；`[dependency-groups]` 私有开发工具 ruff/pytest（不给消费者装）；`[project.optional-dependencies]` 按需可选配件。
**丢分（边界题二连败）**：uvicorn 本体必装，`[standard]` 可选——上次说反（本体说成可选），这次又把 optional 说成必装。
- **锚点：看它在不在 `[project] dependencies` 里。在 → 必装；在 optional → 可选。**

### Q4 pyproject vs uv.lock（2/2 满分）
"pyproject 管我想要什么（愿望/约束），uv.lock 管实际装了什么（全树 62 包精确解 + hash）"。lock 进 Git 保证复现；`.venv` 不进（可由 lock 重建）。0.x 阶段允许破坏性变更（minor 也可能 breaking）。

### Q5 配置三级优先链（1.5/2）
环境变量 > .env > 代码默认值。pydantic-settings 做字符串→真实类型的转换。
**丢分**：环境变量名写成 `KBCLI_data_file`——约定是全大写 `KBCLI_DATA_FILE`（运行时大小写不敏感碰巧能跑，但所有真实项目全大写）。
- **锚点：环境变量的世界只有大写；字段名下划线原样保留。**

### Q6 lru_cache 单例（1.5/2）
`@lru_cache` 保证全进程一个 Settings 实例。去掉的风险：**Settings 对象多副本分裂**（每个调用点各造一个实例，一个被改/环境变了，其他副本不知道 → 不同步）。`cache_clear()` = 测试换血阀门。`.env` 真值不进 Git，`.env.example` 模板进。
- 丢分：说成"配置文件多备份"——分裂的是**内存里的对象**，不是文件。

### Q7 Protocol 与依赖倒置（1.5/2）
Protocol 是结构化类型（看方法签名，不要求显式继承），ABC 要求继承声明。
**W1-Q12 正式面试版（背这个）**：
> "service 只依赖 `KBRepository` 契约（四个方法签名），从不 import 具体实现。MySQL 版只要提供同样四个方法就满足契约，在**组装处**（构造注入那一行）替换——service 零改动。契约稳定、实现可替换，这就是依赖倒置。"
- 丢分：没说清"换在哪"——**组装处换一行**才是面试官要听的具体动作。

### Q8 三层带参装饰器（1.5/2）
三层各收：装饰器参数（times）→ 函数（fn）→ 调用参数（*args/**kwargs）。`times=3` = **总共试 3 次**。成功 `return fn(...)` 即收工；全失败 **`raise last_exc`（最后一次的异常）**——最后一次最代表当前状态。times=1 等价裸调用。
- 丢分："抛异常就行"太糊——**抛最后一次**才是精确答案。

### Q9 ContextVar vs threading.local（1.5/2）
ContextVar 按协程/上下文隔离；threading.local 按线程隔离——async 单线程跑多协程时 local 共享、会串号。Filter 挂在 handler 上，**只盖章、永远放行**（`record.trace_id = var.get(); return True`）。横切关注点：trace_id 不出现在任何业务函数签名里。
- 丢分：说 Filter 有"截断"作用——截断（return False 丢日志）是它的**另一个**用途，本场景不在干。

### Q10 Token 与 reset（2/2 满分）
token = `set()` 的返回值（返程票）。不 reset：线程/协程复用时，下一个任务 set 之前会捡到上一个人的 trace_id（上下文泄漏）。裸调盖的是 ContextVar 的**默认值** `"-"`——拿默认值，不是拿错值。

### Q11 手写 LRU（2/2 满分）
`move_to_end(key)` 挪最新端；`popitem(last=False)` 弹最久未用。put 已存在 key：先 `move_to_end`，**赋值无条件执行**（关进 else = 只挪位不更新值的静默脏数据）。get 命中缺 move_to_end → 退化成 **FIFO**。

### Q12 缓存一致性（1.5/2）
删后不清缓存 → **幽灵读/脏读**：缓存里残留尸体，下次 get 命中直接返回已删除数据，绕过 repo 的 NotFound 判定。（不是"越权"——越权是另一题：命中缓存绕过 owner 校验，修法 = 命中后也判权限。）
**Cache Aside 标准流程（背）**：读 = 先查缓存，命中返回；未命中查库 → 回填缓存 → 返回。写 = **先更新数据库，再删除缓存**。

## 二、30 秒答案集（W3 高频题速答）

1. **循环导入什么时候炸？** 循环 + from 半成品模块取不存在的名字；`partially initialized module`。import 模块本身不炸。
2. **字符串注解会让 FastAPI DI 失效吗？** 不会，get_type_hints 启动时求值；typo 才炸且是 fail-fast。
3. **uv.lock 是什么？** 全依赖树的精确解（版本+hash），pyproject 是愿望、lock 是现实，进 Git 保复现。
4. **配置优先级？** 环境变量 > .env > 默认值；pydantic-settings 负责字符串转类型；变量全大写。
5. **去掉 get_settings 的 lru_cache 会怎样？** Settings 多副本分裂不同步（不是缓存污染）。
6. **换数据库 service 为什么不改？** 只依赖 Protocol 契约，组装处换一行实现。
7. **全失败重试抛什么？** raise last_exc——最后一次的异常。
8. **为什么 ContextVar 不是 threading.local？** async 单线程多协程共享 local 会串号；ContextVar 按上下文隔离。
9. **LRU 两把钥匙？** move_to_end（访问保鲜）+ popitem(last=False)（淘汰最旧）。
10. **Cache Aside 写流程？** 先更库、再删缓存。
