## 2. 依赖倒置（DIP）：为什么 service 不 import 具体 repo

### 2.1 一句话定义

**高层模块不依赖低层实现，双方都依赖抽象**——依赖的方向被"倒置"了：原本 service → MySQL 驱动（高层依赖低层细节），现在 service → 接口 ← 实现。

### 2.2 三种写法的差别

```python
# ❌ 直连实现：service 被绑死在存储上
class KBService:
    def __init__(self) -> None:
        self._repo = MySQLKBRepository(...)     # 换库 = 改 service

# ⚠️ 继承抽象基类：能换，但强制实现方继承（还引入耦合）
class KBService:
    def __init__(self, repo: ABCRepository) -> None: ...

# ✅ Protocol：结构化子类型（今天用的）
class KBService:
    def __init__(self, repo: KBRepository) -> None: ...   # 只认"有四方法"的形状
```

### 2.3 Protocol vs ABC vs duck typing（高频对比题）

| | `Protocol`（结构化子类型） | `ABC`（名义子类型） | 纯 duck typing |
|---|---|---|---|
| 实现方要做什么 | **什么都不用做**，有这几个方法就算 | 必须显式继承 | 什么都不用做 |
| 静态检查 | ✅ mypy 认 | ✅ 认 | ❌ 不认 |
| 运行期强制 | ❌ 不做检查（静态契约） | ✅ 抽象方法没实现就 TypeError | ❌ |
| 侵入性 | 零（可给第三方类"追溯"适配） | 高（修改实现方继承关系） | 零 |
| 典型场景 | 仓储/客户端边界 | 框架基类、模板方法 | 小脚本、内部工具 |

**结论**：**跨边界的可替换点用 Protocol**（不污染实现方）；需要在基类里写共享逻辑或强制子类实现时用 ABC。

### 面试问法："为什么要给 repo 定义接口？"

**30 秒答案**："为了把'业务规则'和'存储细节'解耦。service 只依赖一个 Protocol，声明它需要的四个方法，不 import 任何具体实现。这样换存储只是再写一个满足契约的类，在组装的地方替换掉，service 零改动；测试时也可以塞一个内存实现，不用起数据库。这个模式叫依赖倒置——高层不依赖低层，双方依赖抽象。我在项目里用两个实现（内存和 JSON 文件）跑同一套场景，输出逐行一致，验证了契约的稳定性。"

**追问链**：
- 追问①："Protocol 运行时会检查吗？" → 不会，`runtime_checkable` 也只检查方法名存在与否、不检查签名；它是**静态**契约，靠 mypy 保证。
- 追问②："那怎么保证实现真的符合契约？" → ①mypy 静态检查；②一套契约测试（同一组场景跑所有实现）——我今天就是双实现对拍。
- 追问③："接口应该多大？" → 尽量小（ISP 接口隔离原则）；四方法是"最小可用仓储"，接口一大就没人能完整实现，替换成本也高。
- 追问④（深）："这和六边形架构/整洁架构什么关系？" → 同一个思想的不同命名：领域在中心，端口（Protocol）由领域定义，适配器（repo/HTTP client）实现在外层，依赖永远指向内部。

## 3. 分层的职责边界（今天最有价值的认知）

| 层 | 职责 | 不该做的事 |
|---|---|---|
| repo | 纯存取：给 owner_id+name，还一条记录 | 查重、判权、抛业务异常、生成业务规则 |
| service | 业务规则：同名冲突、归属校验、编排多步操作 | 拼 SQL、知道用的是 MySQL 还是 JSON |
| 接口层（CLI/HTTP） | 解析输入、调 service、**翻译异常** | 写业务判断 |

**两条铁律**：
1. **repo 是老实人**：给什么存什么。查重/判权全在 service——这样两个 repo 才能行为一致。
2. **异常翻译在最外层**：service 抛领域异常，CLI 翻成退出码、FastAPI 翻成 404/403（D6 串起来了）。

**契约的形状倒逼业务的形状**（今天悟到的）："同名冲突按 owner 隔离"不是谁规定的，是 `list_by_owner(owner_id)` 这个契约天然决定的——service 根本看不到别人的库。**接口设计决定了业务规则的表达方式。**

### 面试问法："分层的边界怎么划？业务逻辑放哪？"

**30 秒答案**："按'变化的来源'划。repo 层只负责存取，它的变化来自存储技术；service 层负责业务规则，变化来自需求；接口层负责协议适配，变化来自调用方式（HTTP/CLI/消息）。判断标准是：换个数据库不该改到 service，换个业务规则不该改到 repo。异常也按这个边界翻译——service 抛领域异常，最外层翻译成 HTTP 状态码或退出码。"

**追问链**：
- 追问①："事务放哪一层？" → service 层。事务是**业务用例的边界**（"创建知识库并写审计日志"必须一起成功），不是单条 SQL 的属性；repo 只管自己的操作，事务由 service 包住多次 repo 调用（unit of work 模式）。
- 追问②："service 该返回 ORM 对象吗？" → 不该。返回 ORM 对象会把持久化细节泄漏到接口层（懒加载在 session 关闭后炸、序列化出内部字段）。应返回 DTO/dict（今天返回的就是 dict）。
- 追问③："repo 里能写 join 吗？" → 能，查询语义属于存储层；但不能在里面判业务（"这个用户不能删"不是 SQL 的事）。
- 追问④（深）："循环依赖在分层里怎么避免？" → 依赖只能单向（接口层 → service → repo）；如果 service 需要回调接口层（如发通知），用事件/依赖注入回调，而不是反向 import（这就是 D1 循环导入的架构解法）。

## 4. 手写 `@retry`（三层带参装饰器，白板高频）

### 4.1 三层套娃的规律

> **带参装饰器 = 三层函数，每层只收一样东西**：参数 → 被装饰函数 → 调用参数。

```python
import functools
import time
from typing import Any, Callable, TypeVar

F = TypeVar("F", bound=Callable[..., Any])


def retry(times: int = 3, delay: float = 0.0) -> Callable[[F], F]:
    """最多尝试 times 次；全失败抛最后一次的异常。"""

    def decorator(fn: F) -> F:
        @functools.wraps(fn)
        def wrapper(*args: Any, **kwargs: Any) -> Any:
            last_exc: Exception | None = None
            for _ in range(times):                 # 总共 times 次，不是 1+times
                try:
                    return fn(*args, **kwargs)     # 成功即收工，return 不能漏
                except Exception as exc:           # noqa: BLE001 —— 重试器兜一切是正当的
                    last_exc = exc
                    if delay:
                        time.sleep(delay)
            raise last_exc                          # 全失败 → 抛最后一次
        return wrapper                                # type: ignore[return-value]
    return decorator
```

### 4.2 四个必讲细节

1. **`times` 语义**：总尝试次数，`times=1` 等价裸调用（不用特判）。
2. **`return fn(...)` 不能漏**：漏了 → 成功也不跳出循环 → 把成功当失败重试 → 最后 `raise None` → `TypeError: exceptions must derive from BaseException`。（我亲手踩过）
3. **`functools.wraps`**：保留 `__name__`/`__doc__`/`__wrapped__`，否则日志和调试里函数全叫 `wrapper`。
4. **重试贴哪一层**：贴在**最可能随机失败的那一步**（`_save` 磁盘写入），不是业务流程（`create`）——业务流程重试会重复执行业务副作用。

### 面试问法："写一个带参数的重试装饰器。"

**30 秒答案**：先三层结构——外层收参数、中层收函数、内层收调用参数。循环 `times` 次，try 里 `return fn(*args, **kwargs)` 成功即返回，except 里记下 last_exc 继续；循环结束 `raise last_exc`。用 `functools.wraps` 保留元信息。要提醒两点：**return 不能漏**，否则成功也重试到炸；**重试要贴在幂等或最脆弱的一步**，业务写操作重试要有幂等保证。

**追问链**：
- 追问①："为什么要 `functools.wraps`？" → 元信息（名字/文档/签名/`__wrapped__`）保留，日志、调试器、文档工具、FastAPI 的依赖注入都依赖它。
- 追问②："什么操作不能随便重试？" → 非幂等的写操作（扣款、下单）——重试会重复副作用；必须先去重/幂等键，或只在明确可重试的层（网络传输失败）重试。
- 追问③："重试要配什么？" → 退避策略（指数退避 + 抖动，避免惊群）、上限次数、超时预算、只重试特定异常（超时/连接错误，不重试 4xx 这类确定性失败）；否则重试会放大故障。
- 追问④（深）："重试和熔断/限流的关系？" → 重试是"再试一次"，熔断是"别再试了"（保护下游），限流是"少试一点"（保护自己）；三者一起构成客户端弹性策略。

## 5. 双实现为什么必须对拍（测试思想）

`__main__.py` 的规矩：**不许出现 `if isinstance(repo, ...)`**。两个 repo 走一模一样的代码路径，同一场景输出逐行一致 —— 这就是**契约测试（contract test）**的最小形态。

面试可讲："我给仓储契约写了一套场景（创建、同名冲突、越权、查无、删除、删后重查），对每个实现都跑一遍，输出必须一致。这样新增第三个实现（SQLAlchemy）时，我不用重新想测试用例，直接跑这套就知道合不合格。"

## 7. 核心面试题：换数据库为什么 service 不用改（W1-Q12 正式版）

**30 秒答案**："因为 service 只依赖 `KBRepository` 这个 Protocol 契约——四个方法的签名，不 import 任何具体实现。换数据库就是新写一个满足契约的 repo 类，在组装处（依赖注入那一行）替换掉，service 代码零改动。契约是稳定的，实现是可替换的，这就是依赖倒置。"

追问链见 §2；如果面试官继续问"那 SQLAlchemy 的 session 生命周期怎么管" → 答：session 属于 repo 内部实现细节，由 repo 自己按请求创建/关闭，或由外层注入 session factory；service 完全不感知。

## 8. 易错点速查

| 坑 | 次数 | 教训 |
|---|---|---|
| dict 写成 set（`{a, b}`） | 2 | 没有键值对就是集合，`record["id"]` 直接 TypeError |
| `uuid4()` 忘 `.hex` | 1 | UUID 对象不可切片，先转字符串 |
| 键名 `owner` vs `owner_id` | 2 | 数据形状先定死、全项目统一；串起来才炸的 bug 最阴 |
| `from error import` | 1 | 包内兄弟用 `from .error import` |
| 漏 `self.` | 1 | 类内调自家方法必须 `self.` |
| 注解写成 set/list 字面量 | 2 | 静默坑，只有 mypy 抓 |
| retry 漏 `return` | 1 | 成功不跳出循环 → `raise None` |

## 9. 30 秒答案集（考前速背）

1. **依赖倒置** → 高层不依赖低层实现，双方依赖抽象；换实现不动调用方。
2. **Protocol vs ABC** → 结构化 vs 名义；Protocol 零侵入、静态检查；ABC 可写共享逻辑、运行期强制。
3. **repo 该多老实** → 只存取，不查重不判权不抛业务异常。
4. **异常在哪翻译** → 最外层（CLI 退出码 / HTTP 状态码）。
5. **事务在哪层** → service（业务用例边界）。
6. **带参装饰器三层** → 参数 / 函数 / 调用，各收一样。
7. **重试贴哪** → 最脆弱且可重试的一步（`_save`），不是业务流程。
8. **契约测试** → 同一套场景跑所有实现，输出一致。

## 10. 闭卷自测

1. `Protocol` 和 `ABC` 的三个区别？
2. 为什么 `ConflictError` 必须在 service 抛，不能在 repo 抛？
3. 带参装饰器的三层分别接收什么？
4. retry 漏了 `return fn(...)` 会发生什么？为什么是 `TypeError` 而不是死循环？
5. 事务为什么放 service 不放 repo？

<details><summary>答案</summary>
1. 结构化 vs 名义子类型；Protocol 不要求继承、无运行期检查、可追溯适配第三方类；ABC 需显式继承、有运行期强制、可承载共享实现。
2. repo 要能被多个实现替换且行为一致——查重涉及"跨记录"业务语义，属于规则层；repo 只存不算。
3. 参数 / 被装饰函数 / 调用参数（*args, **kwargs）。
4. 成功也不返回 → 循环跑满 → last_exc 为 None → `raise None` → TypeError（exceptions must derive from BaseException）。
5. 事务是业务用例的原子边界（多步 repo 操作要一起成功/失败），不是单条存储操作的属性。
</details>
