# W3-D4 总结：分层与依赖倒置（repo 契约化）

> 日期：2026-10-26
> 靶子：kb-service `repositories/kb_repo.py` docstring 里那句"W7 TODO：改成 SQLAlchemy，方法签名保持不变"——今天亲手验证了它为什么成立。

## 交付物（layering_practice/ 六件套）

| 文件 | 角色 | 一句话 |
|------|------|--------|
| `kb/error.py` | 异常族 | AppError 基类 + Conflict/NotFound/Forbidden，service 只管 raise |
| `kb/interfaces.py` | 契约 | `KBRepository(Protocol)` 四方法：create/get/list_by_owner/delete |
| `kb/memory_repo.py` | 实现① | dict 即数据库，老实人：不查重、不抛业务异常 |
| `kb/json_repo.py` | 实现② | 状态在磁盘：`_load → 改 → _save`，`_save` 挂 `@retry(times=3)` |
| `kb/service.py` | 规则层 | 只 import error + 契约，**不 import 任何具体 repo** |
| `retry.py` | 横向工具 | 三层带参装饰器：参数层 → 函数层 → 调用层 |
| `kb/__main__.py` | 验收 | 双 repo 同场景对拍，零 if 分叉 |

## 核心结论（验收实测）

```
InMemoryKBRepository → ['conflict', 'forbidden', 'notfound', 'deleted', 'redelete', 'bob同名:bob']
JSONFileKBRepository → ['conflict', 'forbidden', 'notfound', 'deleted', 'redelete', 'bob同名:bob']
```

同一份 KBService，换存储引擎，业务行为逐比特一致。**W7 换 SQLAlchemy = 再写一个四方法实现 + 换 `__main__` 一行构造**，service 一个字不动。

## 必须记住的四条

1. **契约的形状倒逼业务的形状**："同名冲突按 owner 隔离"不是谁规定的，是 `list_by_owner` 这个契约方法天然决定的——service 根本看不到别人的库。
2. **repo 是老实人**：不查重、不判权、不抛业务异常；`ConflictError`/`ForbiddenError` 全部在 service。delete 复用 get_kb 做判定，不重写鉴权。
3. **重试贴着最脆弱的一步**：`@retry` 装在 `_save`（磁盘写）而不是 `create`（业务流程）上。
4. **带参装饰器三层套娃**：每层只收一样东西——参数 → 函数 → 调用；`return fn(...)` 是"成功即收工"，漏了 return 会把成功也重试到炸（`raise None` → TypeError）。

## 今天踩过的坑（都是自己的）

| 坑 | 次数 | 教训 |
|----|------|------|
| dict 写成 set（大括号里没有键值对） | 2 | `{a, b}` 是 set，`record["id"]` 直接 TypeError |
| `uuid4()` 忘 `.hex` | 1 | UUID 对象不可切片，先转字符串再切 |
| 键名 `owner` vs `owner_id` 不一致 | 2 | 数据形状先定死，键名全项目统一；串起来才炸的 bug 最阴 |
| `from error import` 非相对导入 | 1 | 包内兄弟模块用 `from .error import` |
| 方法调用漏 `self.` | 1 | 类内调自家方法必须 `self.` |
| 注解写成 set/list 字面量 | 2 | 静默坑：不求值不报错，只有 mypy 能抓 |
| retry 漏 return | 1 | 成功不跳出循环 → 把成功也重试到炸 |

## 第四档 #04 战报

`review_01_notes.py`：**2/4 合格**。找到键名不一致 + delete 缺 `return False`；漏掉注解静默坑 + rename 缺 `return`。
