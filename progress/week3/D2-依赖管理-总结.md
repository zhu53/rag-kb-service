# W3-D2 · 依赖管理深入【面试参考版】

> 日期：2026-10-24 ｜ 教材就是自己的 kb-service：`pyproject.toml`（愿望）对照 `uv.lock`（现实，62 个包全树）。

---

## 1. pyproject.toml 四大块（PEP 621 + 518）

| 块 | 装什么 | 关键点 |
|---|---|---|
| `[project]` | 身份证 + **对外契约**：name/version/requires-python/dependencies | 别人 pip install 你的包，这些依赖会被自动带上 |
| `[dependency-groups]` | 开发者私有工具（pytest/ruff/mypy） | `uv sync` 默认装 dev 组；生产 `--no-dev` |
| `[build-system]` | 打包后端（hatchling/setuptools）+ 构建要求 | 决定项目怎么被装成 wheel / editable 包 |
| `[tool.*]` | ruff/mypy/pytest/coverage 配置 | **单一事实来源**，不再散落 setup.cfg/tox.ini/.ruff.toml |

**历史脉络**（面试常问）：`setup.py`（命令式脚本）→ `setup.cfg`（声明式但分散）→ `pyproject.toml`（PEP 518 定构建依赖、PEP 621 定项目元数据，统一入口）。

### 面试问法："pyproject.toml 和 requirements.txt 什么区别？"

**30 秒答案**："定位不同。requirements.txt 只是扁平的环境快照清单，没有元数据概念；pyproject.toml 是项目身份证，声明名字、版本、Python 版本要求、运行时依赖、构建方式，还能承载工具配置。它是可发布的包元数据来源，requirements 不是。现代项目用 pyproject 声明意图、用锁文件锁精度，requirements.txt 一般只出现在老项目或某些部署场景。"

## 2. 语义化版本与约束写法

`2.14.1` = **major.minor.patch**：major 变 = 破坏性变更；minor = 向后兼容的新功能；patch = 修 bug。

**⚠️ 0.x 特例（高频考点）**：0.x 阶段的 **minor 允许破坏**——`fastapi>=0.115` 实际会接受任何未来的 0.x，包括破坏性的。实测本机解算到 0.150.0。

| 写法 | 含义 |
|---|---|
| `>=0.115` | 只设下限，未来全收（0.x 下危险） |
| `==0.115.0` | 钉死 |
| `>=1.2,<2.0` | 区间（等价于 `^1.2` 的思路） |
| `~=1.4.2` | 兼容到 1.4.x（`>=1.4.2,<1.5`） |

**兜底策略**：日常靠 lock 钉住，升级时主动 `uv lock --upgrade` 并跑测试——**版本升级是一次有意识的行为，不是装依赖的副作用**。

### 面试问法："你怎么管理依赖版本？0.x 的库怎么处理？"

**30 秒答案**："声明用兼容区间，锁定用锁文件。pyproject 里写区间表达意图，uv.lock 钉死全树精确版本加 hash，一起进 Git，保证任何机器任何时间 `uv sync` 都装出同一个环境。0.x 的库要特别小心，因为 semver 允许 0.x 的 minor 带破坏性变更，所以我会把下限写死一点、升级时显式跑测试。核心原则是：依赖升级是有意识的操作，靠 lock 冻结，靠测试验证，而不是每次安装都漂移到最新。"

## 3. 愿望 vs 现实（D2 核心）

| | pyproject `dependencies` | `uv.lock` |
|---|---|---|
| 本质 | **约束**（"fastapi>=0.115"） | **精确解**（"0.150.0 + sha256 + 下载地址"） |
| 范围 | 直接依赖（8 个） | **整棵树（62 个包）** |
| 维护 | 手写 | 工具生成，**必须进 Git** |
| 价值 | 表达兼容意图 | **跨机器跨时间逐字节复现** |

**工作流**：`uv add` → lock 重新解算 → 两个文件一起 commit → 别人 `uv sync` 复现。
**CI/生产**：`uv sync --frozen`（lock 与 pyproject 不一致直接报错，不偷偷重解算）。
**自检**：`uv lock --check` 验证两者同步。

**不提交 lock 的后果**（面试可当案例讲）：别人 sync 时重新解算 → 装到"当时最新" → 62 个传递依赖逐个漂移 → "我机器上能跑"；同时失去 hash 校验，供应链被投毒也发现不了。

**三个槽位**：
- 运行时必需（sqlalchemy）→ `[project.dependencies]`
- 开发工具（pytest/ruff/mypy）→ `[dependency-groups] dev`
- 可选配件（未来可选部署的 redis 后端）→ extras

### 面试问法："为什么锁文件必须提交到 Git？"

**30 秒答案**："因为 pyproject 只声明兼容范围，真正决定装什么的是解算结果，而解算是随时间变化的——同一个区间，今天解出 1.4.2，三个月后可能解出 1.9.0，六十多个传递依赖每一个都可能在漂。lock 把那次解算的完整结果连同 hash 固化下来，保证 CI、同事、生产装的是同一棵树。不提交 lock，复现性就没了，也没法用 hash 校验防供应链投毒。"

**追问链**：
- 追问①："`--frozen` 和普通 sync 区别？" → 普通 sync 会检查并重新解算以匹配 pyproject；`--frozen` 只用 lock，lock 与 pyproject 不一致就报错——CI 要的是"发现不一致"而不是"悄悄修好"。
- 追问②："lock 冲突了怎么办？" → 通常是两人同时改依赖，`uv lock` 重新解算解决；冲突本质是解算器要满足全树单一版本，无法同时满足时就是真冲突（升/降某个包）。
- 追问③："hash 校验防什么？" → 防包被替换/篡改（PyPI 包被 takeover 的事件真实发生过）；hash 不对直接拒绝安装。

## 4. extras vs dependency-groups（易混，必考）

`uvicorn[standard]>=0.32` = **uvicorn 本体必装** + 勾选它自己的 `standard` 可选组（树里带 `(extra: standard)` 标记的 watchfiles/websockets/httptools 就是买到的配件）。

| | extras `包[名字]` | dependency-groups |
|---|---|---|
| 谁提供 | **别人的包**定义的可选配件 | **你的项目**自己的开发工具 |
| 给谁用 | 使用者按需选择 | 只在开发时（不进发布元数据） |
| 进发布元数据 | ✅ 进 | ❌ 不进 |
| 典型例子 | `uvicorn[standard]`、`psycopg[binary]` | `[dependency-groups] dev = ["pytest","ruff"]` |

**一句话分辨**：**带了别人名字的方括号 → extras；写在自己 pyproject 里的组 → dependency-groups。**

## 5. 依赖树三个现象（`uv tree --depth 2` 实测）

1. `pydantic` 出现两次、第二处标 `(*)` —— **多方依赖只装一份**：解算器保证全树单一版本（Python 环境是扁平的，同一个包不可能装两个版本，除非用 vendoring 隔离）。
2. `starlette` 挂在 `fastapi` 下 —— **FastAPI 是 Starlette 的上层封装**（W6 主线伏笔：路由/中间件都是 Starlette 提供）。
3. extras 在树里肉眼可见兑现：`(extra: standard)` / `(extra: bcrypt)`。

### 面试问法："依赖冲突怎么办？为什么不能同时装两个版本的同一个包？"

**30 秒答案**："Python 的 import 是按模块名找的，site-packages 是扁平命名空间，同一个包名只能有一份，所以依赖必须解算成全树单一版本。冲突时解算器会回溯找共同满足的版本；实在解不出就得升级/替换某个直接依赖，或者用隔离手段——vendoring、独立虚拟环境、或者把冲突的部分拆成独立服务。这也是为什么依赖越少越好的实际理由：每个新依赖都在给未来的解算空间加约束。"

**追问链**：
- 追问①："传递依赖的版本由谁决定？" → 解算器（uv/pip 的 resolvelib），按约束求满足全树的解；直接依赖的约束是硬约束，传递依赖可协商。
- 追问②："依赖地狱怎么缓解？" → 减少依赖、优先选零依赖或依赖少的库、定期 `uv lock --upgrade` 小步升级、CI 里跑测试。
- 追问③（深）："uv 为什么比 pip 快很多？" → Rust 实现 + 并行下载 + 全局内容寻址缓存（同一个包跨项目复用，硬链接进各 venv）+ 更快的解算算法；pip 是串行、每次下载解压到 venv。
- 追问④："虚拟环境隔离的是什么？" → 只隔离 site-packages 和脚本目录，不隔离标准库与解释器；所以 C 扩展的 ABI 兼容仍跟 Python 版本绑定。

## 6. 易错点速查

| 坑 | 教训 |
|---|---|
| 把 uvicorn 本体当成"可选" | `uvicorn[standard]` 里 uvicorn 必装，`[standard]` 才是配件 |
| 以为 lock 可以不入库 | 不入库 = 放弃复现性与 hash 校验 |
| 用 `>=` 约束 0.x | 0.x minor 可破坏，实际等于放开 |
| 生产用普通 `uv sync` | 应用 `--frozen`，让不一致暴露而不是被修好 |
| dev 工具写进 `[project.dependencies]` | 会被所有使用者装上，应进 `[dependency-groups]` |

## 7. 30 秒答案集（考前速背）

1. **pyproject 四块** → project（对外契约）/ dependency-groups（dev 工具）/ build-system（打包）/ tool.*（工具配置）。
2. **pyproject vs lock** → 愿望（区间）vs 现实（全树精确 + hash）。
3. **lock 进 Git 的理由** → 复现性 + hash 防篡改；不提交就随时间漂移。
4. **`--frozen`** → 只按 lock 装，不一致报错（CI/生产防漂移）。
5. **extras 干嘛的** → 别人包的可选配件，进发布元数据。
6. **0.x 风险** → minor 可破坏；靠 lock 钉住 + 升级时跑测试。
7. **全树单一版本原因** → Python 命名空间扁平，同包名只能一份。
8. **uv 为什么快** → Rust + 并行 + 全局内容寻址缓存 + 快解算。

5. `--frozen` 只用 lock、不重解算、不一致直接报错；CI 要暴露漂移而不是悄悄修正。
