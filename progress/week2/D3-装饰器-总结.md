## 1. 本质：`@` 只是语法糖

```python
@decorator
def foo(): ...
```

**完全等价于**：

```python
def foo(): ...
foo = decorator(foo)     # 把函数当参数传进去，返回的东西替换掉 foo
```

**装饰器 = 接收函数、返回函数的函数。** 就这一句。

推论：装饰器不"修改"函数，它**用新对象替换名字绑定**——所以它能换成任何可调用对象（函数、类实例、类本身）。

## 2. 闭包：装饰器的地基

```python
def make_adder(n):
    def adder(x):
        return x + n     # n 来自外层
    return adder

add5 = make_adder(5)     # 外层已返回
add5(3)                  # 8 —— n 还在，因为闭包记住了它
```

`adder.__closure__` 里能翻出那个 cell（存着 n）。**栈帧被"劫持"延长了寿命**——这和生成器暂停时保住局部变量是同一机制。

### 经典坑：闭包捕获变量，不捕获值

```python
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]          # [2, 2, 2]  不是 [0,1,2]！
```

三个 lambda 共享**同一个** `i` cell，循环结束时 `i` 是 2，所以三个都返回 2。

两种修法：

```python
funcs = [lambda i=i: i for i in range(3)]   # A：默认参数，定义时求值复制
def make(i): return lambda: i               # B：工厂函数，每次新闭包
funcs = [make(i) for i in range(3)]
```

## 3. 两层装饰器模板（必须默写）

```python
import functools

def 装饰器名(fn):                      # 第 1 层：接住原函数（定义时执行一次）
    @functools.wraps(fn)               # 保住 __name__ / __doc__ / __wrapped__
    def wrapper(*args, **kwargs):      # 第 2 层：每次调用实际走这里
        # ① 调用前做事（日志 / 计时开始 / 权限检查）
        result = fn(*args, **kwargs)   # ② 调用原函数
        # ③ 调用后做事（日志 / 计时结束）
        return result                  # ④ 把结果还回去
    return wrapper
```

**比喻**：第 1 层 = 装修工人（进场一次装门）；第 2 层 = 防盗门（以后每次进出都经过）。

**三个必须记住的点**（每个都真实踩过）：

| 要点 | 忘了会怎样 |
|---|---|
| `@functools.wraps(fn)` | `__name__`/`__doc__`/签名丢失；**FastAPI 把 `*args/**kwargs` 当必填 query → 全接口 422**（Day7 实测） |
| `*args, **kwargs` | 只能装饰固定签名的函数，换一个就 TypeError |
| `return result` | 被装饰函数的返回值变成 `None` |

### 为什么 `wraps` 会引发 422（面试案例）

FastAPI 注册路由时会 `inspect.signature()` 读取参数签名做请求校验。装饰器返回的是 `wrapper(*args, **kwargs)`——如果不 `wraps`，FastAPI 看到的就是"有两个必填参数 `args`、`kwargs`"，于是把它俩当成 query 参数，**所有请求都缺参 → 422**。

`functools.wraps` 会把 `__wrapped__` 设为原函数，`inspect.signature` 顺着 `__wrapped__` 找到真实签名——签名恢复，422 消失。

> **一句话**：装饰器会"篡改函数身份"，`wraps` 是恢复身份的唯一正确姿势。

## 4. 三层：带参装饰器

```python
def retry(times):                  # 第 1 层：接收装饰器参数
    def decorator(fn):             # 第 2 层：接收被装饰函数
        @functools.wraps(fn)
        def wrapper(*a, **kw):     # 第 3 层：真正调用
            ...
        return wrapper
    return decorator

@retry(times=3)                    # ← 有括号：先调 retry(3) 拿到 decorator
def flaky(): ...
```

**口诀**：`@` 后面**有括号 → 三层**（多的一层只为先把参数吃进来）；**没括号 → 两层**。

**为什么多一层**：`@retry(times=3)` 先执行 `retry(times=3)`，返回值才是真正的装饰器——所以第一层不是装饰器，是"装饰器工厂"。

## 5. 类装饰器

```python
class CountCalls:
    def __init__(self, fn):
        functools.update_wrapper(self, fn)
        self.fn, self.count = fn, 0

    def __call__(self, *a, **kw):
        self.count += 1
        return self.fn(*a, **kw)
```

对象只要实现 `__call__` 就能当函数调用，也就能当装饰器。**适合需要保存状态**（计数器、缓存、熔断器）。

**类装饰器 vs 函数装饰器**：

| | 函数装饰器（闭包） | 类装饰器（`__call__`） |
|---|---|---|
| 状态存放 | 闭包 cell（`nonlocal`） | 实例属性（更直观） |
| 可读性 | 嵌套多了难读 | 状态多时更清晰 |
| 性能 | 略快 | 每次调用多一层 `__call__` |
| 典型场景 | 日志/计时/重试 | 计数器、缓存、状态机（熔断） |

## 6. 两个执行时机（实测）

### 6.1 装饰在定义时执行一次，函数体在调用时才执行

```
定义阶段：  [装饰器执行中] 正在包装 hello     ← 只一次
调用阶段：  [调用时] 进入 hello / hello 执行   ← 每次
```

与 D1 的 import 机制同源：**装饰器在 import 阶段就执行**，所以它用到的名字必须已导入。FastAPI 也靠这一点在启动时扫描全部路由。

### 6.2 多装饰器：从下往上包，从上往下执行

```python
@a
@b
def f(): ...     # 等价于 f = a(b(f))

# 输出：A 进入 → B 进入 → f → B 退出 → A 退出    （洋葱结构）
```

**中间件栈同理**：`trace`（最外层）包 `exception`（内层）——请求先过 trace，异常从内层往外冒。

## 7. 手写验证（timer）

```python
def timer(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        start_time = time.perf_counter()
        result = fn(*args, **kwargs)
        cost = time.perf_counter() - start_time
        print(f"[{fn.__name__}] 耗时 {cost:.4f}s")
        return result
    return wrapper
```

验收 4 项全过：耗时正确 0.1007s / 返回值 `done` 透传 / `__name__` 仍是 `slow` / 套在带参函数 `add(2,3)` 上也得 5。

### 为什么用 `perf_counter` 不用 `time.time`

- `perf_counter()` 是**单调时钟**，专门测耗时，精度最高，不受系统时间调整影响
- `time.time()` 可能被 NTP 校时**往回跳**，算出负耗时
- 同理 `datetime.now()` 不适合测耗时（Windows 上 3.11 精度只有 15.6ms，实测踩过）

## 8. 面试问法 + 30 秒答案

### 8.1 "讲一下装饰器的原理"

**30 秒答案**："装饰器本质是接收函数返回函数的高阶函数，`@` 只是语法糖，等价于 `foo = decorator(foo)`。它靠闭包记住原函数，返回一个 wrapper 在调用前后插入逻辑。带参数的装饰器要多一层——先调一次收参数、返回真正的装饰器。两个工程要点：必须用 `functools.wraps` 保留原函数的名字和签名，否则框架按签名做参数校验会出错，FastAPI 就会把 wrapper 的 `*args` 当成必填参数导致全接口 422；**必须 return 原函数的返回值**，漏了返回值就变 None。"

### 8.2 "装饰器和闭包什么关系？"

**30 秒答案**："装饰器是闭包的应用。外层函数接住参数（或者被装饰的函数），内层函数通过闭包引用它，所以被装饰函数名被替换成 wrapper 之后，原函数依然活着、能被调用。闭包捕获的是变量不是值，所以循环里创建多个闭包会共享同一个变量——`lambda: i` 那个经典坑就是这么来的。"

## 10. 和项目的联系

| 装饰器 | 项目里的位置 |
|---|---|
| 两层无参 | `@app.get(...)` 路由注册（"注册 + 返回原函数"） |
| `@wraps` | 所有自定义装饰器必写 |
| 洋葱顺序 | 中间件栈：`trace` 在外，`exception` 在内 |
| 带参三层 | `@app.middleware("http")`（括号里是参数 → 三层） |
| 类装饰器 | 限流/熔断器（要存计数状态） |

## 11. 30 秒答案集（考前速背）

1. **装饰器是什么** → 收函数返函数的高阶函数；`@` = 赋值语法糖。
2. **闭包捕获什么** → 变量（cell），不是值；循环里共享变量是经典坑。
3. **两层模板四步** → 事前 / 调原函数 / 事后 / return。
4. **wraps 作用** → 保留 `__name__`/`__doc__`/签名（`__wrapped__`）；不写 FastAPI 全 422。
5. **有括号三层** → 工厂 → 装饰器 → wrapper。
6. **执行时机** → 装饰器定义时执行一次；wrapper 每次调用。
7. **多装饰器顺序** → 下包上执行，洋葱。
8. **perf_counter** → 单调时钟测耗时，不受 NTP 影响。
