## 1. 异常链：`raise ... from ...`

### 1.1 三种形态（实测）

| 写法 | traceback 长相 | 存到哪 | 用途 |
|---|---|---|---|
| except 块里裸 `raise 新异常` | `During handling of the above exception, another exception occurred` | `__context__` | 隐式链，Python 自动记录 |
| `raise 新异常 from 原异常` | `The above exception was the direct cause of ...` | `__cause__` | **显式声明因果**，可编程读取 |
| `raise 新异常 from None` | 只有一段 traceback | `__cause__ = None` | **断链**，对外藏内部细节 |

**关键认知**：不写 `from` 也不会丢链——Python 把"当前正在处理的异常"自动塞进 `__context__`。`from` 的价值是**语义升级**：显式声明"我是因为它的直接原因才抛的"，且 `__cause__` 可被程序读取（日志/告警可用）。

### 1.2 `from None` 的两面

对外 API 不想暴露内部实现（数据库表名、文件路径、密钥片段）时断链；
**风险**：把自己排查需要的证据也藏了——所以只在"对外响应"断，日志里仍要记原始异常。

### 面试问法："异常链有什么用？"

**30 秒答案**："保留完整因果证据。排查 500 时不只是看到一个 RuntimeError，还能看到真正炸掉它的是 FileNotFoundError 还是连接超时。不写 `from` Python 也会自动记录到 `__context__`，但 `from` 是显式声明直接原因、写进 `__cause__`，语义更清楚也能被代码读取。反过来 `from None` 可以断链，用于对外接口不暴露内部实现细节——但日志里要保留原始异常，否则以后排查没证据。"

## 2. 自定义异常体系（kb-service 的设计）

```python
class AppError(Exception):
    code: str = "APP_ERROR"        # 对外错误码（前端契约）
    http_status: int = 400         # 翻译规则住在异常自己身上
    message: str = "请求处理失败"

    def __init__(self, message=None, *, detail=None):
        self.detail = detail       # 结构化上下文（日志可查）
        super().__init__(self.message)

class NotFoundError(AppError):     # 子类只改三个类属性
    code = "NOT_FOUND"
    http_status = 404
    message = "资源不存在"
```

### 三个设计点

1. **状态码住在异常身上**：翻译函数只写一次 `exc.http_status`，没有 `if isinstance(...) 404 elif ...` 长串。**加新异常 = 加一个子类，翻译代码零改动**（开闭原则）。
2. **`detail` 带结构化上下文**：日志可查、响应可给前端（注意脱敏）。
3. **基类兜底**：`except AppError` 一把抓住所有业务异常，`ValueError`/`TypeError` 这类程序 bug 不会被误捕。

### 分层职责（背下来）

```
service 层：只 raise 领域异常（不 import fastapi）
API 层：    exception_handler 统一翻译成 HTTP 响应
CLI 层：    except AppError → stderr + return 2（D6 里做过）
```

**谁抛异常、谁翻译成协议 —— 这是接口边界，必须手写一遍的部分。**

### 面试问法："你会怎么设计项目里的异常体系？"

**30 秒答案**："一个基类 AppError 携带对外错误码、HTTP 状态码和默认消息，业务异常继承它只改类属性；service 层只抛领域异常、不 import 任何 Web 框架；最外层统一翻译——HTTP 项目用 exception_handler，CLI 用退出码。这样加新异常只需要加一个子类，翻译层不用改。基类还能兜住所有业务异常，同时让 ValueError、TypeError 这类程序 bug 不被误捕，保持 500 和 4xx 的边界清晰。"

## 3. except 只抓该抓的

```python
# ❌ 一刀切：业务异常也被吞掉重新包装
except Exception as exc:
    raise RuntimeError(f"失败: {exc}") from exc

# ✅ 明确列举你真正能处理的
except (json.JSONDecodeError, KeyError) as exc:
    raise BadRequestError("文档内容不是合法 JSON") from exc
```

**判据一句话**：写 `except` 之前问自己——*这个异常发生了，我有什么办法？*
有办法（重试/降级/翻译成业务错误）才抓；没办法的让它炸，炸得越早越好。

### 为什么一刀切危险（真实案例）

`__init__` 拼成 `__int__` → `ForbiddenError(detail=...)` 抛 TypeError → 被 `except Exception` 接住 → 翻译层 `isinstance(err, AppError)` 认不出 → **403 静默变 500**。

危险不在"范围大"，在**业务错误和程序 bug 混进同一口锅**：一个本该 403 的越权，变成了看起来像服务器崩了的 500，排查方向全错。

### 面试问法："except Exception 有什么问题？"

**30 秒答案**："它把'我能处理的业务异常'和'我处理不了的代码 bug'混在一起。真要一刀切，4xx 会退化成 500，而且掩盖真正的缺陷——我踩过一次，`__init__` 拼错成 `__int__`，抛的 TypeError 被 except Exception 吞掉，最后用户看到 500 而不是 403。正确做法是明确列出能处理的异常类型，再翻译成领域异常；最外层可以有一个兜底的 Exception 处理器，但它的职责是记日志 + 返回 500，不是把异常藏起来。"

## 4. 异常机制的完整语法（面试常被追）

```python
try:
    ...
except (A, B) as exc:      # 多类型；as 绑定
    ...
except C:
    ...
else:                       # try 没抛异常才执行
    ...
finally:                    # 无论如何都执行（清理）
    ...
```

- **`else`**：把"只在成功路径执行"的代码放这里，避免被 except 误捕（常见错误：try 里塞太多代码，把后续逻辑的异常也接了）。
- **`finally`**：资源归还（关闭文件/连接/`reset` ContextVar Token）。`finally` 里不要 `return`——会吞掉正在传播的异常。
- **EAFP vs LBYL**：Python 风格倾向 EAFP（先做，出错再处理），如 `try: d[k] except KeyError` 而非 `if k in d`；但**并发/昂贵操作**要 LBYL 或加锁，否则有 TOCTOU 竞态。

| 4 | 类内缩进 3 空格和 4 空格混用 | IndentationError；全文件统一 4 空格 |

## 6. 核心 API 速查

| API | 用途 |
|---|---|
| `raise X from y` | 显式异常链，`y` 存入 `__cause__` |
| `raise X from None` | 断链，藏内部细节 |
| `e.__context__` / `e.__cause__` | 编程式读取异常链 |
| `traceback.print_exc()` | 打印完整调用栈（比 print(e) 多行号与帧） |
| `traceback.format_exc()` | 拿字符串（适合写日志） |
| `isinstance(err, BaseClass)` | 按"是不是这一族"判断 |
| `sys.excepthook` | 全局未捕获异常钩子（进程级兜底） |
| `ExceptionGroup`（3.11+） | 一次抛多个异常（`except*` 处理） |

## 7. 30 秒答案集（考前速背）

1. **异常链三种** → 裸 raise（`__context__`）/ `from`（`__cause__`）/ `from None`（断链）。
2. **自定义异常设计** → 基类带 code/http_status/message + detail；子类只改类属性。
3. **谁翻译** → 最外层（HTTP handler / CLI 退出码）；service 不 import 框架。
4. **何时捕获** → 问"我能做什么"；有办法才抓。
5. **except Exception 风险** → 业务错误与程序 bug 混锅，403 → 500。
6. **print(e) vs print_exc** → 只有消息 vs 完整调用栈。
7. **finally 里别 return** → 会吞掉正在传播的异常。

## 8. 追问链（面试深挖预演）

| 起点 | 追问 | 你要能答 |
|---|---|---|
| 异常链 | `__context__` 和 `__cause__` 区别？ | 隐式（处理期间发生）/ 显式（`from` 声明） |
| 自定义异常 | 为什么不继承 ValueError？ | 语义与边界：业务异常要能被统一捕获、携带状态码；混用内置类型会让 except 语义模糊 |
| 捕获策略 | 什么时候用兜底 except？ | 只在进程/请求边界：记日志 + 返回 500，绝不吞掉继续跑 |
| EAFP | 和 LBYL 怎么选？ | 常规 Python 用 EAFP；有并发/昂贵副作用时用 LBYL 或加锁防 TOCTOU |
| 性能 | try/except 有开销吗？ | 零成本异常（zero-cost）：没抛时几乎无开销；抛时展开栈代价大，别用异常做流程控制 |
| 3.11 | ExceptionGroup 解决什么？ | 并发/批量任务多个异常同时发生时，用 `except*` 分组处理 |
| 可观测 | 异常里该带什么？ | 错误码、上下文（detail）、trace_id；**不要带敏感信息**（密钥/密码/完整 SQL） |
