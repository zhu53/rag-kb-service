# W2-D4 异常体系 · 知识点总结

> 复习材料标准：核心 API 表 + 实测数据 + 坑 + 闭卷自测。
> 本文所有结论都在 kb-service 的 Python 3.11 下实测过。

## 一、异常链：`raise ... from ...`

### 三种形态（实测）

| 写法 | traceback 长相 | 存到哪 | 用途 |
|---|---|---|---|
| except 块里裸 `raise 新异常` | `During handling of the above exception, another exception occurred` | `__context__` | 隐式链，Python 自动记录 |
| `raise 新异常 from 原异常` | `The above exception was the direct cause of ...` | `__cause__` | **显式声明因果**，`__cause__` 可编程读取 |
| `raise 新异常 from None` | 只有一段 traceback | `__cause__ = None` | **断链**，对外藏住内部细节 |

### 面试 30 秒版本

> "异常链保留完整因果证据。排查 500 时不只看到 RuntimeError，还能看到真正炸掉它的 FileNotFoundError。`from` 是显式声明因果，`from None` 用于对外接口不想暴露内部实现细节的场景。"

## 二、自定义异常体系（kb-service `core/exceptions.py` 的设计）

```python
class AppError(Exception):
    code: str = "APP_ERROR"        # 对外错误码（前端契约）
    http_status: int = 400         # 翻译规则住在异常自己身上
    message: str = "请求处理失败"

    def __init__(self, message=None, *, detail=None):
        self.detail = detail       # 结构化上下文（日志可查）
        super().__init__(self.message)

class NotFoundError(AppError):     # 子类只改三个类属性
    code = "NOT_FOUND"
    http_status = 404
    message = "资源不存在"
```

### 三个设计点

1. **状态码住在异常身上**：翻译函数只写一次 `exc.http_status`，没有
   `if isinstance(x, NotFoundError): 404 elif ...` 一长串。
   **加新异常 = 加一个子类，翻译代码零改动** —— 开闭原则
2. **`detail` 带结构化上下文**：日志可查、响应可给前端
3. **基类兜底**：`except AppError` 一把抓住所有业务异常，
   `ValueError`/`TypeError` 这类程序 bug 不会被误捕

### 分层职责（背下来）

```
service 层：只 raise 领域异常（不 import fastapi）
API 层：    exception_handler 统一翻译成 HTTP 响应
谁抛异常、谁翻译成 HTTP —— 这是接口边界，必须手写一遍的部分
```

## 三、except 只抓该抓的

```python
# ❌ 一刀切：业务异常也被吞掉重新包装
except Exception as exc:
    raise RuntimeError(f"失败: {exc}") from exc

# ✅ 明确列举你真正能处理的
except (json.JSONDecodeError, KeyError) as exc:
    raise BadRequestError("文档内容不是合法 JSON") from exc
```

**判据一句话**：写 `except` 前问自己——*这个异常发生了，我有什么办法？*
有办法（重试/降级/翻译成业务错误）才抓；没办法的让它炸，炸得越早越好。

### 为什么一刀切危险（本次实战案例）

`__init__` 拼成 `__int__` → `ForbiddenError(detail=...)` 抛 TypeError →
被 `except Exception` 接住 → 翻译层 `isinstance(err, AppError)` 认不出 →
**403 静默变 500**。危险不在"范围大"，在**业务错误和程序 bug 混进同一口锅**。

## 四、本次踩的坑

| # | 坑 | 教训 |
|---|---|---|
| 1 | `__init__` 手打拼成 `__int__`（连错两次，描述 bug 时又拼成 `__inite__`） | **dunder 名永远 IDE 补全，不手打**。`__int__` 是合法名，三道检查全不报错 |
| 2 | 越权测试用 `kb1`/alice（owner 就是自己） | 测试数据要先问：这条真的触发目标分支吗？ |
| 3 | `traceback.print_exc()` 放进 except 块 | 正常业务异常（404/403）也打印一大串。放 `translate` 的 500 分支，只有意外异常才看调用栈 |
| 4 | 类内缩进 3 空格和 4 空格混用 | `IndentationError: unexpected indent`。全文件统一 4 空格 |
| 5 | `translate(err: AppError)` 注解写错 | 应为 `Exception`——这个函数的存在意义就是接住"不是 AppError"的东西 |

## 五、核心 API 速查

| API | 用途 |
|---|---|
| `raise X from y` | 显式异常链，`y` 存入 `__cause__` |
| `raise X from None` | 断链，藏内部细节 |
| `e.__context__` / `e.__cause__` | 编程式读取异常链 |
| `traceback.print_exc()` | 打印当前异常完整调用栈（比 `print(e)` 多行号） |
| `isinstance(err, BaseClass)` | 按"是不是这一族"判断，配合异常基类 |

## 六、闭卷自测（先答，再折叠对照）

<details>
<summary>1. 不写 from，异常链会丢吗？</summary>

不会。Python 自动把"当时正在处理的异常"存进 `__context__`（traceback 里显示
"During handling..."）。`from` 的意义是显式声明因果（存 `__cause__`），
语义更清晰且可编程读取。
</details>

<details>
<summary>2. service 层为什么不直接 raise HTTPException？</summary>

分层依赖方向：service 不 import fastapi。业务异常可单测（不起 FastAPI）、
可换框架、状态码翻译集中在 exception_handler 一处。
mini_api C3 复刻的就是这套。
</details>

<details>
<summary>3. `from None` 用在什么场景？风险是什么？</summary>

对外 API 不想暴露内部实现（如数据库表名、文件路径）时断链。
风险：把自己排查时需要的证据也藏了——所以通常只在"对外响应"断，
日志里仍要记录原始异常。
</details>

<details>
<summary>4. 怎么区分"该抓"和"不该抓"的异常？</summary>

问"发生了我有什么办法"。有办法处理（重试/降级/翻译成业务错误）才抓；
没办法的（程序 bug）让它炸——fail-fast，炸在开发期比线上半死不活好。
</details>

<details>
<summary>5. `except Exception` 里 print(err) 和 traceback.print_exc() 的区别？</summary>

print(err) 只有异常类型和消息；print_exc() 打印完整调用栈（哪一行 raise、
经过哪些帧）。排查 500 必须用后者——你要的是"在哪炸的"，不是"炸了句什么话"。
</details>
