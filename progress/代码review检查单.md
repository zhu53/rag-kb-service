# 代码 review 方法论（与技术栈无关）

> 适用于任何语言、任何项目、任何人写的代码。不含具体框架与库。
> 两种对象各有一套落点：**看代码用 §一–§七，看模块用 §八**。
> 本周的具体案例在 `progress/weekN/D*-实测记录.md` 里，那才是它们该待的地方——案例会腐烂，方法不会。

---

## 一、先定清楚：review 在判断什么

不是"代码写得对不对"（语法、类型、命名是工具的事），是判断三件事：

1. **它承诺什么** —— 契约
2. **承诺被破坏时，会响还是会静** —— 失效模式
3. **破坏了以后我能不能发现** —— 可观测性

这三问换个语言照样问，所以它是方法；"这个参数该传 `True` 还是 `False`"，是知识，会过期。

---

## 二、契约三件套

任何函数、接口、服务都能拆成三样：

| | 是什么 | 例子（抽象） |
|---|---|---|
| **前条件** | 调用之前必须为真的东西 | 输入非空、已登录、已持锁、调用方先写过 A |
| **后条件** | 返回之后保证为真的东西 | 返回值已排序、副作用已落盘、失败时不改状态 |
| **不变式** | 整个过程永远成立的东西 | `计数 == 明细条数`、两侧金额之和为常数 |

**动作**：把这三样逐条写出来，每条问一句——

> **"谁在保证它？"**

答案只允许三种：代码自己检查、调用方保证、外部系统保证。

- 说得出出处的 → 这条暂时安全
- **说不出来的 → 这就是 bug 的温床**

这个问法把"看起来对"变成"有出处"。AI 写错的地方，几乎全是它默认某个前提成立，而那个前提没有任何人在维护。

---

## 三、失效模式分三档，决定你先看哪

| 档 | 表现 | 危险度 | 处理顺序 |
|---|---|---|---|
| **硬失败** | 立即抛错、崩溃、测试红 | 最低 | 最后看——它会自己找人 |
| **静默错误** | 结果错了，不报错，日志干净 | **最高** | **第一个查** |
| **延迟失败** | 小数据对、量大/并发/时间久了才错 | 高 | 第二个查 |

审查顺序：**静默 > 延迟 > 硬失败**。

理由很硬：硬失败有反馈回路，会被人发现；另外两种没有反馈，可以一直错下去。一次错误的写入、一个少算的计数，在日志里和正常请求长得一模一样。

**这条也是排优先级唯一的通用依据**：review 时间永远不够，先看"错了不响"的路径。

## 四、四种通用手段（不需要读懂全部逻辑）

### 1. 前提审计

列出代码假设的所有前提 → 每个问"谁保证" → 再问"它不成立时会怎样"。

第三问最关键：**报错、还是算出一个错的值**。前者安全，后者是静默错误。

### 2. 变异探测

改一个东西，看有没有人喊：

- 删掉一行 → 行为变了吗（不变 = 装饰、冗余、或根本没执行到）
- 把某个常量改大改小 → 有没有边界崩
- 把两个步骤的顺序换一下 → 还成立吗（不成立 = 有隐含顺序依赖）
- 把断言里的期望值故意改错 → 测试会红吗（**不红 = 这个测试没在测东西**）

没人喊，说明那里没有防线，不是说明那里没错。

### 3. 反例构造

专挑"不该出现"的输入：

空 / 空集 / 零 / 负数 / 重复 / 超长 / 自己上一次的输出 / 两个同时到达 / 请求中途断开

正常路径写得再好也说明不了什么——**错误都住在不正常的那一侧**。

### 4. 时间轴推演

把三个事件插进流程的任何缝隙，重看一遍：

- **进程在这里死掉**，已做的部分留下什么
- **另一个实例同时在跑**，谁覆盖谁
- **同一步被重试一次**，会不会做两遍

不需要真的并发，纸上推一遍就能发现大部分。

## 五、十二问

不依赖语言，可以对着任何一段代码问：

1. 它被调用**两次**会怎样？
2. 它**永远不被调用**会怎样？（死代码，或者漏了调用）
3. 执行到一半**崩掉**，已完成的留下什么？
4. **两个实例同时**跑，谁覆盖谁？
5. 输入是**它自己上一次的输出**，会不会漂移？
6. 值是**空 / 空集 / 超长**时，走哪条分支？
7. **谁读这个值**？读的人需要什么保证？
8. 这个常量明天要改，得改**几处**？（>1 处就是耦合）
9. 这段**删掉**，谁会发现问题？
10. 出问题时，**日志里能看到什么**？
11. 三个月后改这块的人需要知道什么，**代码里写了吗**？
12. **这段代码假设了什么外部事实？谁在维护那个事实？**

第 12 问是总纲，其余十一问是它的展开。

## 六、别人的代码，尤其是 AI 的代码，看什么不一样

同一个人写久了自己会有一套习惯，所以"风格怪"往往不是错。**换成一个没有习惯、只会模仿的生成者，错的分布会变**：

- 语法、命名、注释、类型标注会**异常漂亮**——这些是模仿得来的
- 错集中在**它无法验证的那一层**：外部系统真实行为、默认值的求值时机、被调用时的环境、量级变化后的性能

所以对生成代码，**"看起来专业"不是可信度信号，反而是危险信号**：越像高级写法、越解释得头头是道，越要问"这个前提谁保证"。

判断不了的时候只有两个合法动作：**查文档**，或者**实测一次**。二者都不做就接受，等于把判断权交出去了。

## 七、能力边界（这条比方法重要）

> **review 能力的上限 = 判断力上限，不是阅读速度。**

看不出错，通常不是眼睛不够快，而是**不知道"对"依赖哪些前提**。所以：

- 一个模块你读不懂它的失败模式 → 先补那个领域的失效方式，再 review
- 补不了 → 只能守到"能跑"这一层，并且**明确知道自己在守哪一层**

承认"这段我看不出对错"，比假装审过一遍有价值得多。

## 八、换个对象：引入一个外部模块时

前七节审的是**代码对不对**。引入一个外部依赖，审的是另一个轴：**这个决定能不能反悔**。

代码是自己的，错了改就是；模块不是。所以同一套骨架照用，但要再加四问。

### 8.1 骨架照搬，但问的东西变了

| 原方法 | 换成"引入一个模块" |
|---|---|
| 契约：它承诺什么 | 它的**公开承诺**是什么，**没承诺什么**（文档没写的部分，是你要自己兜的） |
| 前条件谁保证 | 它假设的运行环境：版本、编码、时区、并发模型、是否允许多实例——**这些由谁保证** |
| 失效三档 | 更要紧，因为你对它的失效一无所知。失败时抛错、返回空、还是返回一个错的值？超时后**部分成功**怎么算？ |
| 变异探测 | 反向探：故意违反它文档里的一句话，看它是否真报错。不报 → 那条"承诺"是假的 |
| 时间轴推演 | 加了它之后：进程重启、连接断、并发、重试，各会怎样 |

### 8.2 加的四问

1. 它承诺什么？**没承诺什么？**
2. 它失效时我这边是**立即知道**，还是**算出一个错的值**？
3. 三个月后要换掉它，我要改**几处**？
4. 它的**维护状态、传递依赖、许可证**，查过了吗？

第 2 问还是老三档（**静默最危险**）。第 3、4 问是新的，它们不属于代码 review——属于**依赖风险**。

- **可逆性**：它只被一个薄封装包住 → 换的成本低；业务代码到处直接引用它 → 换 = 重写
- **带进来什么**：多几层传递依赖、有没有后台线程/连接池/定时器（会和你的生命周期、事务边界打架）、要不要本地编译、许可证是否传染
- **值不值得**：引入一个依赖 = 承接它全部的失败模式 + 升级义务 + 安全补丁义务。有时自己写 50 行更便宜

### 8.3 实操：先探针，后集成

引入之前花 20 分钟写一个**最小探针**，只验证你最不确定的那**一条**承诺，再决定要不要引。

- 文档说"自动管理连接" → 30 行并发跑一次，看它是否真管理
- 文档说"支持事务" → 中途抛异常，看它是否回滚
- 文档说"结果按相关度排序" → 给一组已知答案，看顺序对不对

**探针不追求覆盖，只追求打掉那条"如果错了整个方案就废"的假设。**

### 8.4 可逆性要落在结构上，不是态度上

引入时就把调用面收进一个**端口**（定义"我需要什么能力"的接口），实现放在单独的适配层；业务层只依赖端口，不依赖那个具体模块。

这样换实现只改一个文件——这是"可逆"在代码里的唯一可靠形态。写在文档里的"以后可以换"不算。

---

## 九、压缩成两句话

> **看代码：这段代码假设了什么？谁在保证它？它失效的时候，我会不会知道？**
>
> **看模块：它没承诺什么？换掉它要改几处？它失效的时候，我会不会知道？**

两问落点相同：**静默失效优先**。
