## Bug #1 · `split_text` 参数非法

- **现象**：把 `if overlap >= chunk_size:` 改成 `if overlap > chunk_size:` 之后，用 `chunk_size=400, overlap=400` 调用 `split_text` 会抛 `ValueError: range() arg 3 must not be zero`，异常位置在 `doc_service.py:79`（`for start in range(0, len(text), step)`），**不是**在 76 行的校验处。
- **定位过程**：在 `doc_service.py:77`（`step = chunk_size - overlap`）打普通断点，用 pytest 跑 `split_text("x" * 1000, chunk_size=400, overlap=400)`。停住后 `Alt+F8` 求值 `chunk_size - overlap` 得到 `0`；按 `F8`（Step Over）执行第 77 行，Variables 面板里 `step` 变成 `0`；再 `F8` 到第 79 行，第二次 `F8` 立刻抛异常。**全程没读代码，靠观察变量值定位**。
- **根因**：校验条件少了一个等号。合法条件是 `overlap < chunk_size`（即 `step = chunk_size - overlap > 0`），写成 `overlap > chunk_size` 就放过了 `overlap == chunk_size` 这个边界，此时 `step == 0`。而 Python 的 `range(start, stop, step)` 规定 step 不能为 0——因为它无法推导"下一个起点"，所以构造时直接抛 `ValueError`。
- **补充（为什么这个 bug 隐蔽）**：`_parse_sync` 里参数是写死的 `chunk_size=400, overlap=50`（`doc_service.py:62`），所以**走 HTTP 接口永远触发不到**，只能从函数入口（测试或直接调用）才能复现。这教会一件事：**边界 bug 往往藏在"当前调用方不会传的参数"里**，光测接口测不出来，必须单测函数本身。
- **修复**：`if overlap >= chunk_size: raise ValueError("overlap 必须小于 chunk_size")`

## Bug #2 · 删掉 `SECRET_KEY` 后的报错时机

- **现象**：`.env` 里 `SECRET_KEY=` 留空后重启，服务**根本起不来**，uvicorn 直接退出，控制台打印：
  ```
  pydantic_core._pydantic_core.ValidationError: 1 validation error for Settings
  secret_key
    String should have at least 16 characters [type=string_too_short, input_value='', input_type=str]
  ```
  浏览器访问任何接口都是连接被拒绝（不是返回 500）。
- **定位过程**：`Ctrl+Shift+F8` 打开 Breakpoints 总览，勾选 **Any Exception**；然后用 🐞 启动调试。程序在启动阶段停住，Frames 面板显示：
  ```
  Settings.__init__ / model_validate      ← pydantic 内部
  Settings()                              ← config.py:45
  get_settings()                          ← config.py:44
  health.py / 或 main.py 里第一次调用 get_settings()
  ```
  堆栈最底部是**应用启动时**的调用，不是某个请求的 handler。
- **根因**：`config.py:26` 定义 `secret_key: str = Field(min_length=16)`，pydantic-settings 在 `Settings()` **被实例化时**立刻校验。而 `get_settings()` 被 `@lru_cache` 修饰，意味着它是在**第一次被调用时**才真正构造 `Settings`；这个"第一次"发生在应用启动期间导入模块、注册路由的过程中。所以校验失败 → 进程启动失败。
- **关键问题：为什么这样设计？**
  这是**快速失败（fail-fast）**原则。配置错误属于"部署事故"，不是"运行时错误"：
  - 如果启动时不校验，空 `secret_key` 会让服务"健康"地跑起来，但所有 JWT 签发/校验都失效——要么 token 全错，要么更糟：用空密钥签的 token 可被任何人伪造，这是**严重安全事故**。
  - 启动即崩 → 部署流水线立刻红灯 → 5 秒内发现问题；运行时才发现 → 可能已经带着空密钥对外服务了几小时。
  - 对比：`DATABASE_URL` 这类"连接失败型"配置无法在启动时验证（要真连一次才知道），所以通常是启动时建连接池 + 健康检查兜底。**能静态校验的一律启动时校验**。
- **修复**：恢复 `.env` 里的 `SECRET_KEY`（长度 ≥16）。

## Bug #3 · 路由里删掉 `kb_id` 参数

> ⚠️ **原文档写错了**：它说会看到 422。实测是 **500 + `NameError`**。原因见下——这个纠正比原实验本身更有价值。

- **现象**：把 `create_doc` 的 `kb_id: UUID,` 注释掉后：
  1. **应用启动完全正常**，`create_app()` 不报任何错；
  2. 请求 `POST /api/v1/kbs/{某个uuid}/documents` 返回 **500**，日志里是 `NameError: name 'kb_id' is not defined`，位置在 `documents.py:21` 的 `DocService().create(kb_id, ...)`。
- **定位过程**：先用异常断点（Any Exception）在调试模式下触发请求，程序停在 `NameError` 抛出点；Frames 面板自下而上看：
  ```
  create_doc (documents.py:21)          ← 出错在这一层，业务函数体里
  run_endpoint_function (fastapi/routing.py:372)
  ...
  ```
  注意堆栈里**没有任何 pydantic / request validation 的帧**——说明不是框架校验拦下的。
- **根因**：两层原因叠加。
  1. **Python 是动态语言**：函数定义时不检查函数体引用了哪些名字，只在**执行到那一行**时才去名字空间查。所以删掉参数不会导致定义/导入失败，只在真正调用时报 `NameError`。
  2. **FastAPI 的路由注册靠函数签名（`inspect.signature`）**：删掉 `kb_id` 参数后，FastAPI 不再把它当作路径参数来解析，**请求体里也没人填这个值**——函数体里裸写的 `kb_id` 就变成了未定义名字。框架层完全无感，因为它只保证"签名里声明过的参数都有值"。
- **对比：什么时候才是 422？**
  422 出现在**参数声明了、但请求没给/给了非法值**的时候，由 FastAPI 的 `RequestValidationError` 在**进入函数体之前**拦下。实测（`GET /api/v1/kbs/not-a-uuid`）：
  ```json
  {
    "code": "VALIDATION_ERROR",
    "message": "参数校验失败",
    "detail": [
      {
        "type": "uuid_parsing",
        "loc": ["path", "kb_id"],
        "msg": "Input should be a valid UUID, invalid character: found `n` at 0",
        "input": "not-a-uuid",
        "ctx": { "error": "invalid character: found `n` at 0" }
      }
    ]
  }
  ```
  关键点：
  - 外层 `code` / `message` 是**本项目自己的统一包装**（异常处理器加的），不是 FastAPI 原生格式——原生只有 `detail` 数组。这一点在面试里能区分"用过 FastAPI"和"配过 FastAPI"。
  - `detail` 是**数组**，因为一次请求可能有多个字段同时校验失败。
  - `loc` = `["path", "kb_id"]`：出错位置，`path` 表示路径参数（对比 `body` / `query` / `header`）。
  - `type` = `uuid_parsing`：pydantic 的错误类型码，可以直接拿去前端做细化提示。
- **两者区别一句话**：**422 = 框架在门口拦下（函数体没跑）；500 = 已经进了函数体，业务代码里炸了**。前者是客户端错误（4xx），后者是服务端错误（5xx）——把 4xx 写成 5xx 是 API 设计事故，因为客户端会以为是服务挂了而盲目重试。

## 附加：Depends 源码跟踪笔记

> Day2 的任务 2.2 第 3 条，Step Into 走一遍 `get_current_user_id` → `decode_access_token`。
> 写下你看到的调用顺序（3-5 行即可）：

1. **框架层**：FastAPI 拿到 `GET /api/v1/kbs` 请求后，先读 `list_kbs` 的函数签名，发现 `user_id: UUID = Depends(get_current_user_id)`，于是**在进入函数体之前**先执行依赖。
2. **deps 层**：`get_current_user_id(credentials=...)` 被调用（`deps.py:30`），`HTTPBearer` 已经把 `Authorization: Bearer xxx` 头解析成了 `HTTPAuthorizationCredentials` 对象，所以这里直接取 `credentials.credentials`。
3. **security 层**：`decode_access_token()` 执行（`security.py:39`），走到 `jwt.decode(token, settings.secret_key, algorithms=[settings.algorithm])`。
4. **第三方库**：`python-jose` 的 `jwt.decode` → `jws.py` 里 `_verify_signature`，内部先按 `.` 把 token split 成 `header / payload / signature` 三段，base64url 解码，再用 HS256 重新计算签名比对。
5. **回到路由**：所有依赖解析完毕，`list_kbs` 函数体才开始跑（`knowledge_bases.py:28`），此时 `user_id` 已经是 `UUID` 对象、不是字符串。

**观察到的证据**：在 `knowledge_bases.py:28` 停住时，Variables 面板里 `user_id` 已经**有值**。这就是"依赖先于函数体执行"的直接证据，不需要看框架源码也能确认。

**一句话总结（面试可直接说）**：FastAPI 在路由函数执行前，按函数签名递归解析依赖树；`Depends` 在同一次请求内默认缓存结果（同一依赖被多处引用只算一次），解析失败就抛异常、根本没机会进业务代码。

## 自测 5 问（Day2 §6.2）我的答案

> 标准：**不看文档、不看代码**，能口头说清楚才算过。写下来是为了月末复习。

**1. Step Over（F8）和 Step Into（F7）的区别？**
F8 把当前**整行**当成一个黑盒执行完，遇到函数调用也不进去；F7 遇到函数调用会**钻进被调用函数的第一行**。
判断标准：我只关心"这行执行完变量变了吗" → F8；我怀疑"问题在函数内部" → F7。
**坑**：F7 遇到第三方库也会钻进去。这就是为什么调 `jwt.decode` 要先用 Shift+F7 选目标，或者干脆在目标库文件里打断点。

**2. PyCharm 里 F5 是什么？和 VS Code 有什么不同？**
PyCharm：**F5 = 重新启动调试**（Restart），继续执行是 **F9**（Resume）。
VS Code：**F5 = 启动/继续调试**（Continue），重启是 `Ctrl+Shift+F5`。
**这个差异是 PyCharm 新手最容易踩的坑**——在 VS Code 里按 F5 想继续，到 PyCharm 里按 F5 会反复重启，看起来像"程序死循环了"。

**3. 什么时候该用条件断点？**
- 循环里只想在第 N 次停（`Condition: i == 500`）
- 只想在特定输入的请求上停（`Condition: str(kb_id).startswith("f")`）
- 1/1000 概率的偶现 bug——普通断点等不到，条件断点精准命中
- 高频接口（QPS 100+）根本没法手动按 F9，必须靠条件过滤
**本质**：把"人肉筛选"变成"程序筛选"，条件是求值为 `True` 才暂停。

**4. Frames 面板解决什么问题？**
回答"我是怎么走到这一步的"。它展示**当前线程的完整调用栈**，从当前函数一路回溯到 `main`。
三个实战用途：
- **定位异常的抛出层级**：异常断点停住后，看 Frames 能立刻判断是 services 层抛的，还是 api 层抛的（今天 Bug #2/#3 就是这么做的）
- **看清参数从哪来**：点 Frames 上层的帧，像时间旅行一样看到它传下来的参数值
- **判断是不是框架代码在调我**：堆栈里一堆 `starlette` / `fastapi` 的帧，说明是框架驱动过来的
**注意**：点不同帧，Variables 面板的内容会跟着变——因为每个帧有自己的名字空间。

**5. `Evaluate Expression`（Alt+F8）能做什么 print 做不到的事？**
- **不改代码、不重启**：print 要先改源码、保存、等热重载、重新发请求，一次 30 秒；Alt+F8 是 1 秒
- **能执行任意语句**，包括临时计算：`len([k for k in store.kbs if k.int % 2 == 0])`——不可能为这个专门加 print
- **能调方法看副作用**：`settings.model_dump()` 看整个配置对象
- **作用域是当前栈帧**：能直接访问局部变量（这是 print 做不到的，print 只能打印你写死的表达式）
**今天踩的坑**：求值 `store.kbs` 报 `NameError`——因为 `store` 是另一个模块的全局变量，**不在当前帧的名字空间里**。要么用完整导入路径，要么先切到 Frames 里对应的帧。**`Evaluate Expression` 不是全局控制台**。
