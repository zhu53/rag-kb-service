### 1. uv 和 pip 的核心差异（说三条）

1. **速度**：uv 用 Rust 编写，依赖解析和安装速度比 pip 快一个数量级。
2. **锁文件**：`uv.lock` 记录完整依赖树（含传递依赖的精确版本 + hash），保证"我这里能跑、你那里也能跑"；pip 默认只有 requirements 的手工 pin。
3. **它同时管 Python 版本**：`uv python install 3.11` 能装解释器，pip 只管包。
4. （加分）**workspace 支持**：一个仓库多个包统一管理依赖，pip 需要额外工具。

> 面试如果被追问"conda 呢"：conda 强在**二进制与非 Python 依赖**（CUDA、CUDA toolkit），科学计算场景有优势，但依赖解析慢、环境重。**AI 项目常见组合：uv 管 Python 包 + conda 管 CUDA**。

### 2. `[dependency-groups]` 与 `[project.dependencies]` 的区别

- `[project.dependencies]`：**运行期必需**的依赖。用户 `pip install 你的包` 时会一起装。
- `[dependency-groups]`（PEP 735，取代旧的 `[project.optional-dependencies]` 用法）：**开发/测试期**依赖，默认不装，需要 `uv sync --group dev` 显式指定。

**为什么 dev 依赖不能进主依赖**：用户装你的库不该被迫接受 ruff、mypy、pytest 这些几百 MB 的工具链；而且测试工具版本冲突会污染使用方环境。这是"依赖最小化"原则。

### 3. `ContextVar` 与 `threading.local` 的区别

| | `threading.local` | `ContextVar` |
|---|---|---|
| 隔离单位 | 线程 | **执行上下文**（可理解为协程/task） |
| 异步场景 | ❌ 一个线程跑 100 个协程会互相串数据 | ✅ 每个 task 独立 |
| 传播方式 | 自动随线程 | 自动沿 `await` 传播；`asyncio.create_task` 会**复制**当前上下文 |

**为什么异步框架必须用 ContextVar**：uvicorn 在一个线程里用事件循环调度成千上万个协程。如果用 `threading.local` 存 `trace_id`，A 请求的 trace_id 会被 B 请求读到 —— 日志全乱，这是生产事故级别的 bug。

> 补充：`asyncio.to_thread` 会把当前 context 复制到新线程，所以 ContextVar 在线程池里也能正确传播。

### 4. 不加 `@wraps` 的装饰器会导致什么

装饰器本质是 `f = decorator(f)`，如果不加 `@functools.wraps`，返回的 `wrapper` 会**丢失**原函数的 `__name__`、`__doc__`、`__module__`、`__wrapped__`、以及签名（`inspect.signature` 看到的是 `(*args, **kwargs)`）。

**FastAPI 场景的具体后果**：
1. 所有被装饰的路由函数 `__name__` 都变成 `"wrapper"` → **OpenAPI 里 operationId 冲突**，自动生成的客户端 SDK 直接报错/覆盖。
2. FastAPI **靠函数签名解析参数**（`Depends`、`Query` 的来源）。签名丢了 → 参数解析失败或全部退化成必填 body。
3. 依赖注入缓存 key 基于函数对象，名字重复可能造成缓存错乱。

正确写法：
```python
def timer(fn):
    @functools.wraps(fn)
    async def wrapper(*args, **kwargs):
        ...
    return wrapper
```

### 5. `dataclass` 里 `items: list = []` 为什么报错

`@dataclass` 生成 `__init__` 时，会把默认值作为**函数默认参数**。而函数默认参数在**函数定义时求值一次**——所有实例会共享同一个 list，改一个全变（经典的 mutable default argument 陷阱）。

Python 3.11+ 的 dataclass 会直接抛 `ValueError: mutable default <class 'list'> for field items is not allowed: use default_factory`。

正确写法：
```python
items: list[str] = field(default_factory=list)
```

### 6. `Protocol` 与 ABC 的适用场景

- **ABC（抽象基类）**：**名义子类型**。必须显式继承 `class X(MyABC)`。适合"我控制全部实现类，且要提供共享的模板方法"。
- **Protocol**：**结构化子类型**（静态鸭子类型）。只要方法签名对得上就算满足，无需继承。适合"给第三方库对象加类型约束"或"定义插件接口"，避免侵入式继承。

一句话记忆：**ABC 管"你是谁"，Protocol 管"你能做什么"**。本项目 `Storable` 用 Protocol，所以 `UserDoc`/`NoteDoc` 不用继承任何东西也能被 mypy 接受。

### 7. `asyncio.gather` 某个协程抛异常，其余会怎样？

- **`gather`（默认 `return_exceptions=False`）**：第一个异常会立刻向上传播，但**其余协程不会被取消**，会继续在后台跑（event loop 不关闭的前提下），产生"任务泄漏"和难以跟踪的日志。
- **`TaskGroup`（Python 3.11+）**：结构化并发。任一子任务异常 → 其余任务**被取消**，`__aexit__` 聚合为一个 `ExceptionGroup`（可用 `except*` 拆开）。

结论：新代码优先用 `TaskGroup`；`gather` 适合"全部必须成功，任一失败即整体失败"的场景。

### 8. `rebase` 与 `merge` 的本质区别

- `merge`：**保留分叉历史**，生成一个 merge commit（两个父提交）。
- `rebase`：把当前分支的提交**逐个重放到目标分支顶端**，历史变成一条直线，但**提交 hash 全部改变**。

**绝对不能用 rebase 的场景**：分支已经推到远端且**有别人在基于它工作**。因为 hash 变了，别人的历史会与你分叉，只能 `push --force`，而 force push 会覆盖别人的提交。团队规则：**只 rebase 自己未共享的本地提交**。

### 9. `justMyCode: false` 意味着什么

默认 `true` 时调试器只跟踪你自己的工作目录代码，第三方库（fastapi、starlette、pydantic）会被当成黑盒，Step Into 会直接跳过去。
设为 `false` 后可以**进入第三方源码逐行执行**，这是研究框架实现（比如 Depends 解析、中间件调用链）最快的方式。

代价：异常堆栈会包含大量库内部帧，噪音变多。

### 10. 业务异常体系相比到处 `raise HTTPException` 好在哪

1. **解耦**：`services/` 层不需要 `import fastapi`，将来换框架（Litestar、Django Ninja）业务代码不动。这是分层架构的核心收益，面试高频。
2. **响应契约统一**：所有错误走同一个 handler，`{code, message, detail}` 结构一致，前端只需写一份错误处理逻辑。
3. **可测试**：service 层单测只需 `pytest.raises(NotFoundError)`，不用构造 HTTP 请求。
4. **语义清晰**：`NotFoundError` / `ForbiddenError` 比 `HTTPException(404)` 更接近业务语言，也避免"把 500 写成 400"这类低级错误。

### 11. pydantic 配置校验失败发生在启动时还是请求时？

发生在**应用启动时**（准确说：`Settings()` 第一次实例化时，本项目通过 `lru_cache` 的 `get_settings()` 触发，而它在 `create_app()` 里被调用）。

**对线上部署的意义**：这是**好事**——配置缺失/非法会让进程立刻启动失败，而不是等用户请求进来才 500。容器编排（K8s/Docker）会看到容器反复重启，问题立刻暴露在部署阶段，而不是线上流量阶段。

反面案例：用 `os.getenv("SECRET_KEY")` 且不校验，配置缺失时服务能起来，但一签发 token 就崩 —— 这就是典型的"启动时该失败却没失败"。

### 12. 换成 MySQL 要改哪些文件？

**要改**：
- `repositories/base.py`（删掉内存 store）
- `repositories/kb_repo.py`、`repositories/doc_repo.py`（改成 SQLAlchemy 查询）
- 新增 `models/`（ORM 实体）、`core/db.py`（引擎/Session 依赖）
- 新增 `alembic/`（迁移）
- `main.py`（注册 session 清理依赖）

**不用改**：
- `services/*`（**只要 Repository 的方法签名不变**，业务逻辑一行不动 —— 这就是 Repository 模式的价值）
- `api/*`、`schemas/*`、`core/exceptions.py`、`core/logging.py`
- `tests/`（只要保留 `conftest.py` 里换 fixture 的入口，用例断言不用动）

> 面试讲法："我换持久化实现时，业务层零改动，因为我在 `services` 和 SQLAlchemy 之间隔了一层 Repository，service 只依赖接口不依赖 ORM。" —— 这句话直接对应"依赖倒置原则"。
