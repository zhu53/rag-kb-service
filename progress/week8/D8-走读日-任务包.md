## §六 沿途五个"为什么"（B，能自己答出来的打勾）

这五个是这条链上最容易被追问、也最容易答错的地方。

1. `get_current_user` 在 `router.py:18` 挂了一次，`documents.py:27` 签名里又写一次——**重复了吗？**
2. `_parse_sync` 同步跑（要等它完才返回 201），`run_index` 却丢进 BackgroundTasks——**凭什么一个同步一个异步？**
3. 全线 `flush` 五次、`commit` 一次——**flush 和 commit 到底差在哪？**
4. `incr_doc_count` 用 SQL 表达式而不是 `+= 1`——**省下来的那个窗口，具体是什么故障？**
5. `db.py:9` 的 `expire_on_commit=False`——**如果改成 `True`，哪一行会出问题？**

<details>
<summary>点开看答案（先自己写，写完再对）</summary>

1. **不重复，两处各有职责**。`router.py:18` 是**兜底**：保证这个 router 下任何一条路由都进不了门，就算将来有人加路由忘了写签名也不会漏。`documents.py:27` 是**取值**：函数体要用 `user["id"]`（`documents.py:30`）。FastAPI 的依赖缓存按 (callable, 参数) 缓存，同一次请求里同一个 `get_current_user` 只跑一遍——所以查库还是 1 次。
   > 反过来有个值得记住的推论：**把 `router.py:18` 删掉，测试不会红**，因为还有签名那处。这就是"测试抓不到"的典型——重复的保护让变异体的杀伤力归零。（此条已实测：三处 router 级依赖全删 → 108 passed / exit 0。）

2. **判据是"失败了用户还该不该看到成功"**。chunk 切分和落库是**业务结果**：切不出来就不是一篇可用文档，必须返回失败。索引是**可延后的副作用**：索引没建好，文档本身还在，下次能重建，所以不该让用户等 0.3 秒、也不该因为它失败就把 201 改成 500。
   更深一层：`run_index` 是同步函数，FastAPI 会把它丢进线程池跑；如果它是 `async def` 且里面 `time.sleep`，就会堵住事件循环。

3. **flush = 发 SQL，commit = 划事务边界**。flush 之后 SQL 已经在事务里执行了，但别的连接看不到；commit 才让它可见且不可回滚。所以 11–13 步之间任何一步抛异常，`get_db` 的 `except`（`db.py:16-18`）会 rollback，前面所有 flush 全部作废——这是"文档和 chunk 要么都有要么都没有"的保证来源。
   注意一个坑：`get_db` **不做兜底 commit**，只 rollback + close。commit 全靠 service 显式喊（`doc_service.py:52`）。所以"忘了 commit"的症状是接口返回 200 但库里没数据——静默失败，测试不查库就抓不到。

4. **丢更新（lost update）**。`obj.doc_count += 1` 是"读 → 算 → 写"，两个并发请求都读到 5，都写 6，结果应该是 7 却变成 6。SQL 侧 `doc_count = doc_count + 1` 在数据库内部一次完成，不存在中间窗口。
   这条和 D3 债④ 是同一个思想的两面：**内存里的对象状态和库里的行不是一回事**。债④ 是"改完没 flush 就取快照"，这条是"别在内存里算增量"。

5. `expire_on_commit=False` 让 commit 后对象属性**不过期**。改成 `True` 时，commit 一结束对象属性就失效，下次访问要重新 SELECT——`kb_service.py:56-60`（update 后 `row` 来自 flush 后快照）和 `doc_service.py:53`（覆盖快照再返回）这类"commit 之后还用对象"的地方就会各多一次查询；如果 commit 之后 session 已经关了再访问属性，会抛 `DetachedInstanceError`。
   > **本条是推理，未实测**（2026-11-24 未跑）。想验很简单：把 `db.py:9` 改成 `expire_on_commit=True`，跑一次门禁看哪条红、红的是什么错。这个实验值得你自己做一遍——它是"改一行配置看连锁反应"的最小样本。
   > 顺带把 D3 的坑串起来：`kb_repo.update` 里如果只 `setattr` 不 flush，返回的快照 `updated_at` 还是旧值（差 15ms 那次）。**对象属性 ≠ 库里那一行**，这句话在三个地方以三种形式出现。

</details>

## §九 五道自测题（A，40 分钟，不看代码）

题目先看，答案折叠在最后。**不许边答边翻代码**，也不许翻 §四 的表。

3. 一条请求里 `get_current_user` 被调用几次？如果某条路由同时写了 `Depends(get_current_user)` 和 `Depends(require_role("admin"))`，查库几次？

5. 上传接口返回体里 `status` 是 `"ready"`。如果哪天有人把 `doc_service.py:52` 的 `_commit()` 挪到 `_parse_sync` **之前**，会发生什么？客户端会看到什么？

<details>
<summary>点开看答案（五题全对 = 这条链路真通了）</summary>

**1.** 四处，第五处是测试：
- `schemas/doc.py`：加 `DocUpdate`（不能复用 `DocCreate`——改名不该强制传 content）
- `doc_service.py`：加 `update(doc_id, user_id, data)`，**第一件事必须是 `self.repo.get(doc_id)` 拿到 `kb_id` 再 `get_or_403`**（两跳）。漏了这一跳 = 横向越权，任何人都能改别人的文档
- `doc_repo.py`：加 `update`，改完 **先 `flush()` 再 `to_row()`**（D3 债④ 的同一个坑）
- `api/v1/documents.py`：加路由，`doc_id` 和 `kb_id` 都要在路径里
- 测试：至少一条"B 改 A 的文档 → 403"
**最容易漏的是 doc_service 那跳校验**——因为它不在函数签名里，写代码时不会提醒你。

**2.** 同一个事务。全线只有 `doc_service.py:52` 一次 commit，前面全是 flush。所以 `add_chunks` 抛异常 → `get_db` 的 `except` rollback → **doc 记录和 doc_count 增量一起消失**。这是"要么全成要么全废"的来源，也是为什么 commit 只能有一个位置。

**3.** **1 次**。FastAPI 依赖缓存按 (callable, security_scopes) 缓存，`require_role` 内层又 `Depends(get_current_user)`，指向同一个 callable → 复用结果。所以"admin 路由查两次库"是个常见误解。想验证：在 `deps.py:39` 前加一行 `print`，打一次 admin 接口看打印几次。

**4.** **不会红，什么都不会发生**。因为每条路由签名里都还有 `user: UserRow = Depends(get_current_user)`，验人照样发生。这行纯属**冗余兜底**。

> **这个结论是实测的，不是推理**（2026-11-24 20:05 真跑）：把 `router.py` 里三处 `dependencies=[Depends(get_current_user)]` 全删掉 → `pytest -q --no-cov` → **108 个点全过、2 skipped、exit 0**。所以现在的测试对"router 级兜底"**没有任何覆盖**——你可以在纸上记一句：**被测试保护住的只有"签名那处"，兜底那处删了也没人喊**。
它说明：**"测试全绿"证明不了某行代码有用**。变异体打在冗余保护上必然存活，而存活不代表代码有 bug——这正是变异测试要"人工确认盲区"的原因（`mutation_check.py` 那 4 条盲区探针就是这个道理）。面试版说法：**保护重复时，删一处测不出来，但两处都不该删——一处是契约（签名取值），一处是不变量（router 兜底）**。

**5.** `_parse_sync` 之前 commit，意味着 doc 以 `status="pending"`、`chunk_count=0` 落库；之后才切块、写 chunk、改 ready，而这些改动**没有第二次 commit** → 事务在 `get_db` 的 `finally: close()` 时被丢弃（未提交就关闭 = 回滚）。
客户端拿到的响应体是 `"ready"`（因为 `doc_service.py:53` 是内存覆盖，`53-54` 构造返回），**但库里永远是 pending**——典型的"响应和库不一致"，而且只在重启后再查才暴露。这就是"事务边界必须包住所有相关写入"的反例。

</details>
