## 交付物 1 · RefreshToken 表 + 迁移（已闭环）

- 表结构：`id` 自增 / `user_id` FK→users ON DELETE CASCADE + 索引 / `token_hash` varchar(64) UNIQUE / 三列 `datetime` / `revoked_at` 可空。
- `SHOW CREATE TABLE refresh_tokens` 四项验收全过（CASCADE、UNIQUE KEY token_hash、ix_refresh_tokens_user_id、三列 datetime）。
- 用户两次写错并修正：
  1. 三列裸 `DateTime()` 漏 `timezone=True` → 会导致与 aware `now(UTC)` 比较时 TypeError（交付物 4 实锤）。
  2. `cascade="all, delete-orphan"` 写进 `mapped_column` → 参数属于 `relationship()`，正确写法是 `ForeignKey(..., ondelete="CASCADE")`。
- 判据沉淀：**id 要不要 UUID = 这个 id 会不会暴露给外部**（refresh_tokens 是纯内部表 → 自增 int）。
- 判据沉淀：`token_hash` 唯一索引防的是"同一张票存两行"，**防不了 Q8 的"一票换两票"**（两张新票 hash 不同，各自合法）。

## 交付物 4 · `/auth/refresh` 轮换（已闭环）

**代码**：`refresh_repo.py`（`get_by_hash` / `rotate` 同事务 revoke+insert）、`auth_service.refresh`（四步拒绝链 + 轮换）、`schemas.RefreshIn`、路由。

**实锤的坑（今天最值钱）**：
```
auth_service.py:74  if row.expires_at <= datetime.now(UTC):
TypeError: can't compare offset-naive and offset-aware datetimes   → HTTP 500
```
- 机制：`DateTime(timezone=True)` 只是 SQLAlchemy 的声明，**MySQL DATETIME 不存时区、SQLite 也不保留**，读回来是 naive；写入的 aware 值在存储层被剥掉时区。
- 后果形态：本该是"票过期→401"的正常业务路径，变成 500 服务器错误。**不是安全洞，但比安全洞更容易漏**——没有探针就不会发现。
- 修法：读回后 `if not dt.tzinfo: dt = dt.replace(tzinfo=UTC)` 再比较（测试里同样需要 `_as_utc` 归一）。
- 判据：**时间带不带时区，看存储层支不支持，不看列声明写了什么。**

**HTTP 三步读数**（旧票 `jGFZ...`）：
| 步 | 操作 | 读数 |
|---|---|---|
| 1 | 旧票续票 | 200 + 新 refresh |
| 2 | 同一张旧票再来 | 401「用户凭证无效」 |
| 3 | 新票继续续 | 200 + 再换一张 |

**测试**（我写，`tests/test_refresh.py` 7 条）：签发只存 hash / 轮换+旧票重放 401 / 新 access 能打受保护接口 / 未知票 401 / 过期 401 / 封禁 401 / 四种拒绝响应体一致。

**变异验证**：`if False and row.revoked_at is not None` → 重放两条测试红 → 还原 → 全绿。

**门禁终态：118 passed, 4 skipped / 97.21%（精确浮点）/ ruff / mypy strict 全绿**

## 交付物 5 · logout（已闭环）

**代码**：`RefreshTokenRepository.revoke_by_hash`（条件 UPDATE + rowcount）、`auth_service.logout`（幂等不 raise）、`POST /auth/logout`（`status_code=204`，不挂 `get_current_user`）。

**两个判断题（用户答 2 档 / 2 档，均命中核心、缺第二层）**：
- 204 vs 200：语义答对；缺"204 是 no content 的语义承诺"与"204 下返回 body 会被**静默丢弃**"（实测：`status_code=204` + `return {"msg":"x"}` → 客户端收 `b''`，服务端不报错，前端 `res.json()` 炸）。
- 不挂 `get_current_user` 的三个理由：① 可用性（access 过期后仍要能退出）② 安全性（refresh 原文本身即持有证明）③ **封禁用户 access 一律 401 → 永远无法注销自己，票永久有效**（用户只答出①）。

**mypy 与运行时的分歧（今天第二个值钱的坑）**：
```python
row = self.session.execute(update(...))
row.rowcount   # mypy: "Result[*tuple[Any, ...]]" has no attribute "rowcount"
```
- 运行时 `type(session.execute(...))` = `CursorResult`（实测 `.rowcount` = 1 / 0，逻辑正确）。
- 静态：SQLAlchemy 把 `Session.execute` 注解成父类 `Result[Any]`，`rowcount` 只在子类 `CursorResult` 上 → mypy 只看注解，看不到运行时真相。
- 修法：`cast(CursorResult[Any], row).rowcount > 0`（实测 40 files 过 mypy）。
- 判据沉淀：**运行时对 ≠ 类型系统认；cast 是"我比静态检查器知道得多"的显式背书，不是消音器——写错类型它不救你。**

**rowcount 语义**：MySQL 的 `rowcount` 是**真正改动的行数**，不是匹配行数。条件里的 `revoked_at IS NULL` 让第二次 logout 匹配 0 行 → rowcount=0，幂等才成立；去掉条件后重复 logout 会 rowcount=1（又写了一次新时间），幂等语义当场丢失。

**测试**（我写，`tests/test_refresh.py` 尾部 3 条）：204 + `content == b""` + 库里 revoked_at 非空 + 原票 401 / 幂等（同票退两次 204、**不存在的票也 204**）/ 边界（logout 后 access 仍能打业务接口）。
**变异验证 3 次全部被杀**：不落库 → 1 红；忘 commit → 1 红；路由退回 200 → 3 红。

## 清债槽 ⑥ · doc_count 一致性（已闭环）

**测试**（我写，`tests/test_db_integration.py` 尾部 2 条 + 3 个 helper）：
- `test_document_delete_decrements_counter`：create → 另开 session 查 1/1 → delete → 再开 session 查行没了 + 计数器归零。
- `test_doc_count_conserves_against_actual_rows`：造 3 → 删中间 1 → 全删，每步断言 `doc_count == SELECT COUNT(*) FROM documents WHERE kb_id=?`。

**守恒断言的写法判据**：不写成 `assert doc_count == 3`。硬编码测"这次跑出来的数对不对"，守恒测"这个不变量有没有被破坏"——前者在改 chunk 参数、加软删除时假红，后者只在真漂移时红。

**变异验证 3 次全部被杀**：

| 变异 | 改法 | 结果 |
|---|---|---|
| A 少减 | 删掉 `incr_doc_count(row["kb_id"], -1)` | 2 条红 |
| B 多增 | `incr_doc_count(kb_id, 1)` → `2` | 3 条红（含旧的 chunks 用例） |
| C 多减 | `-1` → `-2` | 2 条红 |

**并发遗留（记 W9 债）**：串行双删因 `doc_service.delete` 先 `get` 后删，第二次 404，不会重复递减；但**并发**两个请求同时 `get` 到行 → 都执行 `-1` → 计数器变负。与 W9 债③「一票换两票」同病：**检查与写入之间有窗口**。

## 设计判断沉淀

- **滑动过期**：每次轮换新票 `expires_at = now + 7 天` → 语义是"连续 7 天不用才失效"，不是"登录后 7 天必重登"。取舍：活跃用户永不重登 vs 被盗会话可无限续命；生产通常叠加绝对上限（`session_started_at` 或 sessions 表）。→ 决策日志候选。
- **轮换带来的表增长**：每次续票留一行 revoked → 需要按 `expires_at` 的清理任务。
