## 探针：间隙锁 vs 唯一约束——"先查后插 + FOR UPDATE"到底防不防得住

**起因**：合书三问第 2 题，用户答"悲观锁防不住重复 email"，教材答案说"能防住但代价大"。分歧不口头裁定，上探针。

**场景还原**：假设删掉 email 唯一约束（保留普通索引 `idx_email` 供查询），注册改成事务内 `SELECT ... FOR UPDATE WHERE email='x'`（0 行）→ `INSERT`。A、B 两个会话并发注册同 email。

**方法**：临时表 `probe_gap`（无唯一约束），SQLAlchemy 两个连接，B 会话 `innodb_lock_wait_timeout=3`；A 先 `FOR UPDATE` 查 `'x'`（查不到），B 同时 INSERT。RR / RC 两种隔离级别各跑一遍。**隔离级别用 SQLAlchemy 的 `execution_options(isolation_level=...)` 按连接设置。**

**读数（2026-11-21，kb_dev @3307，MySQL 8.4.0）**：

| 隔离级别 | B 的 INSERT | 判定 |
|---|---|---|
| REPEATABLE READ（默认） | 阻塞 3.1s → OperationalError（lock wait timeout） | **防得住**（间隙锁锁住 `'x'` 应在的缝隙） |
| READ COMMITTED | 125ms 直接成功 | **防不住**（RC 无间隙锁，查不到=锁不到任何东西） |

**结论**：
1. 用户的"防不住"在 **RC 世界是对的**，在 MySQL 默认的 RR 世界是错的——直觉没白给，缺的是"间隙锁"这块知识。
2. 锁方案即使防得住也不该用：行为挂在**隔离级别这个隐式配置**上（静默失效三档里最阴的），且无索引时 FOR UPDATE 锁范围失控。唯一约束 = 声明式、存储引擎原子保证、不依赖任何隐式配置。
3. 教材 §4.1 已补"实测补注"框（含本表）。

**清理**：`probe_gap` 已 DROP（探针 finally 里执行）；探针脚本一次性，跑完已删。

## 债① 事故：双 handler 让变异验证"假不红"（AI 交付，19:13 发现）

**过程**：AI 代写 handler+测试 → 2 passed → 变异验证（`if True: raise exc` 恒真）→ **测试仍然 2 passed，变异不响**。

**探针读数**：变异在位时第二次同名 POST 仍返回 `409 {"message": "资源已存在或字段冲突"}`——但 AI 写的 handler 文案是「资源已存在或**唯一**字段冲突」。**文案差两个字 = 响应来自另一个 handler**。

**根因**：AI 编辑 main.py 时 Edit 异常叠加，文件里出现**两个** `@app.exception_handler(IntegrityError)`。Starlette 后注册的覆盖先注册的——测试一直打的是第二个（正确的），第一个（变异版死代码）从未被执行。变异"不红"不是测试无效，是**测试根本没测到被变异的代码**。

**教训（判据来自数据·第 5 例）**：
1. **变异验证不是仪式**——这次若跳过，恒真 raise 的死代码 handler 会永远留在文件里，且没有任何症状。
2. **"测试过了"≠"测试测的是你以为的东西"**。识别标记：响应文案与你的实现差一个词，就是另一段代码在说话。
3. Edit 工具叠加写入后，`import` 也会重复（两行 `from sqlalchemy.exc import IntegrityError`）——文件级改动后 grep 一遍目标符号是好习惯。

**修复后闭环**：清理双 handler/重复 import → 正常版 2 passed → 变异版 **1 failed（红）** → 恢复 → 全量门禁 **86 passed / 96.27% 全绿**（新增 test_integrity_409.py 两条：409 翻译 + 非唯一约束不误译）。
