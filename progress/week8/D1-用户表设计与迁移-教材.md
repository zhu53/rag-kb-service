## §零 主线定位

**这条知识在线上哪个位置**（一个带鉴权的请求从进门到落库）：

```
请求 → HTTPBearer 解 token → [D1 之前: 只验签名, sub 自报家门] → 业务层(用 sub 当 owner_id)
                              → [D1 之后: 拿 sub 查 users 表, 验存在+封禁+角色] → 业务层
                                     ↑
                              users 表 = 本周建的"户口本"
```

**一句分界线**：D1 之前，token 里的 `user_id` 是**自报家门**——`dev/token` 给谁签都行，查无此人照样放行；D1 之后，它有了**可查的户口本**。本周后面每一天（登录/RBAC/refresh）全踩在这张表上。

**前置**：如果"token 是什么、凭什么信它"说不清，先读 **§零·五**（5 分钟，含亲手拆解你项目真签出来的 token）。

## §零·五 前置知识：token 到底是什么（A）

> **这一节补的是真正的空白**：你从 W3 起就在用 `Authorization: Bearer xxx`，但没人讲过这张"票"是什么、为什么服务器信它。不补这节，本教材里"验 token 不验人""`sub` 自报家门"全是半懂。

### 0.5.1 痛点：HTTP 没有记忆

HTTP 是**无状态**的：每个请求独立到达，服务器不会自动记得"上一个是同一个人发的"。但几乎所有业务都需要"知道你是谁"。两种解法：

| 解法 | 怎么做的 | 代价 |
|---|---|---|
| **Session（服务器记）** | 登录后服务器在内存/Redis 存一份 `session_id → user_id`，把 `session_id` 发给浏览器（Cookie） | 服务器要存、要查、要清；多台机器要共享；存的就是"登录状态"本身 |
| **Token（客户端带证明）** | 登录成功后，服务器把"你是谁 + 有效期"**签个名**交给客户端；以后每个请求把这张签过名的票带上，服务器验签名就知道是谁 | 服务器**不用存**；但票一旦发出，在过期前收不回来（§0.5.4 的弱点） |

你项目用的是第二种，票的名字叫 **JWT**（JSON Web Token），算法 `HS256`，有效期 `access_token_expire_minutes = 60`（`config.py:27-28` 实测）。

### 0.5.2 最小可跑示例：亲手拆一张真票（5 分钟）

```powershell
# Windows PowerShell —— kb-service 目录
& .\.venv\Scripts\python.exe -c "from kb_service.core.security import create_access_token; from jose import jwt; t=create_access_token('11111111-2222-3333-4444-555555555555'); print('TOKEN:',t); print('段数:',len(t.split('.'))); print('不验签解码:',jwt.get_unverified_claims(t))"
```

实测输出（2026-11-21 本机，secret 未打印）：

```
TOKEN: eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMTExMTExMS0yMjIyLTMzMzMtNDQ0NC01NTU1NTU1NTU1NTUiLCJpYXQiOjE3OTUyMjMzMDYsImV4cCI6MTc5NTIyNjkwNn0.7iW4XdFIxBcHkS3SDhXeS-diebXzaSROe6K74xa5lT0
段数: 3
不验签解码: {'sub': '11111111-2222-3333-4444-555555555555', 'iat': 1795223306, 'exp': 1795226906}
```

**逐段拆开看**（`split('.')` 后 Base64URL 解码）：

| 段 | 原文示例 | 含义 |
|---|---|---|
| 第 1 段 header | `{"alg":"HS256","typ":"JWT"}` | 用什么算法签的 |
| 第 2 段 payload（claims） | `{"sub":"1111...","iat":1795223306,"exp":1795226906}` | **业务信息**：`sub`=主体（谁）、`iat`=签发时间、`exp`=过期时间（Unix 秒） |
| 第 3 段 signature | 43 个字符的乱码 | 用 `secret_key` 对"前两段"算的 HMAC-SHA256 签名 |

关键一行：**`get_unverified_claims` 不传 secret 也能读出 payload**——因为前两段只是 Base64URL **编码**（不是加密），谁拿到都能读。安全靠的是第 3 段。

### 0.5.3 机制：签名为什么防伪

```
签名 = HMAC-SHA256( "header.payload" 这段字符串 , secret_key )
```

- `secret_key` 只有服务器知道（`config.py:26`，min_length=16）。
- 攻击者改 payload（比如把 `sub` 改成别人的 id）→ 前两段变了 → 服务器重算签名 → 和第三段对不上 → `decode_access_token` 抛 `JWTError` → 返回 401。**没有 secret 就造不出合法签名**，这就是"票不能伪造"的全部原理。
- 服务器每次请求只做三件事：**验签名、看 `exp` 过没过、从 `sub` 取身份**——`security.py:61-71` 的 `decode_access_token` 就是这三件事。

一条完整请求的时间轴（背下来）：

```
登录 → 服务器签 token（sub=user_id, exp=now+60min）
     → 客户端存起来
     → 之后每个请求：Authorization: Bearer <token>
     → 服务器: HTTPBearer 取出 token → decode(验签+exp) → 拿 sub → 当 user_id 用
```

### 0.5.4 最重要的一段：签名**证明**什么、**不证明**什么

这是 W8 全部内容的出发点，一定要记死：

| 签名能证明 ✅ | 签名证明不了 ❌ |
|---|---|
| 这张票是**本服务器签发的** | 票里的那个人**现在还存在**吗 |
| 票的内容**没被篡改** | 那个人**被封禁**了吗 |
| 票**没超过有效期**（60 分钟） | 那个人**有权限**做这件事吗 |

所以"验签通过"只等于"这张票是真票"，不等于"这个人现在是合法用户"。**票是签发那一刻的身份快照**：60 分钟内，即使这个人被删号、被封禁，票依然验得过——因为服务器根本没去查任何"人"的数据，它只验了票。

> 现在回头看 §零 那句"`sub` 是自报家门"就通了：服务器信的是**票上的名字**，不是**人**。8 周后你建的 users 表，就是让服务器有地方去**核对票上的名字**。

### 0.5.5 项目的落点与 `dev/token` 的危险

| 文件:位置 | 做什么 |
|---|---|
| `core/security.py:29-34` | `hash_password` / `verify_password`（密码，与 token 无关，D2 用） |
| `core/security.py:37-58` | `create_access_token`：塞 `sub`/`iat`/`exp`，用 secret 签 |
| `core/security.py:61-71` | `decode_access_token`：验签+exp+校验载荷形状，失败抛 `UnauthorizedError` |
| `api/deps.py:22` | `get_current_user_id`：从 `Authorization: Bearer` 取票 → decode → 返回 `sub`，**不查库** |
| `api/v1/dev.py` | `POST /dev/token`：**给任何请求签任何 sub 的合法票**（仅非 prod 挂载） |

`dev/token` 为什么危险：它等于**把签名能力开放给所有能访问的人**。谁能调到它，谁就能拿到 `sub=管理员id` 的真票——签名全对、exp 有效、验签通过，系统完全无法分辨。这不是"演示端点的小问题"，是**谁掌握签发权，谁就掌握身份**。所以 W8-D2 一有真登录就必须删它。

### 0.5.6 易错点表（A）

| # | 误区 | 真相 |
|---|---|---|
| 1 | "token 是加密的，看不出来内容" | **Base64URL 只是编码**，payload 谁都能读（§0.5.2 实测）。**绝不放密码、密钥等敏感信息** |
| 2 | "服务器存着我的登录状态" | 无状态方案下服务器**什么都不存**；票就是全部凭据 |
| 3 | "token 可以像 session 一样注销" | 不能。票一旦签发，过期前一直有效——要撤销必须**额外存东西**（D5 的撤销表/刷新 token 就是为此存在） |
| 4 | "验签通过就能放行" | 验签只证明"真票"；存在性/封禁/权限**一个都没验**（§0.5.4）——这正是 W8 要补的 |
| 5 | "`exp` 是服务器自己记得过期了" | `exp` 是**票里的字段**，服务器每次验票时比对当前时间；靠的是验签保证这个字段没被改 |
| 6 | "Bearer 随便写" | 缺 `Bearer ` 前缀 HTTPBearer 直接 403，请求根本到不了你的代码 |

### 0.5.7 面试问法（A）

**30 秒版**：JWT 是服务器签发的带签名凭证，三段=header+payload+签名，payload 是 Base64 编码可读，签名用服务端密钥算 HMAC 保证不可篡改。服务端无状态，每次请求验签+看 exp 就能拿到身份，代价是**签发后无法主动撤销**。

**追问链（三层）**：
1. 一层：JWT 和 Session 怎么选？→ 横向扩展/多端/跨服务用 JWT；需要即时踢人、权限频繁变更用 Session 或短 token。
2. 二层：JWT 不能撤销怎么办？→ 短 exp + refresh token 轮换 + 服务端撤销表/黑名单（D5 实现）。
3. 三层：验签通过就够了吗？→ **不够**，签名只证明票真，不证明人在；还要查库验存在/封禁/角色（D3-D4），代价是每请求一次主键查询。

## §一 痛点：`owner_id` 查无此人（A）

打开 `models.py:24` 看 `KnowledgeBase` 的第一列：

```python
owner_id: Mapped[UUID] = mapped_column(Uuid)
```

它**不是外键**——库里没有任何一张表能回答"这个 UUID 对应谁"。它从哪来？从 token 的 `sub` 里来，而 `dev/token` 端点给**任何人**签**任意 sub** 的 token。

所以现在的鉴权状态是：

| 问题 | 现状 |
|---|---|
| "这个请求是谁发的？" | token 说是谁就是谁，**无从核对** |
| "这个用户被封禁了吗？" | **不存在"用户"这个概念**，无从封禁 |
| "谁有管理员权限？" | **没有角色**，无从区分 |

没有 users 表，鉴权的一切都是空中楼阁。这就是为什么 W8 第一天不写登录、不写 RBAC，先建这张表——**它不是"又一张表"，它是后面四天所有功能的地基**。

## §三 字段逐个讲（A）

| 字段 | 类型 | 为什么存在 |
|---|---|---|
| `id` | `Uuid` 主键 | 项目全库惯例：UUID 主键（不是自增 int）。好处：不暴露"我们有多少用户"；坏处：主键索引比 int 略大——个人项目无所谓，知道就行 |
| `email` | `String(255)` + **唯一约束** | 用户的自然标识（登录名）。唯一约束是**数据库层的**，§四讲为什么不能只靠应用层 |
| `password_hash` | `String(128)` | **存哈希不存明文**。字段名必须带 `_hash`——名字就是文档，防止后人把明文塞进来。bcrypt 输出固定 60 字符，128 给余量 |
| `role` | `String(20)`，默认 `"member"` | 角色标记，RBAC（D4）的原料。为什么是 String 不是枚举，§四讲 |
| `is_banned` | `bool`，默认 `False` | 封禁开关。**封禁后旧 token 下一个请求 401** 是本周验收指标，这一列就是它的开关 |
| `created_at` / `updated_at` | 同 `KnowledgeBase` | 全库统一：`DateTime(timezone=True)` + `datetime.now(UTC)`。别发明第二套时间写法 |

**注意**：没有 `username`、没有头像、没有昵称。**本周最小集**——要用的时候再加列（加列是 D2 之后一条小迁移的事，先加 = 提前猜测未来 = 大概率猜错）。

## §四 三个设计决策（A）

### 4.1 email 唯一约束为什么必须在数据库层

"先查后插"有个竞态窗口：

```
请求A: SELECT ... WHERE email='x@t' → 空 → 准备 INSERT
请求B: SELECT ... WHERE email='x@t' → 空 → 准备 INSERT
请求A: INSERT 成功
请求B: INSERT 成功          ← 两个同 email 用户诞生了
```

两个请求都没说谎，但结果错了——这就是"先查后插"的失效模式：**检查和写入之间有时间窗，并发下窗口必被穿过**。唯一约束把"检查"下沉到存储引擎：插入那一刻原子判定，第二个 INSERT 直接抛 `IntegrityError`。

（这正好是明天的债①：把 `IntegrityError` 翻译成 409。今天的表就是债①的靶子。）

> **实测补注（11-21，kb_dev 真机探针）**："那用 `SELECT ... FOR UPDATE` 先查后插行不行？"——**答案取决于隔离级别**：
>
> | 隔离级别 | A 事务已 `FOR UPDATE` 查 `email='x'`（0 行），B 并发 INSERT 同 email | 结果 |
> |---|---|---|
> | REPEATABLE READ（MySQL 默认） | 插入**阻塞 3.1s** → lock wait timeout | ✅ 防得住（间隙锁把 `'x'` 应在的缝隙锁住） |
> | READ COMMITTED | 插入 **125ms 成功** | ❌ 防不住（RC 没有间隙锁，查不到=锁不到） |
>
> 结论：锁方案**能防但不可靠**——行为挂在"隔离级别"这个隐式配置上，换库/换配置就**静默变样**；且 email 无索引时锁范围失控（全表）。唯一约束是**声明式**的：由存储引擎原子保证，不依赖隔离级别、不依赖"每个写路径都记得走锁"。这就是选唯一约束的完整判据。探针读数见 `progress/week8/D1-实测记录.md`。

### 4.2 role 为什么用 String 不用 Enum / 角色表

三个候选：

| 方案 | 本周 | 代价 |
|---|---|---|
| `String(20)` + Python 常量 | **选它** | 非法值靠应用层校验 |
| SQLAlchemy `Enum` | 不用 | 改角色集要改**列类型**（迁移 + 兼容风险） |
| roles/permissions 三表 | 不用 | W14 多租户/细粒度权限才需要，现在建 = 猜未来 |

判据是**可逆性**：String 是最松的约束，从 String 改成角色表 = 加表 + 改代码，列类型不用动；从 Enum 回头 = 改列类型 + 迁移。**约束从严容易，从松改严容易，从严改松难**——先松后紧是常态演进路径。

### 4.3 is_banned 为什么是布尔不是 status 枚举

"封禁"只有一个开关语义：禁/不禁。如果以后出现"暂停""冻结""待审核"多态，再加 `status` 列也不迟——**YAGNI**：你还没遇到的灵活性，一律不加。

## §五 迁移工序：四步，一步不能省（A）

```
① alembic revision --autogenerate -m "add users table"   # 生成，不是执行
② 人工审 upgrade/downgrade 两个函数                        # W7 血训：op 顺序不可信
③ alembic upgrade head                                    # 执行
④ alembic check + alembic current                         # 验证库与模型无漂移 + 版本前进
```

**为什么 ② 不能省**（W7 实测教训，两天踩了三雷）：

| 雷 | 症状 | 教训 |
|---|---|---|
| 1101 | MySQL TEXT 不许 DEFAULT | autogenerate 把模型的 `server_default` 照搬进 op → 库不接受 |
| 1553 | FK 列的索引先拆后建 → 报错 | autogenerate 的 op **排序不可信**，人工重排是必要工序 |
| 半途状态 | DDL 隐式提交 → `alembic_version` 和库结构不一致 | 失败后先看 `alembic current` 再决定重跑还是还原 |

users 表这次虽然只是"新增一张表"（无 TEXT、无 FK），雷踩不上，但**工序不变**——审的是习惯，不是这张表。另外人工审时顺手检查：autogenerate 有时会把"模型与库的历史漂移"也生成 op，**只该有 users 相关的 op，多出来的要搞清楚是什么**，不许闭眼 upgrade。

## §六 UserRepository：复用 kb_repo 模式（A）

新文件 `repositories/user_repo.py`，**逐条对照 `kb_repo.py` 的既有规约**（这是本周唯一新 repo，规约抄现成的，不发明新的）：

```python
from __future__ import annotations

from uuid import UUID

from sqlalchemy import select
from sqlalchemy.orm import Session

from kb_service.repositories.models import User
from kb_service.repositories.rows import UserRow


class UserRepository:
    def __init__(self, session: Session) -> None:
        self.session = session

    def get(self, user_id: UUID) -> UserRow | None:
        obj = self.session.get(User, user_id)          # 主键查，最短路径
        return obj.to_row() if obj else None

    def get_by_email(self, email: str) -> UserRow | None:
        obj = self.session.scalar(select(User).where(User.email == email))
        return obj.to_row() if obj else None

    def create(self, email: str, password_hash: str) -> UserRow:
        obj = User(email=email, password_hash=password_hash)
        self.session.add(obj)
        self.session.flush()                            # commit 是 service 层的事（D3 生效）
        return obj.to_row()
```

四条规约，每条都回答"谁在保证它"：

| 规约 | 为什么 | 谁在保证 |
|---|---|---|
| `flush()` 不 `commit()` | 一次请求多个写点要同生共死 | **service 层** `_commit()`（D3 的 AuthService 接管） |
| 返回 `to_row()` 快照不返回 ORM 对象 | 上层拿到的是数据不是活对象，改它不落库、容易产生"以为改了"的假象 | repo 层约定 |
| 主键查用 `session.get` | 命中 identity map 不发 SQL；语义就是"按主键" | SQLAlchemy |
| 构造只收 `session` | 测试用 override 换内存库 / 真库可控 | conftest（W6 的 `dependency_overrides`） |

`rows.py` 加一个 `UserRow`（TypedDict，含 id/email/role/is_banned/created_at——**不导出 password_hash**，它是敏感列，快照里永远不带它）。

## §九 bcrypt 冷知识（L）

passlib 的 bcrypt 实现**只取密码前 72 字节**参与哈希——超长部分静默丢弃，"密码很长更安全"在 72 字节处失效。本周不处理（注册时可限制长度），知道这个坑存在即可。

## §十 要不要给 `owner_id` 补外键（L）

`knowledge_bases.owner_id` 现在指向的 users 表存在了，理论上可以补 `ForeignKey("users.id")`。**本周先不补**：补外键 = 一条带表结构变更的迁移 + 现有孤儿数据（dev 环境手工造的 owner_id）要清理，且 D4 要先让"查用户"跑通。**记进债表，D5 收尾时决策**——可逆性角度：外键是从严约束，等数据干净了再加，比先加再拆容易。

<details>
<summary>参考答案（写完再看）</summary>

1. **查无此人**——不是外键，没有任何表能核对它的身份；解决 = 建 users 表，D4 把 `get_current_user_id` 升级为查库的 `get_current_user`。外键不顺带补：存量孤儿数据要清理 + 迁移风险，记债 D5 决策（从严约束后补比先加再拆容易）。
2. **竞态窗口**：检查（SELECT）和写入（INSERT）之间有时间窗，两个并发请求都查空、都插入成功 → 两条同 email。唯一约束把判定下沉到存储引擎，插入瞬间原子判第二个必报 `IntegrityError`。
3. **可逆性**：String 改成角色表 = 加表改代码，列不动；Enum 改回 = 动列类型。先松后紧是常态演进，从松改严容易、从严改松难。另外角色表现在建 = 猜未来（YAGNI）。
4. **生成 → 人工审 → upgrade → check/current**。审的原因：autogenerate 的 op **顺序不可信**（W7 1553：索引先拆后建报错）、可能把模型与库的历史漂移也生成 op（1101：TEXT 不许 DEFAULT）、失败会留下"库结构 ≠ alembic_version"的半途状态——审的是习惯。
5. **一次请求多个写点要同生共死**，commit 的时机只有 service 层看得见完整操作；repo 只 flush（发 SQL 拿主键），commit 归 service `_commit()`——W7-D6 就是因为漏传 session 导致 `_commit` 静默跳过，201 但 0 行。
6. **password_hash 是敏感列**，快照流向 API 返回体，带上 = 泄漏。字段命名 `_hash` 和快照剔除是同一件事的两端：名字防"塞明文进去"，快照防"带明文出来"。
7. header（算法）+ payload（claims：sub/iat/exp）+ signature。**payload 能被任何人不带 secret 读出来**（Base64URL 是编码不是加密）——不算泄密是因为里面只放"身份标识 + 时间戳"，不放密码/密钥；安全性靠签名保证内容不可篡改，不靠内容不可读。
8. **能证明**：票是本服务器签的、内容没被改、没过期（exp 未超）。**不能证明**：这个人还存在、没被封禁、有权限做这件事——票只是**签发那一刻的身份快照**，验签从不查"人"。
9. `dev/token` 让任何能访问的人拿到**任意 sub 的合法票**（签名、exp 全对）。系统只认票不认人，所以等于**谁有签发权谁就能冒充任何身份**——这不是演示端点的小毛病，所以真登录一通就必须删。
