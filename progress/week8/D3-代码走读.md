## §0 一句话目标 + 在链路里的位置

**目标**：把"验签"升级成"验人"——JWT 只证明票是真票，不证明**持票的人此刻还合法**；再在这个基础上加一层角色检查。

```
请求 → ① _bearer_scheme 取票 → ② get_current_user 解票 + 查库验人（新）
     → ③ require_role 检查角色（新，仅 admin 端点）→ ④ 路由 → ⑤ owner 校验（W7 已有）
```

今天动的是 **②** 和 **③**。①④⑤ 是原来就有的，一行没改（除了调用方签名跟着②变）。

## §2 执行顺序（为什么是这个顺序）

### 第 0 步：先看漏洞，再修（20 分钟）

```powershell
# 1) 拉起 MySQL（3307）和 uvicorn，登录拿 demo1 的 token
# 2) 用 SQL 把 demo1 封了
mysql -h 127.0.0.1 -P 3307 -u root -p kb_dev -e "UPDATE users SET is_banned=1 WHERE email='demo1@example.com';"
# 3) 拿封禁前签的 token 打受保护接口
curl.exe -H "Authorization: Bearer <旧token>" http://127.0.0.1:8000/api/v1/kbs
```

**当时的读数：封禁前后都是 200。** 这个 200 就是今天的全部动机——先让漏洞砸在脸上，改完才知道自己在修什么。修完后同一个请求必须 **401**。

### 第 1 步：`get_current_user`（核心，A 级）

```python
async def get_current_user(
    credentials: HTTPAuthorizationCredentials | None = Depends(_bearer_scheme),
    session: Session = Depends(get_db),
) -> UserRow:
    if credentials is None: raise UnauthorizedError("缺少认证信息")
    claims = decode_access_token(credentials.credentials)      # 验签 + 过期
    user_id = UUID(claims.sub)                                 # 票里的 sub
    row = UserRepository(session).get(user_id)                 # ← 新增的一步：查库
    if row is None:    raise UnauthorizedError("用户不存在")
    if row["is_banned"]: raise UnauthorizedError("账号已被封禁")
    return row
```

三个决策点，每个都能被面试追问：

1. **返回 `UserRow` 而不是 `UUID`**：下游要 role（require_role）、要 id（owner 校验），一次查库全带走。`UserRow` 本来就不含 `password_hash`（最小暴露）。
2. **多查一次库值不值**：代价 = 每请求一条主键 `SELECT`（B+ 树单行读，最便宜的查询）；收益 = **撤销能力**（封禁/删号立刻生效）。有缓存的系统会算"撤销延迟 vs QPS"，我们选即时。
3. **为什么不把 is_banned 放进 token**：放进去就得等票过期，等于封禁无效。

**替换法**：删旧函数 `get_current_user_id`，不留兼容层。这样漏改的地方会直接 `NameError`/mypy 报，而不是静默继续验签不验人。

### 第 2 步：`login` 堵口子（你手写）

`get_current_user` 修好了**用票**这一侧，但登录是**发票**那一侧：封禁用户拿密码登录还能拿到新票。

```python
row = self._repo.get_credentials_by_email(email)     # 只带 id + hash + is_banned
if row is None:
    verify_password(data.password, _DUMMY_HASH)      # 补平时序
    raise UnauthorizedError("邮箱或密码错误")
if not verify_password(data.password, row["password_hash"]):
    raise UnauthorizedError("邮箱或密码错误")
if row["is_banned"]:                                  # ← 放在密码验证之后
    raise UnauthorizedError("邮箱或密码错误")          # ← 文案逐字一致
```

**两个判断，必须能说出来**：

- **为什么扩 `UserCredentialsRow` 而不是再查一次**：同一次查询带出 `is_banned`，零额外代价；再查一次 = 两次读同一行，还多一个 None 分支。
- **为什么放密码验证之后**：放前面 = 封禁用户跳过 bcrypt（~100ms 的哈希），响应时间明显更快 → 攻击者光靠**计时**就能判断"这邮箱被封了"，文案一致也白搭。放后面 = 耗时跟正常登录一样，唯一差别在响应体。这跟 `_DUMMY_HASH` 是同一个思想：**所有失败路径在时序上不可区分**。

### 第 3 步：`require_role` + admin 路由

```python
def require_role(*roles: str) -> Callable[..., Awaitable[UserRow]]:
    async def _check(user: UserRow = Depends(get_current_user)) -> UserRow:
        if user["role"] not in roles:
            raise ForbiddenError("权限不足")
        return user
    return _check
```

机制拆解（面试必问）：

- `require_role("admin")` 在**导入/注册期**执行，返回 `_check` 函数（闭包记住 `roles`）。
- `Depends(...)` 拿到的是**未执行的函数**，FastAPI 在**每次请求时**执行它。
- `_check` 自己不查库，只 `Depends(get_current_user)`——靠**依赖缓存**（同请求同依赖只解析一次），所以哪怕三条依赖都要当前用户，`users` 表只查一次。
- 返回类型为什么是 `Callable[..., Awaitable[UserRow]]` 而不是 `Callable[[], ...]`：内层参数有 `Depends()` 默认值，调用方可以不传 → 参数列表是"任意"。mypy strict 逼你说清楚这件事。

**admin 路由**（`api/v1/admin.py`）：

```python
@router.get("/users")                    # → /api/v1/admin/users
async def list_users(_admin: UserRow = Depends(require_role("admin")),
                     session: Session = Depends(get_db)) -> ApiResponse[list[UserAdminOut]]: ...

@router.patch("/users/{user_id}/ban")    # → /api/v1/admin/users/{id}/ban
async def ban_user(user_id: UUID, _admin=Depends(require_role("admin")), session=Depends(get_db)):
    row = UserRepository(session).set_banned(user_id, True)
    if row is None: raise NotFoundError("用户不存在")
    session.commit()
    return ApiResponse[UserAdminOut](data=row)
```

两个架构判断：

- **权限挂路由级还是 router 级**：都能用。这里选逐路由声明，因为要拿到 `_admin` 行（将来"不能封自己"要用）。挂在 `router.py` 的 `dependencies=[...]` 上更省事，但拿不到人。
- **commit 为什么留在路由**：这条链没有业务规则（改一个布尔位），事务边界一眼看完；出现"不能封自己/写审计"就该抽 service。**能说出理由的分层才叫分层，说不出就是抄。**

## §3 多租户：两种 owner 校验模式（A 级，必背）

| 模式 | 位置 | 写法 | 优点 | 失效方式 |
|---|---|---|---|---|
| 一：条件进 SQL | `kb_repo.py:48` | `WHERE owner_id = ?` | 默认安全，忘传参数 mypy 就红 | 只能覆盖"能进 WHERE 的查询" |
| 二：取回后检查 | `kb_service.py:35` `get_or_403` | 先 `get`，再比 `owner_id` | 能区分"不存在"/"无权" | **靠调用纪律**：绕过它直接 `repo.get()` 不报错，静默泄漏 |

**判据句**：能进 WHERE 的 owner 条件必须进 WHERE；做不到的（按 id 直取、间接归属）必须收敛到**唯一一个检查函数**，所有路由只准通过它拿数据。检查点越少，越权面越小。

**#9 的坑**：`doc` 表没有 `owner_id`，归属是 `doc.kb_id → kb.owner_id` **两跳**推出来的。少那一跳 = 任何登录用户读任何文档，而且 200 无报错。

今天实测读数：`#4 → 403`、`#9 → 403`（两个真用户，真 token）。

## §6 面试口径

**30 秒版**：
> JWT 只保证票没被篡改、没过期，保证不了"持票的人现在还合法"。所以我把鉴权拆成两层：`get_current_user` 每个请求解票后用 sub 查一次库，封禁/删号即时生效（代价是每请求一条主键 SELECT）；权限检查用 `require_role` 依赖工厂，把角色断言收敛成依赖图的一部分，漏写 `Depends` 会直接暴露而不是静默越权。401 给"身份不成立"（含封禁），403 给"身份成立但不够格"。

**追问链（能扛到第三层就赢）**：
1. *为什么不把 role 签进 token？* → 降权/封禁要等票过期才生效；状态必须查库，token 只带 sub。
2. *每请求查库性能怎么办？* → 代价是一次主键读；同请求内多个依赖靠 FastAPI 依赖缓存只查一次；要省可以在网关加短 TTL 缓存，但要把"撤销延迟"变成明确取舍。
3. *封禁返回 401 还是 403？* → 401。判据：票此刻失效（换张票也没用），401 语义上触发重登，而封禁者重登也会被 login 挡住。
4. *不许他探测"这个邮箱被封了"？* → 文案与"密码错"逐字一致 + 封禁判断放在 bcrypt 之后，保证时序也一致。
5. *admin 端点怎么防漏？* → `require_role` 工厂单点收敛；测试同时覆盖 401（没票）和 403（角色不够），两种码分开测。
6. *横向越权怎么防？* → 两种模式：能进 WHERE 的 owner 条件进 SQL（默认安全）；按 id 直取/间接归属收敛到 `get_or_403`（靠纪律，风险更高）。doc 归属两跳，少一跳就是静默泄漏。
