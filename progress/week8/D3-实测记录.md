## 一、交付物 0 · 痛点实验（漏洞实锤）

真库 demo1（`is_banned=1`）拿旧 token 打受保护接口：

```
封禁前: 200
封禁后: 200   ← 漏洞：旧依赖 get_current_user_id 只解 token 不查库
```

**判据**：token 是"开工时签的票"，人不查库 = 封禁/改角色在线上**永远不生效**，只有 token 自然过期才失效。这就是 D3 要把"验人"从 JWT 自足改成"每请求查库"的理由。

顺路实锤：`is_banned=1` 的 demo1 **登录也照样 200**——login 没堵封禁口子，成为交付物 2 的靶子。

## 二、交付物 1 · get_current_user 红绿闭环

1. **红**：删掉旧 `override_current_user_id` 依赖后，15 条测试全 `401 用户不存在`
   ——auth_headers 的 token 指向一个库里不存在的人，真链路一开就现形。
2. **修**：conftest seed `User(id=TEST_USER_ID, ...)`，现有测试零改动、走真链路。
3. **绿**：99 passed / 96.22%。
4. **变异验证**：把 `get_current_user` 查库步骤短路 → 封禁实验复现 200 → 还原 → 401。

**mypy `Depends()` 返回 Any 的教训**：用户改了 knowledge_bases.py 1 处就说"全改了"，mypy 绿是假象——`Depends()` 在静态检查眼里是 Any，类型错配看不见。**实锤来自运行时 traceback**：`'dict' object has no attribute 'hex'`，收尾 5 处 + chat.py 漏网 1 处。
**固化判据**：依赖注入的类型对错，静态检查不背书，只有真请求能验。

** fresh session 断言教训**：seed 后总行数是 2 不是 1，StaticPool 共享连接下按 email 精确查，不断言总行数。

## 三、交付物 2 · login 堵封禁口子（用户手写）

方案对比后选 **扩 UserCredentialsRow**（同一次查询带出 `is_banned`），否掉"login 里再查一次"（两次查询 + 又一个 None 分支，纯亏）。

用户改的三处（实测核对）：

- `rows.py:58` `is_banned: bool`
- `models.py:124-129` `to_credentials_row()` 带出 `is_banned`
- `auth_service.py:35-36` 判断放在**密码验证通过之后**，文案与"邮箱或密码错误"逐字一致

**为什么放密码验证之后**：放前面 = 封禁用户跳过 bcrypt，响应时间明显偏短，攻击者靠计时就能区分"这个邮箱被封了"。放后面 = 耗时与正常登录一致，唯一差别是响应体。与 `_DUMMY_HASH` 补平时序同一思想：**所有失败路径在时序上不可区分**。

### 测试洞（门禁绿 ≠ 被保护）

用户改完代码门禁全绿，但 **tests 里没有任何封禁登录测试**——绿是因为这条路没人测。补守门测试 `test_auth.py::test_banned_user_login_401_same_as_wrong_password`：

- 注册 → 同 session 改 `is_banned=True` + commit → 正确密码登录
- 断言 401，且响应体与"密码错"响应**完全相等**（复用 D2 两条 unknown/wrong 的断言形状）

### 变异验证

```
短路为 if False and row["is_banned"]:
→ FAILED：封禁登录 200 / 密码错 401   ← 红因正是原始漏洞形态
还原 → 100 passed, 2 skipped / 96.24% 全绿
```

**固化判据**：新堵的口子必须有对应的故意破坏验证；门禁绿只说明"没测的路也没红"，不说明"路被保护住了"。

## 四、交付物 3 · require_role + admin 路由

分工：`require_role`（deps.py:45-58）**用户手写**，判断部分一次写对（TypedDict 下标 `user["role"]`、抛 `ForbiddenError` 而非 `UnauthorizedError`）。admin 路由用户写了一半后卡住，AI 收尾。

落点：`api/v1/admin.py`（GET `/api/v1/admin/users`、PATCH `/api/v1/admin/users/{id}/ban`）、`user_repo.py` `get_all_users` / `set_banned`、`schemas/auth.py` `UserAdminOut(UserOut)`、`constants.py` `TAG_ADMIN`、`router.py` 挂载。

收尾过程中实锤三个坑：

| # | 症状 | 根因 | 判据 |
|---|---|---|---|
| 1 | ruff F811 `get_all_users redefined here` | 用户先在 `user_repo.py:20` 写了一份，AI 又加一份——**Python 不报错，后者静默覆盖前者** | 同名方法重复定义只有静态检查能抓；两份实现里一份还是 1.x 的 `session.query()` |
| 2 | 全部 admin 测试 405 而非 403/401 | router 挂了 `prefix="/admin"`、路由写 `""` → 实际路径是 `/api/v1/admin`，测试打 `/api/v1/admin/users`。静态文件兜底把非 GET 翻成 **405** | 405 会伪装成"路径不存在"，其实是路径没对上；先看 `/docs` 的 OpenAPI 路径清单再猜 |
| 3 | mypy strict `Function is missing a return type annotation` | 依赖工厂返回的是"未执行的函数" | 注解写 `Callable[..., Awaitable[UserRow]]`：内层参数有 `Depends(...)` 默认值，调用方可不传 → 参数列表是"任意" |

**架构判断**：ban 链路没有业务规则（改一个布尔位），不单开 service 层，`commit` 留在路由；出现"不能封自己/写审计"这类规则时再抽 service。

## 五、交付物 4 · test_rbac（AI 代写 5 条）

`tests/test_rbac.py`：

1. member 打两条 admin 路由 → **403**（身份过了，缺权限）
2. 无票打 admin → **401**（和 403 分开测，防两种错混成一个）
3. admin 列用户 → 200，含 `is_banned`，且**不含** `password_hash`
4. 封禁闭环：注册 victim → 旧 token 200（封前有效）→ 提权 admin → PATCH 封禁 → **登录 401 + 旧 token 401**

**关键设计**：提权不改 token，只改库里 role —— 一条断言同时证明"验人查库"（改角色立即生效，不用等旧票过期）。这是 D3 全章动机的最小证据。

**覆盖率插曲**：admin 路由写完、测试还没写时覆盖率掉到 **94.15%**（< 95 门禁红）——新代码没测试，门禁会自己喊，这就是"精确浮点覆盖率"的价值（旧版四舍五入会放过）。

### 6.2 实测读数（`tests/test_rbac.py`）

```
#4 A 的 token 打 B 的 KB 详情   → 403
#9 A 的 token 打 B 的文档详情   → 403
```

两次都造了**真第二个用户**（注册 + 真 token），不伪造 sub——否则测的是"我造的 token 对不对"，不是"越权拦不拦"。

**#9 为什么必须两跳**：`doc` 表没有 `owner_id`，归属是 `doc.kb_id → kb.owner_id` 推出来的。直接 `repo.get(doc_id)` 返回 = 任何登录用户可读任何文档，且**静默**（200 + 别人的正文，没有任何报错）。

**发现的细节（记一笔，不是 bug 但不干净）**：`get_doc` 的路径参数 `kb_id` 只用于组路径，校验只走 `doc.kb_id`。所以 A 用 `/kbs/{别人的kb_id}/documents/{自己的doc_id}` 也能拿到自己的文档。没有数据泄漏（返回的仍是自己的），但路径与语义不一致；要堵的话在 `doc_service.get` 里加一句 `if row["kb_id"] != kb_id: raise NotFoundError`。

### 6.3 owner 条件契约（三行判据，进 review 检查单）

```
1. 能进 WHERE 的 owner 条件必须进 WHERE（默认安全，想漏都难）。
2. 做不到的（按 id 直取、跨表间接归属）必须收敛到唯一一个检查函数（get_or_403），
   所有路由只准通过它拿数据。
3. 间接归属（doc→kb）检查点必须跟着归属链走，不能因为"多一跳"就跳过。
判据句：检查点越少，越权面越小；静默失效（漏检查不报错）比硬失败危险一档。
```

## 七、清债槽 ④⑧

### ④ `updated_at` 返回旧值（已修 + 回归测试）

**探针（修前，红）**：

```
PATCH 回显 updated_at = 2026-11-24T11:04:36.474255
库里     updated_at = 2026-11-24T11:04:36.489634   ← 差 15ms
```

**根因**：`kb_repo.update` 改完属性直接 `return obj.to_row()`，**没 flush** → `updated_at` 的 `onupdate=lambda: datetime.now(UTC)` 还没执行，快照带的是旧值。和 W7 那条"flush 报成功≠落库"是同一族：**对象的属性 ≠ 库里那一行**。

**修**：`kb_repo.py` update 分支加 `self.session.flush()` 再取快照（commit 仍归 service 层）。

**修后（绿）**：`tests/test_kb_updated_at.py` —— 断言 PATCH 回显与 GET 回读数**是同一时刻**、且 `updated_at` 前进、`created_at` 不变。

**顺带发现**：同一个资源两种响应外壳 + 两种时间格式——`PATCH /kbs/{id}` 返回裸 `KBOut`（时间带 `Z`），`GET` 返回 `ApiResponse[KBOut]`（时间不带 `Z`）。测试里按"解析成时刻再比"处理，接口一致性欠账记入走读文档。

## 八、红区备忘

### 8.1 `mutation_check.py` 两个静默失效（都已修）

1. **锚点过期**：模板里还写着 `get_current_user_id`，重构后匹配不到 → 原来只打印 `[跳过]` 就继续，脚本照样输出"变异得分 100%"。已改成**锚点失效直接计入失败并退出码非 0**。
2. **退出码被环境钩子污染**（修 1 之后才暴露）：盲区探针全部显示"被杀死"，但手工复现同一变异是**存活**。查看 stderr 发现是宿主的安全删除钩子：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":52,"threshold":50, ...}
```

pytest 默认在系统 temp 里轮转 `pytest-of-<user>/pytest-N`，每轮删旧目录；删除数累计过 50 后被钩子拦截 → **测试全绿但进程退出码 1**。把临时目录钉到项目内也没用（钩子按整轮累计算），最终修法是 `--basetemp=<每轮新目录>`，不再触发轮转删除。

**修后读数**：`变异得分 9/9 = 100%`、`盲区确认 4/4 类改动测试门无感知`、退出码 0。

**判据（第四次同族）**：**rc 不是 0 不等于测试红**。要区分"断言红"和"环境红"，就得看 stderr 和失败尾行——所以给脚本加了 `↳ rc=… 失败尾行` 和 `↳ stderr:` 两行输出。前三次是：flush 报成功 ≠ 落库 / pytest-cov 打印 FAIL 但从不设退出码 / `[PASS]` 打印 ≠ 该段真过。

### 8.2 其余

- 真库验证（admin 封禁/解封走 `/docs`、demo1 封禁登录 401）需重启 uvicorn 读数（无 `--reload` 跑旧代码），D5 注入验收时一并做。
- 接口欠账：`PATCH /kbs/{id}` 返回裸 `KBOut`，`GET` 返回 `ApiResponse[KBOut]`，时间格式一个带 `Z` 一个不带；`get_doc` 路径参数 `kb_id` 未参与校验（不泄漏，语义不干净）。详见 `D3-代码走读.md §7`。
