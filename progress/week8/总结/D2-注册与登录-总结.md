## 二、逐个知识点讲透

### 1. 密码哈希：为什么哈希不加密

**一句话定义**：哈希是单向摘要，加密是可逆变换；密码存储只需要"能验等"，不需要"能还原"。

**为什么存在**：如果存明文或可逆密文，**拖库即得密码**——而用户到处复用密码，一次泄漏会连锁到他的邮箱、支付、社交。哈希让"数据库泄漏"退化成"密码泄漏不了"，只退化成"该站账号被撞"。第二个理由：内部人员、日志、备份、`SELECT *` 回显，任何能看到库的人都不该看到能直接登录的凭据。

**怎么用**（项目实物）：

```python
# core/security.py
def hash_password(raw: str) -> str:
    return bcrypt.hashpw(raw.encode("utf-8"), bcrypt.gensalt(12)).decode("ascii")

def verify_password(raw: str, hashed: str) -> bool:
    try:
        return bcrypt.checkpw(raw.encode("utf-8"), hashed.encode("ascii"))
    except ValueError:      # 非法哈希（不是 bcrypt 格式）→ False，不炸 500
        return False
```

**底层机制**：bcrypt 输出定长 60 字符 `$2b$12$<22字符盐><31字符摘要>`。三个数字各管一件事——`$2b$` 版本标识、`12` 是 cost（2^12 轮，约 100ms/次）、盐 22 字符**每次随机**（所以同密码两次哈希不同，彩虹表失效）。输入上限 **72 字节**：bcrypt 内部只取前 72 字节——24 个汉字（72 字节）刚好，25 个汉字（75 字节）就超；bcrypt 5.0 对超长输入**直接 raise**，不再静默截断（4.x 是截断，会带来"两个不同密码验证通过"的经典 bug）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `==` 比较哈希 | 时序差异可被逐字节试探（理论） | 用 `verify_password`（checkpw 定长比较） |
| 2 | 校验单位混用 | `max_length=72` 数字符，30 个汉字=90 字节被放行 → 500 | `len(v.encode("utf-8")) > 72` 字节校验，与限制同单位 |
| 3 | 非法哈希直接炸 | 库被写脏 → 登录接口 500，泄漏内部格式 | `try/except ValueError` → False |
| 4 | 以为盐要自己存 | 额外加一列 salt | bcrypt 的哈希串里**自带盐**，存一列就够 |
| 5 | cost 越高越好 | 12 调到 14，单次 400ms，登录接口被拖垮 | cost 是安全/性能旋钮，12 ≈ 100ms 是常见折中 |

**面试问法**："密码为什么要哈希，不能加密？"
**30 秒版**："加密可逆，密钥一泄漏等于明文；哈希单向，服务器只做'验等'不做'还原'。bcrypt 还自带每盐不同和可调 cost，把'离线爆破'的成本按 2^cost 抬高。代价是密码不可找回，只能重置——这个'不可逆'恰恰是安全性的来源。补充一点：输入上限是 72 字节，超过就是我项目里 schema 层拦的来源。"

**追问链**：
→ *"如果拖库了，攻击者拿到哈希能做什么？"* 离线暴力/字典：逐个猜、算哈希、比值。bcrypt cost=12 下每秒只能试几十个，弱密码仍然秒破、强密码几乎不可能——所以还要加密码复杂度下限。
→ *"那加盐有什么用？"* 防彩虹表和"同密码不同用户哈希相同"的批量破解。bcrypt 的盐存在哈希串里，不用单独一列。
→ *"为什么不直接用 SHA-256 加盐？"* SHA 是为速度设计的（GPU 每秒几十亿次），bcrypt 是故意慢且内存可控的 KDF。**同一个算法用在错的场景就是错的**——摘要算法不是密码算法。

### 2. 登录失败的统一响应与时序侧信道

**一句话定义**：登录失败对外只有一种答案（401 + 同一句文案），并且两条失败路径的**耗时也要一样**。

**为什么存在**：如果"邮箱不存在"和"密码错误"文案/状态码不同，攻击者就得到一个**账号枚举器**——先批量确认哪些邮箱注册过，再只对这些账号做撞库；耗时差异同样能枚举（存在分支要查库 + bcrypt 校验 ~100ms，不存在分支秒回）。所以统一文案解决"看得到的差异"，假哈希解决"算得出的差异"。

**怎么用**（项目实物）：

```python
# services/auth_service.py
_DUMMY_HASH = hash_password("dummy-password-for-timing")   # 模块级：import 时算一次

def login(self, data: LoginIn) -> str:
    creds = self._repo.get_credentials_by_email(data.email.strip().lower())
    if creds is None:
        verify_password(data.password, _DUMMY_HASH)   # 补时间，结果丢弃
        raise UnauthorizedError("邮箱或密码错误")
    if not verify_password(data.password, creds.password_hash):
        raise UnauthorizedError("邮箱或密码错误")      # 同文案、同状态码
    return create_access_token(str(creds.id))
```

**底层机制**：`bcrypt.checkpw` 的时间由 cost 决定（~100ms），与密码长度几乎无关；所以"用户不存在"时对一个固定假哈希跑一次 checkpw，两条路径的耗时就落在同一量级。`_DUMMY_HASH` 必须**模块级**——放函数里就是每次请求多花 100ms 算哈希，反而制造新的耗时差异。响应体一致性在测试里断言 `r_wrong_pw.json() == r_unknown.json()`，比断言"都有 message"更严。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只统一文案 | 耗时仍差 ~200ms，可被统计探测 | 假哈希把时间补平 |
| 2 | 假哈希放函数内 | 每次请求多 100ms，还可能反向制造差异 | 模块级常量，只算一次 |
| 3 | 假哈希验证"假密码" | `verify_password("fake", _DUMMY)` 形状错 | 用**用户输入**的 `data.password` |
| 4 | 只对"密码错"用例测 | 两条路径文案各自漂移无人发现 | 断言两个响应体**全等** |
| 5 | 在分支里 return 不同 detail | 前端能看到 `detail: "user not found"` | 统一 `UnauthorizedError("邮箱或密码错误")` |

**面试问法**："登录失败为什么要统一提示？还有什么要注意的？"
**30 秒版**："统一提示是防账号枚举——不然攻击者能先确认哪些邮箱注册过，再定向撞库。但光统一文案不够，还要统一耗时：用户不存在时也要对一个固定的假哈希跑一次校验，否则 200ms 的差异同样能被统计出来。我项目里这两件事都有测试守着，其中一条断言是两种失败的响应体完全相等。"

**追问链**：
→ *"统一了耗时，还有别的侧信道吗？"* 有：响应大小、HTTP 头、错误码；还有注册接口本身——"这个邮箱已注册"（409）也是枚举器，生产常见做法是注册也返回"已发送邮件"。
→ *"假哈希会不会被攻击者利用来拖慢服务？"* 每个失败请求固定花 ~100ms 的 CPU，这就是登录接口的成本模型；防刷要靠限流（按 IP/账号）、而不是靠去掉假哈希。
→ *"分布式的限流怎么做？"* Redis 计数（滑动窗口）+ 失败次数阶梯延迟；这也是"多节点下本地状态失效"的典型场景。

### 3. 状态码语义：401 / 403 / 409 / 422

**一句话定义**：401 问"你是谁"、403 问"你能不能"、409 问"现在这个状态冲突吗"、422 问"你给的东西格式对吗"。

**为什么存在**：状态码是**给机器读的契约**。前端/网关/监控全都按码分流：401 触发跳登录、403 提示无权限、409 提示改名、422 标红字段。用错码不是"风格问题"，而是把判断成本转嫁给所有调用方——最常见的错误是把唯一约束冲突写成 500，于是"用户重名"被当成"服务器故障"报进告警。

**怎么用**（项目实物）：

| 场景 | 码 | 谁产生 |
|---|---|---|
| 没带 token / token 无效 / 过期 | 401 | `get_current_user_id` 依赖 |
| 登录密码错 / 用户不存在 | 401 | `UnauthorizedError`（统一文案） |
| 邮箱已注册 | 409 | `IntegrityError` handler（看 `exc.orig`） |
| 密码不足 8 位 / 超 72 字节 / 多传字段 | 422 | Pydantic（`extra="forbid"` + 字段校验） |
| 知识库不属于你 | 404 或 403 | 归属检查（D5 横向越权专项） |

**底层机制**：FastAPI 里异常到状态码有两条路——**手动** `UnauthorizedError` → 全局 handler → `status_code=exc.http_status`；**自动** `IntegrityError` → 第三个 handler 按 `exc.orig` 原话判 duplicate/unique → 409，其余 `raise exc` 回 500。422 由 `RequestValidationError` handler 统一包装成 `ApiResponse(code=42200)`。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 重名/重复注册写 500 | 前端只能显示"服务器错误"，运维收到假告警 | 409 |
| 2 | 未登录写 403 | 前端不跳登录，页面空转 | 401 触发重新登录 |
| 3 | 越权（改别人的库）写 404 | 信息更少但语义含糊；写 403 又泄漏"存在" | 先定策略再统一：本项默认可 404 隐藏存在性 |
| 4 | 422 与 400 混用 | 手写 400 覆盖了框架的字段级错误 | 格式错一律交 Pydantic，不要手动 400 |
| 5 | 所有 IntegrityError 都 409 | FK 违反被当输入冲突，掩盖真 bug | 看 `exc.orig` 原话缩小范围 |

**面试问法**："说说 401 和 403 的区别，以及你项目里怎么用？"
**30 秒版**："401 是身份没确立，403 是身份成立但没权限。区别的实际意义在前端行为：401 跳登录、403 提示无权限。我项目里登录失败用 401 且两种原因统一文案，防止账号枚举；重复注册用 409，因为那是状态冲突不是格式错；越权访问我在 D5 会统一成隐藏存在性的 404。"

**追问链**：
→ *"重复注册为什么不是 422？"* 422 是"你给的格式不对"，而格式完全合法、只是库里的状态不允许——这是 409 的定义（conflict with current state）。
→ *"如果把唯一约束冲突映射成 409，会不会走漏信息（这个邮箱已注册）？"* 会，409 本身就是枚举器。取舍：注册页必须告诉用户"已注册，去登录"，所以这个泄漏是产品接受的；想彻底封住就改成"已发送邮件"式的异步注册。
→ *"多节点/分库后 409 还成立吗？"* 成立，因为判定在存储引擎；如果唯一性靠应用层查重，多节点就会漏——回到知识点 1 的判据。

### 4. PATCH 的两个 null 语义

**一句话定义**：`None` 在部分更新里是**两个意图**——"这个字段我没传"（保持原值）和"我传了，值是空"（清空），必须能区分。

**为什么存在**：PATCH 语义是"只改我给的字段"。如果实现写成 `for k, v in payload.items(): if v is not None: setattr(...)`，那么"清空描述"这个合法需求永远做不到——请求返回 200、库里值不变、**不报错、不 500、测试全绿**，只有用户发现"清不掉"。这就是债②，典型的**静默失败**。

**怎么用**（项目实物，两层配合）：

```python
# schemas/kb.py —— 拦住"name 置空"（名称必须有值）
@model_validator(mode="after")
def _reject_explicit_null_name(self) -> Self:
    if "name" in self.model_fields_set and self.name is None:
        raise ValueError("name 不能置空：改名就传新名字，不改就别传这个字段")
    return self

# repositories/kb_repo.py —— None 是合法值，照写
payload = data.model_dump(exclude_unset=True)   # 只取"客户端真的传了"的键
for k, v in payload.items():
    setattr(obj, k, v)
```

**底层机制**：Pydantic 用 `model_fields_set` 记录"哪些键是客户端给的"（构造时出现过），`model_dump(exclude_unset=True)` 只输出这些键。所以"没传 description"→ 不出现在 payload → 不动；"传了 null"→ payload 里是 `None` → 写 NULL。**判据不能是 `v is None`，必须是"在不在集合里"**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `is None` 当"没传" | 永远清不掉字段（债②） | `model_fields_set` / `exclude_unset` |
| 2 | 用 `exclude_none=True` | 同上，等价写法 | 别开这个开关 |
| 3 | 两个字段一种规则 | name 可清空，坏数据入库 | 每个字段定语义：必填字段不许 null |
| 4 | 只看 PATCH 的响应体 | 响应回显 None，库里没变，误判成功 | **GET/直查库确认**（本次 GET + MySQL 双读数） |
| 5 | 没做变异验证 | 测试和实现对不上也没人知道 | 把 `if v is not None` 塞回去，测试必须红 |

**面试问法**："PATCH 接口怎么区分'不传字段'和'传 null'？"
**30 秒版**："靠'字段是否出现在请求里'，不是靠值是否为 null。Pydantic 用 `model_fields_set` 记出现过哪些键，`model_dump(exclude_unset=True)` 只输出这些键；repo 层就不许再用 `if v is not None` 过滤。对必填字段（比如 name）传 null 要在 schema 层直接 422，因为那不是'清空'而是非法值。"

**追问链**：
→ *"为什么 name 不许 null，description 可以？"* 语义不同：name 是实体标识、有 NOT NULL 约束；description 本来就是可空列。**接口契约应当与数据约束同向**，否则总有一边在说谎。
→ *"如果前端传 `{"description": ""}` 呢？"* 那是空字符串不是 NULL——两种"空"在库里行为不同（`WHERE description IS NULL` 查不到 `''`）。要统一就得在 schema 层把 `''` 规范成 None（或反之），并写测试钉死。
→ *"部分更新还有别的坑吗？"* 乐观锁/版本号：并发两个 PATCH 会互相覆盖（丢失更新），解决是 `updated_at` 版本比对或 `SELECT ... FOR UPDATE`——接回 W7 的丢失更新。

### 5. 分层契约：谁定形状、谁做决策

**一句话定义**：schema 层只描述"数据的形状"，不读配置、不做业务决策；API 契约只暴露调用方需要的东西，不暴露存储细节。

**为什么存在**：每多一层依赖，测试和改动的成本就多一层。如果 `TokenOut` 在 schema 里读 `settings`，那么 schemas 层就依赖了 core/config——构造一个响应对象都得拖着配置走，测试里还得 mock 配置。同理，如果 `UserOut` 复用了 `UserRow`（含 `password_hash`），那么"给客户端的响应"与"存储快照"就绑死了：改动一处泄漏两处。

**怎么用**（项目实物）：

```python
# 1) expires_in 的值由"做决策的地方"填，schema 只规定形状
class TokenOut(BaseModel):
    access_token: str
    token_type: str = "bearer"
    expires_in: int            # 秒；必填，不给默认值

# api/v1/auth.py —— 路由层读配置、填值
settings = get_settings()
return TokenOut(access_token=token, expires_in=settings.access_token_expire_minutes * 60)

# 2) 契约与快照分开：UserOut 只有 id/email/role/created_at
#    （曾经误写成含 pwd_hash + sqlalchemy.Uuid，已被自查纠正）
```

**底层机制**：`get_settings()` 带 `@lru_cache`，进程内只读一次配置；**在函数体内调用**而不是模块级常量，测试里 `get_settings.cache_clear()` 才能生效（模块级会把旧值钉死）。API 层的 `uuid.UUID` 是标准库类型，换成 `sqlalchemy.Uuid` 就等于把 ORM 依赖灌进接口层——改数据库会连累改 API 契约。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | schema 里 import config | 契约层依赖配置，测试要 mock | 决策在 service/route，形状在 schema |
| 2 | 复用 ORM/存储类型 | API 契约跟着表结构漂移 | 标准库类型（`uuid.UUID`、`datetime`） |
| 3 | 响应体带敏感列 | `password_hash` 出网（哪怕不可逆） | 契约字段独立定义 + 测试断言不含 |
| 4 | 模块级 `settings = get_settings()` | 测试改配置不生效 | 函数内调用，靠 lru_cache 兜性能 |
| 5 | 给 `expires_in` 加默认值 | 两处配置各说各话 | 必填，唯一来源是 settings |

**面试问法**："你的 API 契约和数据库模型是怎么分开的？"
**30 秒版**："三层三种形状：ORM 模型对表、Row 快照对内部调用、Schema 对 API。它们不共用，因为变更频率和暴露面不同——表结构加了列不该自动出现在响应里，尤其敏感列。我项目里 `UserRow` 刻意不含 `password_hash`，`UserOut` 也不含，并且有测试断言响应体里没有任何 password 相关字段。"

**追问链**：
→ *"多写一层不是重复劳动吗？"* 是成本，但收益是"改表不等于改接口"。判据：这一层的变更频率是否不同、暴露面是否不同；两者都不同就必须分开。
→ *"什么时候可以合并？"* 内部工具、一次性脚本、字段与暴露面完全同构时。合并的代价是未来拆分时要改所有调用方。
→ *"Pydantic 的 from_attributes 算不算耦合？"* 它是"读属性"而不是"继承类型"，属于弱耦合；但如果 ORM 属性名变化，契约也跟着变——所以关键字段仍建议显式映射。

### 6. "删干净"的判据

**一句话定义**：删除是一个动作，"删干净"是一个**可复现的读数集合**——代码无残留、端点不可达、运行时真的换了。

**为什么存在**：后门 `POST /dev/token` 白给任意身份 token，多租户隔离在它面前等于零。"我以为删了"和"删了"之间的差距，是**四个位置**（模块、挂载、前端调用、测试）加**三个读数**（grep、端点、重启后的服务）。

**怎么用**（本次实物）：

| 位置 | 动作 |
|---|---|
| `api/v1/dev.py` | 删文件 |
| `main.py:86-91` | 删条件挂载块（**先改调用方再删被调方**，否则 `create_app()` 直接 ImportError） |
| `static/index.html` | 改真登录（`/auth/login` + 注册切换 + 401 回登录框） |
| `tests/test_dev_token.py` | 反转为守门测试：端点发不出票 |

三个读数：`grep -rn "dev/token" src/ static/` 0 处 → 端点 405/404 → **重启进程后**再验一遍。

**底层机制**：`StaticFiles` 挂在 `"/"`，兜住所有未匹配路径；它对非 GET/HEAD 回 **405** 而不是 404——所以"不存在的 POST"一律 405。真实服务不感知代码变化（没开 `--reload`），`pytest` 用的是**新 import 的模块**，两者不是同一个运行时。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只删文件不删挂载 | 启动 ImportError（中间态提交即坏） | 按依赖逆序：先删调用方 |
| 2 | grep 只搜 src | 前端还在调后门，页面 405 白屏 | src + static 一起搜 |
| 3 | 删了端点没删测试 | 测试红了才想起 | 测试反转为守门 |
| 4 | 用死数字判"拆干净" | 断言 404，实测 405，红 | 判"发不出票"而不是判某个码 |
| 5 | 只信 pytest | 正在跑的服务还是旧代码 | 重启后真实请求复验 |

**面试问法**："你怎么保证一个后门/旧接口真的下线了？"
**30 秒版**："三个读数：全仓库 grep 无调用、端点请求确认不可用、重启后的服务上再验一次。我项目里拆 dev token 时发现教材写的 404 实际是 405——因为静态文件路由兜住了未匹配路径，非 GET 方法回 405。所以判据改成'发不出票'，而不是死磕某个状态码；测试也改成守门用例，防它被谁加回来。"

**追问链**：
→ *"如果生产环境有灰度/多实例呢？"* 逐个实例验，或从网关层面确认路由不存在；再叠一个监控告警——该路径出现 2xx 就报。
→ *"怎么防回归？"* 守门测试（本次做法）+ CI 里的 grep 守卫（`scripts/check.py` 加一条"禁止 dev/token 字样"）。
→ *"删接口要考虑调用方吗？"* 要：先统计调用量（日志/埋点），再标 deprecated、加 sunset 头，最后删。个人项目里这一步常被跳过，但面试问"你删过线上接口吗"就需要这套流程。

## 三、30 秒答案集（脱稿背，8 条）

1. **密码为什么哈希不加密**：加密可逆、拖库即明文；哈希单向只验等，bcrypt 每盐不同 + cost 可调，把离线爆破成本抬到 2^12 倍/次。
2. **72 字节**：bcrypt 只取前 72 字节；`max_length=72` 数字符会放行 25 个汉字（75 字节），必须用 `len(v.encode())` 校验，同单位。
3. **登录统一失败**：文案统一防账号枚举；耗时也要统一（假哈希补 100ms），否则统计侧信道照样能枚举。
4. **401/403/409/422**：401 身份/403 权限/409 状态冲突/422 格式错；重复注册是 409 不是 422。
5. **PATCH 两个 null**：`model_fields_set` 判"传没传"，`exclude_unset` 只输出传了的键；repo 不许 `if v is not None`。
6. **契约分层**：ORM 对表、Row 对内部、Schema 对 API；schema 不读配置、不 import SQLAlchemy、不含敏感列。
7. **删干净的读数**：grep 0 处 + 端点不可用 + 重启后复验；先改调用方再删被调方。
8. **报告成功 ≠ 实际成功**：passlib 初始化不炸、首次调用才炸；pytest 绿不等于跑着的服务变了；响应文案对不上实现说明别人在改你的代码。

## 四、白板手写靶（必须能手写）

1. **注册链路时间轴**：Pydantic 校验 → 归一化（strip+lower）→ hash → repo.create（flush）→ service.commit → 201；失败分支 1062 → IntegrityError → 409。
2. **登录双分支**：`creds is None` → 假哈希 + 401；`verify` 失败 → 401（同文案）；成功 → `create_access_token(sub)`。
3. **`_reject_explicit_null_name`** 三行（`model_fields_set` 判定 + raise）。
4. **`verify_password` 的 try/except**（为什么非法哈希要 False 不要 500）。

## 五、事故复盘（"我以为是 X，实际是 Y"）

**故事一：passlib 的延迟爆炸。** 我以为是"装了不兼容的包 → import 就炸"（教材原话"初始化即失败"）。实际是 `CryptContext()` 初始化成功，第一次 `hash()` 才炸。差别很致命：门禁只 import 不调用，会**绿着漂到线上首次注册**。教训：**"什么时候炸"和"炸不炸"一样重要**——失效模式要按"静默 > 延迟 > 硬失败"排优先级。

**故事二：405 不是 404。** 我以为拆了路由就是 404。实际任何不存在的 POST 都是 405——`StaticFiles` 挂在 `/` 兜底，非 GET 一律 405。教训：**判据得跟实测走**，教材写的数字也是二手信息。

**故事三：测试绿 ≠ 服务变了。** 我在真实 uvicorn 上验债②，三个读数全是修前行为——因为进程是改代码之前启动的，没有 `--reload`。教训：`pytest` 是"新 import 的代码"，长驻进程是"启动那一刻的代码"，**两者不是同一个运行时**。

**故事四：删一个文件其实是四处。** 用户删了 `dev.py` 就停了，`main.py` 的 import 悬空，仓库处于"起不来"的中间态。教训：**跨文件删除按依赖逆序**，先改调用方再删被调方，且一次 commit 内完成。
