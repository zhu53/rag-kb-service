## 二、知识点详解

### 1. 认证、纵向授权、归属授权三轴

- **一句话定义**：认证答"你是谁"（验签+验人）；纵向授权答"你什么级别"（role）；归属授权答"这资源是不是你的"（owner_id 比对）。
- **为什么存在**：三轴各拦一类攻击——伪造身份（401）、越级访问 member→admin（403 竖）、同级互看（403 横）。D5 六个漏洞里 1/2/5 打第一轴，4 打第二轴，6 打第三轴。
- **怎么用**：`get_current_user`（轴一）→ `require_role`（轴二）→ `get_or_403` 的 `owner_id != user_id`（轴三）。
- **底层机制**：401 = 身份没说清（未认证）；403 = 身份说清了但不够格（未授权）。顺序永远先 401 后 403，否则无票者收到 403 等于被告知"接口存在且有门槛"。
- **易错点**：① 把 403 当 401 用（泄露接口存在性）；② 漏轴三——票、身份、角色全合法，一行 owner 比对缺失就是"合法的陌生人"；③ 横向越权守门最厚（本项目 6 条测试），因为横跨 kb/doc 两条业务链。
- **面试问法**：「横向越权和垂直越权的区别？」30 秒版：垂直是沿角色梯子往上爬（member 打 admin），水平是同级别访问别人资源（B 读 A 的库）；防垂直用角色检查，防水平用资源归属比对，且**归属检查必须在 service 层每个入口做**，不能靠前端隐藏入口。
- **追问链**：① 为什么 404 也能防枚举（资源不存在和没权限同响应，代价是语义模糊）→ ② 归属检查放 repo 层行不行（行但难读：每个查询都塞 owner 条件；放 service 集中收口）→ ③ 数据库行级权限（RLS）是什么（把归属下沉到库，PostgreSQL 有，MySQL 没有）。

### 2. 封禁不变量：存量票失效 ∧ 新票发不出

- **一句话定义**：封禁生效当且仅当"他手里的票全部失效 **且** 他换不到任何新票"——合取命题，缺一即被绕过。
- **为什么存在**：无状态 JWT 的票不会自己知道主人被封了，所以**每个信任入口都要现查一次库**：`get_current_user`（access 存量）、`refresh` 拒绝链第 4 步（refresh 存量）、`login`（发票口）。
- **怎么用**：三处各一行 `is_banned` 判断，缺一处就是 D5 的 BUG-1 或 BUG-2。
- **底层机制**：票是"签发时刻的快照"，人的状态是"持续变化的现值"，两者的唯一连接点是查库这一动作——无状态的代价在撤销场景全部显形。
- **易错点**：① 只堵 login 不清存量票（7 天 refresh 照续）；② 只清存量票不堵 login（重登拿新票）；③ refresh 链里漏 is_banned（D4 亲手写的第 4 步不是装饰，是第三条腿）。
- **面试问法**：「用户被封禁后，他的 token 为什么还能用？」30 秒版：JWT 无状态，签发后服务端不存票，token 落库之前无法批量失效；解法是验人阶段查库读 is_banned，把"信票"改成"信票+信人"。
- **追问链**：① 想不查库行不行（token_version：用户表存整数，签发时写进 claim，封禁时 +1，验签时比对——一次查库变一次轻量读，代价是所有在途 token 全废）→ ② 黑名单方案（Redis 存 jti，TTL 到 exp）→ ③ 三种方案选型判据（撤销频率、存储成本、能否定点撤销单张票）。

### 3. 轮换与重放检测：不轮换 = 盗窃永生

- **一句话定义**：轮换 = 每次续票时作废旧票 + 签发新票（同事务）；它的安全价值不在"防住"，在"**暴露**"——旧票被重放的那一刻，失主下一个请求就撞 401。
- **为什么存在**：refresh 票 7 天寿命、反复使用，是最高价值资产。轮换把"一次性使用"强加给它：任何一次重复使用都是盗窃信号。
- **怎么用**：`rotate(old_row, new_hash, new_exp)` 作废旧票行 + add 新票行，service 一次 `_commit()` 收口。
- **底层机制**：`revoked_at IS NOT NULL` = 重放铁证；作废与签发必须在同一事务——拆开提交会出现"新票已发、旧票还活"的时间窗（W9 债③并发版的近亲）。
- **易错点**：① 只发新票不作废旧票（BUG-3 原型：盗窃可检测退化为盗窃永生）；② 滑动过期叠加不轮换 = 一张被偷的票低调续命十年；③ 把"随便一个 token 都能当通行证"当最坏情形——错，攻击面没有扩大，是**一张票获得永生**。
- **面试问法**：「refresh token 为什么要轮换？」30 秒版：让票一次性化，把"票据被盗"从静默损失变成可检测事件（重放 401 即警报），同时缩短单张票的最大暴露寿命。
- **追问链**：① 检测到重放后应该做什么（安全基线：撤销该用户**全部**票——因为无法区分谁是真主）→ ② 为什么不轮换的方案也有人用（Some 团队接受静默风险换实现简单；判据是有没有秒踢需求和审计要求）→ ③ 轮换与绝对上限怎么配合（滑动续命 + 总寿命封顶，防无限续期）。

### 4. 注入式验收方法论（变异测试思想）

- **一句话定义**：故意在代码里埋真漏洞 → 攻击探针先拿到 ATTACKED 读数（红）→ 修复 → DEFENDED（绿）——**先证明测试/探针能抓到问题，再谈修复**。
- **为什么存在**：与"门禁改完必须故意破坏验证它会红"同源：绿着的代码无法证明防线活着，只有让它红过一次才有证据。
- **怎么用**：每漏洞一探针（5–10 行）+ 守门 pytest 双层证据；修完要求探针绿 + pytest 绿 + 源码 diff 与历史逐字节一致。
- **底层机制**：探针设计遵循**控制变量**——只坏一个东西。探针 5 用真用户的 sub 签死票，保证 401 只可能来自 exp 检查；编 uid 则两个东西坏，读数无法归因。
- **易错点**：① 修完不看探针读数（口头"肯定防住了"，今天第 N 次被数据打脸）；② 漏洞进 git 历史（正确做法：注入与修复一起提交，diff 只见还原）；③ 照抄探针不做敲前猜（手过脑不过）。
- **面试问法**：「你们怎么做安全测试？」30 秒版：注入式验收——人工埋 6 类鉴权漏洞，攻击探针先红后绿，配合变异测试验证测试本身活着；本质是把"测试能抓到问题"变成被证实的命题而不是假设。
- **追问链**：① 和单元测试的区别（单测验正常路径，注入验防线活性）→ ② 和 fuzzing 的区别（fuzz 盲打找未知崩溃，注入是定向验证已知风险点的守卫）→ ③ 漏洞清单从哪来（OWASP API Top 10：BOLA/认证失效/鉴权失效/资源滥用——本项目 6 类正对着前三）。

### 5. 登录接口的泄露契约：文案统一 + 时序拉平

- **一句话定义**：login 的错误响应是**枚举攻击者的探测面**：文案必须与"密码错误"一字不差，封禁判断必须放在 `verify_password` 之后。
- **为什么存在**：对面站着不知道账号是否存在的人。一句「账号已被封禁」= 泄露"邮箱存在 **且** 密码正确"双信号，撞库攻击者直接开奖。
- **怎么用**：`if row["is_banned"]: raise UnauthorizedError("邮箱或密码错误")`——与 :47 行同文案。
- **底层机制**：位置即契约——若把封禁判断提前，被封账号省掉 bcrypt 的几百毫秒，**响应时间差本身就是旁路信道**（时序攻击）。D2 的假哈希 `_DUMMY_HASH` 与此同源：把所有失败路径的耗时拉平。
- **易错点**：① 文案"好心"写清楚被封（在 login 是泄密，在 get_current_user 却无害——判据是**对面站的是谁**：持票者本来就知道自己的 user_id，没有信息差）；② 判断挪到密码验证之前省 CPU（省出来的 CPU 变成泄露通道）。
- **面试问法**：「登录失败提示为什么不能区分'密码错误'和'账号不存在'？」30 秒版：可区分 = 可枚举，攻击者批量探测注册邮箱 + 撞库；所以文案、状态码、耗时三者都要统一。
- **追问链**：① 注册接口同样问题（重复注册返回什么？本项目 409 但文案不区分"已注册"细节的取舍）→ ② 忘记密码接口怎么防枚举（统一返回"如存在已发送"）→ ③ CAPTCHA/限流在哪个层（枚举的另一半防护：探测面缩窄 + 成本抬高）。

### 6. FastAPI 依赖解析顺序（D6 巡检红区）

- **一句话定义**：依赖树**构建**时从路由向外递归（父到子），**运行**时叶子依赖先执行、父依赖的函数体后执行——所以 `get_current_user`（验人）先跑，`_check`（验权）后跑。
- **为什么存在**：`_check` 的参数 `user = Depends(get_current_user)` 决定了"参数先于函数体"——这是依赖注入的普适规则，不独 FastAPI。
- **底层机制**：`solve_dependencies` 深度优先后序：先解析并调用子依赖拿返回值，再以返回值调用父依赖。
- **怎么用**：写鉴权链时把"验人"写成被依赖的子依赖（`get_current_user`）、"验权"写成参数引用它的父依赖（`_check`），顺序由依赖树自然保证，不靠调用约定。
- **易错点**（今日两次答反）：① 说成先验权后验人；② `get_current_user` 内部把 decode 当黑盒一笔带过——真实顺序：**credentials 判空 → decode（验签+exp）→ UUID 解析 → 查库（存在→封禁）**，六个 401 六扇门。
- **面试问法**：「FastAPI 的 Dependencies 执行顺序？」30 秒版：构建期静态建树，运行期深度优先后序——叶子先行；同一依赖多处引用默认走缓存，`use_cache=False` 可关。
- **追问链**：① yield 依赖的 teardown 在哪层跑（AsyncExitStackMiddleware，W6 洋葱图）→ ② 依赖缓存什么时候是坑（同请求内共享 Session 靠它，跨请求绝不能）→ ③ 依赖和中间件的职责分界（依赖管"这次请求要不要放行+要什么"，中间件管"所有请求的共同横切"）。

### 7. `decode_access_token` 的两层防御

- **一句话定义**：10 行代码两层闸门——信封层 `jwt.decode`（验签 + exp/nbf + 算法锁定），载荷层 `TokenClaims.model_validate`（载荷形状）。
- **为什么存在**：信封坏了是**伪造或过期**（外部攻击），载荷坏了多半是**签发逻辑 bug**（自家问题）——分开捕获，日志可归因，对外统一 401。
- **底层机制**：传 key 给 decode 即验签；`exp` 是签发时烤进票里的**绝对时间戳**（签名封存，客户端改不了），每次请求与 now 比较；algorithm 锁定防 `alg=none` / 算法混淆攻击。
- **怎么用**：.decode 时永远传 key + 锁 algorithms 白名单；不传 `options` 就用默认全开；信封层与载荷层各自 try/except 分开归因，对外统一 401。
- **易错点**：① 找不到名为 verify 的函数就以为没验签（verify 藏在 decode 里）；② `options={"verify_exp": False}` 只关一半——jose 各开关独立，关一个不报警（配置漂移是静默的，必须有测试钉着）；③ 两条 except 合并写（丢归因能力）。
- **面试问法**：「JWT 的签名验证在代码哪里发生？」30 秒版：decode 内部——库用 secret key 重算签名比对，同时校验 exp/nbf/算法；alg 白名单必须有，否则 header 篡改可绕签。
- **追问链**：① HS256 vs RS256（对称 vs 非对称；多服务验证场景用 RS256，私钥签公钥验）→ ② secret 泄露了怎么办（全量 token 可伪造 = 换 key 全员重登，所以 secret 进 KMS/环境变量不进 git）→ ③ 为什么 exp 过期是 401 不是 200 带刷新提示（语义归未认证，续票是客户端拦截器的事，W8 前端课）。

## 三、30 秒答案集（8 条，合上文档背）

1. **横向 vs 纵向越权**：纵向沿角色梯爬（防：role 检查）；横向同级互看（防：每入口 owner 比对）。
2. **401 vs 403**：身份没说清 401；说清了不够格 403。顺序先 401 后 403。
3. **封禁怎么生效**：存量票失效 ∧ 新票发不出，三入口各查 is_banned。
4. **轮换的价值**：不在防住，在暴露——重放 401 即盗窃警报；不轮换 = 盗窃永生。
5. **login 泄露契约**：文案一字不差 + 判断在 verify_password 后（时序拉平）。
6. **注入式验收**：先红后绿；探针控制变量，一次只坏一个东西。
7. **exp 在哪**：签发时烤进票里的绝对时间戳，签名封存；decode 每次请求现比。
8. **依赖顺序**：构建父到子，运行子先行——先验人后验权。
