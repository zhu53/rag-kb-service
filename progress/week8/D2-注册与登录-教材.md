## §零·六 前置知识：三个词先讲清（A）

### 0.6.1 哈希（hash）是什么，和加密有什么区别

**加密**：可逆。有钥匙就能把密文解回明文（比如 AES）。用途是"我要能读回来"。
**哈希**：不可逆。只能把明文算成一个定长的指纹，**没有任何办法从指纹反推明文**。用途是"我只要能验证，不需要读回来"。

登录恰好属于后者：服务器**不需要知道你的密码**，只需要验证"你现在输的"和"当初存的那个"是同一个。所以存指纹就够——**数据库被拖走，攻击者也拿不到明文密码**。

两个必须知道的配套概念：

- **盐（salt）**：每个用户随机生成的一串字节，和密码一起哈希。作用：同样密码 `123456`，在 A 用户和 B 用户那里算出来的哈希完全不同（今天的实测会看到），攻击者不能"算一张大表一次撞穿所有人"（这种预计算表叫彩虹表）。
- **慢哈希**：bcrypt 故意设计得慢（本项目实测 **219ms/次**，见 §二）。正常登录多花 0.2 秒无所谓，但攻击者想暴力试 10 亿个密码，就要 6 年。**"慢"在这里是安全属性，不是性能缺陷。**

为什么不能用 `sha256(password)`：SHA-256 太快（GPU 每秒几十亿次），且标准用法没有盐。**快哈希适合校验文件完整性，不适合存密码。**

### 0.6.2 bcrypt 长什么样、有什么硬限制

一个真实的 bcrypt 哈希（今天实测生成）：

```
$2b$12$KIXQJ3nZ0m5T9lQ0mZ8oOe1V8f2h9Fv0m3w7pQ2sT5uY8iI1oP3aS
└┬─┘└┬┘└──────────────────┬──────────────────────────┘
 │   │                    └── 22 字符盐 + 31 字符哈希（同一段里）
 │   └── cost = 12，即 2^12 = 4096 轮，调大更慢更安全
 └── 算法版本 $2b$（bcrypt 当前标准变体）
```

两个实测结论（后面 §二 会自己跑出来）：

| 事实 | 读数 |
|---|---|
| 固定长度 | **60 字符**（所以 D1 建表时 `password_hash: String(128)` 绰绰有余） |
| 同一密码两次哈希 | **不相同**（盐是随机的）——所以**不能**用"哈希相等"当密码相等的判据，必须用 `verify` |
| 长度上限 | **72 字节**（不是 72 个字符！）——24 个汉字 = 72 字节刚好，25 个汉字 = 75 字节直接 `ValueError` |

**72 字节这条今天会咬人**：如果你的注册接口只写 `max_length=72`，用户输入 30 个汉字（90 字节）时 Pydantic 放行，到 `hashpw` 才炸 → 500。正确做法是按**字节**校验，见 §五 决策 5。

### 0.6.3 401 / 403 / 409 / 422：四个码的边界

| 码 | 问的问题 | 本项目例子 |
|---|---|---|
| **401** 未认证 | "你是谁？"（没票 / 票过期 / 密码错） | 登录密码错；token 过期 |
| **403** 已认证但无权限 | "你能干什么？"（知道你是谁，但这事不归你） | 访问别人的知识库（`get_or_403`） |
| **409** 状态冲突 | "现在能这么干吗？"（请求本身合法，但和资源当前状态冲突） | 注册时 email 已存在；建同名 KB |
| **422** 参数不合法 | "你说的我看不懂" | 缺字段、类型不对、超长 |

一句话记：**401 问身份，403 问权限，409 问状态，422 问格式。**
409 和 400 的区别要能说清：400 是"你这个请求本身就是坏的"，409 是"请求没毛病，但库里现在的状态不允许"。

## §一 痛点：两个函数躺在那里，没人调用（A）

先看实物（这是今天动手前必须知道的三个事实，都来自 grep，不是印象）：

**事实 1：密码哈希函数写好了，全项目零调用。**

```
security.py:29  def hash_password(raw: str) -> str
security.py:33  def verify_password(raw: str, hashed: str) -> bool
```
`grep -rn "hash_password\|verify_password" src tests scripts` 除了定义处和 `.pyc` 缓存，**没有任何调用点**。
也就是说：**这套系统到现在为止，从来没有校验过任何人的密码**——因为系统里根本没有"密码"这个概念。

**事实 2：`dev/token` 是一个不需要密码的发证机关。**

```python
# api/v1/dev.py:33
@router.post("/token", summary="[dev] 签发演示 token")
async def issue_dev_token(body: DevTokenRequest) -> DevTokenResponse:
    uid = body.user_id or uuid4()     # ← 不传就随机造一个身份
    return DevTokenResponse(access_token=create_access_token(str(uid)), user_id=uid)
```

它被 `main.py:87` 用 `if settings.env != "prod"` 挡在 prod 外面——**这只是"生产没有"，不代表"本地和测试是安全的逻辑"**。更关键的是：它让"token 从哪来"这个问题一直被绕过。

**事实 3：整条链路上，"用户"是个不存在的概念。**

| 位置 | 现状 | 后果 |
|---|---|---|
| `api/v1/dev.py:35` | `uid = body.user_id or uuid4()` | 每次刷新演示页都是"新用户"，数据看不见 |
| `tests/conftest.py:77` | `create_access_token(str(TEST_USER_ID))` | 测试用户库里**没有这行**——D3 查库后所有测试立刻 401 |
| D1 之后 | `users` 表有了，但没人往里写 | 户口本空着 |

三个后果串起来就是今天的任务：**没有密码 → 无法验证"你是你"；没有真实注册 → users 表永远是空的；后门不拆 → 上面的努力全是装饰。**

## §二 最小可跑示例：5 分钟亲手拆一个哈希（A）

在 `kb-service/` 目录下跑（这是实测过的命令和输出，不是示意）：

```powershell
# Windows PowerShell
& .\.venv\Scripts\python.exe -c "
import bcrypt
h = bcrypt.hashpw(b'correct horse battery staple', bcrypt.gensalt())
print('前缀:', h.decode()[:7], '| 长度:', len(h.decode()))
print('验证正确:', bcrypt.checkpw(b'correct horse battery staple', h))
print('验证错误:', bcrypt.checkpw(b'wrong', h))
print('两次同密码相同?', bcrypt.hashpw(b'same', bcrypt.gensalt()) == bcrypt.hashpw(b'same', bcrypt.gensalt()))
"
```

实测输出：

```
前缀: $2b$12$ | 长度: 60
验证正确: True
验证错误: False
两次同密码相同? False
```

逐行解读：

1. `$2b$12$`——算法版本 `2b`、cost 12（4096 轮）。cost 每 +1，耗时翻倍。
2. **60 字符**——固定长度，所以库里 `String(128)` 完全够，且不同用户哈希长度一致（不会因为密码长而变长）。
3. `验证正确 True / 验证错误 False`——这就是登录要的全部能力：**不是解密，是比对**。
4. **两次同密码结果不同**——盐在起作用。这条最重要：它意味着"哈希值相等"永远不能当判据，你必须用 `checkpw` / `verify`。

再补一个耗时读数（cost 12、本机）：

```
hash:   219 ms
verify: 220 ms
```

**记住这个 220ms**：它就是"登录接口天生比别的接口慢"的原因，也是 D5 注入验收时"故意写个死循环验证密码"会被压测抓出来的原因。同时它是**故意的**——面试问"bcrypt 为什么慢"，答案不是"实现差"，是"慢就是安全"。

最后测 72 字节这条硬限制（今天写 schema 时会用到）：

```powershell
& .\.venv\Scripts\python.exe -c "
import bcrypt
for n in (24, 25):
    p = ('中'*n).encode()
    try:
        bcrypt.hashpw(p, bcrypt.gensalt()); print(f'{n} 个汉字 = {len(p)} 字节 -> OK')
    except Exception as e:
        print(f'{n} 个汉字 = {len(p)} 字节 -> {type(e).__name__}: {str(e)[:50]}')
"
```

```
24 个汉字 = 72 字节 -> OK
25 个汉字 = 75 字节 -> ValueError: password cannot be longer than 72 bytes, truncate
```

## §三 事故：`passlib` 与 `bcrypt 5.0` 不兼容（A）

这是今天第一件"判据来自数据"的事——**教材不能假设 `security.py` 现在能用**。

### 3.1 实测：现成的 `hash_password` 一调用就炸

```powershell
& .\.venv\Scripts\python.exe -c "from kb_service.core.security import hash_password; print(hash_password('hello'))"
```

实测（节选关键帧）：

```
File "...\passlib\handlers\bcrypt.py", line 380, in detect_wrap_bug
    if verify(secret, bug_hash):
ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
```

### 3.2 根因链（三句话）

1. 项目装的是 **passlib 1.7.4**（2020 年后停更）+ **bcrypt 5.0.0**（新）。
2. passlib 初始化 bcrypt handler 时会做一次"兼容性探测"（`detect_wrap_bug`），探测用的是一段 **255 字节**的超长假密码。
3. bcrypt 5.0 改了行为：**超过 72 字节直接抛 `ValueError`**（老版本是静默截断）→ 探测失败 → 整个 handler 初始化失败 → **`hash_password()` 无论输入多长都抛异常**。

注意这个失效模式有多阴：**它不是"长密码才炸"，是"这个函数彻底不可用了"**，而且炸在 `CryptContext` 初始化那一刻。如果直接上注册接口，表现是"任何注册都 500"，而报错里提到的却是"72 bytes"——很容易误判成"用户密码太长"。

> 这条正好是 W8 周计划里那句"passlib 停更，换掉它的债留给本周评估"的兑现时刻：**可逆性审计不是文档工作，是跑一次就发现的**。

### 3.3 决策：换原生 `bcrypt`，不钉版本、不换算法

| 方案 | 判据 | 结论 |
|---|---|---|
| 把 `bcrypt` 钉到 4.0 | 把版本锁死在一个停更封装的行为上，下次升级再炸；`uv lock` 一更新就重演 | ❌ |
| 换 `argon2-cffi` | 更强，但引入新依赖 + 新参数体系，本周目标不是换算法 | ❌ 记 W14 评估 |
| **直接用 `bcrypt` 库**（`import bcrypt`） | 少一层停更的中间件；API 就两个函数 `hashpw`/`checkpw`；行为有实测读数 | ✅ |

改造很小（`security.py`）：

```python
import bcrypt

def hash_password(raw: str) -> str:
    return bcrypt.hashpw(raw.encode("utf-8"), bcrypt.gensalt()).decode("ascii")


def verify_password(raw: str, hashed: str) -> bool:
    try:
        return bcrypt.checkpw(raw.encode("utf-8"), hashed.encode("ascii"))
    except ValueError:
        # 库里存了非法哈希（历史脏数据/手工改过）→ 当作"验证失败"，不要 500
        return False
```

那个 `try/except` 不是防御性编程的洁癖：`checkpw` 遇到格式不对的哈希会抛 `ValueError`，不接住就是 500，而 500 会把"内部数据坏了"这个信息漏给攻击者。**验证函数只该有两个答案：True / False。**

依赖同步改动（这是"一处改，三处对"）：

- `pyproject.toml`：`"passlib[bcrypt]>=1.7"` → `"bcrypt>=4.1"`；dev 组里 `"types-passlib"` 删掉（bcrypt 自带类型）；
- `pyproject.toml` 里那段解释 passlib 警告的白名单注释（~94 行）一起删；
- `uv lock` 重锁，然后跑门禁。

### 3.4 验收（做完才许往下走）

1. `hash_password("hello")` 能返回 `$2b$12$` 开头的 60 字符；
2. `verify_password("hello", 上面那个)` 为 True，`verify_password("hell0", ...)` 为 False；
3. `verify_password("x", "不是哈希")` 返回 False（不抛异常）；
4. **变异验证**：把 `except ValueError` 删掉 → 第 3 条必须红。

## §四 注册与登录：完整链路（A）

### 4.1 注册时间轴（谁在保证什么）

```
POST /api/v1/auth/register   {"email": "...", "password": "..."}
 │
 ├─① Pydantic 校验        格式/长度/字节数      ← 谁保证：schema（422）
 ├─② email 归一化         strip + lower        ← 谁保证：service 入口一行
 ├─③ hash_password        219ms，明文到此为止   ← 谁保证：代码里 hash 之后不再碰明文
 ├─④ UserRepository.create → session.add + flush（拿到 id）
 ├─⑤ service._commit()    提交事务              ← 谁保证：service（不是 repo）
 └─⑥ 201 + UserOut        **不含 password_hash** ← 谁保证：UserRow 快照（D1 已定）
                          
失败分支：email 撞 uq_user_email
 → MySQL 抛 1062 → SQLAlchemy 包成 IntegrityError → 债① handler → 409
```

三个"谁在保证"值得单独记：

| 不变式 | 保证人 | 如果换了会怎样 |
|---|---|---|
| email 唯一 | **MySQL 唯一索引**（不是"先查后插"） | 并发注册两个同 email 都会成功（D1 间隙锁探针已实测） |
| 明文密码不落库 | **代码路径**（hash 之后只用 hash） | 日志、异常栈、debug 打印都可能带出明文——注意别把 `body` 整个打进日志 |
| 事务原子性 | **service 的 `_commit()`** | repo 只 flush，忘了 commit → 201 但 0 行（W7-D6 真踩过） |

### 4.2 登录时间轴

```
POST /api/v1/auth/login   {"email": "...", "password": "..."}
 │
 ├─① 归一化 email（和注册同一套规则，否则大小写不同就登不进）
 ├─② get_by_email → row | None
 ├─③ row 为 None：仍然跑一次 verify_password(密码, 假哈希)   ← 等时，防"用户枚举"
 ├─④ verify_password(明文, row["password_hash"])             ← 220ms
 ├─⑤ 失败 → 401 "邮箱或密码错误"（**不区分**"没这个人"和"密码错"）
 ├─⑥ 成功 → create_access_token(str(row["id"]))
 └─⑦ 200 {"access_token": ..., "token_type": "bearer", "expires_in": 3600}
```

**③ 和 ⑤ 是同一个目标的两面**：不让攻击者通过"响应快慢"或"错误文案"判断出某个邮箱是否注册过。

- 文案层面：两种失败给**一模一样**的 401 和消息；
- 时间层面：用户不存在时如果不做哈希，会快 220ms——这个差异足以被统计出来（叫**时序攻击**，timing attack）。所以拿一个固定的假哈希跑一遍 `verify_password`，把耗时拉平。

> L 级补充：真正严格的等时还要处理"邮箱存在但被封禁"的分支，以及 bcrypt 自身的随机抖动；本项目做到"文案统一 + 假哈希"就够，面试说出这两层即可。

### 4.3 为什么 token 里不放 `role`（A，这是今天最值钱的一个决策）

直觉做法：登录时把 `role` 塞进 payload，鉴权时直接读，省一次查库。**本项目不这么做**，原因：

| | 放进 token | 不放（每次查库） |
|---|---|---|
| 改角色生效时间 | 等 token 过期（最长 60 分钟） | **立刻** |
| 封禁生效时间 | 同上（D3 的核心验收就是这条） | **立刻** |
| 每请求成本 | 0 次查询 | 1 次主键查询（亚毫秒） |
| 撤销能力 | **没有**（JWT 天生不能注销） | 有 |

判据一句话：**授权数据的时效要求，高于一次主键查询的成本。**
这也是面试里"JWT 无状态有什么代价"的标准答案——**无状态的代价就是撤销能力**，不是"性能不好"。

## §五 六个设计决策（A/B）

> 每个决策都写成"选项 / 选择 / 判据"。面试追问基本都落在这张表上。

### 决策 1：email 归一化（A）

- 做法：入库和查询前统一 `email.strip().lower()`。
- 判据：`A@x.com` 和 `a@x.com` 是同一个邮箱（RFC 里域名不区分大小写，实践中本地部分也按不区分处理）。
- **不要依赖数据库的排序规则（collation）来保证这件事**：MySQL 默认 collation 对大小写不敏感，sqlite 敏感——同一行代码在测试和真库上行为不同，是典型的"静默不一致"。**业务语义放在应用层，别托付给引擎配置。**

### 决策 2：注册返回什么（A）

| 选项 | 优点 | 代价 |
|---|---|---|
| 201 + 用户信息（本项目） | 注册/登录职责分离；少一条要测的分支；以后加"邮箱验证"不用改协议 | 客户端要再调一次登录 |
| 201 + 直接发 token | 少一次往返 | 注册接口同时承担了登录的全部失败分支；邮箱未验证就发证，安全语义模糊 |

判据：**一个接口只承担一个语义**。注册的语义是"创建账号"，不是"登录"。

### 决策 3：重复 email → 409（A）

- 已有债① 的 handler 兜底（`main.py:68`），注册接口**不需要自己 try**。
- 但要注意：handler 是在**全局**翻译 `IntegrityError`，所以注册路径要确认报错里确实含 `duplicate`（MySQL）/`unique`（sqlite）。**测试必须在 sqlite 上跑一遍**——两种方言都认，是你昨天写 handler 时就定下的。
- 别加"先 `get_by_email` 查重再插入"：那是把唯一性判据从数据库挪回应用层，并发下必翻车（D1 间隙锁实测：RC 隔离级别下 125ms 就穿过去了）。

### 决策 4：登录失败统一 401（A）

- 文案固定 `"邮箱或密码错误"`，两种失败共用。
- 判据：任何能区分"账号存在与否"的响应，都是给撞库攻击者送情报（这叫**用户枚举**）。
- 同理：注册接口返回 409 其实也泄漏了"这个邮箱已注册"——这是**无法避免的业务必需**（用户必须知道换个邮箱），所以它可接受，但登录接口没有这个必要。

### 决策 5：密码长度（A）

| 约束 | 值 | 理由 |
|---|---|---|
| 最短 | 8 字符 | 低于这个长度的密码在离线爆破下等于没有 |
| 最长 | **72 字节**（按字节校验） | bcrypt 硬限制；`max_length=72` 只数字符，30 个汉字就能突破 |
| 校验位置 | Pydantic validator | 到 `hashpw` 才炸就是 500 |

写法提示（`schemas/auth.py` 里）：

```python
Password = Annotated[str, Field(min_length=8, max_length=72)]

@field_validator("password")
@classmethod
def _check_byte_len(cls, v: str) -> str:
    if len(v.encode("utf-8")) > 72:
        raise ValueError("密码不能超过 72 字节（中文约 24 字）")
    return v
```

> 决策记录：不做"必须含大小写数字"这类复杂度规则。判据是 NIST SP 800-63B 的现行建议——**长度比复杂度有效**，复杂度规则只会逼出 `Password1!` 这种密码。面试可以主动提这句，是个加分点。

### 决策 6：登录请求用 JSON 还是 OAuth2 表单（B）

| | JSON `{"email","password"}`（本项目） | `OAuth2PasswordRequestForm`（form-data） |
|---|---|---|
| 前端调用 | 简单 | 要 `application/x-www-form-urlencoded` |
| Swagger 的 Authorize 按钮 | 不会自动打通 | 原生支持"密码流"登录框 |
| 依赖 | 无 | `python-multipart`（已装） |

选 JSON：演示页直接 `fetch` 好写，且我们的 `/docs` 里已经有 `HTTPBearer` 的 Authorize 按钮（`deps.py:14`），不需要 OAuth2 表单那套。**代价写清楚**：Swagger 里不能直接用登录框换 token，要手动贴。

## §八 债②：PATCH null（B）——债表也会说谎

### 8.1 先实测（债表说 500，真的吗？）

债② 的描述是：`PATCH /kbs/{id}` 传 `{"title": null}` → 撞 NOT NULL → **500**。

今天用 sqlite 真跑了一遍（`TestClient` + `get_db` 覆盖，脚本跑完即删）：

| 请求 | 债表说 | 实测 |
|---|---|---|
| `{"name": null}` | 500 | **200，返回原名不变** |
| `{"description": null}` | — | **200，返回原描述不变** |
| `{"title": null}`（不存在的字段） | 500 | **200，字段被忽略** |

**没有一个 500。** 原因是 `kb_repo.update` 里那句 `if v is not None`（`kb_repo.py:78`）——它把所有 null 都当成"没传"，直接跳过。

结论：**W7 写的债表描述已经过期了**（当时是另一种实现），现在的问题比 500 更隐蔽：

- **静默**：客户端以为清空了，实际没清；
- **能力缺失**：`description` 永远无法被清空（传 null 被忽略，传 `""` 又会被 `not_blank` 拒？——`KbDescription` 没有 `not_blank`，所以传 `""` 能清成空串，但语义上"空串"和"NULL"不是一回事）。

> 这是"判据来自数据"的又一个实例，和第 4 个（CI 假绿）同一个家族：**二手描述（债表、注释、文档）都要实测一遍再动手。**

### 8.2 两个决策，选一个并写清理由

PATCH 的语义是"我改这些字段"。JSON 里**显式写 `null`** 表达的是"我要把它清空"，而不是"我没传"。所以：

| 字段 | 传 null 的语义 | 本项目选择 |
|---|---|---|
| `description`（可空列） | 清空 | **允许**，写 NULL |
| `name`（NOT NULL 列） | 无法清空 | **422**，明确告诉客户端"name 不能为 null" |

实现要点（提示，不直接给答案）：

- **区分"没传"和"传了 null"**：`model_dump(exclude_unset=True)` 只保留"传过的字段"，null 会留在里面 → repo 里的 `if v is not None` 就是罪魁，去掉它；
- **拒绝 name=null**：在 `KBUpdate` 里加 `model_validator(mode="after")`，检查 `"name" in self.model_fields_set and self.name is None` → raise ValueError → 422 handler；
- **改完检查两个方向**：①`{"name": null}` → 422；②`{"description": null}` → 200 且库里真的是 NULL（不是空串）。

### 8.3 验收 + 变异

- 新测试两条：`test_patch_name_null_422`、`test_patch_description_null_clears`（后者要**再 GET 一次**确认，不能只看 PATCH 的返回——返回的是内存快照，不代表落库）；
- 变异验证：把 `if v is not None` 加回去 → 第二条必须红（描述清不掉了）。

## §十一 面试问法（A）

### 30 秒版（背下来）

> "注册时用 bcrypt 把密码哈希后入库——bcrypt 自带随机盐、可调 cost，故意慢到 200 毫秒，让离线爆破不划算。登录时按 email 查用户，用 `checkpw` 比对；失败统一返回 401「邮箱或密码错误」，并跑一次假哈希拉平耗时，防用户枚举。验证通过才签 JWT，payload 只放 `sub` 和过期时间，不放角色——因为授权数据要能立刻生效，代价是每个请求一次主键查询。"

### 追问三层

**第一层（机制）**：
- "为什么不用 SHA-256？" → 太快 + 无盐；快哈希适合校验完整性，不适合存密码。
- "bcrypt 的 cost 是什么？" → 2^cost 轮，每 +1 耗时翻倍；调高要在"安全"和"登录延迟"之间权衡。
- "盐存在哪？" → 就在那 60 字符里，前 29 个字符包含版本 + cost + 盐，验证时自动取出来用，不需要单独存列。

**第二层（边界/故障）**：
- "bcrypt 有什么坑？" → **72 字节上限**：超出直接抛 ValueError（bcrypt 5）或静默截断（老版本）；而且 `max_length` 数字符不数字节，中文会提前撞线。还能补一句今天的事故：**passlib 1.7.4 + bcrypt 5.0 初始化就炸**，因为它拿 255 字节探测密码去试哈希。
- "数据库被拖走会怎样？" → 拿不到明文；但弱密码仍可被离线爆破，所以要有最短长度 + 可选加 pepper（服务端密钥，不进库）。
- "token 被偷了怎么办？" → access token 无法撤销（JWT 无状态），只能等过期；所以 access 要短命 + refresh 可撤销（D4）。

**第三层（场景落地）**：
- "千万用户，登录接口怎么扛住 bcrypt 的 200ms？" → 登录是低频操作，200ms 可接受；真正的问题是**暴力破解**和**撞库**，要在前面加限流（按 IP + 按账号，W10 滑动窗口）和失败计数锁定；另外 bcrypt 是 CPU 密集，同步调用会占线程池，量大时要单独限并发或换异步池。
- "怎么防用户枚举又让用户体验好？" → 注册/找回密码走"我们已发送邮件"的统一文案；登录只给统一 401。
- "多租户下登录有什么不同？" → 账号可能属于多个租户，登录后要选租户/带 tenant 上下文；token 里仍然不放角色，但可能要放 `tenant_id`（这是 W14 的话题）。

## §十二 闭卷自测（合上书，先做再做对答案）

**题目清单**（8 题，写在纸上，写不出画 `?`）：

1. 为什么密码必须哈希而不是加密？说出哈希和加密的一个本质区别。
2. bcrypt 哈希的 60 个字符里包含哪三样东西？为什么同一密码两次哈希不同？

4. 注册链路里，"email 唯一"由谁保证？"明文不入库"由谁保证？"事务原子性"由谁保证？
5. 登录失败为什么不能区分"用户不存在"和"密码错误"？除了文案，还要处理什么？
6. token 里为什么不放 `role`？代价是什么？
7. 删 `dev/token` 要改哪四处？删完怎么证明真的删干净了（给两个读数）？
8. PATCH 传 `{"name": null}` 现在会发生什么？为什么？应该改成什么？

<details>
<summary>参考答案（写完再看）</summary>

1. 加密可逆（有钥匙能解回），哈希不可逆（只能正向算）。登录只需要"验证一致"，不需要"读回密码"，所以用哈希；库被拖走也拿不到明文。
2. 算法版本（`$2b$`）+ cost（`12`）+ 盐与哈希本身；盐每次随机 → 同一密码结果不同，所以判等必须用 `verify`/`checkpw`，不能比字符串。
3. **72 字节**（不是字符）。`max_length=72` 只数字符，30 个汉字 = 90 字节会突破上限 → `hashpw` 抛 `ValueError` → 500。要按 `len(v.encode("utf-8"))` 校验。
4. 唯一 = **MySQL 唯一索引**（`uq_user_email`），并发下靠引擎原子判定（先查后插在 RC 下 125ms 就穿）；明文不入库 = **代码路径**（hash 之后不碰明文，日志也不打 body）；原子性 = **service 的 `_commit()`**（repo 只 flush）。
5. 区分会泄漏"该邮箱是否注册过"（用户枚举）；文案要统一，**耗时也要拉平**——用户不存在时用假哈希跑一次 `verify_password`，否则快 220ms 可被统计出来。
6. 因为授权数据要能立刻生效：封禁、改角色如果写在 token 里，要等最长 60 分钟过期；不放的代价是每个请求一次主键查询（亚毫秒）。
7. `api/v1/dev.py`（删文件）、`main.py`（删条件挂载 + 导入）、`static/index.html`（改调 `/auth/login`）、以及 grep 出来的第四处（测试/脚本/演示脚本）。证明：`grep -rn "dev/token" src tests scripts static` 无输出 + `POST /api/v1/dev/token` 返回 **404**。
8. 现在返回 **200 且原名不变**（静默忽略），因为 `kb_repo.update` 里 `if v is not None` 把 null 当"没传"。应改成：`description: null` = 清空（写 NULL），`name: null` = **422**（NOT NULL 列不能清空）；实现上要区分"没传"和"传了 null"（`model_fields_set`）。

</details>
