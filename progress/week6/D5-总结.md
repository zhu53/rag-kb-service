## 二、逐个知识点讲透

### 1. BackgroundTasks 时序：响应先发、任务后跑

**一句话定义**：`background_tasks.add_task(fn, *args)` 把任务挂到本次响应对象上，Starlette 在**响应体发送完成之后**才依次执行。

**为什么存在**：接口里有些活"用户不需要等"——发通知、记审计、写索引。同步做完再返回，用户白白多等几百毫秒甚至几秒；扔给独立队列（Celery）又要多一个组件。BackgroundTasks 是"进程内、零依赖"的中间态。

**怎么用**：
```python
async def create_doc(
    kb_id: UUID,
    body: DocCreate,
    background_tasks: BackgroundTasks,        # FastAPI 注入，和 Depends 同机制
    user_id: UUID = Depends(get_current_user_id),
) -> DocOut:
    doc = DocService().create(kb_id, user_id, body)
    background_tasks.add_task(run_index, doc.id, body.content)  # 只登记，不执行
    return doc                                 # 这里返回 ≠ 任务已跑
```

**底层机制**（starlette/background.py，全文 36 行）：`BackgroundTask` 在 `__init__` 时判断 `isasyncfunction(func)` 存下标记；响应发送完成后，Starlette 按顺序 `await` 每个 task——async 函数直接 await，同步函数丢进 `run_in_threadpool`（实测线程名 `AnyIO worker thread`）。**多个任务按登记顺序 FIFO 执行，不并行。**

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 以为 `add_task` 后任务已在跑 | 在下一行读任务产生的副作用，读到旧值 | 任务在响应发出后才跑；`add_task` 只登记 |
| 以为"后台"=异步不阻塞 | async 任务里写 `time.sleep`，整个服务卡死 | 见知识点 2 |
| 以为 TestClient 耗时=线上耗时 | 测试里接口"变慢了 300ms" | TestClient 等 ASGI 全周期（含任务）；线上 uvicorn 发完 body 就返回 |

**面试问法**（30 秒版）："FastAPI 的 BackgroundTasks 什么时候执行？会不会影响接口响应时间？"——"响应体发送完成之后才执行，多个任务 FIFO 顺序跑。它不影响响应延迟的前提是任务不阻塞事件循环：同步函数自动进线程池，但 async 函数里写同步阻塞会把整个服务卡住。"

**追问链**：① 追一层：任务挂在哪？（挂在 handler 返回的 Response 对象的 `background` 属性上）→ ② 追二层：任务抛异常会怎样？（客户端已拿到完整响应，异常只进服务端日志——见知识点 5）→ ③ 追三层：什么情况下不该用它？（任务必须成功、需要重试/追踪/持久化 → 上消息队列；它是 fire-and-forget，进程重启任务即丢）。

### 2. async 任务里同步阻塞 = 堵死整个服务

**一句话定义**：`async def` 的任务跑在事件循环上，函数体里任何同步阻塞调用（`time.sleep`、同步 HTTP 请求、同步 DB 驱动）都会**冻住所有并发请求**。

**为什么存在**：事件循环是单线程的"调度员"，它靠"协程主动让出"来实现并发。`time.sleep(0.3)` 期间协程不放手，调度员干等着，其他所有协程排队的 0.3 秒全部冻结——这不是"这个请求慢"，是"全服务慢"。

**怎么用**（两种正确姿势，按 SDK 类型选）：
```python
# 姿势 A：SDK 是同步客户端（本项目 embedding 场景）→ 改成普通 def，Starlette 自动进线程池
def run_index(doc_id: UUID, content: str) -> None:
    time.sleep(0.3)          # 在 worker 线程里睡，事件循环该干嘛干嘛

# 姿势 B：全程异步 → 用异步等待
async def run_index(doc_id: UUID, content: str) -> None:
    await asyncio.sleep(0.3) # 让出循环，调度员去跑别人
```

**底层机制**：同步 `def` 任务被 `run_in_threadpool` 丢进线程池（默认容量 40），线程睡多久都无所谓，因为事件循环空出来了；`async def` 任务直接在循环上跑，阻塞调用 = 循环停摆。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| async 任务里 `time.sleep` | 功能全对、测试全绿，但所有请求间歇性卡顿 | def 走线程池 或 await asyncio.sleep |
| 用 `# noqa: ASYNC251` 压警告了事 | ruff 绿了，坑还在 | noqa 只该在"确认无害"时用，每条都要有书面理由 |
| "线程池=并发安全" | 多任务共享状态没加锁 | 线程池任务仍可能并发，共享可变状态要同步原语 |

**面试问法**（30 秒版）："为什么 async 函数里不能写 time.sleep？"——"async 协程靠主动让出实现并发，time.sleep 不让出，事件循环整个停摆，所有并发请求一起冻结。解法按场景选：同步 SDK 就写成普通 def 让它进线程池，异步场景用 asyncio.sleep。"

**追问链**：① 追一层：普通 def 的端点 handler 是不是也有这问题？（有——FastAPI 对同步 handler 自动丢线程池，所以同步 handler 里 sleep 只堵自己占的线程，不堵循环）→ ② 追二层：线程池耗尽会怎样？（所有同步路径排队，等价于服务不可用，所以线程池容量是隐形容量上限）→ ③ 追三层：怎么发现这类问题？（压测看 P99；本日坑 1 就是"功能测试全绿但延迟异常"的典型——功能测试测不出性能病）。

### 3. 生产环境三个文档入口全关

**一句话定义**：FastAPI 默认开三个门——`/docs`（Swagger UI）、`redoc`、`/openapi.json`（JSON 本体），生产环境要**三个全关**。

**为什么存在**：文档 = 完整接口地图，等于把攻击面清单递给对方。而且 `openapi.json` 里可能带真实示例值、内部字段结构。

**怎么用**：
```python
app = FastAPI(
    docs_url="/docs" if settings.env != "prod" else None,
    redoc_url=None,                                            # 本项目一直不开
    openapi_url="/openapi.json" if settings.env != "prod" else None,   # 第三个门
)
```

**底层机制**：`docs_url=None` 只是不挂 UI 路由，`/openapi.json` 照样服务——UI 只是 JSON 的渲染器，JSON 才是本体。所以只关 `/docs` 是假关，curl 一下 JSON 照拿。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 只关 docs_url | `/docs` 404 了，以为关干净了 | 三门全 None；验证：curl /openapi.json |
| 用中间件拦截 /docs 路径 | JSON 还在，路径猜一下就中 | 用构造参数关门，不是过滤器 |
| dev/prod 条件写反 | 线上开着文档 | 探活：prod 起服务后 curl 三条路径都应 404 |

**面试问法**（30 秒版）："生产环境要不要关 Swagger？怎么关？"——"要。FastAPI 有三个入口：/docs、redoc、openapi.json，构造参数全传 None 才算关干净——/docs 只是渲染器，openapi.json 才是接口清单本体，只关 UI 是假关。"

**追问链**：① 追一层：内部系统（管理后台）也要关吗？（按暴露面定：只要网络可达就关，内网 ≠ 不可枚举）→ ② 追二层：关了之后前端联调怎么办？（dev/staging 环境开着，或用代码生成的静态文档）→ ③ 追三层：还有哪些"默认开着的信息口子"？（/health 泄露 env——D4 踩过、错误响应里的框架版本、verbose 异常页）。

### 4. `responses={401: {"model": ApiResponse}}` —— 只写文档，不改行为

**一句话定义**：路由装饰器的 `responses` 参数把"这个接口可能返回的额外响应形状"写进 OpenAPI JSON，**不添加任何运行时校验或处理**。

**为什么存在**：你的错误格式是统一壳 `{code,message,data}`，但客户端从默认文档里只能看到 422 的 `detail` 格式——它不知道 401 长什么样。契约要"说出去"，而不是让对方猜。

**怎么用**：
```python
@router.post("", responses={401: {"model": ApiResponse, "description": "未认证（code=40100）"}})
```
实测 JSON 里生成 `"$ref": "#/components/schemas/ApiResponse"`——泛型模型也能正常引用。

**底层机制**：FastAPI 启动建 schema 时把 `responses` 合并进 path item 的 responses 节；运行时路径完全不经过它——401 该怎么返回还是异常处理器说了算（main.py 的 `handle_app_error`）。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 以为写了 responses 就会自动返回该形状 | 前端按文档等 401 壳，实际拿到别的 | responses 只管文档；行为由 handler 决定 |
| 忘了 description | 文档里 401 一行没解释 | description 是给人看的，必写 |
| 把 200 也写进 responses 覆盖了 response_model | 200 形状对不上 | 200/201 由 response_model 管，responses 只写"额外的" |

**面试问法**（30 秒版）："responses 参数有什么用？"——"把错误响应的形状写进 OpenAPI 文档，让前端不用猜统一壳长什么样。它纯粹是文档契约，不改变任何运行行为——真正的错误响应还是异常处理器返回的。"

**追问链**：① 追一层：`$ref` 是什么？（`components/schemas` 里的配料表 + 按名字引用，避免每个接口重复内联同一模型）→ ② 追二层：文档和行为不一致谁发现？（没人自动发现——所以契约变更要靠测试钉住，比如 D4 那三条断言 40100 的测试）。

### 5. 任务异常：客户端不知道 / handler 抛异常任务不跑

**一句话定义**：后台任务失败对客户端**完全不可见**（响应早已完整发出）；反过来，**handler 抛异常时已登记的任务不会执行**。

**为什么存在**：任务挂在"handler 正常返回的那个 Response"上。异常处理器（`handle_app_error`）新建了 JSONResponse——它没有 `background` 属性，旧响应连同任务一起丢弃。

**怎么用 / 怎么防**：
```python
# 任务体内部必须自己兜底，且用 error 级别记
def run_index(doc_id: UUID, content: str) -> None:
    try:
        ...  # 业务
    except Exception:
        logger.exception("索引失败 doc_id=%s", doc_id)  # ERROR 级 + traceback
```

**底层机制**：Starlette 响应发送完 body 后遍历 `response.background` tasks，异常向上传播到 ServerErrorMiddleware——但此时响应已发出，只剩日志；TestClient 默认 re-raise，所以测试里能看到。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| except 里用 logger.debug 吞 | 线上 INFO 级别下一个字不出，"合规地丢了" | `logger.exception`（ERROR 级 + 堆栈） |
| 删了 `exc` 变量留孤儿 `%s` | 触发时 stderr 一屏 Logging error 堆栈 | 删变量 = 清它所有引用点（含格式串占位符） |
| 期望"失败也发通知"用 add_task | handler 抛异常 → 通知静默不发 | 关键副作用不能用 BackgroundTasks，走队列/事务后钩子 |

**面试问法**（30 秒版）："后台任务抛异常，用户知道吗？handler 抛异常任务还跑吗？"——"前者不知道，响应已发出，异常只进日志，所以任务体必须自己 try 住并用 error 级别记录；后者不跑，任务挂在 handler 返回的响应对象上，异常处理器新建的响应没有这个属性，任务静默丢失。"

**追问链**：① 追一层：为什么 debug 级等于没记？（线上级别通常 INFO，debug 被过滤）→ ② 追二层：进程重启任务丢不丢？（丢——fire-and-forget，这是"不该用它"的核心判据）→ ③ 追三层：怎么设计"必须执行"的副作用？（本地事务表/消息队列 + 重试 + 幂等消费，进 W8 MQ 主题）。

### 6. 同步任务走线程池 vs `asyncio.sleep` 的选择

**一句话定义**：后台任务的两种正确写法——普通 `def`（自动进线程池，适合调用同步 SDK）和 `async def` + 全异步调用（适合异步 SDK）——按"你依赖的 SDK 是同步还是异步"选。

**为什么存在**：真实项目里 embedding/DB 客户端常常是同步库（openai 老版本、psycopg2），在 async 任务里直接调用就是坑 2 的现场。姿势必须跟 SDK 走，不是跟个人偏好走。

**怎么用**：见知识点 2 的代码。本项目 `run_index` 选了 `def`：W12 要接的 embedding SDK 是同步客户端。

**底层机制**：`isasyncfunction(func)` 在任务构造时判定；同步任务经 `run_in_threadpool`（anyio，默认 40 线程），异步任务直接在循环上 await。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 按喜好混用 | async 任务里调同步 SDK | SDK 同步 → def；SDK 异步 → async + await |
| 以为线程池任务可以随便 sleep | 40 个线程被长任务占满，后续排队 | 长任务评估占用，必要时独立队列 |
| 在 def 任务里调 async 代码 | 阻塞 worker 线程等循环 | 线程池任务保持纯同步 |

**面试问法**（30 秒版）："后台任务写 def 还是 async def？"——"看依赖的 SDK：同步客户端写 def，Starlette 自动丢线程池，不堵事件循环；异步客户端写 async def 全程 await。判断标准是调用链里有没有同步阻塞点。"

**追问链**：① 追一层：线程池默认多大？改不改？（anyio 默认 40，CPU/IO 密集不同策略）→ ② 追二层：任务之间有顺序依赖怎么办？（FIFO 顺序执行保证了单请求内的顺序；跨请求的顺序要自己设计）。

### 7. `/openapi.json` 与 `/docs` 的关系

**一句话定义**：`/openapi.json` 是 FastAPI **自动生成**的接口说明书（JSON，OpenAPI 3.1 规范），`/docs` 和 redoc 只是这份 JSON 的两个网页渲染器。

**为什么存在**：接口契约需要机器可读的标准格式——前端据此生成调用代码、测试据此生成用例、网关据此做校验。FastAPI 从类型注解直接推导出它，这是"注解驱动"的红利。

**怎么用**：
```powershell
& .\.venv\Scripts\python.exe -c "from fastapi.testclient import TestClient; from kb_service.main import create_app; import json; s = TestClient(create_app()).get('/openapi.json').json(); print(list(s.keys()))"
```
顶层五键：`openapi`（版本）/ `info`（封面）/ `paths`（正文）/ `components`（配料表）/ `tags`（章节）。

**底层机制**：启动时（首次访问）从路由表扫描——路径参数、query、body、response_model、responses——全部由 Pydantic 模型转成 schema；构建一次缓存在 `app.openapi_schema`。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 只看 /docs 验证 | UI 好看不代表 JSON 对 | 验证以 JSON 为准（/docs 是渲染层） |
| 手改 /docs 页面元素 | 找不到入口 | 所有内容都来自 JSON，去改模型/装饰器 |

**面试问法**（30 秒版）：直接报五个键 + "FastAPI 的文档不是手写的，是从类型注解推导的，所以注解越准文档越准——这也是坚持类型注解的实际收益之一。"

**追问链**：① 追一层：为什么说"注解驱动"？（response_model/参数类型/Field 约束都被扫描进 schema）→ ② 追二层：JSON 什么时候构建？（首次访问，之后走 `openapi_schema` 缓存——实测函数被调 3 次但真构建 1 次）。

### 8. `openapi_tags` + tag 常量纪律

**一句话定义**：`openapi_tags=[...]` 在 JSON 顶层声明分组章节（name + description）；各接口通过 `tags=[...]` 归组。**tag 名是裸字符串，拼错零报错**——所以必须收敛到常量。

**为什么存在**：拼错的 tag 不会报错，只在 `/docs` 上呈现为"无描述的孤立分组"（探针1 §2.4 实测）。零症状错误只能靠纪律防。

**怎么用**（本项目终态）：
```python
# core/constants.py
TAG_KBS = "knowledge-bases"; TAG_DOCS = "documents"; TAG_CHAT = "chat"; TAG_HEALTH = "health"

# main.py
app = FastAPI(..., openapi_tags=[
    {"name": constants.TAG_HEALTH, "description": "..."},
    ...
])
# router.py / health.py include 时全部 tags=[constants.TAG_XXX]
```

**底层机制**：声明与使用是两份独立数据，FastAPI 只做展示聚合不做一致性校验——常量的意义是把两份字符串变成同一份。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 拼错 tag | 无描述分组，零报错 | 常量收敛；CI 可加"声明 vs 使用"一致性检查 |
| 端点级重复写 tags | 双份维护 | tag 在 include 层管，端点不写 |
| description 复读分组名 | 信息量为零 | 写"读者不看代码需要知道的事"（鉴权/错误码约定） |

**面试问法**（30 秒版）：报出"两个机制各管什么"——常量防拼错、openapi_tags 给章节说明，合起来才闭环。

**追问链**：① 追一层：为什么拼错不报错？（tags 只是元数据，FastAPI 不校验声明集合）→ ② 追二层：还有哪些"零症状配置错"？（本日教材两个：tags 拼错、openapi_tags_metadata 缺失；D4 的 health 双挂载同类）。

### 9. 替换 `app.openapi` 必须先存原方法

**一句话定义**：自定义文档结构（如加 servers）的标准姿势是替换 `app.openapi` 方法，**函数体里必须先 `base = app.openapi` 存原方法再调用 `base()`**——直接调 `app.openapi()` 就是自己调自己。

**为什么存在**：替换是"把属性指向你的函数"，函数体内再访问 `app.openapi` 拿到的已经是新函数——无限自我调用。实测 **966 层 RecursionError**（探针1 §5，教材初稿也踩了这个坑）。

**怎么用**：
```python
def custom_openapi() -> dict:
    if app.openapi_schema:
        return app.openapi_schema
    base = app.openapi            # ① 先存原方法（在替换之前这一行已经跑到了？不——此行在函数体内，此刻 app.openapi 已被替换）
    schema = base()               # ↑ 所以正确做法是把 base 的赋值放在替换之前：见教材 D5a §3.4 的完整模板
    ...
```
**更稳的模板**（教材版）：模块级先 `base = app.openapi`，再 `def custom_openapi(): ... schema = base()`，最后 `app.openapi = custom_openapi`。

**底层机制**：Python 属性查找——`app.openapi()` 找的是**实例属性**（后被替换），不是类上的原方法。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 函数体内调 app.openapi() | RecursionError（966 层） | 替换前 `base = app.openapi` |
| 每次请求都重建 schema | 文档接口变慢 | `app.openapi_schema` 缓存判断开头做 |
| custom 忘了返回 dict | /openapi.json 500 | 返回完整 schema dict |

**面试问法**（30 秒版）："怎么给 OpenAPI 文档加全局自定义字段？"——"替换 app.openapi 方法：先保存原方法引用，构建时调用原方法拿基础 schema、改完写回 app.openapi_schema 缓存。直接在函数里调 app.openapi() 会无限递归，因为属性已被替换。"

**追问链**：① 追一层：为什么是实例属性不是类方法？（赋值发生在实例上）→ ② 追二层：还有哪里用同款"先存后换"手法？（装饰器包装、monkey-patch 测试、 TraceMiddleware 那类包一层——本质都是保存原引用）。

### 10. 中间件耗时不含后台任务（TestClient 含）

**一句话定义**：`call_next` 返回的时刻 = 路由处理完成，**不含**后台任务执行时间；TestClient 的总耗时**含**（它等 ASGI 全周期跑完）。

**为什么存在**：D2 的 TraceMiddleware 记的 `duration_ms` 是"服务处理这个请求"的时间。后台任务是响应发出后的副作用，不该计入请求耗时——这个分界不搞清，监控数字会被误读。

**怎么用（实测数字）**：
```
任务耗时 300ms：中间件记录 1.13ms / TestClient 总耗时 305ms
```
→ 线上监控（中间件口径）看不到任务耗时；测试计时含任务。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 用测试耗时评估线上延迟 | "接口怎么突然慢了 300ms"（其实是后台任务） | 分清两种口径；任务耗时单独打点 |
| 给后台任务加进 SLA 计算 | 任务拖累接口指标 | SLA 按"响应发出"口径算 |

**底层机制**：`BaseHTTPMiddleware` 的 `call_next` 在拿到"路由处理完成的响应对象"那一刻返回——此刻后台任务还没开始（它们在更外层的响应发送阶段才跑）。而 TestClient 是把整个 ASGI 应用从请求跑到任务结束才把响应交给测试代码，所以它的计时含任务。

**面试问法**（30 秒版）："TraceMiddleware 记的耗时包不包括后台任务？"——"不包括，call_next 返回即路由处理完成，任务在那之后跑。但 TestClient 等整个 ASGI 周期，测试计时含任务——两种口径要分清。"

**追问链**：① 追一层：那任务耗时怎么监控？（任务体首尾各打一条日志，单独算）→ ② 追二层：这种"口径分叉"还有哪些？（同步 handler 在线程池的排队时间也不在 handler 计时里）。

### 11. 后台任务日志纪律

**一句话定义**：任务体日志只记**调用链事实**（doc_id、耗时、状态），不记业务内容（正文）；异常用 `logger.exception` 记到 ERROR 级。

**为什么存在**：日志会进聚合系统，访问面远大于业务数据——正文进日志等于内容泄露（同类：D4 health 泄露 env）。而 debug 级吞异常 = 线上查无此案。

**怎么用**（本项目终态）：
```python
logger.info("索引开始 doc_id=%s content_len=%s", doc_id, len(content))  # 长度≠内容
...
except Exception:
    logger.exception("索引失败 doc_id=%s", doc_id)   # ERROR + 自动 traceback
```

**底层机制**：日志级别是输出端的**过滤器**（线上常配 INFO）——`debug` 在过滤线之下，记录动作发生了但一个字都不输出；`logger.exception` 则是"在 except 块内调用时自动把当前异常的 traceback 附到 ERROR 级记录上"，省掉手拼 `traceback.format_exc()`。格式串的 `%s` 占位符数量和参数数量由 logging 在**输出时**才对账，不匹配只在触发输出时报错——所以测试全绿也藏得住。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 字段名撒谎（content=%s 传 len） | 读日志的人误判 | 字段名与值语义一致（content_len） |
| 格式串占位符和参数不匹配 | Logging error 一屏 | 删变量=清所有引用点 |
| except 里手动 f-string 拼 exc | 丢堆栈 | logger.exception（它在 except 块内自动捕获） |

**面试问法**（30 秒版）："日志该记什么？"——"调用链事实 + 足够定位的上下文，不记业务内容；异常在 except 块里用 logger.exception 自动带堆栈记 ERROR 级，debug 级在线上等于没记。"

**追问链**：① 追一层：为什么 len 是安全替身？（长度是有用信号、不可逆推原文）→ ② 追二层：要追踪一个 doc 的完整生命周期怎么办？（结构化字段 doc_id + trace_id 贯穿——D2 打下的地基）。

### 12. 204 可与后台任务共存（与 response_model 相反）

**一句话定义**：204 无 body，但后台任务照常执行——任务挂在响应对象的 `background` 属性上，与"有没有 body"无关；而 204 与 `response_model` 是互斥的（body 校验器无处安放）。

**为什么存在**：两者机制不同——`response_model` 是"出口校验器"，作用于 body；后台任务是"响应后的钩子"，作用于连接生命周期。

**怎么用**：
```python
@router.delete("/{kb_id}/documents/{doc_id}", status_code=204)
async def delete_doc(kb_id: UUID, doc_id: UUID, background_tasks: BackgroundTasks,
                     user_id: UUID = Depends(get_current_user_id)) -> None:
    DocService().delete(doc_id, user_id)
    background_tasks.add_task(run_index, doc_id, "")   # 204 照样能挂任务（探针1 §10 实测）
```

**底层机制**：`response_model` 校验的对象是**响应体**——204 没有 body，校验器无处安放，所以互斥；后台任务挂的是**响应对象**（`response.background` 属性），与有没有 body 无关，204 的响应照样能携带任务列表。分界线：一个机制作用于 body，一个作用于连接生命周期。

**易错点**：

| 坑 | 症状 | 正解 |
|---|---|---|
| 以为 204 + 任务不执行 | 删除接口的清理任务"莫名其妙没跑" | 探针1 §10 实测执行正常 |
| 把壳硬塞给 204 | 启动即崩（D4 结论） | 机器消费接口不套壳（同章法） |

**面试问法**（30 秒版）："204 接口能不能挂后台任务？"——"能。任务机制与 body 无关，挂在响应对象上；而 response_model 与 204 互斥，因为它校验的是 body。机器消费的接口（204 探活）不套壳，但可以有副作用钩子。"

**追问链**：① 追一层：204 + 任务，任务异常客户端还是不知道？（是，同知识点 5）→ ② 追二层：这组对比的统一章法是什么？（先问"这个机制的读者是谁"——body 机制读 body，钩子机制读连接）。

## 三、30 秒答案集（速答版）

1. **BackgroundTasks 什么时候跑？** 响应体发送完成后，FIFO 顺序执行；`add_task` 只是登记。
2. **任务慢会拖慢接口吗？** 不会——响应先发；前提是任务不阻塞事件循环（async 任务禁同步阻塞）。
3. **为什么 async 任务里不能 time.sleep？** 事件循环单线程靠协程让出并发，不让出=全服务冻结；改 def 走线程池或 asyncio.sleep。
4. **同步任务在哪跑？** `run_in_threadpool`（anyio，默认 40 线程），实测线程名 AnyIO worker thread。
5. **任务抛异常客户端知道吗？** 永远不知道，响应已完整发出；任务体自己 try + logger.exception。
6. **handler 抛异常，任务跑吗？** 不跑——任务挂在原响应对象上，异常处理器新建的响应没有 background 属性。
7. **生产环境怎么关文档？** 三门全 None：docs_url / redoc_url / openapi_url；只关 /docs 是假关。
8. **/openapi.json 和 /docs 什么关系？** JSON 是本体（说明书），/docs 是渲染器；验证以 JSON 为准。
9. **responses 参数改行为吗？** 不改，纯文档契约；行为由异常处理器决定。
10. **openapi_tags 拼错会怎样？** 零报错，只出现无描述分组——所以 tag 名必须常量化。
11. **自定义 openapi() 的头号坑？** 函数体内调 app.openapi() = 无限递归（实测 966 层）；先 base = app.openapi。
12. **中间件耗时含任务吗？** 不含（call_next 即路由完成）；TestClient 含（等全周期）——测试耗时≠线上耗时。
13. **204 和后台任务冲突吗？** 不冲突（任务与 body 无关）；204 与 response_model 才互斥。
14. **后台任务日志记什么？** 调用链事实（doc_id/长度/状态），不记业务内容；异常用 logger.exception。
15. **什么时候不该用 BackgroundTasks？** 必须成功、要重试/追踪/跨重启的副作用——那是消息队列的事（fire-and-forget 会丢）。
