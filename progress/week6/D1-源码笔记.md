## 第一版（11-05 原话存档）

1. `params.py:745-749`：定义了一个 dataclass，三个字段：dependency / use_cache / scope；为了让 fastapi 区分当前参数是要继续解析依赖还是可以直接求值。
2. `types.py:12`：定义了一个三元组，里面有调用函数，请求操作范围，缓存周期；只是定义 key 里应该有什么，如果有更好的组合也可以换。
3. `models.py:82-96`：定义了一个取得 key 的函数；就是一个函数的正常功能，代码复用吧。
4. `utils.py:622-638`：构建 override 后的函数的依赖树，并且 `getattr(provider, "dependency_overrides", {})` 默认为空字典，这就是传字符串进来也不会报错的原因，只是永远不会执行而已。
5. `utils.py:656-661`：拿到子依赖的 key，检查子依赖开没开缓存，如果开启缓存并且命中缓存，就直接返回；这样设计可以给是否用缓存一个开关。
6. `utils.py:679-680`：若子依赖的 key 没在缓存中，就把 key 和结果存入缓存；这个算是固定语句吧，你要用缓存功能，就必须要有存缓存的操作。

## 批注（11-05）

**① 过。** 主语修正了（FastAPI 区分，不是 Python）。补一层：区分发生在**注册时**（`get_dependant` 扫描签名），不是请求时——"声明依赖"和"执行依赖"分在两个阶段，dataclass 是这两个阶段之间传递的载体。

**② 换词即可。** 两处名字不对：
- 第二项不是"请求操作范围"，是 **oauth scopes**——`Security(scopes=["kb:read"])` 的权限范围，一个 `tuple[str, ...]`
- 第三项不是"缓存周期"，是**依赖生命周期** scope（`"function"` / `"request"` / `""`，一个字符串）
- ✅ "有更好的组合也可以换"这句有批判意识，但要补上边界：**不能随便换**。key 的每一项都是"会影响结果的因素"——不同 scopes 可能解析出不同的值，漏掉任何一个变化维度，两个不同的请求就会错误共享结果（安全漏洞）。设计 cache key 的通用原则：**把所有影响结果的因素都编进去**。实参不进 key 是因为同一请求内同函数的实参必然相同，不存在变化。

**③【需重说】** "代码复用吧" = 放弃思考。真正的原因：**查缓存的人（660 行）和写缓存的人（679 行）必须用同一个函数算 key**。两处各自手拼三元组，迟早拼出不一样的（漏一项、顺序不同），缓存就错乱。集中到一处 = 单一事实来源。

**④ ✅ 今天最大的进步**：630 行的 `.get(original_call, original_call)` 认出来了，静默失效的出处对上了。
但**因果错了**：
- 不报错的原因是 `.get(key, default)` 的语义——查不到就返回默认值（原函数），**不抛异常**
- `getattr(provider, ..., {})` 的空字典是另一件事：防止 provider 压根没有 overrides 属性时炸掉（防御性默认值）
- 两件事都真实，但你把 B 当成了 A 的原因
还漏一层：632 为什么要**重建**子树？因为替身自己的签名要重新解析——你实测过的"替身 `lambda uid: ...` 必须带 `?uid=`"，机制就是这次重建。现象 → 机制，这条线没连上。

**⑤ 过。** `use_cache and` 抓到了（上一版漏的）。补一层：开关在 `Depends` 字段上而不是全局配置，意味着**同一个函数可以在 A 处开缓存、B 处关**——粒度是"每一处挂载点"，不是"每一个函数"（今天实测 [F]：一次带 `use_cache=False` 就跑两次）。

**⑥【需重说】** "固定语句" = 第二次放弃思考。**没有固定语句，每行代码都是某个人做的决定，都能问为什么。**
真正的问题：为什么 `if key not in cache` 而不是直接 `cache[key] = solved`？
- 命中时 `solved` 已经就是缓存里的值，再写一次多余
- 更关键的语义：**第一次算出的结果就是本次请求的权威值**，后面任何挂载点都改变不了它——这正是 §4.3"两个 repo 拿到同一个 session"的保证
