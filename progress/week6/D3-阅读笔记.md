- [x] **`from_attributes` 到底改了校验器的哪一步？**（11-09 提出，当天实测解决）
  **答**：只改**取值那一步**——原本"按键名从 dict 取值"，开启后扩成"dict 按键、对象按 `getattr`"，**是加法不是替换**（`from_attributes=True` 时 dict 照样能进，实测 `{'id':1,'name':'d'}` 正常）。
  后续的成分一步都没变（实测四条证据）：
  - 对象属性是字符串 `'7'` → 结果 `7`（`int`），**类型转换照旧**；
  - 同一对象在 `strict=True` 下 → `int_type` 报错，**严格模式照旧**；
  - `field_validator` 照常执行（实测打印 `v = 7`）；
  - 对象缺该属性 → `missing / Field required`，**必填规则照旧**。
  **一句话**：`from_attributes` 是**输入侧的数据来源开关**，只影响"值从哪来"，不影响"值怎么验"；也不影响输出（`model_dump()` / schema 都不变）。

## 三、读完这一遍，我能用自己的话说出来的三句

> 不许用教材原句。三个锚点各盖一句。**11-09 定稿。**

1. **进** = 客户端发来的 JSON 先被校验再被转换（`'18'` → `18` 是转换，不只是放行），**出** = 服务端响应按声明的模型序列化。进错了是 422（客户端的错），出错了是 500（程序的 bug）——**同一个校验机制，两个位置两种责任**。
2. `response_model` 有两个身份：**过滤器**（模型里没声明的字段静默丢掉）和**校验器**（声明类型 ≠ 实际返回值 → `ResponseValidationError` → 500）。两者是同一段代码的两个角色，顺序是"先过滤转换、再校验"。
3. `AfterValidator` 写进类型别名后，约束从"字段声明"**变成"类型本身的一部分"**——所以子类（`KBUpdate`）不继承基类也不要紧，**约束跟着类型走，不跟着类走**；而 `field_validator` 是跟着类走的，写在 `KBBase` 上就对 `KBUpdate` 无效。
