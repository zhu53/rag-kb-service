## 零、先看主线：一个请求，两条出路

> 全篇地图，先扫 3 分钟。每读完一节回来对一次位置。

D2 的全部内容可以压成一句话：

> **同一个位置，成功了往回穿，失败了往外炸。**

```
【请求进来】
    ↓
 ① ServerErrorMiddleware      最外层，兜"没人管的异常"，500 由它生成
    ↓
 ② RequestBodyLimitMiddleware （可选，项目没开）
    ↓
 ③ 你的中间件（TraceMiddleware）   打点 A> ，记 t0
    ↓
 ④ ExceptionMiddleware         装着 AppError / RequestValidationError 的 handler
    ↓
 ⑤ Router 匹配 path + method   404 / 405 在这出结果，不进 ⑥
    ↓
 ⑥ 依赖树 → handler → 序列化    422 在这；你的异常也从这抛
    ↓
━━━━━━━━━ 从这里分岔 ━━━━━━━━━
    │
    ├─【成了】响应逐层往回穿：⑥→⑤→④→③→①
    │        每层都过手，所以 ③ 能记 status=200/404/422；打点 <A xxx
    │        ③ 里 call_next 之后的代码在这条路上
    │
    └─【败了】异常从 ⑥ 往外飞：飞过一层少一层
             ④ 有 handler → 翻译成 404/422 响应，这条路就变回上面那条
             ④ 没有 handler → 继续飞，③ 的 except 接住（记日志）、raise
             → ③ 的 dispatch 退栈，打点只有 A>，没有 <A
             → ① 生成 500（③ 已经不在场）
```

### 这条分岔就是 D2 的骨架

九个知识点，全是这条线上的不同位置：

| 知识点 | 挂在线上哪 |
|---|---|
| 后 `add` 的中间件在外层 | ①②③ 的**排列顺序**（注册时决定） |
| 响应路径 / 异常路径 | 上面那条**分岔线**本身 |
| `ExceptionMiddleware`（④）与 `ServerErrorMiddleware`（①） | 分岔后**谁接住**：④ 在内、① 在外 |
| 中间件记不到 500 | 异常把 ③ **炸出调用栈**，500 生成时它不在场 |
| `Router` 选路 vs handler 干活 | ⑤ 与 ⑥ 的分界：404/405 在 ⑤，422 在 ⑥ |
| `BaseHTTPMiddleware` 攒完再转发 | 响应路径上"先攒后发"，start 晚发 → 能改 status |
| 校验失败的 500 bug | ⑥ 里 `serialize_response` 之前，`exc.errors()` 不可序列化 |
| `TestClient` 的 `raise_server_exceptions` | 测试侧：异常在到达 ① 之前被测试客户端截走 |
| `ContextVar` vs `request.state` | ③ 里设、⑥ 里读；跨异步任务时 ContextVar 才跟着走 |

### 用一段话把九个点串起来

请求进来，先穿 ①（外套）、③（你的日志中间件，打 `A>`）、④（handlers 就位），进 ⑤ 匹配路由——**路径不对就是 404，方法不对就是 405，这两个连 ⑥ 都没进**。

匹配上了，进 ⑥：先跑依赖树（422 在这，此时依赖已经跑过），再调你的函数，最后序列化。

**到这里命运分岔**：

- 一切正常 → 响应从 ⑥ 往回穿，每层都过手，③ 打出 `<A 200` 并记下状态码。
- 你的函数抛 `AppError` → 异常往外飞，④ 接住、翻译成 404 响应 → 于是又变回"响应往回穿"，③ 仍然看到 `<A 404`。**这就是为什么中间件能记业务错误、却记不到 500。**
- 你的函数抛 `RuntimeError`（没人注册 handler）→ 飞过 ④、飞进 ③ 的 `call_next` 抛出 → ③ 的 `except` 记一笔然后 `raise` → **`dispatch` 到这里退栈，`<A` 永远打不出来** → 异常继续飞到 ①，① 生成 500。**500 出生时，③ 已经死了。**

## 一、痛点场景：如果没有中间件和异常处理器

### 1.1 只有路由函数的世界

先别想框架。假设你只有一堆处理函数，每个都要自己做三件事：

```python
def list_kbs(request):
    start = time.perf_counter()
    trace_id = request.headers.get("X-Trace-Id") or uuid4().hex[:16]
    try:
        user_id = parse_token(request)        # 鉴权
        rows = repo.list_all(user_id)         # 业务
        result = {"data": rows}
    except TokenExpired:
        return {"status": 401, "msg": "token 过期"}      # 每处格式都不一样
    except NotFound:
        return {"error": "not found", "code": 404}       # 又一种格式
    except Exception:
        log.exception("boom", extra={"trace_id": trace_id})
        return {"message": "服务器错误"}                  # 第三种格式
    finally:
        log.info("req", extra={"path": request.path,
                               "ms": (time.perf_counter() - start) * 1000})
    return result
```

**三个问题，每个都不是"代码丑"这么轻**：

| 问题 | 后果 |
|---|---|
| 三处错误各写一种格式 | 前端要为每个接口写一套解析；改一次格式要改 40 个函数 |
| 每加一个接口就复制一遍计时/trace_id | 漏写的地方，出事时正好没有日志 |
| 业务代码里混着 `request` 和 `return {"status": 401}` | service 层没法单测，也没法被 CLI 复用 |

### 1.2 两样东西各管一件事

- **中间件（middleware）**：**竖着管**。请求进来时穿过它，响应出去时再穿过它。
  适合做"每个请求都要做一次"的事：计时、trace_id、CORS、限流、gzip。
- **异常处理器（exception handler）**：**横着管**。平时不执行，只有异常抛出时才被调用。
  适合做"把内部异常翻译成对外格式"：`AppError` → `{"code","message","detail"}`。

它们互不相干，但**谁在里面、谁在外面**，决定了"异常发生时谁能看见"——这就是今天的全部内容。

改造之后，路由函数变成：

```python
def list_kbs(user_id: UUID = Depends(get_current_user_id)) -> list[KBOut]:
    return kb_service.list_all(user_id)      # 只管业务
```

计时、trace_id、异常翻译全都不在这 3 行里。**这就是今天要讲清的那套机制在替你干活。**

## 二、最小可跑示例（5 分钟亲手跑）

新建 `/tmp/d2_demo.py`（Windows 放任意目录），把下面整段贴进去：

```python
from fastapi import FastAPI, Request
from fastapi.testclient import TestClient
from starlette.middleware.base import BaseHTTPMiddleware, RequestResponseEndpoint
from starlette.responses import Response

log: list[str] = []


class M1(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next: RequestResponseEndpoint) -> Response:
        log.append("M1 进")
        resp = await call_next(request)
        log.append(f"M1 出 {resp.status_code}")
        return resp


class M2(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next: RequestResponseEndpoint) -> Response:
        log.append("M2 进")
        resp = await call_next(request)
        log.append(f"M2 出 {resp.status_code}")
        return resp


class Boom(Exception):
    pass


app = FastAPI()


@app.get("/ok")
def ok() -> dict[str, str]:
    log.append("handler 执行")
    return {"ok": "1"}


@app.get("/boom")
def boom() -> None:
    raise Boom("业务炸了")


@app.exception_handler(Boom)
async def handle_boom(_: Request, exc: Boom) -> Response:
    log.append("异常处理器执行")
    return Response(content='{"code":"BOOM"}', status_code=400,
                    media_type="application/json")


app.add_middleware(M1)      # 先加
app.add_middleware(M2)      # 后加

with TestClient(app) as c:
    log.clear()
    print(c.get("/ok").json(), log)

    log.clear()
    r = c.get("/boom")
    print(r.status_code, r.text, log)
```

跑法：

```powershell
# Windows PowerShell（在 kb-service 下，用项目解释器）
& .\.venv\Scripts\python.exe C:\path\to\d2_demo.py
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/python.exe /tmp/d2_demo.py      # Linux 上是 .venv/bin/python
```

**实际输出（本机实测）**：

```
{'ok': '1'} ['M2 进', 'M1 进', 'handler 执行', 'M1 出 200', 'M2 出 200']
400 {"code":"BOOM"} ['M2 进', 'M1 进', '异常处理器执行', 'M1 出 400', 'M2 出 400']
```

两个反直觉的地方，先记住，第三节解释：

1. **先 `add` 的 M1 反而在里面**（M2 先进）。
2. **异常处理器执行完，M1 拿到的是 200 或 400 的正常响应**——它压根不知道刚才发生过异常。

## 三、概念逐层：洋葱是怎么套起来的

### 3.1 `add_middleware` 是 insert(0)：后加的在外层

源码只有两行（`starlette/applications.py:104-107`）：

```python
def add_middleware(self, middleware_class, *args, **kwargs) -> None:
    if self.middleware_stack is not None:
        raise RuntimeError("Cannot add middleware after an application has started")
    self.user_middleware.insert(0, Middleware(middleware_class, *args, **kwargs))
```

`insert(0)` = 插到列表**最前面**。而构建栈时是**按列表顺序从外往里包**的，所以"列表第一个"= "最外层"。

于是：先 `add(M1)`、后 `add(M2)` → 列表是 `[M2, M1]` → M2 在外层 → **M2 的 `dispatch` 先执行、后返回**。

**为什么这么设计？** 因为这样写出来符合人的阅读顺序——后写的中间件（往往是最新加的、最外层的功能，比如 CORS）盖在已有的上面。代价是它和"按声明顺序执行"的直觉相反，所以必须记牢：**后加的在外面**。

> 一个能立刻用的判据：**最外层中间件 = 你最后 `add` 的那个**。项目里 `TraceMiddleware` 是 `create_app` 里唯一一个 `add_middleware`，所以它在用户中间件层里**唯一**，无所谓顺序。

### 3.2 完整的洋葱：像穿衣服一样包出来

先别管列表顺序，看**包裹的过程**——它就是穿衣服：

```
起点：router（路由器）光着身子，只会匹配路径、调 handler

第 1 穿：套上 ④ ExceptionMiddleware      ← 贴身内衣，兜"注册过 handler 的异常"
第 2 穿：套上 你的 TraceMiddleware        ← 你 add 的
第 3 穿：套上 ① ServerErrorMiddleware    ← 最外面的大衣，兜"没人管的异常"
```

**最后穿上的在最外面。** 所以从外到内是 `① → 你的 → ④ → router`，请求进去一层层穿，响应出来一层层脱。

源码就这几行（`starlette/applications.py:63-83`），对照穿衣顺序看：

```python
middleware = [Middleware(ServerErrorMiddleware, ...)]    # ① 第一个进列表 → 最后穿
middleware += self.user_middleware                        # 你 add 的（add 时 insert(0)，倒序）
middleware.append(Middleware(ExceptionMiddleware, ...))   # ④ 最后进列表 → 最先穿

app = self.router                          # 光着身子的 router
for cls, args, kwargs in reversed(middleware):   # 从列表末尾开始 → 从 ④ 开始穿
    app = cls(app, ...)                    # 每穿一件，新的包住旧的
```

列表顺序和穿衣顺序正好相反，这就是它绕的原因：**列表是 `[①, 你的, ④]`，反转后从 `[④, 你的, ①]` 开始循环，循环里"新的包住旧的"——最后包上的 ① 落在最外面**。把这两行循环读透，"后 add 的在外层"就不用背了。

项目没配 `max_body_size`，所以框架的 `RequestBodyLimitMiddleware` 不存在，你的项目拼出来一共四层：

```
①  ServerErrorMiddleware      框架最外层，兜"没人管的异常"
│
③  TraceMiddleware            你 add 的（项目只有这一个用户中间件）
│
④  ExceptionMiddleware        你 @app.exception_handler 注册的 handler 装在这里
│
⑤  Router（匹配路径） → ⑥ 依赖解析 + 路由函数
```

（编号沿用六层的说法，② 跳过。）

如果更想看"包完之后长什么样"（含可选的 ②），是这样的洋葱——**外层的框包住内层全部**：

```
┌─ ① ServerErrorMiddleware ────────────────────────────┐
│   500 在这里兜底（没人管的异常最终落点）               │
│  ┌─ ② RequestBodyLimitMiddleware（可选，项目没有）──┐ │
│  │  ┌─ ③ 你的中间件（TraceMiddleware）────────────┐ │ │
│  │  │   call_next 前后都能干活；记不到 500          │ │ │
│  │  │  ┌─ ④ ExceptionMiddleware ────────────────┐ │ │ │
│  │  │  │   AppError / RequestValidationError    │ │ │ │
│  │  │  │   两个 handler 装在这里                 │ │ │ │
│  │  │  │  ┌─ ⑤ Router ───────────────────────┐ │ │ │ │
│  │  │  │  │   匹配路径 → ⑥ 依赖解析 + 路由函数 │ │ │ │ │
│  │  │  │  └──────────────────────────────────┘ │ │ │ │
│  │  │  └────────────────────────────────────────┘ │ │ │
│  │  └─────────────────────────────────────────────┘ │ │
│  └──────────────────────────────────────────────────┘ │
└───────────────────────────────────────────────────────┘
```

读法：**一个请求从最外框进，一层层穿到 ⑥；响应原路穿回来；异常从 ⑥ 向外飞——遇到没注册 handler 的框就穿透它，直到 ①。** 两个箭头方向（请求向内、异常向外）都在这张图上，"中间件为什么记不到 500"就是异常在 ③ 那个框里把 ③ 炸掉了。

**这张图是今天唯一需要背下来的东西。** 但光背图还差半步——**一个请求在洋葱里有两种"出去的方式"，两条路完全不同**：

```
方式一：正常返回（响应路径）
  ⑥ handler 的返回值 → ④ 过手 → ③ 过手 → ① 过手 → 客户端
  每一层都活着、都过手 → 所以 404/401/422 你的中间件都看得见

方式二：异常抛出（异常路径）
  ⑥ 抛出 → 向上飞 → 每一层的 except 都在飞行路径上
  谁 catch 了、catch 后有没有再 raise，决定异常死在哪、活到哪
```

关键区别：**响应是"活着逐层经过"；异常是"飞过一层，炸死一层"**。一层只要 catch 后 re-raise，它自己就结束了（函数返回、退出调用栈）——之后发生的一切它都收不到。这就是"为什么中间件记不到 500"的完整原因：不是看不见，是**它已经死了**。下一节逐步追踪给你看。

### 3.3 你的项目现在长什么样

`kb-service/src/kb_service/main.py`：

```python
app.add_middleware(TraceMiddleware)            # ③ 用户中间件层

@app.exception_handler(AppError)               # ④ ExceptionMiddleware 里
@app.exception_handler(RequestValidationError) # ④ 同上

app.include_router(api_router, prefix="/api/v1")   # ⑤
```

所以项目现在的实际层次是：

```
① ServerErrorMiddleware
   ③ TraceMiddleware
      ④ ExceptionMiddleware（装着 AppError / RequestValidationError 两个 handler）
         ⑤ Router → ⑥ deps + 路由函数
```

由此推出两条结论（下节都有实测）：

1. **`TraceMiddleware` 里的 `call_next()` 拿到的是已经翻译好的响应**——`AppError` 在 ④ 就被接住变成了 404 响应，走到 ③ 时异常早就没了，只剩一个普通的 404。所以它能记 `status=404`。
2. **它记不到 500**——500 是 ① 造的，而那时 ③ 已经被异常炸出调用栈。不是"看不见"，是"它已经死了"。

### 3.4 ⑤ Router 和 ⑥ deps+handler 到底差在哪

图上把它俩画成两个相邻的框，容易误读成"两个可以插东西的层"。区别只有一句话：

> **⑤ 只负责"选路"，⑥ 才开始"干活"。**
> 选路只看两样东西——**path** 和 **method**，不看你的函数签名、不查库、不开事务、不跑任何依赖。

用寄快递打比方：⑤ 是分拣中心，看地址把包裹分到哪个区，**不拆包裹**；⑥ 是派送站点，拆包、验货、签收。地址写错（404）或者渠道不对（405），包裹根本没被拆开过。

#### 判据：依赖跑不跑（实测）

探针 `progress/week6/D2-探针-router与handler.py` 里，依赖 `dep_track()` 只做一件事——往列表里记一笔。六种请求的结果：

| 情况 | 状态码 | 依赖跑了吗 | 卡在哪 |
|---|---|---|---|
| 正常请求 | 200 | ✅ 是 | 走完全程 |
| 路径不存在 | 404 | ❌ 否 | ⑤ 就停了（一个 route 都没匹配上） |
| 方法不对（GET 打 POST 路由） | 405 | ❌ 否 | ⑤ 就停了（path 匹配、method 不匹配） |
| query 类型错（`?n=abc`） | 422 | ✅ **是** | ⑥ 里，依赖已跑、handler 没跑 |
| body 校验失败 | 422 | ✅ **是** | 同上 |
| body 正常 | 200 | ✅ 是 | 走完全程 |

**这张表是今天最实用的东西**，它同时回答两个排错问题：

- 看到 **404 / 405** → 不要去看 Pydantic、不要看依赖，问题在路径或方法上。
- 看到 **422 且依赖里有副作用**（写审计日志、开事务、加计数器）→ **副作用已经发生了**。因为参数校验发生在依赖之后，W7 写事务时这意味着"校验失败的请求也会走 teardown 回滚"，不是"什么都没做"。

#### ⑤ 不是一个对象，是 2–3 层递归

`app.include_router(api_router, prefix="/api/v1")` 在 0.150.0 里**不是把路由拍平**，而是塞一个 `_IncludedRouter` 包着原 router（`fastapi/routing.py:1643`），匹配时递归下去。项目实际结构（实测打印）：

```
Router（app 本身）
├── Route /openapi.json, /docs ...        ← 框架自带
└── _IncludedRouter                        ← api_router，prefix=/api/v1
    ├── _IncludedRouter → APIRoute /health
    ├── _IncludedRouter → APIRoute (kbs 的 6 条)
    ├── _IncludedRouter → APIRoute (documents 的 4 条)
    └── _IncludedRouter → APIRoute /chat
```

所以"⑤ Router"在真实调用栈里是**2–3 层 `Router.app` 嵌套**，每层都做同一个动作（`starlette/routing.py:680-700`）：

```python
for route in self.routes:
    match, child_scope = route.matches(scope)   # 只比对 path/method
    if match == Match.FULL:
        scope["route"] = route
        await route.handle(scope, receive, send)  # 交出去，本层结束
        return
```

`matches()` 全程**不碰请求体、不跑依赖**——它手里只有 `scope` 里的 path 和 method。这就是"404 时依赖不跑"的源码级原因。

#### ⑥ 是 `route.handle` 之后的三段，没有名字

匹配上之后，`APIRoute.handle`（`fastapi/routing.py:1312`）交给 `get_request_handler` 生成的闭包（定义在 397 行，内部函数叫 `app`，428 行），里面就三件事，按顺序：

| 行号 | 做什么 | 失败了会怎样 |
|---|---|---|
| `routing.py:511` | `solve_dependencies(...)` —— 跑整棵依赖树 | 依赖自己参数错 → 422；依赖抛异常 → 冒出去 |
| `routing.py:745` | `run_endpoint_function(...)` —— 调你的函数 | 你的异常从这里开始冒 |
| `routing.py:767` | `serialize_response(...)` —— 按 `response_model` 序列化 | 返回类型不符 → `ResponseValidationError`（500） |

**注意 511 在 745 之前**：依赖先跑，你的函数后跑。这就是上表里"422 时依赖已经跑过"的原因。

#### 一句话记住

| | ⑤ Router | ⑥ deps + handler |
|---|---|---|
| 动词 | **选**（which） | **做**（do） |
| 输入 | `scope` 里的 path + method | 完整请求（body、query、header）+ 依赖树 |
| 会失败成 | 404 / 405 | 422 / 业务异常 / 500 |
| 依赖跑吗 | **不跑** | 先跑依赖，再跑 handler |

顺带一个能直接用在面试里的说法：**"FastAPI 的 404 和 422 是两个阶段产生的——404 在路由匹配阶段（还没进依赖），422 在依赖解析阶段（依赖已执行）。所以鉴权写成依赖时，404 路径是不鉴权的；要连 404 都记审计，只能放中间件。"**

### 4.1 三类异常，三条完全不同的路

**先约定记号（本节和 §4.2 都用它）**：探针里的中间件叫 `A`，它只在两个位置打日志——

```python
async def dispatch(self, request, call_next):
    log.append("A>")                    # ← 进入 A，还没碰下游
    resp = await call_next(request)     # 请求往里钻；响应从这里回来
    log.append(f"<A {resp.status_code}")  # ← A 拿到了响应
    return resp
```

| 记号 | 打在哪 | 含义 | 有没有状态码 |
|---|---|---|---|
| `A>` | `call_next` **之前** | 请求**进入** A 这层（`>` 指向里，还没往下走） | 没有，响应还不存在 |
| `<A 404` | `call_next` **之后** | 响应**回到** A 这层（`<` 指向外，往回流） | 有，响应对象已生成 |

所以读日志只看一件事：**成对出现才算这一层活着走完一圈**。`A>` 出现、`<A` 没出现 = 请求进去了但没出来 = 异常在 A 内部（或更深）抛出，把 `dispatch` 炸死在 `await` 那一行。

多层嵌套时顺序一定是 `A> B> handler <B <A`——进最外层先，出最外层最后。

| 抛出什么 | 谁接住 | 中间件看得见吗 | 客户端收到 |
|---|---|---|---|
| `AppError` 子类（`NotFoundError` 等） | ④ ExceptionMiddleware 查 handler 表 | **看得见**：`<A 404` | `{"code":"NOT_FOUND"}` |
| `starlette.exceptions.HTTPException` | ④ ExceptionMiddleware 的**内置默认 handler** | **看得见**：`<A 418` | `{"detail":"teapot"}` |
| 未捕获的 `RuntimeError` | ① ServerErrorMiddleware | **看不见**：只有 `A>`，没有 `<A` | 纯文本 `Internal Server Error` |

实测输出（编号见上表，逐字复制自 `D2-探针.py` 的运行结果）：

```
[A] 正常请求（对照组）
    log: ['A>', '<A 200']      | status: 200 | body: {"ok":"1"}

[B] 路由抛 AppError 子类
    log: ['A>', '<A 404']      | status: 404 | body: {'code': 'NOT_FOUND'}

[C] 路由抛 HTTPException(418)
    log: ['A>', '<A 418']      | status: 418 | body: {'detail': 'teapot'}

[D] 路由抛 RuntimeError（没注册通配 handler）
    log: ['A>']                | status: 500 | body: Internal Server Error

[F] 路由不存在（框架自己抛 404）
    log: ['A>', '<A 404']      | status: 404 | body: {'detail': 'Not Found'}

[E] 绕过 TestClient，直接调 ASGI（等价于 uvicorn 视角）
    已发出的 ASGI 消息: ['http.response.start', 'http.response.body']
    status: 500 | 冒到 ASGI 层的异常: ['RuntimeError']
```

前四行对照着看，`[A]` 是"一切都正常"的基准：`A>` 和 `<A 200` 成对。`[B] [C] [F]` 也是成对，只是状态码不同——**中间件看得到这些错误，因为它拿到的是响应**。`[D]` 只有 `A>`，没有 `<A`。

**D 那行是今天最该记住的一行**：日志里只有 `A>`，没有 `<A`。为什么？逐步追踪一遍，六步：

| 步 | 发生了什么 | 此时你的 dispatch |
|---|---|---|
| 1 | ⑥ 路由函数抛 `RuntimeError` | 在调用栈上（还没被波及） |
| 2 | 异常向上飞，④ 没有对应 handler，不接 | 同上 |
| 3 | 异常飞进 ③ 的 `await call_next(request)`，从这里抛出 | `except Exception:` 捕获，记一笔日志 |
| 4 | 你的代码执行 `raise` → **dispatch 函数结束，退出调用栈** | **死了。** `<A` 那行日志永远执行不到 |
| 5 | 异常飞到 ① 的 `except`，① 自己造 500 响应并发出 | 已死，收不到任何东西 |
| 6 | ① 还会把异常**继续往上抛给 ASGI 服务器**（uvicorn 记 error 日志） | 与你无关了 |

所以"客户端收到 500"和"异常穿透整个 app"是**同时成立**的（`[E]`：`http.response.start/body` 都发出去了，`status: 500`，同时 `RuntimeError` 冒到了 ASGI 层）。你的中间件不是"错过了 500"，是**500 发生时它已经不在场**。

### 4.2 为什么 `Exception` 通配 handler 也"轮不到"中间件

**先说病根**：这段读不懂，几乎都是因为把「谁先收到请求」当成了「谁先捕获异常」。**这两个顺序是相反的。**

请求是**从外往里**走（① → ③ → ⑥）；异常是**从里往外**飞（⑥ → ③ → ①）。所以：

| | 谁在前 | 因为 |
|---|---|---|
| 请求方向 | ①（最外层） | 先穿外套再穿内衣，最外层先碰到请求 |
| 捕获异常的方向 | ③（内层） | 谁离抛出点近，谁先碰到异常 |

**中间件"先捕获"，不是因为它在请求里先跑，而是因为它在调用栈里离异常更近。** 这两件事在脑子里必须是两个方向，一旦并成一个，"handler 后执行"就永远想不通。

#### 把三层压成三个函数，10 秒跑一遍

框架的层层包裹，本质就是函数嵌套调用。把洋葱压扁成三个普通函数，`[J]` 的顺序立刻不神秘了：

```python
from __future__ import annotations

log: list[str] = []


def layer6() -> None:          # 路由 / 依赖（最里面）
    log.append("⑥ 抛出")
    raise RuntimeError("炸了")


def layer3() -> None:          # 你的 TraceMiddleware（中间）
    log.append("A>")
    try:
        layer6()
    except Exception:
        log.append("A 捕获到")
        raise                  # ← 记完原样往外扔，不吞


def layer1() -> None:          # ServerErrorMiddleware + 通配 handler（最外面）
    try:
        layer3()
    except Exception as exc:
        log.append(f"① handler 收到 {type(exc).__name__}")


layer1()
print(log)
```

实际输出（本机实测，一个字都不差）：

```
['A>', '⑥ 抛出', 'A 捕获到', '① handler 收到 RuntimeError']
```

对着这个输出看三件事，比读十遍"飞行顺序"有用：

1. `A>` 最先打——因为**请求经过它时**它就在打点，跟异常无关。
2. `A 捕获到` 排在 `⑥ 抛出` **之后**——因为它是"事后"才知道的，异常得先发生。
3. `① handler 收到` 排在**最后**——因为 ① 在 ③ 外面，是 `raise` 之后才轮到的下一站。

Python 的 `except` 只有一条规则：**异常沿调用栈逐层向外找，碰到第一个 `except` 就停**。① 在 ③ 外面，所以永远排在 ③ 后面。

#### 框架为什么非要把 `Exception` handler 拎到最外层

看源码（`applications.py:68-72`）：

```python
for key, value in self.exception_handlers.items():
    if key in (500, Exception):
        error_handler = value            # ← 交给 ServerErrorMiddleware（①）
    else:
        exception_handlers[key] = value  # ← 交给 ExceptionMiddleware（④）
```

设计意图只有一句：**`Exception` 这个 handler 的职责是"兜住所有没人接的异常"，所以它必须站在所有层的门外**。如果它像 `AppError` 的 handler 一样待在 ④，那 ③ 自己抛出的异常（比如记日志时炸了）就没人兜，进程直接崩。

由此得到两条对照，正好是 §4.1 那张表的来源：

| 抛什么 | handler 在哪 | ③ 看到的是 |
|---|---|---|
| `AppError` 子类 | ④（③ 里面） | **响应**（`<A 404`） |
| 未捕获 `RuntimeError` | ①（③ 外面） | **异常**（只有 `A>`） |

#### 先看两次运行的原始输出

`[I]` 和 `[J]` 是**同一段代码的两次运行**，唯一差别是后一次多写了一行 `@app.exception_handler(Exception)`：

```
[I] 没注册通配 handler
    log: ['A>', 'A 捕获到 RuntimeError']   | status: 500 | body: Internal Server Error

[J] 注册了 @app.exception_handler(Exception)
    log: ['A>', 'A 捕获到 RuntimeError', '通配 handler 收到 RuntimeError']
                                          | status: 500 | body: {"code":"INTERNAL"}
```

两次的 `call_next` **都抛了**——`A 捕获到` 在两组里都出现。差别只在最后：`[J]` 少了一次"纯文本 500"，因为有人在终点把它改写成了 JSON。这就是"handler 改得了响应、改不了路径"的全部证据。

（`A 捕获到` 这条日志是探针里中间件在 `except` 分支加的；项目里的 `TraceMiddleware` 记的是 `request_failed`，位置完全一样。）

#### 逐行读 `[J]` 的日志

```
[J] log: ['A>', 'A 捕获到 RuntimeError', '通配 handler 收到 RuntimeError']
```

| 步 | 谁打的 | 此刻发生了什么 |
|---|---|---|
| 1 | ③ | 请求进到中间件，`await call_next` 之前 |
| 2 | ③ 的 `except` | 异常飞回来，被 ③ 接住（它比 ① 近） |
| 3 | ① | ③ `raise` 之后，异常继续飞到终点，handler 才执行 |

第 2 步有个容易忽略的点：**打了一行日志，不等于它处理了这个错误**。③ 只记录，然后 `raise` 原样放行。它手里自始至终是异常对象，**不是响应**。

#### "handler 改变了响应，改不了飞行路径"——拆成两句

**第一句：路线不由 handler 决定。**
注册 `Exception` handler 之前（`[I]`）和之后（`[J]`），异常都要经过 ③ 的 `except`——因为源码把 handler 放在 ①，而 ③ 在 ① 里面。所以「加了 handler，中间件的 `call_next` 就不抛了」是错的：实测两组的 `call_next` **都抛**。

**第二句：③ 拿不到 handler 造出来的那个 500 响应。**
handler 在 ① 生成响应时，③ 的 `dispatch` 函数早已因为 `await` 处抛出而结束——就是 §4.1 里"只有 `A>`、没有 `<A`"那件事。函数退栈了，后面的代码不可能再执行，所以永远记不到 `status=500`。

一句话：**handler 只决定"最后有没有人把异常变成响应"，决定不了"异常路上撞到谁"。**

#### 所以中间件的错误日志只能这么写

这就是项目里 `TraceMiddleware`（`core/logging.py:86-108`）为什么写成两条路径：

```python
try:
    response = await call_next(request)
except Exception:
    logger.exception("request_failed", extra={... duration_ms ...})  # ← 异常路径
    raise
# 能走到这里，说明真的拿到了响应
logger.info("request", extra={..., "status": response.status_code})  # ← 响应路径
```

**拿到响应 → 记 `status`；拿到异常 → 记 `request_failed` 并带上 `duration_ms`。** 想在 `except` 里写 `status=500` 是写不出来的——那一刻根本没有 response 对象。这也是 §4.3 要讲的：这段 `except` 不是"兜底"，它是中间件唯一能记录 5xx 的位置。

#### 自查三句

1. 请求和异常，哪个顺序是反的？——请求从外往里，异常从里往外。
2. 为什么 ③ 先捕获、① 后执行？——③ 在调用栈里离抛出点更近。
3. 注册了 `Exception` handler，③ 的 `call_next` 还抛吗？——抛。handler 在 ①，比 ③ 更外面，所以异常先撞到 ③，再飞到 ①。

### 4.3 那 `TraceMiddleware` 里那段 `except` 是干什么的

```python
try:
    response = await call_next(request)
except Exception:
    logger.exception("request_failed", extra={...})   # 记一笔，然后
    raise                                             # 必须再抛
```

它唯一的作用是**在异常冒到 ① 之前留下一份带 trace_id 的日志**（第 3~4 步之间）。它不能造响应、不能改状态码，只能记录然后放行。

`raise` 那行删掉会怎样？**实测和直觉完全不同**——不是"客户端等到超时"：

```
dispatch 吞掉异常 → 函数没有 return → 隐式返回 None
  → 框架把 None 当响应用 → 立刻 TypeError
  → 又一个未捕获异常 → 冒到 ① → 客户端收到 500
```

而且更糟：注册了通配 handler 后实测，**handler 看到的异常是 `TypeError`，不是 `RuntimeError`**——真凶彻底消失，错误信息指向了一个根本不存在的 bug。所以这条要这么记：

**中间件里捕获异常后不 re-raise = 两个错误一起犯：真凶被吞 + 报错指向假凶手。** 比"等到超时"严重得多，因为它会把你（或同事）的排查方向带偏到框架内部。唯一合法的例外：你 catch 后**返回一个新的 Response**（比如降级响应），那是"决定不抛"，不是"吞"。

### 4.4 一条重要推论：401/403/404/422 都能记到 status，500 不能

因为前四者都在 ④ 或 ⑤ 生成，是**正常返回**；只有"没人接"的异常才会冒到 ①。

所以线上排查时，"access 日志里只有 `request` 没有 `request_failed`" 和 "只有 `request_failed` 没有 `request`" 是两种完全不同的故障：
- 前者：请求正常结束，状态码是你自己返的 4xx。
- 后者：**500 了**，而且那条 `request_failed` 就是你唯一能拿到的线索。

这个区分在你 D1 之前写的 `logging.py` 里已经天然成立，只是当时不知道为什么。

## 五、`BaseHTTPMiddleware` 的三个常见说法（两个是传说）

这三个说法你在任何一篇"FastAPI 中间件避坑"文章里都能看到。今天在这台机器上逐条跑完，结论是：**只有第三个成立**。前两个是旧版本（或纯 ASGI 中间件）时代的经验，被一代代复制到现在，早已和 1.9.0 的实际行为对不上。

这一节真正要学的是**怎么把"传说"和"事实"分开**：写 10 行探针，跑一次，比读十篇文章可靠。

### 5.1 说法一（错）：读完 body，下游就读不到了

你一定见过这句话："在 `BaseHTTPMiddleware` 里 `await request.body()` 之后，下游路由就读不到 body 了。"

**在本机 starlette 1.9.0 上，这是错的。** 实测：

```
[G] 中间件先读 body，再 call_next
    log: ['BodyReader 读到 b\'{"a":1}\'', 'handler 读到 b\'{"a":1}\''] | status: 200 | body: {'a': '1'}
```

中间件读了一次，下游 handler **照样读到了完整 body**。原因是新版 `BaseHTTPMiddleware` 用 `_CachedRequest` 把 body 缓存下来并在下游重放。

但**这不代表可以随便读**，真正的代价是另外两条：

1. **整个 body 进内存**。传 500MB 文件的接口，读一次 body 就等于把 500MB 塞进进程内存。中间件只该读 header。
2. **它把"流"变成了"块"**。SSE（你项目里的 `/chat`）或大文件下载，本质是边生成边发；中间件一旦 `await request.body()` 或包装了响应流，流式语义就没了。

所以正确做法不是"记住一个坑"，而是：**中间件只碰 metadata（path、header、method、耗时），不碰 body**。

> 这条要特别留意：**技术断言必须在自己项目的版本上跑一遍**。"大家都说 X"在 0.x / 1.x 之间经常反转——W5 那次 `datetime.now()` 精度（3.11 只有 15.6ms）也是同一类教训。

### 5.2 说法二（错，但差一点就对）：`call_next` 返回之后，状态码改不了了

网上原话是：

```python
resp = await call_next(request)
resp.status_code = 201        # ← 据说无效
resp.headers["x-added"] = "1" # ← 据说有效
```

**实测 `[M]`：两个都有效。**

```
[M] BaseHTTPMiddleware：call_next 返回后改 status_code / 加 header
    log: ['x-added: 1', 'status_code 改成 418 后，客户端看到 418'] | body: {'a': '1'}
```

客户端真的收到了 418，header 也在。所以这条"坑"在 `BaseHTTPMiddleware` 上不成立。

#### 为什么它不成立——因为 start 被"扣住"了

`BaseHTTPMiddleware` 内部把下游的 `send` 换成了一个**内存队列**：下游调用 `send(http.response.start)` 时，这条消息只是被记下来，并没有真的发给客户端；等你的 `dispatch` 返回之后，框架才把攒下的消息按顺序重发。既然整个 dispatch 期间 start 都没出去，你在这段时间里改 `status_code` 当然算数。

#### 那什么情况下真的改不了——`[N]` 给了界线

换成**纯 ASGI 中间件**（自己写 `send` 转发），结论就翻过来：

```
[N] 纯 ASGI 中间件：转发 start 之前改有效，之后改无效
    log: ['buffer 模式，客户端看到 418', 'forward 模式，客户端看到 200']
```

| 写法 | start 什么时候出去 | 事后改 status |
|---|---|---|
| 攒完再转发（`buffer`，`BaseHTTPMiddleware` 就是这么干的） | dispatch 返回后 | **有效**（418） |
| 边收边转发（`forward`，手写 ASGI 中间件的默认写法） | 下游发的那一刻 | **无效**（还是 200） |

所以真实的规则不是"中间件改不了状态码"，而是：**谁最后写 `http.response.start`，谁说了算**——ASGI 协议里状态码只存在于这一条消息里，消息发出去了，改 Python 对象上的属性只是自娱自乐。

#### 能改，但别靠它

这条能力是**实现细节，不是契约**：它依赖于"BaseHTTPMiddleware 会缓冲 start"，版本一换就可能变；而且"中间件偷偷改状态码"会让调用方在路由里写的 `status_code=201` 莫名其妙变成 418，排查时极难定位。

正确处理是：**要改结果，就去改产生结果的地方**（路由的 `status_code` 参数、异常 handler 返回的 `Response`）。中间件只做旁观者——加 header、记日志、埋 trace_id 这些"附加信息"才是它的本职。

> 这里和 D1 的 `scope` 要分开看，别混成一条：**yield 依赖的 teardown 默认在响应发出之后跑，那时确实改不了状态码**（实测过 200 vs 500）；而 `BaseHTTPMiddleware` 的 `dispatch` 跑在响应发出**之前**，所以能改。区别不在"是不是中间件"，在"跑在 start 之前还是之后"。

### 5.3 坑三（真的）：流式响应下，中间件的耗时是假的

`resp = await call_next(request)` 返回时，**body 还没发送**（`BaseHTTPMiddleware` 给的是一个 wrapper）。
所以在中间件里算 `time.perf_counter()` 差值，量到的是"路由函数跑完的时间"，**不是"客户端收完的时间"**。

对 SSE 的影响：`/chat` 流式生成 10 秒，中间件记录的 `duration_ms` 可能只有 30ms（生成器还没开始消费）。
**面试如果问"你的接口耗时日志准吗"，这就是标准答案的抓手**：普通 JSON 接口准，流式接口需要监听 `http.response.body` 的最后一帧（纯 ASGI 中间件才能做到）。

## 六、trace_id：为什么用 `ContextVar` 而不是 `request.state`

`request.state` 也能传值（实测 `[L]`：中间件设 `request.state.trace_id`，路由读到了 `t-123`），但**日志里拿不到**。

日志 formatter（`logging.py` 里的 `JsonFormatter`）在 `format()` 时**只拿到一条 LogRecord，拿不到 request**。
要让每条日志都带上 trace_id，只有一条路：存进一个"当前协程可见"的全局变量。

```python
trace_id_ctx: ContextVar[str] = ContextVar("trace_id", default="-")
```

- `ContextVar.set()` 设值，`get()` 取值，**每个请求/协程各自独立**（不是线程本地，是协程本地）
- 中间件里 `token = trace_id_ctx.set(trace_id)`，`finally` 里 `trace_id_ctx.reset(token)`
- 这样 service 层随便哪个 `logger.info(...)` 都会自动带上，**不用把 request 一路传下去**

这正是 W5 八股里 `ContextVar vs threading.local` 那条的项目落点。**面试时这两条要连着说**：
"trace_id 我不放 request.state，因为 formatter 拿不到 request；放 ContextVar，日志自动带，而且协程隔离。"

> 注意 `reset(token)` 而不是 `set("-")`：`reset` 是恢复到**上一个值**（可能是外层中间件设的），`set` 会覆盖掉外层上下文。

## 八、项目里埋着一颗定时炸弹（今天实测发现的真 bug）

`main.py` 的校验异常处理器：

```python
@app.exception_handler(RequestValidationError)
async def handle_validation(_: Request, exc: RequestValidationError) -> JSONResponse:
    return JSONResponse(
        status_code=422,
        content={"code": "VALIDATION_ERROR", "message": "参数校验失败", "detail": exc.errors()},
    )
```

**问题**：`exc.errors()` 里可能含有**不能 JSON 序列化的对象**。

实测（`[H-broken]` / `[H-fixed]`：给 `Payload` 加一个抛 `ValueError` 的 `field_validator`，传 `{"x": 99}`）：

```
[H-broken] handler 直接 json.dumps(exc.errors())
    log: ["errors() 里 ctx.error 的类型: ['ValueError']"]
    status: 500 | body: Internal Server Error

[H-fixed] 先 jsonable_encoder(errors()) 再序列化
    log: ["errors() 里 ctx.error 的类型: ['ValueError']"]
    status: 422 | body: [{"type": "value_error", "loc": ["body", "x"],
                          "msg": "Value error, x 不能大于 10", "input": 99, "ctx": ...}]
```

`exc.errors()` 里那一条长这样（注意最后一个键）：

```python
{'type': 'value_error', 'loc': ('body', 'x'),
 'msg': 'Value error, x 不能大于 10', 'input': 99,
 'ctx': {'error': ValueError('x 不能大于 10')}}    # ← 一个活的异常对象
```

**链条**：pydantic v2 把 validator 抛的原始异常塞进了 `ctx.error` → `JSONResponse` 序列化时遇到 `ValueError` 实例 → 抛 `TypeError` → 这个 handler 自己炸了 → 冒到 ① → **客户端收到 500 而不是 422**。

**为什么现在没炸**：项目里还没有自定义 `field_validator`（D3 要加第一个）。加了当天就会炸，而且症状是"参数校验失败变成了服务器错误"——极难排查，因为日志里是一条 `TypeError`，跟"参数不合法"毫无关系。

**修法三选一**（D3 动手时选一个，说清理由）：

```python
# A. 只保留可序列化的字段（最省事，丢掉细节）
detail = [{"loc": e["loc"], "msg": e["msg"], "type": e["type"]} for e in exc.errors()]

# B. 用 FastAPI 自家的编码器（保留全部，它会把异常转成字符串）
from fastapi.encoders import jsonable_encoder
content={"detail": jsonable_encoder(exc.errors())}

# C. 字符串化兜底（最糙，前端不好解析）
content={"detail": str(exc.errors())}
```

标准答案是 **B**：`jsonable_encoder` 正是 FastAPI 自己序列化响应时用的东西，它认识 `Exception` → 转成 `repr`。

## 十三、面试问法

### 13.1 高频题 30 秒版

**Q：FastAPI 的中间件和异常处理器有什么区别？**

> 中间件是竖着管，每个请求进出都经过，做计时、trace_id、CORS 这类横切逻辑；异常处理器是横着管，只在异常抛出时被调用，负责把内部异常翻译成对外响应。关键在顺序：用户中间件在 `ExceptionMiddleware` 外面，所以业务异常被翻译成 4xx 时中间件能拿到状态码，但未捕获异常的 500 在用户中间件外面生成，中间件看不到。

### 13.2 追问链（三层，面试官会一路往下挖）

**第一层（机制）**：`add_middleware` 两次，谁在外层？
> 后加的在最外层，因为内部是 `insert(0)`，构建时按列表顺序从外往内包。

**第二层（边界/故障）**：中间件里 `await request.body()` 会有什么问题？
> 新版本会缓存重放，下游能读到；但整个 body 进内存，大文件会爆，SSE 会从流式变成块。所以中间件只碰 header 和 path。

**第二层（另一个方向）**：为什么我加了 `@app.exception_handler(Exception)`，中间件里还是记不到 500？
> 因为 `Exception` 和 `500` 的 handler 在 `build_middleware_stack` 里被单独拎出来交给最外层的 `ServerErrorMiddleware`，用户中间件在它里面，异常先穿过中间件抛出，之后才轮到那个 handler。

**第三层（场景落地）**：线上发现某接口偶发 500，日志里只有一条 `request_failed`，没有 `request`。你怎么定位？
> 说明请求走到了未捕获异常，响应由最外层生成，所以 status 那条没打成。用那条 `request_failed` 里的 trace_id 去查同一 trace 的所有日志，定位是哪个 service 方法抛的；再看异常类型——如果是 `AppError` 没被 handler 接住，多半是 handler 注册在错误的位置或子类没匹配上。

**第三层（AI 应用向）**：SSE 流式接口，中间件的耗时日志能反映真实生成时长吗？
> 不能。`call_next` 返回时 body 还没发，量到的是路由函数执行时间。要量真实时长，得写纯 ASGI 中间件监听 `http.response.body` 的最后一帧，或者由业务代码在生成器结束时自己记。

### 13.3 一句话收尾（面试官问"你项目里怎么用"）

> 我们有一个 `TraceMiddleware` 做 trace_id 和耗时，trace_id 用 `ContextVar` 存，这样日志 formatter 自动带上；异常翻译靠 `AppError` + 两个 `exception_handler`，业务层只管 `raise`，不关心 HTTP 状态码。

## 十四、闭卷自测（先答，再展开对答案）

<details>
<summary>Q1：用户中间件、`ExceptionMiddleware`、`ServerErrorMiddleware`，从外到内怎么排？</summary>

`ServerErrorMiddleware`（最外）→ 用户中间件 → `ExceptionMiddleware` → Router。
口诀：框架的"兜底 500"在最外面，你的"翻译异常"在中间件里面。
</details>

<details>
<summary>Q2：路由抛 `NotFoundError(AppError)`，`TraceMiddleware` 里 `call_next` 返回什么？</summary>

返回一个 status 404 的正常 Response，body 是 `{"code":"NOT_FOUND",...}`。
因为 `AppError` 在 `ExceptionMiddleware` 里已被 handler 翻译，异常不会冒到中间件。
</details>

<details>
<summary>Q3：路由抛 `RuntimeError`（没人接），`TraceMiddleware` 的日志会打出什么？</summary>

只有 `request_failed`（`except` 分支），**没有** `request` 那条带 status 的。因为 `call_next` 抛出后函数就中断了。
确切的实测日志只有一条 `['A>']`——连 `M1 出` 都没打出来。
</details>

<details>
<summary>Q4：为什么 `@app.exception_handler(Exception)` 不在中间件层执行？</summary>

`build_middleware_stack` 里 `if key in (500, Exception): error_handler = value`，这类 handler 被交给最外层 `ServerErrorMiddleware`，而不是内层的 `ExceptionMiddleware`。
</details>

<details>
<summary>Q5：`resp.status_code = 201` 为什么在中间件里无效？</summary>

响应已经发过 `http.response.start`，状态码和 headers 已经写进连接；之后改 Python 对象属性不影响已发送的字节。header 也只能在 start 之前加。
</details>

<details>
<summary>Q6：项目里 `handle_validation` 现在有什么隐患？</summary>

`exc.errors()` 里 `ctx.error` 可能是 `ValueError` 实例，`JSONResponse` 序列化失败 → 500。
现在没炸是因为还没有自定义 validator；D3 加了就会炸。修法：`jsonable_encoder(exc.errors())`。
</details>

<details>
<summary>Q7：`ContextVar` 和 `request.state` 传 trace_id，差别是什么？</summary>

`request.state` 只能给拿到 request 的代码用；日志 formatter 只拿到 LogRecord，读不到 request。
`ContextVar` 是协程本地的全局变量，formatter 直接 `get()`，且每个请求互相隔离。
</details>

<details>
<summary>Q8：`BaseHTTPMiddleware` 里读 body，下游还能读到吗？（按本机版本答）</summary>

能。starlette 1.9.0 用 `_CachedRequest` 缓存并重放，实测下游读到完整 `b'{"a":1}'`。
但代价是 body 全部进内存、流式语义被破坏。所以结论不是"不能读"，而是"不该读"。
</details>
