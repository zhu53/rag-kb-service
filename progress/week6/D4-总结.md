## 二、逐个知识点讲透

### 1. 路由级鉴权：`include_router(..., dependencies=[Depends(...)])`

**一句话定义**：把鉴权依赖挂在"一组路由的入口"上，整组生效，而不是每个处理函数各写一遍。

**为什么存在**：端点级 `user_id: UUID = Depends(get_current_user_id)` 是**靠人记**的。新同事加接口忘了写——不报错、不告警、静默无鉴权。这类漏法最危险：它在代码评审时看不出来（函数看着挺正常），上线后也不会崩，只是那个接口对全世界敞开。路由级依赖把"这组必须过鉴权"从约定变成**结构事实**：你在 `include_router` 里挂上，组里每条路由都带上，漏写也绕不过。

**怎么用**（本项目 `router.py`）：

```python
api_router = APIRouter(prefix="/api/v1")
api_router.include_router(
    knowledge_bases.router,
    prefix="/kbs",
    tags=["knowledge-bases"],
    dependencies=[Depends(get_current_user_id)],   # ← 整组保护
)
```

端点里**仍然保留** `user_id: UUID = Depends(get_current_user_id)`，但那时的作用是**取值**（service 要用 owner_id），不是守卫。别担心跑两遍——同一次请求里同一个可调用对象的依赖只执行一次（依赖缓存）。

**底层机制**：`include_router` 在注册期把父 router 的 `dependencies` 和每条子路由自己的 `dependant` **合并成一棵依赖树**。鉴权函数在这棵树的较上层，先于端点函数执行；抛 `UnauthorizedError` → 全局 handler → 401 壳。所以"路由级"不是运行时有个循环去检查，而是**建表时就已经把依赖写进了每条 route 的依赖树**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 写成 `dependencies=[get_current_user_id]`（漏 `Depends`） | 启动/请求时行为异常，依赖不会被当依赖解析 | 列表里必须是 `Depends(...)` 对象 |
| 2 | 鉴权挂到 `api_router` 顶层，连 health 一起保护 | 探活拿到 401 → k8s 判死 → 反复重启 | health 单独挂到 `app` 上，结构上就在保护区外 |
| 3 | 以为端点级 + 路由级会执行两次、浪费性能 | 无实际症状（依赖缓存生效），但讲不清会被追问倒 | 同请求同可调用只执行一次，函数体不会跑两遍 |
| 4 | 以为加了路由级就能删掉端点的 `user_id` 参数 | 函数体里用到 `user_id` 直接 NameError | 守卫和取值是两件事：守卫挂路由，取值留在签名 |

**面试问法**：「如果新加的接口忘记加鉴权，你怎么防止？」

**30 秒版**：端点级声明靠人记，漏写不报错、接口就静默裸奔。我把鉴权提到路由级，`include_router` 时挂 `dependencies`，整组自动带上，漏写也绕不过。需要公开的接口（health）单独挂到 app 上，结构上就不在保护区里。

**追问链**：

- → *"路由级依赖和端点级依赖在框架里是怎么合并的？"* 注册期 `include_router` 把父的 `dependencies` 并入每条 route 的依赖树，是建表时完成，不是运行时遍历检查；同一次请求里同一依赖只解析一次。
- → *"那 health 也被挂了怎么办？"* 探活会 401，k8s 认为实例不健康直接重启——这是我今天真踩的坑（双挂载 + 鉴权归属），解法是把 health 从受保护 router 里摘出去，挂到 app 上。
- → *"如果网关层已经统一鉴权了，应用层还要不要？"* 要。网关只覆盖经过它的流量（内部调用、直连 Pod、调试口都绕过），应用层是最后一道；两层职责不同：网关做粗粒度拦截，应用层做"这个用户能不能访问这个资源"的细粒度判断。

### 2. 统一响应体（envelope）：成功和失败一个形状

**一句话定义**：所有响应都套同一层壳 `{code, message, data}`，客户端一套解析逻辑走全站。

**为什么存在**：只有错误有壳、成功是裸 JSON——**半套比零套更糟**。前端已经为错误写了 `code` 分支，成功分支却要按每个接口的字段单独写；SDK 生成器也没法统一。更隐蔽的是可观测性：日志/监控想统一读 `code` 判断成败，半套的话成功请求根本没有 `code` 字段。

**怎么用**（两条通路各一处）：

```python
# ① 失败：main.py 的异常处理器
return JSONResponse(
    status_code=exc.http_status,
    content=ApiResponse(code=exc.http_status * 100, message=exc.message, data=exc.detail).model_dump(),
)

# ② 成功：端点自己装（response_model 只是出口校验）
@router.post("", status_code=201, response_model=ApiResponse[KBOut])
async def create_kb(...) -> ApiResponse[KBOut]:
    return ApiResponse[KBOut](data=KBService().create(user_id, body))
```

`code=0` / `message="ok"` 是默认值，成功时不用传——**成功码是 0，不是 200**：HTTP 层已经 201/200 了，壳里再写一遍就是重复信息。

**底层机制**：两条通路**根本不是同一条代码路径**。成功响应：端点 return → 路由出口 `serialize_response` 按 `response_model` 校验+序列化 → 写 body。失败响应：端点抛异常 → 向外冒泡 → `ExceptionMiddleware` 捕获 → 调 handler → handler 返回 `Response` → 直接写 body，**完全不经过 `response_model`**。所以"统一"是约定上的统一，实现上必须两处各写一遍壳——这是本日最该记牢的一句话。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | `data` 里塞自定义错误字段、壳里又套壳 | `{"code":0,"data":{"code":40400,...}}`，前端要剥两层 | 壳只有一层；业务细节统一放 `data` |
| 2 | 成功码用 200 / 用 `true` | 前端要按类型分支；与 HTTP 语义重复 | 成功固定 `0`，失败用业务码 |
| 3 | 以为 SSE / 文件下载也会被套壳 | 前端按壳解析流式响应直接崩 | `Response` 子类透传，见知识点 12；这两类接口在文档里要写明"不套壳" |
| 4 | 只在错误 handler 里套壳，成功端点漏了 | 前端两套解析，回归不到（测试只断言字段值） | 每个改写过的端点配一条断言 `r.json()["code"] == 0` |

**面试问法**：「为什么要有统一响应体？」

**30 秒版**：为了让客户端只写一套解析：成功失败都是 `code/message/data`，前端按 `code` 分支，不用为每个接口单独写。实现上要两条通路各写一次——成功在端点里装壳、失败在异常处理器里装壳，因为异常根本不经过路由出口的 `response_model`。

**追问链**：

- → *"成功响应为什么不能靠 `response_model` 自动包？"* `response_model` 是校验器不是包装器：它拿返回值去校验，形状不符直接 `ResponseValidationError` → 500。壳必须由端点自己构造。
- → *"哪些接口不能套壳？"* 204（禁止 body，启动期就断言失败）、SSE/流式、文件下载——凡是"body 不是给人读的 JSON"就都不能套；改造时最容易漏的是 DELETE。
- → *"前端怎么处理 `code` 和 HTTP 状态码并存的情况？"* 分层判：HTTP 码给传输层/网关/重试策略看，`code` 给业务分支看。两者不该互相替代——"错误也返回 200"会让监控和网关的重试策略全部失真。

### 3. `response_model` 是出口校验器，不是包壳器

**一句话定义**：`response_model` 声明"这个接口的返回值长什么样"，FastAPI 在序列化阶段用它校验并过滤字段，同时把形状写进 OpenAPI。

**为什么存在**：① 防止内部字段泄露（ORM 对象上多出来的 `password_hash`、`owner_id` 不该出去）；② 让文档精确——前端和 SDK 生成器读的就是它。没有它，你的返回值就是"内部实现细节"，改一个字段就炸前端。

**怎么用**：

```python
@router.get("/{kb_id}", summary="查询知识库详情", response_model=ApiResponse[KBOut])
async def get_kb(kb_id: UUID, user_id: UUID = Depends(get_current_user_id)) -> ApiResponse[KBOut]:
    kb = KBOut.model_validate(KBService().get_or_403(kb_id, user_id))
    return ApiResponse[KBOut](data=kb)      # ← 壳自己装
```

**底层机制**：请求处理完拿到 `raw_response` 后，FastAPI 判断：如果是 `Response` 子类 → 直接透传（不校验）；否则用 `response_field` 对返回值做一次 Pydantic 校验 → 序列化 → 过滤掉模型里没声明的字段。校验失败抛 `ResponseValidationError`，最终是 **500**，不是 422——因为这不是客户端的错，是服务端自己的契约没兑现（这个区分在面试里很值钱）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只加 `response_model`，端点 `return kb`（裸模型） | 500 `ResponseValidationError`（`KBOut` 对不上 `ApiResponse`） | 端点自己构造 `ApiResponse[KBOut](data=kb)` |
| 2 | 以为多返回的字段会被保留 | 模型没声明的字段被**静默删掉**，调试时以为数据没取到 | 要对外就给字段加进 Out 模型，别指望"多传" |
| 3 | 返回类型注解写成 `Any` / 漏写 | mypy 变松，重构时编译器帮不上忙 | 注解写 `-> ApiResponse[KBOut]`，与 `response_model` 对齐 |
| 4 | 给 204 端点加 `response_model` | 启动期 `AssertionError`，服务起不来 | 204 不要 body，也不要 `response_model` |

**面试问法**：「`response_model` 有什么用？」

**30 秒版**：它声明出参契约：FastAPI 在返回后用它校验并过滤字段，保证不泄露内部字段，同时把精确结构写进 OpenAPI 给前端用。要注意它只校验不包装——想加统一外壳，壳得在端点里自己构造，否则校验不过直接 500。

**追问链**：

- → *"校验失败为什么是 500 不是 422？"* 422 表示"客户端传的东西不对"，校验的是入参；`response_model` 校验的是**服务端自己返回的东西**，错了说明代码违约，属于服务端故障。
- → *"它会不会校验流式响应？"* 不会。返回值是 `Response` 子类时直接透传，`response_model` 不介入——这也是为什么 `chat.py` 要显式 `response_model=None`。
- → *"统一外壳如果用 `response_model` 声明，`data` 类型怎么写才不撒谎？"* 用泛型：`ApiResponse[KBOut]`、`ApiResponse[Page[KBOut]]`，Pydantic 会把嵌套泛型实例化成独立 schema（`ApiResponse_Page_KBOut__`），文档里能点开看到完整结构。

### 4. 异常处理器必须返回 `Response`

**一句话定义**：`@app.exception_handler(X)` 的函数必须返回 `JSONResponse` 之类的 `Response` 实例，不能返回 Pydantic 模型。

**为什么存在**：异常处理器在中间件栈**内侧**被调用，它拿到的返回值会被**直接发送到 socket**，没有"路由出口再序列化一次"这一步。所以它必须交出一个"已经能发出去的字节"。

**怎么用**：

```python
@app.exception_handler(AppError)
async def handle_app_error(_: Request, exc: AppError) -> JSONResponse:
    return JSONResponse(
        status_code=exc.http_status,
        content=ApiResponse(code=exc.http_status * 100, message=exc.message, data=exc.detail).model_dump(),
    )
```

关键两步：**`JSONResponse(...)` 包住**、**`.model_dump()` 转成 dict**。少任何一步都会 500。

**底层机制**：栈的顺序是 `ServerErrorMiddleware`（最外，500 兜底）→ 用户中间件（`TraceMiddleware`）→ `ExceptionMiddleware` → 路由 → 端点。异常冒泡到 `ExceptionMiddleware`，它按类型查 handler 表，调 handler 拿返回值，然后 `await response(scope, receive, send)`——**把你返回的对象当 ASGI 应用去调用**。所以返回 Pydantic 模型时，Starlette 会尝试"调用"它，`ApiResponse` 没有 `__call__`，于是抛 `TypeError: 'ApiResponse' object is not callable`，再被最外层兜成 500。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | handler 里直接 `return ApiResponse(...)` | `'ApiResponse' object is not callable` → 500 | 必须 `JSONResponse(content=....model_dump())` |
| 2 | 忘记 `.model_dump()`，把模型对象塞进 `content` | JSON 序列化失败 → 500 | 先转 dict |
| 3 | 把 `status_code` 写成 200（"反正 body 里有 code"） | 网关/监控/重试策略全部失真 | HTTP 状态码照常（401/404/422），业务码放 body |
| 4 | `exc.errors()` 直接进 `content` | 遇到 `bytes`/异常对象时 JSON 编码失败 | `jsonable_encoder(exc.errors())`（D2 就修过这一处） |

**面试问法**：「全局异常处理是怎么实现的？」

**30 秒版**：在 app 上注册 `exception_handler`，按异常类型分派。handler 里把业务异常翻译成 `JSONResponse`：HTTP 状态码取 `exc.http_status`，body 套统一响应壳。要注意 handler 的返回值必须是 `Response` 实例，它会被直接发送，不会再经过 `response_model` 序列化。

**追问链**：

- → *"handler 在中间件栈的哪个位置执行？"* 在内侧：`ExceptionMiddleware` 捕获异常后调用 handler；比它更外的用户中间件只能看到"异常已经变成响应"，看不到原始异常。
- → *"业务代码里抛 `RequestValidationError` 会怎样？"* 那不属于 Pydantic 请求校验场景；入参校验失败由 FastAPI 自己抛 `RequestValidationError`，你只管注册 handler 统一形状，别在业务层手抛。
- → *"500 的异常谁来兜？"* handler 自己抛异常、或没有匹配的 handler 时，由最外层 `ServerErrorMiddleware` 生成 500——**这一层在你的中间件之外**，所以 `TraceMiddleware` 写不进 `X-Trace-Id`（D2 结论复用）。

### 5. 业务码 vs HTTP 状态码分离

**一句话定义**：HTTP 状态码给基础设施读（缓存/网关/重试），业务码给业务逻辑读（前端分支），两者各自表达、互不替代。

**为什么存在**：一个 400 底下可能有十几种原因（参数格式错、业务前置条件不满足、幂等冲突），一个数字塞不下；反过来，多个业务错误也可以共用 401。混用会导致两个方向的失真：`code == http_status` 时业务码没有细分空间；"错误也返回 200"时网关和监控完全瞎掉。

**怎么用**（本项目派生规则）：

```python
code = exc.http_status * 100     # 401 → 40100，404 → 40400，422 → 42200
```

后两位留给细分：同一个 401 将来要区分"没带 token（40100）/ token 过期（40101）/ 签名错（40102）"，只改 `AppError` 子类的映射，前端按前缀分组处理。

**底层机制**：这不是框架机制，是**契约设计**。项目里的实现方式是"单一事实源"：`AppError` 只声明 `http_status`，`code` 在 handler 里派生——于是**不存在两处维护**。今天顺手删掉了 `AppError.code` 字符串字段和 `ErrorCode` 枚举，正是这个设计的结果：派生之后它们全项目零引用，留着就是会漂移的死代码。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | `code=10001` 这类写死 | 新增错误码要同步改文档/前端枚举，漏一处不一致 | 派生自 `http_status * 100`，细分才往后再加 |
| 2 | 让 `code` 等于 HTTP 状态码 | 丢失细分空间；前端只能判断"哪类错"，判不出"哪个错" | HTTP 码管类别，业务码管具体原因 |
| 3 | 错误响应用 200 | 网关不重试、监控成功率 100%、告警永不触发 | HTTP 语义照常，业务码只在 body 里 |
| 4 | 以为业务码能替代 HTTP 码统一处理 | 只读 HTTP 的中间件（CDN、LB、APM）全部失效 | 两层都要对：状态码给机器，业务码给业务 |

**面试问法**：「你们的接口错误码是怎么设计的？」

**30 秒版**：两层分离：HTTP 状态码表达"传输/协议层怎么了"，网关和监控读它；业务码表达"具体业务为什么失败"，前端按它分支。业务码派生自状态码（401 → 40100），单点维护，后两位留给细分原因。

**追问链**：

- → *"为什么不直接手写业务码表？"* 手写就有两张表要同步（异常定义 + 码表），派生把"码"从维护项变成计算项；真需要细分时再在派生结果上叠加。
- → *"什么情况下错误必须返回非 200 的 HTTP 码？"* 只要客户端/网关需要据此做决策就必须——限流 429 要触发退避、401 要触发刷新 token、5xx 要触发重试；塞进 200 等于让这些机制全部失效。
- → *"前端拿到 40100 和 401 分别做什么？"* 401 触发登录跳转；40100/40101/40102 决定提示文案（未登录/过期/签名错）——这就是"码分层"的实际收益。

### 6. 204 与 envelope 正面冲突

**一句话定义**：204 语义要求"无 body"，与任何 `response_model` / 非 `None` 返回注解互斥，且冲突在**注册期**就断言失败。

**为什么存在**：统一响应体想让 DELETE 也保持形状一致（返回 `data: null` 的壳），但 HTTP 规定 204 不带 body。这不是框架怪癖，是协议约束——所以必须做选择，而不是想办法"绕过"。

**怎么用**（本项目现在的选择）：

```python
@router.delete("/{kb_id}", status_code=status.HTTP_204_NO_CONTENT, summary="删除知识库")
async def delete_kb(kb_id: UUID, user_id: UUID = Depends(get_current_user_id)) -> None:
    KBService().delete(kb_id, user_id)
```

保持 204 + `-> None`。另一个选择是改成 `200 + ApiResponse[None]`，让 DELETE 也返回 `{"code":0,"message":"ok","data":null}`——全站形状统一，代价是前端要把"删除成功"的判断从"204"改成"看 `code`"。

**底层机制**：FastAPI 在**建路由**时检查 `status_code` 与响应模型/返回注解：204（还有 205、304）被列为"禁止有 body"，一旦声明了响应模型或非 `None` 返回注解，直接 `AssertionError: Status code 204 must not have a response body`。**启动就炸**，不是请求时——所以改坏了连服务都起不来，影响面比运行时错误更"友好"，但也更容易在评审时被忽略（CI 里只跑测试就发现不了，得真起服务）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为冲突发生在请求时 | 起服务才炸，本地测试全绿但 uvicorn 起不来 | 改路由后起一次服务（或让测试种 app 实例构造） |
| 2 | 试 `204 + response_model=ApiResponse[None] + -> None` | 同样崩——三种套壳写法实测全崩 | 204 就彻底不要模型和注解，二选一 |
| 3 | 改了状态码但测试还断言 204 | 门禁红，且容易误判成"业务逻辑坏了" | 改契约时同步改断言（今天 health 改造也踩了同类） |
| 4 | 前端按 `data` 判删除成功 | 204 时 body 为空，解析崩 | 204 时按"2xx 且无 body"判成功，团队内写进约定 |

**面试问法**：「DELETE 接口返回 204 还是 200？」

**30 秒版**：204 表示成功且无 body，最符合语义，但它和统一响应体正面冲突——204 不允许自带 body，声明响应模型或非 `None` 注解会在启动阶段直接断言失败。要全站形状一致就改 200 + `data: null`，要语义干净就保持 204，关键是团队内说清楚、前端按对应规则判断。

**追问链**：

- → *"为什么 204 冲突是在注册期炸，不是请求期？"* 因为它是 FastAPI 建路由时对 `status_code` 与响应模型的静态校验，属于"路由定义非法"，和参数校验（请求期）不是一个阶段。
- → *"还有哪些响应不能有 body？"* 204、205、304 都属于这类；另外 1xx 也不能带 body。文件下载、SSE 虽然能有 body，但同样不能被 `response_model` 套壳。
- → *"你们项目最后选了哪种？"* 现在保持 204 + `-> None`，因为删除是幂等动作、前端只需要知道成败；如果将来要求 SDK 统一解 `code`，再统一改成 200 + `ApiResponse[None]`——这是一次全站契约变更，得一起改前端。

### 7. health：机器消费者不套壳、无鉴权、不暴露内部信息

**一句话定义**：`/health` 的读者是探针/负载均衡/监控，它只认状态码和最简 body，因此不套壳、不要 token、不暴露内部信息。

**为什么存在**：三个反直觉点今天全撞了一遍。① 探针逻辑极简（`curl` 看状态码、`jq .status` 看字段），套壳后 `status` 埋在 `data` 里，`jq .status` 直接为空；② 探活要 token 就意味着 k8s 得注入凭证，而且凭证一过期全部实例被判死；③ 把 `env`、`version` 这类字段挂在**无鉴权**的公开接口上，等于告诉扫描器"这是生产环境、跑的是 0.1.0"——攻击者可以直接对版本号查已知漏洞。

**怎么用**：

```python
# health.py：裸 dict，根路径，独立挂载
@router.get("/health", summary="健康检查")
async def health() -> dict[str, str]:
    return {"status": "ok"}

# main.py：挂到 app 上，不在任何带鉴权的 router 里
app.include_router(health.router, tags=["health"])
app.include_router(api_router)
```

**底层机制**：**挂载位置即安全边界**。`app.include_router(health.router)` 之后，health 不在 `api_router` 的依赖树里，路由级鉴权天然覆盖不到它；反过来一旦它被 `api_router.include_router` 也挂一份，就出现了"同一个 handler、两种安全语义"的双路径——这正是今天坑 1 的形状。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 搬家时旧 `include_router` 没删 | `/health` 和 `/api/v1/health` 同时 200，探针配错地址也"看起来正常" | 删 include + 删 import，用 `openapi()["paths"]` 核对 |
| 2 | health 套 envelope | 探针 `jq .status` 拿不到值（或读到 `code` 误判） | 机器消费者走裸 JSON，和 204/SSE 同一章法 |
| 3 | 在无鉴权接口里返回 `env` / `version` / 构建号 | 未认证方即可判断生产环境与版本，配合 CVE 查询 | 只回 `{"status":"ok"}`；详细信息放受保护的内部接口 |
| 4 | health 里查数据库/调下游 | 探活变慢，数据库抖动时全部实例被判死重启（雪崩） | liveness 只查进程活性；依赖检查放 readiness，且要有超时 |

**面试问法**：「健康检查接口怎么设计？」

**30 秒版**：分两个：liveness 只看进程活着，返回最简 `{"status":"ok"}`、不套壳、不要鉴权，因为探针只读状态码和最简字段；readiness 检查依赖（数据库、下游），可以有权重更重的逻辑但必须有超时。共性是都不暴露环境/版本，也不套统一响应体。

**追问链**：

- → *"为什么不套统一响应体？"* 探针是机器消费者，判据是状态码和顶层字段；套壳后 `status` 沉到 `data` 里，`jq .status` 读不到。同一个章法还包括 204 和 SSE。
- → *"liveness 里查数据库会怎样？"* 数据库抖动 → liveness 失败 → k8s 重启全部实例 → 雪崩；所以依赖检查只放 readiness，liveness 只判进程。
- → *"health 接口要不要鉴权？"* 不要——探活发生在"还没有业务身份"的阶段；但因此**响应内容必须最小化**，任何能帮助攻击者判断环境的信息都不该出现。

### 8. 依赖注入：`Annotated[PageParams, Depends()]`

**一句话定义**：把分页参数收成一个 Pydantic 模型，用 `Annotated[PageParams, Depends()]` 注入，字段自动变成 query 参数。

**为什么存在**：之前 `list_kbs` 和 `list_docs` 各写一遍 `page: int = Query(default=1, ge=1)` / `size: int = Query(default=20, ge=1, le=100)`。改一处漏一处就是事故；OpenAPI 里也是各写各的。抽成依赖后：一处定义全站生效，新接口一行接入，约束与文档自动同步。

**怎么用**：

```python
# schemas/common.py
class PageParams(BaseModel):
    page: int = Field(default=1, ge=1)
    size: int = Field(default=20, ge=1, le=100)

# 端点
async def list_kbs(
    params: Annotated[PageParams, Depends()],
    user_id: UUID = Depends(get_current_user_id),
) -> Page[KBOut]:
    return KBService().list(user_id, params.page, params.size)
```

实测（FastAPI 0.150.0 + Pydantic 2.14.1）：`?page=2&size=5` → 原样生效；`?page=0` → 422 `greater_than_equal`；`?size=500` → 422 `less_than_equal`；`?size=abc` → 422 `int_parsing`；OpenAPI 里正确显示为两个 query 参数。

**底层机制**：启动时 FastAPI 扫描函数签名，看到 `Annotated` 元数据里的 `Depends()` 标记，就把注解里的类型（`PageParams`）当依赖函数；Pydantic 模型的每个字段被展开成 query 参数，请求进来时先校验再构造实例，注入到参数上。**类型和元数据被两拨人读**：mypy 只读 `PageParams`（知道 `params.page` 是 int），FastAPI 只读 `Depends()`（知道这不是客户端传的对象，而是自己算出来的）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 忘写 `Annotated`，只写 `params = Depends()` | 启动报错（`Depends()` 无参数且无类型可推） | 注解和 `Depends()` 必须成对出现 |
| 2 | 抽了依赖但函数签名里还留着 `page: int = Query(...)` | 两套约束并存，改一处不生效，容易看漏 | 抽完把旧参数删干净（`Query` import 也要删） |
| 3 | 给 `PageParams` 加 `extra="forbid"` 想拦多余 query | 不生效——query 里多余的键本来就被忽略 | 想严格校验就显式声明字段，别指望 config |
| 4 | 各接口自己算 `offset`，算法散落 | 分页口径不一致（有的从 0 开始有的从 1） | 把 `offset` 做成 `PageParams` 的只读属性/方法，一处定义 |

**面试问法**：「分页参数怎么统一管理？」

**30 秒版**：抽成一个 Pydantic 模型当依赖，`Annotated[PageParams, Depends()]` 注入，字段自动变 query 参数、约束也一起生效，OpenAPI 自动带。好处是一处改全站生效，新接口一行接入，而且分页口径（从 1 开始、上限 100）只有一份定义。

**追问链**：

- → *"`Depends()` 空括号是怎么知道依赖谁的？"* 靠注解：FastAPI 读 `Annotated` 里的类型作为依赖可调用对象；`Depends(某个函数)` 是显式写法，空括号是"从类型推"的简写。
- → *"依赖里的校验失败返回什么？"* 走入参校验失败的同一条路：422 + 统一壳（`code=42200`），因为它属于 `RequestValidationError`。
- → *"上千万数据深分页怎么办？"* 页码分页在大 offset 下会全表扫，要换 keyset/游标（`WHERE id > ? LIMIT ?`）；代价是不能跳页、`total` 不能实时给。这也是 Pydantic 依赖能扩展的地方——加 `cursor` 字段即可。

### 9. 路由搬家要核对路径表

**一句话定义**：`include_router` 是"复制登记"，旧登记不删就两个都在；核对真实路由要用 `app.openapi()["paths"]`，不是 `app.routes`。

**为什么存在**：今天把 health 从 `/api/v1` 搬到根路径，只加了新挂载、没删旧 include，结果两条路径同时 200——测试全绿、服务正常，**没有任何报错**。这类"沉默的重复"只能靠核对路径表发现。

**怎么用**：

```powershell
# Windows PowerShell
& .\.venv\Scripts\python.exe -c "from kb_service.main import create_app; print('\n'.join(create_app().openapi()['paths']))"
```

改前抄一份、改后打一份，逐行对比——**改路由不对比路径表，等于闭着眼睛改**。

**底层机制**：`include_router` 在注册期把子 router 里攒下的 route 逐个复制进父 router（前缀拼接），同一个 router 被两处 include 就登记两次、生成两条不同 path 的 route。而 FastAPI 0.150 的 `app.routes` 里看到的是一行 `_IncludedRouter`（惰性展开），所以想核对真实路径只能走 `openapi()`，它会触发完整展开。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 搬完只加不删 | 新旧地址同时存活，探针配哪个都"正常" | 删 include + 删 import；对比路径表 |
| 2 | 用 `app.routes` 核对 | 只看到 `_IncludedRouter`，误以为路由没注册 | 用 `openapi()["paths"]` |
| 3 | 以为路径重复会报错 | FastAPI 不报错，先注册者赢 | 改动后必须人工/脚本对比清单 |
| 4 | 删了 include 忘删 import | ruff F401 门禁红（今天真发生） | `ruff check --fix` 一把清掉 |

**面试问法**：「怎么确认线上接口都注册对了？」

**30 秒版**：打 `openapi()["paths"]` 出一份"对外合同"，和改动前的清单做 diff；不能看 `app.routes`，因为包含的子路由是惰性展开的。上线前把这份清单和网关/前端 SDK 里的路由对一遍，重复和缺失都能查出来。

**追问链**：

- → *"为什么 `app.routes` 不行？"* 0.150 里 `include_router` 是惰性登记，`app.routes` 只有一条 `_IncludedRouter` 占位，真实路径要 `openapi()` 触发展开。
- → *"路径重复注册，框架为什么不报错？"* 注册表允许同 path 多条 route（方法不同就是合法场景），所以它无法判断你是笔误还是有意——只能靠对比清单。
- → *"微服务里网关和服务的路由怎么保持一致？"* 服务侧导出 `openapi()["paths"]` 作为契约文件，网关配置从它生成或做 CI 校验，两边不一致就挂流水线。

### 10. 泛型 `ApiResponse[T]`

**一句话定义**：用 `TypeVar` + `Generic[T]` 定义一个"格子待定"的壳类，`ApiResponse[KBOut]` 是填好格子的具体版本。

**为什么存在**：全站有六七种 `data` 形状（单个对象、分页、None、列表）。不泛型就得写六七个壳类，或者统一用 `dict`/`Any`——前者重复，后者让 mypy 和 OpenAPI 全部失守。

**怎么用**：

```python
T = TypeVar("T")

class ApiResponse(BaseModel, Generic[T]):
    code: int = 0
    message: str = "ok"
    data: T | None = None
```

用法只有两种形态：`ApiResponse[KBOut]`（选型）、`ApiResponse[KBOut](data=kb)`（选型后构造实例）。

**底层机制**：`Generic[T]` 让类在 `ApiResponse[KBOut]` 时走 `__class_getitem__`，Pydantic 据此**实例化一个具体模型类**（并缓存），字段 `data` 的类型被替换成 `KBOut | None`；OpenAPI 里会生成独立 schema 名（如 `ApiResponse_Page_KBOut__`），前端能看到精确结构。这就是为什么文档"不撒谎"。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 PEP 695 写法 `class ApiResponse[T](BaseModel)` | Python 3.11 语法错误（3.12+ 才有） | 项目锁 3.11，必须 `TypeVar` + `Generic[T]` |
| 2 | 只写 `Generic[T]` 但没定义 `T = TypeVar("T")` | NameError / 类型检查失效 | 两者都要 |
| 3 | 把 `data` 声明成 `T`（无默认） | 成功壳没问题，但 `ApiResponse[None]` 在 204 场景想套壳即崩 | 默认 `None`，配合 `data: T \| None` |
| 4 | 以为 `ApiResponse[KBOut]` 会做运行时校验 | 它只是选型；真正的校验发生在 `response_model` 序列化阶段 | 选型 ≠ 校验，别混 |

**面试问法**：「为什么要用泛型封装统一响应？」

**30 秒版**：不泛型就得为每种 `data` 写一个壳类，或者退化成 `Any` 把类型和文档都丢掉。泛型让壳只定义一次，`ApiResponse[KBOut]`、`ApiResponse[Page[KBOut]]` 各自生成精确 schema，OpenAPI 和 SDK 都能拿到真实结构。注意 3.11 只能用 `TypeVar + Generic`，PEP 695 语法是 3.12+。

**追问链**：

- → *"参数化的时候运行时发生了什么？"* `__class_getitem__` 触发 Pydantic 缓存并创建一个具体模型类，字段类型被替换；所以每个参数化组合在 OpenAPI 里都是独立 schema。
- → *"嵌套泛型（`ApiResponse[Page[KBOut]]`）有问题吗？"* 能正常实例化（实测 schema 名 `ApiResponse_Page_KBOut__`），但组合多了 OpenAPI 体积会涨；接口数量大了要评估。
- → *"协变/逆变要关心吗？"* 运行时无所谓（Python 泛型是"擦除"式的约定）；只有 mypy 严格模式做容器传递时才需要 `covariant=True`，本项目的壳只用来装返回值，不需要。

### 11. 路由匹配顺序与前缀拼接

**一句话定义**：路由表线性匹配、**首个匹配者赢**（不是最具体的赢）；前缀从内到外拼接，空串等于不加。

**为什么存在**：这两条规则都会制造"代码看着没错、行为反直觉"的事故：`/kbs/{kb_id}` 写在 `/kbs/stats/count` 前面时，静态段会不会被参数吞掉？路径写成 `"/"` 时客户端拿到的是 307 重定向。

**怎么用**：

```python
@router.get("/stats/count", ...)   # 静态段路由先注册
async def count_kbs(...): ...

@router.get("/{kb_id}", ...)       # 参数路由后注册
async def get_kb(...): ...
```

**底层机制**：Starlette 用路由列表顺序匹配，命中即返回，不做"最长前缀"比较。`/{kb_id}` 声明为 `UUID` 时，路径段还要过类型转换——`stats` 不是合法 UUID，转换失败即视为不匹配，继续往下找；段数不同（`/kbs/stats/count` 是两段）本身也不会命中一段的 `/{kb_id}`。尾斜杠则是另一件事：`"/"` 结尾的路由与不带斜杠的请求之间会触发 307 重定向。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为"更具体的路由自动优先" | 先注册的参数路由吞掉后面的静态路由 | 静态段在前，参数段在后；或加约束（类型转换器） |
| 2 | 路径写成 `@r.get("/")` | 客户端请求不带尾斜杠 → 307；POST 场景部分客户端降级成 GET | 统一约定：路径里不带尾斜杠 |
| 3 | 以为 prefix 重复拼接会报错 | 实际是 `/api/v1/kbs/kbs`，测试才炸 | 前缀只在一处写；改完对比路径表 |
| 4 | 用 `app.routes` 验证顺序 | 看到的是 `_IncludedRouter`，验证不了 | 用 `openapi()["paths"]` 或真打请求 |

**面试问法**：「两个路由冲突了怎么排查？」

**30 秒版**：先看注册顺序——Starlette 是线性匹配、首个命中即返回，不是"最具体的赢"，所以静态段必须写在参数段前面。再看路径形态（尾斜杠会 307）和类型转换器（`{kb_id}` 声明成 UUID 时非 UUID 段自然不匹配）。最后用 `openapi()["paths"]` 把真实路由清单打出来核对。

**追问链**：

- → *"为什么不是最长匹配优先？"* 路由表就是有序列表，Starlette 顺序扫描，命中即停；顺序即优先级，这也是"路由顺序是契约的一部分"的原因。
- → *"307 有什么风险？"* 307 保留方法（比 301/302 安全），但多一次往返；部分老旧客户端/代理在重定向后改方法，POST 会变 GET——所以干脆统一不带尾斜杠。
- → *"网关剥前缀后应用侧怎么匹配？"* 应用侧只认自己注册的路径；网关剥掉 `/api` 后转发，应用路由必须按剥完的形态注册——两边对不上就是 404，所以路由清单要和网关配置一起做 CI 校验。

### 12. `StreamingResponse` 绕过 `response_model`

**一句话定义**：返回值本身是 `Response` 子类时，FastAPI 直接透传，不做校验、不套壳、不序列化。

**为什么存在**：SSE 的 body 是"一条条推出去的流"，不能整体序列化成一个 JSON；文件下载同理。框架必须让这类响应绕过出参处理，否则流式功能直接失效。

**怎么用**（本项目 `chat.py`）：

```python
@router.post("/chat", response_model=None, summary="知识库问答（支持流式）")
async def chat(body: ChatRequest, user_id: UUID = Depends(get_current_user_id)) -> ChatResponse | StreamingResponse:
    if body.stream:
        return StreamingResponse(svc.answer_stream(...), media_type="text/event-stream")
    return await svc.answer(...)
```

**底层机制**：`serialize_response` 之前先判断 `isinstance(raw_response, Response)`——是就直接返回，`response_model` 完全不参与。于是同一个接口的两条分支形状不同：非流式走统一壳，流式是裸的 `data: ...` 事件。这是"功能正确"和"契约一致"之间的真实取舍。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 `response_model` 会包住 SSE | 前端按壳解析流，直接崩 | 流式接口在文档里显式标注"不套壳" |
| 2 | 同一接口流式/非流式形状不一致但没写文档 | 前端要写两套解析，联调时才发现 | 要么统一约定、要么分开两个端点 |
| 3 | 在中间件里读 body | 流被吃掉，SSE 卡死（D2 已踩过） | 中间件只读 headers/状态码，不碰 body |
| 4 | 流中途出错 | 已经发出 200，错误只能塞进事件里 | 约定 `event: error` 或最后一个 chunk 带错误标记 |

**面试问法**：「流式接口怎么和统一响应体共存？」

**30 秒版**：流式响应必须绕过统一壳——`StreamingResponse` 是 `Response` 子类，FastAPI 直接透传，`response_model` 不介入。所以同一个问答接口，非流式返回统一的 `code/message/data`，流式走 SSE 事件，前端按两条分支解析；这也是要在接口文档里写清楚的部分。

**追问链**：

- → *"为什么框架要特殊处理 `Response` 子类？"* 因为这类对象自带 ASGI 发送逻辑，再包一层序列化就破坏语义（流不能整体转 JSON）。
- → *"流已经开始发送，中途报错怎么办？"* HTTP 状态码已定，只能用应用层协议表达：发一个 `event: error` 事件或末帧带 `code != 0`，前端据此提示重试。
- → *"流式接口怎么做鉴权和限流？"* 鉴权在建立连接前完成（依赖照常执行）；限流和用量统计要看首字节/总时长，不能只按请求数——这也是 AI 应用成本控制里的真实问题（一次流式回答的 token 是随流累计的）。

## 三、30 秒答案集

1. **统一响应体为什么要？** 客户端只写一套解析：成功失败都是 `code/message/data`，前端按 `code` 分支。
2. **壳在哪装？** 成功在端点里装、失败在异常处理器里装——异常不经过路由出口，`response_model` 管不到它。
3. **`response_model` 是什么？** 出参校验器 + 文档来源；不是包装器，形状不符直接 500。
4. **校验失败为什么 500 不是 422？** 422 是客户端传错；`response_model` 校验的是服务端自己的返回值，错了说明代码违约。
5. **异常处理器返回什么？** 必须是 `JSONResponse` 这类 `Response` 实例，并且 `content` 要 `.model_dump()`。
6. **返回 Pydantic 模型为什么炸？** handler 的返回值被当 ASGI 应用调用，模型没有 `__call__` → `'ApiResponse' object is not callable`。
7. **业务码怎么设计？** 与 HTTP 码分层：HTTP 管"哪类错"，业务码管"具体原因"；派生 `http_status * 100`，后两位留细分。
8. **错误能不能返回 200？** 不能：网关不重试、监控成功率失真、告警永不触发。
9. **204 能套壳吗？** 不能，且是启动期 `AssertionError`；要么保持 204 无 body，要么改 200 + `data: null`。
10. **鉴权怎么防漏？** 路由级 `dependencies=[Depends(...)]` 整组保护；health 这类公开接口单独挂 app。
11. **health 为什么裸 JSON？** 读者是探针，只认状态码和顶层字段；套壳后 `jq .status` 读不到。
12. **health 为什么不能回 `env`？** 它无鉴权、公网可达，等于告诉扫描器"生产环境 + 版本号"，直接对 CVE。
13. **`Annotated[PageParams, Depends()]` 是什么？** 类型 + 框架元数据：mypy 读类型，FastAPI 读 `Depends` 并把字段变 query。
14. **分页怎么统一？** Pydantic 模型当依赖，约束写在 `Field`，一处定义全站生效。
15. **流式接口怎么套壳？** 不能套：`StreamingResponse` 被直接透传，同一接口两条分支形状不同，文档要写清。

## 四、白板手写靶

### 靶 1：统一响应体 + 两个 handler

```python
from typing import Generic, TypeVar
from pydantic import BaseModel

T = TypeVar("T")


class ApiResponse(BaseModel, Generic[T]):
    code: int = 0
    message: str = "ok"
    data: T | None = None


@app.exception_handler(AppError)
async def handle_app_error(_: Request, exc: AppError) -> JSONResponse:
    return JSONResponse(
        status_code=exc.http_status,
        content=ApiResponse(
            code=exc.http_status * 100,
            message=exc.message,
            data=exc.detail,
        ).model_dump(),
    )


@app.exception_handler(RequestValidationError)
async def handle_validation(_: Request, exc: RequestValidationError) -> JSONResponse:
    return JSONResponse(
        status_code=422,
        content=ApiResponse(code=42200, message="参数校验失败", data=jsonable_encoder(exc.errors())).model_dump(),
    )
```

要点：`JSONResponse` + `.model_dump()` 两步都不能少；`RequestValidationError` 的 `errors()` 必须过 `jsonable_encoder`。

### 靶 2：分页依赖 + 端点签名

```python
class PageParams(BaseModel):
    page: int = Field(default=1, ge=1)
    size: int = Field(default=20, ge=1, le=100)


@router.get("", summary="分页查询我的知识库")
async def list_kbs(
    params: Annotated[PageParams, Depends()],
    user_id: UUID = Depends(get_current_user_id),
) -> Page[KBOut]:
    return KBService().list(user_id, params.page, params.size)
```

要点：`Annotated` 元数据里必须是 `Depends()`（空括号），类型由注解提供；旧 `Query` 参数和 import 都要删净。

### 靶 3：路由分组骨架（前缀 + 路由级鉴权 + 公开接口分离）

```python
api_router = APIRouter(prefix="/api/v1")
api_router.include_router(
    knowledge_bases.router, prefix="/kbs", tags=["knowledge-bases"],
    dependencies=[Depends(get_current_user_id)],
)
api_router.include_router(
    documents.router, prefix="/kbs", tags=["documents"],
    dependencies=[Depends(get_current_user_id)],
)
api_router.include_router(chat.router, tags=["chat"], dependencies=[Depends(get_current_user_id)])

app.include_router(health.router, tags=["health"])   # 公开，不受鉴权保护
app.include_router(api_router)
```

要点：`health` 只挂 `app` 一次；`api_router` 自身不挂鉴权（否则 health 会被顺带保护）。

## 六、可以讲成故事的三段

**故事 1：我以为 `response_model` 会自动帮我包壳**

背景：要给成功响应也套上统一壳，很自然地想"声明 `response_model=ApiResponse[KBOut]` 就该自动包一层"。我以为是框架的语法糖，实际它只做**出口校验**——拿返回值去比对 `ApiResponse` 的形状，裸 `KBOut` 对不上，直接 `ResponseValidationError` → 500。教训：**`response_model` 是校验器不是包装器；壳得自己装，成功了在端点装、失败了在 handler 装。**

**故事 2：我以为 health 搬完家就完事**

背景：任务是把 health 从 `/api/v1` 挪到根路径，我加了新的挂载，测试全绿、服务正常、`/health` 200。真实情况是旧的 `include_router` 还在 `api_router` 里，`/api/v1/health` 也活着——两个地址、两套安全语义，`/docs` 里 health 出现两次。更隐蔽的是它今天不报错：等到有人给 `api_router` 加全局鉴权，探活就会被 401 判死、反复重启。教训：**搬家要核对路径表（`openapi()["paths"]`），旧地址不会自己消失。**

**故事 3：我以为分页参数两处复制没关系**

背景：`list_kbs` 和 `list_docs` 各写了一份 `page/size` 的 `Query` 约束，看着一致，觉得"就两处，改的时候记得就行"。抽成 `PageParams` 依赖后，我加了一条测试：同一个模型在两处都被 `size=500` 拦住——这才叫"共用"，而不是"长得像"。顺带一个反直觉发现：抽完依赖，旧的 `?page=1&size=10` 测试一个字都不用改，因为**对外契约没变、只是内部换了来源**。教训：**重构的证明标准是"对外行为不变 + 有一个测试证明共用"，不是"代码看着更短了"。**
