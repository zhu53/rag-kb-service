## 二、逐个知识点讲透

### 1. 中间件执行顺序：后 `add` 的在外层

**一句话定义**：`add_middleware()` 把新中间件插到列表头，构建栈时倒序包裹，所以**最后注册的包在最外面**。

**为什么存在**：后加的功能（CORS、压缩、trace）通常是"最外层刚需"，设计成"后写的盖在上面"符合追加式开发。代价是它与"按声明顺序执行"的直觉相反——`A> B> handler <B <A` 里，A 是**后**加的那个。

**怎么用**

```python
app.add_middleware(M1)      # 先加 → 列表位置 1 → 内层
app.add_middleware(M2)      # 后加 → 列表位置 0 → 外层
# 实测输出：['M2 进', 'M1 进', 'handler 执行', 'M1 出 200', 'M2 出 200']
```

**底层机制**（两条源码，`starlette/applications.py`）

```python
def add_middleware(self, cls, *args, **kwargs):          # :104-107
    self.user_middleware.insert(0, Middleware(cls, ...))  # 插到列表头

middleware = [Middleware(ServerErrorMiddleware, ...)]     # :63-83 第一个进列表
middleware += self.user_middleware
middleware.append(Middleware(ExceptionMiddleware, ...))   # 最后一个进列表
app = self.router
for cls, args, kwargs in reversed(middleware):            # 从列表末尾开始穿
    app = cls(app, *args, **kwargs)                       # 新的包住旧的
```

列表是 `[①, 你的, ④]`，反转后从 ④ 开始穿，最后穿上的 ① 落在最外面。**"后加的在外层"不用背，读这两行就出来了。**

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为先 `add` 的在外层 | 计时中间件把另一个中间件的耗时也算进去 | 后加的在外层，判据："外层 = 最后 `add` 的那个" |
| 2 | 以为响应也是外层先返回 | 日志顺序写成 `<A <B` | 响应逆序：`<B` 先、`<A` 后 |
| 3 | 在 `app` 启动后再 `add` | `RuntimeError: Cannot add middleware after an application has started` | 全部 `add` 必须发生在第一次请求之前 |
| 4 | 以为 `include_router` 也能插中间件 | 中间件对某些路由"不生效" | 中间件挂在 app 上，路由级只能靠依赖（`Depends`） |

**面试问法**
> Q：FastAPI 里 `add_middleware` 调两次，谁在外层？
> A：**后加的在最外层**。因为 `add_middleware` 是 `insert(0)` 插到列表头，而建栈时是 `reversed` 遍历、每次用新类包住旧的，所以列表第一个最后被包上、落在最外面。表现就是日志 `A> B> handler <B <A`。

**追问链**
→ *"那 `ExceptionMiddleware` 为什么在最里面？"* 它是框架自己 `append` 到列表末尾的，反转后第一个被穿，所以贴着 router。
→ *"如果我想要某个中间件只对 `/api/v1` 生效呢？"* 中间件只有 app 级，没有路由级；要按路径分支只能在 `dispatch` 里判断 `request.url.path`，或者改用 `APIRouter(dependencies=[...])` 做请求级逻辑。
→ *"线上排查时这个顺序有什么用？"* 耗时统计会互相包含：外层中间件的时间 ≥ 内层。看 `X-Duration-Ms` 突然变大时，先确认是不是新加了一个中间件——它可能被算进了别人的时间里。

### 2. 异常在哪一层被翻译：中间件为什么记不到 500

**一句话定义**：注册的异常由内层的 `ExceptionMiddleware` 翻译成响应，**翻译完它就变成正常响应往回穿**；没人接的异常一路炸到最外层 `ServerErrorMiddleware` 才变成 500。

**为什么存在**：如果所有异常都交给最外层处理，中间件就没法记录 4xx 的状态码；如果全放在中间件里，中间件自己出错就没人兜。所以框架分成两层：内层翻译业务异常，外层兜住所有漏网的。

**怎么用**（项目的两层注册）

```python
app.add_middleware(TraceMiddleware)                 # ③ 用户中间件
@app.exception_handler(AppError)                    # ④ 进 ExceptionMiddleware
@app.exception_handler(RequestValidationError)      # ④ 同上
# 不注册 @app.exception_handler(Exception) —— 那类 handler 会被交给 ①
```

**底层机制**

```python
for key, value in self.exception_handlers.items():   # applications.py:68-72
    if key in (500, Exception):
        error_handler = value            # → ServerErrorMiddleware（① 最外）
    else:
        exception_handlers[key] = value  # → ExceptionMiddleware（④ 内侧）
```

`ExceptionMiddleware` 查表用的是 **MRO**：抛 `NotFoundError`，它按 `NotFoundError → AppError → ...` 往上找，所以 `AppError` 的 handler 能接住子类。

**三条路的实测（教材 §4.1）**

| 抛什么 | 谁接 | 中间件看到 | 客户端收到 |
|---|---|---|---|
| `AppError` 子类 | ④ | `<A 404`（正常响应） | `{"code":"NOT_FOUND"}` |
| `HTTPException(418)` | ④ 内置 handler | `<A 418` | `{"detail":"teapot"}` |
| `RuntimeError`（无 handler） | ① | **只有 `A>`** | 纯文本 500 |

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为中间件"看不到 500" | 在 `except` 里写 `status=500`，永远拿不到 | 那时没有 response 对象，只能记 `request_failed` + `duration_ms` |
| 2 | 以为注册了 `Exception` handler 中间件就不抛了 | 实测 `call_next` 照抛 | handler 在 ①，比 ③ 更外，异常先撞 ③ |
| 3 | 在 `except` 里吞掉不 `raise` | dispatch 隐式返回 `None` → 框架 `TypeError` → **真凶变成假凶手** | 记录后必须 `raise`，或返回一个完整 Response |
| 4 | 以为 500 是中间件"漏记" | 日志里只有 `request_failed` 没有 `request` | 500 出生时中间件已经退栈，不是漏记是不会发生 |

**面试问法**
> Q：为什么你的中间件记不到 500 的状态码？
> A：因为 500 不是任何一个 handler 生成的，是最外层 `ServerErrorMiddleware` 生成的，而它在用户中间件**外面**。异常从里往外飞时先撞到我的中间件，我的 `except` 记一笔再 `raise`，函数就退栈了——之后 500 生成时我已经不在调用栈上。所以我的日志里只有 `request_failed`，没有带 status 的 `request`。

**追问链**
→ *"那 404 和 422 为什么能记到？"* 404 在 Router 匹配阶段就生成了响应，422 由 `RequestValidationError` 的 handler 在 ④ 翻译成响应，两者都是"正常响应往回穿"，所以能拿到 status。
→ *"加了 `@app.exception_handler(Exception)` 会不会好一点？"* 只改变响应的样子（纯文本 500 → 你的 JSON），**不改变路径**——实测两组的 `call_next` 都抛，中间件照样记不到 status。
→ *"线上怎么用这个差异定位故障？"* 只有 `request_failed` 没有 `request` = 5xx 未捕获；两条都有 = 正常结束。用那条 `request_failed` 的 trace_id 拉同一 trace 的日志，就能定位到具体 service 方法。

### 3. `ContextVar` vs `request.state`：trace_id 到底该放哪

**一句话定义**：`ContextVar` 是**协程本地**的全局变量，`request.state` 是挂在单个请求对象上的属性。

**为什么存在**：日志 formatter 只拿到一条 `LogRecord`，**拿不到 request**。想让每条日志自动带 trace_id，只能存到一个"当前执行上下文可见"的地方。

**怎么用**

```python
trace_id_ctx: ContextVar[str] = ContextVar("trace_id", default="-")

token = trace_id_ctx.set(trace_id)       # 进中间件
...
finally:
    trace_id_ctx.reset(token)            # 必须 reset(token)，不是 set("-")
```

**底层机制**：`ContextVar` 的值存在 context 对象里，`asyncio` 每个 task 有独立 context 副本，所以并发请求互不串。`reset(token)` 恢复到**上一个值**（可能是外层中间件设的），`set("-")` 会把这层上下文直接覆盖掉。formatter 在 `format()` 时 `trace_id_ctx.get()`，拿到当前协程的值。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `request.state` 传 trace_id 给日志 | 路由能读到，日志里是 `-` | 日志侧只能读 `ContextVar` |
| 2 | 用 `set("-")` 代替 `reset(token)` | 嵌套中间件的外层 trace_id 被抹掉 | `reset(token)` |
| 3 | 在多线程里用 `ContextVar` 传值 | 新线程里读不到（默认值） | 线程要用 `copy_context()` 或 `threading.local` |
| 4 | 以为 `ContextVar` 会自动跟着 `run_in_executor` 走 | 线程池里日志又是 `-` | 提交时用 `ctx.copy().run(...)` 显式传递 |

**面试问法**
> Q：分布式的 trace_id 你怎么传给日志？
> A：放 `ContextVar`，不放 `request.state`。因为日志 formatter 只拿 `LogRecord`，拿不到 request；`ContextVar` 是协程本地的，中间件里 set、日志里 get，而且并发请求天然隔离。用完 `reset(token)` 恢复上一个值。

**追问链**
→ *"为什么不直接在每个函数里传 request？"* service 层不该知道 HTTP，传下去就把框架耦合进业务；而且 `logger.info` 的调用点根本拿不到 request。
→ *"什么情况下 `ContextVar` 会失效？"* 跨线程（`run_in_executor`、`ThreadPoolExecutor`）不会自动继承；跨进程（Celery、子进程）也不继承，必须把 trace_id 显式放进消息体。
→ *"和 OpenTelemetry 的关系？"* OTel 的 `contextvars` 就是同一个机制，`trace_id` 存在 `Context` 里，跨服务靠 header 传播（`traceparent`）——我们手写的这套是它的最小版。

### 4. `Router` 选路 vs `handler` 干活：404 / 405 / 422 分属哪个阶段

**一句话定义**：Router 只比对 **path + method** 选路（不跑依赖、不碰 body），选中之后才进"依赖树 → handler → 序列化"。

**为什么存在**：选路要快。如果每次 404 都先跑一遍鉴权和查库，一个扫描器打过来的无效路径就能把数据库打满。

**怎么用**（判据就一条：看依赖跑没跑）

| 情况 | 状态码 | 依赖跑了吗 | 卡在哪 |
|---|---|---|---|
| 正常请求 | 200 | ✅ | 全程 |
| 路径不存在 | 404 | ❌ | ⑤ 选路 |
| 方法不对 | 405 | ❌ | ⑤ 选路 |
| query / body 校验失败 | 422 | ✅ **是** | ⑥ 依赖已跑、handler 没跑 |

**底层机制**（`starlette/routing.py:680-700`）

```python
for route in self.routes:
    match, child_scope = route.matches(scope)     # 只比 path/method
    if match == Match.FULL:
        await route.handle(scope, receive, send)
        return
```

进到 handler 之后三段的顺序（`fastapi/routing.py`）：`solve_dependencies`（511 行）→ `run_endpoint_function`（745 行）→ `serialize_response`（767 行）。**511 在 745 之前**，所以"422 时依赖已经跑过"。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 看到 422 就以为"请求什么都没做" | 依赖里的审计日志/事务/计数器已经执行了 | 校验在依赖之后，副作用已发生 |
| 2 | 把审计写成依赖，指望 404 也被记录 | 扫描器打的无效路径全都没日志 | 要连 404 都记，只能放中间件 |
| 3 | 以为 405 也会跑依赖 | 405 时鉴权没跑，统计口径错 | 405 在选路阶段，依赖不跑 |
| 4 | 用 `serialize_response` 的报错当 422 | 返回类型不符是 `ResponseValidationError` → 500 | 出参校验失败是 500，不是 422（D3 会踩） |

**面试问法**
> Q：FastAPI 的 404 和 422 是在同一个阶段产生的吗？
> A：不是。404/405 在路由匹配阶段，只比 path 和 method，**依赖不跑**；422 在依赖解析阶段，**依赖已经跑完**。所以鉴权写成依赖时，404 路径是不鉴权的；要连 404 都记审计只能放中间件。另外，入参错了是 422，出参错了是 500——两个方向不对称。

**追问链**
→ *"为什么 422 不能提前到选路阶段？"* 校验需要 schema 和依赖树，而 schema 属于 route；选路时只知道 path，还没确定用哪套 schema。
→ *"这个顺序会带来什么故障？"* 依赖里开的事务，在 422 时已经开了，`yield` 依赖的 teardown 仍会跑（回滚），但"校验失败什么都没做"这个假设是错的——W7 写事务时这一点会咬人。
→ *"如果我要在 422 时区分'依赖跑了但校验失败'和'依赖也没跑'呢？"* 只能自己在依赖里埋点（比如往 `ContextVar` 记一笔），或者把校验提前到依赖里用 `model_validate` 手动做。

### 5. `BaseHTTPMiddleware`：能改 status，但读 body 有代价

**一句话定义**：`BaseHTTPMiddleware` 把下游的 `send` 换成一个内存队列，**攒完再转发**，所以 `dispatch` 返回前你还能改状态码和 header。

**为什么存在**：纯 ASGI 中间件要自己处理 `http.response.start` / `body` 消息，写法繁琐；`BaseHTTPMiddleware` 让你用"函数式"写法拿到 Response 对象。代价是它在中间加了一层缓冲区。

**怎么用**

```python
class TraceMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        resp = await call_next(request)
        resp.status_code = 201            # 实测有效（buffer 模式）
        resp.headers["x-added"] = "1"     # 有效
        return resp
```

**底层机制**：下游 `send(http.response.start)` 时，消息只是被记进队列，没有真发给客户端；等 `dispatch` 返回后框架才按序重发。**start 没出去，所以改得动。** 换成纯 ASGI 中间件边收边转发，start 一发出去，改 `resp.status_code` 就只是自娱自乐（实测：客户端仍看到 200）。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 在中间件里 `await request.body()` 读大文件 | 整个 body 进内存，500MB 上传直接 OOM | 中间件只碰 path / header / method |
| 2 | 以为读 body 会让下游读不到 | 1.9.0 会缓存重放，下游照样读到 | 能读到，但流式语义被破坏 |
| 3 | 在中间件里算"接口耗时" | `/chat` 实际 10 秒，日志 30ms | call_next 返回时 body 还没发 |
| 4 | 靠中间件偷偷改状态码 | 路由写的 201 莫名变 418，排查极难 | 要改结果就改产生结果的地方 |

**面试问法**
> Q：`BaseHTTPMiddleware` 里 `call_next` 之后改 `status_code` 有效吗？
> A：在 `BaseHTTPMiddleware` 里**有效**，因为它把下游的 `send` 换成内存队列、攒完再转发，`http.response.start` 还没发出去。但换成纯 ASGI 中间件、边收边转发，start 一出去就改不动了。真实规则是"谁最后写 start 谁说了算"。而且能改不代表该改，中间件只该加 header、记日志。

**追问链**
→ *"那读 body 呢？下游还能读到吗？"* 1.9.0 能，`_CachedRequest` 会缓存重放。但整个 body 进内存，流式（SSE）会被降级成块，所以结论是"不该读"而不是"不能读"。
→ *"流式接口的耗时怎么量？"* `call_next` 返回时 body 还没发，量到的只是路由函数时间。要真量得写纯 ASGI 中间件，监听 `http.response.body` 的 `more_body=False` 那一帧。
→ *"所以你的 `/chat` 接口耗时日志准吗？"* 不准，那是"生成器启动前的耗时"。所以我们在生成器结束时自己记了一条 `llm_done`，两条一起看才完整。

### 6. `exc.errors()` 不可序列化 → 422 变 500（项目真 bug）

**一句话定义**：pydantic 把 validator 抛的原始异常塞进错误项的 `ctx.error`，`JSONResponse` 遇到活的异常对象就 `TypeError`，于是"参数校验失败"变成"服务器错误"。

**为什么存在**：这是 pydantic v2 保留原始异常的设计（方便调试），但 FastAPI 的 `JSONResponse` 不认异常对象。两者一直没对上，直到你加第一个自定义 validator。

**怎么用**（修法）

```python
from fastapi.encoders import jsonable_encoder

content={"detail": jsonable_encoder(exc.errors())}   # 推荐
```

**底层机制**：`ValidationError.errors()` 返回的是 list[dict]，其中一个键是 `ctx: {"error": ValueError("x 不能大于 10")}`。`json.dumps` 走 `default` 找不到编码器 → `TypeError`。`jsonable_encoder` 认识 `Exception` → 转成字符串/空 dict，于是能序列化。

**实测两行对比**

```
不修：TypeError: Object of type ValueError is not JSON serializable   → 500
修后：422 {"type":"value_error","loc":["body","name"],"msg":"Value error, ...","ctx":{"error":{}}}
```

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 `exc.errors()` 一定能序列化 | 加了 validator 后 422 变 500 | `jsonable_encoder(exc.errors())` |
| 2 | 用 `str(exc.errors())` 兜底 | 前端拿到一坨字符串，没法按字段展示 | 编码器保留结构 |
| 3 | 以为这个 bug 只在 D3 才会出现 | 只要有一个 validator 抛 `ValueError` 就炸 | 与"有没有 validator"绑定，不是与"哪个接口" |
| 4 | 修完不写测试 | 将来有人改回 `exc.errors()` 也发现不了 | 造一个抛 `ValueError` 的 validator 用例 |

**面试问法**
> Q：FastAPI 里参数校验失败一定返回 422 吗？
> A：不一定。如果你的 `RequestValidationError` handler 直接把 `exc.errors()` 塞进 `JSONResponse`，而某个自定义 validator 抛了 `ValueError`，`ctx.error` 是活的异常对象，序列化会 `TypeError`，客户端收到的是 **500**。修法是用 `jsonable_encoder` 包一层。

**追问链**
→ *"为什么 `ctx.error` 不是字符串？"* pydantic v2 保留原始异常便于调试和自定义渲染；是否字符串化由序列化层决定。
→ *"除了 validator，还有哪里会踩？"* 任何 `extra` 里塞对象、`ctx` 里塞自定义类；以及 `response_model` 校验失败抛的 `ResponseValidationError`（那条更严重，直接 500）。
→ *"怎么保证以后不再犯？"* 测试里固定造一个"validator 抛 ValueError"的用例；再在 code review 时把"handler 里出现 `exc.errors()` 裸用"当作红线。

### 7. 日志里 `ContextVar` 的生命周期：reset 早于打日志

**一句话定义**：`finally: trace_id_ctx.reset(token)` 会在**成功路径的日志语句之前**执行，所以那条日志里的 trace_id 已经变回默认值 `-`。

**为什么存在**：这不是设计，是顺序写错了。`finally` 的语义是"离开 try 之前一定执行"，而把"打日志 + 写响应头"放在 `finally` 之后，等于在上下文已经清空之后再去读它。

**怎么用**（正确结构：成功逻辑进 `else`，`finally` 只负责收尾）

```python
try:
    response = await call_next(request)
except Exception:
    logger.exception("request_failed", extra={...})   # 此时 trace_id 还在
    raise
else:
    duration_ms = round((time.perf_counter() - start) * 1000, 2)
    logger.info("request", extra={..., "status": response.status_code})  # trace_id 还在
    response.headers["X-Trace-Id"] = trace_id
    response.headers["X-Duration-Ms"] = str(duration_ms)
    return response
finally:
    trace_id_ctx.reset(token)                          # 最后才清
```

**底层机制**：`try/except/else/finally` 的执行顺序是 `try` → `else`（无异常）→ `finally`。日志的 `trace_id` 不是打日志那一刻算出来的，而是 `JsonFormatter.format()` 里 `trace_id_ctx.get()` 取的——所以"什么时候 reset"直接决定日志里写什么。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | reset 放 finally、日志放 finally 之后 | 成功日志 `trace_id: "-"`，响应头却正常 | 成功逻辑放 `else`，reset 放 `finally` |
| 2 | 只把 reset 挪到最后 | 异常路径不 reset，上下文泄漏 | 必须 `else` + `finally` 组合 |
| 3 | 靠"响应头对了"判断日志也对 | 头是变量直接赋的，日志是 formatter 现取的 | 两个通道要分别断言 |
| 4 | 测试只断言响应头 | 三天没发现日志全是 `-` | 加一条 `caplog` 断言 trace_id |

**面试问法**
> Q：你怎么保证每条日志都带 trace_id？
> A：两件事。一是值放 `ContextVar`，formatter 每次 `format()` 现取；二是**生命周期要对**——`reset` 必须在所有日志语句之后。我们踩过一次：`reset` 在 `finally`、日志在 `finally` 后面，结果所有成功日志的 trace_id 都是 `-`，而响应头是对的，所以测试一直绿。

**追问链**
→ *"为什么测试没发现？"* 测试断言的是响应头 `X-Trace-Id`，没人断言日志字段。覆盖率 96.57% 照样漏——这是"断言选错通道"的典型。
→ *"日志里丢了 trace_id 后果有多严重？"* 排查时按 trace_id 聚合日志，成功请求的那条查不出来，等于只有失败才有链路。最常用的路径反而没数据。
→ *"怎么系统性防住这类问题？"* 关键字段要在"出口"断言：响应头、日志字段、指标标签三个通道各来一条测试；或者用日志采样断言（`caplog` + `JsonFormatter`）统一校验。

### 8. `ContextVar` 值的信任边界：消毒不能把正常流量挡住

**一句话定义**：`X-Trace-Id` 是客户端可控输入，直接 `set()` 进上下文等于让外部决定你的日志字段；但"消毒"过头会切断跨服务链路对账。

**为什么存在**：不做限制，客户端能塞 8KB 垃圾进日志（日志膨胀、对账错乱）；限制太严（只认小写十六进制），上游用 `str(uuid4())` 或大写 hex 传进来的 trace_id 全被丢弃——上游日志是 A，下游是 B，永远对不上。

**怎么用**（放宽到 W3C 风格的字符集，长度封顶）

```python
_TRACE_ID_RE = re.compile(r"^[A-Za-z0-9._-]{1,64}$")   # 字母/数字/._-，限 64 字符

def _sanitize_trace_id(raw: str | None) -> str:
    if raw and _TRACE_ID_RE.match(raw):
        return raw
    return uuid.uuid4().hex            # 不合格就自己生成
```

**底层机制**：HTTP header 值由 ASGI server 保证不含换行（uvicorn 会拒绝非法 header），所以"头注入"不成立；真正的风险是**长度**和**字符集破坏日志解析**（比如包含空格或引号让 JSON 日志变味）。所以过滤的重点是长度和字符白名单，不是"防注入"。

**实测五种输入**

| 客户端传 | 结果 |
|---|---|
| `abc123` | 透传 |
| `ABC123` | 透传（大写不再被误挡） |
| `11111111-1111-4111-8111-111111111111` | 透传（连字符 UUID 不再断链） |
| 200 位长串 | 重新生成 |
| 空格 | 重新生成 |

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 白名单写成 `[a-f0-9]` | 上游 `str(uuid4())` 全被丢，链路断 | `[A-Za-z0-9._-]` |
| 2 | 消毒函数永远返回非空，外面还写 `or uuid4()` | `or` 右边是死代码，两处长度还不一致 | 只留一处生成 |
| 3 | 定义 `_MAX_TRACE_ID_LEN = 64` 但正则里硬编码 64 | 改一处忘一处 | 常量用进正则（f-string）或删掉 |
| 4 | 以为 header 可能被注入换行 | 白防一场 | ASGI server 已挡住；防长度和字符集 |

**面试问法**
> Q：客户端传来的 trace_id 你会直接用吗？
> A：会透传，但要过一道白名单：长度 ≤ 64、字符集限定字母数字和 `._-`，不合格就自己生成。不能只认小写十六进制——上游常用 `str(uuid4())`（带连字符）或大写 hex，挡掉就等于切断链路对账。

**追问链**
→ *"不透传行不行，全部自己生成？"* 那就断了跨服务追踪：网关生成的 id 传不下来，一个用户请求在日志里会变成 N 条不相关的链路。
→ *"长度上限怎么定？"* 按上游最长的 id 形态定（W3C `traceparent` 是 55 字符，UUID 带连字符 36），64 给足余量；再长的一律视为垃圾。
→ *"如果是多租户/对外 API 呢？"* 还要考虑"客户端故意传同一个 trace_id 污染你的日志"——可以做前缀区分（`ext-`）或按租户加盐，别让外部值和对内值混在一起。

### 9. `TestClient(raise_server_exceptions=False)`：没设过它的测试没测过 500

**一句话定义**：`TestClient` 默认把服务端未捕获异常**原样抛给测试代码**，所以你根本拿不到 500 响应。

**为什么存在**：测试时希望看到真实 traceback，而不是一个不透明的 500。代价是"500 路径永远测不到"。

**怎么用**

```python
with TestClient(app, raise_server_exceptions=False) as c:
    r = c.get("/boom")
    assert r.status_code == 500
```

**底层机制**：`TestClient` 在 ASGI transport 里把异常收集起来，请求结束后在关闭阶段 `raise exception`（`starlette/testclient.py:399`）。所以你会看到 `A>` 只有一条——异常把中间件炸掉了，测试接住的是**原异常**。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 断言 500 却用默认 client | 测试里抛 `RuntimeError`，不是断言失败 | `raise_server_exceptions=False` |
| 2 | 以为 500 分支被覆盖率算进去了 | 行覆盖率高但异常路径没断言 | 覆盖率不区分"跑到"和"断言了" |
| 3 | 用它测业务 4xx | 4xx 是正常响应，不需要这个参数 | 只有"没人接的异常"才需要 |

**面试问法**
> Q：FastAPI 里怎么测 500？
> A：`TestClient(app, raise_server_exceptions=False)`。默认它会把未捕获异常直接抛给测试代码，拿不到 500 响应。反过来说，一个测试文件里从来没出现过这个参数，就说明 500 路径从来没被测过。

**追问链**
→ *"为什么默认要抛？"* 开发期希望看到真实 traceback 和原始异常类型，而不是被 500 遮住。
→ *"那不测 500 有什么风险？"* 500 的响应体是你统一错误格式的最后一道关，没人断言就等于线上可能返回纯文本 `Internal Server Error`，前端解析直接崩。
→ *"你们项目测了吗？"* 目前没有专门测 500 的用例（`grep raise_server_exceptions` 为空），这是明确缺口，D6 反脆弱那天补。

### 10. 中间件的耗时 ≠ 接口耗时（流式接口）

**一句话定义**：`call_next` 返回时**响应体还没发**，中间件量到的是"路由函数跑完的时间"，不是"客户端收完的时间"。

**为什么存在**：`BaseHTTPMiddleware` 拿到的是一个响应 wrapper，body 是待消费的流。真正的发送发生在你把 Response 返回之后。

**怎么用**（能拿到的和拿不到的分开记）

```python
duration_ms = round((time.perf_counter() - start) * 1000, 2)   # 到"响应对象生成"
logger.info("request", extra={"duration_ms": duration_ms})     # 别叫它 latency
```

**底层机制**：ASGI 的响应是 `http.response.start` + 若干 `http.response.body` 消息。中间件在 `dispatch` 里只能看到 start 阶段的产物；body 逐帧发送发生在更外层（甚至 uvicorn 里）。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 `duration_ms` 当接口延迟报警 | SSE 接口 10 秒，告警显示 30ms | 流式接口单独埋点（生成器结束时） |
| 2 | 用 `time.time()` 计时 | 3.11 Windows 粒度 15.6ms，短请求全是 0/15.6 跳变 | `perf_counter()` |
| 3 | 墙钟回拨导致负耗时 | `duration_ms: -12` | `perf_counter()` 单调递增 |
| 4 | 在大文件下载接口上用它算吞吐 | 数字小得离谱 | 吞吐要靠 nginx/uvicorn 的 access log |

**面试问法**
> Q：你的接口耗时日志准吗？
> A：普通 JSON 接口准，量的是路由函数执行时间；流式接口（SSE）不准——`call_next` 返回时响应体还没开始发，量到的只是"生成器启动前"的时间。要量真实时长，得写纯 ASGI 中间件监听 `http.response.body` 的最后一帧，或者在生成器结束时自己记一条。

**追问链**
→ *"为什么用 `perf_counter` 不用 `time.time`？"* `time.time` 是墙钟，会被 NTP 回拨，可能算出负数；而且在 Windows + Python 3.11 上粒度是 15.6ms（实测 `get_clock_info('time').resolution == 0.015625`），短请求的耗时全是同一个值。
→ *"那 `X-Duration-Ms` 给谁看？"* 给排查用的相对值（哪个接口慢一个数量级），不是 SLA 指标；SLA 要看服务端 access log + 客户端测速。
→ *"RAG 场景怎么改？"* LLM 流式输出是主路径，耗时拆成三段：检索、首 token、全部生成完——前两段中间件能记，第三段必须业务侧在生成器里记。

## 三、30 秒答案集

1. **中间件顺序**：后 `add` 的在外层，因为 `add_middleware` 是 `insert(0)`，建栈时 `reversed` 包裹。
2. **响应方向**：响应逆序穿回，`A> B> handler <B <A`。
3. **谁翻译异常**：`AppError` 这类注册过的由内层 `ExceptionMiddleware` 翻译，翻译完就是普通响应。
4. **中间件记不到 500**：500 由最外层 `ServerErrorMiddleware` 生成，那时中间件已被异常炸出调用栈。
5. **`except` 里必须 `raise`**：不 re-raise 会让 dispatch 返回 `None`，真凶被 `TypeError` 顶掉。
6. **404 vs 422**：404/405 在选路阶段（依赖不跑），422 在依赖解析阶段（依赖已跑）。
7. **`BaseHTTPMiddleware` 能改状态码**：它把 `send` 换成内存队列，start 还没发出去。
8. **读 body 的代价**：能读到（会重放），但整个 body 进内存、流式变块。
9. **trace_id 存哪**：`ContextVar`，因为 formatter 拿不到 request；用完 `reset(token)`。
10. **`reset` 的位置**：必须在所有日志语句之后，否则日志里的 trace_id 变 `-`。
11. **`exc.errors()` 会炸**：`ctx.error` 是活的异常对象，要 `jsonable_encoder` 包一层。
12. **测 500 的开关**：`TestClient(app, raise_server_exceptions=False)`。
13. **耗时的真相**：`call_next` 返回时 body 未发，流式接口的耗时是假的。
14. **trace_id 消毒**：白名单 `[A-Za-z0-9._-]{1,64}`，别只认小写十六进制。

## 四、白板手写靶

### 靶 1：`TraceMiddleware.dispatch` 骨架（面试最可能让你写）

```python
class TraceMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next: RequestResponseEndpoint) -> Response:
        trace_id = _sanitize_trace_id(request.headers.get("X-Trace-Id"))
        token = trace_id_ctx.set(trace_id)
        logger = logging.getLogger("kb_service.access")
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            logger.exception("request_failed", extra={"duration_ms": ...})
            raise
        else:
            duration_ms = round((time.perf_counter() - start) * 1000, 2)
            logger.info("request", extra={"status": response.status_code, "duration_ms": duration_ms})
            response.headers["X-Trace-Id"] = trace_id
            response.headers["X-Duration-Ms"] = str(duration_ms)
            return response
        finally:
            trace_id_ctx.reset(token)
```

要点：`logger.info` 必须在 `finally` **之前**（放 `else` 里）；`except` 里必须 `raise`。

### 靶 2：六层栈 + 两条路径

```
① ServerErrorMiddleware        ← 500 在这生成
 ③ TraceMiddleware             ← 记日志，记不到 500
  ④ ExceptionMiddleware        ← AppError / RequestValidationError 的 handler
   ⑤ Router（比 path+method）  ← 404 / 405
    ⑥ 依赖树 → handler → 序列化 ← 422 / 业务异常

响应：⑥→⑤→④→③→①（每层过手，③ 能看到 404/422）
异常：⑥→④(有 handler 就变响应)→③(except 记一笔再 raise，自己死掉)→①(造 500)
```

要点：404 依赖不跑、422 依赖已跑；③ 在异常路径上"死"在 `raise` 那一刻。

### 靶 3：校验错误的统一响应

```python
from fastapi.encoders import jsonable_encoder

@app.exception_handler(RequestValidationError)
async def handle_validation(_: Request, exc: RequestValidationError) -> JSONResponse:
    return JSONResponse(
        status_code=422,
        content={
            "code": "VALIDATION_ERROR",
            "message": "参数校验失败",
            "detail": jsonable_encoder(exc.errors()),
        },
    )
```

要点：`jsonable_encoder` 不能少，否则 `ctx.error` 里的 `ValueError` 让 422 变 500。

## 六、可以讲成故事的三段

**故事一：异常处理器到底在哪一层**
我以为 `@app.exception_handler(Boom)` 注册的 handler 在最外层，所以中间件"应该能看到"它。画图时把 `handler` 画在 `ServerErrorMiddleware` 外面，后来读 `build_middleware_stack` 才发现：`if key in (500, Exception)` 才交给最外层，普通异常类全部进**内层** `ExceptionMiddleware`。教训：**"谁先收到请求"和"谁先捕获异常"是两个相反的方向**——请求从外往里，异常从里往外。

**故事二：我的测试断言了响应头，没断言日志**
`TraceMiddleware` 里 `reset` 写在 `finally`，日志写在 `finally` 之后，于是所有成功日志的 `trace_id` 都是 `-`，而响应头一切正常。测试只断言了 `X-Trace-Id`，所以三天全绿。教训：**同一个值有多个出口（响应头 / 日志 / 指标），断言必须落在每个出口上**；覆盖率 96% 也不代表对。

**故事三：防护做过头，把链路对账切断了**
给客户端可控的 `X-Trace-Id` 加消毒，第一版正则只认小写十六进制。实测发现上游传的 `str(uuid4())`（带连字符）和大写 hex 全被丢弃、重新生成——跨服务的 trace 从此对不上。教训：**输入过滤的白名单要按"合法流量的实际形态"定，不是按"我以为的格式"定**；改完必须回归正常路径，"更严格"不等于"更正确"。

**下日预告（D3 会撞的坑，别说内容说坑）**
1. `response_model` 会**静默丢字段**：路由多返回的键不会报错，直接消失（实测 `{'id':1,'name':'a','secret':'hunter2'}` → `{'id':1,'name':'a'}`）。想靠它防泄露，得先知道它在过滤。
