## 零、先看主线：一次请求的"地址"和"外壳"是怎么被决定的

D4 的所有知识点，都挂在同一条时间轴上。**看清这条轴，比记住任何一条规则都重要。**

```
【注册时 · 进程启动那几百毫秒】                      【请求时 · 每个请求都走一遍】
                                                      ┌──────────────────────────────┐
@router.get("/kbs/{kb_id}")  ← 记下"相对路径"          │ ① 按注册顺序匹配 path          │
        ↓                                             │ ② 解析/校验参数（分页!）        │
api_router.include_router(router, prefix="/kbs")      │ ③ 调 handler 拿返回值          │
        ↓  ← 拼一层                                   │ ④ 按 response_model 套外壳      │
app.include_router(api_router, prefix="/api/v1")      │ ⑤ 序列化 → 发出去              │
        ↓  ← 再拼一层                                 └──────────────────────────────┘
路由表里出现完整路径 /api/v1/kbs/{kb_id}
OpenAPI 文档在此时生成（/openapi.json）
```

**分界线一句话：注册时定"形状"（路径、分组、鉴权、文档），请求时填"内容"（参数、数据、状态码）。**

这条线和 D1 的"注册时建树 / 请求时走树"、D2 的"响应活着穿回 / 异常炸死一层"是同一层思维：**FastAPI 的绝大部分"魔法"都是启动时的一次性登记，不是请求时的动态判断。** 你以后每学一个框架特性，先问它落在轴的哪一侧，能省掉大量误解。

### 本篇四个知识点各自落在轴上的哪个位置

| 知识点 | 落点 | 一句话 |
|---|---|---|
| 路由分组 / prefix | **注册时** | 前缀是**拼**出来的，拼几次出几次 |
| 路由匹配顺序 | **请求时①** | 按注册顺序**首个匹配者赢**，不是"最具体的赢" |
| 统一响应体（envelope） | **请求时④** | 由 `response_model` 决定，不是由你 `return dict` 决定 |
| 分页 | **请求时② + ④** | 入参在②校验，出参 `Page[T]` 在④序列化 |
| 版本化 | **注册时** | 版本号是 URL 的一部分，还是路由表的一份拷贝——两种选择，两种未来 |
| OpenAPI | **注册时** | 文档不是写出来的，是**路由表的副产品** |

### 每节读完之后的自查

> 每读完一节，问自己：**"这一节讲的东西，是在进程启动时生效，还是在这个请求进来时生效？"** 答不出来的那节，回去重读，不要往下走。

## 一、痛点场景：没有分组、没有统一形状、没有分页的世界

### 1.1 四十个接口手工拼字符串

假设没有 `APIRouter`，你只能在 `main.py` 里一个个挂：

```python
@app.get("/api/v1/kbs")
@app.get("/api/v1/kbs/{kb_id}")
@app.get("/api/v1/kbs/{kb_id}/documents")
@app.get("/api/v1/kbs/{kb_id}/documents/{doc_id}")
@app.post("/api/v1/chat")
...
```

三个月的项目，`/api/v1` 这个字符串会出现 40 次。某天产品说"升到 v2"，你要改 40 处——**改漏一处，那个接口就静默停在 v1**，测试不一定抓得到（因为测试可能也硬编码了同一个错误路径）。

`APIRouter` 解决的就是这个：**把"这一段前缀"从 40 处收成 1 处**。它的本质极其朴素——**字符串拼接，发生在注册时**。没有任何魔法，正因为没有魔法，你不知道规则就会拼错（§3.2 那个 `/kbs/kbs` 就是拼错的现场）。

### 1.2 前端要为每个接口写一套解析

看你项目现在的真实响应形状（实测）：

```
成功： {"id": "…", "name": "kb0", "description": null, ...}          ← 裸资源
失败： {"code": "UNAUTHORIZED", "message": "缺少认证信息", "detail": null}  ← 带外壳
```

两套形状。前端每调一次接口，都得判断"这是成功形状还是失败形状"，TS 类型要写两个联合类型，还要处理"HTTP 200 但 body 里 code 非 0"这种恶心情况（你现在的项目还没这种，但很多公司有）。

统一响应体（envelope）就是把这个收成一套：

```
成功： {"code": 0, "message": "ok", "data": {...}}
失败： {"code": "UNAUTHORIZED", "message": "缺少认证信息", "detail": null}
```

注意这两行**看起来像统一了，其实还差一步**——`code` 一处是 `int` 一处是 `str`，`data` 和 `detail` 是两个不同的键。**"统一"不是"都有三个字段"，是"同一套字段、同一套类型"**。这是本篇最容易做假的地方，§7.4 会给出真正的统一方案和它的代价。

### 1.3 没有分页规范的两个真实后果

```
GET /api/v1/documents        → 返回全部 12 万条（4.8MB JSON，前端卡死，DB 被打满）
GET /api/v1/kbs?size=100000  → 客户端能要多少要多少（一个请求打穿服务）
```

第一条是**功能缺陷**，第二条是**安全缺陷**。分页不是"锦上添花的体验优化"，是**接口的第一条硬约束**。你项目里已经有 `size: int = Query(default=20, ge=1, le=100)`——`le=100` 这五个字符就是防御，别把它当装饰（§8.3 实测了它确实拦得住）。

## 二、最小可跑示例（5 分钟亲手跑）

三级嵌套 + 一次重复拼接，看清前缀到底怎么拼：

```python
# 存成 /tmp/d4_prefix.py，用项目解释器跑
from fastapi import FastAPI, APIRouter

inner = APIRouter(prefix="/docs")          # 第 3 层：自带 prefix

@inner.get("")                              # 注意是 ""，不是 "/"
def list_docs() -> str:
    return "list"

mid = APIRouter(prefix="/kbs")             # 第 2 层
mid.include_router(inner)                   # 把第 3 层挂上来

app = FastAPI()
app.include_router(mid, prefix="/api/v1")   # 第 1 层

print("[真实路径]", list(app.openapi()["paths"]))
```

```powershell
# Windows PowerShell（kb-service 目录下）
& .\.venv\Scripts\python.exe ..\..\..\tmp\d4_prefix.py
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/python.exe /tmp/d4_prefix.py     # Linux 用 .venv/bin/python
```

实测输出：

```
[真实路径] ['/api/v1/kbs/docs']
```

三层前缀，**从内到外依次拼接**：`""` + `/docs` + `/kbs` + `/api/v1` = `/api/v1/kbs/docs`。

然后把最后一行改成重复拼一次，看会发生什么：

```python
app.include_router(mid, prefix="/api/v1/kbs")   # 把 kbs 又写了一遍
```

实测输出：

```
[真实路径] ['/api/v1/kbs/kbs/docs']
```

**没有报错，没有警告，只是路径变成了另一个。** 这就是"注册时字符串拼接"的全部真相——它不检查语义，只做连接。§3.2 会告诉你这个坑在真实项目里长什么样。

## 三、概念逐层

### 3.1 `APIRouter` 到底是什么

一个**收集器**。它不处理请求，只做四件事：

```python
router = APIRouter(
    prefix="/kbs",              # 拼到路径前面
    tags=["knowledge-bases"],   # 文档分组（只影响 /docs，不影响请求）
    dependencies=[...],          # 挂在这一组上的依赖（§5 重点）
    responses={404: {...}},      # 这一组通用的响应文档
)
```

`@router.get(...)` 和 `@app.get(...)` 的区别只有一条：**前者登记到 router 上，后者登记到 app 上**。而 `include_router` 做的事，就是**在注册时把 router 里攒下的所有 route，逐个复制到 app 的路由表里，路径前缀拼上**。

推论（面试常问）：**`include_router` 必须在启动前调用完**。你在请求处理函数里调 `include_router`，它确实会往表里加路由——但 Starlette 的路由匹配用的是启动时构建的 matcher，加了也不生效（**未实测**，属于"不要这么写"的设计约束）。

### 3.2 前缀三条规则（每条都有实测）

**规则一：从内到外拼接，空串等于不加。**

`@inner.get("")` 和 `@inner.get("/")` 不一样：

| 写法 | 拼出来的路径 | 结果 |
|---|---|---|
| `@inner.get("")` | `/api/v1/kbs/docs` | ✅ 推荐 |
| `@inner.get("/")` | `/api/v1/kbs/docs/` | 多一个尾斜杠，客户端写 `/docs` 会 307 重定向 |

尾斜杠看起来无害，但**重定向在 POST/PUT 时会被部分客户端降级成 GET**（307 会保留方法，301/302 不会），这是那种"测试全绿、线上偶发"的坑。规矩：**路径里要么全不带尾斜杠，要么全带，别混。**

**规则二：不要重复拼。** 上面实测过 `prefix="/api/v1/kbs"` + router 自带 `/kbs` = `/api/v1/kbs/kbs`。

**规则三：`app.routes` 在 FastAPI 0.150 不再是扁平列表**（本项目实测发现）：

```python
from kb_service.main import create_app
app = create_app()
for r in app.routes:
    print(type(r).__name__, "|", getattr(r, "path", None))
```

```
Route | /openapi.json
Route | /docs
Route | /docs/oauth2-redirect
_IncludedRouter | None          ← 整个 api_router 就这一行，惰性展开
```

所以你**不能用 `app.routes` 去核对真实路径**，要用：

```python
print(list(app.openapi()["paths"]))
```

实测本项目输出（这就是你现在的 API 形状）：

```
GET          /api/v1/health
POST,GET     /api/v1/kbs
GET          /api/v1/kbs/stats/count
GET,PATCH,DELETE /api/v1/kbs/{kb_id}
POST,GET     /api/v1/kbs/{kb_id}/documents
GET,DELETE   /api/v1/kbs/{kb_id}/documents/{doc_id}
POST         /api/v1/chat
```

**这七行是你项目的"对外合同"**。D4 动手任务的第一步就是：先把这七行抄到纸上，改完再打一次，对比着看——**改路由不对比路径表，等于闭着眼睛改。**

### 3.3 路由匹配顺序：首个匹配者赢，不是"最具体的赢"

这节是本篇最值钱的一节，因为它是**唯一一个"代码看着没错、行为反直觉"**的点。

先看一个**不冲突**的例子（很多人会误判成冲突）：

```python
r = APIRouter(prefix="/kbs")
@r.get("/{kb_id}")       # 一段
def get_one(kb_id: UUID): return "detail"
@r.get("/stats/count")   # 两段
def count(): return {"count": 0}
```

实测 `GET /kbs/stats/count` → **200 `{"count":0}`**。

为什么？因为 `/{kb_id}` 只匹配**一段**（`[^/]+`），`stats/count` 是两段，压根到不了这条路由。**段数不同 = 天然不冲突。**

现在看**真会撞**的：同段数。

```python
@r.get("/{kb_id}")    # 先注册
def get_one(kb_id: UUID): return "detail"
@r.get("/stats")      # 后注册，一段，静态
def stats(): return {"count": 0}
```

实测：

```
[参数在前] GET /kbs/stats -> 422      ← stats 被当成 UUID 去解析，解析失败
[静态在前] GET /kbs2/stats -> 200
```

**同一个 URL、同一个 handler 集合，只因为注册顺序不同，一个 422 一个 200。**

机制：Starlette 的路由匹配是**按注册顺序线性尝试**，第一个 path 正则匹配上的就进去。`/{kb_id}` 的正则是 `[^/]+`——它能匹配字符串 `stats`。匹配成功后，FastAPI 才去把 `"stats"` 转成 `UUID`，转不动 → 422。**它不会"发现下一条款式更合适"，它连看都不看下一条。**

你项目里现在是**对的**（`/stats/count` 注册在 `/{kb_id}` 之前），但这是运气还是刻意？**看完这节你应该知道：这是必须写进代码顺序的约束，不是运气。** 更稳的做法是给静态段加语义前缀（`/stats/...`、`/search/...`），或者干脆避开"静态词 + 单段参数"同层。

> **面试一句话**：路由匹配是"注册顺序 + 正则首个命中"，不是"最长前缀优先"或"静态优先"。所以静态路由必须写在参数路由之前，否则会被参数路由吃掉、然后在类型转换时 422。

### 3.4 `tags`：只影响文档，不影响请求

```python
api_router.include_router(knowledge_bases.router, prefix="/kbs", tags=["knowledge-bases"])
```

`tags` 的唯一作用是 `/docs` 里的分组标题。它**不参与匹配、不参与鉴权、不影响状态码**。

但它的价值不小：`tags_metadata` 能给每个分组写描述，让 `/docs` 从"接口清单"变成"能给前端看的说明书"。D5 会细做，这里知道它落在**注册时**就行。

### 3.5 路由级 `dependencies`：一次挂上，全组生效

你现在每个函数都写着 `user_id: UUID = Depends(get_current_user_id)`（实测 6 处重复）。如果某个新接口忘了写——**默认就没有鉴权，而且完全不报错**，这是最危险的漏法。

路由级依赖解决它：

```python
r = APIRouter(prefix="/x", dependencies=[Depends(get_current_user_id)])

@r.get("/a")
def a(): return "a"          # 不用写 Depends
```

实测（无 token）：

```
[路由级依赖] /x/a 无 token -> 401 | /x/b -> 401
[OpenAPI] /x/a 的 security: [{'Bearer Token': []}]
```

两个事实：① 两个路由都被拦 ✅；② **OpenAPI 里 security 自动出现在每个 operation 上** ✅（前端生成 SDK 时会自动带 token 字段）。

对照项目现状（无 token）：

```
[无 token] GET /api/v1/kbs -> 401 {'code': 'UNAUTHORIZED', 'message': '缺少认证信息', 'detail': None}
[无 token] GET /api/v1/health -> 200     ← health 不需要鉴权
```

所以 D4 的重构不是"把 router 全挂上鉴权"，而是：**给需要鉴权的 router 挂，`health` 留在外面**。这个划分必须在代码结构上体现出来（`health` 不挂在受保护的 router 下），不能靠"每个函数记得写"。

### 3.6 版本化：三种策略，两种未来

| 策略 | 长相 | 优点 | 缺点 |
|---|---|---|---|
| **URL path**（主流） | `/api/v1/kbs` | 一眼可见、可缓存、可路由、调试友好 | URL 变长；"资源"和"版本"混在一起 |
| **Header** | `Accept-Version: v1` | URL 干净、语义上版本不属于资源 | 不可分享链接、CDN 缓存要配置 Vary、调试器里看不见 |
| **Media type** | `Accept: application/vnd.api.v1+json` | 最"REST 正确" | 前端发请求要改 header，工具链支持差 |

小厂/内部项目**一律选 URL path**，理由只有一条：**能直接分享、能直接 curl、能在日志里一眼看出**。你项目现在就是 URL path（`/api/v1/...`），方向对。

真正要决策的是**前缀写在哪一层**，这决定了你升到 v2 那天要改什么：

**做法 A（项目现状）：前缀写在 `main.py`**

```python
app.include_router(api_router, prefix="/api/v1")     # main.py
```

升 v2 时：新建 `api/v2/router.py`，再 `app.include_router(api_v2_router, prefix="/api/v2")`。**v1 和 v2 共存是两个 router 各挂各的**，互不影响。缺点：`main.py` 是唯一知道"当前有哪些版本"的地方，新人容易漏看。

**做法 B：版本写进 router 自己**

```python
api_router = APIRouter(prefix="/v1")     # router.py 里
```

`main.py` 只写 `app.include_router(api_router, prefix="/api")`。好处：版本跟着代码目录走（`api/v1/` 目录 → `/v1` 前缀，一眼对应），`main.py` 不用改。坏处：`/api` 和 `/v1` 分居两处，拼错了不容易发现（`/v1/api` 这种）。

**我的建议：选 B**。理由不是"更优雅"，是**目录结构和 URL 结构一致**——`api/v1/` 这个目录名本身就在宣告版本，前缀跟着目录走，重构时不会错位。D4 动手任务里就把 A 改成 B。

> 顺带一个真实世界的细节：v2 上线时 v1 不能立刻删（老客户端还在调）。标准做法是 v1 保留 + 响应加 `Sunset: Sat, 01 Mar 2027 00:00:00 GMT` 头 + 文档标 deprecated。**这属于"知道有这回事"级别，不用现在做。**

### 3.7 统一响应体（envelope）：三种做法与各自代价

先把"为什么要"说清：**客户端只需要一套解析逻辑**。你项目现在有 `{code, message, detail}` 的错误形状，却没有成功形状的外壳——**这是半套，比零套更糟**，因为前端已经写了错误分支，成功分支还得写第二套。

三种实现，逐一说明代价：

**做法 A：每个接口显式写 `response_model=ApiResponse[X]`**

```python
@router.get("/{kb_id}", response_model=ApiResponse[KBOut])
async def get_kb(...) -> Any:
    return {"code": 0, "message": "ok", "data": KBService().get_or_403(...)}
```

实测（嵌套泛型，两层的）：

```
[嵌套泛型] /paged -> {'code': 0, 'message': 'ok', 'data': {'items': [{'id': 1, 'name': 'a'}], 'total': 1, 'page': 1, 'size': 20}}
[嵌套泛型] schema 名: ['ApiResponse_Any_', 'ApiResponse_Page_KBOut__', 'KBOut', 'Page_KBOut_']
```

看那个 schema 名：`ApiResponse_Page_KBOut__`——**pydantic 把嵌套泛型实例化成了独立 schema**，OpenAPI 里前端能看到完整的、精确的结构。这是 A 的最大优势：**文档不撒谎**。

代价：**6 个接口要写 6 次 `ApiResponse[...]`**，而且 handler 的返回类型得从 `KBOut` 改成 `dict` 或 `ApiResponse[KBOut]`（myPy 那里会变松）。

**做法 B：自定义 `APIRoute` 类，全局自动套壳**

```python
class EnvelopeRoute(APIRoute):
    def get_route_handler(self):
        original = super().get_route_handler()
        async def wrapper(request):
            response = await original(request)
            ...把 body 解出来塞进 data...
        return wrapper
```

好处：一处定义，全站生效。代价：**要自己处理 StreamingResponse / 204 / FileResponse / 错误响应**，每漏一种就是一种"某个接口突然坏了"。**未实测**，但 D2 的经验告诉你：包装层越大，绕过它的东西越多。

**做法 C：中间件包 body**

最"全局"，但代价最重：① 整个响应体进内存（D2 已经踩过）；② `StreamingResponse` 的流会被吃掉（SSE 直接废）；③ OpenAPI 完全失真（文档还是裸形状，实际返回有壳）。**不推荐**，写在这里是为了让你在面试里能说出"为什么不用中间件"。

**结论：选 A。** 显式写 6 次换来"文档不撒谎 + 工具链全部正常"，这是笔划算的账。B 留作以后团队化时的进阶。

**两个必须知道的边界（实测）**：

**边界一：204 和任何 `response_model` 互斥，而且是在注册时就炸**：

```python
@r.delete("/bad204", status_code=204)
def bad() -> dict:            # 返回注解不是 None
    return {"msg": "我不该有 body"}
```

实测直接抛（**进程启动阶段**，不是请求时）：

```
AssertionError: Status code 204 must not have a response body
```

而且两种"想套壳"的写法**都崩**（实测）：

```
[1] 204 + response_model=ApiResponse[None] + -> None   -> 崩
[2] 204 + -> ApiResponse[None]                          -> 崩
```

所以结论很硬：**DELETE 想套 envelope 就不能用 204**。两个选择——① 保持 204 无 body，前端按"成功 = 2xx 且无 body"处理；② 改成 200 + `ApiResponse[None]`（`data: null`），全站形状统一。
**这是 envelope 方案在 DELETE 上的真实摩擦点**，面试里说出来很加分（大多数人只会背"204 无 body"，不知道它会和统一响应体正面冲突）。

**边界二：`StreamingResponse` 绕过 `response_model`**（实测）：

```python
@r.get("/sse", response_model=ApiResponse[Any])
def sse():
    return StreamingResponse(gen(), media_type="text/event-stream")
```

```
[SSE 套 envelope] -> 200 'data: hi\n\n'      ← 原样透传，没被套壳，也没报错
```

原因：FastAPI 的 `response_model` 校验只作用于"普通返回值"（dict / BaseModel）；**返回值本身是 `Response` 子类时直接透传**。所以你的 `/chat` 流式接口天然免疫 envelope——这既是好事（SSE 不会被破坏），也是隐患（**同一个接口的流式和非流式两条分支，返回形状不一样**，前端要写两套）。你项目 `chat.py` 里 `response_model=None` 就是在明确这件事。

### 3.8 分页规范：页码还是游标

**两套主流方案**：

| | offset/limit（页码） | keyset/cursor（游标） |
|---|---|---|
| 入参 | `?page=2&size=20` / `?offset=20&limit=20` | `?cursor=<上一页最后一条的 id>` |
| 实现 | `LIMIT 20 OFFSET 20` | `WHERE id > :cursor LIMIT 20` |
| 优点 | 能跳页、能算总页数、实现简单 | 深翻页不退化、数据变动时不错行 |
| 缺点 | **深翻页退化**（OFFSET 100000 要扫 10 万行）、数据插入/删除会串行 | 不能跳页、必须有稳定排序键 |

**你的阶段选页码**，理由：数据量小、前端要"第 3 页 / 共 12 页"、实现直观。但要知道游标分页的存在和它解决什么——这是 W8 换 MySQL 时会真实撞上性能墙的地方（`LIMIT 100000, 20` 是经典的慢查询）。

**`total` 从哪来，是分页最容易做假的地方**：

你现在是内存实现，`total = len(rows)`（一次性拿到全部再切）。真上 DB 后有三种做法：

1. **两次查询**：`SELECT COUNT(*)` + `SELECT ... LIMIT`。简单，但 COUNT 在大表上很贵（尤其是带 JOIN 和 WHERE 时）。
2. **窗口函数**：`COUNT(*) OVER() AS total` 跟数据一起返回。一次查询，但每行都带一个重复的 total。
3. **不算 total**：只给 `has_more`。前端不显示总页数，只给"下一页"按钮（Twitter 就是这么干的）。

**面试里能加分的说法**：`total` 不是免费的，它是一条独立的查询成本；列表页如果要扛量，第一刀砍的就是"精确 total"。

### 3.9 分页参数的实测边界（你项目的真实行为）

```
[分页] page=1 size=2 -> {'items': 2, 'total': 3, 'page': 1, 'size': 2}
[越界] page=99 size=2 -> {'items': 0, 'total': 3, 'page': 99, 'size': 2}
[size 超限] -> 422 less_than_equal ['query', 'size']
[page=0] -> 422 greater_than_equal
```

四条结论：

1. **越界不报错**，返回空列表 + 真实 total。这是对的（空页是合法结果），前端据此显示"没有更多"。
2. **`le=100` 真的拦得住**，而且报错 `loc = ['query', 'size']`——**定位精确到哪个 query 参数**，这正是 D2 修的 `jsonable_encoder` 在起作用（detail 里带上了 `ctx`）。
3. **`ge=1` 挡住 page=0**。不挡的话，`offset = (0-1)*20 = -20`，内存实现里 `rows[-20:]` 会**返回最后 20 条**——一个看着成功、数据完全错的响应。这就是"参数校验是业务正确性的一部分"，不是"防御式编程"。
4. **参数校验发生在请求时②**，不在注册时。所以这四条边界是"每次请求都在算"的，不是启动时算一次。

### 3.10 OpenAPI：文档是路由表的副产品

```
GET /openapi.json  →  一张 JSON，描述了你所有路径、参数、响应 schema
GET /docs          →  Swagger UI，读的就是上面那张 JSON
```

**它不是写出来的，是注册时从路由表 + 类型注解生成出来的。** 这有两个实践后果：

1. **注解写错 = 文档撒谎**，而且不会报错。你写 `-> DocOut` 却 `return None`，`/docs` 里照样写着返回 DocOut。D3 学的 `response_model` 就是"让文档和现实对上"的机制。
2. **改路由必须对比 `/openapi.json`**，不能只看某个接口通不通。上一节那句"先把七行路径抄到纸上"，说的就是这个。

## 四、底层机制：`include_router` 到底做了什么

读一下它做的事（伪代码，核心逻辑来自 `fastapi/routing.py`）：

```python
def include_router(self, router, *, prefix="", tags=None, dependencies=None, ...):
    for route in router.routes:                       # ① 遍历子 router 里攒的 route
        new_path = prefix + route.path                # ② 纯字符串拼接
        self.add_api_route(
            new_path,
            route.endpoint,                           # ③ 复用同一个函数对象
            dependencies=[*(dependencies or []), *route.dependencies],   # ④ 依赖**合并**（父 + 子）
            tags=[*(tags or []), *route.tags],        # ⑤ tags 也是合并，不是覆盖
            ...
        )
```

四件事值得记：

1. **路径是纯字符串加法**，没有 `os.path.join` 那种智能处理——所以 `""`、`"/"`、重复前缀都不会帮你纠错。
2. **依赖是"父 + 子"合并**，不是覆盖。所以路由级鉴权 + 函数级 `Depends` 会**同时生效**，两层都在。
   与 D1 的请求级缓存结合时有个反直觉的细节（本项目实测四种组合 + 源码确认）：

   | 场景 | 执行次数 |
   |---|---|
   | 函数级 `Depends(dep)` + `Depends(dep, use_cache=False)` | **2** |
   | 两处都 `use_cache=False` | **2** |
   | 路由级 `use_cache=False` + 函数级默认 | **1** |
   | 路由级默认 + 函数级 `use_cache=False` | **2** |

   机制（`fastapi/dependencies/utils.py:656-680`）：读缓存前有一道 `if sub_dependant.use_cache and key in cache`，但**写缓存是无条件的** `if key not in dependency_cache: dependency_cache[key] = solved`。
   所以 **`use_cache=False` 只关"读"，不关"写"**；而执行顺序是**路由级在前、函数级在后**。
   推论：路由级写了 `use_cache=False` 反而无害（它先跑、不读、照样写，后面的人读到）；**真正会重复执行的是把 `use_cache=False` 写在函数级**——前面已经有人写进缓存了，它偏不读，于是又跑一遍。

3. **`route.endpoint` 是同一个函数对象**，所以 `dependency_overrides` 依然按函数对象匹配（D1 的结论在嵌套 router 下不变）。
4. **顺序保留**：子 router 内 route 的相对顺序，就是最终匹配顺序。所以"静态在参数前"的规则，在每一层 router 内部都要遵守——**父层写了静态路由，子层有参数路由，父层先注册就父层赢**。

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 前缀重复拼 | 路径变成 `/api/v1/kbs/kbs`，请求 404 | router 自带 prefix 就别在 `include_router` 里再写一段 |

| 3 | 参数路由写在静态路由之前 | 静态路径被参数吃掉 → 422（`loc: path, type: uuid_parsing`） | 静态在前；或静态段加语义前缀 |
| 4 | 用 `app.routes` 核对路径 | FastAPI 0.150 里只有一个 `_IncludedRouter`，看不到真实路径 | 用 `app.openapi()["paths"]` |
| 5 | 忘了给新接口加 `Depends(get_current_user_id)` | 接口裸奔，**零报错** | 路由级 `dependencies=[...]`；`health` 单独放外面 |
| 6 | 给 `status_code=204` 的接口写了返回注解或 `response_model` | **启动即崩**：`AssertionError: Status code 204 must not have a response body` | 204 就 `-> None` 且不写 `response_model`；要 body 就改 200 + `ApiResponse[None]` |
| 7 | 以为 `response_model` 能包住 `StreamingResponse` | 流式接口原样透传，实际形状和文档不一致 | 流式单独声明 `response_model=None`，文档里注明 |
| 8 | 分页只有 `ge=1` 没有 `le` | 客户端 `size=100000` 一次打穿 | 必须有 `le`；上限值从下游成本倒推（D3 §三 那条思维） |
| 9 | `page=0` 没挡住 | `offset` 变负数，内存实现返回**最后几页**（看着成功、数据全错） | `ge=1`；DB 实现里 `OFFSET -20` 直接语法错 |
| 10 | 成功裸资源、失败包外壳 | 前端两套解析逻辑；SDK 生成器报 union 类型 | 成功和失败**同一套字段同一套类型** |
| 11 | 把 envelope 加在中间件里 | SSE 被吃、大响应全进内存、OpenAPI 撒谎 | 用 `response_model=ApiResponse[X]` 显式声明 |
| 12 | 版本前缀分居两处（`/api` 在 main、`/v1` 在 router） | 拼出 `/v1/api` 这种路径 | 前缀只在一处决定 |
| 13 | 以为 `use_cache=False` 是"这次强制重算" | 写在函数级时依赖跑两次（认证查两遍库）；写在路由级却只有一次 | `use_cache` **只关读不关写**：谁先跑谁写缓存。想在函数级强制重算，先想清楚前面有没有人已经写过缓存 |

### 6.1 `api/v1/router.py`（13 行，结构对，缺一层）

```python
api_router = APIRouter()
api_router.include_router(health.router, tags=["health"])
api_router.include_router(knowledge_bases.router, prefix="/kbs", tags=["knowledge-bases"])
```

三个观察：

1. **`documents` 的 prefix 是 `/kbs`，它内部路径写 `/{kb_id}/documents`** —— 两层含义叠在一起：URL 上是"知识库下的文档"，代码上是"独立模块挂了个公共前缀"。这是合理的，但要在注释里写清，否则新人会以为 `documents` 是 `/documents` 开头的。
2. **`health` 也在 `api_router` 里**，所以它也吃 `/api/v1` 前缀，但它**没有鉴权**——因为鉴权是每个函数自己写的。**这就是 §3.5 要改的：一旦你给 router 挂路由级鉴权，`health` 必须搬出去**，否则健康检查也要 token（K8s 探针会直接挂）。
3. **没有 `tags_metadata`**：`/docs` 里四个分组只有名字没有描述。D5 补。

### 6.2 `main.py`

```python
app.include_router(api_router, prefix="/api/v1")     # ← 版本前缀在这里（做法 A）
```

改成做法 B（版本进 router）的理由在 §3.6。注意改的时候 `documents`/`knowledge_bases` 的 `/kbs` 前缀**不要动**——那是"资源分组"，不是版本。

### 6.3 `schemas/kb.py` 的 `Page`

```python
class Page(BaseModel, Generic[T]):
    items: list[T]
    total: int
    page: int
    size: int
```

已经能用（`Page[KBOut]`、`Page[DocOut]` 两个实例，schema 名 `Page_KBOut_` / `Page_DocOut_`），说明**泛型 schema 这条路你已经走通了**。D4 只是把它套进 envelope，再抽一个 `PageParams` 依赖。

### 6.4 分页参数：现在是两处复制

`knowledge_bases.py` 和 `documents.py` 各写了一遍：

```python
page: int = Query(default=1, ge=1),
size: int = Query(default=20, ge=1, le=100),
```

两份复制 = 将来改上限要改两处（漏一处的经典现场）。标准做法是抽成依赖类：

```python
class PageParams:
    def __init__(self, page: int = Query(1, ge=1), size: int = Query(20, ge=1, le=100)):
        self.page, self.size = page, size
        self.offset = (page - 1) * size
```

`params: PageParams = Depends()`——**注意 `offset` 在依赖里算，这是 D1 "依赖能做计算"的直接应用**，也是把"分页语义"从路由层收进一处的正确位置。

### 30 秒版（≤3 句，不许带证据）

**"你的接口怎么分组的？"**

### 追问一层（机制）

**"路由匹配是怎么做的？我两个路径都能匹配同一个 URL，谁赢？"**
> 按**注册顺序**线性试，第一个正则匹配赢，不看"哪条更具体"。所以 `/{kb_id}` 写在 `/stats` 前面，请求 `/stats` 会进参数路由，然后在 UUID 转换时 422。`{kb_id}` 的正则是 `[^/]+`，能匹配 `stats` 这个字符串。

**"前端要一套固定的响应结构，你怎么做？"**
> `response_model=ApiResponse[T]`，泛型实例化后 OpenAPI 里是独立 schema（`ApiResponse_KBOut_`），文档精确。**不用中间件包**：SSE 会被吃、大响应进内存、文档失真。还要注意 204 不能有 body（注册时就断言失败），流式接口返回 `Response` 子类会绕过 `response_model`。

### 追问二层（边界/故障）

按"故障发生在注册时 / 请求时"这条轴排：

1. **注册时**：`include_router` 前缀重复拼，路径变 `/api/v1/kbs/kbs`，**零警告**；`status_code=204` 配非 None 返回注解，**启动直接 AssertionError**。
2. **请求时匹配**：静态路由被参数路由吃掉 → 422，而不是 404（比 404 更迷惑，日志里看着像"参数类型错"）。
3. **请求时响应**：`response_model` 与实际不符 → 类型不符是 500（`ResponseValidationError`）；多返回字段被静默丢掉（D3 结论仍有效）。
4. **数据量边界**：深翻页 `OFFSET 100000` 退化；`total` 是独立查询成本；游标分页解决什么、代价是什么（不能跳页）。

### 追问三层（场景设计）

> **"你接手一个 40 个接口的老项目，接口响应形状三套混用（有的裸、有的 `{data}`、有的 `{result}`）。你怎么统一，怎么保证不漏、不破坏老客户端？"**

这题没有标准答案，答题形状应该是：**清点 → 兼容层 → 分批迁移 → 用文档/测试卡住回归**。

一个可用的骨架（示范形状，不是唯一答案）：

1. **清点**：把所有路径和响应 schema 从 `/openapi.json` 拉出来，按形状分类，列出"裸响应"清单——**这一步不能靠人去读代码**，读代码一定有漏。
2. **兼容层**：新形状只对新路径（或 v2）生效；老路径保持不动，双跑一段时间。
3. **渐进迁移**：按调用量从小到大迁，每次迁完观察前端错误率；提供 SDK 版本号让客户端主动升级。
4. **卡住回归**：加一个契约测试——遍历 `openapi.json` 里所有路径，断言响应都符合统一 schema。**这是"怎么证明不漏"的答案**，比"我一个个改"高一个层级。

**判别法**：这道题答完，别人能照着做、能验证 → 第三层；只能说"加个装饰器统一包一下" → 二层。

## 十一、闭卷自测

<details>
<summary>1. 三层 prefix 各是什么、按什么顺序拼？`""` 和 `"/"` 的区别？</summary>

`@router.get` 的相对路径 + router 自带 `prefix` + `include_router(prefix=...)` + app 层 `include_router(prefix=...)`，**从内到外拼**。
`""` = 不加段（`/api/v1/kbs/docs`）；`"/"` = 多一个尾斜杠（`/api/v1/kbs/docs/`），客户端不带尾斜杠会 307。
</details>

<details>
<summary>2. 为什么 `/kbs/stats/count` 不会被 `/kbs/{kb_id}` 吃掉？那什么情况会被吃掉？</summary>

`/{kb_id}` 只匹配一段（`[^/]+`），`stats/count` 是两段，段数不同不冲突。
会被吃掉的是**同段数**：`/{kb_id}` 在前、`/stats` 在后 → 请求 `/stats` 进参数路由 → UUID 转换失败 → **422**（不是 404）。
</details>

<details>
<summary>3. 为什么不能用 `app.routes` 核对真实路径？FastAPI 0.150 里它长什么样？</summary>

`include_router` 进来的整组 route 在 `app.routes` 里表现为一个 `_IncludedRouter`（惰性展开），`path` 是 `None`。
要看真实路径用 `app.openapi()["paths"]`。
</details>

<details>
<summary>4. 路由级 `dependencies` 有什么用？什么时候会害你？</summary>

好处：一次声明全组生效，不会漏（漏一个 = 裸奔且零报错）；OpenAPI 里每个 operation 自动带 `security`。
害你的情况：① `health` 也被保护，探针挂；② `use_cache=False` 写在**函数级**会和路由级的声明重复执行（写在路由级反而无害——`use_cache` 只关读不关写，见 §四 第 2 点）。
</details>

<details>
<summary>5. envelope 三种做法各自的代价？你会选哪个？</summary>

A 显式 `response_model=ApiResponse[X]`：文档精确、工具链正常；代价是每处写一遍。
B 自定义 `APIRoute`：全局自动；代价是 StreamingResponse / 204 / FileResponse 逐个特殊处理，漏一个坏一个。
C 中间件包 body：最全局；代价是流被吃、响应全进内存、OpenAPI 失真。**选 A。**
</details>

<details>
<summary>6. `status_code=204` 的两个坑分别是什么？</summary>

① `status_code=204` 配非 `None` 返回注解、或配任何 `response_model`（含 `ApiResponse[None]`）→ **启动时** `AssertionError: Status code 204 must not have a response body`（实测两种套壳写法都崩）。
② 想套 envelope 就没法 204（envelope 必须有 body）——DELETE 要么 204 无 body，要么 200 + `ApiResponse[None]`。
</details>

<details>
<summary>7. `page=0` 不挡住会发生什么？为什么说比报错更糟？</summary>

`offset = (page-1)*size = -20`；内存实现 `rows[-20:]` 会返回**最后 20 条**——响应 200、结构正常、数据完全错。这种"看起来成功"的错，比 422 难查十倍。
DB 实现里 `OFFSET -20` 直接语法错，所以内存实现是**更危险的那一版**。
</details>

<details>
<summary>8. `total` 有哪三种来源？为什么说它不是免费的？</summary>

① 两次查询（`COUNT(*)` + `LIMIT`）② 窗口函数 `COUNT(*) OVER()` ③ 不算 total，只给 `has_more`。
因为它是一条**独立的查询成本**，带 JOIN/WHERE 的 COUNT 在大表上很贵；扛量时第一个被砍的就是精确 total。
</details>
