# W6-D6 教材 · 反脆弱验收：注入 5 类错误，看门禁抓不抓得住

> 适用：已经能写 FastAPI 项目、门禁（ruff + mypy + pytest + 覆盖率）全绿的人。
> 本文只讲一件事：**你的测试门禁，究竟能抓住几种破坏？**
> 全部结论本机实测（FastAPI 0.150.0 / Pydantic 2.14.1 / Python 3.11 / pytest 8.x）。

---

## 零、主线：一个 bug 的四道门

先看这张图，它是全篇唯一的一根轴。**一个 bug 从被写进代码到被抓住，中间只有四道门**：

```
写进代码
   │
   ├─① 启动门：import / 装饰器注册 / 建依赖树
   │     ↑ 过不去 = 服务根本起不来（有声：ImportError / RecursionError）
   │
   ├─② 请求门：请求进来，参数校验 → 依赖执行 → handler → response_model
   │     ↑ 过不去 = 500 / 422（有声），或者……悄悄返回一个错的东西（无声）
   │
   ├─③ 测试门：pytest 把 ② 的某些路径提前跑一遍
   │     ↑ 过不去 = 变红（有声）；过不去但没测到 = 全绿（假安全）
   │
   └─④ 上线门：日志 / 监控 / 用户投诉
         ↑ 前两道门都漏了，才轮到它
```

今天要注入的 5 类错误，全部沿这根轴落位。先看它们各自死在哪（本节所有结论都是探针 `D6-探针-五类注入.py` 跑出来的）：

| # | 注入的错误 | 死在哪道门 | 有没有"声音" |
|---|---|---|---|
| 1 | 依赖循环 | **① 启动门** | 有声：`RecursionError`（注册路由时就炸） |
| 2 | 缓存误用 | ② 请求门 | **无声**：值错了但 200 返回 |
| 3 | middleware 顺序 | ② 请求门 | **无声**：响应正常，日志/trace_id 悄悄丢 |
| 4 | response_model 撒谎（类型/缺字段） | ② 请求门 | 有声：500 |
| 4′ | response_model 撒谎（多字段） | ② 请求门 | **无声**：字段静默消失 |
| 5 | 校验放宽 | ② 请求门 | **无声**：越界请求 200 放行 |

**一句话记住主线**：5 类里只有 1 类会被启动门拦住；剩下 4 类全在请求门，而且**3 类半是无声的**——它们唯一的猎手是测试门。所以 D6 真正在问的是：**你的测试门，对无声的 bug 有反应吗？**

这就是"反脆弱验收"：不是证明代码对，而是证明**门禁会响**。

## 一、痛点：门禁全绿给你的假安全感

假设你的考试是"门禁全绿才能提交"。现在有两种世界：

- **世界 A**：代码是对的，测试也真的在测 → 全绿有意义。
- **世界 B**：代码有 bug，但测试没覆盖到那条路径 → **一样全绿**。

从你的屏幕上，A 和 B 长得一模一样。这就是痛点：**"全绿"只证明"没测出问题"，不证明"能测出问题"。**

生活类比：机场安检门没响 ≠ 没有违禁品，也可能是**安检门坏了**。要验证安检门本身，你得主动拿一件测试用的金属制品走过去——它必须响。

软件里的这个动作叫**变异测试（mutation testing）**：故意往代码里注入一个 bug（变异体），跑测试；测试必须变红（"杀死"变异体）。没变红 = 测试在这条路径上是瞎的。

> 工业界工具有 `mutmut`、`cosmic-ray`，全自动。今天用手工版——因为你手工注入时**知道自己在破坏什么**，比工具生成的随机变异学得多。

## 二、先看见它（10 分钟，在真项目上做一次）

不写新代码，直接在你的项目上做一次最小变异。

**第 1 步：确认现在是绿的**

```powershell
# Windows PowerShell，kb-service 目录
& .\.venv\Scripts\python.exe -m pytest -q
# 期望：65 passed
```

**第 2 步：注入变异**——把 `schemas/common.py` 里 `PageParams.size` 的上限删掉：

```python
# 改前
size: int = Field(default=20, ge=1, le=100)
# 改后（注意力：只删 le=100）
size: int = Field(default=20, ge=1)
```

**第 3 步：再跑测试**

```
FAILED tests/test_kb_api.py::test_list_kbs_size_over_limit - assert 200 == 422
FAILED tests/test_kb_api.py::test_list_docs_shares_page_params - assert 200 == 422
2 failed, 63 passed
```

**第 4 步：恢复**（把 `le=100` 加回去，再跑一次确认 65 passed）

### 从这次变异里读出三件事

1. **你的测试门是"有声"的**——至少对"约束丢失"这一类，它响了。
2. **抓住它的是哪两条测试？** 都是**边界测试**（`?size=500` 期望 422）。happy path 测试（`?page=1&size=10`）一条都没红——这类测试对"约束放宽"完全瞎。
3. **反过来想**：如果当时没写那两条边界测试，现在门禁依然全绿，bug 直接上线。**这正是下一节 5 类注入里要反复出现的情形。**

## 三、五类注入逐个拆

每一类按同一个骨架讲：**注入怎么做 → 实测现象 → 死在哪、有没有声音 → 为什么测试可能漏 → 补法**。

### 3.1 依赖循环（死在启动门，有声）

**注入**：让两个依赖互相 `Depends`。

本项目写不出这种环（模块级 def 的默认值在 def 时就求值了），探针用 `__defaults__` 硬造：

```python
def get_a(_x: str = "") -> str: return "a"
def get_b(_y: str = "") -> str: return "b"
get_a.__defaults__ = (Depends(get_b),)
get_b.__defaults__ = (Depends(get_a),)

@app.get("/cyc")           # ← 炸在这一行
def cyc(x: str = Depends(get_a)) -> dict: ...
```

**实测**：

```
① 定义依赖函数：没报错
② 创建 app：没报错
③ 注册路由：RecursionError
```

**死在哪、有没有声音**：**启动门，响亮**。FastAPI 0.150.0 在 `add_api_route` 里就把依赖树建好（`get_dependant` 递归展开子依赖），环会在注册阶段无限递归。服务连起来的机会都没有——这是最好的一类 bug：**错得越早越便宜**。

**真实项目里的两种形态**：

| 形态 | 症状 | 何时炸 |
|---|---|---|
| 依赖树成环（上面这种） | `RecursionError` | import 时 |
| **模块 import 环**（更常见）：`api/deps.py` import `services/kb.py`，`services/kb.py` 又 import `api/deps.py` | `ImportError: cannot import name 'X' from partially initialized module` | import 时 |

**为什么测试不会漏**：漏不了——pytest 连测试都收集不起来（collection error），门禁必红。

**补法**：
1. 依赖方向单向化：共享逻辑抽到第三层（`core/`），让 A → core ← B，而不是 A ↔ B。
2. 必须互相用时，把"另一个"作为**参数**传进来，而不是 import 它。
3. `Depends` 层面成环 → 说明职责划分错了，几乎总是该抽公共依赖。

### 3.2 缓存误用（死在请求门，无声）

**注入**：一段"应该拿最新值"的逻辑，被 `Depends` 的默认缓存吃掉。

```python
calls = {"n": 0}
def counter() -> int:
    calls["n"] += 1
    return calls["n"]

@app.get("/cached")
def cached(x: int = Depends(counter), y: int = Depends(counter)) -> dict:
    return {"x": x, "y": y, "calls": calls["n"]}

@app.get("/uncached")
def uncached(x: int = Depends(counter), y: int = Depends(counter, use_cache=False)) -> dict:
    return {"x": x, "y": y, "calls": calls["n"]}
```

**实测**：

```
同一依赖声明两次（默认缓存）： {'x': 1, 'y': 1, 'calls': 1}
第二处加 use_cache=False  ： {'x': 1, 'y': 2, 'calls': 2}
```

**死在哪、有没有声音**：请求门，**完全无声**。返回 200、形状全对，只是数据是旧的。

**为什么测试会漏**：你的断言几乎总是"字段值对不对""形状对不对"，**很少有人断言"这个依赖跑了几次"或"拿到的是最新数据"**。从响应上根本看不出缓存来自哪份。

**本项目实物**：`get_current_user_id` 被声明了两次——路由级 `dependencies=[Depends(get_current_user_id)]`（D4 任务 2）和端点参数 `user_id: UUID = Depends(get_current_user_id)`。这**不是**误用：它靠缓存保证一次请求只验一次 token，值也一致。**同一个机制，用对用错取决于"你要的是同一份值还是要新的一份"。**

**补法**：
- 需要新值 → `Depends(fn, use_cache=False)`（注意：只对当次声明生效，第一次仍可能命中别人写入缓存的实例，所以**关键路径干脆别复用同一个依赖**）。
- 缓存作用域要记死：**单次请求内**，请求结束即清（`request.scope["fastapi_astack"]` 那套随请求销毁）。跨请求的缓存是 Redis 的事，不是 `Depends` 的事。
- 测试补法：加"调用计数"断言——`calls["n"] == 2` 这种断言比响应字段更能抓这类 bug。

### 3.3 middleware 顺序（死在请求门，无声）

**注入**：交换 `app.add_middleware` 的调用顺序。

```python
app.middleware("http")(make_mw("A-先加"))
app.middleware("http")(make_mw("B-后加"))
```

**实测**：

```
加入顺序 A → B，实际执行顺序：
['B-后加-进入', 'A-先加-进入', 'A-先加-退出', 'B-后加-退出']
```

**规律**：**后加的包住先加的**（后加的在最外层）。请求从外往里进，响应从里往外出。

**死在哪、有没有声音**：请求门，**无声**。响应还是 200、body 全对；坏掉的是"横切面"——trace_id 记不上、耗时统计算错层、500 时日志缺字段。

**为什么测试会漏**：绝大多数测试只断言**响应体**（`r.json()`）。顺序错的后果全在**日志、响应头、埋点**里——测试根本没看那里。

**本项目实物**（D2 学过的链条）：

```
ServerErrorMiddleware（最外，不放行任何例外）
  └ ExceptionMiddleware（查表找 handler）
      └ 你的 TraceMiddleware
          └ 路由/handler
```

TraceMiddleware 必须在业务中间件外侧，才拿得到"从请求进入到响应出去"的完整时间。顺序反了 → `duration_ms` 只算到内层，或者 trace_id 在异常路径上变成 `-`。

**补法**：
1. 顺序问题要用**副作用断言**抓，不是 body 断言：`assert "X-Trace-Id" in r.headers`（项目里已有）、500 响应也断言带 trace_id。
2. 在注释里写死顺序理由（`# Trace 必须在最外层：要给 500 也加 header`），避免有人"顺手整理"。
3. 关键顺序可加一条冒烟测试：500 场景下断言 header 存在。

### 3.4 response_model 撒谎（三种面孔，两种有声一种无声）

**注入**：让 `response_model` 声明的形状和 handler 实际返回的不一致。三种撒法：

```python
class Out(BaseModel):
    id: int
    name: str

@router.get("/lie-type", response_model=Out)
def lie_type() -> dict:
    return {"id": "不是数字", "name": "x"}      # ① 类型不符

@router.get("/lie-missing", response_model=Out)
def lie_missing() -> dict:
    return {"id": 1}                            # ② 必填字段缺失

@router.get("/lie-extra", response_model=Out)
def lie_extra() -> dict:
    return {"id": 1, "name": "x", "secret": "关键字段"}   # ③ 多出字段
```

**实测**：

```
① 类型不符   → 500
② 字段缺失   → 500
③ 多余字段   → 200 {'id': 1, 'name': 'x'}   ← secret 静默消失
```

**死在哪、有没有声音**：①② 请求门有声（500，且 `loc` 第一项是 `("response",)`，一眼看出是出参错）；③ 请求门**无声**——这是最阴的一种。

**为什么 ③ 会被漏**：测试如果只断言"返回里有 id 和 name"，全绿；而真正给前端的那个 `secret` 字段已经没了。**D4 的教训反过来用**：`response_model` 是"只输出声明字段"，那么"少声明一个字段 = 静默数据丢失"，没有任何报错。

**本项目实物**：`create_kb`/`get_kb` 现在 `response_model=ApiResponse[KBOut]`。哪天有人给 `KBOut` 加字段忘了同步、或者端点里返回了 `doc_count` 却在 `KBOut` 里删了它——③ 类事故，测试全绿，前端报"字段 undefined"。

**补法**：
1. 契约测试：关键字段必须在断言里出现（`assert "doc_count" in r.json()["data"]`）。
2. 更狠的：用 `response_model` 的 `model_config = ConfigDict(extra="forbid")`？——不行，那不作用于序列化过滤。真正的办法是**让 handler 的返回类型注解和 response_model 一致**，mypy 才会报"你少了字段"。
3. 冒烟：对每个端点断言响应 schema 与 OpenAPI 文档一致（D5 的 JSON 是机器可读的，可以自动比对键集合）。

### 3.5 校验放宽（死在请求门，无声）

**注入**：把某个约束"顺手放宽"——删 `le=100`、把 `min_length=1` 改成 0、去掉 `AfterValidator`。

**实测**（探针 §5，独立 app）：

```
    ?size=50 → 200
   ?size=500 → 200      ← 本该 422
?size=100000 → 200      ← 全放行
```

**死在哪、有没有声音**：请求门，**无声**。所有越界请求都正常返回，只是你的服务开始被大 size 拖垮（本项目 `size` 会直接变成 SQL `LIMIT`）。

**为什么测试会漏**：happy path 测试（`?page=1&size=10`）永远绿。只有**刚好越界**的测试能抓——这就是 §二 那次真项目变异里红掉的两条。

**补法**：**边界值分析法**——每个约束至少配 4 条：`min-1`（应 422）、`min`（应通过）、`max`（应通过）、`max+1`（应 422）。缺任何一条，这个约束就是"可以被静默删掉"的。

**本项目实物**：`PageParams` 的 `ge=1, le=100` 现在有 `test_list_kbs_size_over_limit` 和 `test_list_docs_shares_page_params` 两条边界测试兜着——今天实测能抓住。但 `KBCreate.name` 的 `min_length/max_length`、`DocCreate.content` 的 5000 上限有没有对应边界测试？**去查**——这就是今天任务的一部分。

## 四、机制：为什么有的炸启动、有的炸请求、有的干脆不响

### 4.1 启动门能覆盖什么

| 检查项 | 触发时机 | 典型报错 |
|---|---|---|
| 语法 / import | import 时 | `SyntaxError` / `ImportError`（含 **import 环**） |
| 依赖树构建 | 装饰器注册时 | `RecursionError`（**依赖环**） |
| 路由冲突 / 路径参数类型 | 注册时 | `FastAPIError` |
| `204` + `response_model` 互斥 | 注册时 | `AssertionError`（D4 踩过） |
| 全局依赖是否可解析 | 注册时 | 类型/签名错误 |

**规律**：凡是"声明期"的信息（装饰器参数、注解、依赖图结构），FastAPI 在注册时就检查；所以**结构性错误炸得早**。

### 4.2 请求门能覆盖什么

| 阶段 | 出问题 → 表现 |
|---|---|
| 参数校验（Pydantic） | 422（有声） |
| 依赖执行 | 抛 `AppError` → handler 装壳（有声）；**返回了错的值 → 无声** |
| handler 逻辑 | 未捕获异常 → 500（有声）；**算错了 → 无声** |
| response_model 校验 | 类型/缺失 → 500（有声）；**多字段 → 静默丢弃** |

**规律**：请求门只对"契约被违反"发声。**契约本身写错了（约束放宽、缓存语义错、顺序错），它一声不吭**——因为没有契约去对照它。

### 4.3 测试门的本质

测试门不是独立的门，它是**把请求门的某些路径提前走一遍**。所以：

> **测试的覆盖率 = 请求门被验证过的比例。**
> 没被测试走到的路径，请求门等于不存在。

这也解释了为什么"覆盖率 100%"不能替代变异测试：覆盖率只统计**某行代码被执行过**，不统计**执行结果被断言过**。一条 `assert True` 也能把覆盖率刷上去。

### 4.4 三类可观测信号 → 哪道门看得见

| 信号 | 启动门 | 请求门 | 测试门 | 上线门 |
|---|---|---|---|---|
| 抛异常（RecursionError/500） | ✅ | ✅ | ✅（若覆盖） | ✅（日志） |
| 状态码不对（200 vs 422） | — | — | ✅（若断言） | ✅（监控） |
| 副作用不对（字段消失/顺序/调用次数） | — | ❌ | ✅（若断言） | ✅（日志/投诉） |

第三行就是今天 5 类注入的主战场。

## 五、易错点表

| 坑 | 症状 | 正解 |
|---|---|---|
| 把"全绿"当"正确" | 变异测试一跑，一半注入都没红 | 全绿只证明"没测出问题"；要主动注入验证测试门 |
| 只测 happy path | 约束被放宽、字段被丢，测试全绿 | 每个约束配 4 条边界（min-1/min/max/max+1） |
| 断言只看 body | middleware 顺序错、trace_id 丢了无人知 | 副作用要单独断言（header/日志/调用计数） |
| 以为覆盖率 100% 就安全 | 断言写空、路径跑到但没断言 | 覆盖率≠断言质量；变异测试才测"抓得住吗" |
| 恢复变异时漏改回 | 变异代码混进提交 | 变异前后各跑一次绿；`git diff` 确认恢复干净 |
| 依赖成环想靠"调顺序"解决 | 越调越乱 | 依赖方向单向化，共享逻辑抽 core/ |
| 缓存误用去调 `use_cache` 硬顶 | 第一处仍命中旧值 | 关键路径别复用同一依赖；跨请求缓存用 Redis |

## 八、面试问法（30 秒 + 追问链）

**30 秒版**：
> "怎么验证测试有效？我会做变异测试——故意注入 bug，看测试会不会红。项目里我手工注入过 5 类：依赖循环、缓存误用、middleware 顺序、response_model 撒谎、校验放宽。结论是依赖循环在启动时就崩，其余 4 类都在请求时，而且大部分是静默的——只能靠测试门抓。所以我给每类补了对应的断言：约束配边界值、副作用配 header/日志断言、调用次数单独断言。"

**追问一层（机制）**：
> "为什么有些错误启动就崩、有些请求才崩？"——"FastAPI 在**装饰器注册**阶段就构建依赖树（`add_api_route` → `get_dependant`），所以结构性错误（依赖环、204+response_model 互斥、路由冲突）在那时就炸；而参数校验、依赖执行、response_model 校验都在**请求生命周期**里，只能等请求进来。契约本身写错了（约束放宽、缓存语义、顺序）连请求门都不响，因为没有契约对照它。"

**追问二层（边界/故障）**：
> "覆盖率 100% 能保证测试有效吗？"——"不能。覆盖率统计的是**行被执行过**，不统计**结果被断言过**。`assert True` 也能刷满覆盖。变异测试才直接测'抓不抓得住'。不过变异测试成本高（变异体数量 × 测试时长），实践上是**按模块抽样**跑，核心路径（鉴权/事务/金额）优先。"

**追问三层（场景落地）**：
> "CI 里怎么落地？"——"三道防线：① 关键约束的边界测试（成本最低、收益最大）；② 每次改核心模块后手工做一次变异抽查（就是今天这套）；③ 用 `mutmut`/`cosmic-ray` 在夜间任务里跑全量变异，看'存活率'。存活率高说明测试网有洞，不是代码有 bug。"

## 九、闭卷自测（先答再看）

<details>
<summary>1. 5 类注入里，哪一类死在启动门？为什么它能被启动门抓住？</summary>

依赖循环。因为 FastAPI 在**路由注册时**就构建依赖树（`add_api_route` → `get_dependant` 递归展开子依赖），环会在注册阶段无限递归 → `RecursionError`。（实测：定义函数不报、创建 app 不报、注册路由时报。）
</details>

<details>
<summary>2. "缓存误用"注入后，为什么请求返回 200、测试还全绿？</summary>

因为坏的不是形状而是**值的来源**：依赖只执行了一次（默认 `use_cache=True`），第二处声明拿到的是第一次的旧值。测试通常只断言字段形状/取值，不断言"依赖调用了几次"或"拿到的是不是新数据"，所以看不出。补法：加调用计数断言，或需要新值时 `use_cache=False`（且关键路径干脆别复用）。
</details>

<details>
<summary>3. middleware 顺序错了，为什么断言 body 的测试抓不到？该断言什么？</summary>

顺序影响的是横切面副作用（trace_id、耗时统计、500 时日志字段），响应体和状态码都正常。所以断言 `r.json()` 没用，要断言 `r.headers`（如 `X-Trace-Id`）、500 场景下的 header/日志、以及依赖调用次数这类副作用。
</details>

<details>
<summary>4. response_model 的三种"撒谎"，哪种最危险、为什么？</summary>

多字段（返回了模型没声明的字段）——静默丢弃，200 正常返回。类型不符和必填缺失都会 500（有声）；多字段没有任何报错，只有断言"这个字段应该在"才抓得到。本项目场景：`KBOut` 少声明一个字段 → 前端拿到 undefined。
</details>

<details>
<summary>5. 为什么"覆盖率 100%"不等于"测试有效"？</summary>

覆盖率只统计行被执行，不统计结果被断言。`assert True`、只跑不断言、断言别的东西都能把覆盖率刷满。变异测试才直接回答"注入 bug 后测试会不会红"。
</details>

<details>
<summary>6. 今天 5 类注入里，预期哪一类在你的项目上"不会红"？为什么？</summary>

（这是给今天任务留的开放题，实测后自己填。）提示：项目里已有 `PageParams` 的两条边界测试，所以"校验放宽"很可能红；而 `KBOut` 多声明/少声明字段、依赖调用次数，大概率没有任何断言。
</details>
