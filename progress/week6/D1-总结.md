## 二、逐个知识点讲透

### 1. 依赖注入的本质：依赖变成**数据** ★★★★★

**一句话定义**：把"我需要什么"从函数体里搬进函数签名，让它成为**可被框架遍历的声明**，而不是运行到那一行才知道的一串调用。

**为什么存在**（四个痛点，按你项目里的真实重量排）：

1. **测试换不动**。`list_kbs` 里直接 `decode_access_token(request.headers[...])`，W4 那套 conftest 只能覆盖 service 层，路由层打进来就是真鉴权，`test_rag_async.py` 里得手写 override 才能测。
2. **依赖不可见**。一个接口到底要不要登录、要几个资源，只能读完 20 行函数体才知道。
3. **副作用重复**。同一请求里三个地方各查一次当前用户，谁也不知道能合并。
4. **重复**（最弱的一条，也是最多人以为的"唯一理由"）。11 个路由写同一行鉴权——但注意：**重复是症状，不是病因**。病因是那 11 份是"逻辑复制"，改一处要改 11 处。

**怎么用**（项目真实代码，`api/v1/knowledge_bases.py` + `api/deps.py`）：

```python
async def get_current_user_id(
    credentials: HTTPAuthorizationCredentials | None = Depends(_bearer_scheme),
) -> UUID:
    if credentials is None:
        raise UnauthorizedError("缺少认证信息")
    claims = decode_access_token(credentials.credentials)
    return UUID(claims.sub)

@router.get("", summary="分页查询我的知识库")
async def list_kbs(
    page: int = Query(default=1, ge=1),
    size: int = Query(default=20, ge=1, le=100),
    user_id: UUID = Depends(get_current_user_id),     # ← 只有这一行是 DI
) -> Page[KBOut]:
    return KBService().list(user_id, page, size)
```

**底层机制**（分两个阶段，混淆这两个阶段是绝大多数误解的来源）：

```
注册期（@router.get 执行时，import 那一刻就跑完了）
  inspect 扫签名 → 默认值是 Depends 实例？→ 记成子依赖，递归
                → 默认值是 Query/Path？  → 记成"从请求取值"
  → 得到 Dependant 树，挂在 route.dependant 上，之后不再重建

请求期（每次请求）
  solve_dependencies(route.dependant) → 深度优先、后序执行 → 调 handler
```

**"搬进签名"之后为什么就自动有了三种能力**——因为依赖关系从"代码"变成了"数据"：

| 能力 | 为什么可能 |
|---|---|
| 画依赖树 | 树是 `Dependant` 对象组成的，可以遍历、可以打印、可以生成 OpenAPI |
| 请求级缓存 | 遍历到同一个节点，用它的**身份**去查表，命中就跳过 |
| 测试替换 | 遍历到节点时先查一张"替身表"，替换是查表，不是改代码 |

这就是你第一版答案缺的那一层：**不是"写清楚了大家就都懂了"，是它先变成了能遍历的数据结构**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 DI 说成"为了少写重复代码" | 面试官追一句"那一个只做一件事的函数为什么还需要 DI"就卡住 | 少写代码是副产品；本体是"依赖关系变成可遍历的数据" |
| 2 | 手动调用依赖函数 `dep_b()` | 依赖内部又调 `Depends`，手动调拿不到注入值 → `TypeError` | 依赖函数只由框架调用；要复用就写成 `Depends` 链 |
| 3 | 把 `Depends(x)` 当默认值理解 | 以为"不传参用自己的默认"，甚至以为 `Depends` 会立即执行 | 它是**声明标记**，注册期被读走，运行期永不出现 |
| 4 | 以为 DI 等于单一职责 | 说"DI 促进函数原子化"，被追一句就露 | 单一职责讲"一个函数只做一件事"，DI 讲"依赖从外面给"——正交 |
| 5 | 认为 DI 是框架魔法，不能解释 | 出问题只能猜 | 两个阶段两个文件：`routing.py` 建树、`dependencies/utils.py` 解析 |

**面试问法**：「FastAPI 的依赖注入解决了什么问题？」

30 秒版：三件事。一是把依赖从函数体搬到签名，于是依赖关系变成可遍历的树，框架能缓存、能替换、能生成文档；二是副作用可控——同一请求里同一个依赖只执行一次；三是测试时用 `dependency_overrides` 换节点，不用改业务代码。写起来少几行只是顺带的。

**追问链**：

→ *"依赖树是在什么时候建的？"*（机制层）注册期。`@router.get` 装饰执行时用 `inspect` 扫签名，把 `Depends` 实例、`Query`、`Path` 分类记成 `Dependant`，之后挂在 route 上不再重建。所以**改了依赖不重启不生效**——这也是为什么 Uvicorn 必须 `--reload`。

→ *"依赖里有 I/O，一个请求挂了 5 个依赖，会不会查 5 次库？"*（边界/故障层）不会，只要它们是同一个 callable。缓存 key 是依赖身份，第二次挂载直接命中。但**同一个函数 + 不同参数不会拆两条**——因为实参不进 key。要拿不同的值必须显式 `use_cache=False`，忘了就是越权漏洞（拿到自己的数据当别人的）。

→ *"AI 应用里这套东西有用吗？"*（场景落地层）最有用的一处是模型可替换：`get_llm() -> LLMClient` 挂成依赖，生产注入真 client、测试注入假返回，接口一行不改。第二处是降级：`get_llm` 内部按配置返回主模型或备用模型，业务代码只声明"我要一个能生成的东西"。第三处是成本记账：用 yield 依赖在 teardown 里累计本次请求的 token 数。

### 2. 请求级缓存 `dependency_cache` ★★★★★

**一句话定义**：FastAPI 在一次请求内维护一张 `{依赖身份: 解析结果}` 的表，同一个依赖无论被挂几处，只执行一次。

**为什么存在**：两个原因，性能只是次要的。

- **语义正确**：一次请求里"当前用户是谁"必须有唯一答案。如果 `get_current_user_id` 执行两次，中间 token 快过期，就可能出现"鉴权用 A、写库署 B"。
- **副作用不重复**：查库、写审计日志、开连接，重复执行都是 bug 而不是慢。

**怎么用**（默认开着，只在需要重算时关）：

```python
# 菱形依赖：dep_b 和 dep_c 都依赖 dep_a
@app.get("/nested")
def nested(b: str = Depends(dep_b), c: str = Depends(dep_c)) -> dict[str, str]:
    return {"b": b, "c": c}

# 实测调用顺序
# ['a', 'b', 'c']      ← a 只出现一次
```

**底层机制**（三段源码，行号是本机 0.150.0）：

```python
# utils.py:615-616 —— 缓存的生命周期由这一行决定
if dependency_cache is None:
    dependency_cache = {}          # 每次请求新建，随请求一起消失

# utils.py:660-661 —— 进入节点时先查表（不是执行完再查）
if sub_dependant.use_cache and sub_dependant_cache_key in dependency_cache:
    solved = dependency_cache[sub_dependant_cache_key]

# utils.py:679-680 —— 没命中才写，命中时不覆盖
if sub_dependant_cache_key not in dependency_cache:
    dependency_cache[sub_dependant_cache_key] = solved
```

key 是三元组（`types.py:12`）：

```python
DependencyCacheKey = tuple[Callable[..., Any] | None, tuple[str, ...], str]
#                   ① 依赖 callable 对象   ② oauth scopes    ③ scope 字符串
```

实测打印：

```
Depends(f)                    -> (<function f at 0x...>, (), '')
Depends(f, scope="function")  -> (<function f at 0x...>, (), 'function')
```

**三项里没有实参**——这是本日最重要的一条。后果链条：

```
实参不进 key
  → 同一个函数挂两处，即使"这次想取不同的人"，也只算一次
  → 想取不同的值，唯一开关是 use_cache=False
  → 忘了写 → 第二处拿到第一处的值 → 越权（不是性能问题）
```

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为缓存按"函数名"区分 | 说"用户和知识库各有一个 `get` 会串"——其实两个不同函数对象，key 第一项就不同，**不串** | key 装的是**对象**，不是名字；同名不同函数天然隔离，同函数不同参数才危险 |
| 2 | 以为缓存是全局的 | 用模块级变量模拟"请求内共享"，跨请求串数据、并发错乱 | `dependency_cache` 每次请求新建；请求内共享靠"依赖消费依赖" |
| 3 | 以为参数影响缓存 | 想用 `dep(x=1)` / `dep(x=2)` 拿两个值，结果只跑一次 | 换参数只能换 callable（`partial` 包一层），key 第一项才变 |
| 4 | 只记得"请求级"三个字 | 说不出为什么必须是请求级 | 因为"当前用户是谁"在一次请求里必须唯一；也是侧效应只该发生一次 |
| 5 | 混用 `lru_cache` 与 DI 缓存 | 以为 DI 缓存会跨请求加速，接口却还是慢 | 两者生命周期不同：`lru_cache` 进程级、DI 缓存请求级。跨请求要缓存得自己上 Redis |

**面试问法**：「FastAPI 的依赖缓存是什么范围？」

30 秒版：一次请求。`solve_dependencies` 里那个 dict 是每次请求新建的，请求结束就丢。所以它保证的是"一次请求里同一个依赖只执行一次"，不是性能优化。跨请求要用就得自己上 Redis，而且得想清楚 key 里放什么。

**追问链**：

→ *"缓存的 key 里有什么？"*（机制层）三元组：依赖的 callable 对象、OAuth scopes、scope（`function`/`request`/`""`）。**没有实参**——同一请求内同函数的实参必然相同，所以不需要。这也意味着"用参数区分"这条路走不通。

→ *"如果这个 dict 变成全局的会怎样？"*（边界/故障层）`get_current_user_id` 的 key 里没有 header，A 用户登录后 B 用户的请求直接命中 A 的凭证 → 越权。这是能写进故障报告的场面：一个用户的私有知识库出现在另一个用户的列表里。缓存范围的设计前提是"值只在请求内有效"。

→ *"RAG 接口里你会缓存什么、不会缓存什么？"*（场景落地层）不会缓存 LLM 的原始回答——同一问题两次答案不同是正常语义，缓存了就没法回归。会缓存的是 embedding：`get_embedder()` 挂成依赖、请求内复用，跨请求用 Redis 按 `(model, text_hash)` 缓存，因为它是纯函数、成本高、可重算无副作用。判据是"这个值重算一次会不会改变语义"。

### 3. yield 依赖的 teardown 时序与 `scope` ★★★★★

**一句话定义**：用生成器写依赖——`yield` 之前是 setup，`yield` 出去的值就是注入值，`yield` 之后是 teardown，由框架在适当时机继续执行。

**为什么存在**：有些依赖是"资源"不是"值"。数据库连接要关、临时文件要删、锁要放、事务要提交或回滚。没有 teardown，这些清理只能写在每个 handler 的 `finally` 里——那就是 11 个路由写 11 遍。

**怎么用**：

```python
def dep_yield() -> Iterator[str]:
    calls.append("setup")        # 解析阶段执行
    try:
        yield "resource"         # 注入这个值
    except Exception:            # handler 抛的异常会被送进这里
        calls.append("rollback")
        raise
    finally:
        calls.append("teardown") # 善后

# 要让 teardown 的失败影响状态码，必须显式声明：
Depends(dep, scope="function")
```

**底层机制**（时序图 + 两种 scope 的真实差异）：

```
默认 scope="request"
  请求进入 → [setup] → handler → 响应发出 → [teardown]
                                              ↑ 此时状态码已定死

scope="function"
  请求进入 → [setup] → handler 结束 → [teardown] → 响应发出
                                        ↑ 这时它抛异常 = 500
```

实测（同一个 dep，只在 handler 与 dep 里各埋一次 raise）：

| 场景 | 客户端收到 | 服务端 |
|---|---|---|
| handler 抛 `ValueError` | **500** | 异常被送进 yield 点，teardown 能 catch、能回滚 |
| teardown 自己抛，默认 scope | **200 + 完整响应体** | 异常只进日志 |
| teardown 自己抛，`scope="function"` | **500** | 正常错误响应 |

**这张表就是今天你最该背下来的东西**——因为它同时回答了两个方向的错：不是"teardown 一定 200"，也不是"teardown 出错一定 500"，而是**看 scope**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 说"teardown 在响应后执行"不带限定 | 面试官追"那 `scope="function"` 是什么时候"就断 | 限定词是"默认 `request` 下"；`function` 下在 handler 结束、响应发出**之前** |
| 2 | 以为 teardown 能改响应 | 在 yield 后面改 `response.status_code`，客户端完全看不到 | 响应已发出；teardown 只做清理 |
| 3 | 以为 teardown 出错会让请求失败 | 事务提交失败，接口照样返回 200，前端以为成功 | 默认 scope 下不可见；要可见必须 `scope="function"`（W7 提交必须这么写） |
| 4 | 反过来以为 setup 的异常会"传到 yield" | 写 `try/finally` 兜 setup 逻辑，永远进不去 | setup 抛异常根本走不到 `yield`，teardown 不执行 |
| 5 | 把 scope 说成"缓存周期" | 被追"那 `use_cache=False` 是改周期吗"就卡 | scope 管**teardown 时机**，与缓存无关；缓存固定一次请求 |
| 6 | 在 teardown 里做耗时操作 | 每个请求多出 200ms，且失败不影响状态码、没人发现 | teardown 只做清理；重活放 BackgroundTasks（D5 会讲） |

**面试问法**：「FastAPI 的 yield 依赖，如果 handler 抛异常了，yield 后面还执行吗？」

30 秒版：执行，而且异常会被送进 yield 点——你可以在 teardown 里 `except` 到它，做回滚。这跟 pytest 的 yield 夹具同源。但有个致命差异：默认 `scope="request"` 下 teardown 在响应发出后才跑，它自己抛异常客户端完全看不到，还是 200。要让提交失败变成 500，必须显式写 `scope="function"`。

**追问链**：

→ *"异常是怎么"送进" yield 点的？"*（机制层）框架用生成器的 `throw()` 把异常抛回 `yield` 那一行，所以你写在 `yield` 外的 `try/except` 能抓到。实测顺序是 `setup → caught:ValueError → teardown`。

→ *"teardown 里能发 HTTP 响应吗？"*（边界/故障层）不能。响应对象早就发出去了，改也不生效。而且 teardown 里再抛异常，在默认 scope 下只会污染日志——服务端看起来一切正常，客户端拿着 200 和半截数据走。

→ *"W7 写数据库事务，你会怎么设计？"*（场景落地层）`get_db_session` 用 yield 依赖：`yield session` 之前开，之后 `commit`，`except` 分支 `rollback`。并且挂载时写 `scope="function"`——因为提交失败必须让客户端知道，否则用户以为存成功了。这条是今天这几个概念唯一的真实落点，面试讲项目时可以直接说。

### 4. `dependency_overrides` 的 key 与静默失效 ★★★★☆

**一句话定义**：`app.dependency_overrides` 是一张 `{原依赖 callable: 替身 callable}` 的普通 dict，解析时按 key 查表，查到就用替身。

**为什么存在**：`TestClient` 打进来的是真实 HTTP 请求，路由内部的 `Depends(get_current_user_id)` 会真跑。要测"登录用户访问自己的库"，只有两条路：造一个真 JWT（脆、要管密钥和过期），或者把那个节点换掉。

**怎么用**（今天真正写进项目的东西）：

```python
# tests/conftest.py
@pytest.fixture
def override_current_user_id(app: FastAPI) -> Iterator[UUID]:
    """把 get_current_user_id 换成固定用户；结束只摘自己这条 override，不动其他。"""

    async def fake_user_id() -> UUID:
        return TEST_USER_ID

    app.dependency_overrides[get_current_user_id] = fake_user_id
    yield TEST_USER_ID                     # yield 的是"值"，不是替身函数
    app.dependency_overrides.pop(get_current_user_id, None)

# tests/test_rag_async.py —— 用例只声明依赖
async def test_chat_sse_via_async_client(
    app: FastAPI,
    override_current_user_id: UUID,
) -> None:
    ...
```

**底层机制**（两行源码 + 三条实测）：

```python
# applications.py:964 —— 就是个普通 dict
self.dependency_overrides: dict[Callable[..., Any], Callable[..., Any]] = {}

# dependencies/utils.py:625-631
original_call = sub_dependant.call
call = getattr(provider, "dependency_overrides", {}).get(original_call, original_call)
```

`.get(key, 默认值)`——查不到**返回原函数**，不抛异常。所以 key 写错永远不报错，只是永远不命中。**静默失效**这个词就是从这里来的。

命中之后还有一层（`utils.py:632-638`）：不是直接调替身，而是用替身重新 `get_dependant(call=替身)` 建一棵子树。三个实测后果：

| 你的写法 | 实测 | 为什么 |
|---|---|---|
| `Depends(partial(dep, uid=7))`，再 override `dep` | **不生效，且静默** | 注册时的 `call` 是那个 partial 对象，两个对象不相等 |
| `Depends(repo.get)`，override 时另取一次 `repo.get` | **生效** | bound method 按（实例 + 函数）比较相等，不按身份 |
| 替身写成 `lambda uid: ...` | 不带 `?uid=` 就 **422** | 替身签名被重新解析，`uid` 当成 query 参数 |

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | key 写成字符串 | 不报错、不生效，测试仍走真实依赖 → 断言莫名其妙失败 | key 必须是 callable 对象；查找是 `dict.get(original, original)` |
| 2 | 用 `clear()` 收尾 | 今天是绿的，明天加第二个 override 夹具就互相踩 | 只 `pop` 自己那一条：`pop(get_current_user_id, None)` |
| 3 | 以为 override 只换一个节点 | 期望 `dep_b`/`dep_c` 不变，实测 `b(FAKE)`/`c(FAKE)` 全变了 | 依赖是**数据流**：换节点的输入，下游输出自然跟着变 |
| 4 | 用 `partial` 或没 `wraps` 的装饰器包依赖，再 override 原函数 | 静默不生效，排查方向会被带偏 | 注册时的 `call` 已经是新对象；要 override 就打那个新对象 |
| 5 | 以为 override 会破坏缓存语义 | 担心替身在同一请求里被调多次 | 缓存 key 按**原依赖**算（`utils.py:656-657`），替身同样只跑一次 |

**面试问法**：「你项目里怎么测鉴权接口？」

30 秒版：不造 JWT，用 `dependency_overrides` 把 `get_current_user_id` 换成一个返回固定 UUID 的替身，做成 conftest 夹具，用例签名里只写 `override_current_user_id: UUID`，需要用户 id 就用夹具 yield 的值。收尾用 `pop` 不用 `clear`——`clear` 会踩掉别的夹具装的 override。

**追问链**：

→ *"override 的 key 必须是函数对象，为什么？"*（机制层）因为查找就是 `dict.get(sub_dependant.call, ...)`，`sub_dependant.call` 是注册时的那个 callable 对象。字符串 key 只是挂在 dict 里没人查——**不报错、不生效**，比报错更难查。

→ *"如果依赖被装饰器包了一层，会发生什么？"*（边界/故障层）两件事同时发生：override 原函数失效（`call` 已是 wrapper）；如果装饰器没写 `functools.wraps`，`wrapper(*a, **kw)` 的 `*a`/`**kw` 会被当成必填 query 参数，直接 422 `missing query a`。所以依赖上加装饰器，`wraps` 和"签名可解析"两件事都得管。

→ *"测 LLM 调用怎么用这套？"*（场景落地层）`get_llm()` 挂成依赖，测试里 override 成固定返回的假 client——这样 RAG 链路能离线跑、能断言 prompt 结构、不花钱。但要注意替身签名：假 client 如果写成 `async def fake(prompt)`，FastAPI 会想从 query 里取 `prompt` → 422。要么给它默认值，要么用真实 client 的接口签名。

### 5. 依赖树：节点、箭头、后序遍历 ★★★★☆

**一句话定义**：注册期把路由签名展开成一棵树，每个节点对应"一个参数"，箭头表示"我需要谁的返回值"，请求期深度优先、后序执行。

**为什么存在**：因为这是 1、2、4 三个能力的共同底座。看不懂树，就解释不了"为什么只跑一次"（同一个节点）、"为什么换了 a 会影响 b"（子树）、"为什么参数也是节点"（`page` 也在树上）。

**怎么用**（画你自己项目的真实树）：

```
list_kbs                                    ← 根：路由函数
├── page: Query(default=1)                  ← 从请求取值的节点（不是函数）
├── size: Query(default=20)
└── user_id: Depends(get_current_user_id)   ← 依赖节点
        └── credentials: Depends(_bearer_scheme)   ← HTTPBearer 实例，也是节点
```

三条读图规则（这是今天卡过的地方）：

1. **一个节点 = 路由函数的一个参数**。`page` 是节点，只是它不需要调用任何函数。
2. **箭头 = "我需要谁"**。方向是"用谁的值"，不是"谁先执行"。
3. **可调用对象就能当节点**。`_bearer_scheme` 是实例不是函数，但它实现了 `__call__`。

执行顺序（真实请求 `GET /api/v1/kbs?page=1&size=20` + Bearer token）：

| 步 | 框架做什么 | 值 |
|---|---|---|
| ① | 调 `_bearer_scheme(request)` | `HTTPAuthorizationCredentials(scheme="Bearer", credentials="eyJ...")` |
| ② | 把①当实参调 `get_current_user_id(credentials=...)` | `UUID('7f36...')` |
| ③ | 把②和 query 一起调 `list_kbs(page=1, size=20, user_id=UUID(...))` | `Page[KBOut]` |

**底层机制**：**进入是前序，执行是后序**。这一点今天说错过一次（说成"后续遍历"）：

```
solve_dependencies(list_kbs)          ← 进入（前序），先把节点登记进递归
  solve_dependencies(user_id 节点)
    solve_dependencies(credentials 节点)
      → 调用 _bearer_scheme()         ← 叶子先执行
    → 调用 get_current_user_id()      ← 子全解完，父才执行（后序）
  → 调用 list_kbs()                   ← 根最后
```

**为什么"只跑一次"能在这一步发生**：查缓存是在**进入节点时**做的，不是执行完之后。第二次挂载同一依赖时，子依赖递归都还没开始，就先命中缓存直接返回了。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把"前序/后序"说混 | 说"后续遍历"，被追"到底是进入还是执行"答不清 | 进入前序（DFS 进节点），执行后序（子全解完才执行父） |
| 2 | 把 `page: Query(...)` 排除在树外 | 画图时漏掉参数节点，后面理解"参数也是依赖"就断 | 每个参数都是节点，只分"从请求取值"和"调函数取值" |
| 3 | 以为箭头方向 = 执行顺序 | 画成 `get_current_user_id → list_kbs` 却解释成"前者先跑" | 箭头是"我需要谁"；执行顺序要用后序遍历推 |
| 4 | 以为 `_bearer_scheme` 只是内部工具 | 画树时把 `HTTPBearer()` 漏在图外（今天真实发生） | 被 `Depends` 包住的**一切可调用对象**都是节点 |
| 5 | 以为依赖树每次请求重建 | 担心性能 | 树在注册期建好挂在 route 上，请求期只是遍历 |

**面试问法**：「FastAPI 怎么知道一个参数是依赖还是普通参数？」

30 秒版：注册期扫签名看默认值。默认值是 `Depends` 实例 → 依赖节点，递归展开；是 `Query`/`Path`/`Body` → 从请求取值；是普通标量没有标记 → 当成 query 参数。树建好挂在 route 上，之后每个请求只遍历不重建。

**追问链**：

→ *"树上的执行顺序能说出来吗？"*（机制层）深度优先后序：叶子先执行，父节点拿子节点的值当实参。所以 `['a','b','c']` 里 `a` 在最前、handler 在最后。

→ *"依赖抛异常了，树会怎么走？"*（边界/故障层）立刻中断，异常沿调用栈上抛，被 `AppError` 处理器翻译。**已执行的依赖的 teardown 仍会跑**——这就是 yield 依赖能回滚的前提。但注意：这条链上"还没进入"的节点不会执行，也不会有 teardown。

→ *"依赖树能按路由前缀复用吗？"*（场景落地层）能，`APIRouter(dependencies=[Depends(require_admin)])` 会把依赖挂到该 router 所有路由的根上。但它是**新增一个根级依赖**，不是"爸爸节点"——树还是每路由一棵，只是共用同一个子树结构。

### 6. `auto_error=False` 换来了什么 ★★★★☆

**一句话定义**：`HTTPBearer` 的开关，决定"请求缺少 Authorization 头时，是框架替你抛 401，还是返回 `None` 让你自己决定"。

**为什么存在**：因为框架的默认响应体**不一定是你系统的契约**。项目所有业务错误都是 `{"code","message","detail"}`（`AppError` 统一格式），如果鉴权错误走框架默认，前端就要写两套解析、日志没法按 `code` 聚合、OpenAPI 里也描述不出这个结构。

**怎么用**：

```python
_bearer_scheme = HTTPBearer(scheme_name="Bearer Token", auto_error=False)

async def get_current_user_id(
    credentials: HTTPAuthorizationCredentials | None = Depends(_bearer_scheme),
) -> UUID:
    if credentials is None:                  # ← auto_error=False 才有这个分支
        raise UnauthorizedError("缺少认证信息")
    ...
```

**底层机制**（`fastapi/security/http.py` 的 `__call__`，核心就一处分支）：

```python
if not (authorization and scheme and credentials):
    if self.auto_error:
        raise self.make_not_authenticated_error()   # 默认
    else:
        return None                                 # 你选的
```

**本机实测（0.150.0，不带 header 打 `GET /api/v1/kbs`）**：

| | `auto_error=True` | `auto_error=False`（项目在用） |
|---|---|---|
| 头缺失时 | 抛 `HTTPException` | 返回 `None` |
| **实际状态码** | **401** | **401** |
| 响应体 | `{"detail": "Not authenticated"}` | `{"code":"UNAUTHORIZED","message":"缺少认证信息","detail":null}` |
| 谁的代码产生 | HTTPBearer 内部（框架） | 你的 `UnauthorizedError` + `AppError` 处理器 |

**两边的状态码都是 401**——很多老教程写 403，实测已经变了（`make_not_authenticated_error()` 现在抛 401 并带 `WWW-Authenticate` 头，符合 HTTP 语义：缺凭证是"未认证"不是"禁止访问"）。所以这个开关换来的**不是状态码，是响应体契约**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 `auto_error` 决定 401 还是 403 | 面试说"关掉就是从 403 变 401"，实测两值都是 401 | 差别在**响应体契约**和"谁来翻译异常" |
| 2 | 照抄老教程的状态码 | 文档写 403、实际 401，联调对不上 | 教程会过期，源码和实测不会；`make_not_authenticated_error` 是 401 |
| 3 | 忘了自己处理 `None` | 开了 `auto_error=False` 却没写 `if credentials is None`，后面 `credentials.credentials` 直接 `AttributeError` | 关掉框架报错 = 你必须自己报错，否则 500 |
| 4 | 以为 `auto_error=True` 更方便 | 少写 3 行，但错误格式分裂成两种 | 项目里统一 `AppError` 契约，宁多 3 行 |
| 5 | 改了 `auto_error` 没跑测试 | 响应体变成 `{"detail"}`，`assert code == "UNAUTHORIZED"` 的红正好该出现 | 这条断言就是它的作用，别改测试迁就实现 |

**面试问法**：「你为什么把 `HTTPBearer` 的 `auto_error` 关掉？」

30 秒版：为了统一错误响应体。开着的时候框架自己抛 401，响应体是 `{"detail": ...}`；关掉之后它返回 `None`，我自己抛业务异常，走统一处理器，响应体跟其他错误一样是 `{"code","message","detail"}`。状态码两边都是 401，换的是契约不是码。

**追问链**：

→ *"关掉之后少了什么保护？"*（机制层）少了"由框架保证一定报错"。现在如果忘了写 `if credentials is None`，后面的 `.credentials` 会 `AttributeError` → 500。类型注解写成 `| None` 加上 strict mypy 能拦住大部分。

→ *"401 和 403 到底怎么分？"*（边界/故障层）401 是"你没证明你是谁"（缺凭证、凭证过期、格式错），要带 `WWW-Authenticate` 头告诉客户端怎么认证；403 是"证明过了但没权限"（普通用户删别人的库）。这两个混淆在前端表现为"登录失效"和"无权限"提示错乱。

→ *"AI 应用里模型超时了，该返回什么？"*（场景落地层）不能 401/403，那是客户端问题；也不能裸 500 让前端无法区分。项目里应该是 `AppError` 的子类（比如 503 + `code=LLM_UNAVAILABLE`），前端才能"降级到检索结果、提示稍后重试"。这正是 W14 降级重试要落的地方——`auto_error=False` 的同一个姿势：**别让框架替你决定错误形态**。

### 7. 可调用对象当依赖（类 vs 实例） ★★★☆☆

**一句话定义**：FastAPI 对依赖的唯一要求是"可调用 + 参数可解析"，所以类、实例、函数、`functools.partial` 都能当依赖。

**为什么存在**：让"带配置的依赖"成为可能。`HTTPBearer(scheme_name=..., auto_error=False)` 把配置存在实例属性上，比给函数加一堆参数干净。

**怎么用**：

```python
class Auth:
    def __call__(self, request: Request) -> str: ...

Depends(Auth)      # 传类：每请求新建实例，无状态可共享
Depends(Auth())    # 传实例：实例状态跨请求共享
```

**底层机制**：`Depends(Auth)` 时框架调 `Auth()` 拿实例再调它，所以每请求一个新对象；但**同一请求内挂两处仍只建一次**——因为 cache key 第一项是 `Auth` 这个**类对象**，两处相同，命中缓存。

`Depends(Auth())` 的实例是模块级对象，属性在请求间共享。只读配置（`scheme_name`、`auto_error`）没问题；可变状态就是 §4.3 警告的全局可变状态，并发下会串。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 `Depends(Auth)` 和 `Depends(Auth())` 等价 | 并发下出现莫名数据串门 | 传类 = 每请求新建；传实例 = 状态共享 |
| 2 | 在实例属性里存请求级数据 | 两个用户看到彼此的 id | 请求级数据只能放 yield 依赖或 `request.state` |
| 3 | 以为传类会"每请求每挂载点各建一次" | 同类里初始化逻辑跑两次，日志对不上 | 同请求内按类对象命中缓存，只建一次 |
| 4 | 忘了 `__call__` 的签名同样会被解析 | 参数名写错，运行时 422 | 类实例当依赖时，参数按 `__call__` 的签名解析 |

**面试问法**：「`Depends(Auth)` 和 `Depends(Auth())` 有什么区别？」

30 秒版：传类时每个请求新建一个实例，传实例时那个实例跨请求共享。所以带可变状态的依赖必须传类，配置类依赖才传实例。同一请求里两者都只建（或只调）一次，因为缓存按依赖身份算。

**追问链**：

→ *"为什么同一请求内只建一次？"*（机制层）cache key 第一项是 `Auth` 类对象，两处挂载点算出来的 key 完全相同，第二次进入节点时直接命中缓存。

→ *"实例里存连接池行不行？"*（边界/故障层）可以，但要清楚这是进程级共享：多个 worker 会各有一份；连接数 × worker 数是实际连接数。真正的连接池应该由 engine 管，依赖只引用它。

→ *"RAG 里 retriever 用类还是实例？"*（场景落地层）实例——它持有向量库 client、embedding 配置，天然是开销大且只读的对象，用实例避免每请求重建。但要保证 client 本身线程安全，否则并发下会出问题。

### 8. `use_cache=False` 的粒度 ★★★☆☆

**一句话定义**：`Depends(f, use_cache=False)` 关掉**这一处挂载点**的缓存读/写，不影响别处。

**为什么存在**：有些依赖在同一个请求里就是需要重算一次——比如"当前用户资料"和"目标用户公开资料"都靠 `get_user(id)` 取，两个不同 id 必须查两次。

**怎么用**：

```python
@app.get("/nocache")
def nocache(
    x: str = Depends(dep_fresh),
    y: str = Depends(dep_fresh, use_cache=False),   # 只关这一处
) -> dict[str, str]:
    return {"x": x, "y": y}

# 实测：调用顺序 ['fresh', 'fresh']，响应 {'x': 'F', 'y': 'F'}
```

**底层机制**：判断在 `utils.py:660` —— `if sub_dependant.use_cache and key in cache`。`use_cache` 是 `Depends` 的字段（`params.py:748`），所以粒度是**挂载点**，不是函数，也不是全局开关。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 想用参数区分取值 | 两处都写 `Depends(get_user)` 期望查两次，实际一次 → 拿到自己的数据当别人的 | 想拿不同的值只能 `use_cache=False`，参数进不了 key |
| 2 | 当性能开关用 | 以为关缓存能"刷新数据"，实际是重复查库/重复鉴权 | 它的语义是"这次要重算"，代价是副作用也重跑 |
| 3 | 全局关缓存 | 所有依赖都 `use_cache=False`，鉴权查 3 次 | 粒度到挂载点，只关真需要重算的那一处 |
| 4 | 以为关了缓存会影响别处 | 担心 `x` 的值也变 | 只影响声明了这一处的节点 |

**面试问法**：「什么时候需要 `use_cache=False`？」

30 秒版：同一个依赖在一次请求里要拿不同结果的时候。典型是"查当前用户"和"查目标用户"都走 `get_user(id)`——缓存 key 不含实参，不关缓存第二处会直接复用第一处的值，那是越权而不是性能问题。

**追问链**：

→ *"为什么参数不能区分？"*（机制层）key 是 `(callable, scopes, scope)` 三元组，实参不在里面。同一请求内同函数的实参本来也必然相同，设计上就没打算用它区分。

→ *"关了缓存会不会破坏别的依赖？"*（边界/故障层）不会，粒度是挂载点。但注意副作用：关掉的那一处会重新执行依赖内部的一切（查库、写日志、加锁），如果依赖有非幂等副作用，这里就出问题了。

→ *"多租户场景下，同一个 service 要读两个租户的数据怎么写？"*（场景落地层）`get_repo(tenant_id)` 参数化 + 两处都 `use_cache=False`，或者干脆做成两个不同的 callable（`partial(get_repo, tida)` / `partial(get_repo, tidb)`）——后者 key 第一项不同，天然隔离，更不容易踩。这是"用身份区分"比"用开关"更稳的例子。

### 9. 请求作用域容器（依赖消费依赖） ★★★☆☆

**一句话定义**：让一个依赖"拥有"资源（如数据库 session），其他依赖通过 `Depends` 消费它，靠请求级缓存天然实现"同一请求共享同一份"。

**为什么存在**：想在一个请求里让多个 repo 共用一个 session（同事务、同连接）。直觉方案是模块级变量——那是**所有请求共享**，还会并发错乱。

**怎么用**（W7 会落成真代码）：

```python
async def get_db_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:
        yield session

async def get_kb_repo(session = Depends(get_db_session)) -> KBRepo:
    return KBRepo(session)

async def get_doc_repo(session = Depends(get_db_session)) -> DocRepo:
    return DocRepo(session)          # 同一请求，同一个 session
```

**底层机制**：`get_db_session` 在请求内只执行一次（缓存命中），两个 repo 拿到的是**同一个对象**。这就是 FastAPI 版的"请求作用域容器"，不需要任何额外机制——缓存就是容器。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用模块级变量做"请求内共享" | 跨请求串数据、并发出错 | 依赖消费依赖，缓存保证同请求同一份 |
| 2 | 以为两个 repo 会各开一个 session | 事务提交一半，另一半看不到 | 都 `Depends(get_db_session)` 就是同一个 |
| 3 | session 放模块级 | 多请求共用一个连接，事务互相污染 | session 必须是 yield 依赖，请求结束关闭 |
| 4 | 依赖里 `await session.close()` 又配 teardown | 二次关闭报错 | 关闭只写在一处（`async with` 的出口） |

**面试问法**：「一个请求里多个 repo 怎么共用一个数据库 session？」

30 秒版：把 session 做成 yield 依赖，两个 repo 都 `Depends(get_db_session)`。依赖缓存保证同一请求只建一个 session，所以两个 repo 拿到同一个对象，天然同事务。不用模块级变量——那是进程共享，会串。

**追问链**：

→ *"怎么能确定是同一个 session？"*（机制层）`Depends(get_db_session)` 的 cache key 两处完全相同（同一个 callable、同样 scope），第二次进入节点时直接命中，不执行 setup。

→ *"并发请求会不会串？"*（边界/故障层）不会，`dependency_cache` 每次请求新建。会串的是模块级变量和 `Depends(Session())` 这种传实例的写法——那才是真正的坑。

→ *"AI 应用里这个模式还能装什么？"*（场景落地层）装"一次请求的 token 预算"：`get_budget()` yield 一个计数器，LLM client 依赖它记账，teardown 里把总量打日志/上报。这样成本归因能精确到接口，也不用每个调用点手动传。

## 三、30 秒答案集（面试速答）

1. **依赖注入解决什么问题？** 把依赖从函数体搬到签名，依赖关系变成可遍历的树——于是能缓存、能替换、能生成文档；少写几行是副产品。
2. **依赖树什么时候建？** 注册期，`@app.get` 执行时扫签名建好挂在 route 上；请求期只遍历不重建。
3. **依赖缓存的 key 是什么？** 三元组 `(依赖 callable 对象, oauth scopes, scope)`。**不含实参**。
4. **缓存范围多大？** 一次请求。dict 每次请求新建，请求结束即丢；不是进程级，和 `lru_cache` 完全不同。
5. **为什么同一依赖挂两处只跑一次？** 进入节点时先查缓存，第二次进入时子依赖还没开始递归就命中了。
6. **yield 依赖的异常流向？** handler 抛的异常被送进 yield 点（生成器 `throw`），所以 teardown 能 catch、能回滚；setup 抛的走不到 yield。
7. **teardown 出错客户端看到什么？** 默认 `scope="request"` → 200 + 完整响应（异常只进日志）；`scope="function"` → 500。
8. **`scope="function"` 为什么存在？** 唯一理由：让 teardown 的失败可见。事务提交失败必须返回 500。
9. **`dependency_overrides` 的 key 是什么？** 原依赖的 callable 对象；value 是替身 callable。写字符串不报错、也不生效。
10. **override 了 `dep_a`，`dep_b` 会变吗？** 会。依赖是数据流，换节点的输入，下游输出跟着变。
11. **`Depends(Auth)` 和 `Depends(Auth())` 区别？** 传类每请求新建实例，传实例跨请求共享状态；同请求内都只执行一次。
12. **`auto_error=False` 换来了什么？** 不是状态码（两值都是 401），是响应体契约统一成 `{"code","message","detail"}`。
13. **`use_cache=False` 什么时候用？** 同一请求里要拿不同结果时；粒度是挂载点，不是函数也不是全局。
14. **`Query(default=1)` 算依赖吗？** 算节点，只是"从请求取值的节点"，不需要调函数。
15. **FastAPI 的 DI 和 pytest 夹具什么关系？** 形状同源（setup / yield / teardown），失败可见性不同源——pytest teardown 出错必挂，FastAPI 默认静默。

## 四、白板手写靶（必须能默写）

**靶 1：一条真实鉴权依赖链**

```python
_bearer_scheme = HTTPBearer(scheme_name="Bearer Token", auto_error=False)

async def get_current_user_id(
    credentials: HTTPAuthorizationCredentials | None = Depends(_bearer_scheme),
) -> UUID:
    if credentials is None:
        raise UnauthorizedError("缺少认证信息")
    claims = decode_access_token(credentials.credentials)
    try:
        return UUID(claims.sub)
    except ValueError as exc:
        raise UnauthorizedError("凭证 subject 不是合法用户") from exc
```

要点：`auto_error=False` 必须配 `if ... is None` 分支；`UUID(...)` 要包 `try`。

**靶 2：yield 依赖 + 事务语义**

```python
async def get_db_session() -> AsyncIterator[AsyncSession]:
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

# 挂载时
Depends(get_db_session, scope="function")   # 提交失败才能变 500
```

要点：`commit` 写在 `yield` 之后、`except` 之外；`scope="function"` 不能漏。

**靶 3：conftest 里的 override 夹具**

```python
@pytest.fixture
def override_current_user_id(app: FastAPI) -> Iterator[UUID]:
    async def fake_user_id() -> UUID:
        return TEST_USER_ID

    app.dependency_overrides[get_current_user_id] = fake_user_id
    yield TEST_USER_ID
    app.dependency_overrides.pop(get_current_user_id, None)
```

要点：key 是函数对象；`yield` 的是值；收尾 `pop` 不用 `clear`。

## 六、可以讲成故事的三段

**故事 A：「我以为缓存按参数区分」**

读教材时看到菱形依赖只跑一次，我推断"缓存 key 里应该有参数"。写三句话时为了证明结论，顺手编了"`f(dep, x=1)` 和 `f(dep)` 会拿到同一个结果"——结果被告知 `Depends` 根本不接受实参，这个调用在 FastAPI 里不存在。跑了一次源码打印才看见 key 是 `(函数对象, scopes, scope)`，实参压根不在里面。**教训：举不出真实例子的时候，说明那个结论是背来的，不是推出来的。**

**故事 B：「只知道结论，所以还得再问一遍」**

我答对了"override 的 key 是函数对象"，隔了半小时又问"那个 key 到底存什么"。差别在于：前者是结论，后者是结构。结论能回答"怎么写"，回答不了"为什么我用 `functools.partial` 包了一层之后就不生效了"——实测那条 partial 的响应纹丝不动，`{'v': 'real:7'}`，一个错都没有。**教训：能答"是什么"不算懂，能答"换成别的会怎样"才算。**

**故事 C：「同一个概念，我在两道题里说了两种话」**

被问"全局缓存会出什么事"，我举的例子是"用户和知识库各有一个 `get`，参数相同所以会串"。同一场对话里我刚答对"cache key 是函数对象"——两个不同的函数，key 第一项就不同，压根不串。真正的危险是另外一件事：`get_current_user_id` 无参，key 永远一样，全局缓存下 B 用户会拿到 A 的凭证。**教训：新学的知识和用了三周的旧直觉会并存一段时间，旧的那个会在放松的时候接管推理。**

**D2 预告（中间件与异常处理器执行顺序）**

明天不写新业务代码，但会解释一个你今天已经在用的现象：

1. **`AppError` 是谁接住的、在树的哪一层**：依赖解析阶段抛的异常和 handler 抛的异常，走的处理器不完全一样；`Exception` 通配处理器跑在**中间件外面**（`ServerErrorMiddleware` 那层），所以中间件日志里看不到 500 的原始异常——这是最容易写错的一条。
2. **项目里埋着一个真 bug**：`handle_validation` 直接返回 `exc.errors()`，pydantic v2 会把自定义 validator 的原始异常对象塞进 `ctx.error`，JSON 序列化失败 → 422 变 500。D3 加第一个 `field_validator` 当天就会炸，明天先修掉。
3. **`await request.body()` 到底能不能读**：网上流传"读了之后下游读不到"，实测 starlette 1.9.0 已经会缓存重放，下游照样读到。真正的代价是整个 body 进内存、SSE 失去流式语义——结论要从"不能读"改成"不该读"。
