# W6 周总结 · FastAPI 工程化（12-07 ~ 12-12）

> 本周主题：把一个能跑的 FastAPI 服务，改造成**有契约、有分层、有门禁**的工程。
> 六天不是六个孤立主题，是**同一个请求的六个截面**。这份总结按"截面在轴上的位置"组织，不按日期。

---

## 一、一周主线（先有轴，再挂点）

**一个 HTTP 请求的一生**：

```
启动期：路由注册 → 依赖树建立（Dependant 树）
   ↓
请求期：中间件栈（外→内）→ 路由匹配 → 依赖求解（鉴权）→ 参数校验 → handler
   ↓
出口：  response_model 校验+序列化 → 装壳 → body 发出 → 后台任务 → 中间件收尾
```

**分界线在第 3 行**：竖线左边是**契约**（必须准、必须快、错了要喊），右边是**副作用**（可以慢、错了没人知道）。

**六天各在哪一段**：

| 天 | 主题 | 在轴上的位置 | 一句话 |
|---|---|---|---|
| D1 | 依赖注入 `Depends` | 启动建树 / 请求走树 | 依赖树是**启动时**建的，请求时只是**走一遍** |
| D2 | 中间件与异常处理器 | 轴的两端，方向相反 | 请求外→内，异常内→外；**壳在 handler 装，中间件只调度** |
| D3 | Pydantic v2 | 校验的两个位置 | 同一套机制，**入口是 422（客户端错）、出口是 500（我的 bug）** |
| D4 | 路由分组 + 统一响应体 | 路径分层 + 两条线的装壳点 | 成功线 handler 装壳，失败线 handler 装壳——**两个位置，一个形状** |
| D5 | OpenAPI + BackgroundTasks | 竖线两侧各一个 | 文档管"别人怎么看你"，后台任务管"别让用户等" |
| D6 | 注入式验收 | 四道门 | 只有 1/5 的 bug 在启动时喊，其余靠**测试门的断言** |

## 三、五个贯穿全周的模式（比单个知识点值钱）

### 模式 1：**层错位** —— 本周出现 4 次

| 次数 | 错在哪 | 正确说法 | 钉死的证据 |
|---|---|---|---|
| 1（D2） | "异常退栈后帧死了" | 帧活着，**手里没有 response** | 源码 `build_middleware_stack` |
| 2（D4） | "失败响应的壳在 ExceptionMiddleware 装" | 中间件只**查表+调用**，壳在 handler 函数体 | `_exception_handler.py:64-66`：`await handler(...)` → `await response(...)`，从没碰 body |
| 3（D7 主线） | "Router 把异常抛给 ExceptionMiddleware" | Router **没有捕获**，异常自然冒泡穿过 `call_next` | — |
| 4（D7-Q3） | 又回到"中间件装壳" | 见上 | grep：`ApiResponse` 只在 `main.py` 和端点里出现，中间件文件零命中 |

**根因**：把"**调度点**"当成"**执行点**"。ExceptionMiddleware 决定**谁来处理**，handler 决定**怎么处理**——两件事在同一个流程里，但字节码不在同一个文件。

**判据（以后自问）**：这件事的代码写在哪一行？写不出来就是没懂。

### 模式 2：**限定词决定对错**

同一个结论，限定词错一个字就变错：

- "过滤再校验" → 错；**同一次 `model_validate` 的两面**（没声明的字段是"没读过"，不是"读过再删"）
- "捕获异常" → 错；**查表后转交**
- "response 没了" → 不准；**任务没被挂到任何发出去的 response 上**
- "语义等价改动抓不住 = 盲区" → 错；那是**等价变异体**，抓不住才对

### 模式 3：**实测优先于记忆**（本周打脸 4 次，其中 2 次打的是我）

| 断言 | 实测结果 | 谁错了 |
|---|---|---|
| "`use_cache=False` 能让整个路由不缓存" | 只关"读"不关"写"，路由级 False 仍 1 次 | 教材初稿（我） |
| "老写法 `Depends()` 会触发 Ruff 警告" | ruff 一声不吭，64 测试全绿 | 用户脑补 |
| "缓存键是二元组 `(call, scopes)`" | **三元组**，第三项 scope 决定 teardown | 我（旧版本记忆） |
| "自定义 `openapi()` 里调 `app.openapi()` 没事" | 966 层 `RecursionError` | 我写探针时自己踩 |

### 模式 4：**零症状 bug 才是真风险**

本周抓到的零症状 bug：health 双挂载（两条路径都 200）、`logger.debug` 吞异常（线上 INFO 级别下一个字不出）、`min_length` 被 `not_blank` 兜住（删了行为也没变）、`response_model` 多余字段静默丢（200 但字段消失）。

**共同点**：测试全绿、服务正常、日志干净。**唯一猎手是"有人专门去注入它"** —— 这就是 D6 变异测试存在的理由。

### 模式 5：**契约的载体和归属**

本周反复问的三个问题，可以推广到任何"约束写在哪"的场合：

1. 这条约束**属于谁**？（入参 schema 不该有 `status`，那是输出/内部状态）
2. 它**由谁执行**？（`response_model` 校验，不是包装）
3. 它**失效时谁喊**？（机器消费的接口不套壳、边界测试守住 `le=100`）

## 四、30 秒答案集（本周 10 题，面试速答）

**1. Depends 的缓存键是什么？**
三元组：依赖函数对象、oauth scopes 元组、scope 字符串（`"function"`/`"request"`/`""`）。不含实参——同函数不同参数**不会**自动拆条目。缓存活在**一次请求**里，请求结束即销毁，所以不能跨请求复用（否则 A 的鉴权结果会给 B 用）。

**2. 菱形依赖 A→(B,C)→D，D 跑几次？**
默认 1 次（第二处命中缓存）。C 若写 `use_cache=False` → 2 次。注意缓存只让**这一个节点**不执行，子树是否执行取决于子树自己的缓存。

**3. 中间件的顺序？**
外→内：`ServerErrorMiddleware`（最外）→ 后 add 的 → 先 add 的 → `ExceptionMiddleware`（最内，紧贴路由）。**后 add 的在外层**，所以"最后加的中间件最先看到请求、最后看到响应"。

**4. 异常从 service 抛出来，怎么变成带壳 JSON？**
冒泡穿过路由层 → `ExceptionMiddleware` 沿 `type(exc).__mro__` 查注册表 → 找到 handler → `await handler(request, exc)` → handler 里 `JSONResponse(content=ApiResponse(...).model_dump())` → 中间件把 Response 发出去。壳在 handler 装，中间件只负责调度和发送。

**5. 没有 handler 接会怎样？**
继续外抛到 `ServerErrorMiddleware` → 裸 `{"detail":"Internal Server Error"}` 500，**不套壳**。所以"壳没出现"本身就是"handler 没注册"的信号。

**6. `response_model` 到底管什么？**
只管出参：按声明字段校验类型 + 只输出声明字段（多余字段不输出）。类型错抛 `ResponseValidationError` → 500。**入参校验与它无关**，是参数注解上的 Pydantic 模型干的，失败 422。

**7. 为什么入参错是 422、出参错是 500？**
判据是**修复动作在谁手里**：入参错客户端改参数重发；出参错服务端改代码。不是"因为一个客户端错一个服务端错"——那是倒果为因。

**8. 统一响应体在几个地方装壳？**
两个：成功路径在**端点函数**里（`return ApiResponse[T](data=...)`，`response_model` 只校验不包装）；失败路径在 **`main.py` 的 handler** 里。形状相同，位置不同。

**9. 哪些接口不该套壳？**
204（无 body）、health/metrics（机器只读 HTTP 状态码，套壳会造成两套健康判据）、SSE（流式）。判据：**读者是谁、走不走路由出口**。

**10. 覆盖率和变异得分的区别？**
覆盖率量"哪几行被跑到"；变异量"故意改坏后测试会不会喊"。覆盖率 96% 仍可能对 4 类改动零反应。**两者都量不了"规范本身对不对"和"跨请求的状态"**。

## 七、面试故事（三个，都能扛追问）

**故事 1：一次"测试全绿"的路由搬家**

health 从 `/api/v1/health` 搬到根 `/health`。测试全绿、服务正常，但旧地址还活着——`router.py` 里的 `include_router` 忘了删，同一个健康检查有两个地址。更麻烦的是，它挂在业务 router 下：哪天有人给 `api_router` 加全局鉴权，health 就会 401，k8s 判定不健康，反复重启实例。
**追问点**：你怎么发现？——`/docs` 里 health 出现两次 + 两条路径都回 200。

**故事 2：三个坑，两个是零症状的**

给"创建文档"挂后台任务 `run_index`。交付版埋了三个坑：`async def` 里 `time.sleep` 堵事件循环、`except` 里用 `logger.debug` 吞异常、日志打文档正文全文。
**追问点**：哪个最难发现？——`debug` 那个，因为测试全绿、服务正常，只有线上日志级别是 INFO 时才暴露"异常被合规地吞掉"。
**反转**：我修的时候删了 `exc` 变量但漏了格式串里的 `%s`，真触发时 logging 会往 stderr 打一屏 `--- Logging error ---`。**改一处漏一处**，修复类改动的通病。

**故事 3：给测试门做体检**

覆盖率 96% 看着很安全。我把 9 个"真 bug 等价改动"注入进去，9 个全被杀；又注入 4 个"测试没断言的维度"，4 个全存活。结论：**覆盖率量"跑没跑到"，不量"错了会不会喊"**。
**追问点**：那 4 个盲区怎么办？——分两类：`use_cache=False`/中间件重复注册属于"该补断言"；删 `min_length` 属于**等价变异体**（`not_blank` 还兜着，行为真没变），不该被杀。
