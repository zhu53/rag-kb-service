## 零、开写之前的 5 分钟（"话到嘴边说不出"时用这个）

> 读教材顺畅 = **再认**（看到能点头）；写笔记要 = **提取**（合上书能自己生成）。
> 卡在提取层不是没读懂，是缺一个具体的提问。别硬憋，按下面三步走。

**第 1 步：先开口，别先写字（60 秒）**
合上教材，手机语音备忘录打开，对着下面「起步问题」里任意一条讲 60 秒。说话不需要组织结构，写才需要，门槛低得多。

**第 2 步：回听，只抄"卡住的那半句"（2 分钟）**
你会听见自己在某个词上反复绕。绕不过去的那句，原样抄进 §二。

**第 3 步：用填空句起头，别从"我原来怎么想"硬想（1 分钟）**
三个句式挑一个，缺的空自己填：

- `教材说 ___，我脑子里自动补的是 ___` ← 最有杀伤力，直接把错误理解钓出来
- `这里为什么要 ___ ？如果换成 ___ 会怎样`
- `总觉得 ___ 和 ___ 有关，但说不上来` ← **半句也算合法条目**，后面回填

## 二、还挂着的问号

> 抓问号的唯一技巧：读的时候一遇到「这里先记住」「后面会讲」「暂时不管」，**把作者那句话原样抄下来**。
> 那是作者替你标记的债，也是你最容易假装没看见的洞。解决了不要删，改成 `[x]` + 一句话答案。

- [x] **`dependency_overrides` 的 key 里到底装什么？**（11-05 提出，当天解决）
  原话：「我知道要写 `overrides[get_current_user_id] = ...`，但 key 存的是名字，还是 `Depends` 那个对象？」
  **答**：`dict[callable, callable]`。key = 注册依赖时那个 callable **对象本身**，value = 替身。查找只有一句 `dict.get(original_call, original_call)`（`utils.py:625-631`）——**找不到就用原函数**，所以 key 写错不报错、只静默不命中。
  **附带的两个新事实**：① 命中后不是直接调替身，是用替身重新 `get_dependant()` 建一棵子树（`utils.py:632-638`），所以替身可以有自己的参数（当 query 解析）、也可以有 `Depends`；② bound method 作 key 时按（实例 + 函数）比较，`functools.partial` 包装后则对象不等 → override 原函数静默失效。
  **证据**：实测 partial 那条 `{'v': 'real:7'}` 纹丝不动；`repo.get` 新取一次仍然 `{'v': 'FAKE'}`。
- [x] **`dependency_cache` 的 key 存什么？跟 overrides 的 key 是同一个东西吗？**（11-05 提出，当天解决）
  **答**：不是。`DependencyCacheKey = tuple[Callable | None, tuple[str, ...], str]`（`types.py:12`）——**三元组** `(依赖 callable 对象, oauth scopes 元组, scope 字符串)`，value 是依赖**解析出来的值**。overrides 的 key 是**单个 callable**，value 是替身 callable。
  实测长相：`Depends(f)` → `(<function f at 0x...>, (), '')`；`Depends(f, scope="function")` → `(..., (), 'function')`。
  实测第三项真参与：同一个 `f`，一处默认一处 `scope="function"`，同请求内调用了 **两次**（key 差一项，没命中）。
  **一句话区分**：overrides 是"**替身表**"（谁换成谁），cache 是"**结果表**"（谁算过什么）。

## 三、读完这一遍，我能用自己的话说出来的三句

> 不许用教材原句。写完念一遍——如果念的时候自己都觉得含糊，那句就是假的懂。
> 这三句以后会长成周总结第六节的"面试故事"，现在只要 3 行。
> **三句各盖一个机制**：① DI 的本质 ② 缓存 / 替身（override） ③ yield 依赖。

**最终版（11-05 定稿）**

1. 依赖注入把依赖从函数体搬到签名里，于是依赖关系变成了**可遍历的数据**（`Dependant` 树），框架能走这棵树——这才是"能画树、能缓存、能替换测试"的机制原因。它促进单一职责，但两者不等价：单一职责讲"只做一件事"，DI 讲"依赖从外面给"。
2. 缓存的 key 是三元组 `(call, scopes, scope)`，**不含实参**，value 是解析结果。所以同一个函数挂两处只跑一次，想重算只能 `use_cache=False`——改参数没有意义，参数进不了 key。override 的 key 是被依赖的那个 `callable` 对象，value 是替身函数。
3. yield 依赖与 pytest fixture **形状相同、功能不同**：handler 抛的异常会被送进 yield 点（所以能在 teardown catch、能回滚）；默认 `scope="request"` 时 teardown 在**响应发出后**执行，异常只能进日志、客户端仍拿 200；要让它变成 500 必须 `scope="function"`——此时 teardown 改在 handler 结束后、响应发出前执行。

**11-05 第一版（原话存档，不改）**

1. 依赖注入不仅仅是为了节省/复用代码，它还把函数体内的依赖关系从函数体移到了签名里，所以能够画依赖树，缓存复用，替换测试，让我想起了函数原子化的这个说法，就是每个函数的职责是单一的。
2. auto_error=false，第三方库的返回值不一定是项目需要的值，第三方库的异常消息格式统一为项目业务异常格式，可以减少维护成本，统一管理。
3. fastapi 的依赖注入和 pytest 的 fixture 是形状相同，不是功能完全相同，fastapi 的 setup 的异常可以通过 yield 传回，所以可以接入数据库事物操作，而且 teardown 是请求发送后才执行，所以异常信息只能在日志看到，服务端还是 200 的状态

**批注**

**① ✅ 前半段满分。**"从函数体搬到签名"这句可以直接进面试。缺一层机制：搬进签名之后，依赖关系就变成了**数据**（`Dependant` 树上的节点），框架能遍历它——**"能画树 / 能缓存 / 能替换"的前提是它先变成了数据**，不是"写清楚了大家就都懂了"。
⚠️ "函数原子化 / 单一职责"是**联想不是等价**：单一职责讲"这个函数只做一件事"，DI 讲"依赖从外面给"。面试官会追一句"那一个只做一件事的函数为什么还需要 DI？"——答不上就露馅。

**② ⚠️ 跑题。**这句是 W5 的残影（`auto_error` / `cast` / 异常翻译），不属于 D1 的三个机制，占了三句里的一个名额。
但它的**直觉是对的**：`auto_error=False`（别让框架替你报错）、`cast`（别让检查器替你猜）、`overrides`（别让框架用真依赖）——三者是同一个姿势：**把控制权从框架手里收回来**。想保留就按这个统一句重写；但今天真正缺的那句是**缓存 / override**。

**③ ✅ "形状相同不是功能相同"本身就是好答案。两处必须拧正：**
- ❌ "setup 的异常可以通过 yield 传回" —— **方向反了**。是 **handler 抛的异常被送进 yield 点**（生成器的 `throw`），所以你才能在 teardown 段 catch 到。`setup` 里抛异常根本走不到 `yield`。
- ❌ "请求发送后才执行" —— 是**响应发送后**。一字之差，W7 写事务会话会写错方向。
- 补一条漏的：teardown 能影响状态码的前提是 `scope="function"`，默认（`request`）改不了——今天实测的 200 vs 500 就是这件事。

**11-05 第二版（原话存档）**

1. 缓存的 key 存的是一个三元组，不存具体实参，值是运行结果，所以开启缓存后，f（dep，x=1）和 f（dep）拿到的是同一个结果，override 的 key 存的是调用函数本身，值是替换函数。
2. fastapi 的依赖注入，setup 后，handler 的异常能够传回 yield，所以能够在 teardown 获取异常并处理。并且 teardown 是在响应发送后才执行的。

**批注（第二版）**

**① 四个短句全对**：三元组 ✅ 不含实参 ✅ 值是运行结果 ✅ override 的 key/value ✅。
⚠️ **但例子不成立**：`Depends(f)` 的签名只有 `dependency` / `use_cache` / `scope`，**不收实参**；实参来自请求，同请求内必然相同。所以"`f(dep, x=1)` 和 `f(dep)`"这个场景在 FastAPI 里根本不存在——你是为了证明结论**现造**了一个调用。
成立的例子（今天实测过）：同一个 `f` 挂两处 → 只跑一次，log 只有一条 `call:f`。想让某一处重算，唯一开关是 `use_cache=False`；改参数没有意义，因为参数进不了 key。
真正的落点：**key 只认"身份 + scope"，不认"这次调用看到的数据"**。这才是全局缓存会串的根因——`get_current_user_id` 每次看到的 header 都不同，但 key 一样。

**② ✅ 方向全对**（handler 的异常 → yield 点 → teardown 能 catch），比第一版前进了一步。
⚠️ **缺一个限定词**："teardown 是在响应发送后才执行"是**默认**（`scope="request"`）。写 `Depends(dep, scope="function")` 时，teardown 在响应发出**之前**跑。少了这个限定，这就是一句错的绝对句。

**两句的共同毛病：缺限定词。**
第 1 句缺"同一个 callable"→ 于是举出了不存在的例子；第 2 句缺"默认 scope 下"→ 于是把默认值说成了规则。
面试被追问破的，十次有八次是这种**绝对化表述**——不是不懂，是话说满了。

**11-05 第三版（第 2 句补完）**：默认 scope 是 request，teardown 在响应发送后执行；指定 function 时不是——teardown 在 handler 结束后、响应发出前执行，所以它抛异常能变成 500。

## 格式说明（为什么是这样）

**为什么不抄知识点？** 抄写产生"我在学"的手感，但不产生理解。判断标准很简单：抄完合上书，能不能答出"如果没有它，代码会长什么样"。答不出，抄的那页纸就是废纸。

**为什么"原来怎么想"是必填项？** 因为那才是面试会露馅的地方。你带着"Depends 等于调用函数"这个念头写了三周代码，它不会自己消失，只会在被追问时冒出来。把它写下来 = 把它钉在纸上，之后每看到一次就弱一分。

**为什么问号不许删？** 保留"当时不懂"和"后来懂了"两条记录，才看得出能力跨度。这也是 W5 那三个面试故事的原材料——反转点全在接受错误认知的那一刻。

**一读就懂的章不要跳过。** 写 `§X 一读就懂，因为___`（原因必须填）。全篇零卡点只有两种解释：教材太浅，或者你没在预判、只是在读字。

**和另外两份东西的分工**：

|---|---|---|---|
