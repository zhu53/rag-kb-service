# 每日总结 · 固定模板

> **用途**：每个学习日结束时，按本模板写 `progress/weekN/DN-总结.md`。
> **为什么固定**：W1–W4 每天形态都不一样——D4 缺「底层机制」、D6 和 D1 缺「逐知识点易错点表」。复习时同一块内容在不同文件的不同位置，等于没有索引。
> **基准样本**：`progress/week5/D1-总结.md`（8 个知识点 × 7 项骨架全齐，578 行）。
> **原则**：节可以短，不可以缺。哪一节写不出来，说明当天那个环节没做（比如没踩坑 = 没真动手）。

---

## 一、七节骨架（顺序固定，不增不删）

| 节 | 标题 | 必备 | 标准 |
|---|---|---|---|
| 头部 | 4 行元信息 | ✅ | 资产 / 环境 / 门禁 / 第四档 |
| 一 | 知识地图（按面试出场率排） | ✅ | 8–12 行，5 列，星级降序 |
| 二 | 逐个知识点讲透 | ✅ | 每点 7 项，40–70 行 |
| 三 | 30 秒答案集 | ✅ | 10–15 条，每条 ≤ 2 句 |
| 四 | 白板手写靶 | ✅ | 3 个，只放代码不放解释 |
| 五 | 踩坑实录 | ✅ | 3–5 行，只写当天真踩的 |
| 六 | 可以讲成故事的三段 | ✅ | 3 段，每段有反转 |
| 七 | 能力画像与下日衔接 | ✅ | 强项 2 / 待补 2 / 预告 2–3 |

### 头部 4 行

```markdown
> 本日资产：{一句话量化产出，如「58 个类型错误 → 清掉 50 个，留 8 个给 D2」}
> 环境：{实测用的版本，如 mypy 2.4.0 / Python 3.11.18 / 46 files checked}
> 门禁：{N passed / 分支覆盖 X% / 变异 N/N / ruff}
> 第四档 `review_NN_topic.py`：{几个坑} 个坑命中 {几个}
```

**判断标准**：一年后只看这 4 行，能不能判断"这份总结对应哪个代码状态"。写不出量化产出的那天，等于没产出。

### 一、知识地图

```markdown
| # | 知识点 | 出场率 | 掌握要求 | 本日证据 |
|---|---|---|---|---|
| 1 | `Any` 的传染性 | ★★★★★ | **能讲清它比 `# type: ignore` 更危险** | 第四档坑 1 |
```

三条硬要求：

1. **按星级降序排**，不按讲述顺序、不按天的顺序。复习时先看上面的。
2. **掌握要求必须是可验证的动作**——「能讲清 X 和 Y 的区别」「能默写 X」。写「理解 X」「熟悉 X」等于没写。
3. **本日证据必须有具体指向**——第四档第几坑 / 哪条报错 / 哪个测试名。空着说明这个知识点今天没有落点，该降星或删掉。

### 二、逐个知识点讲透

每个知识点的 7 项骨架，**顺序固定**：

| 项 | 写什么 | 不合格 |
|---|---|---|
| 一句话定义 | ≤ 40 字，说清它**是什么** | 抄官方文档的整段 |
| 为什么存在 | 解决什么问题；**没有它会怎样** | 只写"为了方便" |
| 怎么用 | 能跑的代码 + 本项目的真实片段 | 只有伪代码 |
| 底层机制 | 它在**实现层面**怎么做到的（查表/字节码/查找路径/阶段） | 只重复"怎么用" |
| 易错点 | 表：`# / 坑 / 症状 / 正解`，3–5 行 | 只写"注意不要写错" |
| 面试问法 | 一句真题 + **30 秒版答案**（口语，能直接念） | 书面定义 |
| 追问链 | 3 条，格式 `→ *"追问"* 答案`，**至少一条挖到底** | 三条都是同层问题 |

长度参考：每点 40–70 行。低于 40 行大概率有项在敷衍。

### 三、30 秒答案集

10–15 条，每条 **≤ 2 句**，是"能直接念出来"的口语。

**判断标准**：合上文档，能不能背出来。背不出来的不算答案，算笔记。

### 四、白板手写靶

3 个，**只放代码/表格，不放解释**（解释放第二节）。

挑选标准：面试现场**真的可能让你写**的东西——装饰器、Protocol、SQL、状态机。样板 CRUD、DTO 转换不用背。

每个靶后面一行「要点」，写最容易写错的那一处。

### 五、踩坑实录

```markdown
| 坑 | 现象 | 教训 |
|---|---|---|
| 给 native 命令加 `2>&1` | PowerShell 把 stderr 包成 ErrorRecord、`$?` 变 false | mypy 错误全在 stdout，本来就不用重定向 |
```

3–5 行，**只写当天真实发生的**。写"假设性"的坑没有价值——你不是在写教材，是在记自己的病历。

### 六、可以讲成故事的三段

每段 4–6 行，结构固定：

```
背景（一句话）→ 我以为是 X → 实际是 Y → 教训（一句能背下来的话）
```

**判断标准**：能在面试里讲满 60 秒，**且有反转**。没有反转的经历不是故事，是流水账。

### 七、能力画像与下日衔接

- **强项 2 条**：必须带证据（"3/3 全中"而不是"掌握不错"）
- **待补 2 条**：具体到"哪一句说不准"（"说'硬说 `{} or None` 为字典'，漏了'先得到 None'这一步"）
- **下日预告 2–3 条**：预告**坑**，不预告**内容**（"会撞变异性，参数逆变写反就匹配不上"比"明天学 Protocol"有用）

## 二、两张表别写混（最容易出错的地方）

| | 第二节的「易错点」 | 第五节的「踩坑实录」 |
|---|---|---|
| 谁的坑 | **任何人的通病** | **你自己**当天踩的 |
| 列 | `# / 坑 / 症状 / 正解` | `坑 / 现象 / 教训` |
| 数量 | 每个知识点 3–5 行 | 每天 3–5 行 |
| 用途 | 考前扫读速查 | 面试讲故事的原始素材 |
| 举例 | "用 `cast` 消掉 Optional 报错 → 边界输入才炸" | "我今天把 `2>&1` 加在 mypy 后面，结果 `$?` 变 false" |

**两者不能互相替代**：只有通病表 = 没有真实经历；只有踩坑实录 = 复习时找不到系统性的坑。

## 三、出场率怎么打

| 星级 | 含义 |
|---|---|
| ★★★★★ | 几乎每场后端/AI 应用面试都会碰到 |
| ★★★★☆ | 一半以上会问 |
| ★★★☆☆ | 约三分之一 |
| ★★☆☆☆ | 偶尔，或作为追问出现 |
| ★☆☆☆☆ | 只在特定岗位（如基础架构、编译器） |

**只升不降的场合**：这个知识点在**你的项目里有真实落点**（能讲成故事），比纯理论高一级。

> **PowerShell 版的两个注意点**（here-string 的坑）：
> 1. 这里用的是**双引号** here-string `@"..."@`，PowerShell 会展开里面的 `$`。脚本里现在没有 `$`，所以安全；哪天要写 `$`，就改成单引号版 `@'...'@`（那样内部单引号得换成双引号）。
> 2. `"@` 必须**顶格写在行首**，前面有任何空格都会报 `Unrecognized token`。
>
> 验证边界：bash 版我实跑过（上面的输出就是它打的），并做过**变异测试**——故意把第 4 个知识点的「底层机制」改名，脚本准确报出 `缺项: [(4, ['底层机制'])]`，说明它不是永远打印"齐全"。PowerShell 版的 here-string 内容我验证过解析正确（5 行、中文无乱码、`$` 无展开），但这个沙箱起不了外部进程，端到端请你第一次用时跑一遍确认。

## 五、什么情况下可以精简

模板不是凑字数。以下情况允许写短，但要注明原因：

| 情况 | 允许省什么 | 不能省什么 |
|---|---|---|
| 纯概念日（无代码落地） | 「怎么用」可写"在项目里怎么体现" | 底层机制、面试问法 |
| 操作型日（配环境/装工具） | 「底层机制」可省 | 踩坑实录（这类天坑最多） |
| 复习日（闭卷/补考） | 整份可以合并进周总结 | 能力画像、待补项 |

**不允许**：整节空着、用"略"字代替、把「易错点」写成一句话。
