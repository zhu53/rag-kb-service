## 0. 一句话主线

> **单元测试测业务规则，集成测试测拼装，外部世界才隔离；被测逻辑本身绝不能替换。**
> 而"测试是不是假的"，看的是**它杀不杀得死 bug**，不是它绿不绿。

## 1. 测试金字塔

### 1.1 定义（一句话）

按"真实度换成本"排的三层测试结构：底层单元测试最多（快、定位准），中层集成测试适量（验拼装），顶层 E2E 最少（慢、脆、粗）。

```
        ／  E2E  ＼          少量：全链路冒烟
       ／ 集成 API ＼        中量：TestClient 打路由
      ／   单元     ＼       大量：一个类/一条规则
```

### 1.2 为什么存在（解决什么问题）

三个真实痛点：

| 痛点 | 只有集成测试时 | 有单元层后 |
|---|---|---|
| 失败定位 | 一条链路红，不知道哪环 | 一条测试 = 一条规则，红了就是那条规则 |
| 断言能力 | 只能看最终 HTTP 响应，测不到"repo 没被调用" | 有 fake 账本，能断言副作用没发生 |
| 变更成本 | 换存储实现，业务规则测试全要重写 | 规则测试不动，只改装配 |

### 1.3 怎么用：本项目三层怎么分

| 层 | 测什么 | 本项目实例 | 时长 |
|---|---|---|---|
| 单元 | 一个类的业务规则 | `test_kb_service_unit.py`（8 个）：403/404/先鉴权后删除/offset 计算/委托 | 0.03s / 8 个 |
| 集成 | 层间拼装：路由、Pydantic 校验、全局异常翻译、鉴权 | `test_kb_api.py`（TestClient） | 0.01s / 个（内存存储下也很快） |
| E2E | 用户视角完整场景 | `test_chat_returns_sources`（建库→传文档→提问→引用来源） | 同上 |

**放弃教条**：本项目现在用内存存储，集成测试 0.01s/个，所以"金字塔为了快"现阶段不成立。现阶段金字塔的真实收益是**定位精度 + 交互断言能力**；速度红利在 W7 接 SQLAlchemy 后兑现。面试能这样分情况讲，比背"单元测试快"高一档。

### 1.4 机制：为什么上层更慢更脆

- 上层要组装更多对象（TestClient → ASGI 应用 → 中间件 → 路由 → service → repo）
- 上层引入更多不确定性（网络、数据库、时间、并发）
- 上层一条测试覆盖多条规则 → 失败信息粒度粗（"这条链路坏了" vs "这条规则坏了"）

### 1.5 面试问法

**Q：单元测试和集成测试怎么划分？**
> 30 秒：按被测对象的边界划分。单元测试测一个类的业务规则，依赖用 fake 替身，毫秒级、失败即定位；集成测试测层间拼装——真路由、真 Pydantic 校验、真异常处理器，只隔离外部网络。原则是：业务规则的全部分支放单元层，拼装正确性放集成层。

**追问链**：
- ①"为什么不全部用集成测试？" → 定位粗 / 交互断言做不到（"没被调用"需要替身视角）/ 换存储时规则测试要重写。
- ②"为什么不全部用单元测试？" → 拼装错误测不到：路由顺序、异常处理器没挂上、Pydantic 版本行为变化——只有集成层能抓。
- ③"金字塔一定是金字塔形吗？" → 不一定。遗留系统先补上层冒烟兜底再下沉；反过来"冰淇淋筒反模式"（大量 E2E + 无单元层）= CI 半小时 + 随机红。
- ④（深）"你怎么决定一条规则放哪层？" → 看它的失败是否与框架/IO 无关。纯业务判断（权限、分页、状态机）→ 单元；涉及序列化、HTTP 语义、中间件 → 集成。

### 1.6 易错点

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 在集成测试里 mock 掉 service | 测试全绿但拼装没验，改坏路由也绿 | 集成层不替换被测路径上的层 |
| 2 | 单元层测 HTTP 状态码 | 单元测试反而要去读 `exc.http_status`，耦合框架 | 状态码翻译归集成层 |
| 3 | 追求"分层齐活"给纯 CRUD 写 8 个单元测试 | 维护成本高于收益 | 无规则可测的薄层交给集成测试兜 |

### 1.7 关联

- W3-D4 分层与依赖倒置 → 分层让单元测试成为可能（service 不 import FastAPI 就能测）
- W4-D6 覆盖率 + 植入 bug 必红 → 金字塔形状决定"杀伤力"分布在哪个层次

## 2. Test Double 五兄弟

### 2.1 定义

Test Double（测试替身）= 冒充真依赖、让被测代码以为拿到了真实现的对象。五兄弟按"真实行为含量"排：

| 替身 | 定义 | 有真实行为 | 本项目的例子 |
|---|---|---|---|
| dummy | 只为填参数，从不被使用 | 无 | 永远不被调用的 repo 占位 |
| stub | 被问就答固定值 | 无 | `get()` 永远返回同一 row |
| spy | stub + 记录被如何调用 | 记录 | `FakeKBRepo.calls` 账本 |
| mock | 预先编排期待，结尾自动校验 | 无（编排） | `Mock(spec=...)` + `assert_called_once` |
| fake | **一个真实现的简化版** | **有** | 内存 dict 版 KBRepository |

### 2.2 为什么是"五兄弟"而不是只有 mock

因为不同场景需要的"真实度"不同：

- 只想让代码跑起来 → dummy
- 想控制一个返回值 → stub
- 想断言"没发生" → spy
- 想验证协作协议（谁调谁、几次）→ mock
- 想在不连数据库的情况下保留存储语义 → fake

**统一认知**：替身不是"偷懒"，是**边界隔离**。真实依赖（数据库/网络/时间）不可控、慢、有副作用；替身让测试可控可重复。

### 2.3 怎么用：三组关键对比（面试高频）

**fake vs mock（最重要）**

| | fake | mock |
|---|---|---|
| 行为来源 | 自己实现的真逻辑（dict 存取） | 测试里编排的假设 |
| 出错方式 | fake 自己写错 → 也要 review | 编排错了 → 测试验的是幻觉 |
| 适合 | 有简单实现价值的边界（repo、缓存、文件系统） | 没有简化价值的外部服务（第三方 SDK、HTTP 客户端） |

**stub vs fake**：stub 不管状态，问就答固定；fake 有状态，create 了就能 get 出来、list 能分页。

**spy vs mock**：spy 只记录，断言权在你手里（`assert calls == []`）；mock 预设期待并自动校验（`assert_called_once`）。spy 更直白、更 Python。

### 2.4 机制：为什么 fake 能"塞进"只认具体类的构造参数

```python
def __init__(self, repo: KBRepository | None = None) -> None:
    self.repo = repo or KBRepository()
```

- Python **运行时不检查类型注解**，只要对象有同签名方法就能跑（鸭子类型 / 结构化子类型）。
- 注解只服务人和 mypy。想让它"正规化"→ 把注解指向 Protocol（W3 `layering_practice/kb/interfaces.py` 的做法）。
- **真值坑**：`repo or ...` 是真值判断。fake 若定义 `__len__` 且返回 0（比如内部包一个空 dict 并转发 `__len__`），会被当成假值**静默替换成真 repo**——测试仍绿，但测的是真实现。

### 2.5 面试问法

**Q：fake 和 mock 有什么区别？你为什么选 fake？**
> 30 秒：fake 是缩小版真实现——行为是自己写的真逻辑，比如内存 dict 版 repo，create 了真能 get 出来；mock 的行为全是测试里编排的假设。存储语义简单（dict 够用）所以我选 fake，保留真实行为、验证力更强；mock 留给没有简化价值的外部服务，比如第三方 HTTP 客户端。判据是：这个依赖我能不能用 20 行写出可信的简化版？

**追问链**：
- ①"fake 会不会和真实现不一致？" → 会。所以 fake 必须照契约写（签名逐个照抄），且集成层要继续存在——单元抓规则，集成抓契约。
- ②"你怎么保证 fake 和真 repo 行为一致？" → W3 做过双实现对拍；换成 fake 同理，同一组场景两边跑，输出逐行一致。
- ③"magic mock 有什么危险？" → `MagicMock()` 对任意属性都返回 mock 对象，拼错方法名也不报错；必须 `spec=` 绑定真实类型。
- ④（深）"spy 和 mock 的判定权差异有实际影响吗？" → 有。mock 的期待写在 setup 里易过时；spy 把断言留在测试末尾，读起来就是"这条规则"。

### 2.6 易错点

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | fake 方法签名和真 repo 不一致 | 能跑但只是巧合，参数一改静默接不住 | 照抄真 repo / Protocol 签名 |
| 2 | fake 忘了 `_log` 记账（**零症状**） | 断言"没被调用"永远通过——账本里本来就没有 | fake 每个方法都要记账；fake 也要 review |
| 3 | 用 MagicMock 顶一切 | 断言的是"我编排的假设发生了" | 有实现价值就用 fake |
| 4 | 测试间共享 fake 实例 | 用例顺序一换就红 | 每个测试新建 fake |

### 2.7 关联

- W3-D4 Protocol 契约 → fake 是契约的第三个实现
- W4 第四档 #07 假测试 → "stub 换掉被测逻辑"正是替身滥用
- W4-D5 respx / 假时钟 → 外部 HTTP 与时间也是边界

## 3. mock 边界判据（本日核心）

### 3.1 一句话判据

> **被测逻辑本身绝不能替换；被测逻辑的"外部世界"（慢、不确定、有副作用、会烂）才值得替换。**

### 3.2 对号入座（本项目）

| 依赖 | 该不该隔离 | 用什么 | 理由 |
|---|---|---|---|
| repo（存储） | 该（service 单测里） | fake | 存储是边界；fake 保有真行为不丢验证力 |
| 时间（JWT 过期、`now()`） | 该 | 假时钟 / freezegun（D5） | 真实时间让测试不可重复 |
| 外部 HTTP（LLM API） | 该 | respx / 假 transport（D5） | 网络会抖、会花钱 |
| **service 的权限判断** | **绝不能** | — | 被测逻辑本身，mock 掉=测试不存在 |
| **Pydantic 校验** | 单测不碰；集成用真的 | — | 校验是真实行为 |
| **异常 → HTTP 状态码翻译** | 绝不能（集成层） | — | 层间拼装的核心价值 |
| repo 的 SQL 语义（W7 起） | 该（repo 自己的测试里） | 真 SQLite / 假驱动 | 此时数据库是 repo 的边界 |

### 3.3 面试问法

**Q：什么该 mock，什么绝不能 mock？**
> 30 秒：判据是"它是不是被测逻辑"。被测逻辑本身——权限判断、参数校验、状态机、异常翻译——绝不能替换，换掉就等于测了个假货；被测逻辑的外部世界——数据库、网络、时间、随机数、消息队列——才隔离，因为它们慢、不确定、有副作用。我一般用 fake 替存储、用假时钟替时间、用 transport 替 HTTP。

**追问链**：
- ①"你项目里 mock 了什么？" → 存储用 fake（内存 dict），HTTP/time 在 D5 做；service 里的规则一行没换。
- ②"怎么发现测试 mock 过头了？" → 判据：patch 之后被调链路里还有没有被测逻辑。没有 → 测的是假货（#07 的 stub 坑）。
- ③"数据库该 mock 还是用真的？" → 单元层 fake；集成层真库（或 testcontainers/SQLite）；SQL 方言差异只有真库能抓。
- ④（深）"契约测试 / consumer-driven contract 是什么？" → 服务间依赖用契约测试替代 mock：消费方定义期望，生产方验证，避免两边 mock 各自漂移。

## 4. 断言"没发生"（spy 手法）

### 4.1 怎么用

```python
class FakeKBRepo:
    def __init__(self) -> None:
        self.kbs: dict[UUID, dict] = {}
        self.calls: list[tuple[str, tuple]] = []

    def _log(self, method: str, args: tuple) -> None:
        self.calls.append((method, args))

    def delete(self, kb_id: UUID) -> bool:
        self._log("delete", (kb_id,))
        return self.kbs.pop(kb_id, None) is not None
```

```python
delete_calls = [c for c in repo.calls if c[0] == "delete"]
assert delete_calls == []
```

### 4.2 关键区分（我今天亲手踩的）

| 断言 | 对错 | 原因 |
|---|---|---|
| `assert repo.calls == []`（403 测试里） | ❌ 错 | service 判断权限**必须先 get** 看 owner_id，账本里必有一笔 get |
| `assert _calls_named(repo, "delete") == []` | ✅ 对 | 只断言"该发生的没发生"，不否定必要的读取 |

**原则**：断言"没发生"要**精确到具体方法**；"账本全空"只在 service 完全不触达依赖时成立。

### 4.3 面试问法

**Q：怎么测试"某个操作没有发生"？**
> 30 秒：用 spy——fake 依赖维护一个调用账本，每个方法进来先记一笔（方法名+参数），测试末尾按方法名过滤，断言那一笔不存在。关键是要精确到具体方法：比如"无权删除时 repo.delete 不该被调用"，但不能断言账本全空，因为鉴权前必须先读数据拿 owner_id。

**追问链**：mock 的 `assert_not_called` 也能做 → 但那要求你先 patch，patch 就要求依赖是可替换的（构造注入），顺带考依赖注入；更进一步问"账本记什么"，答方法名+参数+（可选）调用顺序。

## 5. 假测试的四种新形态（第四档 #08 蒸馏）

D2 总结过四种（永真断言 / 镜像断言 / stub 换掉被测逻辑 / try 吞断言）。#08 又补了四种**更隐蔽**的：

| 形态 | 长什么样 | 为什么绿 | 抓法 |
|---|---|---|---|
| **异常类型太宽** | `pytest.raises(AppError, match="不能为空")` | `AppError` 是基类，子类全接得住；match 精确制造"严谨"错觉 | 断言到**具体子类**（`BadRequestError`） |
| **选例不分叉** | offset bug 只测 `page=1` | 两种公式在该输入下结果相同 | 选例必须落在"两种实现会分叉"的输入上 |
| **缺副作用断言** | 只 `raises(ForbiddenError)`，不查数据 | 抛异常和"数据已删"可以同时成立 | 断言副作用：数据还在 / delete 未调用 |
| **账本本身漏记**（零症状） | fake 的 `delete` 忘了 `_log` | 断言"没被调用"永远通过——证据被销毁 | fake 的每个方法都要记账；fake 也是代码 |

### 面试故事素材（真实经历，可讲）

> "我给一个 service 写单元测试，4 个测试全绿。后来做反脆弱验收，把'先删除后鉴权'的 bug 植入进代码，测试照样全绿——因为测试只断言了抛 `ForbiddenError`，没断言数据还在。这件事之后我写测试会多问一句：**这条测试能杀死哪种 bug？** 覆盖率只说明代码被执行过，不说明行为被验证过。"

## 6. 30 秒答案集（高频速答）

1. **测试金字塔** → 按真实度换成本排的三层；单元最多测规则、集成适量测拼装、E2E 最少做冒烟。
2. **unit vs integration** → 按被测边界分；单元替换外部依赖、测规则，集成用真栈测拼装。
3. **mock 边界** → 被测逻辑绝不替换，外部世界才隔离。
4. **fake vs mock** → fake 有真行为（简化实现），mock 行为全是编排假设。
5. **怎么测"没发生"** → spy 账本 + 按方法名过滤断言。
6. **为什么不用 MagicMock** → 任意属性都返回 mock，拼错名字不报错；且断言变镜像。
7. **覆盖率陷阱** → 覆盖率说明"被执行过"，不说明"行为被验证过"。
8. **怎么判断测试有没有用** → 植入 bug 看它会不会红（变异测试思维）。
9. **可测试性怎么来** → 依赖注入 + 分层：service 不 import 框架，构造参数收契约。
10. **fake 与 Protocol 的关系** → 同一契约的第三个实现；有契约才塞得进 fake。

## 8. 今日踩坑实录（我犯的，最有价值）

| 坑 | 症状 | 教训 |
|---|---|---|
| 全凭印象写 `svc.get(...)` / `svc.count(...)` | 8 个测试全红，报错指向 fake 的 create | **写测试前先抄一遍被测类的方法签名**（签名是契约，不能凭记忆） |
| `assert repo.calls == []` 用于 403 场景 | 必红（get 一定发生） | 断言"没发生"要精确到方法 |
| `def _log(self, method, *args)` + `self._log("get", (kb_id,))` | 参数双重包裹 `((kb_id,),)`，断言永假 | `*args` 与传元组不能混用；`_log(method, args: tuple)` |
| fake 用 `uuid4().hex[:8]` | `KBOut.id: UUID` 校验失败 | fake 产出的数据要过得了下游 Pydantic 校验 |
| `_svc_with_kb` 里 `repo.create(owner, repo.create(...))` | create 套 create | 一次调用够了，返回值的类型要看清楚 |

## 9. 闭卷自测（先做，再折叠）

1. Test Double 五兄弟，fake 与 mock 的本质区别一句话。
2. mock 边界的一句话判据。
3. 为什么 fake repo 是分层架构的正当红利？
4. 怎么断言"无权时 delete 没被调用"？为什么不能断言账本全空？
5. `repo or RealRepo()` 有什么坑？
6. 覆盖率 91% 为什么可能什么都抓不住？
7. 一条好测试必须能回答什么问题？
8. 本项目的单元层和集成层各测什么，为什么现阶段"为了快"不成立？

<details><summary>答案</summary>

1. dummy/stub/spy/mock/fake。fake 有自己实现的真实行为，mock 的行为是测试里编排的假设。
2. 被测逻辑本身绝不能替换；慢的/不确定的/有副作用的外部世界才隔离。
3. service 只依赖方法签名契约，构造函数传实现即可；fake 是"为测试而生的契约实现"，W3 双 repo 对拍同理。
4. fake 维护 `calls` 账本，按方法名过滤断言为空。不能断言全空：鉴权前必须先 `get` 读 owner_id。
5. 真值判断：带 `__len__` 且返回 0 的 fake 被当假值，静默换成真 repo，测试测了真实现而不自知。
6. 覆盖率只说明"代码被执行过"，不说明"行为被验证过"——断言太弱（永真/镜像/类型太宽/选例不分叉）时，代码跑过一百次也抓不到 bug。
7. "这条测试能杀死哪种 bug？"——答不出就是假测试。
8. 单元层测业务规则（fake 替代 repo，毫秒级、精确到规则）；集成层测拼装（路由/校验/异常翻译/鉴权）。内存存储下集成测试 0.01s/个，速度不是现阶段理由；理由是定位精度和交互断言，速度红利 W7 接真库后兑现。

</details>

**#08 的核心教训**：能把 bug 找出来 = 代码 review 能力；能说出"测试为什么放过它" = 测试设计能力。面试问"你怎么保证质量"，答案永远在后者。

**下一步要刻意练的**：拿到一条测试先问"它能杀死哪种 bug"，再问"它断言的是结果、副作用，还是两者都有"。
