# W4-D6 质量门禁与反脆弱 · 面试参考版总结

> 主题：怎么证明"这套测试有用"。核心工具是**覆盖率**和**变异测试**两把尺子，
> 核心认知是——**覆盖率度量执行，不度量验证**。

---

## 1. 一句话定义

| 概念 | 一句话 |
|---|---|
| 语句覆盖率 | 有多少行代码被执行过 |
| 分支覆盖率 | 有多少个 if/循环的"每条出路"都被走过 |
| 覆盖率门禁 | 覆盖率低于阈值就让命令以非 0 退出码失败，从而卡住 CI |
| 变异测试 | 故意把源码改坏一小处，看测试会不会红；红=杀死，绿=存活 |
| 变异得分 | 被杀死的变异体 / 全部变异体 |
| flaky test | 同一条测试有时绿有时红，依赖了不受控状态（时间/顺序/网络/随机） |

---

## 2. 为什么存在

### 覆盖率解决什么问题

没有覆盖率时，"测了没测"只能靠感觉。覆盖率把"哪些行从没被执行过"变成行号清单，
让补测试有靶子。它是**最低标准**：连执行都没执行过的代码，一定没被测过。

### 覆盖率为什么不够

因为它只统计"执行"，不统计"断言"。三个真实案例（都发生在自己项目里）：

| 案例 | 覆盖率 | 漏掉的 bug |
|---|---|---|
| `review_04_lexicon.py`（#07） | 91%，6 测全绿 | `unique_words` docstring 承诺忽略大小写，实现没做 |
| `review_05_notes.py`（#08） | 4 测全绿 | `delete` 先删后鉴权 → 无权用户删掉了别人的笔记 |
| `review_07_gateway.py`（#10） | 5 测全绿 | 降级兜底文案被写入缓存 60 秒，服务恢复后仍返回"不可用" |

### 变异测试解决什么问题

它把问题从"这行执行了吗"换成"**这行改坏了，测试会发现吗**"。
只有真正验证了行为的断言才能杀死变异体——永真断言（`is not None`）、
镜像断言（expected 是被测函数自己算的）、stub 换掉被测逻辑，在这里全部现原形。

## 3. 怎么用

### 3.1 覆盖率

```powershell
# 报告 + 缺失行号
pytest --cov --cov-report=term-missing

# HTML 报告（大文件排查好用）
pytest --cov --cov-report=html && start htmlcov/index.html

# 门禁：不达标 → 退出码 1
pytest --cov --cov-fail-under=95

# 关掉覆盖率（跑得快，变异检查/调试时用）
pytest --no-cov
```

配置（`pyproject.toml`，本项目已有）：

```toml
[tool.coverage.run]
source = ["src/kb_service"]
branch = true            # 分支覆盖必须开

[tool.coverage.report]
show_missing = true
skip_covered = true
```

### 3.2 变异测试（手工版，60 行）

```python
MUTANTS = [
    ("src/.../doc_service.py", "offset = (page - 1) * size", "offset = page * size", "分页偏移少减 1"),
]

for path_str, old, new, label in MUTANTS:
    original = path.read_bytes().decode("utf-8")          # ① 备份（字节级）
    try:
        path.write_bytes(original.replace(old, new).encode("utf-8"))   # ② 改坏
        code = run_tests()                                             # ③ 子进程跑测试
    finally:
        path.write_bytes(original.encode("utf-8"))         # ④ 必定还原
```

四个要点：

1. **唯一性检查**：`original.count(old) == 1`，否则变异位置不确定
2. **字节级还原**：`write_text` 在 Windows 会把 `\n` 翻成 `\r\n`，还原时污染全文件行尾
   （症状：`git status` 显示 M，`git diff` 却是空）
3. **子进程跑 pytest**：模块已 import 进 `sys.modules`，同进程再跑用的还是旧代码
4. **`try/finally`**：测试可能崩、你可能 Ctrl+C，只有 `finally` 保证还原

### 3.3 门禁编排

`scripts/check.py`：ruff check → ruff format --check → pytest + `--cov-fail-under=95` →（可选）变异检查。
任何一步失败 → 退出码 1。CI 只调这个脚本，不写新逻辑。

## 4. 底层机制

### 4.1 报告各列在说什么

| 列 | 含义 |
|---|---|
| `Stmts` | 可执行语句数（`def`、注释、空行不算） |
| `Miss` | 一次都没执行的语句数 |
| `Branch` | 岔路口数量（`if`/`for`/`while`/`try` 每条出路算一条） |
| `BrPart` | 岔路口走了，但只走了一条路 |
| `Missing` | 缺失明细；`A->B` 表示"A 跳到 B"这条路没走过（部分分支） |

**先看 TOTAL、再看 per-file 最低、最后看 Missing 行号。**

### 4.2 语句覆盖 vs 分支覆盖（实测）

```python
def describe(code: int) -> str:
    label = "ok"
    if code >= 400:
        label = "error"
    return label
```

只测 `describe(500)`：

```
语句覆盖（无 --branch）：100%
分支覆盖（--branch）   ：86%    Missing: 3->5
```

`label = "ok"` 这行"执行过"（先赋值后被覆盖），但"条件为假"这条路从没走过。
**`describe(200)` 这个最常见的输入，一次都没测。**

### 4.3 退出码为什么是核心

| 命令 | 输出 | 退出码 |
|---|---|---|
| `--cov-fail-under=95`（当前 92.43%） | `FAIL Required test coverage of 95% not reached` | **1** |
| `--cov-fail-under=90` | `Required test coverage of 90% reached` | **0** |

CI 只认退出码。**一个永远不会红的检查 = 没有检查。**

### 4.4 覆盖率为什么不敏感、变异测试为什么敏感（实证）

删掉 `tests/test_split_text.py`（5 个真测试）：

| 指标 | 删前 | 删后 |
|---|---|---|
| TOTAL 覆盖率 | 92.43% | **92%**（几乎不动） |
| 变异得分 | 2/5 | **0/5** |

原因：`DocService.create → _parse_sync → split_text` 这条链被上传接口测试顺带跑到了。
**间接调用也能刷覆盖率，但刷不出断言。**

## 5. 面试问法（真题 + 30 秒答案）

### Q1 你们项目测试覆盖率多少？怎么保证质量？

> "分支覆盖率 96%，CI 里 `--cov-fail-under=95` 硬门禁，不达标流水线直接中断。
> 但我不太信覆盖率——它骗过我两次：一次是 91% 的套件抓不到一个函数没按 docstring 忽略大小写，
> 一次是有三个方法压根没测、被其他高覆盖率文件平均成了 92%。
> 所以我加了变异测试：故意把源码改坏一小处，看测试会不会红。第一次 5 个变异体只杀死 2 个，
> 补测试后 5/5。**覆盖率说明代码被碰过，变异得分说明代码被守住。**"

**追问链**：

- *分支覆盖和语句覆盖区别？* → 语句看行执行，分支看 if 每条路。举例：`if code >= 400` 只测 500 → 语句 100%、分支 50%。
- *为什么覆盖率不能当唯一指标？* → 度量执行不度量验证；`assert x is not None` 能刷满覆盖率。
- *门禁设多少？* → "跳一跳够得着"：略高于现状，逼新代码自带测试。设成现状=没门禁，设 100%=逼人写假测试。
- *怎么防为了达标写垃圾测试？* → code review 看断言质量；变异测试定期跑（成本高，不必每次提交）。
- *变异测试工具有哪些？* → `mutmut`、`cosmic-ray`；Windows 上不稳就手写，60 行足够，好处是每一行都能解释。
- *变异体必须满足什么条件？* → 语法合法、能跑、行为接近原版。语法错误造成的"红"是假杀死。

### Q2 什么是 flaky test？怎么处理？

> "同一条测试有时绿有时红，因为它依赖了不受控状态：真实时间（`sleep` 等过期）、
> 执行顺序（共享全局变量）、网络、随机数。这周我自己踩了两个：TTL 缓存用 `sleep(0.15)` 赌过期，
> 一个测试读上一个测试留下的缓存。处理原则是把不确定性注入成可控的——时间用 freezegun 或注入时钟，
> 外部 HTTP 用 respx 拦在 transport 层，共享状态用 fixture 每次新建。
> 还有一种隐蔽形态：异步测试漏 `await`，测试是绿的，只在 stderr 留一条 RuntimeWarning，
> 所以我把 `-W error::RuntimeWarning` 写进了验收标准。"

**追问链**：

- *怎么发现 flaky？* → 随机顺序跑（`pytest-randomly`）、重复 N 次、CI 记录历史失败率。
- *flaky 为什么比没测试更糟？* → 团队开始忽略红色，测试失去信号价值。
- *顺序依赖怎么根治？* → 每个测试自己造数据自己清；禁止模块级可变单例被共享。
- *漏 await 为什么不变红？* → 协程对象被创建后丢弃，无异常；GC 时抛 RuntimeWarning，默认不升级为错误。
- *覆盖率门禁和 flaky 有关系吗？* → 有：为了凑覆盖率写 `sleep` 型测试，会把 flaky 引进门禁。

### Q3 如果让你设计这个项目的质量门禁，你怎么分层？

> "三层：①提交前 pre-commit 跑 ruff 格式/静态检查，秒级；②CI 每次 push 跑 ruff + pytest + 覆盖率门禁，
> 分钟级；③变异测试和端到端测试定期跑（每晚或发版前），因为成本高。
> 关键原则是 **CI 调的是本地同一个脚本**，不是复写一遍命令——否则本地绿 CI 红，排查成本极高。"

## 6. 30 秒答案集（速答版）

1. **覆盖率门禁怎么实现** → `pytest --cov --cov-fail-under=95`，不达标退出码 1，CI 中断。
2. **语句 vs 分支** → 行执行 vs 路径走全。分支更接近"测过"。
3. **覆盖率三个谎言** → 平均值掩盖短板 / 执行≠验证 / 为覆盖写假测试。
4. **变异测试是什么** → 改坏源码看测试红不红；红=杀死，绿=存活。
5. **变异得分多少算好** → 没有绝对标准；趋势往上、关键路径必须 100%。工业界常用 60~80% 作为及格线。
6. **变异脚本为什么要子进程** → 模块缓存，同进程改文件不生效。
7. **为什么要字节级还原** → Windows 的 `write_text` 会把 `\n` 翻成 `\r\n`。
8. **门禁该设多少** → 略高于现状，随代码质量逐步上调。
9. **CI 的设计原则** → 只调用本地脚本，不写新逻辑。
10. **覆盖率 100% 能上线吗** → 不能作为唯一依据；还要 code review、变异测试、集成/E2E。

## 7. 白板手写靶（必须能默写）

1. `pyproject.toml` 里的 coverage 配置段（`source` / `branch` / `show_missing`）。
2. 一条 `--cov-fail-under` 命令 + 说明失败时退出码。
3. 变异脚本的 `try/finally` 四步骨架（备份 → 改坏 → 跑测试 → 还原）。
4. `scripts/check.py` 的三步编排 + 退出码聚合逻辑。

## 8. 今日踩坑实录（真实、可直接当面试故事）

1. **变异脚本第一版污染行尾**：用 `read_text/write_text`，Windows 把 `\n` 翻成 `\r\n`，
   还原后 `git status` 显示 M、`git diff` 却是空。改用 `read_bytes/write_bytes`。
2. **标题顺序断言在 Linux 会挂**：`list_by_kb` 按 `created_at` 倒序排，而 Windows 3.11 的
   `datetime.now()` 精度只有 15.6ms，连建 5 条文档时间戳全相同、排序"碰巧稳定"；
   Linux 是微秒精度会反序。改为 **spy 断言传给仓储的 `offset`**，与排序无关。
3. **`page=1, size=2` 只断言条数杀不死 offset 变异**（实测）：错误公式返回的仍是 2 条，
   只是内容从 d0,d1 变成 d2,d3。**选例必须落在"两种实现会分叉"的输入上。**
4. **print 不 flush 导致输出乱序**：父进程缓冲、子进程直写终端，日志顺序全乱。
5. **变异脚本必须能失败**：第一版 `return 0` 无论得分多少——接进门禁等于永远 PASS。

## 10. 闭卷自测

**1. 覆盖率和变异测试分别回答什么问题？**

<details><summary>答案</summary>

覆盖率问"这行被执行过吗"；变异测试问"这行被改坏，测试会发现吗"。前者度量执行，后者度量验证。

</details>

**2. 语句 100%、分支 86% 说明什么？**

<details><summary>答案</summary>

所有语句执行过，但有 if/循环的一条路径没走过。例：`if code >= 400: label = "error"` 只测 500 —— `label="ok"` 执行了（被覆盖），但假分支的路径从没走过。

</details>

**3. 门禁不达标时 pytest 退出码是几？为什么重要？**

<details><summary>答案</summary>

1。CI 只认退出码，非 0 中断流水线——门禁的约束力全在这里。注意此时**测试本身是全绿的**，门禁红 ≠ 测试红。

</details>

**4. 变异体"存活"意味着什么？**

<details><summary>答案</summary>

改坏源码后测试仍全绿：这段路径的测试是摆设，或压根没测。每一个存活都对应一条"写了但没起作用"的测试线索。

</details>

**5. 变异脚本为什么必须用字节读写还原？**

<details><summary>答案</summary>

`Path.write_text` 在 Windows 上把 `\n` 翻译成 `\r\n`，还原时改动全文件行尾——`git diff` 空但 `git status` 显示 M，等于悄悄污染仓库。

</details>

**6. 为什么删掉 5 个真测试，覆盖率只掉 0.4 个点？**

<details><summary>答案</summary>

因为 `DocService.create → _parse_sync → split_text` 被上传接口测试间接跑到了。间接调用算覆盖，但不算验证——这正是覆盖率不敏感的原因。

</details>

**7. 如果 mutation 把代码改成语法错误，算不算"杀死"？**

<details><summary>答案</summary>

脚本会记为杀死（退出码非 0），但这是**假杀死**：红的原因是编译失败，不是断言发现行为变化。变异体必须语法合法、能跑。

</details>

**8. 给项目再加一条门禁，你选什么？**

<details><summary>答案</summary>

任一能说清理由即可：单文件覆盖率下限（防平均值掩盖）/ 变异得分门禁（定期跑）/ `-W error::RuntimeWarning`（防漏 await 假绿）/ 测试时长上限（防 sleep 型慢测试回潮）。

</details>
