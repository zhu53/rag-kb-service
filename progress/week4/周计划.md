## 本周主线问题

> **"怎么证明代码是对的？"**
> 测试不是给老师看的作业，是**你下次改代码时兜底的网**。网破没破，只能靠"故意放个 bug 进去看它漏不漏"来验证。

## 验收清单（D7 核销）

- [ ] 能说清 pytest 的执行流程（collect → fixture setup → 运行 → teardown），assert 为什么不用 `assertEqual`
- [ ] fixture 作用域四档（function/class/module/session）与依赖链；conftest.py 的查找/生效规则
- [ ] 参数化：多参数组合 + `ids` + `pytest.param(marks=)`，能把重复用例压成一张表
- [ ] monkeypatch 测环境变量优先级，**测完自动还原**；tmp_path 测文件读写
- [ ] 测试金字塔：能说出本项目哪些逻辑该单元测、哪些必须集成测、哪些绝不能 mock
- [ ] 用 fake repo（不是 MagicMock）写 service 单元测试 —— **W3 的 Protocol 契约在这里兑现红利**
- [ ] async 测试能跑：`AsyncClient(transport=ASGITransport(app))`，且能异步依赖注入
- [ ] freezegun 冻结时间测 token 过期；respx 拦外部 HTTP（或等价 Transport mock）
- [ ] **分支覆盖率：全局 ≥90%，`services/` `repositories/` `core/security.py` ≥95%**
- [ ] **反脆弱验收（主菜）：我往代码里植入 N 个 bug，你的测试必须变红**——漏一个扣一档
- [ ] 12 题闭卷 ≥18

## 第四档安排（本周主题特别适配）

- **#07 假测试套件**：一份全绿、覆盖率很高的测试，但里面全是"永真断言/测实现细节/mock 掉了被测逻辑"——找出哪些测试抓不住 bug
- **#08 变红的理由**：给你一段有 bug 的代码 + 一套"看起来该红却没红"的测试，定位测试本身的缺陷
- **#09 慢与脆**：测试能过但顺序依赖 / 时间依赖 / 共享状态——找出 flaky 源
