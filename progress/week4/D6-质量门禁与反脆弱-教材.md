## §1 五分钟示例：亲手看一眼 70% 长什么样

```powershell
cd kb-service
```

三个观察点，逐个看：

1. **`TOTAL 92%` 是被平均出来的。** 19 个文件 100%、5 个文件 85~96%、1 个文件 70%。平均值掩盖了那个 70%。
2. **`Missing` 列直接给你行号。** 这是覆盖率最实用的地方——它不只告诉你"不够"，还告诉你"缺哪几行"。

## §2 覆盖率在数什么

`coverage.py` 的报告有几列，第一次看会懵。逐个拆：

| 列 | 含义 | 白话 |
|---|---|---|
| `Stmts` | 语句数 | 这个文件有多少条"可执行语句"（`def`、空行、注释不算） |
| `Miss` | 没执行的语句数 | 一次都没跑到的行 |
| `Branch` | 分支数 | 有多少个"岔路口"（`if`/`for`/`while`/`try` 每处 2 条出路起） |
| `BrPart` | 部分分支 | 岔路口走了，但只走了一条路 |
| `Cover` | 综合覆盖率 | `(Stmts - Miss + 已走分支) / (Stmts + Branch)` 之类，不用背公式 |
| `Missing` | 缺失明细 | 具体行号；`A->B` 表示"A 行跳到 B 行"这条路没走过 |

关键概念只有两个：

- **语句覆盖**：这行代码被执行过吗？
- **分支覆盖**：这个 if 的两条路都走过吗？

### 为什么分支覆盖更重要（实测对比）

你的 `pyproject.toml` 里已经开了分支覆盖：

```toml
[tool.coverage.run]
source = ["src/kb_service"]
branch = true
```

关掉它对比一下差别。下面这个 5 行的模块，只测了"错误"那条路：

```python
def describe(code: int) -> str:
    label = "ok"
    if code >= 400:
        label = "error"
    return label
```

```python
def test_error_path():
    assert describe(500) == "error"
```

实测结果（同一份代码、同一个测试，只换开关）：

```
=== 语句覆盖（无 --branch）===
guard.py            5      0   100%

=== 分支覆盖（--branch）===
guard.py            5      0      2      1    86%   3->5
```

**语句覆盖 100%，分支覆盖 86%。** 为什么？因为 `label = "ok"` 这行确实执行了（先赋值再被覆盖），但 `if code >= 400` 为假的那条路（`3->5`，直接跳到 return）从来没走过。

意思是：`describe(200)` 这个最常用的输入，**一次都没测过**。而语句覆盖给了你 100% 的错觉。

> 一句话：**语句覆盖统计"代码碰没碰到"，分支覆盖统计"逻辑走没走全"。** 后者才接近"测过"。

## §3 覆盖率的三个谎言

覆盖率是必要指标，但它有三处会骗人。三个都来自你自己的项目。

### 谎言一：平均值掩盖短板

`TOTAL 92%` 里藏着 `doc_service.py 70%`。一个 100% 的文件能替一个 70% 的文件"还债"。

**对策**：门禁只看 TOTAL 是妥协；真正的做法是盯 per-file 最低的几个。CI 上可以再加一条"任何单文件不得低于 80%"，但先别急着上，本周先做到 TOTAL 达标 + 人工看一遍 `Missing`。

### 谎言二：执行过 ≠ 验证过（你自己踩过）

`review_04_lexicon.py`（第四档 #07）：6 个测试、覆盖率 91%、全绿。里面有个真 bug——`unique_words` 的 docstring 承诺"忽略大小写"，实现没做。**覆盖率 91% 是因为那个函数确实被调用了很多次，但没有一条断言检查过大小写行为。**

`review_05_notes.py`（第四档 #08）：4 个测试全绿，`delete` 先删后鉴权这种事故级 bug 照样活着。

结论：**覆盖率分母是"代码行"，不是"行为"。** 一行 `if row is None: raise` 被执行了，但你有没有验证"此时抛的异常类型对不对"？覆盖率不知道。

### 谎言三：为覆盖而写的测试

```python
def test_create():
    result = svc.create(...)
    assert result is not None      # ← 覆盖率 +1，杀伤力 0
```

这种测试能让数字变好看，但改坏代码它照样绿。**这周你已经见过四种形态了**（永真断言、镜像断言、stub 换掉被测逻辑、异常类型太宽）。

那怎么办？——**换一个问法**。不问"这行执行了吗"，问"把这行改坏了，测试会红吗"。这就是变异测试。

## §4 门禁：让"不达标"变成"过不去"

覆盖率只有变成**门禁**才有约束力。否则它永远是"有空再看"的报告。

`pytest-cov` 提供 `--cov-fail-under`：

```powershell
# 当前总覆盖率 92.43%，要求 95% → 失败
./.venv/Scripts/python.exe -m pytest --cov --cov-fail-under=95 -q
```

```
FAIL Required test coverage of 95% not reached. Total coverage: 92.43%
```

**实测退出码**：

| 命令 | 输出 | pytest 退出码 |
|---|---|---|
| `--cov-fail-under=95` | `FAIL ... not reached` | **1** |
| `--cov-fail-under=90` | `Required test coverage of 90% reached` | **0** |

退出码是关键：CI 只认退出码。**门禁的价值不在于那个百分比，而在于它能在不达标时把流水线卡住。** 一个"永远不会红"的检查等于没有检查。

### 门禁放哪儿

三个层次，从轻到重：

1. **命令行**（今天用这个）：`pytest --cov --cov-fail-under=95`
2. **`addopts`**：写进 `pyproject.toml`，以后每次 `pytest` 自动带。好处是忘不掉，坏处是每次跑都多花零点几秒
3. **CI / pre-commit**：推到远端或提交时自动跑。真正的团队做法

> 注意：`--cov-fail-under` 只管 TOTAL，不管单文件。想管单文件得自己写脚本解析报告——今天不做，知道有这回事即可。

## §5 变异测试：从"执行了吗"到"改坏了能发现吗"

### 思想（一句话）

**故意把源码改坏一点点，跑测试。测试红了 → 这个变异"被杀死"；测试还是绿 → 变异"存活"，说明这条路径的测试是摆设。**

这是对测试套件的测试。覆盖率问"碰没碰到"，变异测试问"有没有守住"。

### 它为什么有效

因为变异体必须"语法合法、能跑、行为接近原版"——只改一个符号、一个边界、一个方向。这种改动**只有真正验证了行为的测试才能发现**。永真断言、镜像断言在这里全部现原形。

### 手工版（60 行，你项目里已经有了）

工业界有 `mutmut`、`cosmic-ray`，但 Windows 上都不太顺。手工版足够，而且**你能看懂每一行**——这一点比工具重要。

`scripts/mutation_check.py` 的核心只有三件事：

```python
MUTANTS = [
    ("src/kb_service/services/doc_service.py",
     "offset = (page - 1) * size",
     "offset = page * size",
     "分页偏移少减 1（第二页开始全错）"),
    ...
]

for path_str, old, new, label in MUTANTS:
    original = path.read_bytes().decode("utf-8")   # ① 备份
    try:
        path.write_bytes(original.replace(old, new).encode("utf-8"))  # ② 改坏
        code = run_tests()                                            # ③ 跑测试
    finally:
        path.write_bytes(original.encode("utf-8"))  # ④ 无论如何都还原
```

四个要点：

- **`count(old) == 1` 的检查**：原文必须在文件里唯一出现，否则变异位置不确定
- **`try/finally` 还原**：哪怕测试崩了、你 Ctrl+C 了，源码也必须还原。`finally` 是唯一可靠的位置
- **`run_tests()` 用子进程**：`pytest` 必须在新进程里跑，否则模块已经被 import 过了，改文件不生效
- **`--no-cov`**：变异检查要跑 N 遍测试，关掉覆盖率提速

> 一个真实的坑（我今天写这脚本时踩的）：`Path.write_text()` 在 Windows 上会把 `\n` 翻译成 `\r\n`，还原时把整个文件的行尾都改了——`git status` 显示文件被修改，但 `git diff` 是空的。**还原必须字节级。** 所以第一版我用 `read_text/write_text`，第二版改成 `read_bytes/write_bytes`。

### 现在跑一遍

```powershell
./.venv/Scripts/python.exe scripts/mutation_check.py
```

当前输出：

```
基线：先确认原始代码是绿的 …… 绿

[存活] 分页偏移少减 1（第二页开始全错）  ← 测试套件没发现
[存活] 删除文档时计数方向反了  ← 测试套件没发现
[杀死] 边界从 <= 放宽成 <（零长度不再拦）
[杀死] 边界漏掉等号（overlap == chunk_size 会死循环风险）
[存活] 空块不再过滤（切出空字符串也塞进结果）  ← 测试套件没发现

变异得分：2/5 = 40%
```

三个存活，逐个读：

- **`offset = page * size`** 存活 → `DocService.list` 分页从第二页起全是错的，而**没有任何测试调用过 `list`**。这和覆盖率报的 `34-37` 缺失是同一个事实，但说法不同：覆盖率说"没跑到"，变异测试说"改坏了也没人管"。
- **`incr_doc_count(..., -1)` → `(..., 1)`** 存活 → 删文档时计数不减反增，没人测 `delete`。
- **`if chunk:` → `if True:`** 存活 → 空白块不再被过滤，切分会产出空字符串块。这个最阴：`split_text` 有 5 个测试，**语句覆盖 100%**，但没有一条测过"窗口里全是空白"的情况。报告里 `81->83` 正是提示。

**这三个存活，就是你今天的作业。** 每杀死一个，你得先想清楚："哪种输入能让这段代码的两种写法表现不同？"——这就是测试设计。

## §6 门禁一键化：`scripts/check.py`

零散的检查命令没人记得住，也没人会每次都跑。所以把检查编成一条命令：

```powershell
./.venv/Scripts/python.exe scripts/check.py              # 格式 + 测试 + 覆盖率
./.venv/Scripts/python.exe scripts/check.py --mutation   # 再加变异检查（约 13 秒，实测）
```

它做三件事，任何一步失败整体返回 1：

```python
COV_FLOOR = 95
checks = [
    ("ruff check",           [..., "ruff", "check", *TARGETS]),
    ("ruff format --check",  [..., "ruff", "format", "--check", *TARGETS]),
    ("pytest + 覆盖率门禁",   [..., "pytest", "--cov", f"--cov-fail-under={COV_FLOOR}"]),
]
```

**当前跑出来的结果是红的**：

```
[PASS] ruff check
[PASS] ruff format --check
[FAIL] pytest + 覆盖率门禁 (95%)
门禁未通过：pytest + 覆盖率门禁 (95%)
```

这不是坏了——**这就是今天的起点**。D6 的任务就是让它变绿。

> 为什么门禁要写成一个脚本，而不是让你背三条命令？
> 因为 **CI 里跑的就是这个脚本**。本地能过、CI 就能过，"我机器上是好的"这个问题从根上消失。

## §8 动手实验（跑之前先猜）

猜错的地方记下来，写进今天的总结。

**实验 1**：把 `scripts/check.py` 里的 `COV_FLOOR` 改成 `99`，跑 `pytest --cov --cov-fail-under=99`。退出码是几？测试本身红了吗？

<details><summary>答案</summary>

退出码 1（`FAIL Required test coverage of 99% not reached`），但 **48 个测试全绿**。覆盖率门禁和测试结果是两套判定：门禁红 ≠ 测试红。

</details>

**实验 2**：把 `mutation_check.py` 里某个 `MUTANTS` 的 `new` 改成一个语法错误的字符串（比如 `"offset = page * size +"`），会发生什么？脚本能还原源码吗？

<details><summary>答案</summary>

`run_tests()` 返回非 0（收集阶段 SyntaxError）→ 变异被记为"杀死"。**但这是假杀死**：测试红不是因为断言发现行为变化，而是因为文件编译不过。所以变异体必须语法合法——这是变异测试的基本要求，也是 `MUTANTS` 手工维护的缺点。`finally` 保证源码照样还原。

</details>

**实验 3**：写一个只测 `list` 的 happy path——`page=1, size=2`，只断言 `len(items) == 2`（库里 5 条）。跑变异脚本，`offset` 那个变异体会死吗？

<details><summary>答案</summary>

**不会死（实测 2/5，与不写这条测试时一样）。**

`page * size` 在 `page=1, size=2` 时算出的 offset 是 **2**（正确是 0），返回的仍然是 **2 条**——只是内容从 `d0, d1` 变成了 `d2, d3`。**只断言条数时，两种实现完全无法区分。**

想杀死它，两条路：①用 `page=2`（正确返回 `d2, d3`，变异后返回空）；②断言具体标题列表（`[d.title for d in items] == ["d0", "d1"]`）。

这是 #08 坑 2「选例不分叉」的第三次现身：**不是断言写错了，是输入选在了"两种实现表现相同"的地方。** 写测试时要问自己：这个输入，能让正确实现和错误实现分开吗？

</details>

**实验 4**：把 `tests/test_split_text.py` 整个移走（改名成 `test_split_text.py.bak`），跑一次 `pytest --cov` 和变异脚本。覆盖率和变异得分各掉多少？

<details><summary>答案（实测数据）</summary>

- **覆盖率**：`TOTAL 92.43% → 92%`（Miss 30→32，BrPart 10→12）——**几乎没动**
- **变异得分**：`2/5 → 0/5`（五个全部存活）

为什么覆盖率不掉？因为 `DocService.create` → `_parse_sync` → `split_text` 这条链会被 `test_kb_api.py` 的上传测试顺带跑到。**间接调用也能算覆盖。**

这就是今天最重要的实证：**删掉 5 个真测试，覆盖率只掉 0.4 个点，杀伤力掉 100%。** 所以别再问"覆盖率够不够"，要问"这些行被守住没有"。

</details>

## §11 面试问法

### Q1：你们项目的测试覆盖率多少？怎么保证质量？

**30 秒版**：
> "后端服务分支覆盖率 96%，CI 里设了 95% 的硬门禁，不达标直接卡住合并。但我不太相信覆盖率——它有两次骗过我：一次是 91% 覆盖率的套件抓不到一个函数没按 docstring 忽略大小写的问题，一次是三个方法压根没测、被其他高覆盖文件平均成了 92%。所以除了覆盖率，我还会做变异测试：故意把源码改坏一小处，看测试会不会红。第一次跑 5 个变异体只杀死 2 个，补测试后到 5 个全杀——那个过程比覆盖率数字更能说明测试有没有用。"

**追问链**：

- *"变异测试和生产环境改代码有什么关系？"* → 它验证的是断言的有效性。能杀死变异体的测试，才可能在真实 bug 出现时报警。
- *"覆盖率为什么不能作为唯一指标？"* → 覆盖率度量"执行"，不度量"验证"。`assert result is not None` 能把覆盖率刷满，但什么都发现不了。
- *"分支覆盖和语句覆盖的区别？"* → 语句看行有没有执行，分支看 if/循环的每条路径有没有走。举例：`if code >= 400: label = "error"` 只测 500，语句 100%、分支 50%。
- *"门禁设在多少合适？"* → 设在"跳一跳够得着"：略高于现状，逼着新代码自带测试。设成现状值等于没有门禁，设成 100% 会逼人写假测试。
- *"你们怎么防止有人为了达标写垃圾测试？"* → code review 时看断言质量；CI 里加变异测试（成本高，通常定期跑而不是每次提交跑）。
- *"为什么本地门禁要写成一个脚本？"* → 保证 CI 跑的和本地跑的是同一套命令，消除环境差异。

### Q2：什么是"脆弱测试"（flaky test）？怎么处理？

**30 秒版**：
> "指同一条测试有时绿有时红，原因是它依赖了不受控的外部状态：真实时间（sleep 等过期）、执行顺序（共享全局变量）、网络、随机数。这周我自己踩过两个：一个 TTL 缓存用 `sleep(0.15)` 赌过期，一个测试读上一个测试留下的缓存。处理原则是——把不确定性注入成可控的：时间用 freezegun 或注入时钟，外部 HTTP 用 respx 拦截，共享状态用 fixture 每次新建。还有一个隐蔽形态：异步测试漏了 `await`，测试是绿的，只在 stderr 留一条 RuntimeWarning，所以我把 `-W error::RuntimeWarning` 加进了验收标准。"

**追问链**：
- *"怎么发现 flaky？"* → 随机顺序跑（`pytest-randomly`）、重复跑 N 次、`-p no:randomly` 对比；CI 上记录历史失败率。
- *"flaky 测试为什么危险？"* → 团队会开始忽略红色，测试就失去信号价值——比没有测试更糟。
- *"顺序依赖怎么根治？"* → 每个测试自己造数据、自己清理；禁止模块级可变单例被测试共享。
- *"漏 await 为什么不变红？"* → 协程对象被创建后丢弃，没有异常；只有 GC 时抛 RuntimeWarning，默认不升级为错误。

## §12 闭卷自测

**1. 一句话解释覆盖率和变异测试的区别。**

<details><summary>答案</summary>

覆盖率问"这行代码被执行过吗"；变异测试问"这行代码被改坏后，测试会发现吗"。前者度量执行，后者度量验证。

</details>

**2. 语句覆盖 100%、分支覆盖 86%，说明什么？举一个具体情形。**

<details><summary>答案</summary>

所有语句都执行过，但至少有一个 if/循环的一条路径没走过。例：`if code >= 400: label = "error"`，只测了 code=500，`label = "ok"` 这行执行了（先赋值）但"条件为假"的路径从没走过。

</details>

**3. `--cov-fail-under=95` 不达标时，pytest 的退出码是几？为什么这个数字重要？**

<details><summary>答案</summary>

1。CI 只认退出码，非 0 就中断流水线——门禁的约束力全在这个数字上。

</details>

**4. 变异测试里"杀死"和"存活"分别意味着什么？**

<details><summary>答案</summary>

杀死 = 改坏源码后测试变红，说明有断言守住了这段行为；存活 = 测试仍然全绿，说明这段路径的测试是摆设（或者根本没测）。

</details>

**5. 为什么变异脚本必须用 `try/finally` 还原？**

<details><summary>答案</summary>

因为测试可能抛异常、你可能 Ctrl+C。只有 `finally` 能保证无论发生什么源码都被还原，否则仓库带着被改坏的代码继续开发。

</details>

**6. 为什么变异检查要用子进程跑 pytest？**

<details><summary>答案</summary>

Python 模块 import 一次就缓存在 `sys.modules` 里了。同进程再跑测试用的还是旧代码，改文件不生效。必须新进程重新 import。

</details>

**7. 有 100% 覆盖率的测试套件，还可能漏掉什么？举你项目里的真实例子。**

<details><summary>答案</summary>

漏掉"行为是否符合约定"。例：`review_04_lexicon.py` 覆盖率 91%，`unique_words` 的 docstring 说忽略大小写、实现没做，6 个测试全绿。因为覆盖率只统计行被执行，不检查断言内容。

</details>

**8. 如果让你给这个项目再加一条门禁，你会加什么？为什么？**

<details><summary>答案</summary>

参考方向（任一，能说清理由即可）：①单文件覆盖率下限（防平均值掩盖）；②变异得分门禁（定期跑，不每次提交）；③`-W error::RuntimeWarning`（防漏 await 的假绿）；④测试执行时间上限（防 sleep 型慢测试回潮）。

</details>
