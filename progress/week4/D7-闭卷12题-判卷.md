## 逐题标准答案

### Q1 · pytest 的一生

**阶段顺序**：

1. **启动**：解析命令行 → 确定 rootdir / ini → 加载插件（`-p`、entry points）→ **加载 conftest.py**（rootdir 向下逐层）
2. **收集（collect）**：扫描 `test_*.py` / `*_test.py` → 导入模块（此时 assert 已被重写）→ 生成 item 树
3. **执行**：对每个 item 走 `setup → call → teardown` 三阶段；fixture 在 setup 阶段按依赖拓扑求解
4. **报告**：汇总 passed / failed / error / skipped / xfail，写 exit code

**裸 assert 的原理**：pytest 用 import hook 在**导入期**把测试模块和 conftest 里的 `assert` AST 重写成"带表达式解释"的形式，失败时能打印 `assert 3 == 4` 左右两边的实际值和中间子表达式。

**代价**：

- **只有被 pytest 收集的模块才被重写**——`helpers.py` 里的 assert 拿不到详细 diff；
- 依赖 pytest 的导入器，直接 `python test_x.py` 跑失去重写（断言仍生效但信息退化）；
- 有导入开销（模块级重写 + 编译缓存 `.pyc` 之外的一层）。

### Q2 · fixture 洋葱

**① 顺序**
```
open db
new repo on DB
drop repo
new repo on DB
drop repo
close db
```

**② `db` 改 function**：每个测试各一轮
```
open db → new repo on DB → drop repo → close db   (test_a)
open db → new repo on DB → drop repo → close db   (test_b)
```

**③ session 不能依赖 function**：`ScopeMismatch`。长生命周期对象不能持有短生命周期对象——session 结束时 function 级实例早已销毁。

**④ conftest 三规则**：

- **位置**：放在 rootdir 到测试文件之间的任意目录（通常在 `tests/` 或仓库根）
- **查找方向**：从测试文件所在目录**向上**逐层找，**全部加载**（不是找到第一个就停）；rootdir 之上不找
- **生效范围**：所在目录及**所有子目录**；越靠近测试文件的越后加载（同名 fixture 覆盖外层）

### Q3 · 参数化

```python
@pytest.mark.parametrize(
    "text,chunk_size,overlap,expect",
    [
        pytest.param("abcdef", 0, 50, "chunk_size 必须大于 0", id="zero_chunk"),
        pytest.param("abcdef", 3, 3, "overlap 必须小于 chunk_size", id="overlap_too_big"),
        pytest.param("abc", 400, 50, ["abc"], id="short_text"),
    ],
)
def test_split(text, chunk_size, overlap, expect):
    if isinstance(expect, str):
        with pytest.raises(ValueError, match=expect):
            split_text(text, chunk_size=chunk_size, overlap=overlap)
    else:
        assert split_text(text, chunk_size=chunk_size, overlap=overlap) == expect
```

（用 `str` 而不是 `ValueError` 实例做哨兵，避免每次收集都构造异常对象；`match` 是**正则**，含特殊字符要 `re.escape`。）

**`ids=`**：参数是元组/对象、报告里的 `test_x[a-b-c]` 不可读时，给每个 case 起名。

**`pytest.param(marks=...)`**：给单个 case 挂标记。`xfail` 的语义是**记录已知缺陷/未实现功能**，不是"绕过红叉"——默认 `strict=False`，失败记 xfail、**意外通过记 xpass（也不红）**，所以能用它把真 bug 安静地盖住；要"意外通过就报错"必须 `strict=True`。

### Q4 · monkeypatch 与配置测试

```python
def test_secret_from_env(monkeypatch):
    monkeypatch.setenv("SECRET_KEY", "x" * 20)
    get_settings.cache_clear()                      # ← 关键
    assert get_settings().secret_key == "x" * 20
    assert get_settings() is get_settings()         # 证明确实走了缓存路径
```

**② 谁负责还原**：`monkeypatch` fixture 自己。它把每次改动登记在账本里，在 **teardown** 阶段逐个回滚（`setenv` → 恢复旧值或删键，`setattr` → 还原原对象）。测试中途抛异常也会走 teardown，所以照样还原。

**③ 为什么必须落磁盘**：`.env` 的优先级链是 `环境变量 > .env > 默认值`，其中"读 `.env`"是**磁盘文件解析**行为，纯内存造不出来。用 `tmp_path`：

```python
def test_env_file_priority(monkeypatch, tmp_path):
    env_file = tmp_path / ".env"
    env_file.write_text("SECRET_KEY=" + "d" * 20, encoding="utf-8")
    monkeypatch.delenv("SECRET_KEY", raising=False)   # ← 不清就永远读不到 .env
    get_settings.cache_clear()
    assert get_settings(_env_file=env_file).secret_key == "d" * 20
```

两处易错：`_env_file` 要走构造参数（`Settings(_env_file=...)` 或 `get_settings` 内部能接收）；**测 `.env` 前必须清掉同名环境变量**，否则优先级链第一层就把你挡住了。

### Q5 · 金字塔的诚实版

**① 三例**

- **该写单元测试**：`split_text` 的切分边界（`chunk_size<=0`、`overlap>=chunk_size`、空块过滤）——纯函数，零依赖，跑得极快。
- **必须集成测试**：`POST /api/v1/chat` 的完整链路（路由 → 鉴权依赖 → service → store → SSE 输出）——层间契约只有拼起来才能验。
- **绝不能用替身换掉**：**被测的那段逻辑本身**。比如测 `DocService.delete` 时，`DocService.delete` 绝不能 patch；`KBService.get_or_403` 也不能 patch 掉（它就是"先鉴权后删除"这条约束的一部分）。

> 注意：`get_current_user_id` 这类**外部输入源**是可以替换的（D4 就在用 `dependency_overrides` 换它）——"鉴权依赖"和"鉴权逻辑"不是一回事。

**② 金字塔在"集成也不慢"时还剩什么**

1. **定位精度**：单测红了 = 直接知道 `split_text` 坏了；集成红了 = 要一层层往下查才知道坏在哪。
2. **能断言"没发生"**：单测能看到 `repo.delete` 有没有被调用（spy 账本）；集成测试只能看 HTTP 响应，看不见内部协作——"先删后鉴权"这类 bug 它抓不到。

（速度红利在内存存储阶段确实不值钱，W7 换真库后才兑现。这一点在 D3 教材里就写明过。）

### Q6 · fake vs mock

**① 本质区别**：**行为是真是假**。fake 有真实业务逻辑（dict 存取真的会存、真的会取，只是没走 SQL）；mock 的行为**全是你在测试里假设的**——你没设的调用它返回一个 Mock 对象、你没设的属性它自动生成，所以它永远只会证明"你假设的东西"，不会证明"真实世界的样子"。

**② 四个依赖**

| 依赖 | 判定 | 理由 |
|---|---|---|
| `DocRepository` | **fake** | 接口简单、可内存实现，且真实行为（存了能取回）能造出来 |
| `datetime.now()` | **注入时钟 / freezegun** | 不可控；注入是"设计可测"，freezegun 是"外部拨表" |
| 外部 LLM API | **respx（传输层拦截）** | 慢、贵、不确定、可能挂 |
| 被测的 `DocService` | **绝不替换** | 它就是被测对象，替换了等于测自己 |

### Q7 · 断言"没发生"

```python
def test_delete_forbidden_does_not_delete(monkeypatch):
    repo = SpyDocRepo()                       # 带 calls 账本
    svc = DocService(repo=repo, kb_repo=KBRepository())
    kb = svc.kb_service.repo.create(ALICE, KBCreate(name="库"))
    doc = repo.create(kb["id"], DocCreate(title="t", content="c"))
    repo.calls.clear()                        # setup 的调用不算

    with pytest.raises(ForbiddenError):
        svc.delete(doc["id"], user_id=BOB)

    # 交互断言（更强）+ 状态断言（更直白），两个都写
    assert [c for c in repo.calls if c[0] == "delete"] == []
    assert repo.get(doc["id"]) is not None
```

**为什么 `assert repo.calls == []` 是错的**：`DocService.delete` 必须先 `repo.get(doc_id)` 拿到 `row["kb_id"]`，才能判断"这个库是不是 BOB 的"。账本里**必然有一笔 get**。403 拦的是"get 之后的操作"，不是"不读数据"。

### Q9 · 为什么不直接用 TestClient

**① 挡住的三件事**（失去的**能力**，不是实现细节）：

1. 不能直接 `await` 你的 async service 函数（`TestClient` 的调用是同步的，测试体里拿不到运行中的 loop）；
2. 不能用 **async fixture**（需要一个持续存在的事件循环）；
3. 不能做**异步依赖替换**（`dependency_overrides` 里塞 async 依赖时行为不可控）。

**② ASGITransport**：在**进程内**按 ASGI 协议直接调用 app 对象，不开端口、不走 TCP、不启 uvicorn。请求/响应仍是真实的 ASGI 生命周期。

**③ 骨架**（见上文 Q9 标准答案代码块）。

**④ 异步的绿为何更不可信 + 怎么防**：协程不 `await` 就**根本不执行**，而 Python 只发一条 `RuntimeWarning`，测试照样绿。命令层面防：`pytest -W error::RuntimeWarning`（把未 await 升级为错误），CI 门禁里固定带上。`--strict-markers` 与此无关（那是检查 marker 拼写）。

### Q10 · 不可控的世界

**① 拦截层**

- **freezegun**：替换 `datetime` / `time` 模块里的取时函数 → 拦住"时间不可控"
- **respx**：挂到 **httpx 的 Transport 层** → 拦住"网络不可控"（连 DNS 都不出）

**② 红线**

- **freezegun**：只影响 Python 层，管不到数据库的 `NOW()`、管不到系统时间；别指望用它测"真实并发下的超时"。
- **respx**：**它不会告诉你"注册了却没被调用"的路由**——实测 0.23.1 下即使 `assert_all_called=True` 也不报。想证明请求真发出了，必须自己 `assert route.called`。另外路由别写 `respx.route(host=...)` 一把抓（#10 头号坑：掩盖了 `/v1/chat` 的路径错误）。

**③ 关注点分离**：红了要能**立刻定位**。请求组装和响应解析挤在一个测试里，红一次你不知道是拼装错还是解析错；拆开后各有各的红，指向明确。（不是"会掩盖缺陷"——两处都断言的话缺陷反而更容易被发现，问题是定位成本。）

### Q11 · 覆盖率

**① 三个谎言**

1. **平均值掩盖短板**：19 个 100% 的文件把 `doc_service` 的 70% 平均成 92%，看总数以为很健康。
2. **执行 ≠ 验证**：#07 的 91% 覆盖率套件抓不住一个 spec 违反；#08 的 4 个测试全绿却放过"先删后鉴权"。
3. **为覆盖而写的测试**：`assert result is not None` 能把行数刷满，杀伤力为零。

**② 语句 100% / 分支 86% 漏了什么**

```python
def describe(code: int) -> str:
    label = "ok"
    if code >= 400:      # 只测了 500
        label = "error"
    return label
```
三条语句全执行（100%），但 `if` 的**假分支**（`code < 400` 那条边）从没走过 → 分支覆盖 86%，`Missing` 列显示 `3->5`。

**③ 实测数字**

> 移走 `tests/test_split_text.py`：覆盖率 **92.43% → 92%**（仅 -0.4pt），变异得分 **2/5 → 0/5**（-100%）。

### Q12 · 门禁与那次 CI 事故

**① 变异三词**

- **变异体**：把源码改一个算子/边界/布尔值得到的一份"坏代码"
- **杀死**：加上这个变异体后测试变红 → 说明测试能感知这处行为变化
- **存活**：加上变异体后测试仍然绿 → 说明这处行为**没人在看**

存活说明什么：该路径的测试是"执行过但没验证过"（或压根没测）。补什么：**一条能区分新旧行为的断言**（选落在"两种实现会分叉"的输入上）——不是加覆盖率，是加断言。

**② CI 红叉**

根因链：

```
.env 在 .gitignore 第 9 行、从未入库
  → GitHub 上没有这个文件
    → tests/conftest.py 导入 create_app
      → main.py 模块级 app = create_app()
        → get_settings() → ValidationError: secret_key Field required
          → conftest 加载失败 → 一条测试都没收集到
```

**证据**：CI 的 Quality gate 只跑 **3 秒**（本地变异检查要 13 秒）——极早崩，不是"跑完发现红"。

**为什么不能在 `ci.yml` 里加 `SECRET_KEY`**：那只按绿这一次。任何新同事 clone 下来、没建 `.env`，本地 `pytest` 一样炸。病是「**测试套件不自包含**」——它依赖了机器上碰巧存在的文件。得在测试侧治：

```python
# kb-service/conftest.py（rootdir 级，比 tests/conftest.py 更早加载）
import os
os.environ.setdefault("SECRET_KEY", "test-secret-key-0123456789")
```

用 `setdefault`：真提供了密钥时以真值为准。
