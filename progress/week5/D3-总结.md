## 二、逐个知识点讲透

### 1. `dict[str, Any]` 是类型黑洞，不是"没类型"

**一句话定义**：`dict[str, Any]` 声称"键是字符串、值是任意类型"，实际上它对**键的集合和每个键的类型都不作任何保证**——写入方和读取方可以各自理解一套结构，谁也不报错。

**为什么存在**（没有严格类型时的现实）：早期快速开发时，把 ORM 行、JSON 响应、日志字段都塞进同一个 `dict` 最省事，mypy 也不会拦（`Any` 会使一切检查短路）。代价是**结构信息只存在于人的脑子里**，一旦两个人的理解不一致，编译器帮不上任何忙。今天这个项目支付的就是这个代价：`store` 里 `created_at` 同时存在 `datetime` 和 `str` 两种值，四周没有任何提示。

**怎么用**（本项目实测的潜伏 bug）：

```python
# kb_repo.create —— 真实 repo 放的是 datetime 对象
now = store.now()
row: KBRow = {"id": ..., "created_at": now, "updated_at": now, ...}

# tests/test_rag_async.py:109 —— 集成测试自己塞数据，塞的是字符串
now = datetime.now(UTC).isoformat()      # ← str
store.kbs[kb_id] = {"created_at": now, ...}
```

改成 `KBRow` 后 mypy 立刻给出 4 个：

```
tests\test_rag_async.py:111: error: Incompatible types
  (expression has type "str", TypedDict item "created_at" has type "datetime")  [typeddict-item]
```

**底层机制**：mypy 对 `dict[str, Any]` 的处理是"元素访问表达式类型为 `Any`"，而 `Any` 与任何类型都双向兼容，于是 `r["created_at"]` 既可以是 `datetime` 也可以是 `str`，任何后续操作都合法。**`Any` 不是"未知类型"，是"免检通行证"**——它消掉的不只是报错，还有报错本来能提供的定位信息。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 `dict[str, Any]` 当"暂时没写类型" | 以为补类型只是加注释 | 它是主动放弃检查；改 TypedDict 时一定会有报错暴露出来 |
| 2 | 用 `# type: ignore` 压掉 `typeddict-item` | 报错消失，两种类型继续共存 | 报错是资产：它指出"同一个键有两种类型"，先判断哪个对 |
| 3 | 看到 `Any` 就全线消灭 | 日志字段、JWT payload 被硬造类型 | 三分类：行结构→TypedDict、值域→Literal、真任意→保留并写理由 |
| 4 | 以为 pydantic 已经兜住了 | 测试全绿就以为类型一致 | pydantic 的宽松解析会**掩盖**类型错配（`str → datetime` 自动转），只有静态检查能提前发现 |

**面试问法**
> *"你怎么看 Python 里的 `Any`？项目里怎么治理？"*
> 30 秒版：`Any` 不是"不知道类型"，是"免检"——它让双向赋值都合法，等于把结构信息从代码里删掉。治理上我按三分类走：行结构用 TypedDict 点名每个键，值域用 Literal 或枚举钉死，真正动态的（日志字段、JWT payload）保留 Any 但必须写清理由。判断标准是"改它能不能暴露真 bug"——我们项目把 store 行改 TypedDict 后立刻暴露了测试塞字符串、repo 放 datetime 的错配。

**追问链**
→ *"你怎么保证改了不会引入新问题？"* 先小步：一次只换一个模块（我是 store 行 → repo → service → fakes → 测试），每步跑 mypy + pytest，报错数就是进度条。改完再跑覆盖率与变异检查，确认测试没被削弱。
→ *"如果第三方库返回的就是裸 dict，你怎么办？"* 在边界处收窄：要么用 pydantic 校验（`Model.model_validate(raw)`），要么写一个 `from_api(raw: dict[str, Any]) -> Row` 的转换函数，把 `Any` 关在函数内部，出了函数就是精确类型。
→ *"线上真出了这种类型错配，怎么发现？"* 静态检查抓不到运行期数据时靠契约测试（用真实返回样本跑一遍转换）+ 埋点校验（关键字段 `isinstance` 断言，失败上报而不是崩）；这也是为什么"边界处校验"比"到处 cast"可靠。

### 2. `TypedDict` 的本质：静态契约，运行时就是 `dict`

**一句话定义**：`TypedDict` 是给"固定键集合的 dict"写的**静态类型声明**，运行时不产生新类型——构造出来还是普通 `dict`。

**为什么存在**：`dict[str, Any]` 无法表达"这个 dict 一定有这 7 个键、每个键是什么类型"。用一个类来表达又太重（要写 `__init__`、要序列化、每次读写都要构造对象），而存储层的行本来就是裸 dict——TypedDict 正好填这个空档：**静态可检查，运行时零成本**。

**怎么用**（本项目的 `rows.py`，实测输出在后面）：

```python
class KBRow(TypedDict):
    """kb_service.store 里一行知识库的结构。"""

    id: UUID
    owner_id: UUID
    name: str
    description: str | None
    doc_count: int
    created_at: datetime
    updated_at: datetime
```

实测（Python 3.11）：

```
MRO: (<class '__main__.Row'>, <class 'dict'>, <class 'object'>)
required: frozenset({'id', 'note'})  optional: frozenset()
构造出来的类型: dict
isinstance 报错: TypedDict does not support instance and class checks
```

**底层机制**：`TypedDict` 类只承载 `__annotations__`（字段声明）、`__required_keys__` / `__optional_keys__`（必备/可选键集合，`total=False` 影响的就是后者），**它本身是 `dict` 的子类但没有任何实例状态**。所以：
- `Row(id="1")` 返回的是 `dict`，`type()` 是 `dict` 不是 `Row`
- `isinstance` 无法工作——运行时没有"这个 dict 是不是 Row"的信息，Python 选择直接抛 `TypeError` 而不是给个不可靠的答案
- 所有检查都在 mypy/IDE 里完成，**运行期零成本**（这也是它适合存储层的原因）

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 TypedDict 当类用：`isinstance` / 加方法 | mypy `[misc]` + 运行时 `TypeError` 双杀 | 它运行时就是 dict；要判断结构就写显式键检查函数 |
| 2 | 以为构造会校验 | `KBRow(id=1)` 传错类型运行时不报错 | 构造不校验，只有静态检查；外部数据走 pydantic |
| 3 | 在 TypedDict 里写 `def method` | 运行时能调，但类型系统不认 | 行为放模块级函数（`summary_of(e)` 而不是 `e.summary()`） |
| 4 | 用 `total=False` 的类当"可选行"到处传 | 后续 `[]` 取值可能 `KeyError` | 可选性要在**消费点**处理（`.get()`），不是靠声明 |

**面试问法**
> *"TypedDict 和 dataclass 有什么区别？"*
> 30 秒版：TypedDict 只是静态声明，运行时就是 dict，零开销、天然可 JSON 序列化，适合"存储/传输层的行"；dataclass 是真类，有实例、能带方法、运行时占对象开销，适合领域对象。判据是"这个东西要不要在运行时存在"——要行为用 dataclass，只要结构用 TypedDict。

**追问链**
→ *"TypedDict 能在运行时校验数据吗？"* 不能。它没有 `__init__` 校验逻辑，构造、赋值都不检查。要校验就得上 pydantic（`model_validate`）或手写校验函数——这也是"静态契约"和"运行时守卫"的分工。
→ *"那 `isinstance(x, MyTypedDict)` 为什么不行？"* 因为 `TypedDict` 类不是真实类型标记，运行时数据就是 `dict`，没有任何标记能区分"这是 Row 还是 Doc"。硬要判断只能逐键检查（`all(k in x for k in Row.__required_keys__)`），而且只能判"键齐不齐"，判不了类型。
→ *"线上收到一个 JSON，怎么安全变成 TypedDict？"* 边界处先过 pydantic 模型（类型 + 约束校验），再 `model_dump()` 出来的 dict 才是可信的 TypedDict；直接 `cast` 等于把校验责任扔给运气。

### 3. `TypedDict` vs pydantic vs dataclass 选型

**一句话定义**：三者分别对应"只要静态结构"、"要运行时校验 + 序列化"、"要运行时对象 + 行为"三种需求。

**为什么存在**：同一个"数据形状"在不同层有不同要求——HTTP 边界要校验和文档（pydantic），存储层要零成本和可序列化（TypedDict），领域层要方法和不变量（dataclass）。用一种打天下必然在某处付额外代价：用 pydantic 当存储行，每次读写都要 validate/dump 仪式；用 TypedDict 当 API 入参，非法请求会直接进业务逻辑。

**怎么用**（本项目的实际分工，两边都真实存在）：

```python
# 边界层：pydantic —— 校验、默认值、OpenAPI 文档
class KBCreate(BaseModel):
    name: str = Field(min_length=1, max_length=64)
    description: str | None = None

# 存储层：TypedDict —— 零成本、可直接进 dict store
class KBRow(TypedDict):
    id: UUID
    owner_id: UUID
    name: str
    ...

# 两者之间的转换是显式的、单向的
row: KBRow = {"id": uuid4(), "owner_id": owner_id, "name": data.name, ...}
```

**底层机制**：pydantic v2 的核心校验在 Rust 侧（`pydantic-core`），构造模型时逐字段跑类型 + 约束，失败抛 `ValidationError`；`model_dump()` 再序列化回 dict。TypedDict 没有任何运行时动作。dataclass 由 `@dataclass` 生成 `__init__` / `__repr__` / `__eq__`，有真实实例开销。**三者的成本差在"每次数据经过"时累积**——高频存储读写用 pydantic 会明显拖慢，而 API 入参一天几千次无所谓。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 store 行改成 pydantic 模型 | 每次读写都 validate/dump，代码里到处 `.model_dump()` | 离存储近用 TypedDict，校验只放在入口 |
| 2 | 用 TypedDict 当 API 入参 | 非法请求直穿业务层，报错位置很深 | 入参永远 pydantic，出参可用 TypedDict + `response_model` |
| 3 | 三层都定义一遍同名字段 | 加字段要改三处，容易漏 | schema（边界）/ row（存储）各一份，领域对象能省则省 |
| 4 | 以为 `response_model` 会改返回值 | 返回 dict 被过滤/转换，测试断言对不上 | `response_model` 是出参校验 + 文档，字段不全会报错，属于设计而不是装饰 |

**面试问法**
> *"FastAPI 项目里，你会用 pydantic 模型还是 TypedDict 表示数据？"*
> 30 秒版：分边界。API 入参出参用 pydantic——要校验、要默认值、要 OpenAPI 文档；存储层和内部传参用 TypedDict——零运行时成本、可直接进 dict/JSON。判据是"这份数据要不要在运行时被校验"，不是"哪个更现代"。

**追问链**
→ *"pydantic 校验会不会成为性能瓶颈？"* 入口层不会（QPS 几千级），但放热路径会——v2 有 Rust 核心，单次校验微秒级，可高频循环里累积明显；所以仓储层不该有它。
→ *"出参用 `response_model` 有什么坑？"* 它会把返回值**过滤/转换**成模型形状：字段少了报错、多了被丢掉、类型不符报错。好处是契约被强制，坏处是调试时"我明明返回了"却看不到——排查要看 `response_model_exclude_unset` 这类开关。
→ *"如果一个 dict 既要在 API 出参、又要存库，你怎么避免两套结构漂移？"* 让 row 成为唯一事实源，出参模型从 row 派生（显式转换函数 + 一条测试断言"字段集合一致"）；或者反过来——但必须有测试盯住两者，否则一定漂移。

### 4. 类型兼容：字面量逐键查、变量查兼容、TypedDict 之间不能互赋

**一句话定义**：mypy 对 `dict` 字面量会**逐键**对照 TypedDict 检查（多键少键都报），对变量只检查整体类型兼容性；而两个不同的 TypedDict 之间**不因为字段相同就互相可赋**。

**为什么存在**：字面量写出来时，编译器看得见每个键，能给出精确诊断（"缺 `created_at`"比"类型不匹配"有用得多）。但对变量，编译器只知道它的声明类型，无法追溯里面到底有哪些键——所以只能按声明类型判兼容。这条规则解释了今天所有的"看起来矛盾"的报错。

**怎么用**（三条实测结论）：

```python
# ① 字面量：逐键检查（多键/少键/类型错都报）
row: KBRow = {"id": uuid4(), "owner_id": owner_id, "name": "x"}
#    error: Missing keys ("description", "doc_count", "created_at", "updated_at")

# ② dict[str, Any] 变量传 TypedDict 参数：被拦
raw: dict[str, Any] = {"doc_id": "d-1", "title": "ok"}
add(raw)      # error: Argument 1 has incompatible type "dict[str, Any]"; expected "Entry"

# ③ 两个 TypedDict 之间赋值：不因为"字段覆盖"就通过
e: EnrichedEntry = make_entry("d-1", "未补摘要")
#    error: Incompatible types in assignment
#    (expression has type "IndexEntry", variable has type "EnrichedEntry")
```

**底层机制**：TypedDict 的兼容规则是**名义式**的（不是 Protocol 那种结构式）：mypy 认为两个不同的 TypedDict 类型没有子类型关系，除非显式子类化（`class EnrichedEntry(IndexEntry, total=False)`）。所以 `IndexEntry` 赋给 `EnrichedEntry` 不行——即使 `EnrichedEntry` 的额外键全是可选的。这条和 D2 学的 Protocol 形成对照：**Protocol 看形状，TypedDict 看名字**。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 TypedDict 之间是结构化兼容 | 想不通"字段明明够"为什么不给赋 | TypedDict 名义式；用 `{**e, "summary": s}` 显式构造新行 |
| 2 | 以为变量传参也逐键查 | 想不通 `dict[str, Any]` 为什么被拦 | 字面量逐键、变量看声明；想传变量就先转成字面量或精确类型 |
| 3 | 给 TypedDict 造"部分行"塞 store | `Missing keys (...)`，一长串键名 | 行的完整性是存储契约；测试也要造完整行（用工厂函数） |
| 4 | 用 `cast` 绕"命名不兼容" | 报错消失，运行期仍在传错结构 | 显式构造（`{**base, ...}`）或调整类型层级，cast 只留给表达力边界 |

**面试问法**
> *"Python 的 TypedDict 是结构化类型还是名义类型？"*
> 30 秒版：名义式。两个字段完全相同的 TypedDict 也不能互相赋值，除非有继承关系；这和 Protocol 正好相反——Protocol 只看形状。所以用 TypedDict 表达"同一份数据的不同视图"时，要么显式继承，要么显式构造新 dict。

**追问链**
→ *"为什么 mypy 对字面量能给精确报错，对变量不行？"* 字面量的键在 AST 里全可见，可以逐个比对 `__required_keys__`；变量只剩声明类型，`dict[str, Any]` 里面是什么编译器不知道，所以只能按"dict 不能当 TypedDict 用"拒绝。
→ *"那 `{**e, "summary": s}` 为什么能过？"* 因为它是字面量表达式，mypy 能推导出结果包含 e 的所有键 + summary，正好满足 `EnrichedEntry`；这也是"显式构造"比 cast 好的原因——类型信息是**算出来的**，不是担保的。
→ *"生产代码里 TypedDict 视图多了会不会很难维护？"* 会，所以视图要少且有明确边界（读模型 / 写模型两种足够）；如果发现要为同一行维护 4、5 个视图，说明该上 dataclass 或 pydantic 了——类型工具的选择要跟着复杂度走。

### 5. `row.update(payload)`：类型系统的表达力边界与 cast 登记制

**一句话定义**：给 TypedDict 合并一个任意 `dict`（如 `payload = data.model_dump(exclude_unset=True)`）在类型系统里**无法被证明安全**，只能通过 `cast` 局部降级来表达"我知道得比编译器多"。

**为什么存在**：`update` 的签名要求参数是"键全可选的同名字典"，而 `dict[str, Any]` 可能带来声明之外的键——一旦允许，TypedDict 的"键集合确定"这个唯一保证就破了。所以类型系统必须拒绝。但业务上这个合并是合法的（键集合由 `KBUpdate` 决定），于是产生一个**表达力缺口**：正确代码写不出来。

**怎么用**（三种解法实测，只有一种全绿）：

```python
# ① 逐键赋值 —— mypy 报 "TypedDict key must be a string literal"
for k, v in payload.items():
    row[k] = v            # k 是变量，不是字面量

# ② |= 运算符 —— 同 update，Argument 1 has incompatible type
row |= payload

# ③ cast 局部降级 —— 唯一通过
cast("dict[str, Any]", row).update(payload)
```

**底层机制**：`cast` 是**纯静态声明**，编译后完全消失（`dis` 里看不到任何指令）；它只是告诉 mypy"把这个表达式当成另一个类型"，运行时不做任何检查。所以 `cast("dict[str, Any]", row)` 到期是同一个 `row` 对象，`update` 正常执行，`row` 的静态类型仍是 `KBRow`——**这就是"局部降级"的含义：只在这一个表达式上放弃检查，不污染变量**。相比之下 `row2 = cast(...)` 再把 `row2` 传出去，就等于把降级扩散了。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `# type: ignore` 代替 cast | 报错消失，但"为什么安全"没有记录 | cast 在代码里可见、可搜索、可登记；ignore 是黑洞 |
| 2 | cast 之后把结果赋给新变量继续用 | 降级范围扩散，后面全是 Any | 只在表达式上 cast，不落变量 |
| 3 | 用 cast 掩盖"没校验"（如 `cast("Status", raw)`） | 脏值静默进系统 | cast 只用于"我确实知道得更多"；不确定就先校验 |
| 4 | 以为 `model_dump(exclude_unset=True)` 已保证键合法 | PATCH 语义下确实合法，但没人写下来 | 在 cast 上一行写注释 + 在逃生口清单登记删除条件 |

**面试问法**
> *"你项目里用 `cast` 吗？什么时候用？"*
> 30 秒版：用，但有登记制。只用在"类型系统表达力不够、但我能证明安全"的地方——比如给 TypedDict 合并一个由 pydantic 模型 dump 出来的 payload，编译器无法证明键集合合法，代码里必须局部降级。每处 cast 都写理由和删除条件，能删就删；用它掩盖"没做校验"是滥用。

**追问链**
→ *"`cast` 和 `assert isinstance(...)` 有什么区别？"* cast 零开销零检查，纯声明；assert 有运行时开销但真的收窄——而且 `assert` 在 `-O` 下会被去掉，不能当业务校验用。要真校验就写 `if not isinstance(...): raise`。
→ *"cast 错了会怎样？"* 什么都不会发生，直到你把错的数据用在该用的地方才炸（D1 的坑 2 就是 `cast` 把 `None` 担保成 dict，查不存在的 id 直接 `TypeError`）。这是最坏的错误形态：**延迟、远离现场、且测试可能覆盖不到**。
→ *"如果团队里有人到处 cast 怎么办？"* 拉清单治理：grep 出全部 cast，逐条问"能不能用显式构造 / 校验函数 / 泛型替代"，剩下的写进文档并加 code review 规则；更好的做法是在 CI 里加一条检查（比如禁止 `cast(` 出现在非白名单文件）。

### 6. `Literal` 值域收窄，与 `StrEnum` 的分工

**一句话定义**：`Literal["draft", "ready"]` 把类型从"任意字符串"收窄到"这几个具体值"，让拼写错误在静态检查阶段暴露。

**为什么存在**：状态、模式、渠道这类字段取值有限，但声明成 `str` 时 `"processsing"`（拼错）和 `"RUNNING"`（大小写错）都能进系统，错误要到业务判断时才表现为"怎么都不匹配"。`Literal` 把值域写进类型，mypy 就能在调用点拦住。

**怎么用**（三个实测行为）：

```python
Status = Literal["draft", "ready", "archived"]

set_status("ready")        # OK
set_status("processsing")  # error: Argument 1 has incompatible type "Literal['processsing']"
                           #        expected "Literal['draft', 'ready', 'archived']"

s: str = "ready"
set_status(s)              # error: 值是合法的，但类型是 str —— 收窄不了

def handle(s: Status) -> str:
    if s == "ready":
        return s.upper()   # 这里 s 收窄成 Literal["ready"]，是 str，可以调方法
    return s
```

**底层机制**：`Literal` 是"单值类型"的联合，mypy 做的是**值级类型检查**（value-level typing），比对的是字面量的字面值而不是基类；`==` 比较时能做**类型收窄**（narrowing），因为 `s == "ready"` 为真时 `s` 只可能是那一个字面量。与 `StrEnum` 的区别在运行时：枚举是真对象（能 `for` 遍历、能带属性、能 `is` 比较），`Literal` 运行时**完全不存在**（`get_args(Status)` 才能拿到候选值）。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 `str` 变量传给 `Literal` 参数 | `expected "Literal[...]"`，值明明合法 | 先收窄（`==` / `in` 判断）或在校验函数里 `cast` 并背锅 |
| 2 | 用 `cast` 把任意 str 变 Literal | 拼错的值静默通过（#13 坑 3） | 先校验 `raw in get_args(Status)`，不合法 raise |
| 3 | 已有枚举却又加一套 Literal | 两处定义漂移，改一处漏一处 | 一个值域只有一个事实源：要运行时对象用枚举，纯静态用 Literal |
| 4 | 以为 `Literal` 能在运行时校验 | `isinstance(x, Status)` 直接报错 | 运行时校验用 `get_args` + `in`，或者上 pydantic |

**面试问法**
> *"`Literal` 和 `Enum` 怎么选？"*
> 30 秒版：判据是"运行时要不要这个对象"。需要遍历、需要 `is` 比较、需要挂属性或方法 → 枚举；只在类型层约束、数据以裸字符串流转（如 JSON API）→ Literal。同一条值域只能有一个事实源，否则两处定义必然漂移。

**追问链**
→ *"Literal 能在运行时校验吗？"* 不能直接校验，但可以 `from typing import get_args` 拿到候选值元组做 `in` 判断——这正好是"校验 + 收窄"的正确写法，校验通过后再 cast 才有依据。
→ *"API 里状态字段用 Literal 有什么副作用？"* OpenAPI 会生成 enum 约束（好事），但客户端 SDK 可能被重新生成、新增值属于兼容性变更；另外 pydantic 支持 `Literal` 字段，校验和文档都自动，是 FastAPI 项目的常见组合。
→ *"如果状态将来要支持扩展（插件自定义状态），Literal 还合适吗？"* 不合适——Literal 是封闭集合，扩展就得改代码。这时该用 `str` + 注册表（合法值由运行时注册），把"编译期值域"换成"运行期注册"，同时补一套校验中间件。

### 7. `overload` 三个必要条件 + 运行时只有实现体

**一句话定义**：`@overload` 让同一个函数对不同的入参类型声明不同的返回类型，**但只是静态声明**——运行时只存在最后那个实现体。

**为什么存在**：有些函数按入参"形状"返回不同类型（按 id 查返回单条、按条件查返回列表），单一签名只能写联合类型，调用方拿到 `A | B` 还得自己收窄。overload 把"入参→返回"的映射写进类型，调用方直接拿到精确类型。

**怎么用**（三必要条件 + 顺序）：

```python
@overload
def get(self, key: str) -> list[str]: ...
@overload
def get(self, key: int) -> list[str]: ...
def get(self, key: str | int) -> list[str]:   # ← 必须有实现体，且参数名要与变体一致
    if isinstance(key, str):
        return [...]
    return []
```

实测结论：
1. 顺序从**精确到宽**（宽在前 → `overload-cannot-match`，mypy 自己能抓）
2. 实现体**必须有**（缺了报 `no-overload-implementation`）
3. 变体**不能有函数体**（写了也被同名实现覆盖）
4. **方法**的 overload 实现参数名必须与变体一致（模块级函数可以不同）

**底层机制**：`@overload` 装饰的函数体被丢弃（运行时它们只是被同名实现覆盖的普通函数），`typing.overload` 只登记一个哨兵供类型检查器识别。所以运行时 `f.__annotations__` 是空的、`inspect.signature` 看到的是实现体——**变体在运行时彻底不存在**。这就是"实现体漏分支 mypy 不报"的根源：类型检查器只验证"实现体签名兼容所有变体"，不验证"实现体真的区分了每个分支"。

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 宽分支写在前 | `overload-cannot-match`（mypy 能抓） | 变体从精确到宽排，像 except 从子类到父类 |
| 2 | 实现体漏分支 | **mypy 放行**，运行时静默丢语义（#13 坑 2） | 实现体逐分支对齐；用 `assert_never` 做穷尽性检查 |
| 3 | 给变体写函数体 / docstring | 白写，运行时被同名实现覆盖 | 变体只有签名，文档写实现体上 |
| 4 | 方法 overload 的实现参数名与变体不同 | 报 `overload` 相关错误，信息难懂 | 方法与变体参数名保持一致 |

**面试问法**
> *"`@overload` 在运行时生效吗？"*
> 30 秒版：不生效。运行时只存在最后那个实现体，所有 `@overload` 声明都被同名函数覆盖，`__annotations__` 是空的。它纯粹是给类型检查器看的映射表，所以实现体漏写分支 mypy 不会报——这也是 overload 最危险的地方。

**追问链**
→ *"那怎么保证实现体真的覆盖了所有变体？"* 用穷尽性检查：实现体末尾 `assert_never(key)`，类型没穷尽时 mypy 会报；或者写成 if/elif/else + `raise`，让漏分支在运行时立刻炸而不是静默返回空。
→ *"overload 和 Protocol 有什么关系？"* 互补：Protocol 约束"对象提供哪些能力"，overload 约束"一个函数对不同入参提供什么返回"。写仓储接口时两者常一起用——Protocol 里也可以用 overload 声明 `get(key: str) / get(key: int)`。
→ *"什么时候不该用 overload？"* 当返回类型其实一致（只差参数类型）时——那是普通联合类型就够了；以及分支超过 3、4 个时，overload 会迅速变成维护负担，考虑拆函数或上泛型（`TypeVar` + `bound`）。

### 8. `cast` 是"担保"不是"转换"，必须登记

**一句话定义**：`cast(T, x)` 告诉类型检查器"把 x 当 T 看"，运行时什么都不做——**它不改变值，只改变编译器对值的看法**。

**为什么存在**：类型系统是保守的，有些正确代码它证明不了（TypedDict 合并、`Optional` 收窄、第三方库返回 Any）。cast 提供一个"人工担保"的逃生口，让这类代码能通过检查。代价是：**担保错了没人管**。

**怎么用**（两类用法，必须分清）：

```python
# 合法：承认表达力边界（值确实满足，只是编译器证不了）
cast("dict[str, Any]", row).update(payload)   # 键集合由 KBUpdate 决定
cast(str, os.environ.get("APP_ENV"))          # 环境变量一定有（启动时校验过）

# 滥用：掩盖没做校验（值可能不满足）
cast("Status", raw.strip())                   # "deleted" 也会被担保成合法状态
```

**底层机制**：`cast` 的实现是 `def cast(typ, val): return val`——**直接返回原值**，运行时零动作（`dis` 里只有 `RETURN_VALUE`）。这意味着：
- 类型不匹配时不会抛错，错误会延迟到"用它的那一刻"
- `cast` 之后不可逆：类型检查器相信你，后面所有断言都建立在担保上
- 这就是为什么"cast 比 `# type: ignore` 好"——**它在代码里可见、可搜索、可 review**，而 ignore 只是一行注释，没人知道它掩盖了什么

**易错点**

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 cast 掩盖未校验的输入 | 脏值静默进系统（D1 坑 2、#13 坑 3 同一个病） | 校验后 cast，或校验后直接返回精确类型 |
| 2 | cast 后赋给新变量 | 降级扩散，后续全 Any | 只在表达式上 cast，不落变量 |
| 3 | 以为 cast 会做转换 | `cast(int, "1")` 返回 `"1"` | 转换用 `int(x)`；cast 只改看法 |
| 4 | 逃生口不登记 | 半年后没人知道为什么在这 cast，也不敢删 | 每处写理由 + 删除条件，集中列在文档里 |

**面试问法**
> *"`cast` 和 `type: ignore` 你更倾向哪个？"*
> 30 秒版：cast。ignore 是整行失忆，cast 是"我知道这里是 T"——可搜索、可 review、范围更小（只在表达式上）。但两者都是逃生口，必须登记：写清为什么安全、什么条件下能删。

**追问链**
→ *"cast 错了会引发什么类型的问题？"* 最坏的一种：不报错、测试也过，直到某个边界输入走到那条路径才炸，且炸点离 cast 很远。D1 那道题里 `cast(dict, x or None)` 就是——查一个不存在的 id 才 `TypeError`。
→ *"为什么 `cast` 不能替代校验？"* 因为它不读值。校验必须读值（`in` / `isinstance` / pydantic），而 cast 只是把责任从编译器转给你。凡"输入来自外部"的地方，先校验再 cast。
→ *"怎么系统性减少 cast？"* 三条：①用显式构造（`{**base, ...}`）替代结构 cast；②用泛型 / Protocol 把"编译器证不了"变成"能证"；③把 cast 收进边界函数（如 `parse_row(raw) -> Row`），让业务代码里一个 cast 都没有。

## 三、30 秒答案集

1. `Any` 不是"不知道类型"，是"免检"——双向兼容，消掉的不只是报错，还有定位信息。
2. `dict[str, Any]` 的代价：结构只活在人脑子里，两种类型可以共存四周不报错。
3. TypedDict 运行时就是 dict：`type()` 是 `dict`、`isinstance` 抛 `TypeError`、零开销。
4. TypedDict 的保证只有一条：键集合确定 + 每个键类型确定；它不做运行时校验。
5. TypedDict 是名义式类型，两个字段相同的 TypedDict 也不能互赋——和 Protocol 正相反。
6. mypy 对 dict 字面量逐键检查，对变量只查声明兼容性——所以 `dict[str, Any]` 变量传参被拦。
7. `row.update(payload)` 只能 `cast("dict[str, Any]", row).update(payload)`，这是表达力缺口。
8. 选型判据：要运行时校验 → pydantic；只要静态结构 → TypedDict；要对象和行为 → dataclass。
9. `Literal` 是值级类型：拼错报错、`str` 变量传不进、`==` 能收窄；运行时不存在。
10. `Literal` vs 枚举的判据：运行时要不要这个对象；一个值域只能有一个事实源。
11. overload 三必要条件：实现体必须有、变体不能有函数体、实现签名覆盖全部变体。
12. overload 运行时只存在实现体，`__annotations__` 是空的——所以实现体漏分支 mypy 不报。
13. `cast` 运行时是 `return val`，不改值只改看法；错了延迟到使用点才炸。
14. `total=False` 键用 `[]` 取：mypy 放行（盲区）、pyright 报、运行时 `KeyError`。
15. `or` 判断"缺失"会连空串、0、空列表一起吃——`x is None` 才是缺失判据。

## 四、白板手写靶

### 靶 1：TypedDict + 可选键的正确消费

```python
class IndexEntry(TypedDict):
    doc_id: str
    title: str
    tokens: list[str]


class EnrichedEntry(IndexEntry, total=False):
    summary: str
    status: str


def entry_line(e: EnrichedEntry) -> str:
    return f"[{e['title']}] {e.get('summary', '')}"


def summary_of(e: EnrichedEntry) -> str:
    s = e.get("summary")
    return "(无摘要)" if s is None else s
```

要点：`total=False` 的键**永远 `.get()`**；`get` 的默认值和 `or` 的区别就是"空串算不算缺失"。

### 靶 2：三行 overload（精确到宽）

```python
@overload
def get(self, key: str) -> list[str]: ...


@overload
def get(self, key: int) -> list[str]: ...


def get(self, key: str | int) -> list[str]:
    if isinstance(key, str):
        return [e["title"] for e in self._docs.values() if e["doc_id"].startswith(key)]
    return [e["title"] for e in list(self._docs.values())[:key]]
```

要点：变体只有签名（没有函数体）；实现体必须把每个分支都写出来——**mypy 不会替你检查这个**。

### 靶 3：带校验的 str → Literal 转换

```python
from typing import Literal, get_args

Status = Literal["draft", "ready", "archived"]


def normalize_status(raw: str) -> Status:
    value = raw.strip().lower()
    allowed = get_args(Status)
    if value not in allowed:
        raise ValueError(f"非法状态：{raw!r}，允许值：{allowed}")
    return value  # 收窄后无需 cast
```

要点：`get_args` 拿候选值 → `in` 校验 → 返回时类型已收窄。**校验过的 cast 才是合法 cast，而这里连 cast 都不需要**。

## 六、可以讲成故事的三段

### 故事 1：一个 `isoformat()` 藏了四周

背景：把 `store` 的行从 `dict[str, Any]` 换成 TypedDict，mypy 突然报 4 个 `typeddict-item`，全指向测试里同一个变量。
我以为是 mypy 太严：测试造数据而已，字符串和 datetime 反正都能用。
实际是**测试造错了数据**——真实 repo 存的是 `datetime` 对象，测试塞的是 `isoformat()` 字符串，两者在 `Any` 底下和平共存，四周没人发现；没炸全靠 pydantic 的宽松解析把字符串又转回了时间。
教训：**`Any` 掩盖的不是"小瑕疵"，是一个已经坏了但还没发作的契约**；mypy 报错的地方，先假设"它是对的"。

### 故事 2：`update` 的报错形状

背景：给 TypedDict 合并 pydantic dump 出来的 payload，`row.update(payload)` 直接红。
我以为是签名写错了，试了 `|=`、试了 for 循环逐键赋值，全是错。
实际是类型系统的**表达力缺口**：`update` 允许任意键，而 TypedDict 的唯一保证就是"键集合确定"，所以它必须拒绝——但我这边的键集合确实由 `KBUpdate` 决定，属于"我知道得比编译器多"。
教训：**遇到"正确代码写不出来"，那不是 bug 是边界**；`cast` 是承认边界的手段，但要在旁边写清"我凭什么比编译器知道得多"。

### 故事 3：第四档判分时的自我修正

背景：判 #13 时我准备拿 `e: EnrichedEntry = make_entry("d-1", "x")` 当"mypy 放行的证据"，讲 total=False 的盲区。
我以为 extra 键全可选，所以 IndexEntry 能赋过去。
实际 mypy 直接报 `[assignment]`：TypedDict 是名义式，字段覆盖不等于可赋值；真正的盲区是**字面量省略 summary**（mypy 允许），然后 `[]` 取值运行时报 `KeyError`。
教训：**讲"类型系统的坑"时，坑必须在真解释器上验过**——凭直觉推的类型规则，一半是反的。

### 强项（2 条，带证据）

### 待补（2 条，具体到哪一句说不准）

1. **`total=False` 的消费方式（#13 坑 1 未命中）**：你能看出 `status: str` 该收窄，却没看出 `e["summary"]` 才是会炸的那处。补法：见到 `total=False` 就默念"这个键可能不在"，`[]` 一律换 `.get()`——并记住 mypy 不管、pyright 管。
2. **"缺失"和"空值"分不清（连续两次）**：`#11 坑 2` 的 `{} or None`、`#13 坑 4` 的 `"" or fallback` 是同一个病——你把"看起来为空"当成了"不存在"。判据只有一条：**只有 `is None` 表示缺失**；`or` 用来做默认值时必须先确认"空值也接受 fallback"。
