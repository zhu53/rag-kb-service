# W5-D5+D6 教材 · 质量门禁的最后一公里：ruff 速通 + mypy 进门禁 + 反脆弱验收

> **读者假设**：你从没认真看过 ruff 配置，从没给门禁加过新步骤，也没试过"故意写错代码看门禁拦不拦"。
> **这天要多久**：3 小时（ruff 1h + 门禁收口 1h + 反脆弱验收 1h）。
> **一句话目标**：把 type checker 接进自动门禁，然后**亲手证明门禁真的会红**——因为一直绿的门禁，可能是它根本没在检查。

## 零、先看痛点：一个"永远绿"的门禁有多危险

你现在的门禁（`kb-service/scripts/check.py`）跑三步：

```text
=== ruff check ===          [PASS]
=== ruff format --check === [PASS]
=== pytest + 覆盖率 ===     [PASS]
```

昨天（D4）我全程**手动**跑 mypy：

```powershell
& .\.venv\Scripts\python.exe -m mypy src tests
```

**问题不在于麻烦，在于它不在门禁里**。这意味着：

- 你今天改完代码，`check.py` 全绿 → 你以为能提交 → 其实 mypy 可能已经报了 8 个错
- CI 也不会拦 → 错误进主干 → 下一周才发现
- 更糟的是：**你从此不信门禁了**，因为它答应保护你，但没做到

还有第二层问题，更隐蔽。假设你真把 mypy 加进去了，怎么知道它**真的在工作**？

> 门禁绿了，可能是"代码没问题"，也可能是"这一步根本没跑"、"跑错了目录"、"被 `exclude` 掉了"。
> **这两种情况在输出上一模一样。**

所以今天要干是三件事：

| # | 做什么 | 解决哪个痛点 |
|---|---|---|
| 1 | ruff 9 组规则速通（1h） | 你不知道它在管什么，就不知道它漏了什么 |
| 2 | mypy 进 `check.py` + CI | 类型错误必须能拦住提交 |
| 3 | **注入式验收**：亲手写 5 类错误，看门禁红不红 | 证明门禁真的在工作，并找出它的盲区 |

第 3 件是今天的核心。做完你会发现：**5 类错误里有 2 类门禁拦不住**——这不是 bug，是你要记住的边界。

```bash

```

你会看到（实测输出，节选）：

```text
=== ruff check ===
All checks passed!
[PASS] ruff check

=== ruff format --check ===
[PASS] ruff format --check

=== pytest + 覆盖率门禁 (95%) ===
61 passed, 1 warning in 2.21s
Required test coverage of 95% reached. Total coverage: 96.56%
[PASS] pytest + 覆盖率门禁 (95%)

==============================================
门禁全绿，可以提交
```

### 1.1 为什么顺序是 ruff → format → pytest

不是随便排的，按"**快 → 慢**"和"**失败信息好读 → 难读**"两个维度排：

| 步骤 | 耗时 | 失败时你知道什么 |
|---|---|---|
| ruff check | ~0.1s | 哪个文件哪一行哪条规则 |
| ruff format | ~0.1s | 哪个文件要格式化（`--fix` 能自动修） |
| pytest | ~2.2s | 哪个测试挂了，但**可能连带 20 个** |

如果先跑 pytest：代码有个未使用的 import（F401），pytest 全绿，你还是得再跑 ruff；反过来先跑 ruff，2 秒内就把"格式类"问题清干净了，pytest 只需要处理真正的逻辑问题。**先跑快的那一步，等于把失败信息变少。**

### 1.2 `step()` 函数在干什么

```python
def step(name: str, cmd: list[str]) -> bool:
    print(f"\n=== {name} ===", flush=True)
    code = subprocess.run(cmd, cwd=ROOT).returncode
    print(f"[{'PASS' if code == 0 else 'FAIL'}] {name}", flush=True)
    return code == 0
```

三个细节，每一个都有原因：

1. **`cwd=ROOT`**：不管你从哪个目录调 `check.py`，子进程都在 `kb-service/` 下跑。没有它，从仓库根跑就会找不到 `pyproject.toml` 的配置
2. **`flush=True`**：不加的话，子进程的输出会被缓冲，你在 CI 日志里看到的顺序是乱的（`[PASS]` 可能跑到 `=== ruff ===` 前面）
3. **返回 `code == 0`，不 `raise`**：某一步失败后，后面的步骤**继续跑**。这是故意的——一次看到所有失败，比修一个跑一次快得多

## 二、ruff 的 9 组规则（1 小时速通）

项目配置（`kb-service/pyproject.toml`）：

```toml
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B", "SIM", "RUF", "ASYNC", "PT"]
ignore = [
    "B008",    # FastAPI Depends() 默认参数是官方用法
    "RUF001", "RUF002", "RUF003",   # 中文标点被判成"歧义字符"，纯噪音
]
```

**为什么是这 9 组**：ruff 有 800+ 条规则、50 多个规则族。全开会淹没在噪音里（`D` 强制 docstring、`ANN` 强制注解、`S` 安全检查会把你自己的 `assert` 全拦下来）。这 9 组的共同点是：**报出来的几乎都是真问题，不是风格偏好**。

### 2.1 逐组过：它管什么 + 一个真实例子

| 组 | 全名 | 管什么 | 典型报错 |
|---|---|---|---|
| `E` | pycodestyle errors | 行太长、缩进错、行尾空格 | `E501 Line too long (105 > 100)` |
| `F` | pyflakes | **未使用的 import**、未定义的名字、f-string 缺占位符 | `F401 imported but unused` |
| `I` | isort | import 分组与排序 | `I001 Import block is un-sorted` |
| `UP` | pyupgrade | 老写法升级 | `UP006 Use list instead of List` |
| `B` | flake8-bugbear | **可变默认参数**、裸 `except:`、循环里 `+=` 拼字符串 | `B006 Do not use mutable data structures for argument defaults` |
| `SIM` | flake8-simplify | 多余的 if / 可合并条件 | `SIM108 Use ternary operator` |
| `RUF` | Ruff 自有 | 各种杂项（本项目 ignore 了中文标点三条） | `RUF100 Unused noqa` |
| `ASYNC` | flake8-async | async 函数里调阻塞 API | `ASYNC109 async function with timeout parameter` |
| `PT` | flake8-pytest-style | pytest 写法规范 | `PT009 Use a regular assert instead of unittest-style assertEqual` |

### 2.2 三组值得单独讲

**① `F` 组是"最值钱"的一组**

`F401`（未使用 import）在真实项目里出现频率最高。为什么值钱：它抓到的是**重构后的残骸**——你把一段逻辑删了，import 忘了删。这种代码不影响运行，但会让下一个人以为"这个模块还在用 `cast`"。

昨天 D4 就踩了一次：

```text
F401 [*] `typing.Any` imported but unused
 --> kb-service\src\kb_service\core\security.py:5:20
```

原因是：`cast` 恢复了，`Any` 的注解删了，import 留在原地。

**② `UP` 组会连锁改两处（这是 `--fix` 最容易看走眼的地方）**

实测：给它一段 `typing.List` / `Optional` 的代码，`ruff check --diff` 输出：

```diff
--- src\kb_service\_p.py
+++ src\kb_service\_p.py
@@ -1,5 +1,4 @@
-from typing import List, Optional
 
 
-def f(x: List[int]) -> Optional[int]:
+def f(x: list[int]) -> int | None:
     return None

Would fix 4 errors.
```

**注意**：动的地方有两处，不是一处——注解从 `List[int]` 变成 `list[int]`（`UP006`），同时 `import` 行因为两个名字都不再使用被整行删掉（`UP035`）。你以为只改了类型写法，实际 import 也没了。

**③ `ASYNC` 组：`noqa` 的正当用法就在这里**

项目里 `llm_client.py:38`：

```python
async def chat(self, prompt: str, timeout: float = 10.0) -> str:  # noqa: ASYNC109
    """POST /chat/completions，返回 assistant 文本。

    timeout 是 httpx 客户端的连接/读超时，不是 asyncio 超时域，故屏蔽 ASYNC109。
    """
```

`ASYNC109` 的意图是好的：async 函数里应该用 `asyncio.timeout()`，不该自己收一个 `timeout` 参数（容易写出阻塞的假超时）。但这里的 `timeout` 是**传给 httpx 的**，语义完全不同。

**这条 `noqa` 的正当性来自三点**：带了具体 code、docstring 写清了为什么、是唯一一条。三条缺一条就是"偷懒"。

### 2.3 `ignore` 里的三条为什么必须留

```toml
"RUF001",  # ambiguous-unicode-character-string
"RUF002",  # ambiguous-unicode-character-docstring
"RUF003",  # ambiguous-unicode-character-comment
```

这三条检测的是"看起来像 ASCII 但实际是全角的字符"——`，` vs `,`、`：` vs `:`。英文项目里这是真问题（复制粘贴会导致语法错），**中文项目的注释和 docstring 里用全角标点是正常需求**。

判别：`ignore` 里每一条都应该能回答"为什么这条规则在本项目里是错的"。答不上来就该修代码，不该 ignore。

## 三、`--fix` 的边界：能自动改什么、不能改什么

### 3.1 三种规则

| 类型 | 标记 | 例子 | 说明 |
|---|---|---|---|
| 可自动修 | `[*]` | `F401`、`I001`、`UP006` | 改法唯一，无歧义 |
| 不可自动修 | 无标记 | `E501`（行太长） | 怎么折行需要人判断 |
| 可修但有风险 | `[*]` + unsafe | `SIM` 部分规则、`B` 部分 | 需要 `--unsafe-fixes` 才动 |

**判据**：报错信息里带 `[*]` 就能 `--fix`。不带就老实手改。

### 3.2 正确姿势：先看 diff，再决定改不改

```powershell
# Windows PowerShell —— 只看不改
& .\.venv\Scripts\ruff.exe check --diff src tests reviews
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/ruff.exe check --diff src tests reviews
```

`--diff` 会把"如果 fix 会怎么改"输出成标准 diff，**不落盘**。养成这个习惯的原因：

- `--fix` 是**批量**修改，一次可能动 20 个文件
- 你没法 review 20 个文件的意外改动，但能 review 一个 diff
- 之前就出过事：`--fix` 把 `typing.Mapping` 的 import 从 `typing` 挪到 `collections.abc`，同时因为顺序变化把另一处 import 也动了，diff 里混在一起，差点没看出来

### 3.3 `--fix` 改完必须复跑

```powershell
& .\.venv\Scripts\ruff.exe check --fix src tests reviews
& .\.venv\Scripts\ruff.exe format src tests reviews
& .\.venv\Scripts\python.exe scripts\check.py
```

原因：`--fix` 修完 `F401` 可能**引入**新的 `I001`（import 删了，分组顺序变了），需要再跑一遍直到干净。ruff 自己也会提示"再跑一次"。

## 四、`noqa` 的正当用法

### 4.1 三种写法，只有一种合格

```python
x = something()  # noqa                 # ❌ 裸 noqa：屏蔽这一行全部规则，以后加的规则也被吞
x = something()  # noqa: ASYNC109       # ✅ 指明规则
x = something()  # noqa: ASYNC109  -- 这个 timeout 是 httpx 的，不是 asyncio 域  # ✅✅ 带理由
```

**裸 `noqa` 是最糟的**：它不只是屏蔽当前这条规则，而是屏蔽**这一行上未来出现的所有规则**。半年后有人在这行改出个 `F821`（未定义名字），也一起被吞了。

### 4.2 ruff 能帮你查"没用的 noqa"

```powershell
# Windows PowerShell
& .\.venv\Scripts\ruff.exe check --select RUF100 src tests reviews
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/ruff.exe check --select RUF100 src tests reviews
```

`RUF100` = `Unused noqa`。触发场景：你 `noqa` 了一条规则，但那条规则后来不报了（改代码了、改配置了）。**这种 noqa 是纯负债**——它让人以为这里有特殊情况，其实没有了。

> 顺便：`RUF` 组已经包含 `RUF100`，所以项目门禁本来就会报。可以试一下在某个文件里加一条 `# noqa: E501`（项目里没有超长行），看它会不会红。

## 五、`per-file-ignores` 的死配置（今天实测出的一个真坑）

项目配置里有这么一行：

```toml
[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S101"]
```

读起来是："给 tests 目录放行 `S101`（`assert` 的使用）"。**看起来很有道理**——测试里当然要用 assert。

**但它是死配置。** 因为 `select` 里根本没有 `S` 这一族！

实测（往 `src/` 塞一个 `assert`）：

```text
$ ruff check --stdin-filename src/kb_service/_tmp_probe.py -
All checks passed!          ← 没报，因为 S 族没启用
```

显式开 S101 才报：

```text
$ ruff check --select S101 --stdin-filename src/kb_service/_tmp_probe.py -
S101 Use of `assert` detected
 --> src\kb_service\_tmp_probe.py:2:5
2 |     assert 1 == 1
  |     ^^^^^^
```

### 5.1 为什么这类坑最难发现

代码里的死代码，pytest 覆盖率会告诉你"这行没被跑过"。**配置里的死配置，没有任何工具会告诉你。**

它的危害不是"多写了一行"，而是：

- 你以为 `assert` 被检查过了 → 其实 `src/` 里的 `assert` 也能随便写
- 你以为 tests 有豁免 → 其实不需要豁免
- 更重要的是：它让你**误判了门禁的能力边界**（而今天整天的主题就是"边界"）

### 5.2 怎么处理（三选一）

1. **删掉这行**（最干净）：`select` 里没有 S，这行就没有意义
2. **同时打开 `S` 族**并保留豁免：但那会引入一堆安全检查噪音（`S105` hardcoded password、`S311` 随机数用于加密），对学习项目不划算
3. **留着但加注释**说明"为将来打开 S 预留"——可以接受，但要在注释里写清

我建议选 1，然后在 D7 周总结里记一笔"配置也要定期审计"。

## 六、mypy 进门禁：一行改动，一个陷阱

### 6.1 改动本身很简单

`scripts/check.py` 里在 pytest 之后加一步：

```python
checks = [
    ("ruff check", [...]),
    ("ruff format --check", [...]),
    ("mypy", [sys.executable, "-m", "mypy", *TARGETS]),   # ← 新增
    (f"pytest + 覆盖率门禁 ({COV_FLOOR}%)", [...]),
]
```

`TARGETS` 现成的：`["src", "tests", "scripts", "conftest.py"]`。实测 mypy 扫这些是 **48 source files**，耗时 **0.96 秒**（比 pytest 快一倍）。

### 6.2 陷阱：**REVIEWS 绝对不能传给 mypy**

这是今天最重要的一行代码判断。`check.py` 里有两个列表：

```python
TARGETS = ["src", "tests", "scripts", "conftest.py"]      # 项目代码
REVIEWS = [str(REPO / "reviews")]                          # 第四档题面
```

ruff 的目标是 `[*TARGETS, *REVIEWS]`，**mypy 只传 `*TARGETS`**。

为什么？实测把 reviews 也塞给 mypy：

```text
$ mypy src tests scripts conftest.py ../reviews
..\reviews\review_08_notes.py:137: error: Function is missing a return type annotation  [no-untyped-def]
..\reviews\review_08_notes.py:139: error: Argument "repo" to "NoteService" has incompatible type "FakeNoteRepo"; expected "InMemoryNoteRepo | None"  [arg-type]
..\reviews\review_02_api.py:50: error: Dict entry 0 has incompatible type "str": "int"; expected "str": "str"  [dict-item]
..\reviews\review_10_gateway.py:45: error: Returning Any from function declared to return "str"  [no-any-return]
Found 48 errors in 8 files (checked 62 source files)
```

**48 个错误**，全在 `reviews/` 里。这些不是 bug——**练习题就是故意写宽类型、故意不写注解的**。#11 考 `Any` 传染、#14 考 `cast` 滥用，它们的"错误"正是题目本身。

如果让 mypy 扫 reviews，结果就是：**门禁永远红，你只能把 mypy 关掉**。这比不接 mypy 更糟。

> 一句话记住：**练习题的"错误"是内容，不是缺陷。门禁只检查交付物，不检查教材。**
> 这和 `pytest` 不收 `reviews/`（它不在 `testpaths` 里）、覆盖率不计 `reviews/` 是同一个道理。

### 6.3 顺序：mypy 放 pytest 之前还是之后

我放在 ruff 之后、pytest 之前。理由：

| 位置 | 好处 | 坏处 |
|---|---|---|
| pytest 之前 | 快（0.96s），类型错误先暴露；避免 pytest 因为类型错崩溃产生一堆噪音 | 如果 mypy 挂了，pytest 还是要跑（不影响，因为 `step()` 不中断） |
| pytest 之后 | 先看行为对不对 | 2.2 秒后才看到"其实有个 F821" |

**没有绝对答案，但有一条硬标准**：`check.py` 里的顺序要和 CI 里的 step 顺序**一致**。否则本地"第 3 步红"、CI"第 4 步红"，对不上号。

### 6.4 加完之后立刻验一次

```powershell
# Windows PowerShell
& .\.venv\Scripts\python.exe scripts\check.py
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/python.exe scripts/check.py
```

预期看到四步全 PASS（mypy 那步输出 `Success: no issues found in 48 source files`）。如果 mypy 报错，说明你的代码本来就有类型问题，只是以前没人拦——先修，别急着往下走。

## 七、mypy 进 CI：为什么要分步，不直接跑 check.py

`ci.yml` 现在是这样：

```yaml
- name: ruff check
- name: ruff format --check
- name: pytest + coverage
- name: mutation
```

**明明有 `check.py` 一条命令，为什么 CI 要拆成四步？**

因为失败时的**信息粒度**不同：

| 方式 | 失败时你看到 | 修起来 |
|---|---|---|
| `run: python scripts/check.py` | 一个红叉，点进去翻日志找是哪步 | 翻 200 行日志 |
| 分步 | 红的是 `ruff check` 那个 step，日志只有那一步的 | 直接看 |

CI 里**步骤名就是诊断信息**。所以本地一条命令（方便），CI 分步（好诊断）——两者不矛盾。

加 mypy 那一步：

```yaml
      - name: mypy
        run: |
          set -o pipefail
          uv run python -m mypy src tests scripts conftest.py 2>&1 | tee /tmp/step.log || {
            MSG=$(tail -30 /tmp/step.log | sed -e 's/\r$//' -e 's/%/%25/g' | sed -e ':a' -e 'N' -e '$!ba' -e 's/\n/%0A/g')
            echo "::error title=mypy failed::${MSG}"
            exit 1
          }
```

注意三个地方：

1. **`uv run` 而不是 `./.venv/Scripts/python.exe`**：CI 在 Ubuntu，路径是 `.venv/bin/python`。`uv run` 两边都能用，就不用写平台分支
2. **不传 `reviews`**：和本地一样
3. **`set -o pipefail`**：没有它，`cmd | tee` 的退出码是 `tee` 的（永远 0），失败会被吞掉——这是 shell 管道最经典的坑

`set -o pipefail` 这一条值得单独记：**只要你在 CI 里用了 `| tee`，就必须加它**，否则红的一步会被报成绿。

## 八、反脆弱验收：注入 5 类错误，必须全红（今天最重要的一节）

### 8.1 为什么要"注入"

"门禁绿了"和"门禁有用"是两件事。要证明后者，只有一种办法：**故意写错，看它红不红**。

正式名字叫**故障注入**（fault injection）/ **变异测试**（mutation testing）。项目里的 `scripts/mutation_check.py` 就是做这个的（W4-D6 写的，5 个变异体全被杀）。

今天做的是**类型层面**的注入：写 5 个"人类常犯"的类型错误，看 ruff + mypy 能不能全拦。

### 8.2 实测结果（5 类，2 类拦不住）

| # | 注入的错误 | 人类场景 | mypy | ruff |
|---|---|---|---|---|
| 1 | 删掉 `from __future__ import annotations` | "这行没用，删掉清爽" | ✅ **全绿** | ✅ 全绿 |
| 2 | `TokenClaims.sub: str` 改成 `sub: Any` | "报错？收成 Any 就过了" | ✅ **全绿** | ✅ 全绿 |
| 3 | 加一条多余的 `# type: ignore[no-any-return]` | "先 ignore 再说" | ❌ 1 error | ✅ 全绿 |
| 4 | 测试函数漏写 `-> None` | 手写新测试时最常见 | ❌ 1 error | ✅ 全绿 |
| 5 | `create_access_token(subject: str)` 改成 `bytes` | 改契约没同步 | ❌ **8 errors in 4 files** | ✅ 全绿 |

实测原文（第 3、4、5 类）：

```text
=== 3 加一条多余的 type: ignore ===
  mypy exit=1: Found 1 error in 1 file (checked 45 source files)
  ruff exit=0: All checks passed!

=== 4 测试函数漏写 -> None ===
  mypy exit=1: Found 1 error in 1 file (checked 45 source files)
  ruff exit=0: All checks passed!

=== 5 参数类型写错 str->bytes ===
  mypy exit=1: Found 8 errors in 4 files (checked 45 source files)
  ruff exit=0: All checks passed!
```

### 8.3 三个结论，一个比一个重要

**① ruff 一类都没拦住——因为它不管类型**

5 类全是类型问题，ruff 是 linter（语法/风格/bug 模式），不是 type checker。这正好说明为什么两者都要：

> **ruff 管"这段代码看起来对不对"，mypy 管"这段代码类型上通不通"。** 一个未使用的 import 只有 ruff 抓；一个类型写错只有 mypy 抓。

**② 门禁拦不住的两类，都是"你自己主动放弃保护"**

- 第 1 类：删 `from __future__ import annotations` —— 在 Python 3.11 下**确实不影响运行**（`X | Y` 语法 3.10+ 原生支持），所以不报错是"正确"的。它的价值是可读性/前向兼容，不是正确性
- 第 2 类：`sub: str` → `sub: Any` —— **这是最危险的**。它看起来像"修好了报错"，实际是把契约拆了。pydantic 的必填校验还在（没默认值），但**类型层面失去全部保护**：`deps.py` 里 `UUID(str(sub))` 拿到 `Any`，mypy 不再帮你检查任何东西

第 2 类的教训直接接昨天的 D4：**`Any` 不是"万能兼容"，是"关闭检查"**。mypy 没法阻止你关掉它自己——就像编译器没法阻止你写 `--no-verify`。

**③ 第 5 类的 8 个错误，是"契约变更"的真实代价**

改一个函数参数的类型，连带 **4 个文件 8 处**报错。这不是噪音，这正是 D4 知识点 6 说的"签名是契约"。mypy 帮你把全部调用点找出来了——**这就是接它进门禁的最大收益**。

### 8.4 那 2 类拦不住怎么办

门禁不是全能的，要接受并用别的手段补：

| 拦不住的 | 补法 |
|---|---|
| 删 `__future__` import | 代码评审（这行在文件第一行，review 时能看见）；或写一条 `conftest`/自定义检查断言"每个模块都有它" |
| `str` → `Any` 降级 | **评审 + 约定**：`Any` 出现必须带 TODO 和原因；或定期 `grep -rn ": Any" src/` 人工过一遍（D1 就定过"`Any` 要登记"） |

> 一句话：**自动化能覆盖 80%，剩下 20% 靠评审和约定。真正的危险是以为自动化覆盖了 100%。**

## 十二、面试问法（30 秒版 + 追问链三层）

### 12.1 "你们 CI 里跑什么？"

> **30 秒版**：一条命令 `check.py` 跑四步——ruff lint、ruff format、mypy 类型检查、pytest 带 95% 覆盖率门禁，可选再加变异测试。本地跑一条命令，CI 里拆成独立 step，因为步骤名本身就是诊断信息：红的是哪一步，一看就知道。

**追问链**：

→ *（机制）"ruff 和 mypy 分工？"*
ruff 是 linter，管语法、风格、bug 模式（未使用 import、可变默认参数）；mypy 是类型检查器，管类型是否自洽（参数类型、返回值、契约）。**一个未使用 import 只有 ruff 抓，一个参数类型写错只有 mypy 抓**，两者不重叠，所以都要。

→ *（边界/故障）"门禁一直绿，你怎么知道它真在工作？"*
做故障注入：故意写 5 类错误，看它红不红。我实测过——5 类里 3 类被 mypy 拦住，2 类拦不住：删 `from __future__ import annotations`（3.11 下确实不影响运行）和把 `str` 字段降级成 `Any`（类型检查器没法阻止你关掉它自己）。**知道边界比知道它能拦更重要。**

→ *（场景落地）"新同事提交了 `# type: ignore` 想绕过检查，你怎么处理？"*
先看是哪条规则、为什么报。如果是我漏掉的真实问题，修代码；如果是第三方库的类型缺口，用精确的 `[[tool.mypy.overrides]]` 或边界 `cast` 收敛，并在评审里写清理由。**裸 ignore 一律不接受**——它连"我认为它是什么类型"都没说，半年后没人敢删。

### 12.2 "怎么保证代码质量？"

> **30 秒版**：三层——写的时候就防（类型注解 + ruff 实时提示）、提交时拦（pre-commit 钩子）、合并前卡（CI 四步门禁）。三层里最容易被忽略的是**验证门禁本身有效**，所以我会定期注入错误看它红不红。

**追问链**：

→ *（机制）"pre-commit 和 CI 都跑 ruff，重复吗？"*
不重复，是两层时间点：pre-commit 在**提交前**（几秒，只跑改动文件，让你立刻改），CI 在**合并前**（全量，防绕过 `--no-verify`）。pre-commit 是"帮你省时间"，CI 是"保证底线"——有人本地不装钩子也拦不住，所以 CI 必须有。

→ *（边界/故障）"CI 里 `cmd | tee log` 会有什么坑？"*
管道的退出码是最后一个命令（`tee`）的，永远 0，所以红的步骤会被报成绿。必须加 `set -o pipefail`。这个坑很隐蔽——本地因为没有 `| tee` 所以是好的，只在 CI 出现。

→ *（场景落地）"覆盖率 96% 了，还需要变异测试吗？"*
需要。覆盖率只证明"这行被执行过"，不证明"断言有效"。`assert True` 也能刷覆盖率。变异测试把代码改坏看测试红不红，才能证明断言有杀伤力——我们项目 5 个变异体全被杀，但那是**已经被验证过的路径**；新写的代码没做过变异，覆盖率再高也不敢说测住了。

### 12.3 "你怎么看 lint 规则全开？"

> **30 秒版**：不该全开。全开的结果是几百条噪音，团队会集体 `noqa`，等于没开。我的做法是按"报出来是不是真问题"选组，`ignore` 里每一条都要能解释为什么在本项目里不适用，并且定期用 `RUF100` 清掉失效的豁免。

## 十三、闭卷自测（6 题，先答再看）

<details>
<summary>1. 为什么 mypy 不能扫 `reviews/`？</summary>

因为练习题故意写宽类型、故意不写注解——那些"错误"正是题目本身。实测扫进去报 48 errors，门禁会永远红，最后只能把 mypy 关掉，比不接更糟。

**一句话**：门禁只检查交付物，不检查教材。
</details>

<details>
<summary>2. `check.py` 里为什么 ruff 要带 `REVIEWS`，mypy 不带？</summary>

ruff 检查的是**风格**，练习题也应该是干净的风格（题面有噪音会干扰做题）；mypy 检查的是**类型正确性**，而练习题的类型"错误"是设计出来的。

两者目标不同，所以目标列表不同。
</details>

<details>
<summary>3. CI 里 `uv run pytest ... | tee /tmp/log` 不加 `set -o pipefail` 会怎样？</summary>

退出码变成 `tee` 的（0），哪怕 pytest 失败，这一步也报绿。CI 变成"永远通过"，形同虚设。

**规则**：只要用了 `| tee`，必须 `set -o pipefail`。
</details>

<details>
<summary>4. `per-file-ignores` 里的 `"tests/*" = ["S101"]` 为什么是死配置？</summary>

因为 `select` 里没有 `S` 族，`S101` 本来就不会触发，豁免自然也没意义。

**验证方法**：往 `src/` 塞一个 `assert`，跑 `ruff check`——全绿就说明 S 没启用。
</details>

<details>
<summary>5. 5 类注入里哪 2 类门禁拦不住？为什么？</summary>

① 删 `from __future__ import annotations`：Python 3.11 下 `X | Y` 语法原生支持，删了确实不影响运行，不报错是对的。

② `TokenClaims.sub: str` → `sub: Any`：mypy 认为 `Any` 兼容一切，所以放行。**类型检查器没法阻止你关掉它自己**——这是所有静态检查的共同边界。

补法：评审 + 约定（`Any` 必须登记理由）。
</details>

<details>
<summary>6. 为什么 CI 要分步跑，而不是直接跑 `check.py`？</summary>

**步骤名就是诊断信息**。一条命令红了你只知道"红了"，要翻 200 行日志；分步之后，红的是 `mypy failed` 这个 step，日志只有那一步的。

本地一条命令是为了方便，CI 分步是为了诊断，两者不冲突——但**顺序要一致**。
</details>
