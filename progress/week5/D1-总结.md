## 二、逐个知识点讲透

### 1. `Any` 的传染性 ★★★★★

**一句话定义**：`Any` 是类型系统里的"通行证"——它同时兼容所有类型，并且**与它交互之后，检查结果也变成 `Any`**。

**为什么存在**：为了让渐进式迁移成为可能。一个没注解的老项目，没法一次全改完，`Any` 让"还没改的部分"不阻塞"已经改好的部分"。

**怎么用（及为什么不该滥用）**：

```python
def first_title(self) -> Any:      # 坑
    ...
```

**底层机制**：`Any` 参与类型运算的规则是"吸收"——`Any` 和任何类型做运算，结果都是 `Any`。

```python
n: int = view.first_title()   # Any 赋给 int，mypy 零报错（实测 Success: no issues found）
print(n + 1)                  # 运行时 str + int → TypeError
```

**和 `# type: ignore` 的区别（面试常问）**：

| | `# type: ignore` | `-> Any` |
|---|---|---|
| 开口范围 | **一行** | **所有用到它的地方** |
| 能否被发现 | strict 会报 `unused-ignore` | **永远不会被提醒** |
| 传播性 | 不传播 | **一路传染** |

`ignore` 是"这一行我知道，别的行照查"；`Any` 是"从这里开始别查了"。后者危险一个数量级。

**面试问法**：「你项目里用 `Any` 吗？」
30 秒版：只在两种地方用——① 第三方库没有类型信息（如 `resp.json()` 的返回值）；② 泛型容器里真的是异构数据。其余一律给具体类型。判断标准是"这个 `Any` 会不会流到别人的函数签名里"，会就不要用。

**追问链**：
→ *"第三方库返回 `Any` 怎么办？"* 三选一：装 stubs（`types-requests`）／自己写 `cast` 收窄／包一层返回具体类型。
→ *"`cast` 不也是在骗 mypy？"* 是，但 `cast` 是**局部、显式、可搜索**的，而 `Any` 是**隐式、传染、搜不到**的。
→ *"`mypy --strict` 能拦住 `Any` 吗？"* 只能拦一半：`disallow-any-generics` 拦裸容器、`warn-return-any` 拦函数返回 `Any`。但 `x: int = any_value` 这种赋值**拦不住**——因为 `Any` 兼容一切。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 函数返回 `-> Any` 图省事 | mypy 零报错；下游 `n: int = f()` 也零报错，`n + 1` 才 `TypeError` | 返回具体类型；真异构就用 `object` 或 `JsonValue` |
| 2 | 以为 `Any` 只影响那一行 | 存进变量再传两层出去，中间全静默，查不出从哪开始失守 | 记住"吸收"规则：与 `Any` 运算，结果仍是 `Any` |
| 3 | 用 `Any` 消掉 `arg-type` 报错 | 红字没了，契约也真的不再被检查 | 用 `Protocol` 或 `cast` 定点解决，别用 `Any` 抹平 |
| 4 | 把 `Any` 当 `object` 的反面用 | `def f(x: object)` 里 `x.title()` 报错，改成 `Any` 就不报了，以为"修好了" | `object` 是"能存不能用"（必须 `isinstance` 收窄），`Any` 是"能存也能用但都不查"——宽的方向相反 |
| 5 | 认为 `cast` 能替代 `Any` 的角色 | 两者混用后不知道哪个在掩盖问题 | `Any` 是**声明式放行**（隐式、传染），`cast` 是**定点担保**（显式、可搜索） |

### 2. `cast` vs `assert` ★★★★★

**一句话定义**：两者都能让 mypy 闭嘴，但一个是**声明**，一个是**证明**。

**为什么存在**：mypy 只做静态推理，它不知道运行时的事实。两种事实来源不同——
- 事实来自**你自己刚做过的检查** → `assert`
- 事实来自**外部承诺**（库的行为、上游契约）→ `cast`

**怎么用**：

```python
# 场景 A：值可能是 None，但你已有运行时证据
kb = world.kb_repo.get(world.kb_id)
assert kb is not None              # 对 mypy 是"证据"，对你是"真断言"
assert kb["doc_count"] == 1        # 没这行，mypy 报 dict | None 不能下标

# 场景 B：库说返回 str，但它没写类型
return cast(str, jwt.encode(payload, key, algorithm=alg))
```

**底层机制**：`cast` 在运行时**就是个恒等函数**——

```python
def cast(typ, val):
    return val
```

零开销、零检查。它唯一的作用是给静态分析器改写类型。**`cast` 的语义不是"转换成"，而是"我担保它是，你别查了"。**

**为什么不用 `str()` 代替 `cast`**（这是本日最关键的一个判断）：

```python
return str(jwt.encode(...))   # ✗ 运行时真的在转换
return cast(str, jwt.encode(...))  # ✓ 纯声明
```

如果 jose 哪天返回 `bytes`：`str(b"abc")` 得到 `"b'abc'"` —— **把"类型不对"这个明显错误，变成了"值被悄悄改坏"这个隐蔽错误**。而 `cast` 会让他下游在正确的位置炸。

**面试问法**：「`cast` 有什么风险？」
30 秒版：`cast` 是无检查的强制声明，担保错了 mypy 不会替你挡，错误会推迟到运行时。所以它只该用在"我确信外部库的行为"这种场合，并且必须留注释说明依据和失效条件。项目里 `cast` 的数量应该是个位数，多了说明类型设计有问题。

**追问链**：
→ *"`cast` 写错了怎么被发现？"* 只能靠测试。所以我给 `llm_client` 那处注了"W14 换 pydantic 模型校验"——用**运行时校验**替代静态担保，这是正解。
→ *"`assert` 在生产环境会被 `-O` 去掉，用它做类型收窄安全吗？"* **不安全**（这是个很好的反问点）：`python -O` 会删掉所有 assert，收窄就失效了。但本项目的 assert 是测试代码，且 `-O` 下测试根本不该跑。生产代码里该用 `if x is None: raise`，而不是 assert。
→ *"有没有两者都不用的情况？"* 有——如果是自己的代码返回了 `Optional` 而调用方不该收到 `None`，那是**设计问题**，应该在返回处就不返回 `None`，而不是在调用处 `cast`。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `cast` 消掉 Optional 报错 | 主流程正常，边界输入（id 不存在）才 `TypeError: 'NoneType' object is not subscriptable` | 先问"这里该不该是 None"；能 `assert` / `if raise` 就别 `cast` |
| 2 | `cast(str, x)` 和 `str(x)` 搞混 | `str(b"x")` → `"b'x'"`，类型错误变成**值被悄悄改坏** | `cast` 是声明不转换；要转换就明确写转换 |
| 3 | 在生产代码用 `assert` 做类型收窄 | `python -O` 剥掉所有 assert，收窄失效、程序带着 `None` 往下跑 | 生产用 `if x is None: raise`；`assert` 只留在测试里 |
| 4 | 用裸 `# type: ignore` 代替 `cast` | 将来这一行出现的**任何**错误都被吞掉 | 必须带错误码 `[arg-type]`，并写理由 |
| 5 | `cast` 越写越多（几十个） | 每个都"我担保"，实际没人验证过担保 | 个数应该是单个数字；多了说明该建 `TypedDict` / pydantic 模型 |

### 3. 名义类型 vs 结构化类型 ★★★★☆

**一句话定义**：判断"是不是这个类型"有两套规则——**名义类型看声明（有没有写继承）**，**结构化类型看形状（方法签名对不对）**。

**为什么存在**：名义类型简单、快速、无歧义，但如果两个类都实现了同样的接口（比如真 repo 和测试 fake），你不可能让 fake 去继承真 repo（会把实现一起继承过来）。

**本日的证据链**：

```
FakeKBRepo 的 6 个方法与 KBRepository 逐个对齐（签名完全一致）
   ↓ 但
mypy: Argument "repo" to "KBService" has incompatible type "FakeKBRepo"; expected "KBRepository | None"
   ×8
```

**原因**：`KBRepository` 是**普通类**（`kb_repo.py:10`），Python 的类型检查默认走名义类型——**你声明了继承才算，长得像不算**。

**为什么运行时没事**：Python 运行时是鸭子类型——"能叫能走就是鸭子"。57 个测试全部通过，说明**行为**上确实兼容。mypy 拦的是**声明**层的不兼容。两个都没错，是两套规则。

**怎么用（解法，D2 主题）**：把 `KBRepository` 声明成 `Protocol`：

```python
from typing import Protocol

class KBRepoProto(Protocol):
    def get(self, kb_id: UUID) -> dict[str, Any] | None: ...
    def create(self, user_id: UUID, data: KBCreate) -> dict[str, Any]: ...
    # ...
```

`Protocol` = "结构化类型的接口声明"。子类不需要 `class FakeKBRepo(KBRepoProto)`，只要方法签名对得上就自动兼容。

**底层机制**：名义类型的默认地位来自 Python 的对象模型——`isinstance(x, C)` 走的是 `type(x).__mro__` 里"有没有 C"这条链，纯运行时、纯声明。mypy 沿用同一套判断，所以它看的是**类声明**。

`Protocol` 是把这条路换成另一种判断：mypy 对 `Protocol` 类**只登记成员签名**，然后对实参类型做"是否具备这些成员"的结构比对。所以 `FakeKBRepo` 不需要知道自己"是" `KBRepoProto`——mypy 单向检查它"够不够"。

关键差别在于**判断时机**：`isinstance` 在运行时问"你是不是"，`Protocol` 在静态检查时问"你像不像"。前者的答案写在 `__mro__` 里，后者的答案由方法签名算出来。

**面试问法**：「Python 是鸭子类型，为什么还需要 `Protocol`？」
30 秒版：鸭子类型管运行时，`Protocol` 管**静态检查时的鸭子类型**。它让"结构一致"在类型系统里也可表达，从而能对 duck-typed 的代码做静态检查，而不用强迫实现方继承一个抽象基类。

**追问链**：
→ *"`Protocol` 和 ABC 有什么区别？"* ABC 要**显式继承**（名义）；`Protocol` 只要**结构匹配**（结构）。ABC 可以带实现，`Protocol` 通常只有签名。ABC 用 `isinstance` 能查，`Protocol` 要 `@runtime_checkable` 才能查（而且只查方法名，不查签名）。
→ *"`Protocol` 的方法参数类型能随便写吗？"* 不能，这里有**变异性**规则：参数是**逆变**（实现方必须接受得**更宽**），返回值是**协变**（实现方可以返回得**更窄**）。写反了 `Protocol` 就匹配不上——D2 实测。
→ *"为什么不用 `abc.ABCMeta.register` 虚拟子类？"* 那个是运行时注册，mypy 看不见；`Protocol` 是静态的。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 认为"方法签名一致就兼容" | 8 条 `arg-type`，全都是这个想法 | Python 默认**名义类型**：声明了继承才算，长得像不算 |
| 2 | 为消错让 fake 去继承真 repo | 把 DB 会话、SQL、连接管理一起继承进来，fake 变成半个真货，测试反而更脆 | 抽 `Protocol`，真货和 fake **都不继承**它 |
| 3 | 用"测试全绿"证明类型兼容 | 57 测全绿 + mypy 8 红，两句话都成立 | 运行时鸭子类型 ≠ 静态名义类型，是两套规则，不能用一套证明另一套 |
| 4 | 给 `Protocol` 的方法写实现体 | 能跑，但失去了"只要签名"的意义，还可能被误当真接口用 | `Protocol` 方法用 `...` 结尾；带实现的公共逻辑放 mixin 或 ABC |
| 5 | 以为 `isinstance` 能查任意 `Protocol` | `TypeError: Instance and class checks can only be used with @runtime_checkable protocols` | 加 `@runtime_checkable`，但要接受它只查方法**名**不查签名（D2 实测） |

### 4. `--strict` 到底开了什么 ★★★★☆

**一句话定义**：`--strict` 不是"更严格的检查"，而是**13 个独立开关的合集**。

**实测原文**（`mypy --help`）：

```
--disallow-any-generics       裸 list/dict 不行，必须写元素类型   → 本日 5 个 type-arg
--disallow-subclassing-any    不能继承 Any
--disallow-untyped-calls      不能调无注解的函数
--disallow-untyped-defs       自己不能写无注解的函数             → 本日 40 个 no-untyped-def
--disallow-incomplete-defs    不能只标一半参数
--check-untyped-defs          即使函数无注解也要检查函数体
--disallow-untyped-decorators 装饰器必须有类型
--warn-redundant-casts        多余的 cast 会警告
--warn-unused-ignores         过期的 type: ignore 会警告         → 本日 1 个 unused-ignore
--warn-return-any             函数返回 Any 会警告                → 本日 2 个 no-any-return
--no-implicit-reexport        不写 __all__ 不算重导出
--strict-equality             不同类型之间不能直接 ==
--extra-checks                杂项
```

**为什么存在**：渐进式迁移需要一个"中间档"。`--strict` 就是项目成熟后的目标状态，但它不强制你一次全开。

**怎么用**：本项目 `pyproject.toml` 里：

```toml
[tool.mypy]
python_version = "3.11"
strict = true
plugins = ["pydantic.mypy"]
warn_unreachable = true
disallow_untyped_decorators = false   # FastAPI 装饰器类型信息不全，暂时关掉
mypy_path = "src"
explicit_package_bases = true

[[tool.mypy.overrides]]
module = ["passlib.*", "jose.*"]
ignore_missing_imports = true         # 这两个库没有类型信息
```

**注意 `overrides` 的副作用**（这是今天埋下的一个伏笔）：`ignore_missing_imports = true` 让整个模块变成 `Any`，于是 `jwt.encode(...)` 的返回值也是 `Any`——**这正是 `no-any-return` 两个错误的来源**。`overrides` 是"局部放弃"，放弃的代价会以 `cast` 或 `Any` 的形式出现在下游。

**底层机制**：这 13 个开关看起来毫不相干，因为它们作用在 mypy 的**不同阶段**：

| 阶段 | 开关 | 在管什么 |
|---|---|---|
| 语义分析期 | `disallow-untyped-defs`、`disallow-incomplete-defs`、`disallow-any-generics`、`no-implicit-reexport` | 还没开始推理，先看**签名写得完不完整** |
| 类型检查期 | `warn-return-any`、`strict-equality`、`warn-redundant-casts`、`warn-unused-ignores`、`disallow-subclassing-any` | 推理过程中，看**类型用得对不对** |
| 调用边界 | `disallow-untyped-calls`、`disallow-untyped-decorators` | 跨函数时，看**对方有没有写** |

理解这一层，才能解释两个现象：① 为什么 `disallow-untyped-defs` 一开，错误数会**暴涨**——它让"原本被整段跳过的函数体"进入检查范围（本日 40 条就是这个）；② 为什么有些错误只有补了注解才出现——**没注解的函数体根本不参与类型检查**。

**面试问法**：「`--strict` 和老项目怎么过渡？」
30 秒版：不要一次全开。先用 `--check-untyped-defs` 让无注解函数也被检查，再按目录逐步加 `disallow-untyped-defs`，用 `[[tool.mypy.overrides]]` 给暂时不改的模块降级。关键是**新代码必须严格，老代码按模块还债**，否则一次全开会导致几百个错误、团队直接把整个检查关掉。

**追问链**：
→ *"`disallow_untyped_decorators` 为什么关掉了？"* FastAPI 的 `@router.get` 装饰器类型标注不完整，开了会误报。这是一个**有记录的、有理由的例外**——关掉的开关必须写注释说明为什么，否则下一个人不知道能不能打开。
→ *"`warn_unreachable` 为什么单独开？"* 它不在 `--strict` 里，但很值：能发现 `if isinstance(x, int)` 之后又判断 `x is None` 这种死代码。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把 `--strict` 当成"一种检查" | 开了之后不知道哪些规则在生效，报错看不懂 | 记住它是 13 个开关的合集，`mypy --help` 里逐条能查 |
| 2 | 老项目一次全开 | 几百个错误，团队直接把整个检查关掉，比不开还糟 | 按目录/模块渐进：先 `--check-untyped-defs`，再逐模块开 `disallow-untyped-defs` |
| 3 | 关掉某个开关不写理由 | 下一个人不知道能不能打开，也不敢动 | 关掉的开关**必须**写注释：为什么关、什么时候能开（本日 `disallow_untyped_decorators` 就是范例） |
| 4 | 给库开 `ignore_missing_imports` 以为无副作用 | 整个库变 `Any`，下游冒出 `no-any-return`——**自己代码没改却在报错** | 局部放弃的代价会以 `cast` / `Any` 的形式出现在下游，要一并算进成本 |
| 5 | 改了 `[tool.mypy]` 后直接跑 | 增量缓存混用新旧配置，结果忽多忽少 | 动配置后必须 `--no-incremental` 全量重算 |

### 5. PEP 561 / `py.typed` ★★★☆☆

**一句话定义**：`py.typed` 是一个**空文件**，它是 PEP 561 规定的"本包自带类型信息"的标记。

**为什么存在**：mypy 需要区分两种"第三方代码"：
- 有类型的库 → 分析它
- 没类型的库 → 当作 `Any`，报 `Skipping analyzing` 然后跳过

没有 `py.typed` 时，mypy 无法判断你的包属于哪种，默认按"没类型"处理。

**本日的证据链**（这是今天最有教育意义的一段）：

```
mypy src      → Found 3 errors          ← 看起来干净
mypy tests    → 20 errors，其中 19 条是：
                Skipping analyzing "kb_service.core.config":
                module is installed, but missing library stubs or py.typed marker
```

这 20 条里**没有一条在说你的代码**，全是"我没有分析你的代码"。

加上 `py.typed` + 两行配置后：

```
Found 58 errors in 14 files (checked 46 source files)
```

**从"3 个错误"到"46 个文件被真正检查、58 个真实问题"——报错数变多，可能是进步。**

**为什么 `mypy src` 只有 3 个**：直接给路径时，mypy 把文件当"源码"直接分析；`mypy tests` 里 `import kb_service` 走的是"已安装包"路径，于是触发 PEP 561 判定。

**怎么用**：

```powershell
New-Item src\kb_service\py.typed -ItemType File -Force
```

```toml
mypy_path = "src"
explicit_package_bases = true
```

两行配置的作用：`mypy_path` 告诉 mypy 去哪找 `kb_service`；`explicit_package_bases` 解决"同名模块被当成两个"（`tests/conftest.py` 和 `kb_service` 都在 `src` 外时，mypy 会把模块名算错）。

**底层机制**：mypy 判断"一个 import 该去哪找类型"，走的是**三步查找**：

```
import kb_service.core.config
  ① 沿 sys.path 找到 kb_service/（源码目录）或 kb_service-*.dist-info（安装元数据）
  ② 在该目录下找 py.typed   →  有：读 .py 里的行内注解
                             →  没有：继续
  ③ 找 stub 包 types-kb-service（几乎不存在）→ 还是没有：Skipping analyzing，整体当 Any
```

关键在**第 ② 步只看包根目录**（`src/kb_service/py.typed`），不看子模块。所以标记文件放错层级（比如放进 `kb_service/core/`）等于没放。

`py.typed` 之所以是**空文件**却有效：mypy 只判断它**存在与否**，不读内容——它是一个零字节的信号，PEP 561 的规范原文只要求"必须存在于 wheel 的包目录中"。`partial` 是唯一的可选内容（声明"我只标注了一部分"），用于那种"只有核心 API 有类型、内部模块没有"的库。

**面试问法**：「`py.typed` 是干什么的？」
30 秒版：PEP 561 规定的类型信息标记文件，空文件即可。有它的包，mypy 会读包内的注解；没有的，mypy 认为这个包不带类型，直接当 `Any` 处理并报 `Skipping analyzing`。自己写库发布时一定要放，否则用户装完还是没类型提示。

**追问链**：
→ *"`py.typed` 里能写东西吗？"* 能，PEP 561 支持写 `partial`（声明这是部分类型化的包）——但绝大多数情况留空。
→ *"为什么 `mypy src` 和 `mypy tests` 结果差这么多？"* 因为前者走"源文件"路径，后者走"已安装包"路径，PEP 561 判定只作用于后者。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只看 `mypy src` 的 3 个错误就以为项目干净 | 真正被检查的代码只有一半，tests 里的问题全被跳过 | 判断是否生效看 **`checked N source files`**，不看错误数 |
| 2 | 把 `Skipping analyzing` 当代码 bug 去改 | 改了一下午代码，这个错误一条也没消 | 它说的是"我没分析你"，不是"你写错了"；先补 `py.typed` |
| 3 | 以为 `py.typed` 里必须写内容 | 建了个空文件又删掉，怕有问题 | 空文件即可；PEP 561 允许写 `partial`，但极少用 |
| 4 | 只建 `py.typed` 不加 `mypy_path` | 仍然报 `Cannot find implementation or library stub` | 标记文件 + 两行配置是**一套**，缺一不可 |
| 5 | 多路径混合检查时项目包被判第三方 | **没改过的文件**突然报 import 分组错（如 `conftest.py` 的 I001） | 工具的"配置基准"可能被上移，让两处配置指向同一物理目录 |

### 6. 注解在运行时到底生不生效 ★★★☆☆

**一句话定义**：注解**不会**改变运行时行为，它只是被存进 `__annotations__` 这个字典。

**实测**：

```python
def add(a: int, b: int) -> int:
    return a + b

add("1", "2")      # → "12"，不报错
add.__annotations__ # → {'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

**为什么存在**：Python 的设计哲学——注解是**给工具看的元数据**，不是运行时约束。这让注解可以零成本地被忽略，也让"渐进式加类型"成为可能。

**怎么用（会真的读注解的四种场景，面试加分项）**：有几种东西确实会在运行时读注解：
- `pydantic` / `dataclasses`：读注解来生成校验逻辑/`__init__`
- `FastAPI`：读注解来生成 OpenAPI schema 和参数解析
- `typing.get_type_hints()`：可以取出注解（会解析字符串前向引用）
- `from __future__ import annotations`：注解变成**字符串**，不立即求值

最后一条很重要：本项目所有文件都用了它，好处是可以在定义前引用还没定义的类（前向引用不用加引号），代价是运行时拿到的是字符串。

**底层机制**：注解的落点在**函数对象 / 类对象**的属性上。

```python
def add(a: int, b: int) -> int: ...
add.__annotations__   # {'a': <class 'int'>, 'b': <class 'int'>, 'return': <class 'int'>}
```

`def` 语句执行时，解释器把注解表达式**求值一次**，装进一个 dict 挂到函数对象上，之后再也不碰。所以：

- 注解**不是**签名的一部分——`inspect.signature` 读的是它，但调用时不校验；
- 注解**不是**字节码里的检查指令——`add` 的字节码只有一次 `BINARY_OP`，没有任何类型判断；
- 开销只在**定义时**一次（模块导入时），不在调用路径上。这就是"零运行时开销"的准确含义。

加了 `from __future__ import annotations` 后，求值这一步被跳过，`__annotations__` 里存的是**字符串** `'int'`——连定义时的开销也没了，代价是任何要"用"注解的代码都得先 `get_type_hints()` 解析。

**面试问法**：「Python 注解会影响性能吗？」
30 秒版：运行时零开销。注解只在定义时被求值一次并存进 `__annotations__`（用了 `from __future__ import annotations` 连求值都省了，存的是字符串）。检查全部发生在静态分析阶段。

**追问链**：
→ *"`list[int]` 在 Python 3.8 能用吗？"* 运行时不能，`list[int]` 在 3.9 才支持 `__class_getitem__`。但加了 `from __future__ import annotations` 后，注解不求值，所以 3.8 也能写——**这是 `from __future__` 的另一个实际价值**。
→ *"pydantic 怎么用注解做校验？"* 它在类创建时读 `__annotations__`，为每个字段建 validator。所以 pydantic 模型的字段注解**写错了会真的错**——这是"注解影响运行时"的典型反例。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为加了注解运行时会校验参数 | `add("1", "2")` 照样返回 `"12"`，没有任何警告 | 注解不改变运行时；要运行时校验用 pydantic / 显式 `isinstance` |
| 2 | 加了 `from __future__ import annotations` 后直接读 `__annotations__` | 拿到的是字符串 `'int'` 而不是 `int`，任何基于注解的反射都失效 | 用 `typing.get_type_hints()` 解析（它会求值字符串） |
| 3 | 在 3.8 直接写 `list[int]` | `TypeError: 'type' object is not subscriptable` | 加 `from __future__ import annotations`，或写 `List[int]` |
| 4 | 以为 pydantic 模型字段注解写错"反正也不检查" | 模型创建时就报错，或校验行为悄悄变了 | pydantic / FastAPI **真的读**注解，这里的注解是运行时代码的一部分 |
| 5 | 用注解当文档替代校验 | 以为写了 `-> int` 调用方就不会传错 | 注解只约束**看代码的人**和**静态检查器**，不约束运行时 |

### 7. 泛型参数缺失（`type-arg`）★★★☆☆

**一句话定义**：`list` / `dict` 不带元素类型，等于说"里面装什么都行"，mypy 也就什么都不能检查。

**为什么存在**：为了兼容 Python 2 时代的写法，裸 `list` 是合法的。但 `--strict` 的 `disallow-any-generics` 会禁止它。

**怎么用（本日的 5 处）**：

| 原来 | 改成 | 位置 |
|---|---|---|
| `dict` | `dict[UUID, dict[str, Any]]` | `test_unit_demo.py` |
| `dict` | `dict[str, Any]` | `test_rag_async.py` |
| `list` | `list[tuple[str, tuple[Any, ...]]]` | `_calls_named` 的返回类型 |

**底层机制**：裸 `dict` 等价于 `dict[Any, Any]`。所以 `row["title"]` 得到的类型是 `Any`，后面所有操作都不检查——**这正是 `Any` 传染的另一个入口**。

**面试问法**：「`dict` 和 `dict[str, Any]` 有区别吗？」
30 秒版：运行时完全没区别（都是 `dict`）。静态上有本质区别：裸 `dict` 等价 `dict[Any, Any]`，读出来任何值都是 `Any`，不检查；`dict[str, Any]` 至少约束了键必须是 `str`，而且 `dict` 本身缺少参数会被 `--strict` 报错。

**追问链**：
→ *"值也是 `Any`，那写 `dict[str, Any]` 有意义吗？"* 有——键的类型被约束了，而且**它是一个"我知道这里会填类型"的声明**。更好的写法是定义 `TypedDict`，那样连值的结构都能检查（W5 后续内容）。
→ *"什么时候可以用 `dict[str, Any]`？"* 只在"从 JSON 解析出来、结构外部决定"的边界上。一旦这个 dict 进入核心逻辑，就该转成 `TypedDict` 或 pydantic 模型。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 写裸 `dict` 觉得"反正都是 dict" | 取出来的值是 `Any`，后续所有操作静默不查 | 补参数：`dict[str, Any]` 至少约束键类型 |
| 2 | 认为 `dict[str, Any]` 值还是 `Any` 所以没意义 | 放弃了键约束 + 完全不做结构检查 | 它至少声明了"我知道这里该有类型"；结构检查交给 `TypedDict` |
| 3 | 让 `dict[str, Any]` 贯穿核心业务逻辑 | 字段名拼错（`row["ttile"]`）也不报错，运行时 `KeyError` | 边界处（JSON 解析完）立刻转 `TypedDict` / pydantic 模型 |
| 4 | 反向过度收紧成 `dict[str, object]` | 取值后每处都要 `isinstance` 收窄，代码写不动 | 边界用 `Any`，核心用 `TypedDict`——按"谁知道结构"来分 |
| 5 | 把 `type-arg` 当成纯体力活批量替换 | 补了个更宽的参数，报错消失但没变好 | 每补一处都问"这个 dict 里到底装什么" |

### 8. `type: ignore` 的生命周期 ★★☆☆☆

**一句话定义**：`# type: ignore[code]` 是给 mypy 的"这一行别报"指令。

**为什么存在**：因为**静态检查器不可能永远正确**。mypy 要根据静态信息推断，而总有它推不出的场景：库的类型声明写错、动态生成的属性、框架的元编程（`__getattr__`、装饰器改写签名）。没有逃生口，这些地方会导致"要么关掉整个检查，要么改坏代码"，两条路都比留一个显式的洞更糟。

所以 `type: ignore` 的设计意图是**技术债的显式标记**：把"这里我知道有问题"写进代码，可搜索、可审计、可定期清理。它不是"解决问题"，是"记账"。

**本日的那一处**：

```python
return Settings()  # type: ignore[call-arg]   ← 报 unused-ignore，删掉
```

**为什么它变成废物**：pydantic v2 的 mypy 插件**知道** `BaseSettings` 的必填字段可以来自环境变量，所以无参调用是合法的。这条 ignore 是更早版本留下的。

**怎么用（底线规则）**：
1. **必须带错误码**：`# type: ignore[call-arg]`，不要裸 `# type: ignore`——否则它会把将来任何错误都吞掉。
2. **必须写理由**：为什么需要这一行，什么条件下能删。
3. **strict 会帮你清理**：`warn_unused_ignores` 让过期的 ignore 变成错误。

**底层机制**：mypy 不是"运行到这里跳过"，而是**读源码文本**。

CPython 的 `ast` 在解析时会把 `# type: ignore` 注释收进 `Module.type_ignores`（一项带行号的列表），mypy 拿到 AST 后先用这份列表建一张"抑制表"，再跑类型检查；每条诊断产生后去表里查**行号**，命中就丢弃。带码（`[call-arg]`）时还要**错误码也对上**才丢弃，这就是为什么裸 ignore 更危险——它等于"这一行不论什么码都丢"。

因为匹配的是**行号**，所以有两个可预期的后果：① 代码挪了行、ignore 没跟着挪，就失效（报 `unused-ignore`）；② 一行写两条 `ignore` 只有第一条生效，这类问题肉眼极难发现。

**面试问法**：「`# type: ignore` 该不该出现在生产代码里？」
30 秒版：可以有，但必须满足三条——带错误码、带理由、数量可控。它是"技术债的标记"，不是"问题解决"。一个项目里 ignore 的数量应该是两位数以内并能逐个解释，如果需要几十个，说明类型设计或依赖选型有问题。

**追问链**：
→ *"`unused-ignore` 为什么是错误而不是警告？"* 因为过期的 ignore 会**掩盖未来出现的同类错误**。删掉它是纯收益。
→ *"给第三方库开 `ignore_missing_imports` 和写 `type: ignore` 有什么区别？"* 前者是**模块级**（整个库当 Any），后者是**行级**。前者更粗暴但更好维护，适合"这个库完全没类型"的情况。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 写裸 `# type: ignore` 不带错误码 | 这一行以后出现的**任何**错误都被吞掉，包括你新写的 bug | 必须带码：`# type: ignore[call-arg]` |
| 2 | 写了 ignore 不写理由 | 半年后没人敢删，也不敢改，变成永久化石 | 写成"为什么需要 + 什么条件能删"，最好带日期或 issue 号 |
| 3 | 用 ignore 解掉本来能修的错 | 债越积越多，最后几十个 ignore 谁也不敢动 | 先分清"是我的类型写错了"还是"库没类型"；前者改代码，后者才开口子 |
| 4 | 升级依赖后不复查旧 ignore | 变成 `unused-ignore`（本日实例：pydantic v2 插件已支持无参调用） | `warn_unused_ignores`（`--strict` 自带）会替你抓出来 |
| 5 | 以为 ignore 和 `cast` 可以互换 | 不知道哪个在掩盖问题、覆盖面多大 | ignore 是"整行不查"，`cast` 是"这一个值的类型由我担保"，粒度不同 |

## 三、30 秒答案集（面试速答）

1. **类型注解影响运行时吗？** 不影响。只存进 `__annotations__`，检查全在静态阶段。但 pydantic/FastAPI 会主动读它。
2. **`Any` 和 `object` 有什么区别？** `object` 是最宽的具体类型（能存任何值，但**不能**当任何东西用，必须收窄）；`Any` 是"放弃检查"（能当任何东西用，且传染）。
3. **`cast` 是什么？** 运行时的恒等函数，静态的强制声明。语义是"我担保，你别查"。
4. **`cast` 和 `assert` 怎么选？** 有运行时证据用 `assert`，只是担保外部库行为用 `cast`。
5. **`--strict` 是什么？** 13 个开关的合集，不是一个检查。
6. **`py.typed` 干什么？** PEP 561 标记，告诉 mypy"这个包自带类型信息"。
7. **为什么 Python 是鸭子类型还要 `Protocol`？** 把"结构兼容"这件事搬到静态检查里。
8. **`Protocol` 和 ABC 区别？** 结构匹配 vs 名义继承；`Protocol` 无需实现方修改代码。
9. **`type: ignore` 怎么用才对？** 带错误码 + 带理由 + 数量可控。
10. **mypy 报错数突然变多是怎么回事？** 大概率是检查范围变大了（补了 `py.typed`、补了注解），不是代码变差了。先看 `checked N source files` 这个数字。

## 四、白板手写靶（必须能默写）

**靶 1：写一个 `Protocol`**（D2 会用到）

```python
from typing import Any, Protocol
from uuid import UUID

class KBRepoProto(Protocol):
    def get(self, kb_id: UUID) -> dict[str, Any] | None: ...
    def list_by_user(self, user_id: UUID, offset: int, limit: int
                     ) -> tuple[list[dict[str, Any]], int]: ...
```

要点：不用继承、只要签名、`...` 结尾。

**靶 2：Optional 收窄的三种写法**

```python
# ① assert（测试代码）
assert kb is not None

# ② if 提前返回（生产代码）
if kb is None:
    raise NotFoundError(...)

# ③ 赋值给新变量（mypy 认这个）
if (found := repo.get(kb_id)) is None:
    raise NotFoundError(...)
use(found)          # 这里 mypy 知道不是 None
```

**靶 3：三种让 mypy 闭嘴的手段，并说出代价**

| 手段 | 代价 |
|---|---|
| `cast(T, x)` | 无检查，错了运行时才炸 |
| `# type: ignore[code]` | 只影响一行，strict 会提醒过期 |
| `-> Any` | 传染性最强，永不被提醒 |

## 六、可以讲成故事的三段

**故事 A：「20 个错误，没有一条在说我的代码」**
接手项目后加类型门禁，`mypy tests` 报 20 个错。逐条读发现全是 `Skipping analyzing ... missing py.typed marker`——mypy 根本没分析代码。补一个空文件 `py.typed`，错误从 20 降到 1，同时真正的检查开始了：58 个真实错误浮现。**教训：判断类型检查是否生效，先看 `checked N source files`，不要看错误数。**

**故事 B：「运行时全绿，静态全红」**
`FakeKBRepo` 和真 repo 的六个方法签名逐一一致，57 个测试全过。但 mypy 报 8 条 `arg-type`。原因是 repo 是普通类，走名义类型——长得像不算，声明了继承才算。解法不是给 fake 加继承（会把实现一起继承过来），而是把接口声明成 `Protocol`，让"结构匹配"在类型系统里可表达。

**故事 C：「`cast` 掩盖了一个 None」**
第四档代码里 `cast(dict[str, Any], self.find(doc_id) or None)`：`{} or None` 先得到 `None`，`cast` 再把 `None` 说成 dict。主流程正常，查不存在的 id 直接 `TypeError: 'NoneType' object is not subscriptable`。`cast` 不是"转换"，是"闭嘴"——**它不会让代码变安全，只会让 mypy 不再提醒你**。

## 七、能力画像与 D2 衔接

**本日强项**
- 三个类型的坑 3/3 全中，且能用"太宽/没检查/硬说成"自己的话表述——说明不是背的
- 第 2 条（`-> Any`，运行时无任何症状）能找出来，是读代码而不是跑代码的结果

**本日待补**
- 第 3 条表述精度：说"硬说 `{} or None` 为字典"，漏了"`{} or None` 先得到 `None`"这一步。因果链要说到"谁制造了错误，谁掩盖了错误"。
- `object` vs `Any` 的区别还没被问到：`object` 是**最窄的使用面**（什么都不能干），`Any` 是**最宽的使用面**（什么都能干）。两者都"宽"，但宽的方向相反。

**D2 预告**
8 个 `arg-type` 不会自己消失。D2 用 `Protocol` 收线，会顺带撞上两个新东西：
1. **变异性**：`Protocol` 的方法参数是**逆变**的，实现方必须接受得**更宽**；返回值**协变**，可以返回得**更窄**。写反了匹配不上。
2. **`Protocol` 要不要 `@runtime_checkable`**：不做的话 `isinstance` 会报错；做了的话 `isinstance` 只查方法名不查签名。
