## 二、逐个知识点讲透

### 1. `Protocol` 与结构化类型

**一句话定义**：`Protocol` 是只声明能力、不提供实现的类，它让 mypy 改按"方法签名对不对得上"判兼容，而不是按"有没有继承"。

**为什么存在**：普通类走**名义类型**（血缘）。`KBService.__init__` 标 `repo: KBRepository` 时，mypy 判的是"你是不是这个类的子孙"，连 `FakeKBRepo` 六个签名全对的方法都不看，直接判 8 个 `arg-type`。没有 `Protocol`，想让替身过关只有两条烂路：替身继承真实现（失去隔离、被真类的 `__init__` 连累）或到处 `cast`（把门禁关掉）。而第三方类（W7 的 SQLAlchemy session 包装）你根本改不了继承，没有结构化类型依赖倒置就落不了地。

**怎么用**（本日真实落点，`src/kb_service/repositories/protocols.py`）：

```python
class KBRepo(Protocol):
    def create(self, owner_id: UUID, data: KBCreate) -> dict[str, Any]: ...

    def get(self, kb_id: UUID) -> dict[str, Any] | None: ...
    # ... 其余 5 个，判据 = KBService 用到哪些

class DocReader(Protocol):
    """只读视角：RagService 只检索，不需要能写。"""
    def list_by_kb(
        self, kb_id: UUID, offset: int, limit: int
    ) -> tuple[list[dict[str, Any]], int]: ...

class DocRepo(DocReader, Protocol):   # 第二个 Protocol 不能省
    def create(self, kb_id: UUID, data: DocCreate, *, status: str = ...) -> dict[str, Any]: ...
```

service 侧只换标注：`def __init__(self, repo: KBRepo | None = None)`——**默认实现 `KBRepository()` 一个字不动**，它只是"其中一个适配器"。

**底层机制**：mypy 对 `Protocol` 类型做**成员匹配**——被检类的每个方法与协议对应方法做签名兼容判定（参数逆变、返回协变，见知识点 2）。匹配发生在静态分析期，**运行时零开销零强制**：`FakeKBRepo` 不 import 协议、不知道协议存在，Python 解释器根本不参与。协议类实例化会 `TypeError: Protocols cannot be instantiated`，但显式继承它的子类可以实例化（那就退化成普通类了）。方法体的 `...` 是空语句；出现在**默认值**位置时是另一个意思——"有默认值但值不重要"，且"有没有默认值"参与匹配（实测：协议 `x: int = 0`、实现 `x: int` 必报 `Expected: def f(self, x: int = ...)`）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 让替身继承真实现消 `arg-type` | 测试开始碰真实 `store`，用例互相污染 | 用 `Protocol`，不用继承 |
| 2 | 协议照抄实现方**全部**方法 | 替身被迫写一堆永不调用的空方法 | 只写依赖方用到的；太胖拆窄协议 |
| 3 | `class DocRepo(DocReader)` 漏写第二个 `Protocol` | `DocRepo` 变普通类，可实例化，结构化匹配失效 | 继承协议必须再写一次 `Protocol` |
| 4 | 协议文件 import 具体实现类 | 循环 import / 分层倒置 | 协议只依赖 `schemas` 和标准库 |
| 5 | 方法体写 `pass` 而不是 `...` | 能跑，但读者以为"应该有实现" | 协议里一律 `...` |

**面试问法**：*"Protocol 和 ABC 什么区别？为什么有了 ABC 还要它？"*

**30 秒版**："ABC 要求实现方显式继承，走名义类型；Protocol 只要求方法签名对得上，走结构化类型。关键差别在第三方类——我没法让 SQLAlchemy 的类继承我的 ABC，但它只要长得像我的 Protocol 就能被注入。所以 Protocol 适合描述'我要什么能力'，ABC 适合'提供共享实现加强制子类填坑'。我项目里三个 service 现在都依赖协议，FakeKBRepo 一行继承都没写。"

**追问链**：

→ *"Protocol 能实例化吗？"* 不能，`TypeError: Protocols cannot be instantiated`；但显式继承的子类可以，且那时它就是普通类了。

→ *"运行时能检查吗？"* 默认不能（直接 TypeError），加 `@runtime_checkable` 后可以——但只查成员名存在性，不查签名（详见知识点 6）。

→ *"协议在运行时有任何强制力吗？挖到底。"* 零。协议匹配只存在于 mypy 的静态分析里；运行时 `FakeKBRepo` 和协议类彼此完全不认识，`isinstance` 是唯一入口还只查名字。所以协议的"契约保证"完全靠两样外部东西：CI 里的 mypy 步骤 + 测试。这也解释了为什么 D6 要把 mypy 真正进门禁——**没有门禁的协议只是注释**。

### 2. 变异性：参数逆变 / 返回协变

**一句话定义**：变异性描述"子类型关系沿类型构造器怎么传递"；落到函数签名上就是——实现方的参数必须比协议**更宽或相等**（逆变），返回值必须比协议**更窄或相等**（协变）。

**为什么存在**：`Protocol` 的全部意义是"能替换"，而替换的判据只有一条：原来能跑的调用，换实现后**一个都不能炸**。参数是调用方喂进来的，新实现必须吃下所有原本合法的输入；返回值是调用方按协议拿去用的，新实现必须给到至少协议承诺的精度。两个方向的风险承担方相反，所以规则相反。

**怎么用**（四方向实测表，全部在本机 3.11 跑过）：

| 方向 | 协议声明 | 实现写成 | 结果 |
|---|---|---|---|
| 参数写宽 | `k: UUID` | `k: object` | ✅ 通过 |
| 参数写窄 | `k: UUID` | `k: int` | ❌ `Expected/Got` 冲突 |
| 返回写窄 | `-> dict \| None` | `-> dict` | ✅ 通过 |
| 返回写宽 | `-> dict \| None` | `-> object` | ❌ `Expected/Got` 冲突 |

写窄时的真实报错结构（背下来，认得出就不慌）：

```
note: Following member(s) of "Fake" have conflicts:
note:     Expected:
note:         def get(self, k: UUID) -> dict[str, object] | None
note:     Got:
note:         def get(self, k: int) -> dict[str, object] | None
```

**底层机制**：mypy 在协议匹配时对每个成员做**签名子类型判定**：`impl.__call__` 的参数类型必须是协议参数类型的**超类型**（消费方收得更宽），返回类型必须是协议返回类型的**子类型**（生产方给得更窄）。形式化说：`def (A)->R` 是 `def (B)->S` 的子类型当且仅当 `B <: A` 且 `R <: S`。默认值是参数签名的延续——协议承诺"可省略"，实现要求"必填"就违反了"更宽"原则（实测报 `Expected: def f(self, x: int = ...)`）。`Callable[[A], R]` 的变异性与此同构。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为"参数类型必须一样"才兼容 | 见 `object` 通过觉得工具抽风 | 逆变：更宽合法；协变：更窄合法 |
| 2 | 协议有默认值、实现写成必填 | `Expected: x: int = ...` / `Got: x: int` | 实现方只能更宽松，不能更严格 |
| 3 | 用 `# type: ignore[arg-type]` 压逆变冲突 | 报告绿，但该输入下静默出错 | 修签名；ignore 只给"知道得更多"的边界 |
| 4 | 返回值故意声明成 `object` 图省事 | 调用方被迫 `cast`，类型保护失效 | 声明真实的最窄类型 |
| 5 | 把 `list` 写进协议的返回/参数 | 要么报 invariant 要么限制调用方 | 协议里用 `Sequence`/`Iterable` |

**面试问法**：*"什么是协变逆变？为什么函数参数和返回值的方向相反？"*

**30 秒版**："变异性是子类型关系在类型构造下的传递规则。参数逆变——实现必须能吃下协议方可能传的一切，所以只能更宽；返回协变——调用方按协议用返回值，所以实现只能给得更具体。方向相反是因为参数往里、返回值往外，风险承担方不同。我的第四档题里就埋了一个逆变写反的坑：fake 的 find 参数从 UUID 收窄成 str，比较恒 False，报告命中数静默归零。"

**追问链**：

→ *"list[str] 能当 list[object] 用吗？"* 不能，`list` 是**不变**的——它能 append，允许的话就能往一个实际装 str 的列表里塞 int。只读的 `Sequence[object]` 才收 `list[str]`（详见知识点 5）。

→ *"Callable 呢？"* 参数逆变、返回协变，和函数签名同构；`Sequence[_T_co]` 的 `_T_co` 后缀就是标准库在声明协变。

→ *"自己写泛型类时怎么声明变异性，挖到底。"* `T_co = TypeVar("T_co", covariant=True)` / `T_contra = TypeVar("T_contra", contravariant=True)`。mypy **会强制执行**：把协变 TypeVar 用在参数位置会报 `Cannot use a covariant type variable as a parameter`。判断口诀就是消费/生产：只出现在返回位置 → covariant；只出现在参数位置 → contravariant；两处都有 → invariant（不加标记）。标准库源码 `collections.abc` 里全是这套标记，读得懂就够，自己定义容器类才会真写。

### 3. 接口隔离：窄协议拆分

**一句话定义**：协议的内容 = **依赖方需要的最小能力集合**，不是实现方拥有的全部能力。

**为什么存在**：`RagService` 只调 `doc_repo.list_by_kb` 一个方法。如果它依赖 5 个方法的胖 `DocRepo`，那么将来 `create` 签名一变，一个只读的服务被迫跟着改；测试替身也被迫实现 4 个永远不被调用的空方法。胖接口把"不相关的变化"传导给了不相关的依赖方。

**怎么用**（本日真实改动）：

```python
class DocReader(Protocol):
    """只读视角：RagService 只检索，不需要能写。"""
    def list_by_kb(self, kb_id: UUID, offset: int, limit: int) -> tuple[list[dict[str, Any]], int]: ...

class DocRepo(DocReader, Protocol):   # 胖协议继承窄协议，DocService 继续用它
    ...

# rag_service.py —— 换成窄协议，FakeDocRepo 一个字不用改
def __init__(self, doc_repo: DocReader | None = None) -> None:
```

**底层机制**：结构化类型下，"实现窄协议"只需要相应子集的方法——`FakeDocRepo`（只有 `list_by_kb`）直接满足 `DocReader`。这就是协议比 ABC 灵活的地方：ABC 下拆接口意味着动继承树，协议下拆接口只是"换一个更小的能力清单"，**实现方甚至不需要知道拆分发生过**。实测效果：8 错 → 5 错（补 `incr_doc_count`）→ 2 错（拆 `DocReader`）→ 0 错（复用 fake），最后一步 `FakeDocRepo` 零改动。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 报"缺方法"就急着补全 | 替身膨胀，空方法还得维护 | 先查依赖方实际用了几个 |
| 2 | 一上来就拆微协议 | 文件里十几个单方法协议没人用 | 出现第二个不同需求的依赖方再拆 |
| 3 | 拆完忘了让胖协议继承窄协议 | 两处重复声明，改一处漏一处 | `class DocRepo(DocReader, Protocol)` |
| 4 | 用"实现方有什么"决定协议内容 | 协议越写越胖 | 用"依赖方用什么" |

**面试问法**：*"说说接口隔离原则在你项目里的实际应用。"*

**30 秒版**："我的 RagService 只做检索，原来却依赖五方法的 DocRepository。按 Protocol 落地时我把它拆成只读的 DocReader，RagService 只依赖窄的，测试替身一个字没改就通过。判断标准是'依赖方用了哪些方法'，不是'实现方有哪些'。收益是 create 签名将来变了，只读服务完全不受牵连。"

**追问链**：

→ *"这和依赖倒置什么关系？"* ISP 管"接口多宽"，DIP 管"依赖指向谁"——这次改动同时做了两件事：依赖从具体类转向抽象（DIP），接口从胖变窄（ISP）。面试里分开说，别搅在一起。

→ *"会不会拆太碎？挖到底。"* 判据是**使用方的数量与差异**：只有一个使用方时不要预拆（YAGNI），第二个使用方出现且能力需求不同时再拆。反过来有个更实用的信号：**替身被迫写空方法**，说明协议已经超出某个使用方的需要。极限情况是一个方法一个协议（Go 的 `io.Reader`/`io.Writer` 就是这么极端的），什么时候到那个程度？当"能不能读"和"能不能写"真的会被独立组合时——比如 `io.ReadWriter` 就是两个单方法协议的组合。

### 4. 依赖倒置的落点

**一句话定义**：高层模块（service）依赖抽象（`Protocol`），不依赖具体实现（`KBRepository`）。

**为什么存在**：D1 结束时 `repo: KBRepository | None` 写的是"我要这个类本身"。换成 `KBRepo` 后写的是"我要一个能存取知识库的东西"。前者把 service 和内存实现焊死，后者让 W7 换 SQLAlchemy 时 service 一行不改。

**怎么用**：本日改动的三行就是落点——`kb_service.py:18`、`doc_service.py` 构造、`rag_service.py:22`，全部从具体类换成协议；同时**保留** `repo or KBRepository()` 作为默认装配（组合根的职责）。

**底层机制**：这是纯静态层面的解耦——mypy 只检查"传进来的对象满足协议"，运行时靠鸭子类型自然工作。依赖方向上：`services → protocols ← repositories`，`protocols.py` 只 import `schemas` 和标准库，**不 import 任何 repo 实现**，所以不会出现 service→repo→service 的环。这是分层架构"依赖指向抽象"在文件层面的直接体现。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 协议文件 import repo 实现 | 循环 import | 协议只认 schemas |
| 2 | 把"默认实现"也塞进协议 | 协议长出构造逻辑 | 默认装配留在组合根（service 构造函数） |
| 3 | 以为依赖倒置=必须用 DI 框架 | 过度设计 | 构造函数注入就够了，W9 之前不引框架 |

**面试问法**：*"依赖倒置在你的项目里怎么体现的？"*

**30 秒版**："我的 service 构造函数参数全是 Protocol 类型，比如 KBRepo；具体实现 KBRepository 只在 `repo or KBRepository()` 这一处作为默认值出现。依赖方向是 service 指向协议文件，协议文件谁也不依赖，实现在另一侧指向协议。W7 换 SQLAlchemy 时理论上是新建一个 repo 类、改一行组合根，service 层零改动。"

**追问链**：

→ *"那测试怎么受益？"* 替身不需要继承任何东西，长得像就行——FakeKBRepo 现在零继承。

→ *"组合根是什么？挖到底。"* 组装依赖图的唯一位置。本项目现在很小：service 构造函数的 `or` 默认值就是组合根；FastAPI 侧是 `Depends` 工厂（api 层）。原则是**组装信息只允许出现在组合根**——如果 `RagService` 内部自己 `KBService()` 而不接受注入，它就偷偷把"用哪个实现"的决策抄进了业务层，换实现时要改业务代码。大型项目用容器（`dependency-injector` / FastAPI Depends）把组合根集中成一处。

### 5. 容器不变性：`list` vs `Sequence`

**一句话定义**：可写容器（`list`/`dict`/`set`）的类型参数是**不变**的；只读协议（`Sequence`/`Iterable`/`Mapping`）是**协变**的。

**为什么存在**：如果 `list[str]` 能当 `list[object]` 传，函数里就能 `xs.append(42)`——往一个实际装 str 的列表里塞 int，原列表的类型保证被破坏。**可写=不变**是防污染的硬规则。

**怎么用**：

```python
def take_list(xs: list[object]) -> None: ...   # 只收 list[object]
def take_seq(xs: Sequence[object]) -> None: ...  # 收 list[str]、tuple[str, ...] 都行

ys: list[str] = ["a"]
take_list(ys)  # error: "list" is invariant
take_seq(ys)   # OK
```

真实报错还带教学提示：

```
note: "list" is invariant -- see https://mypy.readthedocs.io/...
note: Consider using "Sequence" instead, which is covariant
```

**底层机制**：`Sequence` 在标准库里声明为 `Sequence[_T_co]`（协变标记），因为它**没有写方法**；`MutableSequence[_T]` 不变，因为 `__setitem__`/`append` 既有读又有写。规则一句话：**类型参数出现在"生产"位置→协变，出现在"消费"位置→逆变，两处都有→不变**。`Mapping[K, V]` 的 K 不变（`__getitem__` 和 `keys()` 使 K 既是产出又被用于查找约束），V 协变。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 函数参数用 `list[X]` | 调用方传 `list[子类]` 被拒 | 只读就写 `Sequence[X]` / `Iterable[X]` |
| 2 | 返回值用 `Sequence[X]` | 调用方想 `append` 被拒 | 返回值声明真实能力：可变就 `list` |
| 3 | 以为 `dict` 的 key 也协变 | 查找语义破坏 | K 不变，V 协变（只读 `Mapping` 时） |

**面试问法**：*"为什么 list 是 invariant 而 Sequence 是 covariant？"*

**30 秒版**："因为 list 可写。假如 list[str] 能当 list[object] 传，函数里 append 一个 int 就污染了原列表，所以类型参数必须严格一致。Sequence 没有写方法，只会产出 T，所以协变安全。所以我的习惯是：函数参数收窄能力用 Sequence/Iterable，返回值按真实能力声明。"

**追问链**：

→ *"dict 呢？"* `Mapping` 的 V 协变、K 不变；`dict` 整体不变（可写）。

→ *"那 `tuple[str, ...]`？"* 协变——tuple 不可变，只产出。

→ *"这个规则和函数参数的逆变是一回事吗？挖到底。"* 是同一套规则的两个投影。把容器看成一个"提供 `__getitem__` 的东西"：`list[str]` 的 `__getitem__(int) -> str`，产出 `str`，所以容器协变性由元素的生产方向决定；而 `list.append(x: str)` 是消费 `str`，这个消费方向的存在把整个类型参数拖成不变。也就是说**可写容器 = 生产者 + 消费者二合一 = 双向都要满足 = 不变**。

### 6. `@runtime_checkable` 的边界

**一句话定义**：给协议开 `isinstance` 的许可，但检查粒度只有"成员名存在性"，不含签名。

**为什么存在**：结构化匹配需要逐成员比对，mypy 在静态期做没问题，运行时做有开销且有歧义（异步函数算不算方法？属性算不算？），所以 PEP 544 要求显式声明才开放。

**怎么用**（实测三个事实）：

```python
@runtime_checkable
class Repo(Protocol):
    def get(self, k: str) -> int: ...

class Liar:
    def get(self) -> None: ...     # 签名完全不对

isinstance(Liar(), Repo)   # True  ← 假阳性
isinstance(object(), Repo) # False ← 成员缺失才 False

# 不加装饰器时：
isinstance(Fake(), Repo)   # TypeError: Instance and class checks can only be used
                           #        with @runtime_checkable protocols
```

**底层机制**：`@runtime_checkable` 往协议类挂一个自定义 `__instancecheck__`，只做 `hasattr` 式的成员名扫描。签名是静态信息——注解运行时已被丢弃（D1 的结论），运行时根本没有"签名"可比。所以它天然不可能查签名，这不是实现偷懒，是**信息不存在**。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 拿它当类型守卫 | 签名不符的类通过检查，后续调用炸 | 只做粗筛；筛完 try/except 兜底 |
| 2 | 忘加装饰器直接 isinstance | `TypeError`（不是 False！） | 看清报错是"不能用"不是"不相等" |
| 3 | 对泛型协议 isinstance | 运行时直接拒绝 | 泛型协议不可运行时检查 |

**面试问法**：*"runtime_checkable 的 isinstance 能保证什么？"*

**30 秒版**："只保证'有这些名字的成员'，不保证签名。我实测过一个签名完全不对的类照样返回 True，因为注解运行时已被丢弃，签名信息根本不存在。所以它只能做动态分发时的粗筛，精确校验靠 mypy 加测试。我项目目前没有一处用它——所有依赖都是构造注入，静态可查。"

**追问链**：

→ *"什么时候才真的需要它？"* 动态加载来的对象：插件注册表、`importlib` 加载的模块、外部传进来的 `object`。

→ *"isinstance True 但调用炸，这算谁的责任？挖到底。"* 这暴露的是"运行时契约检查"这个概念本身不可靠——Python 的动态性意味着任何运行时检查都是**采样**而非**证明**。工业界的应对是把检查前移：类型检查器管静态部分，测试管行为部分，`isinstance` 只在"两条腿都够不着"的动态边界做粗筛。这个分层认知比"记 decorator 用法"高一个档次。

### 7. mypy 的盲区：参数名

**一句话定义**：mypy 做协议匹配时**不比较参数名**，位置调用无事，但任何关键字调用会运行时 `TypeError`。

**为什么存在**：mypy 推不出"调用方会不会用关键字传参"，做严格参数名匹配会大量误报，所以选择了宽松——宽松的代价就是这块完全交给运行时。

**怎么用**（本日实测，先静后炸）：

```python
class Port(Protocol):
    def find(self, doc_id: UUID) -> Row | None: ...

class Impl:
    def find(self, key: UUID) -> Row | None: ...   # 名字不同

p: Port = Impl()          # mypy --strict：Success
p.find(uuid4())           # 运行时 OK（位置传参）
p.find(doc_id=uuid4())    # TypeError: unexpected keyword argument 'doc_id'
```

**底层机制**：Python 的函数签名兼容性在语言层面分两部分——**参数能吃下什么**（类型）和**参数叫什么**（绑定）。`def find(self, key)` 的形参表里根本没有 `doc_id`，关键字绑定自然失败。mypy 的协议匹配只覆盖类型部分；绑定名的信息它有（能看到 `key`），但选择了不比（避免误报），这是**工具的取舍**不是能力缺失。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为 mypy 绿=运行时对 | 关键字调用才炸，且炸点远离定义处 | 实现协议时参数名照抄协议 |
| 2 | 炸了去查 mypy 为什么不报 | 浪费时间找配置开关 | 记住这是已知盲区，靠约定防御 |
| 3 | 给协议参数起缩写名（`k`） | 实现方随手改名没人拦 | 协议参数名用完整业务名，当文档用 |

**面试问法**：*"mypy 全绿就代表运行时没问题吗？"*

**30 秒版**："不代表。我能现场举一个可复现的反例：协议参数叫 doc_id，实现叫 key，mypy 完全放行，但任何 doc_id=xxx 的关键字调用会 TypeError。类型检查覆盖不了参数绑定、cast 的担保错误、Any 传染、运行时类型转换和所有业务逻辑。它的定位是'把某一类错误提前'，不是证明正确，所以测试和变异测试不能省。"

**追问链**：

→ *"还有哪些盲区？"* `cast` 错担保、`Any` 传染、`if/else` 只在部分分支正确、`int()` 截断、`str(bytes)` 得 `"b'x'"`。

→ *"怎么系统性兜住盲区？挖到底。"* 三层：① 类型层——strict 开满 + 禁 `Any` 扩散（D3 的 `disallow_any_explicit` 思路）；② 行为层——测试断言外部可观察行为；③ **门禁有效性层**——这是 W4 变异测试和 D6 注入式验收的意义：不信任"检查全绿"，而是**故意注入已知错误验证检查器会红**。工具互补的链条是：静态分析→测试→变异测试→注入式验收，一层比一层更怀疑上一层。

### 8. `cast` 的使用纪律

**一句话定义**：`cast(T, x)` 是对类型系统的**口头担保**——"我知道 x 是 T"，零运行时开销、零运行时校验。

**为什么存在**：类型系统的信息不完备（第三方 stub 缺失、JSON 解析、框架动态注入）。在"你确实知道得比类型系统多"的边界，需要一个不付运行时代价的显式出口——否则只能写 `# type: ignore` 把整行检查关掉，更糟。

**怎么用**：

```python
# 正当：第三方库 stub 缺失（本项目 security.py 的 jose 返回值）
payload = cast(str, decode_token(token)["sub"])

# 滥用：用 cast 压本该修的契约冲突（第四档坑 2 的模式）
payload = cast("list[Row]", self.snap.load())   # 协议声明 -> object 才被迫这么写
# 正解：把协议声明改成 -> list[Row]，cast 整个删掉
```

**底层机制**：`cast` 在运行时就是 `return x`（CPython 里被特判），唯一作用是给 mypy 一条"此处类型为 T"的指令。正因为零校验，担保错了**没有任何东西拦**——错误延迟到真正使用返回值的那个点才炸，且栈帧离 `cast` 可能很远。它与 `assert isinstance(x, T)` 的区别：后者运行时真的查（可被 `-O` 优化掉），兼具收窄与校验。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 cast 压 `arg-type` | 报告绿，契约冲突还在 | 修签名；cast 不用于掩盖设计冲突 |
| 2 | `cast(str, x)` 而实际可能是 None | 边界输入炸在远处 | 先收窄 Optional 再 cast，或直接 assert |
| 3 | cast 后类型变了忘了同步 | 双处维护 | 尽量缩小 cast 作用域到单行 |

**面试问法**：*"cast 和 type: ignore 什么时候是正当的？"*

**30 秒版**："只在边界——第三方库 stub 缺失、JSON 反序列化、框架动态注入，也就是'我知道得比类型系统多'的地方。我项目里两处 cast 都在 security 和 llm_client，都是 jose 响应解析，每个都配了理由和删除条件。用 cast 压设计冲突是不行的——我第四档题里那个 load 声明成 object 再 cast 回来，正确做法是把协议声明改对，cast 就消失了。"

**追问链**：

→ *"cast 和 assert isinstance 怎么选？"* 需要运行时校验（数据来自外部）→ assert；纯静态信息修正（stub 缺失）→ cast；assert 在 `-O` 下会被剥掉，安全敏感路径不能只靠它。

→ *"你们项目每个 cast 我都能问倒你吗？挖到底。"* 这是 D4 的验收项。当前清单：`security.py` cast(str)——jose 的 `decode_token` 返回 `dict[str, Any]`，取出的值是 Any，cast 到 str 是"我读过签发逻辑知道 sub 是字符串"，删除条件是换库或官方出 stub；`llm_client.py` 同理。`config.py` 的过期 ignore 已在 D1 删掉。**说不出删除条件的 cast = 给未来的自己留的雷**，这是"逃生口要登记"原则。

## 三、30 秒答案集

1. **Protocol 是什么**：只声明能力的类；让 mypy 按"长得像"而不是"血缘"判兼容。替身零继承即可注入。
2. **和 ABC 的区别**：ABC 要显式继承、能提供共享实现；Protocol 不用继承、改不了第三方类也能匹配、运行时默认不可查。
3. **为什么叫结构化类型**：兼容性由"结构"（成员与签名）决定，与"名义"（类名与继承）无关。鸭子类型的静态版。
4. **参数为什么逆变**：实现是消费方，必须吃下调用方按协议可能给的一切——只能更宽，不能更窄。
5. **返回为什么协变**：实现是生产方，调用方按协议使用返回值——只能更具体，不能更含糊。
6. **list 为什么不变**：可写。能往里 append 的容器，类型参数必须严格一致，否则污染原列表。
7. **参数什么时候用 Sequence**：函数只读不写时。调用方传 list/tuple 都行，意图也更清楚。
8. **默认值算契约吗**：算。协议有默认值、实现必填 = 违反"实现只能更宽松"，mypy 直接报 Expected/Got。
9. **runtime_checkable 查什么**：只查成员名存在，不查签名——签名是静态信息，运行时不存在。
10. **mypy 绿 = 对吗**：不。参数名不匹配它就不查，关键字调用运行时 TypeError。类型检查是分类器不是证明器。
11. **协议报"缺方法"先干什么**：先查依赖方用了几个。只用一个 → 拆窄协议，别补空方法。
12. **cast 什么时候正当**：边界处且知道得比类型系统多；每个 cast 要说得出理由和删除条件。

## 四、白板手写靶

**靶 1：协议 + 隐式实现 + 依赖注入（含 Optional 收窄）**

```python
from typing import Protocol
from uuid import UUID

class KBRepo(Protocol):
    def get(self, kb_id: UUID) -> dict[str, object] | None: ...

class FakeKBRepo:
    def __init__(self) -> None:
        self.kbs: dict[UUID, dict[str, object]] = {}

    def get(self, kb_id: UUID) -> dict[str, object] | None:
        return self.kbs.get(kb_id)

class KBService:
    def __init__(self, repo: KBRepo | None = None) -> None:
        self.repo = repo or KBRepository()

    def get(self, kb_id: UUID) -> dict[str, object]:
        row = self.repo.get(kb_id)
        if row is None:
            raise NotFoundError
        return row
```

要点：`FakeKBRepo` **不写任何继承**；返回值收窄靠 `if row is None` 而不是 cast。

**靶 2：逆变/协变四方向判对错**

```python
class Port(Protocol):
    def f(self, k: UUID) -> dict | None: ...
# 实现 g 的参数/返回怎么写能过？
# 参数：UUID→object ✅ ｜ UUID→int ❌
# 返回：dict|None→dict ✅ ｜ dict|None→object ❌
```

要点：记"消费更宽、生产更窄"，两端方向相反。

**靶 3：窄协议拆分**

```python
class DocReader(Protocol):
    def list_by_kb(self, kb_id: UUID, offset: int, limit: int) -> tuple[list[Row], int]: ...

class DocRepo(DocReader, Protocol):   # 第二个 Protocol 不能省
    def create(self, kb_id: UUID, data: DocCreate, *, status: str = ...) -> Row: ...
```

要点：继承协议时基类列表里必须再写 `Protocol`，否则退化成普通类。

## 六、可以讲成故事的三段

**段 1：8 个错误没有一个赖注解**
背景：D1 收尾时 mypy 还剩 8 个 `arg-type`，我默认它们是"注解没写全的尾巴"。→ 我以为是：照着报错修注解就行。→ 实际是：在副本上把修复路径跑完发现，8 个错误对应 3 个**设计问题**——替身漏实现契约、接口对只读服务太胖、项目里有两个重复的 fake。`Protocol` 没有制造错误也没有消灭错误，它把"你血统不对"翻译成"你缺什么"，翻译完我才发现这些都是真问题。→ 教训（可背）：**类型检查的收益不在"改掉报错"，而在"报错暴露设计问题"；压报错等于把设计债藏进更贵的未来。**

**段 2：mypy 绿了，运行时炸了**
背景：验证协议匹配的边界时，我造了一个参数名不同的实现（协议 `doc_id`，实现 `key`）。→ 我以为是：mypy 至少会给个警告，最不济也是"运行时也不报"。→ 实际是：`mypy --strict` 打出 `Success`，而 `p.find(doc_id=...)` 运行时 `TypeError: unexpected keyword argument`。位置调用一切正常，这个雷可以埋到有人第一次用关键字传参。→ 教训（可背）：**类型检查器是分类器，不是证明器；每一层工具都有确定性的盲区，兜盲区的不是更好的工具，是下一层手段（测试→变异→注入验收）。**

**段 3：窄协议让替身一个字没改**
背景：`FakeDocRepo` 报"缺 4 个方法"，我的第一反应是补全。→ 我以为是：替身不完整，补就是了。→ 实际是：数了 `RagService` 的调用点——只用了 `list_by_kb` 一个。缺的不是替身的方法，是协议太胖。拆出只读的 `DocReader` 后，`FakeDocRepo` 零改动通过，而 `DocService` 继续用继承自 `DocReader` 的胖协议，两边都成立。→ 教训（可背）：**看到"缺方法"，一半的概率是接口太宽，不是实现太少；协议内容 = 依赖方需要的最小能力。**

**强项**
1. **变异性四方向全对 + 能识别 ignore 压报错**——第四档坑 1 不止定位到 `str` 参数，还点破了 `# type: ignore[arg-type]` 是共犯，这已经越过"找坑"进入"找掩盖手法"。

**待补**
1. **追问链深处接不住**：`TypeVar(covariant=True)` 的声明和使用限制只能说到名词（知识点 2 追问 3），`Mapping` 的 K 为什么不变只能说到一半（知识点 5 易错 3）——这两处是 D3/D4 的回头客，不急但要登记。
2. **"组合根"一词说不出正式定义**：能指出本项目哪几行是组合根，但被问"组合根集中到什么程度算过度"会卡——W9 引入 `Depends` 工厂时正面补。

**下日预告（D3 · 精准类型）**
1. 会撞 `TypedDict(total=False)` 的陷阱：非 total 键用 `row["title"]` 取值 mypy 放行、运行时 `KeyError`——和今天"mypy 绿运行时炸"同族，但这次解法不是测试，是 `row.get()` + 收窄。
2. 会撞 `overload` 顺序坑：精确分支写在宽分支后面就永远走不到，报错发生在"看不出问题"的地方。
3. `dict[str, Any]` 在协议里到处都是——D3 的主线就是用 `TypedDict` 把它逐个点名，注意 `TypedDict` 也是结构化类型，和今天的 `Protocol` 是一族。
