## 二、逐个知识点讲透

### 1. 门禁四步的职责边界

**一句话定义**：门禁是"一条命令跑完四道关"——ruff check（风格 + bug 模式）、ruff format（格式）、mypy（类型）、pytest + 覆盖率（行为），任一步非零退出就算失败。

**为什么存在**：没有门禁时，交付质量靠"我记得跑过测试"。问题在于**人记不住四个维度**：你跑 pytest 想着逻辑对不对，就不会想 import 排没排序；你对着 ruff 修格式，就不会想类型通不通。四步各管一个维度，缺一维就有盲区——今天的实测就是证据：**5 类类型错误，ruff 一类都没拦住**。

**怎么用**（本项目真实代码，`scripts/check.py`）：

```python
checks = [
    ("ruff check", [sys.executable, "-m", "ruff", "check", *TARGETS, *REVIEWS]),
    ("ruff format --check", [..., "format", "--check", *TARGETS, *REVIEWS]),
    ("mypy", [sys.executable, "-m", "mypy", *TARGETS]),          # ← 今天新增
    (f"pytest + 覆盖率门禁 ({COV_FLOOR}%)", [...pytest..., f"--cov-fail-under={COV_FLOOR}"]),
]
for name, cmd in checks:
    if not step(name, cmd):
        failed.append(name)
```

关键在两个常量，它们的差别就是"什么该被管"：

```python
TARGETS = ["src", "tests", "scripts", "conftest.py"]   # 交付物 → 四步全查
REVIEWS = [str(REPO / "reviews")]                       # 练习题 → 只给 ruff
```

**底层机制**：`subprocess.run(cmd, cwd=ROOT)` 逐个执行，只看 `returncode`。`step()` **不中断**——某步失败也继续跑后面，最后统一列出 `failed` 并以非零退出。这是有意的：一次跑完拿到全部问题，比修一个跑一次快。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 给 mypy 传 `REVIEWS` | 门禁永远红（**48 errors**），最后只好把 mypy 删掉 | 练习题故意写宽类型，`*TARGETS` 单独传 |
| 2 | 本地顺序与 CI 顺序不一致 | 本地"第 3 步红"、CI"第 4 步红"，对不上号 | 两边都写成 ruff → format → mypy → pytest |
| 3 | 只跑 pytest 就叫"验过了" | `import` 排错、类型写错全放过 | 四步跑完才算验 |
| 4 | 加 `--cov-fail-under` 但覆盖率数字是浮点 | 96.5% 被判成低于 95（不会，但 94.9 会） | 门槛取整数，别卡在边界 |
| 5 | 门禁脚本自己没进 ruff/mypy | `scripts/check.py` 语法错到运行时才发现 | `TARGETS` 里带上 `scripts` |

**面试问法**："你们 CI 里跑什么？"
> 30 秒版：四步——lint、格式、类型检查、测试加覆盖率门禁。lint 抓未使用的导入和 bug 模式，mypy 抓类型契约，pytest 抓行为，覆盖率是底线不是目标。一条命令本地能复现，CI 是拆成分步的。

**追问链**：
- → *"为什么要四步，不能只跑测试吗？"* → **测试通过只证明你测到的路径对**。今天实测 5 类类型错误，pytest 有 3 类根本没红（类型错不一定改变行为）。类型错误最典型的表现是"能跑、结果对、下个月接口改了才炸"，只有 mypy 能在写的时候拦。
- → *"哪类错误你的门禁拦不住？"* → 两类：① 主动放弃保护（`str` → `Any`）；② 值语义错误（`x or y` 吞掉 `0`）。前者是类型系统的边界，后者是类型检查器**本来就不管值**。
- → *"线上出了事故要 15 分钟内给结论，门禁能帮什么？"* → 帮不了线上，但能帮"是不是这次改动引入的"：让 CI 在 PR 上分步跑，哪一步红直接指到维度。再配合"注入式验收"证明每一步真的会红，避免出现"门禁绿但漏检"的假安全感。

### 2. 注入式验收：门禁绿 ≠ 门禁有效

**一句话定义**：故意往代码里注入已知错误，看门禁是否变红——红了才算"检查有效"，绿了说明这道关有洞。

**为什么存在**：门禁绿只证明一件事——**当前代码通过了现有检查**。它不证明"检查有能力发现问题"。三个反例都能让门禁绿而毫无保护：规则没开（`select` 里没 `S`）、配置空转（`per-file-ignores` 豁免了未启用的规则族）、路径没覆盖（`REVIEWS` 没进去）。**你无法通过"跑绿"来判断"能不能红"**，只能主动制造红。

**怎么用**（今天做的 5 类，都写进教材 §8.2）：

| # | 注入的错误 | 人类场景 | mypy | ruff |
|---|---|---|---|---|
| 1 | 删 `from __future__ import annotations` | "这行没用，删掉清爽" | **全绿** | 全绿 |
| 2 | `TokenClaims.sub: str` → `sub: Any` | "报错？收成 Any 就过了" | **全绿** | 全绿 |
| 3 | 加一条多余的 `# type: ignore` | "先 ignore 再说" | 1 error | 全绿 |
| 4 | 测试函数漏写 `-> None` | 手写新测试最常见 | 1 error | 全绿 |
| 5 | `create_access_token(subject: str)` → `bytes` | 改契约没同步 | **8 errors in 4 files** | 全绿 |

第 6 类是你自己想的（`x or y`），由 `is None` 对照实验坐实：

```text
=== or 版：mypy Success / ruff All checks passed ===
  空标题 -> '无标题'      ← 合法空串被吞
  page_size=0 -> 20      ← 合法 0 被吞
=== is None 版：同样 mypy Success / ruff 全过 ===
  空标题 -> ''           ← 保留
  page_size=0 -> 0       ← 保留
```

**底层机制**：这件事的正式名字叫**故障注入**（fault injection）。它的自动化形式就是变异测试——程序化地改代码、跑测试、看是否失败。手工注入是人肉版的变异测试，优点是能挑选"人类真实会犯的错"，缺点是不可持续（每次手动改、手动还原）。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 注入完忘了还原 | 下次跑门禁莫名红，或者带着错误提交 | 注入前后都 `git status`，还原后 `git diff` 必须干净 |
| 2 | 只注入一类就收工 | 以为"门禁有效"，其实只验了一条路径 | 至少覆盖：语法/风格类、类型类、行为类各一 |
| 3 | 注入的错误不真实 | 写 `x: int = "abc"` 这种没人会写的错 | 挑"人类真的会犯"的：漏注解、`Any` 降级、`or` 判缺失 |
| 4 | 全绿就当成"代码没问题" | 忽略了"检查没覆盖"这一可能 | 全绿时先问："这个错本来就该被发现吗？" |
| 5 | 注入后只跑 ruff 不跑 mypy | 漏掉类型层面的洞 | 注入一次跑完整门禁 |

**面试问法**："你怎么保证你的检查是有效的？"
> 30 秒版：门禁绿只能证明当前代码通过，不能证明检查有效。所以我定期做注入验收——故意写 5 类人类常犯的类型错误，看门禁红不红。实测有 2 类全绿，一类是 `Any` 降级，一类是 `or` 判缺失，这两类只能靠代码评审兜。

**追问链**：
- → *"为什么门禁拦不住 `str` → `Any`？"* → 因为 `Any` 与所有类型双向兼容：赋给 `str` 合法、调用任意方法合法、返回也合法。类型检查器没法阻止你关掉它自己——就像编译器没法阻止你传 `--no-verify`。
- → *"那这 2 类漏检会造成什么后果？"* → `Any` 降级后 `pydantic` 的必填校验还在，所以**运行时看起来一切正常**，但下游所有类型保护失效；`or` 判缺失则是直接吞掉合法值（`page_size=0` 变成 20），属于"配置改了不生效"这类最难查的故障。
- → *"在你项目里怎么补这两类？"* → ① `Any` 必须带原因注释 + 定期 `grep -rn ": Any" src/` 清点（D1 已定"`Any` 要登记"）；② `or` 判缺失写进代码评审清单，同时在测试里加"空值/零值"用例——这类 bug 只有测试能拦。AI 场景同理：模型返回的字段为空串是合法值，用 `or` 兜默认会把"模型确实返回了空"变成"模型没返回"，导致重试逻辑误判。

### 3. `Any` 降级是门禁拦不住的自我拆台

**一句话定义**：把注解从具体类型改成 `Any`，mypy 会完全静默——不是"修好了报错"，是"关掉了检查"。

**为什么存在**：这是人类面对类型报错时最省力的解法。`sub: str` 报错？改 `sub: Any`，一秒绿。代价是**下游全部失控**：`deps.py` 里 `UUID(str(sub))` 拿到的 `Any` 可以喂给任何函数、调用任何方法，mypy 一句话不说。更阴的是 pydantic 的运行时校验还在（`sub` 仍是必填），所以**接口测试全过、行为完全正常**，只有到了生产环境某个分支才炸。

**怎么用**：`Any` 不是禁用，是**必须登记**。项目里的规则（D1 定的）：

```python
# 允许：库的类型缺口，且有据可查
# jose 没有 stub，jwt.encode 在 mypy 眼里是 Any。
# cast 是收敛库缺口，零运行时开销。
return cast(str, jwt.encode(payload, settings.secret_key, algorithm=settings.algorithm))

# 不允许：数据校验缺口，用 Any 掩盖
def get_title(row: dict[str, object]) -> Any:   # ← 下游全部失守
    return row.get("title")
```

判别只有一句：**`Any` 是库给的还是数据来的？** 库给的用 `cast` 收敛；数据来的必须 `model_validate`。

**底层机制**：mypy 的类型系统里，`Any` 是"一致性逃逸舱"（consistent with anything）——它同时是所有类型的子类型和父类型。任何涉及 `Any` 的表达式，结果也是 `Any`，所以错误会**沿着赋值链一路传下去，直到某个非 `Any` 的边界才爆**。这就是"污染"：报错位置和真正的错误位置相隔很远，栈里看不到源头。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 用 `Any` 消报错 | mypy 立刻绿，但下游全裸奔 | 先问"这个值从哪来"，来自数据就 `model_validate` |
| 2 | 以为 `Any` = "未知类型" | 语义上被当成"运行时才知道" | `Any` 的真实含义是"不检查"，未知类型应该用泛型或 `object` |
| 3 | 用 `cast` 代替 `Any` 就以为安全 | `cast(str, 123)` 运行时返回 `123` | `cast` 只骗检查器，零校验（D4 已实测） |
| 4 | 忘了 pydantic 还在校验 | "接口测试全过，应该没事" | 运行时校验 ≠ 静态类型保护，二者管不同阶段 |
| 5 | `Any` 传染后仍按"类型安全"写代码 | 以为 mypy 会兜底 | 凡有 `Any` 的地方，mypy 都不再兜 |

**面试问法**："mypy 全绿就代表没类型 bug 吗？"
> 30 秒版：不代表。`Any` 会让检查器完全静默，所以"全绿"只说明"没有在检查范围内发现问题"。我实测过把必填字段 `sub: str` 改成 `sub: Any`，mypy 零报错，但下游全部失守。所以 `Any` 在我们项目里必须带原因登记。

**追问链**：
- → *"`Any` 和 `object` 有什么区别？"* → 都是"什么都能装"，但 `object` 装进去之后**不能随便调**（要先 `isinstance` 收窄），`Any` 装进去之后**什么都能调**。所以 `object` 是安全的宽，`Any` 是危险的宽。
- → *"那为什么 `str` 改成 `Any` 门禁不报？"* → 因为语法合法、类型也合法（`Any` 与 `str` 兼容）。类型检查器只能检查"你说的类型自不自洽"，不能检查"你说的类型是不是你想要的"——**意图无法静态验证**。
- → *"AI 生成的代码里 `Any` 特别多，你怎么处理？"* → 把它们当"待审清单"而不是"已完成"：每个 `Any` 追到来源（库缺口 / 外部数据 / 懒得写），库缺口留 `cast` + 注释，外部数据换 pydantic 模型，懒得写的退回重写。这条是 2026 面试的新追问点——"AI 写的代码你怎么验"。

### 4. `x or y` 判缺失：类型系统的值语义盲区

**一句话定义**：`or` 判断的是 **falsy**，不是 `None`——`0`、`""`、`{}`、`[]`、`False` 都会被当成"缺失"。

**为什么存在**：Python 的 truthiness 规则让"空"和"无"混为一谈，这在脚本里很顺手（`name = arg or "default"`），在业务代码里是灾难。因为业务上"用户填了空标题"和"用户没填标题"是两件事，"配置 `page_size=0` 表示不分页"和"没配置"也是两件事。`or` 把这两件事压成一件。

**怎么用**：

```python
# ❌ 吞掉合法值
title = payload.get("title") or "无标题"        # title="" 被吞
size = int(raw) if raw else 20                  # raw="0" 被吞

# ✅ 只判 None
title = "无标题" if title is None else title
size = 20 if raw is None else int(raw)
```

判据一句话：**`or` 只在"所有 falsy 值都等价于缺失"时安全**。`page_size` 的 `0` 是合法值，就不安全。

**底层机制**：`x or y` 的执行是 `bool(x)` 为真则返回 `x`，否则返回 `y`。`bool()` 走 `__bool__`，没有则退到 `__len__`——所以容器类型的"空"天然是 falsy。**类型层面**：`str | None` 和 `str` 做 `or`，结果类型是 `str`（`None` 被排除），mypy 认为完全正确，于是全绿。**值层面**：`"" or "默认"` 返回 `"默认"`，与类型系统无关。这就是今天对照实验里"两种写法 mypy 都 Success、运行时结果完全不同"的原因。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | `payload.get(k) or default` | 空串/0/空 dict 被当缺失 | `is None` 判据 |
| 2 | `int(raw) if raw else DEFAULT` | `"0"` 被吞，配置失效 | 先判 `raw is None`，再转换 |
| 3 | `x = a or b or c` 多级兜底 | 中间某一级为 falsy 就跳过，逻辑静默错 | 显式 `if ... is None` 链 |
| 4 | 类型注解看起来完全正确 | mypy 全绿，给假安全感 | 值语义问题只能靠测试，不能靠类型 |
| 5 | `if not value:` 判"没传" | 同 1，`0`/`""` 也算没传 | 区分"没传（None）"和"传了空值" |

**面试问法**："Python 里怎么判断一个参数有没有传？"
> 30 秒版：一律用 `is None`，不用 `or` 也不用 `not`。因为 `0`、`""`、`{}`、`[]` 都是 falsy，用 `or` 会把合法的空值和零值当成没传。这个区分在配置项上最要命——`page_size=0` 往往表示不分页。

**追问链**：
- → *"为什么 mypy 不报？"* → `or` 的结果类型是两边的 join：`str | None` 或 `str` 得到 `str`，类型上完全正确。类型检查器**只检查类型，不检查值**，`""` 和 `"abc"` 在类型上没区别。
- → *"这种 bug 大概多久能发现？"* → 可能永远发现不了。它不抛异常、不报错，只是"某个配置不生效"。今天这个 `page_size=0` 的例子，症状是"请求了 100 条却只返回 20 条"，排查时第一反应是查数据库和分页 SQL，很少有人会回头看这一行。
- → *"AI 应用里哪里会撞这个？"* → 模型返回的字段用 `or` 兜默认值。比如 `answer = resp.get("content") or "抱歉"`，模型真的返回空串（合法的"无内容"）会被伪装成"调用失败"，下游的重试/降级逻辑就会误触发，成本和延迟一起上去。正确做法是先判 `is None`（真没这个字段），再单独处理空串。

### 5. 契约变更的连锁代价

**一句话定义**：改一个函数的参数类型或返回类型，等于改所有调用点的契约；mypy 会一次性列出全部受影响处。

**为什么存在**：动态语言里"改签名"最危险的地方是**调用点不会报错**。D4 你把 `decode_access_token` 的返回值从 `dict` 改成 `TokenClaims`，`deps.py` 改了，但测试里还有 3 处 `payload["sub"]`——pytest 报 3 个 TypeError 时你才知道。静态检查的价值就是把这件事**提前到写代码的时候**，而且一次全给。

**怎么用**（教材 §8.2 第 5 类的实测）：

```text
=== 5 参数类型写错 str->bytes ===
  mypy exit=1: Found 8 errors in 4 files (checked 45 source files)
```

改 `create_access_token(subject: str)` 一个字符，4 个文件 8 处报错。这不是噪音，这是**mypy 帮你把所有调用点找出来了**。改对之后，所有调用点自动同步。

**底层机制**：mypy 先建符号表（每个函数的名字 + 完整签名），再对每个调用表达式检查实参类型是否 `consistent-with` 形参类型，返回类型是否满足使用处的期望。所以一次分析就能扫全仓库——这也是为什么它慢（0.96s 扫 48 个文件）但值得。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只改实现不改调用方 | 测试挂一片，或者运行时 `KeyError` | 改完立刻跑 mypy，按报错逐个改 |
| 2 | 用 `cast` 压掉调用点的错 | 报错消失，运行时照炸 | `cast` 只用在"库缺口"，不用在"我懒得改" |
| 3 | 加 `# type: ignore` 而不是改调用 | 技术债累积，下次改更痛 | ignore 必带 code + 理由，且登记 TODO |
| 4 | 只改 src 忘了 tests | pytest 红一片才知道 | `TARGETS` 里必须有 `tests` |
| 5 | 改返回值类型但保留旧字段访问 | `payload["sub"]` 在模型上不可下标 | 属性访问 `payload.sub`，让 mypy 帮你找 |

**面试问法**："你怎么保证重构不破坏调用方？"
> 30 秒版：两件事——静态检查和测试，缺一不可。静态检查保证"类型上所有调用点都被找到了"，测试保证"行为没变"。我昨天把鉴权函数的返回值从 dict 改成 pydantic 模型，mypy 立刻列出 3 个失效的下标访问，pytest 又抓出 3 个测试没跟着改。

**追问链**：
- → *"静态检查能找出全部调用点吗？"* → 类型层面能，动态层面不能。`getattr(obj, name)`、反射、字符串拼出来的调用，mypy 看不见。所以还必须有测试兜行为。
- → *"如果调用点太多，改不动怎么办？"* → 加一层适配器/重载，让新旧签名共存，逐步迁移。或者用 overload 提供兼容签名，内部转成新类型——但这是过渡手段，要有明确的清理计划。
- → *"AI 写的大量代码里，你改了公共函数会怎样？"* → 最容易出的问题就是"AI 只改了它看得见的那几个文件"。所以必须靠门禁：mypy 扫全仓库 + 测试覆盖率。**这也是我坚持把 mypy 接进门禁的原因**——AI 的改动范围和人的注意力不匹配，只有工具能对齐。

### 6. 变异测试：覆盖率证明不了断言强度

**一句话定义**：变异测试是自动改一处代码逻辑（`<=` 改 `<`、`+` 改 `-`），跑测试看是否失败；失败=变异体被"杀死"，说明测试有效。

**为什么存在**：覆盖率只回答一个问题——**这行代码被执行过吗**。它不回答"这行代码写错了测试会发现吗"。极端例子：一个函数写了 20 行，测试里只调一次不写任何断言，覆盖率 100%，但任何 bug 都拦不住。变异测试是唯一能证明"断言有杀伤力"的自动化手段。

**怎么用**（本项目 `scripts/mutation_check.py`，今天实测）：

```text
=== 变异检查 ===
基线：先确认原始代码是绿的 …… 绿
[杀死] 分页偏移少减 1（第二页开始全错）
[杀死] 删除文档时计数方向反了
[杀死] 边界从 <= 放宽成 <（零长度不再拦）
[杀死] 边界漏掉等号（overlap == chunk_size 会死循环风险）
[杀死] 空块不再过滤（切出空字符串也塞进结果）
变异得分：5/5 = 100%
```

**底层机制**：读源码 → 按预设规则做字符串替换 → 写回 → 跑 pytest → 测试失败则"杀死"（好），测试通过则"存活"（坏，说明这个逻辑没有断言保护）→ 还原。所以它是**工具层面的注入式验收**：和今天手工注入 5 类错误是同一件事，只是自动化 + 挑的是逻辑变异而不是类型变异。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 把覆盖率当质量指标 | 覆盖率 97%，变异得分 40% | 覆盖率是底线，变异得分才反映断言强度 |
| 2 | 断言只写"不抛异常" | 变异体全部存活 | 断言必须校验具体值/状态 |
| 3 | 变异体选得假 | 改成一眼能看出的错，测试当然抓到 | 选"语义接近但结果不同"的边界变异 |
| 4 | 变异测试进每次 CI | CI 时间翻几倍 | 放 nightly 或本地手动跑（`--mutation`） |
| 5 | 基线不绿就跑 | 全部变异体"杀死"，得分虚高 | 先断言原始代码通过，再变异 |

**面试问法**："覆盖率怎么算？95% 就够了吗？"
> 30 秒版：覆盖率是行/分支被执行的比例，95% 是团队定的底线，不是质量证明。真正验证测试有没有杀伤力要用变异测试——自动改代码逻辑看测试会不会失败。我们项目 5 个变异体全被杀，才算"这条路径的测试真的有效"。

**追问链**：
- → *"变异测试和覆盖率的关系？"* → 覆盖率是必要条件，变异得分是充分性证据。覆盖率高但变异得分低，说明"代码跑到了但没校验"；覆盖率低时变异得分通常也不会高（那部分逻辑压根没跑）。
- → *"变异得分 100% 说明什么？"* → 只说明"这 5 个变异体都被抓到了"，不说明"所有 bug 都能抓到"。变异体的选取决定了它的覆盖范围——今天这 5 个都在分页和切块逻辑上，别的模块没变异体就不在证明范围内。
- → *"AI 生成的测试怎么验质量？"* → 这是变异测试最实用的场景：AI 特别喜欢写"能跑通就算过"的测试（没有断言、或者只断言 `status_code == 200`）。把 AI 写的测试拿去跑变异，存活率高就说明它只是在"执行代码"而不是"验证行为"。

### 7. CI 分步 + `pipefail`

**一句话定义**：CI 里把门禁拆成多个命名 step，每个 step 用 `set -o pipefail` + `| tee` + 失败时输出一条多行注解。

**为什么存在**：两个独立的问题。① **定位**：本地一条命令红了只知道"红了"，CI 拆成 step 后，"哪一层红"由 step 名字直接给出（ruff check / format / mypy / pytest）。② **退出码被吞**：`cmd | tee log` 的退出码是 `tee` 的（永远 0），所以失败的步骤会被报成绿——这是 CI 里最经典的"假绿"。

**怎么用**（`ci.yml` 今天的 mypy step）：

```yaml
- name: mypy
  run: |
    set -o pipefail
    uv run python -m mypy src tests scripts conftest.py 2>&1 | tee /tmp/step.log || {
      MSG=$(tail -30 /tmp/step.log | sed -e 's/\r$//' -e 's/%/%25/g' | sed -e ':a' -e 'N' -e '$!ba' -e 's/\n/%0A/g')
      echo "::error title=mypy failed::${MSG}"
      exit 1
    }
```

三件事各管一件事：`pipefail` 让管道返回第一个非零退出码；`tee` 保留完整日志；`%0A` 把多行折成一条注解（GitHub 每个 check run 只展示前 10 条，逐行 echo 会被挤掉）。

**底层机制**：POSIX 规定管道的退出码是**最后一个命令的退出码**。`cmd | tee log` 里最后一个命令是 `tee`，它只要写成功就返回 0，于是 `cmd` 失败被完全掩盖。`set -o pipefail` 改规则：管道中任一命令非零，整个管道返回最右边那个非零码。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | `\| tee` 不加 `pipefail` | 红步骤被报成绿，最危险 | 用了 `\| tee` 必加 `set -o pipefail` |
| 2 | 一行一条 `echo "::error"` | 只显示前 10 条，关键信息被挤掉 | `tail -N` + `%0A` 折成一条 |
| 3 | 本地一条命令、CI 分步但顺序不一致 | 本地第 3 步红、CI 第 4 步红 | 两边顺序写成一样 |
| 4 | `tee` 不落盘 / 路径不可写 | 失败时没有日志可 tail | 用 `/tmp/step.log`，别用仓库内路径 |
| 5 | 把 `check.py` 直接塞进 CI 一个 step | 红了不知道哪层 | 分步跑（本地保留一条命令的便利） |

**面试问法**："CI 红了，你怎么定位？"
> 30 秒版：先看是哪个 step 红的——我们 CI 是分步的，step 名字就是维度。然后用注解里的日志定位到文件和行。如果出现"本地绿、CI 红"，第一步是比对版本：CI 的 Environment step 会把 Python 和工具版本打进日志。还有一个坑是管道吞退出码，用了 `tee` 必须加 `pipefail`，不然失败会被报成绿。

**追问链**：
- → *"为什么要分步，不能一条命令跑完吗？"* → 分步不是为了跑得快，是为了**失败可归因**。一条命令的失败信息是一堆日志，分步的失败信息是 step 名字 + 那一步的 tail。调试成本差一个数量级。
- → *"`pipefail` 不加会怎样？给我一个具体场景。"* → 加 mypy 那一步，如果没加 `pipefail`，mypy 报 48 errors 但 `tee` 成功写日志返回 0，整步报绿——于是 PR 带着类型错误合并，直到某个下游服务炸了才回头查。
- → *"CI 里除了跑门禁，还该加什么？"* → 三样：① 环境版本打日志（排查"本地绿 CI 红"的第一手证据）；② 失败诊断步骤（`if: failure()` 时直接 import 模块，绕开 pytest 的包装异常）；③ 变异测试（放 nightly，证明测试有杀伤力）。

### 8. `strict = true` 到底开了什么

**一句话定义**：mypy 的 `strict = true` 不是"打开严格模式"一个开关，而是十几个具体检查项的集合，包括 `no-any-return`、`disallow-untyped-defs`、`warn-unreachable` 等。

**为什么存在**：不打开的话，mypy 只做"最低限度的一致性检查"——大量 `Any`、未注解函数、隐式 Optional 都会放过。但打开之后，每条报错都对应一个具体规则，**不知道规则名字就不知道该怎么修**。今天最典型的坑就是 `no-any-return`。

**怎么用**（D4 的实战，我判错过一次）：

```python
def create_access_token(subject: str) -> str:
    return jwt.encode(payload, settings.secret_key, algorithm=settings.algorithm)
```

`jwt.encode` 在 mypy 眼里返回 `Any`（jose 没有 stub）。我一度以为"函数签名已经声明 `-> str`，Any 赋给 str 是合法的，不需要 cast"——**错**。门禁当场报：

```text
security.py:50: error: Returning Any from function declared to return "str"  [no-any-return]
```

`no-any-return` 专门拦"return 一个 Any"，签名声明挡不住它。正确写法是 `return cast(str, jwt.encode(...))`。

**底层机制**：`strict = true` 等价于同时开启：

```text
--disallow-untyped-defs          # 函数必须有完整注解
--disallow-incomplete-defs       # 不能只注一半
--disallow-untyped-calls         # 不能调未注解的函数
--warn-return-any                # return Any 报警（就是 no-any-return）
--warn-unused-ignores            # 多余的 type: ignore 报警
--no-implicit-optional           # def f(x: str = None) 报错
--strict-equality                # 不兼容类型比较报警
...（十余项）
```

所以"开 strict"= 接受这十几条约束。记不住全部没关系，**看到错误码去查规则名**是最实用的路径。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 以为签名声明能挡 `Any` 返回 | 删了 cast，门禁报 `[no-any-return]` | 库返回 `Any` 就用 `cast` 收敛 |
| 2 | 用 `Any` 消 `no-any-return` | 报错消失，保护也没了 | 用 `cast` 或 `assert isinstance` |
| 3 | 多余的 `type: ignore` | `[unused-ignore]` 又报一条 | ignore 用完要清理，或加 `warn_unused_ignores=false`（不推荐） |
| 4 | 只注了一半（参数注了返回没注） | `[no-untyped-def]` | 函数头整体注解 |
| 5 | 以为 `strict` 能抓逻辑错 | 值语义 bug（`or` 吞 0）全绿 | `strict` 只管类型，不管值 |

**面试问法**："mypy strict 模式踩过什么坑？"
> 30 秒版：`no-any-return` 最常撞——库函数返回 `Any`（比如没有 stub 的 JWT 库），你写 `-> str` 直接 return 会被拦，必须 `cast`。踩过之后我才明白：`strict` 不是"更严格地检查我写的类型"，它还会检查"你有没有偷偷用 `Any` 溜过去"。

**追问链**：
- → *"`cast` 和 `# type: ignore` 有什么区别？"* → `cast` 是**声明一个更窄的类型**，检查器继续按新类型检查下游；`ignore` 是**关掉这一行的检查**，下游仍按原类型。所以 `cast` 保留保护，`ignore` 放弃保护。
- → *"那什么时候可以用 `ignore`？"* → 库的类型标注本身错了（且无法升级），或者 Python 版本差异导致的误报。必须带 `[code]` 和理由注释，并登记 TODO——因为 `strict` 会报 `unused-ignore`，修好了不删会二次报错。
- → *"AI 生成代码时大量用 `ignore` 消错，你怎么看？"* → 这是比 `Any` 更糟的信号：它说明 AI 在"让门禁变绿"而不是"让代码变对"。我的做法是给 `ignore` 加数量上限（比如 5 条），超了就停下来人工过一遍——数量本身就是"质量债"的度量。

### 9. `select` / `per-file-ignores` / 死配置

**一句话定义**：`select` 决定启用哪些规则族，`per-file-ignores` 按路径豁免特定规则；两者组合可能出现"豁免了一条从未启用的规则"的死配置。

**为什么存在**：不同目录标准不同——`tests/` 里 `assert` 是 pytest 的标准写法，`src/` 里 `assert` 应该被拦（生产代码的 assert 会被 `-O` 优化掉）。所以需要按路径豁免。问题在于：**豁免写下了，但对应规则族没启用，它就永远不生效，而且没有任何工具会提醒你**。

**怎么用**（今天实验 4 的完整因果，这是我说反过的那条）：

原来的配置是：

```toml
select = ["E", "F", "I", "UP", "B", "SIM", "RUF", "ASYNC", "PT"]   # ← 没有 S
[tool.ruff.lint.per-file-ignores]
"tests/*" = ["S101"]                                                 # ← 豁免一条没启用的规则
```

因为 `select` 里没有 `S` 族，`S101`（assert 检测）从来没被启用过，这条豁免就是死配置。删掉它**当前不改变任何行为**——ruff 依然全绿。

但实验 4 暴露了代价：**加上 `S` 之后**，因为豁免已经被删，`tests/` 里的 `assert` 全部被拦：

```text
Found 99 errors.
     26 tests/test_kb_api.py
     14 tests/test_kb_service_unit.py
     13 tests/test_doc_service.py
     12 tests/test_rag_async.py
     10 tests/test_config.py
      6 tests/test_health.py
      5 tests/test_llm_client.py
      5 tests/test_jwt_expiry.py
```

99 条 `S101 Use of assert detected`，全在 `tests/` 下。

**底层机制**：ruff 的检查分两阶段——先按 `select`/`ignore` 收集诊断，再按 `per-file-ignores` 的 glob 匹配路径做过滤。所以豁免只对"已经被收集到的诊断"起作用。规则族没启用 → 没有诊断 → 豁免空转。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 豁免未启用的规则族 | 死配置，永不生效且无人提醒 | 用 `--select <族>` 反查一次，确认这条豁免真的有用 |
| 2 | 删死配置当"清理"，不问代价 | 将来有人加 `S` 时 tests 全红、且不知原因 | 删可以，但要留注释说明"加 S 前先补回豁免" |
| 3 | 裸 `# noqa` | 屏蔽整行未来所有规则 | 必带 code + 理由 |
| 4 | `per-file-ignores` 的 glob 写错 | 以为豁免了实际没豁免 | 用 `ruff check --select S101 tests/` 验证 |
| 5 | 全局 `ignore` 里堆规则 | 整个项目永久失守 | 优先按路径豁免，别全局关 |

**面试问法**："你怎么看 lint 规则全开？"
> 30 秒版：全开不现实，规则之间有冲突，且中文项目会被全角标点规则刷屏（`RUF001-003`）。我们的做法是选九个规则族 + 按路径豁免：`tests/` 允许 assert，`src/` 不允许。关键是每条豁免都要能反查——死配置比没配置更危险，因为它给了假安全感。

**追问链**：
- → *"怎么发现死配置？"* → 反查：`ruff check --select <族> <路径>`。如果开启后一条都不报，说明那条豁免在保护空气。今天实测加 `S` 后 99 条，证明这 99 条 assert 一直是"没人管"的状态。
- → *"那删了它是不是更好？"* → 分两种。如果确定永不启用 `S`，删掉更干净；如果将来可能启用（安全规则对大项目很有价值），**保留 + 注释**更稳。今天做了前者，代价是"加 S 时会突然红 99 条"——这个代价必须写下来，否则下次加 S 的人会懵。
- → *"CI 里怎么防止这类问题再出现？"* → 定期（比如每季度）跑一次"全集检查"：`ruff check --select ALL`，把报告 diff 一次。不是为了全开，是为了知道"我们关掉了什么"。这个思路和"`Any` 要登记"是同一件事——**关闭保护必须是有意识的决定，不是默认状态**。

### 10. `--fix` 三连与 `noqa` 的正当用法

**一句话定义**：`ruff check --fix` 会自动修可修复的问题，但修一条可能引入另一条，所以必须 `--diff` 看 → `--fix` 修 → `format` 对齐 → `check` 复跑。

**为什么存在**：ruff 的规则是独立判断的，修 A 可能让 B 从不合规变成不合规。教材 §5 的实测：删掉未使用的 `import`（F401）之后，import 块的排序变了，触发 `I001`。如果你只跑一次 `--fix` 就以为搞定，门禁还是红。

**怎么用**：

```powershell
# Windows PowerShell —— 三连
& .\.venv\Scripts\ruff.exe check --diff src tests          # 1. 先看会改什么
& .\.venv\Scripts\ruff.exe check --fix src tests           # 2. 修
& .\.venv\Scripts\ruff.exe format src tests                # 3. 对齐格式
& .\.venv\Scripts\ruff.exe check src tests                 # 4. 复跑确认
```

```bash
# Git Bash / Linux / macOS
./.venv/Scripts/ruff.exe check --diff src tests
./.venv/Scripts/ruff.exe check --fix src tests
./.venv/Scripts/ruff.exe format src tests
./.venv/Scripts/ruff.exe check src tests
```

**底层机制**：`--fix` 是迭代的——修完一轮重新分析，还有可修的继续修，直到没有。但 `format` 是独立通道（它不管 lint 规则），所以 `--fix` 改变了缩进/换行后，必须再 `format` 一次让两者都满足。

**易错点**：

| # | 坑 | 症状 | 正解 |
|---|---|---|---|
| 1 | 只 `--fix` 不复跑 | 修了 F401 引入 I001，门禁还红 | 三连：fix → format → check |
| 2 | 不看 `--diff` 直接 `--fix` | 一次改了 20 个文件，看不出意外改动 | 先 `--diff`，尤其跨模块重构时 |
| 3 | 用 `--unsafe-fixes` | 语义被改（比如把 `x == None` 改成 `x is None` 之外的东西） | 只在明确知道风险时用，且必看 diff |
| 4 | 裸 `# noqa` | 屏蔽整行所有规则，未来问题全隐形 | `# noqa: E501  理由` |
| 5 | `noqa` 写在错误的行 | 行号错位，没屏蔽到目标 | 写在问题行末，不复用 |

**面试问法**："你们 lint 怎么落地？"
> 30 秒版：ruff 进 pre-commit，提交时自动跑，不过就拦。CI 里再跑一次全量，防止有人 skip hook。`--fix` 用得克制——先 `--diff` 看改动，修完再 `format` 再 `check` 复跑，因为它会连锁。`noqa` 必须带规则码和理由，不然下个人不敢动那行。

**追问链**：
- → *"pre-commit 和 CI 都跑 lint，不重复吗？"* → 不重复，是两道防线。pre-commit 是本地快速反馈（只跑改动的文件），CI 是全量 + 不可跳过。`--no-verify` 能绕过前者，绕不过后者。
- → *"`--fix` 改坏了代码怎么办？"* → 三个保险：① 先 `--diff` 看清改动；② 不用 `--unsafe-fixes`；③ 改完立刻跑门禁（测试 + mypy），语义错误会被拦。最坏情况 `git checkout` 重来。
- → *"如果 AI 一次提交了 50 个文件的全量 `--fix`，你怎么审？"* → 直接拒绝。这类提交无法 review，也无法 blame。正确做法是按目录分批、每批一个语义边界（比如"只修 import 排序"），让 diff 可读。**这本身就是一个工程判断力问题**，比会不会跑命令重要。

## 三、30 秒答案集（合上文档能背）

1. **门禁四步**：lint 抓风格和 bug 模式，format 抓格式，mypy 抓类型，pytest + 覆盖率抓行为。缺一维就有盲区。
2. **门禁绿 ≠ 有效**：绿只证明当前代码通过，不证明检查能发现问题。要证明，只能故意写错看它红。
3. **5 类注入 2 类漏**：`Any` 降级、`or` 判缺失，mypy 全绿。前者是类型系统边界，后者是它本来就不管值。
4. **`Any` 是关闭检查**：与所有类型双向兼容，赋值调用返回全合法，还能传染。用 `Any` 消错等于自拆防线。
5. **`or` 判缺失吞值**：`0`、`""`、`{}`、`[]` 都是 falsy。判缺失只有 `is None`。
6. **契约变更代价**：改一个参数类型，实测 8 errors in 4 files。mypy 帮你把全部调用点列出来，这是接它进门禁的最大收益。
7. **覆盖率高 ≠ 断言强**：覆盖率证明"执行过"，变异测试证明"错了会被发现"。我们 5 个变异体全被杀。
8. **管道吞退出码**：`cmd | tee log` 的退出码是 `tee` 的（永远 0）。用了 `tee` 必加 `set -o pipefail`。
9. **`no-any-return`**：`strict` 下 `return` 一个 `Any` 会被拦，签名声明挡不住。库缺口用 `cast` 收敛。
10. **死配置**：豁免了未启用的规则族，永不生效且无人提醒。加 `S` 后 tests 立刻 99 条 `S101`。
11. **关闭保护要有意识**：`Any` 要登记、豁免要能反查、`noqa` 要带码和理由。默认状态不该是"全关"。
12. **`--fix` 会连锁**：修 F401 触发 I001。三连是 `--diff` → `--fix` → `format` → `check`。

## 四、白板手写靶

### 靶 1：门禁脚本骨架

```python
checks = [
    ("ruff check", [sys.executable, "-m", "ruff", "check", *TARGETS, *REVIEWS]),
    ("ruff format", [sys.executable, "-m", "ruff", "format", "--check", *TARGETS, *REVIEWS]),
    ("mypy", [sys.executable, "-m", "mypy", *TARGETS]),           # 不带 REVIEWS
    ("pytest", [sys.executable, "-m", "pytest", "--cov", f"--cov-fail-under={COV_FLOOR}"]),
]
failed = [name for name, cmd in checks if not step(name, cmd)]
return 1 if failed else 0
```

> 要点：`mypy` 那行**只传 `TARGETS`**，`REVIEWS` 只给 ruff。

### 靶 2：CI 单步模板

```yaml
- name: mypy
  run: |
    set -o pipefail
    uv run python -m mypy src tests scripts conftest.py 2>&1 | tee /tmp/step.log || {
      MSG=$(tail -30 /tmp/step.log | sed -e 's/\r$//' -e 's/%/%25/g' | sed -e ':a' -e 'N' -e '$!ba' -e 's/\n/%0A/g')
      echo "::error title=mypy failed::${MSG}"
      exit 1
    }
```

> 要点：`set -o pipefail` 必须在管道**之前**，写在同一个 `run` 块里。

### 靶 3：`or` vs `is None`

```python
# ❌
title = payload.get("title") or "无标题"
size = int(raw) if raw else 20

# ✅
raw_title = payload.get("title")
title = "无标题" if raw_title is None else str(raw_title)
size = 20 if raw is None else int(raw)
```

> 要点：`or` 判断的是 truthiness，`is None` 判断的是缺失。`0` 和 `""` 是合法值。

## 六、可以讲成故事的三段

### 故事 1：门禁绿了，然后呢

背景是我一直觉得"门禁全绿"就等于"代码没问题"，直到今天我故意写错了 5 处类型。
我以为是"随便写错一处，门禁立刻就红"。
实际是 5 类里有 2 类全绿——把必填字段 `str` 改成 `Any`，mypy 一句话不说；用 `or` 判缺失，mypy 和 ruff 双双通过，运行时却把合法的 `page_size=0` 换成 20。
教训：**自动化能覆盖 80%，剩下 20% 靠评审和约定。真正的危险是以为自动化覆盖了 100%。**

### 故事 2：99 条 assert

背景是我想清理一条"死配置"——`per-file-ignores` 里豁免了 `S101`，但 `select` 里根本没有 `S` 族，所以它从来没生效过。
我以为是"删掉它没有任何影响"，删完 ruff 确实还是全绿，我更确信了。
实际是我做实验往 `select` 里加了 `S` 之后，**99 条 `S101` 一次性爆出来，全部在 `tests/` 下**——因为那个"没用"的豁免，正是保护这 99 个 assert 的唯一一道网。
教训：**死配置的"死"往往是因为依赖的条件没满足，不是因为它没价值。删之前先问"它在等什么条件"。**

### 故事 3：我判错了一次 `cast`

背景是我在给 JWT 的 `encode` 收类型，`jose` 没有 stub，返回值全是 `Any`。
我以为"函数签名已经写了 `-> str`，`Any` 赋给 `str` 是合法的，所以不需要 `cast`"，还把这句写进了代码注释。
实际是我删掉 `cast` 之后门禁立刻报 `[no-any-return]`——`strict` 模式下 `return` 一个 `Any` 会被专门拦，签名声明挡不住它。
教训：**`strict` 不是"更严格地检查我写的类型"，它还会检查"你有没有偷偷用 `Any` 溜过去"。**
