## 三、正文文案（小红书版，约 280 字）

给 5000 行的表写了个查询，90% 的行都命中，我顺手建了索引。

EXPLAIN 一看：type=index，走索引了，很完美。

然后我去数这把 UPDATE 加了多少把锁——5039 个，清一色挂在主键上。

这个锁形只有全表扫描才有。也就是说：EXPLAIN 说走了索引，实际执行根本没走。

我不信 EXPLAIN 会骗人，于是用 Handler 计数器验尸：

FLUSH STATUS，执行语句，再看 SHOW SESSION STATUS LIKE 'Handler_read%'。

Handler_read_rnd_next = 5001，Handler_read_next = 0。

顺着全表读了 5001 行，沿索引读 0 次。实锤：优化器在执行时放弃了索引。

为什么？90% 命中率下，走二级索引要回表 4500 次随机 IO，全表顺序扫反而更便宜。优化器没算错，只是 EXPLAIN 展示的计划和真正执行的计划可以不是同一个。

记住这句：EXPLAIN 是意图，Handler 是事实。验证 SQL 到底怎么跑的，别只看 EXPLAIN。
